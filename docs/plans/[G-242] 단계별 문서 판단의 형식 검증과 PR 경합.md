## Purpose

원격에 직접 반영된 프로젝트 일반 planning과 ExecPlan 실행 대응의 분리를 유지하면서 DOCUMENT_RESULT의 엄격한 의미 검증과 legacy 개정 후보의 게시 직전 실제 PR 출현 처리를 보완한다. 현재 새 실행 대응은 plan_text=null이고, 기존 proposed/prepared 후보만 이전 게시 복구를 따른다. 정상 planning 전환·snapshot·단계 선택·선행 Review와 Worker 범위 기록 보존은 다시 만들지 않는다.

## Acceptance Criteria

- DOCUMENT_RESULT는 기존 result_normalization helper로 명확한 marker·공백·구분자·다중 줄 JSON을 처리한다. 같은 의미의 형식 차이만으로 모델을 다시 호출하지 않으며 저장 원문과 정규화 결과를 현재 호출 입력에 결합한다.
- 중복 marker·중복 JSON key·상충 판단·누락/빈 evidence·잘못된 relevant/implementation·명시 identity 불일치를 거부한다. json.loads의 마지막 key 값으로 구현 부족을 satisfied로 바꾸지 않는다. 실제 부족한 판단은 기존 교정/보존 경로다.
- 새 ExecPlan 실행 대응은 프로젝트 planning이 확정한 작업 조건과 현재 후보·발견 단계만 확인하고 plan_text=null 계약을 지킨다. 연결 Requirement/상위 명세의 관련성과 전체 작업 개정을 다시 판단하거나 새 단일 개정 후보를 생성하지 않는다. 보존된 legacy 결과의 plan_text는 원래 근거·stage·게시 사실에 결합해 복구하며 새 결과의 계약으로 소급 폐기하지 않는다.
- 일반 planning의 snapshot 선정 이후 또는 legacy proposed/prepared 게시 직전에 실제 연결 PR이 나타나면 기존 계획 개정을 게시하지 않는다. 후보·실행 이력·동일 PR 연결은 보존하며 추가 범위는 PR 이후 새 ExecPlan 정책으로 인계한다. PR 출현만으로 기존 계획을 PLAN_INPUT_INVALID로 최종 차단하지 않는다. PR 조회 실패는 부재로 해석하지 않는다. 무관한 작업의 개정 권한까지 함께 해제하지 않는다.
- 원격/후보 변경·PR 경합·중단 재시작에서도 오래된 개정 권한이나 결과로 다음 단계를 시작하지 않는다. 이미 게시한 후보·미완료 보완을 구분하며 실제 원격·현재 ownership/generation을 다시 확인한다. 사용자 결정·다른 실패·session/level과 검증 근거를 보존한다.
- 형식 교정·PR 경합 처리는 현재 Planner 전용 worktree의 별도 scope와 checkpoint를 유지한다. Worker의 agent_role·agent_snapshot·agent_result_snapshot·session·미커밋 작업을 Planner 기록으로 덮어쓰지 않으며, Worker 후보/파일과 문서 입력 변경 때 저장된 판단을 재사용하지 않는다. Manager가 만든 worktree/ref 비교 보정은 기존 허용 metadata 경계에 한정한다.
- Worker/verify/Reviewer/게시의 최초·교정·재개, 작업 branch의 검증된 채택, 프로젝트 planning 후 조건 유지/변경 대응과 선행 Review→구현/검증 보완을 유지한다. R-082 문서 변경 선행 PASS/VERIFY_REQUIRED는 검증 보완 뒤에도 최종 verify/Review 승인이나 게시 token으로 재사용하지 않는다. R-086 일반 선행 결과·최종 승격과 별도로 유지한다.
- PRODUCT·ARCHITECTURE에는 실제 보완한 결과 형식·legacy PR 경합·보존 조건만 반영한다. 이미 정합화된 프로젝트 planning·작업별 ExecPlan 기준을 다시 옛 상위 명세 영향 판단으로 바꾸지 않는다. 현재 작업의 실행 대응 성공은 전체 planning 성공이 아니다.

## Implementation

- [x] 확인한 `loop_manager_internal/execution/stage_documents.py`의 `parse_assessment()`를 기존 `loop_manager_internal/application/result_normalization.py`의 `tagged_json()` 경계로 연결한다. marker/공백/다중 줄 형식은 처리하되 중복 key·상충 판단·필수 근거 누락은 거부한다. 현재 네 필드 계약과 호출 당시 후보·문서 입력 identity 검증을 보존하며 결과에 새 metadata를 일괄 요구하지 않는다.
- [x] 새 실행 조건은 stage Planner 판단을 만들지 않고 기존 Worker revision gate에 넘긴다. 저장된 legacy scope 없는 assess/proposed/prepared/done 결과만 원래 stage·원문·후보·권한·게시 사실을 대조해 복구한다. 새 Planner prompt를 되살리거나 legacy plan_text를 새 결과 계약으로 소급 폐기하지 않는다.
- [x] `stage_documents.py`의 legacy proposed snapshot 제외·prepared 게시 직전 PR 재확인에서 실제 연결 PR을 다시 조회하고, 확인되면 후보와 실행 이력을 보존해 기존 PR 경로로 넘긴다. PR 없는 계획은 기존 권한 검증을 유지하고 조회 실패는 부재로 해석하지 않는다. 일반 planning의 실제 PR 출현은 `planning/planner_validation.py`·게시 경계에서 구분해 defer한다.
- [x] 형식·PR 교정 뒤 실제 구현·검증 부족을 발견 단계별 기존 경로로 연결하고 제품·설계의 관련 설명만 통합한다. parser·legacy 복구와 실행 대응의 범위를 넘어 전체 lifecycle이나 충돌 교정을 재설계하지 않는다.

현재 legacy `document-assessments` 작업 공간의 planner_scope/history, worker_snapshot과 `assert_assessment_inputs`·`remember_workspace_metadata` 경계를 재사용한다. 제거된 Worker worktree의 begin_scope/clear_scope 호출은 복원하지 않는다. 저장된 판단의 형식 정규화도 원래 구현 후보와 마지막 반영 ExecPlan·최신 조건에 결합하며 후보/원격 변화에서는 기존 재관측을 따른다.

## Validation

- `tests/test_stage_documents.py`의 targeted unit case로 marker·구분자·다중 줄 JSON 정규화, 중복 marker/key·상충 판단·필수 근거 누락 거부와 legacy 원문/정규화 판단 보존을 확인한다. 새 실행 대응은 기존 Worker revision gate를 사용하고 legacy checkpoint에 새 metadata를 강제하지 않는다.
- 실제 SQLite-backed mutable snapshot과 `ExecutionRevisionHandler`를 연결해 proposed 후보가 PR 때문에 snapshot에서 빠진 뒤 실제 PR 재조회로 최종 차단 없이 후보·Worker·verify 기록을 보존하는 회귀를 확인한다. PR 없는 계획은 재조회 뒤 기존 갱신 권한 오류를 유지한다.
- `tests/test_incremental_planning.py`·`tests/test_planning_publication.py`의 기존 회귀는 일반 planning의 snapshot 이후 PR 출현·조회 실패·미게시 후보 보존을 확인한다. 단계별 Reviewer 선행 PASS/FAIL/VERIFY_REQUIRED 뒤 검증/교정 및 최종 게시 금지 회귀도 유지한다.
- 현재 `test_stage_documents.py`의 전용 workspace·Worker 원문/호출 감사 보존·후보/원격 경합과 `test_incremental_planning.py`의 실제 게시 연결 회귀를 유지한다. R-055에 따라 중단 재개는 현재 작업·결과·후보 유효성을 확인하며 과거 Git snapshot의 접근 위반 판정을 다시 실행하지 않는다. parser/PR 처리에서 실제 보존 조건을 함께 검사하고 직접 구현된 분리를 소급 계획하지 않는다.
- 전체 verify는 직접 구현된 snapshot 실행 이력 보존·작업 branch 채택·후보 무효화·rebase/checkpoint·원격 경쟁을 유지한다. 실제 Git은 기존 게시/rebase 연결 회귀를 재사용하며 새 정책 조합은 관측 mock으로 검사한다. Reviewer는 문서/코드/검증 근거 정합성을 읽기 전용으로 확인한다.
