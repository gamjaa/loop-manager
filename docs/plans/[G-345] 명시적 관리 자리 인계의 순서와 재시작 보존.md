## Purpose

명시적 수동 제출·차단 해제의 관리 자리 인계에서 원래 배정 순서를 보존하고, 새 요청 없는 한도 축소가 기존 작업을 밀어내지 않게 한다. 포화 중 수락·원자적 unblock·공유 묶음 계산·실제 호출 반환 대기는 원격의 직접 구현을 재사용한다. 남은 순서 저장·인계 자격·재시작 연결만 담당한다.

현재 `management_admission.reconcile()`은 수락 행이 하나라도 있으면 매번 `ranked[:limit]` 밖의 기존 단위를 대기시킨다. 새 명시 요청과 과거 수락 행을 구분하지 않아 이후 한도 축소에도 이 경로가 적용된다. RETRY 순서는 `Task.retry_order`와 `TaskScheduler.retry_sequence`에만 있고, 대기 단위의 task가 종료되면 `scheduler.tasks`에서도 제거된다. 재진입·재시작의 순서 근거를 현행 저장 행의 `sequence`만으로 복원할 수 없다.

현재 base는 `cycle_allows_recovery(..., explicit_request=True)`를 통해 게시가 확정된 유지보수 범위 밖 명시 요청을 수용하고, `ManualWorkService.resume()`·`_resume_group()`은 활성 단계 보존·조건부 갱신·parked 대상의 투영 생략을 제공한다. 이 직접 구현은 재사용하고, 아래 순서 저장·인계 교정이 해당 자격과 현재 교정 단계를 보존하는 연결만 확인한다.

## Acceptance Criteria

- R-091: 실제 후속 실행이 가능한 명시 요청 때문에 자리가 필요할 때만 같은 프로젝트의 가장 늦은 관리 단위를 선택한다. 기존 수동 최초 수락 → 명시적 해제 수락 → RETRY → 일반 재개 → 신규의 현재 비교·유효 priority·동순위 규칙을 재사용한다. 공유 수동 묶음은 한 단위이며 다른 프로젝트를 밀어내지 않는다.
- 밀려난 단위의 원래 순서와 RETRY 자격·재등록 순서가 보존 대기·task 반환·DB 재연결·Manager 재시작 뒤에도 유지된다. 단계·후보·session·checkpoint generation·미완료 rebase·실패·사용량을 초기화하지 않고 같은 단계에서 재진입한다. 반복 요청·복수 대상은 최초 수락 순서를 바꾸거나 이중 배정하지 않는다.
- 새 우선 요청이 없으면 기존 상한 축소 규칙을 적용한다. 과거 admission 행만으로 이미 관리 중인 단위를 밀어내지 않고 신규 관리 편입만 보류하며, 기존 작업은 실제 실행 상한 안에서 후속 단계를 이어간다. 실제 새 명시 요청에 따른 인계와 이 경우를 구분한다.
- 실행 중 호출·verify와 미확정 Git/게시 전이는 강제 종료하거나 소유 예약을 회수하지 않는다. 새 후속 배정을 막고 선택한 단위의 안전 반환을 확인한 뒤 자리만 넘긴다. 자격 없는 요청 때문에 빈 자리를 예약하지 않고 현재 dependency·pause·planning drain·runtime 종료·소유권 gate를 유지한다. R-074/R-077/R-091의 미확정 게시 없는 prerequisite·refactoring·기존 후속 확인 단계에서는 범위 밖 수락 수동 제출·명시적 해제도 같은 인계 순서로 처리한다. 일반 신규 작업의 범위 제한·cycle의 고정 범위/완료 조건은 보존하고, 이미 활성인 구현·교정·verify·Review·게시 단계를 최초 제출 단계로 덮어쓰지 않는다.
- 수락·인계 선택·반환 확인·재편입 사이 중단과 요청/단계/소유권 경쟁에 기존 요청·순서·작업물과 실제 실행 자리를 보존한다. 관리 대기는 timeout·교정 실패·검증 성공이나 실질 진전으로 집계하지 않는다. 조회 소비자가 수락 순서·밀려난 대상·인계 대기와 실제 시작을 구분할 저장 근거를 사용할 수 있다.
