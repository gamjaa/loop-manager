## Purpose

유지보수 평가 성공 근거의 Git 관측을 DB 접근 밖에서 준비하고, 짧은 transaction에서는 현재 소유권·선정 범위·generation과 준비된 근거만 대조해 확정하도록 나눈다. 파일별 legacy 복구와 현재 tiered 게시의 근거 검증을 유지하며, 이후 G-331이 게시 batch 전체의 DB 확정을 분리할 수 있는 준비/적용 경계를 제공한다.

revision `f5a9d4ea510c62cea769eacd32c604f32bf25425`의 저장된 발견 11은 `storage/maintenance_file_ledger.py:record_success()`가 `_prepare_evidence()`를 transaction 안에서 다시 호출하고 마지막 원격 revision 검사도 잠금 안에서 수행함을 확인했다. inventory/root/tree 검사는 실제 Git subprocess로 연결된다. 공통 DB 접근이 외부 처리와 결합된 구조이며 실제 지연·교착을 측정한 결과는 아니다.

## Acceptance Criteria

- 파일/root/원격 입력·게시 blob 관측과 인용 검증은 DB 접근 구간 밖에서 수행한다. 확정 transaction에 Git subprocess·원격 조회·다른 자원 대기가 남지 않는다. 상위 transaction에서 호출하는 경로도 같은 조건을 만족한다.
- 준비한 근거는 원본 revision·hash/mode·scope·지침·실제 검토·게시 identity를 그대로 갖는다. 현재 cycle·선정 집합·소유권·generation이 달라지면 적용을 거부하고 원래 근거·미확정 게시를 보존한다.
- 프로젝트/root 변경 rollback·실제 게시 확인·기존 성공 근거 보호를 약화하지 않는다. 정적 inventory를 의미 검토 성공으로 만들거나 미검토 원본의 ledger를 합성하지 않는다.
- 사용자 동작과 공개 계약인 ledger 호출·cycle cadence·legacy 복구, DB schema·JSON/receipt의 저장 형식을 보존한다. 검증을 transaction 밖으로 옮긴다는 이유로 원격 확인이나 CAS를 삭제하지 않는다.

## Implementation

- [ ] 확인한 `loop_manager_internal/storage/maintenance_file_ledger.py`의 준비·검증·성공 쓰기를 분리한다. 원격에서 얻은 검증 결과는 호출 내 불변 값으로 전달하고, 현재 DB 상태 비교와 성공 행/기준 갱신은 기존 repository·`storage/db_access.py`/`runtime_state._transaction` 경계에서 원자 처리한다. 새로운 전역 cache나 별도 성공 원본을 추가하지 않는다.
- [ ] 확인한 `loop_manager_internal/maintenance/maintenance_file_inventory.py`의 관측을 재사용한다. 마지막 원격 재확인도 DB 접근 전에 수행하고 관측한 publication/assessment identity를 적용 값에 결합한다. 관측과 확정 사이에 발생한 DB 입력·owner·generation 경쟁은 CAS로 거부한다. 실제 원격 변경/관측 실패는 기존 보류로 반환한다.
- [ ] 확인한 `loop_manager_internal/maintenance/maintenance_publication.py`의 ledger 관련 호출에서만 prepare를 외곽으로 올리고 순수 적용을 기존 batch transaction에 연결한다. public facade가 필요하면 기존 시그니처를 유지하되 그 안에서 중첩 transaction 때문에 외부 관측을 다시 실행하지 않도록 호출 경계를 함께 정리한다. 같은 파일의 계획 등록·나머지 promote 외부 처리 분리는 G-331에 남긴다.
- [ ] 확인한 `tests/test_maintenance_file_review.py`·`tests/test_tiered_publication.py`·`tests/test_db_access.py`의 실제 SQLite·임시 파일·Event fixture를 재사용한다. root 보호 판정과 G-289의 선택적 예약 경로 목표를 재구현하거나 수정하지 않는다.
- [ ] 구현과 함께 `docs/ARCHITECTURE.md`의 유지보수 근거 확정 절에 관측/DB 적용 경계를 통합한다. 새로운 평가·마지막 Merge 후 재검증 단계는 추가하지 않는다.

## Validation

- Worker targeted unit은 위 세 테스트 모듈에서 바꾼 준비/적용·rollback·접근 경계 case다. Git 원격 관측은 제어 가능한 double로 제공하고 실제 ledger·CAS·SQLite 적용을 검사한다.
- 관측 double이 Event로 대기하는 동안 같은 파일 DB의 다른 연결이 짧은 조회/갱신을 완료해야 한다. observer에서 활성 transaction/공통 접근 소유가 없음을 검사하고 wall-clock 성능 임계값만으로 통과를 판정하지 않는다.
- 준비 뒤 root/source hash·mode·선정 범위·cycle/owner·generation·게시 근거 변경, 관측 오류와 DB rollback을 주입한다. 낡은 근거의 확정은 0회이고 기존 행·원문·게시 intent가 유지돼야 한다. 외부 관측이나 완료한 게시를 DB 요청 재시도마다 반복하지 않는다.
- 전체 verify는 파일별 legacy 복구, tiered/root 인용·reserved path·publication blob·성공 기준 원자성·cycle 종료 회귀를 유지한다. 읽기 전용 Review에서 외부 관측 이동을 근거 검증 생략으로 바꾸지 않았는지 확인한다.

## Decision Log

- complexity high: legacy와 tiered 상위 transaction을 함께 다루면서 동일 근거·게시·소유권 검증을 유지해야 한다. risk high: 잘못된 적용은 미검토 원본을 성공으로 기록해 유지보수 장벽을 풀 수 있다. 원래 receipt·publication intent 보존, CAS 실패 시 rollback, 원래 입력에서 재준비하는 경로를 유지한다. 최초 level은 5다.
- DB 저장 형식·상태 의미·게시 권한의 변경 없이 내부 준비 값과 확정 책임만 분리한다. Git 모듈이라는 이유로 priority를 올리지 않으며 지연 실측이 없어 normal을 유지한다.
- G-331은 이 경계를 소비한다. 이 계획만 Merge해도 ledger 관측과 DB 적용의 독립 검증이 가능하며 G-331 완료나 새 유지보수 평가를 완료 조건으로 요구하지 않는다.
