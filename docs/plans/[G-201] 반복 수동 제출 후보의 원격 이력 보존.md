## Purpose

반복 submit의 보존 Merge 후보와 그 후보를 만든 정확한 원격 기준을 함께 복구한다. 후보 저장 뒤 중단·외부 후속 push가 겹쳐도 낡은 후보에 새 원격 OID의 lease를 부여해 사용자 commit을 덮어쓰지 않도록 R-077의 이력 보존·중단 재개 계약을 완성한다.

## Acceptance Criteria

- source 변경 반영의 저장 후보·제출 commit·대상 branch·묶음 소유권과 후보 생성 당시 원격 OID가 결합된다. 재개 때 새로 관측한 OID만으로 저장 후보의 게시 권한을 갱신하지 않는다.
- 후보 저장 뒤 journal intent 전, push 전후 및 SQLite 확정 전의 중단에서 동일 후보가 이미 게시됐으면 Git 쓰기를 반복하지 않고 같은 요청·전체 G의 결과만 확정한다. 후보 생성 뒤 추가된 사용자 commit은 보존하며 안전한 보존 통합이 가능하면 현재 이력으로 이어가고, 불명확·삭제·재작성·경쟁은 이유와 작업물을 보존한다.
- 검증된 동일 소유 branch의 정확한 기대 OID에만 게시한다. 최초 source branch를 수정하지 않으며 reset·clean·사용자 lock 삭제·임의 operation abort 또는 관측만으로 새 이력의 강제 교체를 하지 않는다.
- 충돌 후보는 incoming 변경을 자동 교정 대상에 보존한다. 새 후보에는 오래된 생략·verify·Review·게시 근거를 적용하지 않고 기존 Worker 교정과 필수 최종 단계로 이어간다. 전체 묶음·session·로컬 staged/untracked 작업·실패 감사와 다른 차단을 유지한다.

## Implementation

- `git/manual_source_update.py`와 `storage/manual_work_state.py`의 pending source/candidate를 기존 `manager_git_journal`의 정확한 전이·equal/recovered 결과에 연결한다. 후보 저장과 게시 권한의 관측 기준을 함께 보존하고, 자원 재관측은 그 기준의 유효성 확인에 사용한다.
- 이미 완료한 Git 전이와 SQLite 미확정을 구분하며, 외부 후속 commit을 포함하지 않은 후보는 그대로 게시하지 않는다. 안전한 통합·충돌 교정은 기존 협업 Git 및 수동 후속 처리 책임에 남기고 새로운 실행 엔진이나 범용 journal을 만들지 않는다.
- R-077에 연결된 PRODUCT의 복구 판단과 최종 차단 및 ARCHITECTURE의 차단 작업의 원격 반영과 보존을 따른다. 기존 반복 submit·journal fixture를 재사용하고 새 루트 항목을 만들지 않는다.

## Validation

- Worker는 후보/기대 원격 identity와 journal 재개의 최소 unit case만 실행한다. 저장 후보와 관측 OID 불일치, 이미 게시된 equal 결과, 누락된 과거 근거 및 lease 거부에서 예상 밖 push가 없는지 확인한다.
- 실제 Git 회귀를 `tests/test_manual_work.py`의 반복 source 사례와 기존 journal fixture로 작성한다. 후보 저장 직후 중단→다른 기기의 소유 branch 후속 push→재시작, push 완료 뒤 SQLite 미확정, 재개 중 다시 경쟁, conflict와 dirty worktree를 포함한다. 통합 실행은 Manager 전체 verify에 맡긴다.
- Manager 전체 verify는 모든 사용자 commit의 보존·최초 source 불변, 중복 G/PR/게시 부재, 한 묶음의 단일 변경 자리, 오래된 생략 무효화와 교정 뒤 최종 verify·Review·lease를 확인한다. Reviewer는 저장 후보의 부모/기준과 실제 push lease를 대조해 외부 commit 손실 경로가 남지 않는지 검토한다.

## Decision Log

- `update_source`는 candidate를 먼저 저장하지만 당시 remote OID는 group에 결합하지 않는다. 재개 시 candidate가 있어도 현재 remote를 `before` 및 exact lease에 사용한다. journal intent 생성 전 중단 후 `prepared_head`의 후속 사용자 push는 ancestry 검사를 통과해, 그 commit을 포함하지 않은 저장 candidate의 강제 게시가 가능하다. 기존 반복 submit 테스트는 정상 반영만 다룬다.
- complexity high: 후보 저장·journal의 미완료/완료·외부 push·SQLite 확정과 충돌 교정 사이에서 같은 요청의 보존 및 재개 불변식을 정해야 한다. risk high: 소유 원격 branch의 사용자 후속 commit을 잃거나 제출 반영을 잘못 확정할 수 있다. 관측 OID·원본 commit·후보·intent를 보존해 수동 이력 복원·안전 재통합이 가능하도록 하며 코드 rollback만으로 원격 이력이 복구된다고 가정하지 않는다. 위험 시나리오와 복구 조건을 완료·검증·Review 기준에 포함한다.
