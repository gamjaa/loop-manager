## Purpose

활성 위치로 내용 보존 복원된 R-001의 READY-first 계약과 현재 Merge된 입력 변경 우선·유효 우선순위 계약 사이의 적용 범위를 사용자 판단으로 확정하고, 확정된 기준에서 실제로 남은 선택·회귀 검증만 구현한다.

## Acceptance Criteria

- 사용자가 R-001에 일반 Planner·빠른 점검과 실행 가능 또는 dependency 대기 READY·안정된 PR_OPEN·PLAN_BLOCKED의 선택 순서, 최초 성공 기준이 없는 경우의 처리, 선언/유효 priority 적용과 compact catalog의 draft·오류 근거 확장을 명시하고 관련 PRODUCT·ARCHITECTURE 계약을 정합하게 확정한다. 이 결정과 명세의 원격 확인 전에는 구현을 시작하지 않는다.
- 확정된 선택은 진행 중 변경·확정 PR 충돌 복구·프로젝트 안전·dependency·사용자 승인·게시 복구 gate를 보존한다. Planner를 보류하는 동안 미처리 원격 입력을 성공한 계획 주기로 기록하거나 지우지 않는다.
- R-001 AC 33의 dependency 대기 READY 시나리오는 확정된 정책에 맞는 실제 프로젝트 실행과 등록 프로젝트 scheduler로 검증한다. READY-first를 선택하면 해당 프로젝트의 Agent 미호출·WAITING·catalog 및 planning_fingerprint 보존·같은 scheduler의 독립 프로젝트 진행과 명시된 테스트 identity를 모두 충족한다. 다른 정책을 선택하면 사용자가 먼저 해당 AC를 정합하게 개정해야 한다.
- 같은 입력·대상에는 Planner를 반복하지 않고, 활성 작업·PR·session·branch·worktree와 실패 감사를 보존한다. 독립 프로젝트의 실행과 기존 priority 값·legacy normal 해석을 유지한다.

## Implementation

- planning/planning_contracts.py의 결정 함수와 planning/selection_service.py의 안전한 선택 경계, catalog/project_selection.py·effective_priority.py 및 application/project_runner.py·scheduler.py의 기존 책임을 재사용한다. 새 상태나 실행 자리를 추가하지 않는다.
- tests/test_catalog_scheduling.py의 기존 실제 scheduler fixture를 재사용한다. 현재 이 테스트는 Planner 호출과 OPERATIONAL_ERROR를 기대하므로 R-001의 기대 결과를 만족하는 것으로 취급하지 않는다.
- 사용자 결정 뒤 최신 원격 코드·테스트와 catalog를 다시 대조한다. 현행 정책 유지로 구현이 이미 충족되면 소급 구현·검증 성공을 만들지 않고 남은 명세·테스트 차이만 판단한다. PRODUCT의 현재 동작 갱신은 실제 변경에 필요한 범위로 제한하며 사용자 소유 설계 결정을 Worker가 대신 작성하지 않는다.

## Validation

- 확정된 정책의 changed specification/code, runnable/dependency-waiting READY, stable PR_OPEN·PLAN_BLOCKED, 최초 기준 부재와 동일 입력 재시작을 최소 선택 unit case로 검증한다.
- R-001이 요구하는 실제 run_project_result·scheduler 회귀는 프로젝트 결정 경로를 mock으로 대체하지 않는다. Agent 호출을 프로젝트별로 관측하고 다른 프로젝트의 정상 진행을 함께 확인한다.
- Manager 전체 verify는 PR 동기화·충돌 우선, 단일 변경 실행, dependency·priority 전파, 원격 입력 보존과 실패한 planning의 성공 기준 미갱신을 유지한다.

- R-037·R-049의 변경 입력 우선과 R-075의 유효 priority는 현재 구현·PRODUCT에 반영돼 있다. 원문 복원만으로 그 동작을 다시 승인하거나 철회했다고 추정하지 않는다. 유지보수 정책 충돌은 독립 draft G-205에서 다룬다.

## Draft Decision

Question: R-001 복원이 READY-first를 다시 도입하는 요청인지, 현행 변경 입력 우선 정책을 유지하면서 과거 기준을 정합하게 재정의하는 요청인지 R-001에 명시해 달라. 안정된 PR_OPEN·PLAN_BLOCKED에서의 Planner 허용, 최초 기준 부재, R-075의 유효 priority 및 R-061·R-055의 compact catalog 추가 근거 유지 여부도 포함한다.
Facts: 비교 구간에는 R-001 archive→active의 내용 보존 이동만 있다. R-001 AC 5~8·15·24·29·31·33은 현재 PRODUCT의 작업 선택·계획 입력 규칙, ARCHITECTURE의 계획 변경 감지 및 choose_planning_decision·compact_execplan_catalog와 일치하지 않는다. CatalogSchedulingTest.test_dependency_blocked_ready_is_not_an_empty_catalog는 실제 scheduler를 사용하지만 Planner와 Worker 호출 및 OPERATIONAL_ERROR를 기대한다. R-037·R-049·R-075는 이미 반영된 후속 정책이며 R-061·R-055는 draft·catalog hold 근거를 요구한다. 제공된 catalog에는 이 재선택 작업이 없다.
Options: A는 필요한 최신 보호 조건을 명시한 READY-first로 선택을 바꾸고 R-001의 대기 회귀를 복원한다. B는 현행 문서 변경 일반 Planner·코드 변경 점검 우선과 유효 priority를 유지하도록 R-001의 해당 기준을 사용자가 개정한다. 부분 적용은 각 조건의 허용·보류와 입력 보존을 명시한 구체적 답변이 필요하다.
Impact: A는 다음 Worker·Planner의 실행 순서와 실제 scheduler 테스트 변경이 필요하다. B는 이미 충족된 구현을 중복 계획하지 않고 명세 정합성 확인 뒤 남은 테스트 차이만 재판단한다. 결정과 원격 명세가 일치할 때까지 이 계획과 의존 작업의 Worker·workspace·branch·PR은 시작하지 않는다.
