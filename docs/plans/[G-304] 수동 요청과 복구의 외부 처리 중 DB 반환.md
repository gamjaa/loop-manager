## Purpose

수동 요청·로컬 복구의 외부 관측·실행 동안 공통 DB 접근을 반납하고, 결과 적용 때 같은 요청·소유 예약·현재 상태를 재확인한다. 직접 구현된 수동 ID 예약 전 Git 관측 분리와 등록/catalog의 snapshot 적용은 재사용하며 같은 명령 안에서 충돌 없는 준비·수락을 완료하는 계약을 유지한다.

현재 `manual_concurrency.preparation_gate(inspect_workspace=False)`도 `validate_workspace()`를 호출해 Git worktree catalog를 관측한다. `manual_work.complete()`·`_accept_submit()`는 writer transaction 안에서 profile/설정 입력을 준비한다. `commands.recover_local_environment()`는 연결 context 전체 안에서 실제 복구를 실행하므로, 중간 commit 뒤에도 `CoordinatedConnection._depth`가 DB 접근을 유지한다. 이 확인된 소비자 경계를 보완한다.

## Acceptance Criteria

- R-091: Git/worktree·profile/설정 관측, 실행 잠금·배정 대기와 실제 복구/외부 실행 동안 DB 접근을 점유하지 않는다. 명시적 writer transaction 유무뿐 아니라 상위 연결 context·미확정 쓰기가 남긴 접근 소유권도 없어야 한다. 다른 DB 요청과 독립 작업은 그동안 처리될 수 있다.
- R-077: 수동 start/complete/submit의 현재 G·묶음·source·계획 revision·작업/게시 예약을 짧은 DB 처리에서 조회한다. 외부 관측 뒤 같은 예약·요청·구성원·단계와 관측에 사용한 상태를 재확인해 한 번만 적용하며 경쟁 변경은 보존한다. Git·소유권 검사를 생략해 DB 점유만 줄이지 않는다.
- 충돌 없는 준비·수락은 짧은 DB 차례만 기다려 같은 명령에서 완료한다. 실제 계획·자원 충돌은 기존대로 구체적으로 거부하며 전체 자동 작업의 종료를 기다리거나 요청 저장만으로 준비 완료를 대신하지 않는다. 수락 순서·묶음 직렬 처리·정확한 후보의 사용자 면제 조건은 유지한다.
- 로컬 recover는 수락된 요청과 자동 실행 lease를 보존하며 실제 복구를 DB 밖에서 실행한다. 후속 기록은 현재 요청·대상·진행 근거를 재확인한다. DB 재시도 때문에 Git·Agent·verify·게시 또는 완료 사건을 중복하지 않고, 외부 효과 후 저장이 끊기면 기존 intent/receipt와 실제 상태로 재개한다.
- 실패·취소·기록 대기에서는 기존 작업물·source branch·후보·session·감사를 유지한다. 저장 실패를 성공으로 표시하거나 관계없는 계획·프로젝트의 소유권을 바꾸지 않는다.

## Implementation

- [ ] 확인한 `loop_manager_internal/application/manual_concurrency.py:preparation_gate()`의 DB 충돌 판정과 `application/manual_work.py`의 start/complete/submit·`_accept_submit()`·generate/prepare 호출을 구분한다. `application/bindings.py`가 연결한 `git/workspace.py:validate_managed_worktree()`의 외부 Git 관측을 DB 밖으로 분리하고 현재 `resource_locks`·`storage/work_claims.py`·Git journal의 소유 예약을 유지한다.
- [ ] 확인한 `execution/manual_candidate.py:stage_input_tokens()`·`candidate_token()`을 사용해 외부 profile/설정 관측과 DB에 고정한 guidance/묶음 입력의 계산·확정을 분리한다. 현재 `storage/manual_work_state.py`·`runtime_state.py`의 snapshot/transaction을 재사용하며 관측 이후 요청·문서·소유권 변경은 낡은 수락만 거부한다. 새 수동 명령·면제 정책·별도 후보 저장소는 만들지 않는다.
- [ ] 확인한 `application/commands.py:recover_local_environment()`·`execute_local_recovery_request()`의 연결 수명과 짧은 요청 처리 수명을 분리한다. `storage/local_recovery_state.py`의 기존 request identity·snapshot·진행 기록을 재사용하고 외부 실행 뒤의 상태 확정을 G-303의 DB 요청 경계에 연결한다.
- [ ] 확인한 `tests/test_manual_concurrency.py`·`tests/test_manual_work_validation.py`·`tests/test_local_environment_recovery.py`에 실제 공통 DB 연결의 최소 회귀를 연결한다. 기존 단일 연결/비조율 fixture의 통과만으로 파일별 조율 계약을 검증하지 않는다. PRODUCT·ARCHITECTURE의 수동/복구 설명은 해당 소유 절에서 실제 구현과 맞춘다.

## Validation

- Worker는 변경 관련 최소 unit case만 실행한다. 실제 file DB·`open_connection()`과 Event/Barrier를 사용하고 Git·profile·복구 실행만 double로 제공한다. `validate_workspace`·profile 준비·실제 recover를 멈춘 동안 별도 연결의 상태 조회·쓰기가 완료돼야 한다. 준비 단계가 아직 같은 DB gate를 보유하면 실패해야 한다.
- 관측과 적용 사이 묶음 request·계획 revision·소유 예약·단계 변경을 주입해 낡은 complete/submit 확정만 거부하고 경쟁 값·원문·기존 수락을 보존한다. 정상 수동 준비는 같은 명령에서 완료하며 실제 공유 자원 충돌은 계속 거부한다.
- recover 요청 수락 뒤·외부 효과 뒤·DB 확정 전의 중단/대기에서 요청 identity와 저장 자료로 재개하며 mock Agent/Git/verify 호출이 중복되지 않아야 한다. DB 기록도 실패하면 원래 오류와 저장 오류를 로그에서 구별한다.
- 기존 `tests/test_manual_concurrency.py`의 실제 Git 준비·lease·원문 보존과 local recovery의 요청 중복 제거 회귀를 유지한다. 정책 조합별 실제 Git lifecycle을 추가하지 않으며 조회·수동 준비·독립 작업이 같이 진행하는 누락된 경계만 보강한다.
