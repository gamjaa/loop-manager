## Purpose

수동 요청·로컬 복구의 외부 관측·실행 동안 공통 DB 접근을 반납하고, 결과 적용 때 같은 요청·소유 예약·현재 상태를 재확인한다. 직접 구현된 수동 ID 예약 전 Git 관측 분리와 등록/catalog의 snapshot 적용은 재사용하며 같은 명령 안에서 충돌 없는 준비·수락을 완료하는 계약을 유지한다.

현재 `manual_concurrency.preparation_gate(inspect_workspace=False)`는 workspace 관측을 생략하고, `manual_work.complete()`·`_accept_submit()`는 profile을 DB 밖에서 관측한 뒤 group과 candidate token을 재확인한다. `commands.recover_local_environment()`의 연결 context도 transaction과 분리됐다. 이 직접 구현은 재사용한다. 남은 범위는 관측 당시 구성 G의 계획 revision·상태·소유 근거까지 연결한 수락 재검사와 G-303의 요청 재시도 적용이다. recover의 외부 실행 후 `complete_request()`·`record_progress()`도 현재 pending 요청과 관측 상태를 짧은 처리에서 재확인해야 한다.

## Acceptance Criteria

- R-091: Git/worktree·profile/설정 관측, 실행 잠금·배정 대기와 실제 복구/외부 실행 동안 DB 접근을 점유하지 않는다. 명시적 writer transaction 유무뿐 아니라 상위 연결 context·미확정 쓰기가 남긴 접근 소유권도 없어야 한다. 다른 DB 요청과 독립 작업은 그동안 처리될 수 있다.
- R-077: 수동 start/complete/submit의 현재 G·묶음·source·계획 revision·작업/게시 예약을 짧은 DB 처리에서 조회한다. 외부 관측 뒤 같은 예약·요청·구성원·단계와 관측에 사용한 상태를 재확인해 한 번만 적용하며 경쟁 변경은 보존한다. Git·소유권 검사를 생략해 DB 점유만 줄이지 않는다.
- 충돌 없는 준비·수락은 짧은 DB 차례만 기다려 같은 명령에서 완료한다. 실제 계획·자원 충돌은 기존대로 구체적으로 거부하며 전체 자동 작업의 종료를 기다리거나 요청 저장만으로 준비 완료를 대신하지 않는다. 수락 순서·묶음 직렬 처리·정확한 후보의 사용자 면제 조건은 유지한다.
- 로컬 recover는 수락된 요청과 자동 실행 lease를 보존하며 실제 복구를 DB 밖에서 실행한다. 후속 기록은 현재 요청·대상·진행 근거를 재확인한다. DB 재시도 때문에 Git·Agent·verify·게시 또는 완료 사건을 중복하지 않고, 외부 효과 후 저장이 끊기면 기존 intent/receipt와 실제 상태로 재개한다.
- 실패·취소·기록 대기에서는 기존 작업물·source branch·후보·session·감사를 유지한다. 저장 실패를 성공으로 표시하거나 관계없는 계획·프로젝트의 소유권을 바꾸지 않는다.

## Implementation

- [x] 확인한 `loop_manager_internal/application/manual_concurrency.py:preparation_gate()`와 `application/manual_work.py`의 start/complete/submit·`_accept_submit()`·generate/prepare에서 현재 DB 충돌 검사·외부 관측 분리를 유지한다. `application/bindings.py`가 연결한 `git/workspace.py:validate_managed_worktree()`를 transaction 안으로 되돌리지 않고 현재 `resource_locks`·`storage/work_claims.py`·Git journal의 소유 예약을 소비한다.
- [x] 확인한 `execution/manual_candidate.py:stage_input_tokens()`·`candidate_token()`과 현재 group 비교를 재사용해 수락의 관측/적용 경계를 완성한다. candidate token은 head/base·documents·환경·고정 guidance를 담지만 현재 catalog 구성 G의 revision·content hash·소유 상태 전체를 비교하지 않는다. `storage/manual_work_state.py`·`runtime_state.py`의 기존 요청·구성원·계획 snapshot을 짧게 확보하고 적용 때 다시 대조해 낡은 수락만 거부한다. R-077의 동일 요청·수락 순서·정확한 후보 면제를 유지하며 새 수동 명령·정책·별도 후보 저장소는 만들지 않는다.
- [x] 확인한 `application/commands.py:execute_local_recovery_request()`와 `storage/local_recovery_state.py:complete_request()`·`record_progress()`의 결과 확정을 G-303의 요청 경계에 연결한다. `complete_request()`가 transaction 전에 만든 snapshot과 pending 여부만으로 최신 상태를 덮지 않게 요청·대상·관측 상태를 재확인한다. 직접 구현된 recover 연결/transaction 수명 분리·`begin_request()`의 중첩 처리는 보존하고 실제 복구나 수동 Git 효과를 replay하지 않는다.
- [x] 확인한 `tests/test_manual_concurrency.py`·`tests/test_manual_work_validation.py`·`tests/test_local_environment_recovery.py`에 실제 공통 DB 연결의 최소 회귀를 연결한다. 기존 단일 연결/비조율 fixture의 통과만으로 파일별 조율 계약을 검증하지 않는다. PRODUCT·ARCHITECTURE의 수동/복구 설명은 해당 소유 절에서 실제 구현과 맞춘다.

## Validation

- Worker는 변경 관련 최소 unit case만 실행한다. 실제 file DB·`open_connection()`과 Event/Barrier를 사용하고 Git·profile·복구 실행만 double로 제공한다. 기존 `test_profile_observation_returns_db_and_rejects_changed_manual_request`·`test_recover_releases_database_access_during_external_execution`을 재사용한다. submit 및 새 요청 재시도/적용 경계에 빠진 독립 조회·쓰기만 보강하고 이미 검증하는 complete profile/recover 반환 assertion을 복제하지 않는다.
- 관측과 적용 사이 묶음 request·계획 revision·소유 예약·단계 변경을 주입해 낡은 complete/submit 확정만 거부하고 경쟁 값·원문·기존 수락을 보존한다. 정상 수동 준비는 같은 명령에서 완료하며 실제 공유 자원 충돌은 계속 거부한다.
- recover 요청 수락 뒤·외부 효과 뒤·DB 확정 전의 중단/대기에서 요청 identity와 저장 자료로 재개하며 mock Agent/Git/verify 호출이 중복되지 않아야 한다. DB 기록도 실패하면 원래 오류와 저장 오류를 로그에서 구별한다.
- 기존 `tests/test_manual_concurrency.py`의 실제 Git 준비·lease·원문 보존과 local recovery의 요청 중복 제거 회귀를 유지한다. 정책 조합별 실제 Git lifecycle을 추가하지 않으며 조회·수동 준비·독립 작업이 같이 진행하는 누락된 경계만 보강한다.

## 구현 결과와 targeted 확인 (2026-10-24)

- start·complete·submit 수락 전에 같은 짧은 DB snapshot에서 group/request, 구성원 membership, 구성 G의 전체 ExecPlan 행과 소유 fingerprint를 확보한다. Git·profile 관측 뒤 후보 입력·계획 상태와 현재 DB 자원 gate를 다시 확인하고 바뀐 리비전·상태·예약은 거부한다.
- 복구 `complete_request()`·`record_progress()`는 G-303 `run_request` 경계에서 request ID·repo·plan 범위·pending 상태와 관측 snapshot이 유지될 때만 확정한다. 상태가 달라지면 pending 요청과 경쟁 값을 보존하고 DB 재시도는 외부 executor를 다시 호출하지 않는다.
- 실제 파일 DB·두 연결·SQLite writer 경합에서 finalization 재시도와 stale 상태 거부를 확인했다. Git/profile 관측 중 독립 쓰기, start·complete·submit의 리비전 경합, 진행 요청의 identity 재사용과 pending 보존을 targeted unit test로 확인했다. 기존 수동 준비·profile 분리·복구 DB 반환·수동 verify/Review 회귀도 통과했다.
- 두 targeted test의 첫 harness 실행은 각각 테스트 연결의 `row_factory` 누락과 미확정 fixture transaction 때문이었다. 설정을 고친 뒤 같은 command를 재실행해 통과했다. `test_next_run_consumes_saved_plan_request_once`의 첫 시도는 sandbox가 localhost socket 생성을 거부했다. 이 테스트는 recovery request의 scheduler 전달을 확인하고 verify transport는 사용하지 않으므로 해당 case에서 coordinator만 격리했다. 이어 mock 실행이 실제 transaction 경계처럼 recheck 기록을 commit하도록 맞춘 뒤 같은 command가 통과했다.
- 전체 verify는 Worker 경계에 따라 실행하지 않았다.
