## Purpose

Manager의 프로젝트·ExecPlan 조율을 유한한 단계 실행과 재등록으로 전환한다. 실행 자리·사용 한도·retry 시각·기존 호출 종료·입력 변화의 대기는 조건과 다음 재확인만 보존하고 반환하며, 실제 Agent·verify 등의 외부 실행만 해당 실행 자원을 사용한다.

현재 `scheduler.schedule_registered_projects()`는 프로젝트 Future 전체를 기다리고 `run_project_tasks()`는 계획별 thread와 wait/join을 유지한다. `wait_usage()`·`wait_retry()`·`wait_existing_call()`·`finish_storage()` 등도 대기 stack을 유지한다. 기존 호출 예약·영수증·단계별 checkpoint와 G-350/G-352의 정책을 재사용해 조율 방식을 바꾼다.

## Acceptance Criteria

- R-091: 프로젝트/계획별 조율 단계는 유한한 상태 확인·실행 배정·완료 확정 후 반환한다. 실행 불가능한 요청은 소유 대상·원인·조건 변경 이벤트 또는 재확인 시각과 원래 순서를 보존해 재등록한다. 작업마다 대기 thread나 `while True`/`join`으로 자리·사용량·retry·종료·입력 변화를 기다리지 않는다.
- 실제 Agent·verify는 기존 전체 실행 상한, 관리 단위·프로젝트 한도와 별도 verify 상한 안에서 수행한다. 조율을 위한 thread 수가 대기 계획 수만큼 증가하지 않는다. 실행 가능한 후보가 없으면 중앙 조율기만 다음 이벤트/시각까지 효율적으로 대기하고 같은 조건의 즉시 재삽입·busy loop가 없다.
- G-350의 프로젝트 단계 게이트·G-352의 이어하기 순서와 기존 수동 제출/명시 해제/RETRY 정책을 유지한다. A의 조건 보류 중 B와 다른 프로젝트의 실행·결과 수집이 진행하고, 같은 계획/후보에는 중복 실행·동시 writer가 없다.
- R-023/R-076: planning은 해당 프로젝트, runtime 종료 결정은 전체의 새 단계 배정을 중단한다. 실행 중 호출은 handoff의 안전 반환을 유지하고 사용자 pause의 저장·종료 확인은 별도 정책을 적용한다. 대기 중 runtime 원격 조회는 하지 않고 실제 단계 진입의 기존 최초/30초 TTL을 유지한다.
- 재시작·DB 확정 실패 뒤 원래 단계·session·후보·완료 외부 효과와 미확정 결과를 재관측한다. 실행 종료 확인과 저장만 남은 상태를 구별하며 미종료 예약을 회수하거나 완료한 호출을 재실행하지 않는다. 실행 전 대기는 timeout·실패/교정 횟수를 소비하지 않는다.
- Git·DB·알림의 소유 처리 경계는 유지하고 각 자원 요청의 재등록을 받을 수 있게 연결한다. 해당 자원 자체의 순번 대기 전환은 G-354/G-355, 공통 전송과 네 큐의 최종 연결은 G-356이 소유한다. 이 작업만으로 모든 큐의 전환 완료를 선언하지 않는다.

## Implementation

- [ ] 확인한 `application/scheduler.py`·`task_scheduling.py`·`project_runner.py`의 장수명 프로젝트/계획 루프를 재확인 가능한 단계 결과와 중앙 완료 수집으로 통합한다. `application/project_service.py`·`execution/execution_runtime.py`의 현재 단계·결과 계약과 명명된 effects를 재사용한다. 실제 운영 경로를 전환하며 사용하지 않는 별도 scheduler나 상주 서비스·설정·루트 파일을 추가하지 않는다.
- [ ] `storage/task_calls.py`·`execution_checkpoint_state.py`·`runtime_state.py`·`management_admission.py`의 실행 원본·예약·durable 순서로 요청/실행/확정을 구별한다. 동기 callback의 stack에만 보존하던 완료 결과는 기존 receipt/checkpoint에 필요한 호환 근거로 보존하고, 재시작은 실제 프로세스·저장 상태를 대조한다. DB 연결·TEMP 문맥을 다른 thread로 그대로 넘기지 않는다.
- [ ] 현재 `retry_inputs()`·무변화 retry 억제·일반 예외 묶음 반환·`parked` 복구 요청 양보를 소비한다. 의미 있는 진전의 지속 이력은 G-325, planning 잔여 정리/원인 복구는 G-337/G-338에 남긴다. 새 retry 엔진이나 targeted 임계값 정책을 만들지 않는다.
- [ ] 확인한 `tests/test_task_scheduling.py`, `test_registered_project_scheduler.py`, `test_project_services.py`, `test_local_environment_recovery.py`의 제어된 실행·fake clock·실제 SQLite fixture로 단계 반환·재등록을 검증한다. 스레드 대기를 전제로 한 테스트는 정책/상태 assertion을 새 단계 경계로 옮기고 대응을 기록한다. PRODUCT·ARCHITECTURE의 조율·연결 소유 절을 실제 구현과 함께 갱신한다.

## Validation

- Worker targeted unit은 변경한 위 최소 case다. 사용 한도·retry 시각·Agent/verify 종료 불명·입력 변화·자리 부족 각각에서 한 차례 조율이 반환하고, 해소 이벤트 뒤 한 번만 배정되는지 fake clock과 제어된 외부 실행으로 확인한다. 지연 시간을 늘려 통과시키거나 queue flag만 검사하지 않는다.
- A의 보류 동안 B의 실행·다른 프로젝트 완료 수집, 실행 중 verify와 독립 Worker/Review, 수동 우선·이어하기·신규 순환·공정성·관리/실행 상한을 기존 회귀와 연결한다. 조율 대기 thread가 요청 수만큼 생기지 않고 무변화 입력에서 effect 호출 수가 증가하지 않아야 한다.
- 실행 종료 뒤 결과 확정 전 중단·DB 재시도, 미종료 예약, pause·planning drain·handoff 중 재등록, 재시작을 검사한다. 기존 session/실패·targeted 이력·checkpoint 보존과 완료 효과 무반복·무호출 성공 금지를 유지한다. 실제 OS 종료/자식 보존은 기존 최소 통합 회귀를 재사용한다.

- R-091이 요청한 기존 Manager 조율 변경이다. 외부 infrastructure·새 daemon·동시 실행 한도 변경이나 비호환 migration을 도입하지 않는다. G-236의 pause는 G-350→G-338 선행 closure로 소비한다. 자원별 전환과 이력/진단 의미 판단을 별도 소유 계획에 남겨 같은 구현을 중복하지 않는다.
- complexity high·최초 level 5: callback stack의 진행·외부 실행·결과 확정을 재시작 가능한 경계로 나누고 여러 실행 상한/제어 신호를 보존해야 한다. risk high: 중복 호출·조기 예약 반환·결과 유실이 실제 외부 효과와 수동 복구를 만들 수 있다. 기존 receipt·소유권/generation·종료 확인 및 단계별 중단 회귀로 제한한다. priority high, Model·Effort는 Manager 설정을 따른다.
