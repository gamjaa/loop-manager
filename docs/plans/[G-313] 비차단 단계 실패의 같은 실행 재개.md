## Purpose

게시/복구의 원격 상태 불확실성을 현재 이력 재구성·통합, 실제 관측 경쟁, 조건 대기와 안전 거부로 구별해 같은 실행에서 이어간다. 고정된 과거 OID 차이는 최신 commit 관계로 판단하고 재시도만 반복하지 않는다. #293/#294의 retry 시점·Review 묶음/사용량 대기·runtime 교체·push 뒤 context 재구성과 기존 원격 통합을 재사용하며 일반 retry 엔진을 다시 구현하지 않는다.

현재 `recovery/recovery_runtime.py:decide()`는 `REMOTE_OID_UNCERTAIN`·`PUBLICATION_OWNERSHIP_UNCERTAIN`을 재관측 없이 최종 차단으로 처리할 수 있다. ownership/workspace/checkpoint 소비자의 bool 거부는 정상 게시/원격 후속 전진·조회 실패와 실제 다른 소유권을 구별하기 어렵다. 일반 단계 예외/DB 준비·수집의 남은 재편입은 G-297, checkpoint DB 확정은 G-307, 전체 후속 감사는 G-189가 담당한다.

현재 `recovery/work_branch_integration.py`의 비조상 보존/통합·원자 수용/무효화와 `git/publication_service.py`의 낡은 intent 감사 폐기는 직접 구현으로 소비한다. `worker_checkpoint.py:resume_request()`는 수용된 rebase의 후속 요청을 `_publish_rebased_checkpoint(candidate_head=...)`로 연결하고, `managed_rebase_publication.py`는 현재 소유권·완료 acceptance·정확한 lease를 다시 확인해 보류된 게시도 재개한다. 후속 immutable commit별 범위 검사도 유지한다. 진행 중 rebase에서는 `WorkspaceHandler.recover()`·`WorkerHandler.run()`이 일반 저장 요청보다 rebase 해결·완료를 먼저 처리한다. `_owned_checkpoint_remote()`는 완료 게시의 intent/result·현재 acceptance와 현재 소유권/범위·실제 원격을 확인해 과거 차단 receipt의 unpublished 상태만으로 거부하지 않는다. 현재는 결과 ID와 일치하는 `retired_rebase_publications`의 intent도 소비하며, `_rebased_request_commit()`이 `rebase_operation_history`의 동일 요청·원래 commit 증거와 현재 수용/소유권을 연결하고 완료 감사에 현재 `head`·재작성 전 `original_head`를 남긴다. 이 직접 구현은 다시 만들지 않는다. 남은 범위는 상위 소비자의 포괄적 OID 거부·기존 차단 재평가와 요청 처리 도중 원격 통합으로 후보가 달라진 경우의 실제 게시/확정이다. 현재 요청 소비의 `candidate_changed` 예외는 남아 있으므로, 낡은 intent 폐기·후보 변경과 실제 원격 보존을 구분해야 한다. 무진전 이력은 G-325, ref 격리는 G-324, 진단 전송은 G-326에 남긴다.

## Acceptance Criteria

- R-055/R-091: 원격 OID/게시 소유권 불확실성을 즉시 최종 차단하지 않는다. 현재 Manager intent·checkpoint·branch/PR·원격 OID를 같은 관측 경계에서 확인하고 완료한 자기 push, 확인한 후속 입력, 일시 관측 실패/lease 경합과 실제 다른 소유권을 구별한다.
- 정상 HEAD/OID 전진과 push/DB 시점 차이는 현재 intent·실제 원격·공통 이력과 양쪽 전용 commit/변경으로 재구성한다. 로컬 전용·원격 전용·양쪽 전진과 base rebase/원격 이력 재작성을 구분해 보존 가능한 입력은 기존 통합·필요한 재검증으로 이어간다. 사용자 commit의 존재만으로 다른 소유권을 단정하지 않는다. 비선형/손상 이력에서 관계·삭제 의도·작업 목표를 확인하지 못하면 그 대상의 쓰기만 보류하고 원문·양쪽 작업물·진단을 보존한다.
- `REMOTE_SNAPSHOT_RACE`는 실제 push/lease 실패 또는 fetch·PR 관측 중 값이 바뀐 경우의 제한 재관측에 사용한다. 고정된 과거 `publication_remote_oid`·PR head·checkpoint 불일치는 같은 과거 값으로 되돌아오기를 기다리지 않는다. 새 관측·복구 전이 없는 재시도는 G-325의 대상별 조건 대기로 이어간다.
- 게시 후보의 현재 commit·branch·PR과 검증 입력을 확인하고 일반 fast-forward와 검증된 재작성의 정확한 이전 원격 OID lease를 구분한다. lease 일치만으로 원격 사용자 변경 보존을 승인하지 않으며, 후보가 바뀌면 필요한 검증·Review를 유지한다. 이미 성공한 commit/push는 journal·현재 원격으로 확인해 누락 DB/checkpoint만 확정한다. 다른 origin/branch/PR·명시적 branch 삭제·실제 권한 거부와 미커밋 파일/index·심볼릭 ref 대상 밖 쓰기 보호를 유지한다.
- R-093: `retired_worker_checkpoints`의 `confirmed: false`·`pushed: 0`, 원격 입력 수용과 `candidate_changed`는 checkpoint 게시 성공이 아니다. 미완료 요청의 원래 parent/tree/message·commit과 통합된 현재 후보는 기존 history/acceptance 검사로 연결해 보존한다. 현재 tree를 과거 tree와 같다고 가정하지 않고 완료 감사의 `head`·`original_head`, 동일 intent의 확인된 결과·보존 intent와 요청/session/전달 identity를 유지한다. 실제 원격 보존이 확인되기 전 새 Worker·요청 완료·prompt 전달 확인을 진행하지 않는다. 재시작에서도 낡은 요청 때문에 완료한 commit을 반복하거나 원형 불일치만 재검사하며 정체하지 않고, 같은 소유 요청의 남은 통합/게시/확정부터 이어간다. 새 후보의 Worker·verify·Review 성공은 별도 gate로 유지한다.
- 재관측/대기는 G-297의 기존 순번·재시도 시점을 사용하되 대기 자체가 runtime 원격 코드 조회를 유발하지 않는다. 해소된 복구가 실제 다음 단계로 진입할 때 G-312의 최초·30초 TTL 적용 gate와 캐시된 종료 결정을 소비한다. 무대기 반복·형제 verify 완료/다음 외부 실행만 기다리는 보류·완료한 Git/Agent 효과 replay를 만들지 않는다. 조건 미해소/종료 불명에서는 새 writer를 시작하지 않고, runtime 종료 결정이 없는 동안 독립 작업은 계속한다.
- 후속 성공으로 해소되지 않은 실제 targeted test 연속 5회·검증/보고의 명시적 최종 차단·사용자 결정과 필수 입력/권한·사용량 제한을 우회하지 않는다. 직접 구현된 targeted 수집/근거 없는 보고·Review 교정 묶음·사용량 조건 대기의 집계와 session/논리 실행·실패/교정/사용량/시간·예약을 유지한다.
- 자원 대기·retry 묶음 소진·자동 재개 가능 상태는 사용자 행동 요청으로 바꾸지 않는다. 명시적 사용자 결정·실제 자동 복구 불가와 G-325가 확인한 동일 원인/입력의 지속 정체를 구분해 기존 알림 경계에 근거만 제공한다. 지속 장애 전송은 G-326이 담당하며 FINAL_BLOCK 이름이나 bool false 자체를 조치 근거로 삼지 않는다.

- [ ] 확인한 `execution/worker_checkpoint.py:resume_request()`·`execution/execution_ports.py:_publish_worker_checkpoints()`에서 원격 통합으로 후보가 바뀐 요청의 실제 게시/확정만 보완한다. 포트는 통합 뒤 낡은 intent를 폐기하고도 `candidate_changed`를 반환하며, 요청 소비자는 이를 원격 확인 대신 사용할 수 있다. 직접 구현된 rebase 후속 `candidate_head` 게시와 intent 재개·commit별 범위 검사, `_rebased_request_commit()`의 원래 parent/tree/message·동일 요청 검증과 현재 acceptance/소유권 검사는 그대로 소비한다. 기존 request/commit·완료 통합의 `before`/현재 HEAD·폐기 감사와 실제 게시 결과를 연결해, 처리 도중 후보가 바뀐 뒤 낡은 HEAD를 완료로 쓰거나 미게시 요청을 조기 소비하는 경계를 교정한다. 이미 구현된 재작성 요청 식별을 별도 매핑 계층이나 과거/현재 tree 동일성 검사로 대체하지 않는다. 같은 commit 재생성·새 lease만 넣은 덮어쓰기·감사 폐기·새 범용 복구 계층은 도입하지 않는다. 요청 없는 완료 후보의 기존 gate도 유지한다.

## Validation
