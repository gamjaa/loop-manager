## Purpose

게시/복구의 원격 상태 불확실성을 현재 이력 재구성·통합, 실제 관측 경쟁, 조건 대기와 안전 거부로 구별해 같은 실행에서 이어간다. 고정된 과거 OID 차이는 최신 commit 관계로 판단하고 재시도만 반복하지 않는다. #293/#294의 retry 시점·Review 묶음/사용량 대기·runtime 교체·push 뒤 context 재구성과 기존 원격 통합을 재사용하며 일반 retry 엔진을 다시 구현하지 않는다.

현재 `recovery/recovery_runtime.py:decide()`는 `REMOTE_OID_UNCERTAIN`·`PUBLICATION_OWNERSHIP_UNCERTAIN`을 재관측 없이 최종 차단으로 처리할 수 있다. ownership/workspace/checkpoint 소비자의 bool 거부는 정상 게시/원격 후속 전진·조회 실패와 실제 다른 소유권을 구별하기 어렵다. 일반 단계 예외/DB 준비·수집의 남은 재편입은 G-297, checkpoint DB 확정은 G-307, 전체 후속 감사는 G-189가 담당한다.

현재 `recovery/work_branch_integration.py:synchronize()`는 유효한 `remote_adoption`의 원래 head를 anchor로 사용하고, 비조상 이력은 `GIT_INPUT_UNCERTAIN`으로 반환한다. 해당 사유의 조건 대기·무통지, PR 관측/기존 실행 재개에서 독립 작업 계속 진행, 게시 OID 불일치의 `CHECKPOINT_STALE` 분류와 완료 push 뒤 DB 확정 재개는 직접 구현돼 있다. 남은 범위는 비조상이라는 이유만으로 멈춘 입력의 실제 변경 관계를 재구성해 보존 가능한 재작성은 통합·재검증으로 연결하고, 불명확한 대상은 현재 조건이 달라졌을 때만 재평가하는 것이다. 무진전 이력/대기는 G-325, 일괄 fetch의 다른 ref 영향 분리는 G-324, 지속 장애 전송은 G-326에서 소비한다.

## Acceptance Criteria

- R-055/R-091: 원격 OID/게시 소유권 불확실성을 즉시 최종 차단하지 않는다. 현재 Manager intent·checkpoint·branch/PR·원격 OID를 같은 관측 경계에서 확인하고 완료한 자기 push, 확인한 후속 입력, 일시 관측 실패/lease 경합과 실제 다른 소유권을 구별한다.
- 정상 HEAD/OID 전진과 push/DB 시점 차이는 현재 intent·실제 원격·공통 이력과 양쪽 전용 commit/변경으로 재구성한다. 로컬 전용·원격 전용·양쪽 전진과 base rebase/원격 이력 재작성을 구분해 보존 가능한 입력은 기존 통합·필요한 재검증으로 이어간다. 사용자 commit의 존재만으로 다른 소유권을 단정하지 않는다. 비선형/손상 이력에서 관계·삭제 의도·작업 목표를 확인하지 못하면 그 대상의 쓰기만 보류하고 원문·양쪽 작업물·진단을 보존한다.
- `REMOTE_SNAPSHOT_RACE`는 실제 push/lease 실패 또는 fetch·PR 관측 중 값이 바뀐 경우의 제한 재관측에 사용한다. 고정된 과거 `publication_remote_oid`·PR head·checkpoint 불일치는 같은 과거 값으로 되돌아오기를 기다리지 않는다. 새 관측·복구 전이 없는 재시도는 G-325의 대상별 조건 대기로 이어간다.
- 게시 후보의 현재 commit·branch·PR과 검증 입력을 확인하고 일반 fast-forward와 검증된 재작성의 정확한 이전 원격 OID lease를 구분한다. lease 일치만으로 원격 사용자 변경 보존을 승인하지 않으며, 후보가 바뀌면 필요한 검증·Review를 유지한다. 이미 성공한 commit/push는 journal·현재 원격으로 확인해 누락 DB/checkpoint만 확정한다. 다른 origin/branch/PR·명시적 branch 삭제·실제 권한 거부와 미커밋 파일/index·심볼릭 ref 대상 밖 쓰기 보호를 유지한다.
- 재관측/대기는 G-297의 기존 순번·재시도 시점을 사용하되 대기 자체가 runtime 원격 코드 조회를 유발하지 않는다. 해소된 복구가 실제 다음 단계로 진입할 때 G-312의 최초·30초 TTL 적용 gate와 캐시된 종료 결정을 소비한다. 무대기 반복·형제 verify 완료/다음 외부 실행만 기다리는 보류·완료한 Git/Agent 효과 replay를 만들지 않는다. 조건 미해소/종료 불명에서는 새 writer를 시작하지 않고, runtime 종료 결정이 없는 동안 독립 작업은 계속한다.
- 실제 targeted test 3회·검증/보고의 명시적 최종 차단·사용자 결정과 필수 입력/권한·사용량 제한을 우회하지 않는다. 직접 구현된 targeted 수집/근거 없는 보고·Review 교정 묶음·사용량 조건 대기의 집계와 session/논리 실행·실패/교정/사용량/시간·예약을 유지한다.
- 자원 대기·retry 묶음 소진·자동 재개 가능 상태는 사용자 행동 요청으로 바꾸지 않는다. 명시적 사용자 결정·실제 자동 복구 불가와 G-325가 확인한 동일 원인/입력의 지속 정체를 구분해 기존 알림 경계에 근거만 제공한다. 지속 장애 전송은 G-326이 담당하며 FINAL_BLOCK 이름이나 bool false 자체를 조치 근거로 삼지 않는다.

## Validation

- Worker는 `tests.test_recovery_runtime`·`tests.test_execution_workspace_phase`·`tests.test_execution_retry_policy`와 checkpoint 게시의 변경 관련 최소 unit을 실행한다. 실제 recovery·SQLite/checkpoint와 제어된 원격 관측으로 자기 push 시점 차이·정상 원격 전진·확인 가능한 재작성의 재구성/통합, 실제 조회/lease 경쟁의 제한 재관측, 관계 불명·다른 origin/branch/PR의 대상별 보류를 구분한다. reason 상수만 바꾸고 정상 결과를 mock해 판단을 대신하지 않는다.
- `tests/test_task_remote_inputs.py`의 최소 실제 Git 효과 회귀는 로컬·원격 전용 commit과 dirty/staged/untracked 자료 보존, 정상 사용자 push 뒤 통합·필요 검증·게시를 확인한다. 기존 비선형 rewrite case의 `GIT_INPUT_UNCERTAIN`·양쪽 OID·파일·operation 보존 assertion은 유지하고, 새로 관계를 증명할 수 있는 재작성의 통합/검증을 구별한다. 실제 관계를 증명하지 못한 이력은 계속 무쓰기이며, 정책 조합은 unit double로 검사한다. 이 실제 Git 회귀는 Worker가 실행하지 않는다.
- 일반 FF와 검증된 재작성 lease의 차이, lease 실패 뒤 새로운 원격 관측/통합, push 성공/DB 확정 중단을 검사한다. 타인 작업을 덮는 쓰기·완료 push replay는 0회여야 한다. 같은 고정 불일치의 재시도/다음 실행 재등록은 G-325의 보존 대기로, 실제 새 입력은 같은 작업의 재개로 연결되고 독립 작업은 계속 진행한다.

- 저장된 기존 OID 차단의 재평가에서 입력 지문 변경 없이 해소된 현재 원인만 풀고 명시적 사용자 판단·독립 차단·종료 불명은 남긴다. retry/usage/자원 대기 중에는 runtime 원격 조회 0회, 실제 복구 단계 진입에서는 G-312의 TTL 적용 확인을 사용하며 캐시된 종료 결정 뒤에는 추가 조회·새 writer 0회여야 한다. 코드 동일은 기존 retry 순서로 진행하며 사용자 pause를 삼키지 않는다.
- `tests/test_worker_checkpoint_publication.py`의 자기 push/후속 입력 분리·중단 복구와 `tests/test_task_scheduling.py`의 Review/usage/retry 시점 보존 회귀는 재사용한다. 실제 targeted 3회·보고/권한·branch 삭제 차단과 사용 한도 무probe assertion은 유지한다. 이미 직접 구현된 같은 실행 retry 테스트를 새 구현 작업으로 반복하거나 폐기하지 않는다.
- `tests/test_recovery_runtime.py:test_unproven_git_history_waits_without_user_action_or_timer_retry`와 `tests/test_task_scheduling.py:test_unproven_pr_history_releases_projection_and_continues_other_work`의 현재 분류·독립 진행 근거를 재사용한다. 새 조건을 확인한 뒤 같은 대상의 보류만 재평가하는 연결을 보강하고 타이머만으로 대기를 풀거나 다른 작업의 row·후보·승인을 바꾸지 않는다. 기존 인수 anchor/게시 재개 unit의 동일 조합·assertion은 복제하지 않는다.
