## Purpose

게시/복구의 원격 상태 불확실성을 현재 자원 재관측·비차단 대기와 실제 차단으로 구별해 같은 실행에서 이어간다. #293/#294의 retry 시점·Review 묶음/사용량 대기·runtime 교체·push 뒤 context 재구성은 재사용하며 일반 retry 엔진을 다시 구현하지 않는다.

현재 `recovery/recovery_runtime.py:decide()`는 `REMOTE_OID_UNCERTAIN`·`PUBLICATION_OWNERSHIP_UNCERTAIN`을 재관측 없이 최종 차단으로 처리할 수 있다. ownership/workspace/checkpoint 소비자의 bool 거부는 정상 게시/원격 후속 전진·조회 실패와 실제 다른 소유권을 구별하기 어렵다. 일반 단계 예외/DB 준비·수집의 남은 재편입은 G-297, checkpoint DB 확정은 G-307, 전체 후속 감사는 G-189가 담당한다.

## Acceptance Criteria

- R-055/R-091: 원격 OID/게시 소유권 불확실성을 즉시 최종 차단하지 않는다. 현재 Manager intent·checkpoint·branch/PR·원격 OID를 같은 관측 경계에서 확인하고 완료한 자기 push, 확인한 후속 입력, 일시 관측 실패/lease 경합과 실제 다른 소유권을 구별한다.
- 정상 HEAD/OID 전진과 push/DB 시점 차이는 기존 통합·재검증 또는 해당 자원 대기로 처리한다. 다른 origin/branch/PR·타인 commit·명시적 branch 삭제·확인된 복구 불가 상태의 기존 보존/거부는 유지하며 정확한 lease를 최신 값으로 임의 치환하지 않는다.
- 재관측/대기는 G-297의 기존 순번·재시도 시점을 사용하되 대기 자체가 runtime 원격 코드 조회를 유발하지 않는다. 해소된 복구가 실제 다음 단계로 진입할 때 G-312의 최초·30초 TTL 적용 gate와 캐시된 종료 결정을 소비한다. 무대기 반복·형제 verify 완료/다음 외부 실행만 기다리는 보류·완료한 Git/Agent 효과 replay를 만들지 않는다. 조건 미해소/종료 불명에서는 새 writer를 시작하지 않고, runtime 종료 결정이 없는 동안 독립 작업은 계속한다.
- 실제 targeted test 3회·검증/보고의 명시적 최종 차단·사용자 결정과 필수 입력/권한·사용량 제한을 우회하지 않는다. 직접 구현된 targeted 수집/근거 없는 보고·Review 교정 묶음·사용량 조건 대기의 집계와 session/논리 실행·실패/교정/사용량/시간·예약을 유지한다.
- 자원 대기·retry 묶음 소진·자동 재개 가능 상태는 사용자 행동 요청으로 바꾸지 않는다. 남은 명시적 사용자 결정이나 실제 자동 복구 불가 근거만 G-226/G-189의 알림 판정에 제공한다. 기존 FINAL_BLOCK 이름이나 bool false 자체를 그 근거로 삼지 않는다.

## Implementation

- [ ] 확인한 `loop_manager_internal/execution/execution_workspace_handler.py`·`execution_ownership_handler.py`·`execution_ports.py`, `recovery/checkpoint_service.py`·`project_blocked_recovery.py`의 OID/소유권 거부를 현재 원인으로 추적한다. 기존 게시 intent·accepted/active 원격·PR identity·generation 재관측을 재사용해 재준비 가능한 상태와 실제 안전 거부를 구별하는 제한된 결과를 전달한다. 이미 구현된 push 후 `pushed`/`candidate_changed` 분리와 context 재구성을 다시 만들지 않는다.
- [ ] 단계 실패의 실제 재진입에서만 G-297의 대기 해소·호출 gate와 G-312의 30초 TTL·확정 종료 결정 정책을 소비한다. 재시도 시점/usage/자원 대기 중 runtime 원격 관측을 추가하거나 별도 polling·runtime 캐시를 구현하지 않는다. 종료 결정이 있으면 다음 단계·writer를 시작하지 않고 기존 물리 호출의 결과·checkpoint 보존과 안전 반환을 적용한다.
- [ ] 확인한 `recovery/recovery_runtime.py:decide()`·`execution/execution_recovery_handler.py`의 typed reason/action을 해당 결과에 연결한다. `storage/recovery_state.py`의 identity·generation·실패/대기 시점과 G-297의 재배정을 사용하고 관측 실패를 정상/성공으로 확정하지 않는다. Git/PR 관측 동안 DB writer·실제 호출 자리를 점유하지 않으며 적용 전 같은 작업/소유권을 재검사한다.
- [ ] 기존 작업에서 이미 저장된 포괄적 OID 차단도 현재 원인별 재평가 경로로 보내 해소 가능한 대상만 재개한다. 사용자의 실제 질문·권한 거부·독립 차단과 작업물/양쪽 commit·intent는 보존한다. 강제 reset·DB 직접 수정·새 provider/유료 probe로 우회하지 않는다.
- [ ] 확인한 `tests/test_recovery_runtime.py`·`test_execution_workspace_phase.py`·`test_execution_retry_policy.py`·`test_task_remote_inputs.py`의 실제 정책/SQLite·원격 double을 재사용한다. PRODUCT·ARCHITECTURE의 소유 복구 절에 보완한 사유별 결과만 통합한다. DB 요청 경계와 일반 단계 재배정은 G-303/G-297/G-307에서 소비하고 별도 retry 엔진을 추가하지 않는다.

## Validation

- Worker는 위 모듈의 변경 관련 최소 unit을 실행한다. 실제 recovery 판단·checkpoint/실행 상태와 제어된 원격 관측을 연결해 자기 push 후 시점 차이·후속 원격 전진·조회 실패/lease 경합을 재관측/대기로, 다른 origin/branch/PR·타인 OID를 보존/거부로 구분한다. reason 상수만 바꾸고 정상 결과를 mock해 판단을 대신하지 않는다.
- 형제 verify를 Event로 유지한 상태에서 대상의 재시도 시점 전 호출 0회·해소 뒤 같은 실행 재개·독립 작업 진행을 검사한다. 완료한 commit/push/물리 Agent 호출 수와 원래 session·실패/교정·reservation·양쪽 commit·intent가 보존돼야 한다.
- 저장된 기존 OID 차단의 재평가에서 입력 지문 변경 없이 해소된 현재 원인만 풀고 명시적 사용자 판단·독립 차단·종료 불명은 남긴다. retry/usage/자원 대기 중에는 runtime 원격 조회 0회, 실제 복구 단계 진입에서는 G-312의 TTL 적용 확인을 사용하며 캐시된 종료 결정 뒤에는 추가 조회·새 writer 0회여야 한다. 코드 동일은 기존 retry 순서로 진행하며 사용자 pause를 삼키지 않는다.
- `tests/test_worker_checkpoint_publication.py`의 자기 push/후속 입력 분리·중단 복구와 `tests/test_task_scheduling.py`의 Review/usage/retry 시점 보존 회귀는 재사용한다. 실제 targeted 3회·보고/권한·branch 삭제 차단과 사용 한도 무probe assertion은 유지한다. 이미 직접 구현된 같은 실행 retry 테스트를 새 구현 작업으로 반복하거나 폐기하지 않는다.
