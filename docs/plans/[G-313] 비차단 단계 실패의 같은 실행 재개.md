## Purpose

Worker·verify·Reviewer·게시·복구의 비차단 실패를 재시도 대기와 실제 조건 대기로 구별해 같은 실행에서 필요한 재검증·교정으로 연결한다. G-297의 작업별 대기·재배정과 G-311/G-312의 runtime 확인·재시작을 소비하고, 단계 handler가 예산 소진이나 새 테스트 근거 부재를 다음 외부 실행 전용 pause로 반환하는 남은 정책을 바꾼다.

현재 `recovery/recovery_runtime.py:decide()`는 transient/reconcile 묶음 소진과 `TARGETED_TEST_CORRECTION`의 attempts에 PAUSE를 반환한다. Worker는 새 targeted 근거 부재를 attempts=1로 보내고 Review 교정의 외부 실행별 예산 소진도 별도 PAUSE로 처리한다. `agents/agent_invocation.py`는 제한된 CLI retry를 이미 수행한다. 이 기록·분류·세션 복구와 실제 최종 차단은 재사용한다.

## Acceptance Criteria

- `REMOTE_OID_UNCERTAIN`·`PUBLICATION_OWNERSHIP_UNCERTAIN` 등 포괄적인 Git 상태 불확실성을 즉시 FINAL_BLOCK하지 않고 최신 Manager 게시 intent·checkpoint·PR/branch·원격 OID를 같은 시점에 재관측한다. 정상 HEAD/OID 전진·push/DB 기록 시점 차이·lease 경쟁은 통합·재검증이나 해당 자원 대기이며, 확인된 다른 저장소/작업 소유권이나 복구 불가능한 상태만 대상 범위로 차단한다.
- 재시도 예산 소진·다음 실행 자동 재개·사용량/CPU/Git/DB 자원 대기 등 실제 복구 가능성이 있는 상태는 사용자 조치 요청이나 Telegram 알림으로 전환하지 않는다. 명시적 사용자 결정이 필요하거나 실제로 자동 복구가 불가능한 최종 중단만 R-053의 메시지 판단 대상으로 넘긴다.

- R-055/R-091: 새 개별 테스트 실행 근거 없는 Worker 실패 보고는 실제 실패 streak에 더하지 않으며, 실제 차단 조건이 없으면 같은 작업·session에서 실제 재검증/교정을 다시 배정한다. 형제 verify 종료·runtime 재시작·외부 실행을 재개의 조건으로 요구하지 않는다. pending 수집은 기존 자료 재수집을 우선하며 살아 있는/종료 불명 writer에 새 Worker를 겹치지 않는다. 저장 VERIFYING 또는 verify slot 배정 뒤의 수집 대기는 Worker 근거 없는 실패 보고와 구별해 기존 Worker 결과·session·후보를 보존하고, 조건 해소 뒤 같은 실행의 검증 진입으로 돌아간다. 세 번째 실패가 재수집되면 기존 원자 차단을 따르며 새 Worker나 verify로 우회하지 않는다.
- 일시 CLI 실패·Review 교정 등 실행별 retry 묶음이 소진돼도 실제 최종 차단이 아니면 작업을 보존한 재시도 대기 후 같은 실행에서 재개한다. 짧은 묶음·대기와 누적 실패/교정 감사를 구별하며 새 run ID·session·후보·runtime으로 이력을 초기화해 예산을 우회하지 않는다. 대기 없이 같은 실패를 반복하거나 재배정마다 이미 실행한 물리 호출/외부 효과를 반복하지 않는다.
- 모든 비차단 단계 재개는 runtime 변경 확인을 먼저 통과한다. 교체 필요 시 G-312의 안전 인계 뒤 동일 작업에서 이어가며, 코드 동일이면 G-297의 수동 제출→RETRY→일반 재개→신규 순서로 재배정한다. 대기 중 독립 작업·운영 요청·원격 runtime 확인이 계속되고 관리 단위·자리·timeout은 기존 의미를 유지한다.
- 실제 동일 targeted test 연속 3회, verify/Review의 실패 지문·프로토콜/명세 교착·문서/완료 보고의 최종 소진, 명시적 사용자 결정·원격 branch 삭제·소유권/권한 등 기존 실제 차단은 유지한다. 사용 한도·필수 입력·종료 불명·공유 자원의 미충족은 해당 조건의 확인 대기로 남기며 해소 근거 뒤 같은 실행에서 재개한다. 사용 한도/정책 거부를 새 session·provider 전환·유료 호출 probe로 우회하지 않는다.
- 실패·기록 오류·중단·재시작에서도 원래 provider 결과/사용량·피드백·개별 테스트 집계·작업물·session·checkpoint·수동 수락 순서를 보존한다. 대기 해소는 verify/Review/게시 성공·질문 승인·프로젝트 완료가 아니다. R-082의 같은 실패 planning 입력 재호출 금지와 독립 작업 허용은 유지하며 새 Planner 호출 조건을 만들지 않는다.

## Validation

- Worker는 위 모듈에서 변경 경계의 최소 unit만 실행한다. G-299에 해당하는 형제 verify를 Event로 붙들고 G-298에 해당하는 Worker가 새 targeted 근거 없이 실패하도록 한다. 실제 파서·recovery 판단·저장·대기/재배정을 연결해 형제 verify 반환 전에 새 테스트 실행/교정이 시작되고 이전 결과·session·streak·관리 개수는 유지되는지 확인한다. 최종 코드 RETRY 상수만 주입해 성공을 대신하지 않는다.
- 짧은 retry 묶음 소진→clock 대기→원인 해소→같은 외부 실행의 성공과 지속 실패→다음 대기를 검사한다. 대기 전 재호출은 0회이고 독립 Worker/Review·운영 요청이 진행해야 한다. Review 네 번째 교정은 대기를 거쳐 실제 새 turn으로 집계되며 총 교정/지문/level 이력은 초기화되지 않아야 한다. 기존 `test_distinct_review_issues_pause_before_fourth_worker_correction`·`test_review_issue_in_changing_sets_pauses_after_three_corrections`는 이 새 결과로 개정하고 지문/집계 assertion을 보존한다.
- 같은 테스트 실제 3회·verify/Review 실제 최종 소진·보고 오류·사용자 판단·사용 한도·권한/정책 거부·remote branch 삭제·종료 불명은 별도로 확인한다. 조건 대기 중 종료/사용 한도/필수 입력 해소 근거가 없으면 호출은 0회이고 해소 후에만 기존 단계에서 재개해야 한다. `tests/test_execution_verify_phase.py`의 저장 VERIFYING·slot 배정 후 pending 회귀를 실제 재배정 fixture에 연결해, 자료 미확정 동안 effect 0회·검증 실패 집계 불변·미시작 자리 반환과 독립 작업 진행을 확인한다. 종료/수집 근거 해소 뒤 같은 실행에서 새 Worker 없이 필요한 검증을 재개하고, 성공 receipt 재사용이면 기존 run만 연결해야 한다. gate 자체의 같은 수집/차단 assertion은 복제하지 않는다.
- Worker·부분/전체 verify·Reviewer·게시·복구의 대표 비차단 실패를 각 기존 fixture에 연결한다. runtime 코드 동일/변경/관측 실패에서 각각 재배정/안전 인계/원인 보존으로 갈리고, 재시작 후 작업·session·실패/교정·예산·예약과 이미 완료한 외부 효과가 보존되는지 확인한다. 정상 PR/작업 완료까지 반복하는 불필요한 Git/CLI 통합은 추가하지 않는다.
