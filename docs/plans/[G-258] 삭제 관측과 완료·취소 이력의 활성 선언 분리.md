## Purpose

검증한 원격 문서 삭제와 완료·취소·예약 이력을 함께 관측하되 현재 선언과 감사의 수명을 분리한다. 실행 row가 없거나 완료 문서까지 삭제된 경우에도 확인 가능한 삭제를 복구 입력으로 제공하고, 역사 source의 부재를 활성 오류나 신규 ID 등록으로 오인하는 경로를 교정한다.

## Acceptance Criteria

- 한 원격 revision의 문서·마지막 채택 선언·최초 게시·Merge·취소·예약 및 보류 근거에서 Requirement·ExecPlan의 실제 삭제를 식별한다. rename·내용 보존 archive·로컬에만 있는 삭제·원격 조회 실패와 구분하며 삭제·신규 추가 동시 관측으로 ID 변경을 추정하지 않는다. 일괄 삭제·등록 전 삭제·실행 row 없이 남은 예약과 보류도 확인 가능한 원문·revision·identity 및 미확인 이유를 제공한다.
- 실제 Merge 증명과 완료·취소·ID 예약 감사는 문서 부재 뒤에도 보존된다. 그 이력만 남은 문서의 source·링크 부재는 활성 선언 오류나 새 계획·`unknown-plan-id` 예약 충돌을 만들지 않으며 실제 MERGED 선행 충족은 유지된다. 완료를 취소로 바꾸거나 파일 부재를 Merge 증거로 만들지 않는다.
- 계속 실행하는 작업의 유효 source·dependency와 실제 identity 충돌 검사는 유지한다. 같은 ID의 재등장은 취소 해제·READY 재등록의 근거가 아니고, 번호 공백은 누락 판정에 쓰지 않는다. 역사적 문서라는 경로만으로 source 검사를 생략하지 않고 검증된 이력과 현재 선언 자격을 구분한다.
- catalog·일반 및 유지보수 Planner 입력·source 읽기·Requirement 판단과 archive·dependency와 우선순위 선택·기존 조회가 같은 현재 관계와 감사 구분을 소비한다. 철회·완료 감사만 남은 항목을 활성 작업이나 완료 대기로 재추가하지 않는다. 실제 미충족 목표·독립 보류·수동 예약은 보존한다.
- 과거 원문 조회 실패는 그 대상의 미확인 근거로 남고 확인 가능한 독립 입력의 검토를 막지 않는다. 원격·저장 snapshot 경쟁과 재시작은 검증되지 않은 삭제·관계 해제·완료 성공을 만들지 않으며 같은 관측을 반복 등록하지 않는다.

## Implementation

`catalog/remote_deletions.py`, `catalog/execplan_catalog.py`, `storage/execplan_catalog_state.py`와 현재 source resolver·Merge proof·ID 예약 경계를 대조한다. 기존 삭제 증명의 원문·hash·ancestry 확인을 재사용하고 현재 선언 자격과 보존 감사의 판단을 공통 소비자에 전달한다. archive 파일의 source를 일괄 무시하거나 가짜 선언·새 성공 상태를 만들어 graph를 통과시키지 않는다. 저장은 기존 호환 계약 안에서 유지하고 운영 SQLite를 직접 교정하거나 비가역 migration을 도입하지 않는다.

이 작업은 관측·관계 조회를 교정한다. Requirement 삭제의 의미 판단·문서 게시는 G-259, 실행 이력 있는 작업의 현재 취소·수명 정리는 G-260, 자원 삭제는 G-261이 담당한다. G-257의 기존 선행 보류와 복구 게시 구분을 재구현하지 않는다. 실제 구현된 관측·역사 조회 계약만 PRODUCT·ARCHITECTURE에 반영한다.

## Validation

- `tests/test_execplan_catalog.py`, `tests/test_execplan_catalog_state.py`, `tests/test_project_catalog_refresh.py`의 최소 targeted unit으로 완료 Requirement와 MERGED 작업 동시 삭제, 완료 작업을 필요로 하는 활성 후속 작업, 취소·예약만 남은 ID 및 같은 ID 재등장을 확인한다. 실제 parser·resolver·정책·SQLite를 사용하고 Git·PR 관측만 mock한다.
- `tests/test_incremental_planning.py`, `tests/test_catalog_scheduling.py`, `tests/test_requirement_retirement.py`의 관련 fixture에서 일괄·등록 전·row 없는 삭제, 원문 부재, 정확한 rename/archive, 유효 활성 source 오류와 미확인 관계 보존을 확인한다. 삭제된 감사 문서 때문에 독립 입력 조회가 실패하거나 종료 감사가 신규 작업으로 선택되지 않아야 한다.
- Manager 전체 verify는 최초 게시·Merge·취소·ID 예약 보존, 실제 identity 재사용 거부, 독립 READY 지속과 활성 Requirement의 미충족·draft 대기를 유지한다. Reviewer는 역사 조회 예외가 활성 source·dependency gate까지 완화되거나 삭제만으로 성공이 합성되는 경우를 blocking issue로 확인한다.

## Decision Log

- 현재 `reference_issues`는 실행 row의 부재를 기준으로 하고 `recovery_goals`의 missing-plan 입력도 실행 row에 연결된다. reconciliation은 부재한 완료/예약 이력에 missing-plan을 만들며 문서 source 검증은 archive에도 적용된다. 이미 구현된 무소유 READY 취소·참조 판단을 유지하고 이 새 관측·이력 구분만 보완한다.
- G-189는 기존 전체 차단 감사다. 그 계획에는 G-257이 기록한 기존 선행 보류·게시 제약이 있어 이번 빈 `deleted_goals` snapshot에서 dependency를 임의 제거하거나 개정하지 않는다. 이 계획의 근거와 후속 삭제 구현은 G-189의 새 유효 snapshot 감사에서 연결할 수 있으며, 이 작업의 Merge로 전수 감사나 프로젝트 최종 전문 확인을 완료하지 않는다.
- complexity medium: 기존 원격 관측·catalog·source·감사 경계에서 현재 실행 자격과 검증된 이력을 구분하는 계약이 명확하다. risk high: 잘못된 분류는 필요한 선행을 충족한 것으로 선택하거나 취소된 ID를 재실행시킬 수 있다. 원본 선언·Merge proof·예약과 관측 근거를 보존해 수동 재평가할 수 있어야 하며, AC와 회귀에서 실제 활성 오류·재등장·무근거 성공을 거부한다.
