## Purpose

운영 로그에서 일시 중단·예상된 대기와 최종 실패를 구분하고 수동·복구 명령의 실제 대상과 다음 행동을 연결한다. 문서 수정본의 원문 stdout에는 운영 로그가 섞이지 않게 한다. 직접 구현된 공통 포맷·ContextVar·bootstrap 실행 ID·주기적 reporter를 재사용하며 실행 상태·종료 코드·명령의 의미를 바꾸지 않는다.

## Acceptance Criteria

- PRODUCT 운영 로그와 ARCHITECTURE의 운영 로그 정책: 프로젝트 결과·전체 실행 집계의 수준은 확인한 결과 종류와 복구 판단에 따른다. `TRANSIENT_PAUSE`·사용 한도 대기·접수 후 복구 대기의 비정상 종료 코드만으로 최종 ERROR를 표시하지 않는다. 실제 최종 실패·차단은 ERROR, 자동 재시도 가능한 실패는 WARN, 정상 진행·예상된 대기는 INFO로 구분하고 다음 외부 실행·사용자 조치·조건 대기를 설명한다. 기존 exit code와 SQLite 전이·실패 및 Telegram 정책은 유지한다.
- `manual start/complete/submit`, `recover`와 기존 대상 명령은 확인한 repository·계획 또는 요청 범위를 자신의 로그 문맥으로 사용한다. 준비 시작·수락·게시 확인·실행 대기·실제 처리 완료를 구분하며 다른 프로젝트/계획의 문맥을 이어 쓰지 않는다. 처리 종료·예외 뒤 이전 문맥을 복원하고 병렬 프로젝트 문맥은 격리한다. 긴 명령 처리의 대상·경과·관측 가능한 대기는 기존 reporter로 표시하되 실제 실행이나 진척률을 추측하지 않는다.
- `document-drafts show/generate/create`의 결과 전용 stdout은 기존 `review_artifact_bytes()`와 같은 bytes로 유지한다. 부모 bootstrap과 runtime 자식의 운영 로그는 모두 stderr로 보내고 문서 원문·diff를 운영 로그 포맷으로 바꾸지 않는다. 출력 경계는 실제 파싱한 명령·출력 계약으로 선택하며 repository 등 값에 우연히 포함된 `--json`·`--raw` 문자열로 선택하지 않는다. 아직 없는 CLI 옵션·명령을 추가하지 않는다.
- 선택적 출력·진행 관측 실패는 명령의 원래 성공/실패·예외·요청·소유 intent·작업물·session을 바꾸지 않는다. 새 모델·Git/PR 조회·검증을 로그 작성 목적으로 실행하지 않으며 비밀값·prompt·문서/코드 전문을 운영 요약에 넣지 않는다. 필수 상태·격리·소유권 증거의 실패는 기존 경계대로 처리한다.

## Implementation

- [x] 확인한 `loop_manager_internal/application/project_runner.py:run_project_result()`·`_run_project_result()`와 `application/scheduler.py:run_registered_projects()`의 출력 수준을 기존 `application/contracts.py:ProjectRunKind`·복구 결과와 연결한다. 일시 Git lock의 `error=True` 출력과 `application/commands.py:execute_local_recovery_request()`가 접수/미해결 의미로 반환한 비정상 코드를 최종 실패로 오인하는 집계를 함께 대조한다. 전체 집계는 실제 프로젝트 결과를 요약하며 단계/프로젝트 사건을 중복 생성하거나 결과 종류·종료 코드를 수정하지 않는다.
- [x] 확인한 `loop_manager.py:main()`에서 파싱된 명령으로 결과 전용 stdout 문맥과 확인 가능한 대상 문맥을 bootstrap 전에 선택한다. `runtime/bootstrap.py:run_runtime_child()`의 실행 ID 전달을 재사용하고 자식은 자기 파싱 결과로 출력 경계를 선택한다. 내부 권한·runtime 소유 표식·명령행 비밀값 경계를 넓히지 않는다.
- [x] 확인한 `application/commands.py:_document_drafts_command()`·`recover_local_environment()`·`execute_local_recovery_request()` 및 `application/manual_work.py:manual_command()`의 의미 있는 접수/처리 경계에 기존 `runtime/operation_events.py:log_context()`·`activity()`·`progress()`를 연결한다. 접수와 실제 실행, 즉시 실행과 다음 run 대기를 구분하고 이미 기록된 단계는 재사용한다. 읽기·출력 때문에 DB schema나 요청 상태·소유 예약·Git 게시 경계를 바꾸지 않는다.
- [x] 확인한 테스트 fixture로 아래 회귀를 추가한다. PRODUCT·ARCHITECTURE의 운영 로그 설명은 해당 누락의 실제 구현과 필요한 부분만 정합하게 통합하고 새 정책·승인·로그 보존 기간을 만들지 않는다.

## Validation

- Worker targeted unit은 `python3 -m unittest tests.test_operation_observability.OperationObservabilityTests`와 `tests/test_execution_progress_logs.py`에 추가하는 명령/결과별 최소 unit case를 실행한다. scheduler·bootstrap·provider 경계는 mock으로 처리하며 실제 log formatter·문맥과 명령 선택을 검사한다. 기존 Git·CLI 통합 테스트를 Worker 명령에 포함하지 않는다.
- 프로젝트/전체 집계에 completed·waiting·usage pause·transient pause·configuration/operational error·blocked·runtime handoff를 제공하고, 비정상 코드의 일시 대기는 ERROR가 아니며 실제 최종 실패는 정확히 ERROR인지 확인한다. 결과·종료 코드·호출 횟수와 다음 행동을 함께 대조한다. 동시 두 프로젝트와 순차 다른 대상 명령 뒤 문맥이 섞이지 않아야 한다.
- 모의 bootstrap 부모/자식에서 `document-drafts show/generate/create`의 기존 원문 bytes가 stdout에 정확히 한 번 있고 INFO/WARN/ERROR·주기적 로그가 stderr에만 있는지 검사한다. repository 인수의 `--json`·`--raw` 문자열은 명령 출력 정책을 바꾸지 않아야 한다. 기존 `tests/test_bootstrap_entry.py`의 interpreter·인자·실제 lock 계약은 유지하고 동일 연결의 실제 CLI 실행을 새로 반복하지 않는다.
- `tests/test_local_environment_recovery.py:LocalEnvironmentRecoveryCommandTests`의 실제 SQLite·모의 실행 fixture와 `tests/test_manual_work.py`·분리된 `tests/test_manual_work_publication.py`·`tests/test_manual_concurrency.py`의 기존 소유/게시 회귀를 재사용한다. 공통 `tests/support/manual_work_case.py`를 사용하되 로그 검사는 최소 unit case로 분리해 복구 접수 후 대기·실제 실행·수동 수락/거부와 관측 실패에도 요청/intent·작업물·기존 결과가 보존되는지 확인한다. Agent·verify 실행과 외부 Git 동작을 로그 검사 때문에 추가하지 않는다.
- 부분/전체 verify는 기존 command dispatch·bootstrap 전달·수동/복구 수락·프로젝트 결과 집계와 비밀 비노출 회귀를 유지한다. 선행 부분 검사와 로그 회귀 통과를 전체 검증·Review·사용자 Merge 성공으로 확대하지 않는다.
