## Purpose

실제 최종 차단 없이 지속 실패를 사용자 조치 알림으로 보내는 경로를 제거한다. 같은 대상·원인의 PLAN_BLOCKED 또는 PROJECT_BLOCKED가 확정되면 기존 checkpoint를 포함한 차단 알림으로 통합하고, 과거 지속 실패 알림의 남은 전송에도 새 조건을 적용한다.

## Acceptance Criteria

- WORKING의 targeted unit test 실패·worker_correction 두 번·지속 실패 판정·연속 외부 실행 횟수만으로 실패/사용자 조치 알림을 생성하지 않는다. 자동 교정·다음 외부 실행 재개 대기는 무통지이며 다른 계획이나 다른 원인의 차단을 근거로 사용하지 않는다.
- 같은 실패의 실제 최종 차단과 checkpoint 결과가 확정된 뒤 확인된 조치·보존 상태를 담은 기존 차단 알림만 한 번 생성한다. 별도 persistent_execution_failure 알림은 추가하지 않는다. 사용자 판단·독립 차단·대기 및 실제 재개 사건은 기존 조건을 유지한다.
- 전송 직전 같은 대상·원인의 현재 차단 근거를 다시 확인한다. 실제 차단 없는 legacy 지속 실패의 미전송 메시지와 부분 전송의 남은 조각을 취소하고, 같은 실제 차단에도 별도 지속 실패를 중복 전송하지 않는다. 이미 전송한 조각·attempts·오류·원문·실패/복구 감사는 보존하며 row 삭제로 취소를 대신하지 않는다.
- 취소·차단 전송 경합과 재시작에서 남은 조각을 다시 보내거나 과거 실패를 성공으로 바꾸지 않는다. 알림 필터를 이유로 실행 단계·교정 횟수·session·실패 이력을 초기화하지 않는다. 전송 실패와 Telegram 비활성화는 정상 작업을 막지 않는다.
- PRODUCT의 Telegram 조건과 ARCHITECTURE의 outbox/전송 설명에 최종 차단 통합과 legacy 지속 실패의 취소 예외를 반영한다. 그 외 정책 변경 전 outbox의 내용·주의 수준·이어 전송 계약은 유지한다.

## Implementation

notifications/events.py의 지속 실패 생성·차단 통합과 notifications/delivery.py의 조각 claim 경계를 기존 block incident·outbox transaction에 연결한다. storage/recovery_state.py의 실제 실패 관측·외부 실행 집계는 진단으로 보존하고 알림 자격과 분리한다. 확인된 대상·원인의 차단만 사용하며 과거 실패 payload로 새로운 사용자 조치를 추측하지 않는다. 기존 취소 표식·전송 cursor와 checkpoint를 재사용하고 새 알림 저장소나 실행 차단 정책을 만들지 않는다.

## Validation

- Worker는 test_notification_events.py·test_execution_failure_boundary.py·test_recovery_state.py의 관련 최소 unit case를 실행한다. 실제 SQLite와 실행/복구 판단으로 차단 없는 반복 실패·교정 지속·다른 대상/원인 차단·실제 최종 차단의 outbox 차이와 실패/session 보존을 검사한다. 과거 연속 실패만으로 알림을 기대하던 assertion은 새 요구와 대응시키며 실패 진단 검사는 유지한다.
- test_notification_delivery.py·test_notification_incidents.py의 기존 fixture로 legacy 미시도·시도 실패·부분 전송·이미 전송된 조각, 차단 확정/해제와 claim 경합·재시작을 확인한다. 실제 Telegram은 mock으로 대체하고 취소 감사·단일 차단 알림·원문/횟수 보존을 검증한다.
- Manager 전체 verify는 checkpoint 결과 확정 후 차단 알림, 통지된 사건의 재개·독립 작업·대기·legacy 다른 사건 이어 전송과 전송 실패 중 실행 지속 회귀를 유지한다. Reviewer는 실제 차단 없는 실패 전송과 감사 삭제가 남지 않았는지 읽기 전용으로 확인한다.
