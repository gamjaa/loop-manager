## Purpose

직접 구현된 DB 부재 표식·정확한 원격 HEAD의 worktree 생성·PR 전체 이력 조회를 재사용해 새 환경의 인수 자격과 실제 MERGED의 terminal 완료를 보완한다. 과거 검증을 추정하지 않는 열린 PR 재개와 닫힌 PR 보류를 실제 실행 경로에서 확인한다.

현재 `created_from_absence`는 DB 전체의 영구 표식이고 `workspace_seen`은 계획별 준비 완료 뒤에만 기록된다. 부재 초기화에서 복구하는 대상과 이후 기존 DB의 행 누락을 충분히 구분하지 못한다. PR 이력의 MERGED 우선 선택은 호출자의 등록 base 대조 전에 이루어지며, 공통 terminal 처리에는 `remote_base()`·cleanup 이후에 Merge를 저장하는 순서가 남아 있다. 기존 함수별 회귀만으로 이 인수→실행/완료 연결을 완료로 판정하지 않는다.

## Acceptance Criteria

- R-093: DB 전체 부재에서 명시적 초기화·재등록으로 이어진 새 환경의 복구 범위를 증명한다. 손상·읽기 불가·일부 작업 행 유실·오래전에 생성된 DB의 미관측 계획을 영구 `created_from_absence`만으로 인수하지 않는다. 기존 DB·작업·session·검증 근거를 덮어쓰거나 DB를 자동 재생성하지 않는다.
- 같은 고정 원격 revision의 등록 repository·base·활성 ExecPlan identity/선언·정확한 관리 branch·전체 OID를 대조한 대상만 인수한다. 로컬 branch/worktree가 있으면 저장된 인수 intent와 실제 소유권·HEAD·작업물까지 확인하며 이름 또는 동일 OID만으로 사용자 자원을 탈취하지 않는다.
- PR 없는 대상은 정확한 원격 HEAD의 관리 worktree·새 소유 상태·새 Worker session으로 시작한다. 중단 뒤에는 같은 인수 intent/대상으로 재개하며 원격 전진·삭제·경쟁은 재관측/보존한다. 진행 중인 이전 환경의 writer를 자동 조율하거나 동시 환경 지원을 추가하지 않는다.
- PR 전체 이력의 head/repository/base와 현재 선언 관계를 검증한다. 조회 실패·일부 응답·상한 도달·복수 OPEN·알 수 없는 상태·불일치 대상을 PR 부재나 완료로 바꾸지 않는다. 유효한 MERGED가 없고 정확한 OPEN 하나이면 같은 URL·branch를 연결하고 새 PR을 만들지 않는다. CLOSED unmerged만 있으면 명시적 처리 결정까지 보류한다.
- 유효하게 연결된 실제 MERGED는 원격 branch 부재나 merge commit의 현재 base ancestry와 무관하게 Worker 없이 terminal 완료로 먼저 보존한다. 후속 fetch·base/catalog 동기화·cleanup·archive가 실패해도 MERGED를 되돌리거나 Worker/대체 PR을 시작하지 않고 남은 동기화만 재개한다. 검증된 Merge와 dependency 반영, archive의 실제 게시 확정은 각 기존 계약을 지킨다.
- 새 환경 DB에 검증 근거가 없는 OPEN 재개는 필요한 targeted test·verify·Review를 수행한다. commit·PR·외부 check로 Worker 성공·receipt·승인을 합성하지 않는다. 최신 문서 반영·dependency·사용자 판단·실제 자원 소유권은 계속 확인한다.

## Validation

- Worker는 위 기존 DB/PR 이력/Workspace handler의 변경 관련 최소 unit case만 실행한다. 부재 초기화·기존 정상/손상 DB·작업 행만 누락·표식이 오래 남은 DB·인수 중 재시작을 구분하고 기존 자료의 불변과 실제 인수 자격을 검사한다. Git/PR/provider 관측은 double로 제공하고 실제 판단·SQLite·파일 상태를 사용한다.
- PR 없음·정확한 OPEN·CLOSED만 존재·유효 MERGED와 새 OPEN 공존·다른 base/head/repository·복수 OPEN·조회 실패·상한 응답을 실제 `prepare()`에 연결한다. PR 없음/OPEN은 정확한 remote HEAD·새 session·무승인 상태를 확인하고 CLOSED·불명확 대상은 Worker/새 PR 호출 수가 0이어야 한다. 이미 존재하는 parser 단독 회귀를 그대로 복제하지 않는다.
- 실제 MERGED에서 branch 삭제·현재 base에 merge commit 없음·fetch 실패·cleanup 오류·archive 실패·DB 확정 뒤 재시작을 검사한다. Worker/재검증/대체 PR을 시작하지 않고 완료 상태·관측 PR·dependency 근거와 재시도할 후속 처리만 남아야 한다. source 동기화 실패를 Merge 전 상태로 되돌리는 기존 순서는 이 경계에서 허용하지 않는다.
- OPEN 재개에서 DB receipt/승인 부재를 실제 검증 단계까지 연결해 필요한 검증/Review가 생략되지 않는지 확인한다. session·작업물·기존 PR identity를 유지하며 중단 뒤 같은 요청·같은 PR을 사용한다. 실제 provider·모델은 호출하지 않는다.
- mock으로 증명할 수 없는 정확한 OID의 새 worktree 생성·로컬 충돌 보존·branch 삭제 상태의 재개는 기존 격리 Git helper를 사용한 최소 Manager 통합 회귀로 확인한다. 정책 조합마다 clone·bootstrap 전체를 반복하지 않는다. Windows 경로·인자·잠금에 영향이 있으면 기존 native 핵심 회귀 목록을 유지하고 Linux/mock 결과를 Windows 실환경 성공으로 기록하지 않는다.

## Decision Log

- 원격 branch 인수와 기존 DB의 개별 행 복구는 서로 다른 자격이다. 영구 DB 생성 표식만으로 두 경계를 합치지 않으며, DB 부재 복구의 확인한 범위·소유 intent를 보존한다. 사용자 branch의 작성자 이력 분석이나 여러 환경 간 lease 서비스를 추가하지 않는다.
- R-093의 terminal MERGED는 대상 작업과 연결된 실제 PR 상태를 뜻한다. 등록 대상 불일치는 인수하지 않되, 일치하는 Merge의 현재 base ancestry나 head branch 존속은 완료 조건으로 요구하지 않는다. 동기화 실패를 실제 Merge 취소로 바꾸지 않는 기존 제품 보장을 재사용한다.
- 직접 구현을 소급 계획하거나 이전 테스트 존재를 실행 성공으로 기록하지 않는다. G-307의 checkpoint push, G-303의 공통 DB 요청 처리, 기존 archive·Requirement 판단의 목표를 중복 구현하지 않는다.
- complexity high는 부재 초기화의 제한된 수명·인수 중단/경쟁·PR 전체 이력 identity·terminal 완료와 후속 효과 분리를 함께 보존해야 하기 때문이다. risk high는 잘못된 인수가 사용자 branch를 연결하거나 잘못된 완료/재개가 작업을 유실시킬 수 있기 때문이다. 정확한 선언/OID·소유권·짧은 CAS와 실제 효과/중단 회귀로 완화한다. 최초 level은 5다.
