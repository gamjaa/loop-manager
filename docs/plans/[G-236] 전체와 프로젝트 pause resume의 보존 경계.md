## Purpose

자동 실행 중에도 전체/프로젝트 pause를 접수해 새 작업을 막고 대상 프로세스 종료·작업 보존을 확인한다. 범위별 resume는 pause만 해제하며 자동 실행이나 독립 차단 해제를 수행하지 않는다.

## Acceptance Criteria

- R-061의 문서 보고 결합도 pause에서 보존한다. Worker 결과 원문·작업 base/후보와 작업별 `manager_metadata`의 `document-report:` 근거를 유지하며 저장 전·후의 pause를 결합 완료나 설명 승인으로 간주하지 않는다. resume 명령은 base 조회·보고 재결합/소비나 잘못된 base·과거 해시 오류 차단 해제를 수행하지 않는다. 다음 자동 실행만 기존 검증/게시 경계에서 같은 작업 base와 현재 후보의 문서별 patch를 대조한다. 원격 base 전진만으로 작업 base를 바꾸지 않고 rebase 완료 근거 뒤에만 통합된 target으로 전환한다. 작업 base 조회 실패·근거 부재는 후보·원문·진단을 보존해 기존 복구로 이어가며 실제 patch 변경·설명 결합 부재의 교정과 구별한다.

- pause [repo]는 먼저 요청을 저장하고 대상 Agent·verify·자식 종료를 유한 시간 안에 확인한다. 단계·session·작업물·진단·게시 intent를 보존하며 다른 프로젝트나 다른 기기의 수동 구현 종료를 주장하지 않는다.
- Git·게시 중단 결과는 현재 소유권·실제 원격·기존 복구 증거로 확인한다. 게시 전, 게시 후 DB 미적용, DB 적용 후 worktree 정리·최종 해제 대기를 구분한다. 적용된 catalog·목적별 성공 기준은 pause나 정리 실패로 되돌리지 않고, planning 소유권·결과·session·intent와 `publication_remote_oid`를 보존한다. worktree 제거 뒤 DB 해제 전에 중단돼도 제거된 경로를 재생성하거나 batch를 다시 적용하지 않는다. 별도 작업의 intent는 R-055의 실제 충돌 범위로 판단하고 pause가 그 intent·원인 차단을 정리하지 않는다. 종료·저장·게시 결과 미확인에서는 pause와 미완료 대상을 보존하고 완료·새 자원 사용을 허용하지 않는다. 재시작도 같은 요청을 이어간다.
- 전체 pause의 run은 bootstrap/runtime·원격·Agent·verify·알림 전에 안내·코드 0으로 종료한다. 프로젝트 pause는 해당 대상을 제외하며 명시 repo로 우회하지 않는다. 수락된 수동 제출·복구·유지보수의 자동 후속 처리도 pause를 준수한다.
- 전체/프로젝트 pause는 독립 저장하고 resume [repo]는 해당 범위만 해제한다. 기존 사용자 결정·차단·usage 제한·dependency·PR 대기는 유지하고 resume 자체는 작업을 시작하지 않는다.
- pause 중 조회·설정·제어·기존 수동 준비와 요청 접수는 가능하다. 정상 무변경/완료 0, 안전 거부·종료 미확인 1, 인자 오류 2이며 요청 저장과 실제 중단을 구분한다.
- R-082의 일반 planning 전환 중에도 pause는 실제 Planner·verify·Agent와 자식만 대상으로 종료를 확인한다. `planning_resume_plan_id`로 보존한 원래 작업, 별도 planning worktree·결과·게시 intent·오류와 실행/실패 이력을 유지한다. 보존한 rebase의 HEAD·index·작업물·원래 target·checkpoint도 유지하며 Git 표식만으로 실행 중 자식이 있다고 판단하거나 임의 continue/abort하지 않는다. `plan_input_invalid`가 안전한 START 관측으로 이미 해제됐어도 미시작 rebase intent와 기존 단계만 보존하며, START를 완료·게시 소유 근거로 바꾸지 않는다. 사용자 resume는 pause만 해제하고 planning 성공·영향 확정·rebase 완료·원래 작업 재개를 합성하지 않는다. 다음 실행의 planning 게시·DB 적용과 같은 작업 재개는 기존 R-082 gate를 따른다.
- R-091의 프로젝트 planning 배정 중단과 R-076의 사용자 pause를 구별한다. 프로젝트 준비·planning이 작업 배정 중단 중 Git 자원을 사용할 수 있어도 사용자 pause·runtime handoff·실제 자원 잠금은 계속 적용한다. Git 자원 대기·관측 중 또는 자동 해제의 상태 확정 전에 pause를 접수하면 추가 효과 없이 보존 경계로 반환한다. 이번 관측 lease는 반환하되 원인 작업의 intent·checkpoint·차단과 다른 프로젝트의 자원·작업은 유지한다. pause 중 허용된 수동 준비·요청 접수와 자동 후속 처리의 중단을 구분한다.
- R-055/PRODUCT의 targeted 기록 수명도 pause·resume에서 보존한다. 호출별 JSONL·디렉터리 identity·process receipt·미소비 결합은 종료/수집·저장이 불확실해도 남긴다. 저장된 VERIFYING의 초기 gate와 verify slot 배정 뒤 재확인 사이에서도 사용자 pause는 새 검증을 막고 Worker 결과·session·후보·미소비 자료를 보존한다. 배정 후 preflight에서 시작을 보류한 검증은 기존 미시작 호출 자리만 반환하고 새 검증 실행·실패·성공 receipt를 만들지 않는다. 이미 시작했거나 종료 불명인 검증에는 기존 종료 확인을 적용한다. resume 자체는 기록을 소비하거나 도달 표식·실패 이력을 초기화하지 않는다. 다음 자동 실행은 기존 호출 재수집을 거치며 후속 성공은 실패 횟수·도달 표식을 초기화하며, 해소되지 않은 연속 다섯 번째 실패와 수집 대기는 해당 작업의 기존 차단/대기 경계로 이어진다. 다른 작업의 자료와 살아 있는 수동 writer는 변경하지 않는다.
- R-023/R-091의 코드 변경 handoff·비차단 재시도 대기와 사용자 pause를 구별한다. pause 요청은 대기 중에도 처리하며 전체 pause가 저장되면 새 원격 효과·runtime/단계 호출을 시작하지 않는다. pause는 진행 중 호출의 기존 종료/보존 경계를 적용하고, 정상 handoff는 안전 반환을 기다린다. 사용자 resume가 실패/교정/테스트 이력·재시도 대기·독립 조건을 초기화하거나 handoff 승인·자동 작업 시작을 뜻하지 않는다.
- R-023의 관리 Claude 호출에도 같은 pause 계약을 적용한다. 준비 전/후·launch 결합 후 spawn 전 pause는 모델 실행과 새 실패를 만들지 않고, 실행 중 pause는 실제 process group 종료를 확인한 뒤에만 finished receipt·자리 반환을 확정한다. `prepared` 구성·원래 session·attempt의 결과/targeted 원문·attempt 밖 receipt와 호출 소유 Bash 임시 경로의 연결을 보존한다. 종료 불명은 중단 완료나 수집 완료로 바꾸지 않으며 resume 자체로 재실행·수집·source 정책 변경을 하지 않는다.

- R-093의 Manager checkpoint 요청·commit·push·결과 저장 사이 pause에서도 요청/intent·이미 생성한 commit·실제 게시/종료 근거·session과 미확인 prompt 전달 cursor를 보존한다. 새 원격 통합 중에는 원래 `before`·현재 후보·`accepted_work_branch`·검증 무효화 상태와 미완료 request를 함께 보존하고, 낡은 push intent가 이미 폐기됐으면 `retired_worker_checkpoints`의 원래 intent·관측 원격·`confirmed: false` 감사도 유지한다. 수용된 rebase의 후속 checkpoint도 같은 계약을 따른다. 진행 중 rebase와 일반 checkpoint 요청이 함께 남으면 원래 target·충돌 처리·요청을 보존하고 rebase 해결·완료가 일반 요청 소비보다 먼저 이어지게 한다. 완료 게시의 intent/result·현재 acceptance는 과거 차단 checkpoint가 unpublished로 바뀌어도 보존하며, 다음 자동 실행에서 현재 소유권·범위·실제 원격을 다시 확인한다. 현재 요청 commit·정확한 lease를 고정한 `rebase_publication_intent`·원래 acceptance와 게시 확인/DB 확정을 보존하고, pause 뒤 과거 deferred 표시나 최종 PR 대기를 이유로 요청을 버리지 않는다. pause/재시작·입력 수용·intent 폐기 자체로 push 성공·요청 완료·문맥 전달 확인을 만들지 않으며, 미확정 게시가 해결되기 전 새 Worker는 시작하지 않는다. Worker의 직접 Git 쓰기 금지와 완료 후보/복구점 구분을 유지한다.

## Implementation

- [ ] 최신 `execution/execution_worker_handler.py:_bind_document_report()`·`documents/pr_description.py:common_guidance_report()`의 staging 뒤 작업 base 조회·Git diff·지문 저장을 기존 pause 경계에 연결한다. 조회/저장 전후 중단 시 Worker 원문·후보·확인한 base·기존 근거를 보존하고, 다음 자동 진입만 현재 보고 검사를 소비한다. 진행 중 rebase를 최종 보고로 확정하거나 resume에서 최신 원격으로 base를 교체하지 않는다. Manager 결합 알고리즘·파서·해시 계산이나 resume 전용 복구를 새로 만들지 않으며 G-189의 후속 감사를 이 pause 작업의 선행으로 만들지 않는다.

기존 process/resource lock·subprocess 종료/verify 자식 조율·실행 checkpoint·수동 요청 저장을 재사용한다. bootstrap 이전의 pause 조회와 실행 중 요청 접수는 실행 잠금 소유자의 작업을 탈취하지 않는다. 필요한 호환 저장·요청/확인 전이는 기존 runtime/storage 경계에 두고 PRODUCT·ARCHITECTURE와 운영 안내에 반영한다. 새 daemon·실행 엔진·자동 병렬 Worker를 만들지 않는다.

- [ ] 확인한 `loop_manager.py`의 bootstrap 전 진입·`loop_manager_internal/application/commands.py`·`scheduler.py`의 등록된 선택 범위와 `application/project_service.py`의 실행 dispatch 경계에 pause 확인을 연결한다. 이미 반영된 `add/remove`와 다중 repo 정규화·미등록 사전 거부는 재사용하고 전체 pause가 이 준비보다 먼저 종료되는 조건을 유지한다.
- [ ] `loop_manager_internal/storage/runtime_state.py`의 planning 전환/재개와 `planning/selection_service.py`의 오류 보존을 읽는 제어 경계에서 실제 실행 대상과 보존 작업을 구별한다. pause/resume를 프로젝트 planning의 투영 비우기/재투영과 혼동하거나 같은 작업의 재개 identity를 초기화하지 않는다. 최신 base의 `planning/git_ports.py:execution_blocks_planning()`은 보존한 rebase와 다른 Git operation을 이미 구별한다. 이 정상 전환과 `execution/execution_state.py:recover_rebase_checkpoint()`의 소유권 복구를 재구현하지 않고 사용자 pause 전후에 원래 target·index·checkpoint가 보존되도록 연결한다. `planning/publication_service.py:_complete_publication_release()`·`planning/state_ports.py`의 `pending_publication_release()`/`complete_publication_release()`와 `storage/planning_publication_state.py:retain_planning_after_publication()`의 적용·정리·해제를 그대로 소비한다. 외부 관측/제거를 DB 요청 안으로 옮기지 않고 pause를 각 효과 진입에 연결하며, resume 명령은 정리·CAS·원래 작업 재개를 실행하지 않는다. 다음 자동 실행만 실제 게시/제거 근거와 현재 release identity를 재확인해 남은 단계를 이어간다. R-082의 실패 planning suspend·독립 선택은 G-278에 남긴다.
- [ ] 확인한 `runtime/resource_lock.py:resource_locks()`의 대기/획득 뒤 `_check_runtime_handoff()`와 보존 후보의 `runtime/handoff_gate.py`·`runtime/pause.py`를 통합한다. 최신 `git/manager_git_journal.py:has_conflicting_project_mutation()`의 `pending-git-scope` lease 취득·관측에도 같은 자동 실행 scope를 적용한다. `current_task`가 없는 프로젝트 준비·planning의 Git 접근 허용과 사용자 pause 검사를 함께 유지한다. `application/manual_concurrency.py:manual_preparation()`·`manual_git_protection()`과 `recovery/manual_work_recovery.py:release_wait()`의 호출자 `ExitStack`·상태 확정 전 identity/열린 lease 검사는 그대로 소비한다. pause 반환·예외에서 이번 관측이 취득한 lease를 반환하고 원인 rebase의 intent·checkpoint·차단은 보존한다. 공통 helper에 무조건적인 pause 거부를 넣어 기존 수동 준비·요청 접수까지 막지 않으며, 자동 후속 처리에만 대상 pause를 적용한다. task의 `PlanningDrain`과 runtime 전체 handoff도 보존하며 같은 scope·프로세스 종료 근거를 재사용한다.
- [ ] 보존 후보에 이미 있는 `loop_manager_internal/runtime/pause.py`·`tests/test_pause.py`와 최신 base의 `agents/invocation_service.py`·`agents/process_receipt.py`·`storage/agent_invocation_state.py`·`storage/targeted_test_state.py`를 통합해 pause 예외 전후에도 호출 결합과 미소비 기록을 유지한다. 후보의 과거 finally 수집과 새 durable 수집·별도 pending 표식을 대조해 필요한 차이만 보완한다. `execution/execution_verify_handler.py:_targeted_test_gate()`·`_verify_once()`와 `application/task_scheduling.py:verify_preflight()`·`scheduled_call()`의 배정 후 확인을 재사용해 pause 검사를 연결하고, 기존 callback·ContextVar 복원과 미시작 자리 반환을 유지한다. G-302의 재수집·원자 차단을 별도 pause gate로 복제하거나 수집·receipt 경로를 옮기지 않는다. `execution/execution_revision_handler.py:_post_effect_guard()`의 최신 context 재구성도 유지한다. 보존 후보의 코드·기록은 현재 Planner가 수정하지 않는다.
- [ ] 현재 `agents/provider_adapters.py:run_claude()`의 `checked_handoff`·`on_launch_prepared`·process group 종료/finally와 `agent_claude_preflight.py:ClaudeLaunch`의 attempt/짧은 Bash 임시 경로를 위 pause 경계에 통합한다. 기존 source 재검사·prepared 근거·실제 receipt/원문 저장을 소비하며 pause 제어 신호가 정책 오류·일반 CLI 재시도로 변환돼 모델을 다시 실행하지 않게 한다. 새 provider 종료 엔진·source 선택·collector를 만들지 않고 G-292의 일반 기록 전달 회귀는 재사용한다.
