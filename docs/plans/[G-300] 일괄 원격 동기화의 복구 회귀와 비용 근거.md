## Purpose

직접 반영된 R-092 일괄 fetch와 G-299의 ref 보존 교정을 재사용해 남은 중단·자원 경합·설정 보존 회귀와 같은 조건의 전후 비용 근거를 확보한다. 새 fetch 구현이나 검증 runner를 만들지 않으며, 기존 테스트가 이미 보장하는 조건은 그 근거를 연결한다.

현재 mock 회귀에는 복수 OID·신규 branch, 삭제·OID 경쟁의 1회 재시도, 실패 후 오래된 FETCH_HEAD 거부, 긴 stdin과 이전 단일 fetch의 pending 복구가 있다. 실제 Git 회귀는 설정된 refspec·prune/tag·dirty checkout 보존과 ref 쓰기 후 결과 기록 전 중단을 검사한다. 객체 수신 후 첫 ref 반영 전·한 ref 확정 뒤의 중단, 정확한 대상 ref 잠금과 fetch 간 겹침, 활성 submodule 설정의 실제 보존 및 전후 비용 비교는 별도 근거 보완이 필요하다.

## Acceptance Criteria

- branch 수와 변경 수를 달리한 정상 관측에서 목록 조회 1회·수신 0회 또는 1회를 검사한다. 다중 branch의 수신 누락·중복·잘못된 OID·commit 검증 실패와 재시도 소진 뒤 다음 실행 재관측을 실제 판단·journal로 확인한다. 기존 사례와 같은 조건/assertion은 재작성하지 않는다.
- 객체 수신 확인 뒤 첫 ref 반영 전, 한 ref의 결과 확정 뒤 다음 ref 반영 전, ref 쓰기 후 결과 확정 전 중단을 구분한다. 완료한 ref 쓰기는 반복하지 않고 남은 ref만 반영하며 원래 intent·결과·소유 reflog와 사용자 상태를 보존한다. 이전 버전의 pending 및 원격 변경 없는 재개는 기존 회귀를 유지한다.
- fetch 자원과 정확한 대상 ref 자원의 점유는 인수·강제 갱신 없이 처리한다. 일괄 수신과 단일 branch fetch가 겹쳐도 각 호출의 수신·FETCH_HEAD 확보가 같은 잠금 경계에 있고 다른 호출의 결과를 채택하지 않는다. 잠금 해제 뒤 같은 원격 입력으로 정상 재시도할 수 있다.
- 조회 뒤 일반 branch 삭제의 기존 추적 ref와 저장 PR head·작업 기록이 보존된다. 필수 base 부재·명령/인증/통신 실패와 반복 경쟁은 현재 실패 근거를 유지하며 catalog의 정상 입력으로 소비되지 않는다.
- 기존 최소 Git 회귀에 활성 submodule 재귀 설정과 다른 공유 ref를 향한 사용자 refspec·파생 HEAD 설정의 보존 근거를 보완한다. 공백·한글 경로와 특수 문자 branch의 기존 검증을 유지하며, 대상 밖 refs·태그·submodule 상태·checkout/index/파일이 보존돼야 한다.
- Windows의 UTF-8/LF stdin·경로 핵심 회귀가 선택 목록과 연결돼 있고 결과는 Linux/WSL 전체 검증과 구분된다. 환경 미수행을 PASS로 만들거나 검증 범위를 축소하지 않는다.
- 일괄화 전 revision과 현재 후보에 같은 원격 응답·branch 수·변경 수·초기 ref/journal·계측·반복 조건을 적용한 전후 비교를 남긴다. 조회/수신 횟수, 국소 경과 시간과 측정 환경·범위를 구분한다. 실제 원격의 지연·처리량 개선이나 전체 verify 절감률을 관측 없이 주장하지 않는다.

## Implementation

- [ ] 확인한 `tests/test_project_fetch_branch_deletion.py:ProjectFetchBranchDeletionTest`의 fake Git 관측·실제 journal을 재사용해 위 미검증 중단 위치와 정확한 ref 잠금·수신 겹침을 추가한다. 제어된 Event/Barrier와 실제 `runtime/resource_lock.py`를 사용하고, 실제 정책/저장 결과를 성공값 mock으로 바꾸지 않는다. 긴 목록 검사의 journal mock은 stdin 길이 계약용으로 유지하며 journal 완료 근거로 사용하지 않는다.
- [ ] 확인한 `loop_manager_internal/git/base_fetch_service.py`의 `_recorded_project_fetch()`·수신 파서·`_record_fetch_ref()`와 `git/manager_git_journal.py`의 결과 확정 경계를 중단 주입 위치에 대응시킨다. 검증으로 드러난 R-092 위반만 해당 기존 경계에서 보완하며 새 복구 계층이나 전역 상태를 추가하지 않는다. 완료한 ref 쓰기와 재개 시 필요한 객체 재수신을 구분한다.
- [ ] 확인한 `tests/test_plan_block_revalidation.py`·`tests/test_project_block_revalidation.py`의 같은 원격 입력 잠금 재시도와 `tests/test_checkpoint_adoption.py`·`tests/support/blocked_remote.py`의 실제 SQLite fixture를 재사용한다. 기존 잠금 분류는 직접 구현으로 소비하고, 일반 branch 삭제 뒤 저장 PR head·작업 기록 불변과 수신 실패의 입력 미채택에 부족한 assertion만 보완한다. G-297의 일반 작업 배정·예외 처리와 G-189의 전수 감사를 중복 구현하지 않는다.
- [ ] 확인한 `tests/test_origin_isolation.py`의 `test_bulk_fetch_keeps_configured_refs_tags_and_dirty_checkout`·`test_project_fetch_recovers_owned_ref_update_after_result_write_crash`를 먼저 대응시킨다. `tests/support/origin.py`·`tests/support/git.py`의 격리를 유지하고 submodule/shared-ref 설정 효과에 필요한 최소 native 준비만 확장한다. 정책 조합·세 중단 위치 전부를 실제 Git으로 반복하지 않는다.

## Validation

- Worker는 `tests.test_project_fetch_branch_deletion`과 관련 journal/plan/project recovery 모듈에서 실제 변경한 최소 unit case를 실행한다. branch 수 1/복수/긴 목록과 변경 수 0/일부/전체의 필요한 경계만 선택하고 기존 실패·삭제·재개 assertion과 대응시킨다.
- 중단 fixture는 기존 journal 파일과 ref 상태를 직접 검사한다. 첫 쓰기 전에는 ref 변화가 없어야 하고, 일부 확정/미확정 쓰기 뒤에는 완료한 `update-ref` 횟수가 증가하지 않아야 한다. 저장 원격 입력이 같은 재개와 새 경쟁 입력을 구분한다.
- 실제 fetch 잠금 보유 중 다른 단일/일괄 경로의 Git 호출이 시작되지 않는지 확인하고, 대상 ref 잠금에서는 해당 ref가 바뀌지 않아야 한다. 정상 해제 뒤에는 재시도 가능하며 원래 pending/실패 자료는 남아야 한다. 전용 스레드 시험을 실제 네트워크나 Agent 호출로 대체하지 않는다.
- 실제 Git 설정 보존 case는 관련 ref·태그·파생 HEAD·submodule 저장소·부모 checkout의 전후 상태에 assertion을 둔다. mock 인자에 `--recurse-submodules=no`가 있다는 사실만으로 native 효과 검증을 대체하지 않는다.
- 같은 통제 입력의 전후 비용 비교를 재현해 횟수와 시간·측정 한계를 기록한다. Worker의 국소 결과·Manager의 전체 검증·Windows native 핵심 회귀 결과를 구분하고 미실행 환경은 남은 확인으로 명시한다.
