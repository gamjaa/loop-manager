## Purpose

코드의 차단·중단 생성과 재개 경로를 추적하고 R-055의 현재 작업 입력·게시·sandbox 경계에 맞지 않는 잔여 처리를 교정한다. 직접 구현된 Git 접근 감시 제거·원격 작업 통합·삭제 브랜치 재시작·파일별 재작업을 소비자까지 감사한다. 원격 통합의 ignored 경로 보호 후속과 기존 선행 작업을 재사용하며 P1/P2 및 비Git 차단 감사의 미충족 범위를 보존한다.

## Acceptance Criteria

- R-055의 T01–T37을 실제 코드 경로·기존 회귀·필요한 교정·유지 이유에 연결한다. 기존 checkpoint·단계별 문서·ignored·로컬 동기화와 이번 delta의 직접 구현을 재구현하지 않는다. 과거 T01–T24 감사 기록을 새 37개 조건의 충족으로 합성하지 않는다.
- provider sandbox와 실제 호출 정책은 접근 권한을 강제하고, 쓰기 역할의 최종 결과·허용 문서·draft/User Decision 검증은 유지한다. Reviewer/점검 Planner의 읽기 전용은 내장 정책으로 확인한다. ref/config/HEAD/index/worktree 차이·과거 격리 ledger 부재를 접근 위반으로 귀속하거나 읽기 전용 역할에 사후 Git 범위 검사를 복원하지 않는다. 폐기된 진단의 동일 입력 자동 해소와 결과·session·실패/승격 감사 보존을 후속 소비자까지 확인한다.
- R-055의 D01–D12는 G-257–G-261의 확인된 삭제·복구 게시·현재 취소·소유 자원 정리 뒤의 실제 소비 경로에 연결한다. rename/archive와 삭제, 현재 선언과 종료 감사, 판단 게시와 실행 준비·실제 Merge를 구분하며 선행 계획의 목표를 전수 감사에서 중복 구현하지 않는다. G-261의 사용자 판단·실제 Merge gate를 생략하거나 정리 pending을 전체 차단으로 확대하지 않는다.
- 정상 원격 원본 기준 로컬 rebase는 과거 원격 작업 tip의 조상 관계나 checkpoint HEAD 일치만으로 거부하지 않는다. 현재 로컬 수용·새 원격 통합·게시 lease를 분리하고 실제 충돌·삭제·재작성의 영향 범위만 보존·보류한다.
- 게시 경쟁은 최신 원격 통합·후보 재검증으로 돌아가며 무조건 force push·lease OID만 교체하는 재시도는 없다. 중간 checkpoint 게시 실패가 로컬 입력 수용을 무효화하지 않는다.
- 같은 repository·origin·작업 branch·PR URL/head/base의 OID 전진은 보존·통합·재검증으로 처리한다. OID만 바뀌었고 구현 입력이 유효하면 필요한 verify·Review로 이어가며 Worker를 반복하지 않는다. 실제 대상 불일치·조회 실패·관측 경쟁·불명확한 삭제/재작성은 영향받은 자원을 보류한다. immutable 진단 ref의 다른 OID는 해당 게시·삭제만 보류하며 verify·Review나 독립 작업을 막지 않는다.
- Merge 전 Manager 게시 브랜치의 실제 삭제는 해당 작업의 명시적 재시작 대기로 처리한다. 일반 재실행·pause 해제·동명 ref 재생성으로 재개하지 않으며 PR이 있어도 승인된 reset 예외만 최신 원본의 새 실행을 준비한다. 실제 Merge 우선 처리·기존 작업물/PR/session/감사 보존·이전 성공/게시 intent의 새 실행 재사용 금지를 확인한다.
- 복구 불가 파일의 pinned 원본 복원은 해당 파일만 재작업으로 연결한다. 일반 문서 채택과 구분하고 확보 불가능한 과거 원형을 진입 gate로 요구하지 않는다. 다른 파일·현재 HEAD·사용자 교정·소유 operation target과 실패 기록을 보존하며 복원·OID 관측을 구현/검증 성공으로 기록하지 않는다.
- journal은 현재 자원·미완료 전이에만 적용하고 cleanup 실패는 완료 결과를 보존한다. 과거 확정 문서 게시와 최신 사용자 편집, diff 소멸의 실제 PR Merge·외부 목표 충족·구현 부족을 구분한다. NO_CHANGE만으로 최종 차단하거나 외부 충족을 MERGED로 기록하지 않는다.

- 실제 코드의 모든 block/pause/error 생성·해제 경로를 조건·scope·보호 규칙·자동 복구·사용자 조치·관련 테스트와 담당 ExecPlan에 연결한 목록을 이 ExecPlan의 Implementation/Decision Log에서 확인할 수 있다. 담당 작업은 참조로 연결하며 Worker가 다른 ExecPlan이나 frontmatter를 갱신하지 않는다.
- 문제가 없는 경로에도 검토 근거가 있고 오탐/과도한 중단에는 재현 가능한 코드·테스트·필요한 수정과 유지할 실제 위반의 회귀를 연결한다. 선행 구현이 바꾼 경로와 남은 불확실 범위를 구분한다.
- R-020·R-023의 정상 외부 base 전진·runtime B 선택 후 C 전진·파생 HEAD 변화와 R-072의 기록 변경을 Agent 결과·저장 선검증·계획/프로젝트 재평가·checkpoint에서 끝까지 대조한다. G-192·G-182의 함수별 PASS만으로 동일 원인의 재발 방지가 완료됐다고 판정하지 않는다.
- checkpoint cause/evidence/status 변경의 stale 요청은 R-055대로 취소·현재 원인 재검증되며, 그 identity 불일치만으로 새 프로젝트 차단·Worker 교정 횟수나 다른 계획의 진단 보존 거부가 발생하지 않는 근거를 확인한다. 실제 공유 안전 차단·원격 lease·소유권 경쟁은 유지한다.
- 일시 실패·실행별 한도·계획별 실패·공유 안전·승인·PR 종료·cleanup 보존을 구분한다. 동일 입력의 무한 호출/Git 쓰기/알림, 단순 지문 변경을 요구하는 이미 해소된 오탐과 독립 차단 일괄 해제를 감사한다.
- 로컬 base·Python 캐시는 R-056·R-059의 담당 계획을 참조한다. 운영 SQLite 사건의 수정/삭제나 빈도 주장을 하지 않으며 보관 Requirement는 과거 근거로만 읽고 후속 구현은 현재 PRODUCT와 활성 Requirement에 연결한다.
- 수동 준비의 수락 전 자원 충돌 거부와 수락 뒤 dependency·실행 자리 대기를 구분해 감사한다. 독립 준비가 자동 실행 projection을 교체하거나 실제 충돌·미종료 Agent·Git 작업·Planner 게시 예약을 우회하지 않으며, 거부된 요청이 자동 대기로 등록되지 않는 근거를 확인한다. 수락 뒤에는 등록 순서와 기존 단일 자동 변경 자리·정상 coordinator 순서를 유지한다.
- G-175 Merge 뒤 R-053의 차단 후 재개 규칙을 실제 Worker·Planner·PR 시작 소비자까지 대조한다. 독립 planning 오류가 남은 해당 계획의 재개, 다른 계획 시작의 무통지, 시작 전 거부, 부분 전송 중 해제·재시작과 전송 실패를 포함한다. 이전 차단의 scope·계획·원인과 실제 시작만 표시하고 해결 주체를 추측하지 않으며, 계획·프로젝트·planning 사건 및 일반 재개를 중복 통지하지 않는다.
- G-225 Merge 뒤 빠른 Planner의 물리적 시작도 같은 통지된 사건에 연결되는지 감사한다. R-053의 Planner 일반 시작·단순 실패·자동 재시도 무통지와 차단 후 실제 재개 조건을 함께 대조하며, 기존 outbox와 실패 이력의 보존 근거를 확인한다.

## Implementation

R-085 연관 감사는 최신 공급자별 공통 홈·호출별 임시 경로와 실제 소비 source를 기준으로 한다. 준비 중 설정 생성/교체는 최종 현재 설정의 검사에 연결하고, 사용하지 않는 과거 runtime config·개인 Hook/Plugin을 이유로 차단하거나 복원하지 않는지 G-263/G-264의 근거와 대조한다. 실제 프로젝트/관리 정책 충돌·소유권 미확인·최종 검사 후 변경·독립 차단은 유지한다. R-085 Non-Goals의 session/CLI·실계정/OS 호환성 미수행을 공통 홈 변경의 새 차단 gate로 쓰지 않으며 G-191의 독립 격리 목표와 실제 호출의 기존 미지원 거부는 유지한다. 아래 기존 전수 감사와 수행 기록은 보존한다.

- [ ] P0는 이번에 읽은 `agents/scope_validation.py`·`scope_lifecycle.py`, `planning/agent_ports.py`, `recovery/scoped_blocking.py`·`blocked_plan_reconciliation.py`와 실행 handler를 대조한다. 현재 결과·대상 검증과 역사 감사만 유지하며 폐기된 Git 감시 진단의 계획/프로젝트/planning/지속 실패 해소를 후속 소비자까지 확인한다. 선행 실패 슬롯 교정과 실제 sandbox 오류·독립 승인/Review 실패를 구분한다.
- [ ] P1은 git/managed_rebase_validation.py·managed_rebase_adoption.py, recovery/checkpoint_recovery.py·checkpoint_ownership.py·work_branch_integration.py·blocked_plan_reconciliation.py와 execution_ownership_handler.py에서 로컬 수용과 원격 게시 증명을 분리한다. 직접 구현된 현재 원격 통합·후보 단계 선택과 ignored 경로 보호 후속을 재사용하며 과거 ancestry·receipt·표식 완전 일치의 중복 gate만 교정한다.
- [ ] publication_resume.py·execution_publication_handler.py, git/publication_service.py·direct_rebase_service.py와 recovery/pull_request_recovery.py·pr_ownership.py·waiting_pr_service.py의 관측 경쟁을 기존 통합·재검증 경계로 연결한다. 현재 PR identity·후보·명시적 expected OID lease를 보존하고 `recovery/deleted_branch_restart.py`의 명시적 새 실행과 일반 재개를 구분한다. `git/rebase_documents.py`·`rebase_file_evidence.py`의 이미 구현된 파일 복원은 저장 결과·Worker 재작업·verify/Review의 실제 소비와 연결한다.
- [ ] P2는 runtime/bootstrap.py·registration_service.py, git/base_fetch_service.py·source_sync.py·source_rebase.py·merge_cleanup_service.py·manager_git_journal.py와 planning/maintenance 게시 소비자의 잔여 실패 전파만 교정한다. 선택 runtime revision·무관한 journal·cleanup_pending·과거 게시 확인과 현재 원격 입력을 구분한다. 새 `catalog/requirement_correction_publication.py`·`archive_service.py`와 `application/project_service.py`의 교정 진입 보류·진입 뒤 실패·confirmed 역사 재검사도 현재 경로에 포함하며, G-233의 구현을 다시 계획하지 않는다.
- [ ] 실행 Worker·verify·최신 base·게시 handler의 NO_CHANGE는 최신 목표와 실제 PR 상태를 확인해 Planner의 미충족 목표·관계 정리로 연결한다. 새 완료 상태·범용 복구 계층을 만들거나 MERGED 의미를 바꾸지 않는다.

- scoped_blocking·recovery state·catalog/planning/maintenance/execution와 cleanup 소비자를 코드 검색/직접 읽기로 감사한다. 목록과 근거는 이 ExecPlan 본문에 통합하고 담당 작업의 기존 근거는 읽기 전용으로 연결한다. 다른 계획에 필요한 선언·본문 개정은 원인과 경로를 보고해 Planner·Manager의 snapshot 검증·게시로 인계하며 새 운영 상태 원본을 만들지 않는다.
- R-082의 직접 구현된 프로젝트 planning 전환, 실패 보존 뒤 실제 실행 자리와 원래 작업 재개, 소유 commit의 기록 기준을 후속 소비자까지 대조한다. 별도 선행 작업이 보완하는 실패 슬롯·폐기된 Git 진단 재평가와 commit 완료 checkpoint의 기록 근거 보존을 중복 구현하지 않고, Merge 뒤 복구·dependency·PR·실제 verify/Review에서 재차단·무근거 성공·같은 입력 재호출이 없는지 감사한다.
- R-055의 참조 복구에서 실행 보류와 일반 Planner의 검토 권한을 분리한다. `missing-plan` 원문·채택 revision·삭제 근거를 제공하고 PR 전 영향 문서만 개정하게 한다. Manager의 게시·소유권·관계 검증 뒤 확인된 문서 hash에 복구 판단을 결합하며, 실행 보류의 이전 단계·session과 독립 차단을 보존한다.
- 기존 재현/회귀를 재사용해 목록의 각 판정을 뒷받침한다. 활성 R-055 선행 계획으로 해결된 항목, 실제 사용자 판단 항목과 현재 활성 명세의 미충족·불확실 항목을 명시해 미충족을 완료로 숨기지 않는다.
