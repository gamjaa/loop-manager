## Purpose

코드의 차단·중단 생성과 재개 경로를 추적하고 R-055의 현재 작업 입력·게시·sandbox 경계에 맞지 않는 잔여 처리를 교정한다. 실제 자동 복구 불가능·사용자 개입 필요와 확인된 무진전 지속 장애를 Git/비Git 최종 차단·진단 통지와 구분해 전수 감사한다. 직접 구현된 Git 접근 감시 제거·원격 작업 통합·삭제 브랜치 재시작·파일별 재작업을 소비자까지 감사한다. 원격 통합의 ignored 경로 보호 후속과 기존 선행 작업을 재사용하며 P1/P2 및 비Git 차단 감사의 미충족 범위를 보존한다. targeted test의 호출 결합·재수집과 G-302에 반영된 저장 verify 진입은 현재 구현을 소비하고, G-290의 native 분류·G-292의 Claude 전달과 함께 실제 후속 소비자를 확인한다.

## Acceptance Criteria

- R-055/R-091의 고정 OID 불일치는 G-313의 관계 재구성·필요 통합/검증 뒤 후속 선택·복구·게시·알림까지 추적한다. 실제 lease/fetch/PR 관측 경쟁만 제한 재시도하고 동일 과거 OID 비교·타이머·재시작을 진전으로 재등록하지 않아야 한다. 확인한 사용자 작업·현재 후보 검증·완료 push와 DB 확정 분리를 유지하며 관계 불명은 대상별 보류로 남긴다.
- G-325/G-326 뒤 같은 실행의 retry 묶음과 여러 외부 실행의 동일 원인/입력 정체가 대상별 보존 대기와 현재 진단 1건으로 연결되는지 감사한다. 실제 새 입력·복구 단계·조건 해소 후 같은 작업 재개, 정상 외부 조건/DB/호출 자리 대기의 무통지, 독립 작업 진행과 오래된 잔여 조각 취소를 확인한다. 지속 판정·통지 엔진은 각 선행에서 소비한다.
- R-092의 ref별 경쟁은 G-324 → G-300의 실제 Merge 뒤 확인한 base/독립 ref 적용·pending 복구 유지와 미확정 ref의 소비 보류를 후속 catalog·단일 작업 복구·재시작까지 감사한다. 전체 묶음 실패·동일 입력 재생이 독립 작업을 반복 정지시키거나 완료 ref 쓰기를 재수행하지 않아야 한다.
- R-055 W01–W06은 직접 구현된 생성 HEAD/실행 기준 분리·깨끗한 예약 복구와 G-322/G-323의 실제 Merge 뒤 후속 재개·선택·checkpoint/요청·알림까지 감사한다. 승인된 생성/변경 근거·writer 종료·작업/자원 소유권이 설명하는 현재 상태만 채택하고, 생성 journal/HEAD 일치만으로 전체 소유권을 승인하지 않는다. 소유권이 확정된 작업은 Manager rebase의 START/WAITING이 남아 있어도 해소된 소유권 차단만 풀고 checkpoint·원래 HEAD·target·파일·index·저장 단계와 별도 계획 차단을 보존한다. writer 종료 불명·다른 rebase 대상·관측 중 checkpoint/원인/복구 기록 변경은 해제하지 않는다. 작업 범위 미해소와 실제 공유 안전 불확실성을 구분해 차단 해제/축소·독립 진행이 재시작 뒤에도 유지되는지 확인한다. 예약 복구·scope 전환·rebase 대기 중 해제의 직접 구현은 소비하며 복구만으로 검증·rebase 성공·승인·실패 초기화·재개 통지를 만들지 않는다.
- R-082의 일반 차단 계획 개정은 G-318/G-319의 실제 Merge 뒤 후속 복구·선택·알림까지 감사한다. 삭제 복구와 무관한 PR 전 `PLAN_BLOCKED`도 보호 조건 안에서 개정되고, 원격·catalog·DB 확정 전에는 원인 해제가 없어야 한다. 직접 source 외 관련 활성 Requirement를 반영한 원인 재평가와 무관한 변경의 보류 유지를 구분하며, 문서 개정·source 추가·질문 삭제가 사용자 승인·검증 성공이나 독립 차단 해제로 바뀌지 않아야 한다. 기존 질문·작업물·session·실패/승격·checkpoint와 실제 dependency Merge gate를 유지한다.
- Git·비Git의 모든 차단 생성·재개 경로에서 안전한 대기·자동 복구 가능성, 실제 사용자 개입과 무진전 지속 장애를 구분한다. 단순 `PLAN_BLOCKED`·`PROJECT_BLOCKED`, OID 변경·Manager checkpoint push 후 stale OID·retry/교정 예산 소진·CPU/DB/Git 자원 대기·cleanup pending만으로 최종 사용자 차단이나 Telegram을 만들지 않는다. 실제 복구 불가 중단·사용자 승인/설정/권한/PR 행동과 R-091 이력으로 확인한 동일 원인/입력의 지속 정체만 현재 근거로 한 번 알리며, 진단 통지를 사용자 조치나 최종 차단으로 바꾸지 않는다.
- `notifications/policy.py`·`events.py`·`incidents.py`·`delivery.py`·`work_exhaustion.py`·`rendering.py`의 신규/legacy outbox와 후속 소비자에서 시작·진행·완료·재개·유지보수·PR 충돌 수정 시작·단순 작업 대기 메시지가 생성·재생되지 않는지 감사한다. 현재 필요한 draft 판단·PR 검토·실제 복구 불가 중단과 G-326의 확인된 지속 정체만 남기고 오래된 미전송/잔여 조각은 취소하되 감사는 보존한다. G-226의 공통 정책·scope별 근거 보존·조각 확인과 G-326의 새 진단 소비는 재구현하지 않는다.
- G-285형 Worker 변경 → Manager frontmatter/보호 문서 복원·commit/push → checkpoint/DB 반영 → 원격/PR 소유권 재확인에서 `candidate_changed`·`pushed`와 원격 OID 시점 혼합에 의한 전체 PROJECT_BLOCKED가 없어야 한다. 다른 origin/branch/PR과 타인의 OID 덮어쓰기는 계속 거부한다.

- R-055의 범위 밖 공통 결함은 G-310의 인계·일반 planning·실제 검증/Merge 뒤 재평가를 후속 선택·알림·중단 복구까지 감사한다. 같은 원인/목표의 기존 계획 재사용과 다른 원인·미확정 근거 보존을 구분하고, Worker 범위 확대·새 Planner 호출 조건·구현 교정의 불필요한 사용자 질문·독립 작업 차단이 없어야 한다. 기존 질문·작업물·session·실패/검증 이력과 별도 승인/소유권 차단을 보존하며 단순 계획 게시·Merge·문구 삭제를 승인이나 현재 후보 성공으로 바꾸지 않는다. G-309의 신뢰된 통합 단계 실패·대기/실행·종료 불명도 원래 실행 identity로 추적한다.
- R-055의 targeted test 기준은 완료 보고 횟수와 실제 개별 실행을 분리해 감사한다. 현재 호출 결합·재수집과 G-290/G-292/G-302/G-313 뒤 native 실패/fixture·중복과 상충·미소비 기록의 재시작·공급자별 전달을 Worker·rebase·CLI retry·저장된 verify·최종 차단·알림·다음 선택까지 추적한다. 세 번째 실제 실패 도달과 차단/표식 소비의 원자성, 새 근거 부재의 같은 실행 재검증·수집 조건 대기 및 독립 작업 지속을 확인하고 문서·전체 verify·Review의 실제 최종 차단 집계를 합치지 않는다.
- R-091의 공통 DB 경계는 현재 직접 구현과 G-303/G-304/G-305·G-297의 보완을 소비해 감사한다. 준비·단계·복구·기록·조회 소비자에서 일시 DB 경합이 일반 실패/교정 소진·영구 provider 오류로 바뀌거나 완료한 외부 효과를 반복하지 않아야 한다. 외부 관측/실행 중 독립 DB 요청이 진행하고 현재 소유권·generation 경쟁은 적용만 거부하며 원래 오류·저장 오류·미확정 자료를 보존한다.
- R-091/R-055: BLOCKED Agent 중단 복구의 대상 선택부터 오류 기록·다음 선택까지 같은 계획 identity를 유지한다. 대표/활성 A 아래 B의 복구가 실패해도 A의 last_error·차단 evidence·단계·session·투영은 바뀌지 않는다. B의 원인·요청·checkpoint와 원래 오류를 보존하고 실제 공유 안전 문제와 구분해 독립 작업을 이어간다. owner가 없거나 손상된 기존 기록은 확인 가능한 기존 호환 경계로만 처리하며 활성 계획을 임의 대상에 쓰지 않는다.
- R-093의 직접 구현된 Manager checkpoint와 G-307/G-308의 보완을 checkpoint 대기·새 환경 인수·PR terminal·다음 선택/알림까지 감사한다. 신규 Worker는 직접 Git commit하지 않고 Manager가 허용 범위·index 검증 뒤 checkpoint를 생성한다. 기록된 Manager commit과 과거 검증된 이력을 HEAD 변화만으로 거부하지 않고, 게시 대기·불명확한 소유권·CLOSED unmerged는 해당 작업에 보존한다. 유효한 실제 MERGED 뒤 동기화 실패가 Worker 재개나 완료 취소로 바뀌지 않아야 하며, 복구점·새 환경 인수를 검증/Review 성공이나 여러 환경의 동시 실행 지원으로 표시하지 않는다.
- R-055의 T01–T39를 실제 코드 경로·기존 회귀·필요한 교정·유지 이유에 연결한다. T38/T39의 planning·대표 투영과 작업 실행 원본의 혼선은 현재 자원·checkpoint·소유 근거로 복구한 뒤 저장 단계의 후속 소비까지 감사한다. 근거 부족·복수 후보·현재 자원 불일치·종료 불명 writer·확정 중 경쟁에서는 작업물과 독립 차단을 보존하며 reset·재생성·중복 실행 없이 영향 범위만 보류한다. 기존 checkpoint·단계별 문서·ignored·로컬 동기화와 직접 구현된 혼선 예방/자원 복구를 재구현하지 않는다. 과거 T01–T24 감사 기록을 현재 39개 조건의 충족으로 합성하지 않는다.
- R-055/R-082의 관리 rebase 검사 시점을 정상 실행·저장 단계 재개·계획/프로젝트 복구·cleanup 소비자까지 감사한다. 시작에는 현재 대상·소유권·고정 target·원격/PR·writer 경합·index 안전·보존 조건과 target의 유효한 작업 identity를 확인하고 파일·선언은 비교/복구 기준으로 기록한다. 최신 frontmatter 일치·전체 역할 diff·보호 문서/archive 최종 내용·과거 definition snapshot 존재를 시작 gate로 요구하지 않는다.
