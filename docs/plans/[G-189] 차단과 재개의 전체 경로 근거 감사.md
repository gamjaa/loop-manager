## Purpose

코드의 차단·중단 생성과 재개 경로를 빠짐없이 추적해 R-055가 요구하는 코드/테스트 근거와 책임별 감사 기록을 남긴다.

## Acceptance Criteria

- 실제 코드의 모든 block/pause/error 생성·해제 경로를 조건·scope·보호 규칙·자동 복구·사용자 조치·관련 테스트와 담당 ExecPlan에 연결한 목록을 관련 계획의 Implementation/Decision Log에서 확인할 수 있다.
- 문제가 없는 경로에도 검토 근거가 있고 오탐/과도한 중단에는 재현 가능한 코드·테스트·필요한 수정과 유지할 실제 위반의 회귀를 연결한다. 선행 구현이 바꾼 경로와 남은 불확실 범위를 구분한다.
- R-020·R-023의 정상 외부 base 전진·runtime B 선택 후 C 전진·파생 HEAD 변화와 R-072의 기록 변경을 Agent 결과·저장 선검증·계획/프로젝트 재평가·checkpoint에서 끝까지 대조한다. G-192·G-182의 함수별 PASS만으로 동일 원인의 재발 방지가 완료됐다고 판정하지 않는다.
- checkpoint cause/evidence/status 변경의 stale 요청은 R-055대로 취소·현재 원인 재검증되며, 그 identity 불일치만으로 새 프로젝트 차단·Worker 교정 횟수나 다른 계획의 진단 보존 거부가 발생하지 않는 근거를 확인한다. 실제 공유 안전 차단·원격 lease·소유권 경쟁은 유지한다.
- 일시 실패·실행별 한도·계획별 실패·공유 안전·승인·PR 종료·cleanup 보존을 구분한다. 동일 입력의 무한 호출/Git 쓰기/알림, 단순 지문 변경을 요구하는 이미 해소된 오탐과 독립 차단 일괄 해제를 감사한다.
- 로컬 base·Python 캐시는 R-056·R-059의 담당 계획을 참조한다. 운영 SQLite 사건의 수정/삭제나 빈도 주장을 하지 않으며 archive 감사에서만 발견한 후속은 원문 복원·원격 확인 전 새 구현 범위로 승격하지 않는다.
- 수동 준비의 수락 전 자원 충돌 거부와 수락 뒤 dependency·실행 자리 대기를 구분해 감사한다. 독립 준비가 자동 실행 projection을 교체하거나 실제 충돌·미종료 Agent·Git 작업·Planner 게시 예약을 우회하지 않으며, 거부된 요청이 자동 대기로 등록되지 않는 근거를 확인한다. 수락 뒤에는 등록 순서와 기존 단일 자동 변경 자리·정상 coordinator 순서를 유지한다.
- G-175 Merge 뒤 R-034의 일곱 기준을 실제 Worker·Planner·PR 시작 소비자까지 대조한다. 독립 planning 오류가 남은 해당 계획의 재개, 다른 계획 시작의 무통지, 시작 전 거부, 부분 전송 중 해제·재시작과 전송 실패를 포함한다. 이전 차단의 scope·계획·원인과 실제 시작만 표시하고 해결 주체를 추측하지 않으며, 계획·프로젝트·planning 사건 및 일반 재개를 중복 통지하지 않는다.

## Implementation

- scoped_blocking·recovery state·catalog/planning/maintenance/execution와 cleanup 소비자를 코드 검색/직접 읽기로 감사한다. 목록은 현재 선택 ExecPlan 및 실제 관련 계획의 허용 기록 경계에 남기고 새 운영 상태 원본을 만들지 않는다.
- 기존 재현/회귀를 재사용해 목록의 각 판정을 뒷받침한다. 활성 R-055 선행 계획으로 해결된 항목, 실제 사용자 판단 항목과 archive 원문 복원 대기를 명시해 미충족을 완료로 숨기지 않는다.
- 정상 외부 ref·runtime·HEAD·checkpoint 교정은 G-192, rebase 중 기록/구현 조건 분류는 G-182에 연결해 두 구현 Merge 뒤 공통 소비자를 감사한다. 이 계획은 전수 감사 책임을 유지하며 구현 성공·운영 사건 원인을 문서만으로 확정하지 않는다.
- 직접 Merge된 `application/manual_concurrency.py`·`storage/work_claims.py`, resource lock·Git journal·bootstrap 및 Planner 게시의 경합도 기존 감사에 포함한다. 실제 자원 소유자·수락 여부·보존된 intent로 판정하며 살아 있는 별도 runtime·Agent를 중단 이력으로 오인하거나 정리하는 경로를 대조한다. 새 병렬 실행 엔진이나 소급 구현 계획은 만들지 않는다.
- 자동 역할·권한·검증은 docs/AGENTS.common.md와 해당 역할의 docs/AGENTS.*.md를, 프로젝트 규칙·설계·계획 작성은 AGENTS.md·docs/ARCHITECTURE.md·docs/PLANS.md를 참조한다. 기존 helper·관련 테스트를 재사용하고 지정 루트 경로를 보존한다.

## Validation

- 감사 중 실제로 추가/변경한 판정 unit case의 최소 범위만 실행한다. 코드 변경 없이 기존 근거만 연결했다면 그 이유와 사용한 테스트 경로를 남긴다.
- Manager 전체 verify는 독립 계획/프로젝트 지속, 실제 안전·승인 차단, session/작업물·실패 피드백·PR 복구와 후보 재검증을 유지한다. 감사 문서만으로 전체 R-055 충족을 추정하지 않는다.
- 동일 원격 전진·runtime/HEAD·기록 변경의 증거로 Agent 결과 → 저장 선검증 → 차단 재평가 → checkpoint 요청/게시·재시작을 잇고, 오래된 요청 갱신과 독립 작업 보존을 확인한다. 실제 Agent 위반·ref 재작성·target 변조·새 구현 조건이 섞인 거부 case를 같은 감사 근거에 연결한다.

- `tests/test_manual_concurrency.py`의 독립 준비, 동일 G의 Worker/수동 예약, Planner 양방향 선점 및 push 뒤 SQLite 미확정, 자원 충돌·미종료 Agent 보존, 등록 순서와 별도 runtime 정리를 감사 근거로 재사용한다. 추가 판정의 최소 unit case와 Manager 전체 verify는 거부와 수락 후 대기 구분, 작업물·session·projection 보존 및 독립 자원의 지속을 확인한다.
- R-034는 `tests/test_notification_incidents.py`·`tests/test_notification_delivery.py`와 G-175의 실제 시작 회귀를 재사용한다. 기존 기준별 근거와 G-175의 교정 근거를 연결하고, 함수 단독 성공이나 차단 기록 해제만으로 실제 재개를 확정하지 않는다. 감사에서 추가한 판정만 최소 unit으로 실행하며 전체 verify는 사건별 단일 재개·미전송 조각 취소와 알림 실패 중 정상 작업 지속을 확인한다.
