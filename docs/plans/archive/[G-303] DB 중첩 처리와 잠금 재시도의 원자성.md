## Purpose

직접 구현된 파일별 DB 접근 조율을 재사용해 중첩 처리의 transaction 소유권과 일시 잠금 재시도를 완성한다. 같은 연결의 안쪽 helper가 바깥 변경을 먼저 확정하지 않고, 일시 SQLite 경합은 짧은 DB 요청을 최신 상태에서 다시 준비해 처리한다. DB 파일별 연결 격리·cursor 물질화·독립 snapshot과 기존 접근 제한 시간은 유지한다.

기존 `storage/db_access.py`의 중첩 context·명시적 caller transaction의 savepoint와 `runtime_state._transaction()` 경계, schema script의 암묵 commit 제거를 재사용한다. 보완 범위는 transaction 안 BUSY/LOCKED 뒤의 요청 재준비·제한 재시도, 재획득에도 유지할 요청 예산과 프로세스 간 반복 접근의 공정성이다. commit·backup의 runtime 중단 확인을 유지하고 backup 잠금 대기의 시간 분류를 실제 처리와 구분한다.

## Acceptance Criteria

- R-091: 같은 연결의 관련 조회·갱신과 중첩 helper는 처리 소유권·transaction을 이어 쓴다. 안쪽 정상 반환이 바깥 미확정 변경을 commit하지 않으며, 예외의 rollback 범위와 최상위 commit/rollback/close 뒤 접근 반환이 명확하다. 다른 연결을 같은 스레드에서 기다리는 자기 대기는 계속 거부한다. TEMP·작업별 연결을 전역 단일 연결로 합치지 않는다.
- 접근 차례·cursor 수명 교정 뒤에도 발생하는 BUSY/LOCKED는 해당 DB 요청을 rollback하고 현재 상태·소유권·generation을 다시 읽어 제한 재시도한다. SQL 한 문장만 다시 실행해 관련 판단의 원자성을 깨거나 Agent·Git·verify·전송 효과를 통째로 재실행하지 않는다. 재시도 가능한 DB 처리 단위와 재시도 불가능한 외부 효과 경계가 구분된다.
- 스레드·프로세스 대기, SQLite 재시도·commit·backup은 요청의 공통 제한 시간·취소·종료 요청을 적용한다. 재시도로 예산을 초기화하거나 SQLite 자체 timeout으로 중복 소비하지 않는다. 반복 요청이 먼저 대기한 다른 요청을 계속 밀어내지 않으며 한도 초과는 상태를 보존하는 DB 대기 종료로 구분한다.
- DB 대기·재시도는 일반 단계/Worker 교정 실패 횟수를 소비하지 않는다. 확인된 미실행 대기만 실제 실행 예산에서 제외하며, 살아 있거나 종료 불명인 프로세스의 실제 시간·종료 확인은 유지한다. 손상·권한·잘못된 SQL은 잠금 대기로 바꾸지 않는다.
- R-091의 요청 제한 시간은 유지하고 소진 결과는 호출자가 재시도 대기로 보존해 실제 차단이 없으면 같은 실행에서 다시 준비할 수 있게 전달한다. 요청 한도 소진 자체로 다음 외부 실행까지의 보류·최종 차단을 결정하지 않는다. 대기열/재배정은 G-297, 수동/복구·물리 Agent 결과의 소비는 G-304/G-305가 맡으며 이 DB 경계가 외부 효과를 replay하지 않는다.
- 정상·예외·취소·한도 초과 뒤 열린 cursor·미확정 transaction·접근 소유권이 다음 요청을 막지 않는다. canonical 경로의 별칭은 같은 DB 경계를 쓰고 독립 DB·정적 snapshot은 불필요하게 기다리지 않는다. 읽기 전용 연결은 DB 생성·migration·journal 변경으로 복구하지 않는다.

## Implementation

- [x] 확인한 `loop_manager_internal/storage/db_access.py`의 `_call()`·`access()`·commit/backup과 `storage/runtime_state.py:_transaction()`을 재사용해 짧은 DB 요청의 rollback·현재 상태 재준비·제한 재시도를 연결한다. 현재 값을 다시 읽는 책임과 CAS를 보존하고 임의 contextmanager 본문이나 외부 효과를 자동 replay하지 않는다. 직접 구현된 savepoint·최상위 소유권·`_Cursor.executescript()`·`storage/local_recovery_state.py:begin_request()`는 재사용하며 재시도/취소 뒤 중첩·명시적 caller transaction·schema 원자성도 유지한다. 호출자 적용은 G-297의 작업 조율·G-304의 수동/복구·G-305의 Agent 경계에서 맡고 새 범용 DB 엔진·설정·별도 상태 저장소는 만들지 않는다.
- [x] 파일별 접근 순서와 현재 잠금 방식을 재사용해 스레드/프로세스 공정성·공통 deadline·취소를 일관되게 적용한다. 보완 전 `access()`는 반환 후 재획득마다 deadline을 만들고 프로세스 잠금은 파일별 비차단 재획득을 반복했으므로, 요청 재시도가 예산·먼저 대기한 요청을 우회하지 않게 한다. commit·backup의 추가된 중단 확인은 유지하고 backup 내부 BUSY/LOCKED 대기는 확인된 미실행 구간만 clock에 연결한다. 확인한 `verification/execution_clock.py`·`execution/verify_process.py`의 실제 프로세스 시간은 제외하지 않는다.
- [x] 확인한 `tests/test_db_access.py`·`tests/test_state_foundations.py`의 실제 SQLite·스레드·별도 프로세스 fixture를 확장한다. `scripts/verify-windows-tests.json`에 이미 연결된 DB 회귀를 유지하고 PRODUCT·ARCHITECTURE의 공통 DB 절에 실제 보완한 보장만 통합한다.

## Validation

- Worker는 위 두 테스트 파일의 변경 관련 최소 unit case를 실행한다. `test_nested_helpers_and_scripts_do_not_commit_the_outer_transaction`·`test_caught_inner_error_rolls_back_only_its_savepoint`·`test_outer_context_owns_a_preexisting_implicit_transaction`·`test_explicit_transaction_survives_inner_helper_and_trigger_script`와 기존 schema 회귀를 재사용한다. 새 재시도/취소 경계에서 빠진 rollback·소유권 반환만 보강하며 같은 중첩 assertion을 복제하지 않는다.
- 실제 SQLite 파일의 외부 잠금과 제어된 Event/Barrier로 transaction 중 경합 → rollback → 최신 상태 재준비 → 한 번의 원자 확정을 검사한다. 한도 초과·재시도 중 generation 변경·비잠금 오류에서 원본 데이터·경쟁 변경을 보존하고 외부 effect 호출 수는 늘지 않아야 한다.
- commit·backup·스레드/프로세스 차례 대기 중 취소와 공통 예산 소진 뒤 다음 요청의 진행을 확인한다. 먼저 대기한 별도 프로세스와 반복 접근자의 진행을 관측하는 최소 사례를 사용하고 wall-clock 성능 수치로 공정성을 대신하지 않는다.
- 기존 `test_open_iteration_does_not_retain_a_read_lock`·읽기 전용·독립 DB·별칭·실제 프로세스 대기 회귀는 유지한다. clock 회귀는 대기 30초/실행 2초/예산 10초와 실제 실행 초과를 구분하며 Windows 파일 잠금 회귀는 기존 native 선택 목록으로 유지한다. mock 통과를 실제 OS 실행 성공으로 기록하지 않는다.

## Decision Log

- 이번 R-091 delta는 DB 요청 한도와 작업 전체의 재개 수명을 구별한다. 이 계획의 원자 요청·공통 deadline·공정성·실패 분류 목표는 보존하고 소진 결과의 소비를 같은 실행 재시도 대기에 연결한다. G-297이 이 결과를 소비하므로 역방향 dependency나 별도 DB 재배정 엔진은 추가하지 않는다. 구현·테스트는 실행하지 않았다.

- 이번 delta의 savepoint·schema 원자성과 중단 확인은 직접 구현으로 소비한다. 남은 요청 rollback/재준비·공통 예산·공정성만 같은 ID로 보완하고 G-297/G-304/G-305의 소비자 dependency는 유지한다. 부분 구현이나 테스트 존재를 계획 전체 완료로 판단하지 않는다.
- complexity high: 중첩 transaction의 소유권, 재시도할 DB 단위와 외부 효과의 분리, 파일별 대기 순서·취소·공통 예산을 함께 보존해야 한다. risk high: 조기 commit이나 잘못된 replay는 작업·소유권·감사 상태를 부분 확정할 수 있다. 실제 SQLite의 rollback/CAS·중단/경쟁 회귀와 기존 자료 보존을 복구 근거로 유지한다. priority high는 병렬 자동 실행의 상태 원자성 보완 기준이다.
- 새 공통 경계 도입을 소급 계획하지 않는다. unittest adapter version 1·launcher Python 3.11–3.14·모듈별 독립 실행·필수 compile 및 실제 Agent 차단을 유지한다. Model·Effort는 Manager 설정을 따른다. 이 계획은 delta의 미충족 범위이며 프로젝트 최종 전문 확인이나 검증 성공이 아니다.

## 구현 및 문서 기반 재검증 (2026-10-22)

- `origin/main`과 같은 `f7909364d133c58b0d90ddb53714647c0d6e6f76`의 원격 G-303에서 별도 worktree를 만들었다. 기존 checkout의 branch와 파일은 유지했다.
- `CoordinatedConnection.run_request(operation)`은 DB 전용 함수의 전체 transaction만 재시도한다. BUSY/LOCKED 뒤 rollback·접근 반환·현재 상태 재조회와 동일 deadline을 연결했다. 안쪽에서 잠금 예외를 잡아도 부분 변경을 확정하지 않으며 caller transaction은 인수하지 않는다. 외부 효과와 호출자 적용은 기존 G-297/G-304/G-305 경계를 유지한다.
- 기존 `.access.lock`에 대기 순서와 OS byte lease를 연결했다. 별도 프로세스의 선행 요청·종료된 대기자의 회수·반복 접근을 실제 자식 프로세스로 확인했다. 새 DB나 설정은 추가하지 않았다.
- commit·backup은 SQLite 자체 timeout을 끄고 공통 deadline·취소를 적용한다. backup은 native sleep을 끄고 확인된 BUSY/LOCKED sleep만 clock에서 제외한다. 즉시 획득·실제 DB 처리·복사 시간과 실행 중 프로세스의 시간은 유지한다.
