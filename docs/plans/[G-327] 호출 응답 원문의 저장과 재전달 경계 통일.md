## Purpose

provider가 반환한 역할 응답의 호출별 저장과 저장 대기 후 재전달을 같은 artifact 계약에 연결한다. 실제 호출·응답·session·사용량과 재호출 금지를 보존하며, Reviewer도 기존 attempt의 `last-message.txt`로 복구할 수 있게 한다. 새로운 호출 성공 재사용이나 Review 승인 정책을 도입하지 않는다.

저장된 모듈 receipt의 발견 0은 revision `f5a9d4ea510c62cea769eacd32c604f32bf25425`의 `agents/provider_adapters.py`에서 Reviewer 응답을 공용 `reviewer-last.txt`에 기록하는 반면, `agents/process_receipt.py:result_message()`는 호출 attempt의 `last-message.txt`만 읽는 불일치를 확인했다. 정상 응답 뒤 DB 확정·전달 중 중단하면 원문 부재로 `CallDeferred`를 반복할 수 있다. 기존 Planner mock의 파일 선작성 회귀는 이 연결을 보장하지 않는다.

## Acceptance Criteria

- Reviewer와 다른 역할이 반환하는 응답은 기존 호출 identity·메시지 지문에 결합된 원문으로 저장되며, 같은 입력의 미전달 응답만 같은 invocation에서 복구된다.
- 실제 종료 후 DB 반영 또는 전달 표식 확정이 중단돼도 provider 재호출 없이 기존 결과·session·사용량을 한 번 전달한다. 다른 attempt·역할·작업의 원문이나 공용 최신 파일을 대체 증거로 사용하지 않는다.
- 원문 부재·symlink·경로 치환·지문 불일치·입력 변경은 기존 보류로 남긴다. 과거에 원문이 없는 호출의 성공이나 원문을 합성하지 않는다.
- 사용자 동작과 공개 계약인 호출 시그니처·CLI 인자·응답 형식·읽기 전용 정책, 기존 DB/receipt의 저장 형식을 보존한다. 공용 최신 응답 파일의 기존 소비도 유지하되 복구의 원본으로 승격하지 않는다. 새 비밀값·stdout 전체를 저장하지 않고 기존 정제·진단 보호를 유지한다.

## Implementation

- [ ] 확인한 `loop_manager_internal/agents/provider_adapters.py`의 Codex/Claude 응답 수집과 `agents/process_receipt.py`의 원문 읽기 계약을 맞춘다. 이미 반환하기로 결정한 역할 메시지의 저장 책임을 호출 attempt 소유 경계에 모으고 기존 경로·지문 계산·원자 파일 쓰기 패턴을 재사용한다. provider 실행 구성과 G-191/G-264의 정책·설정 작업은 변경하지 않는다.
- [ ] 확인한 `agents/invocation_service.py`·`storage/agent_invocation_state.py`의 `database_pending`·원래 요청 session·실제 종료/저장 대기·전달 표식 순서를 유지한다. 원문 확정 실패를 새 provider 호출이나 성공으로 바꾸지 않고 반환된 물리 결과와 미확정 자료를 보존한다.
- [ ] 확인한 `tests/test_agent_invocation.py`·`tests/test_agent_process_receipt.py`의 기존 SQLite·receipt fixture에서 실제 Reviewer adapter를 CLI double과 연결한다. Planner mock이 원문을 미리 만드는 방식으로 새 회귀를 대신하지 않는다. 기존 provider 실행 fixture와 보안·사용량 검증을 재사용한다.
- [ ] 실제 구현과 함께 `docs/ARCHITECTURE.md`의 호출 관측과 ledger 절에 원문 저장 주체·실패·재전달 조건을 통합한다. 설정·DB migration·새 Agent 역할·전체 호출 재설계는 추가하지 않는다.

## Validation

- Worker targeted unit은 `python3 -m unittest tests.test_agent_invocation tests.test_agent_process_receipt` 중 변경한 adapter/원문·재시작 case다. provider 프로세스만 double로 제공하고 실제 원문 저장·receipt 읽기·SQLite 반영을 검사한다.
- Reviewer 응답 수집 → DB 확정 전 중단, 결과 저장 → 전달 표식 전 중단을 연결해 원래 invocation·session·메시지·usage 보존, provider 호출 1회, 전달 완료 뒤 같은 응답의 재전달 0회를 확인한다. 원문 쓰기 실패와 다른 호출의 공용 파일 덮어쓰기에서도 복구 원본이 바뀌지 않아야 한다.
- 기존 symlink/치환·해시 불일치·다른 요청/session·종료 불명 거부와 Planner/Worker 재전달 회귀를 유지한다. actual CLI/계정 실행 성공을 mock 결과로 기록하지 않는다.
- 전체 verify 회귀는 호출 ledger·배정 자리 반환·session 귀속·targeted pending·최종 Review/게시 gate를 유지해야 한다. 읽기 전용 Review에서 응답 저장을 새 승인 근거로 쓰거나 비밀값 보존 범위를 넓히지 않았는지 확인한다.

## Decision Log

- complexity medium: 기존 attempt·원문 검증·DB 대기 경계를 재사용하되 adapter 반환과 재시작 사이의 저장 순서를 맞춘다. risk medium: 잘못된 원문 연결은 중복 전달 또는 다른 응답 수용을 일으킬 수 있어 identity·지문·중단 회귀를 유지한다.
- priority high는 정상 Reviewer 종료 뒤 저장 대기 재시작에서 필수 원문 부재로 `CallDeferred`가 반복되어 자동 실행의 후속 단계가 중단될 수 있는 구체적 경로에 근거한다. 실환경 장애를 재현하거나 관측했다는 뜻은 아니다. 최초 level은 3이며 Model·Effort는 Manager 설정을 따른다.
