## Purpose

현재 원격·catalog와 실행 근거로 확인한 안정적 작업 소진을 일반 알림으로, 최신 프로젝트 최종 전문 확인과 모든 완료 gate를 통과한 완료 주기를 무음으로 전달한다. 기존 `WorkReasonSnapshot`·대기 episode·완료 cycle과 outbox를 재사용하고 실행 가능한 작업 선택이나 완료 판정을 알림을 위해 새로 만들지 않는다.

## Acceptance Criteria

- R-053: 미완료 목표가 남아 있고 독립적으로 시작/재개 가능한 작업이 없다는 안정된 관측에서만 일반 작업 소진 알림을 한 번 만든다. draft·PLAN_BLOCKED·PROJECT_BLOCKED의 ID·제목·확인된 원인·문서 링크를 먼저, PR Merge/dependency/기타 외부 조건과 재평가 조건을 이어 표시한다. 프로젝트 차단도 실제 안정성 확인을 거쳐 포함하며 확인되지 않은 사용자 조치를 요구하지 않는다.
- 실행/verify/복구가 진행 중이거나 실행 가능한 독립 후보·조건 재검사·정상 순번/짧은 retry가 남았으면 소진이 아니다. 일시 원격/상태 조회 불확실·상세 없는 반환·대표 phase만으로 안정성을 확정하지 않는다. 프로젝트 수준 조기 반환에서도 현재 대상별 실행·복구 근거를 확인하고 실제 차단/대기·일시 오류를 구분한다. `pending` 요청·`parked` 보류·`handoff` 안전 반환 대기는 정상 배정 상태로 대조하며, 저장된 활성 단계나 관리 자리 수 하나로 소진을 확정하지 않는다. 이미 관리 중인 단위는 새 적격 요청 없는 한도 축소 뒤에도 후속 진행 대상이고, 유지보수 범위 밖의 유효한 명시 재진입도 현재 선택 결과에 포함한다.
- 같은 대기 episode는 재실행·재시작·부분 전송 재시도에서 중복되지 않는다. 실제 진행 뒤 다시 소진되거나 관련 입력·차단 원인·목록이 실질적으로 달라지면 새 episode를 한 번 알릴 수 있다. 다른 draft·차단·PR 알림의 전송 여부로 프로젝트 소진 알림을 생략하지 않는다. 링크 표시나 무관한 SHA·archive 이동만으로 새 대기 episode를 만들지 않는다. admission 재저장·RETRY 순번 등록/소비·task 반환/복원만으로 episode를 새로 만들거나 기존 소진/완료를 실제 진행 뒤의 새 주기로 전환하지 않는다. 현재 실행 가능성이나 차단 원인이 실질적으로 바뀌면 기존 현재성 경계에서 재검사한다.
- R-053/R-082: 최신 입력의 유효한 프로젝트 최종 전문 확인과 기존 완료 gate가 모두 충족된 완료 주기에서만 무음 완료 1건을 만든다. delta의 새 계획 없음·개별 PR 생성/Merge·유지보수 종료·내용 보존 archive를 전체 완료로 승격하지 않는다. 전체 완료이면 소진 사건은 만들지 않는다.
- 생성과 전송 직전·각 조각 claim에서 대기 episode/완료 주기와 현재 입력·실행 상태를 재검증한다. 새 작업·관련 입력·진행/차단 변화로 무효가 된 대기/완료의 잔여 조각만 취소하고 원래 payload·고정 본문·확인 cursor·전송/실패/취소 감사를 보존한다. 과거에 취소된 사건은 일괄 부활시키지 않는다.
- Telegram 비활성·전송 실패에서도 현재 완료/대기 결과·이유·주기와 실행·검증·복구 판단은 유지된다. 별도 Agent·Git/원격 조회·주기적 방송·상태 대시보드를 추가하지 않는다. 지속 장애는 G-325/G-326의 별도 근거·경고 정책으로 남긴다.

## Implementation

보존 후보 `8ba33f33`에는 소진/완료 outbox·claim 현재성·완료 세대·조기 반환과 전송 감사 작업 및 해당 검증 기록이 이미 있다. 아래 항목은 최초 범위와 최신 base 통합 시 확인할 잔여 조건이며 후보의 완료 기록을 초기화하는 지시가 아니다. 원격에만 반영된 G-345의 scheduler/admission 구현과 설계·회귀를 통합하고 새 인계 상태의 알림 소비에 필요한 누락만 보완한다.

- [ ] 확인한 `loop_manager_internal/application/project_runner.py`의 `_stable_work_reason()` 소비·PROJECT_BLOCKED/planning 오류 조기 반환과 `notifications/work_exhaustion.py:collect()`·`WorkReasonSnapshot`을 대조한다. 전체 대상의 실행·복구·후속 처리 근거를 사용하는 기존 안정적 선택 경계를 확장하고 프로젝트 차단만으로 관측을 생략하지 않는다. `has_distinct_wait`나 관련 계획 상태가 있다는 이유로 사용자 행동을 추정하는 설명은 현재 사실·재평가 조건으로 교정한다. scheduler/복구의 실행 결정 자체는 재설계하지 않는다. 현재 `application/task_scheduling.py`·`storage/management_admission.py`의 실제 선택/반환 자료를 소비하고 `WorkReasonSnapshot`을 만들기 위해 `reconcile()`·순번 재등록·차단 해제를 호출하지 않는다. 정상 인계 대기 자체는 소진 사건이 아니며, 실제 안정 소진이면 기존 R-053 조건을 사용한다.
- [ ] 확인한 `notifications/events.py:enqueue_waiting_reason()`·`mark_work_available()`·`enqueue_completion_if_ready()`와 `repository.py`의 episode/cycle 저장을 재사용해 확정 결과와 outbox를 결합한다. 최초 계획 기준 base의 대기 취소·완료 cycle 저장에서 확장한 후보의 사건 생성·중복 방지·claim 재검사와 commit 후 flush를 보존하고 최신 배정 상태와의 연결만 확인한다. G-297/G-325/G-338 등의 현재 결과는 같은 관측 계약으로 소비하며 그 엔진을 구현하지 않는다.
- [ ] 확인한 `notifications/policy.py`·`delivery.py`의 공통 claim, `rendering.py`의 대기/완료·문서 URL 표시와 silent 전달을 연결한다. 최신 G-340의 `plans_published`·생성/질문 혼합 `draft_decisions` 현재성, `confirmed_publication_keys()`·미확인 유효 항목의 후속 전송과 게시 등록 commit 뒤 flush를 유지하면서 대기/완료 종류를 추가한다. 생성·질문·대기 episode·완료 cycle의 유효성은 각각 소유 근거로 판정하며 한 종류의 취소/전송 확인을 다른 종류의 발생·소진·완료 증거로 사용하지 않는다. 완료 receipt·planning 목적의 기존 유효성을 재사용하고 새로운 완료 증거·사용자 승인을 만들지 않는다. 기존 pending/부분 사건의 현재성·감사와 취소 상태를 보존한다.

## Validation

- Worker는 위 모듈에서 변경한 안정적 선택·episode/cycle·claim의 최소 unit만 실행한다. 실제 SQLite와 fake 관측으로 draft/계획 차단/프로젝트 차단·PR/dependency 혼합 소진의 일반 1건, 실제 시작 가능/실행/verify/복구/자원 대기·조회 불확실의 0건을 확인한다. 다른 계획 진행을 대표 phase가 가리는 경우도 검사한다.
- 재시작 뒤 동일 episode 1건, 실제 진행 뒤 재소진과 관련 원인/목록 변경의 새 1건, 개별 draft/차단 통지와 프로젝트 소진의 독립성을 검사한다. 단순 재관측·링크 변화·archive만으로 새 사건이 생기면 실패다. `tests/test_task_scheduling.py`의 durable RETRY 재연결·과거 수락 뒤 한도 축소·선택된 인계의 반환 대기 자료와 기존 `tests/test_notification_work_cycles.py`·후보 `tests/test_stable_work_reason.py`를 재사용해 정상 관리 대기에서는 소진 0건, 관리 자료만의 변화에서는 새 episode/완료 세대 0건을 확인한다. 실제 실행 가능성/원인 변화는 현재성 재검사에 반영하고 인계 순서 자체의 행렬은 복제하지 않는다.
- 기존 `CompletionCycleTest`의 완료 gate·동일/새 cycle·archive·비활성 보존을 재사용한다. 최종 전문 확인 부재·delta 결과·활성 목표/미Merge·미확정 게시에서는 완료 0건, 실제 gate 충족 뒤 무음 1건이며 완료와 소진이 동시에 발송되지 않아야 한다.
- 일부 조각 전송 뒤 새 입력/실제 진행·차단/완료 변경, 재연결·송신 오류·늦은 확인을 주입해 오래된 잔여분 취소·원래 감사/확인 cursor 보존을 확인한다. 구정책의 무통지 assertion만 최신 허용 사건으로 분리하고 필수 실패/보존 회귀는 유지한다. 기존 `tests/test_notification_delivery.py:TimelyProgressDeliveryTest`·`DraftListNotificationTest`의 일반/draft 게시·유효 항목 후속 전송·늦은 확인 회귀와 일반/유지보수 게시의 commit 후 flush 검증을 재사용한다. 공유 claim 변경의 영향 case만 실행하며 대기/완료 테스트에 게시 행렬을 복제하지 않는다.

## Decision Log

- G-345는 같은 ID·source·무dependency를 유지한 archive이며 현재 순서·인계 저장 구현을 소비한다. 후보에 없는 이 원격 변경을 후보가 삭제한 것으로 보지 않고 기존 알림 작업과 통합한다. 신규 계획·선행을 추가하지 않으며 기존 ID·경로·metadata·수행 기록을 유지한다. 관리 자료의 변화와 실제 진행·안정 소진·최종 전문 확인은 각 소유 근거로 판단한다.

- 이번 원격 변경의 게시 알림과 유지보수 중 명세 변경 감지는 현재 구현으로 소비한다. G-346은 같은 ID·source·dependency를 보존해 archive됐으며 이 이동이나 delta의 추가 계획 없음은 프로젝트 완료 근거가 아니다. 소진 판단은 현재 선택/복구 결과를 소비하고 G-346의 선택 교정이나 G-340의 게시 알림을 다시 구현하지 않는다. snapshot의 ID·경로·metadata·무dependency·기존 기록과 R-053의 미충족 소진/완료 목표를 보존한다.
- 소진과 완료는 같은 안정적 선택의 상호 배타 결과이므로 한 Merge 단위로 둔다. G-340의 개별 문서/질문·G-341의 실제 시작·G-326의 지속 장애와는 독립적으로 검증한다. 공유 파일만을 이유로 dependency를 추가하지 않으며 기존 완료 gate나 최종 전문 확인의 의미를 바꾸지 않는다.
- complexity medium·최초 level 3: snapshot/episode/cycle이 있으나 프로젝트 조기 반환·대상별 실행·조각 현재성을 연결해야 한다. risk medium: 오판은 허위 전체 완료나 대기/경고 오발송을 만들므로 최종 확인·현재성·실제 진행과 감사 보존으로 제한한다. 실행 gate를 변경하지 않으며 priority normal, Model·Effort는 Manager 설정을 따른다.
