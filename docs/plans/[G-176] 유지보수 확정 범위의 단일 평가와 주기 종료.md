## Purpose

prerequisite 후 재평가와 마지막 리팩터링 뒤 post-revalidation을 없애고 확정 범위의 실제 Merge 뒤 종료하는 R-074 정책을 구현한다.

## Acceptance Criteria

- 한 cycle의 모듈 검토·필요한 종합/계획 작성으로 prerequisite·리팩터링·필요한 dependency closure를 확정한다. prerequisite Merge나 개선 결과 때문에 새 전체 평가로 범위를 계속 늘리지 않는다.
- 확정 범위의 모든 계획이 실제 MERGED이고 미확정 게시·catalog 반영이 끝나면 장벽을 해제하고 일반 선택으로 돌아간다. 계획 없음/기존 계획 연결/근거 있는 제외도 검증·게시 뒤 종료하며 post-revalidation Planner나 대체 일반 Planner를 추가 호출하지 않는다.
- 정상 종료 시 마지막 유지보수 Merge까지 포함한 수를 다음 주기의 기준으로 저장한다. 최초 평가와 새 명시 요청을 제외하고 이후에는 양의 interval(기본 20)만으로 시작한다. 코드 영향·평가 receipt 차이·완료 후보만으로 새 cycle을 시작하지 않는다.
- 평가 성공 원본과 종료 cadence를 분리한다. 명시 요청은 한 번 소비하고 평가/게시 중단은 같은 cycle에서 필요한 관련 범위만 재검증한다. 최신 코드에 가짜 평가 receipt를 만들지 않는다.
- 기존 prerequisite/refactoring/post 단계·미게시 자료·이력을 보존해 정책을 전환한다. 실제 Merge와 게시 확인 없이 종료하거나 주기 기준을 전진시키지 않는다. 불확실한 종료 경계는 기존 복구로 남긴다.
- due 평가는 현재 작업/실제 Open PR이 없을 때 일반 READY·변경 입력보다 먼저 한다. 실제 PR 동기화 실패·안전 차단·필요 dependency는 유지하고 시작/범위/종료/다음 대기 사유를 로그와 진행 사건에서 확인할 수 있다.

## Implementation

- maintenance/cycle_service.py·planning/tiered_assessment.py·planning/selection_service.py·storage/maintenance_state.py의 cycle 전이를 정리한다. 현재 모듈 receipt 재사용·PR preflight·게시 reconciliation을 재사용한다.
- 처리 범위와 cadence 기준의 durable identity를 분리하고 기존 활성/유휴 cycle의 전환을 관측 가능한 실제 이력에 결합한다. 구조 참조 개정은 필요할 때 기존 의미 판단 역할에 남기고 종료 gate로 재도입하지 않는다.
- 공통 경계는 AGENTS.md, docs/ARCHITECTURE.md와 docs/PLANS.md를 참조한다. 기존 helper·관련 테스트를 재사용하고 지정 루트 경로를 보존한다.

## Decision Log

- R-074가 R-054·R-071 및 현재 명세의 사후 재검증/반복 평가를 명시적으로 대체한다. 상태 전환·이력 호환·선택 cadence의 결합으로 complexity high, 일반 작업 기아와 잘못된 완료 영향으로 risk high다.
- 범위 대응: `assessment_service`·`maintenance_validation`에서 기존 발견 대상과 새 DAG의 READY 선행을 같은 평가에서 검증한다. 기존 prerequisite validator·catalog helper를 재사용하며, 선행 계획을 역방향 barrier에서 제외해 순환을 막는다. `maintenance_orchestration`·catalog 선택은 확정 대상과 필요한 dependency만 실행한다.
- 종료 대응: `maintenance_state`에 cycle 종료 SHA/수·요청·cycle identity·기존 발견 대상만 additive migration으로 저장한다. `cycle_service`는 실제 MERGED와 현재 원격 catalog, 게시 identity를 확인한 transaction에서 종료한다. 기존 평가 원본·receipt·계획 집합은 보존하며 불명확한 종료는 복구 진단으로 남긴다.
- 재개 대응: 기존 게시 reconciliation·모듈 receipt를 재사용한다. prerequisite 결과도 검증 자료·artifact 게시를 거친 뒤 기다린다. 원본 변경 시 기존 모듈과 직접 관계·테스트·루트 변동만 재검증하며 같은 모듈의 새 파일을 포함한다. 전체 원본을 검토하지 않은 재개는 targeted 성공으로 기록한다. 새 명시 요청은 다음 cycle까지 보존한다.
- 선택 대응: 안전 차단·활성 작업·실제 Open PR 동기화 경계를 유지하며 due 평가가 일반 READY보다 우선한다. 기존 사후 단계는 보존된 결과·게시를 복구하거나 안전한 빈 실행 자리를 해제하고 새 모델 호출 없이 종료한다. 코드 영향·receipt 차이·완료 후보로 새 평가를 시작하지 않는다.
- 제품 규칙은 허용된 동일 변경의 `docs/PRODUCT.md`에 반영했다. 기존 모듈 경계를 사용하고 새 루트 항목·설정·infrastructure를 추가하지 않았다. Requirement·ARCHITECTURE·AGENTS·PLANS 원본은 수정하지 않았다. 전체 verify·Review·Merge 이후 완료 판단은 Manager와 사용자에게 남긴다.
- verify 진단 대응: 종료 기준선 backfill은 해당 column을 처음 추가하는 migration에서만 수행한다. column 추가와 backfill은 기존 transaction helper로 함께 rollback하며 호출자의 transaction을 보존한다. 초기화된 Repository 조회에는 UPDATE가 없어야 한다. 검증 항목·verify script·시간 상한을 유지한다.
- Review `catalog-hold-crash` 대응: 전체 catalog에서 확정 범위·dependency closure를 계산하고 별도의 실행 목록에서 후보·Merge dependency를 판정한다. hold된 대상·선행은 대기하며 독립된 확정 대상은 실행할 수 있다. 확정 범위의 hold가 남아 있으면 durable MERGED row만으로 cycle을 종료하지 않는다. 실제 hold row를 저장한 재시작·해제 case로 세 실행 단계를 검증했다.
- Review `legacy-release-interruption` 대응: 기존 진단 보존·경로 소유권·Agent/Manager 쓰기 gate를 재사용한다. clean workspace 삭제 전에 cycle revision과 planning snapshot hash에 결합된 해제 intent를 additive column에 저장한다. 삭제 뒤 중단되면 같은 intent·경로 부재·Git 등록 부재를 확인한 뒤 intent와 planning 슬롯을 한 SQLite transaction에서 정리한다. intent 없는 경로 부재, 바뀐 입력·cycle, 살아 있는 Agent, 남은 Git 등록·Manager 쓰기는 거부한다. 삭제 직후·상태 정리 중 중단 및 실제 SQLite backup 재개를 검증했으며 새 모델 호출·평가 receipt·종료 기준 합성은 없다.
