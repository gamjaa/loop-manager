## Purpose

Worker의 최초 실제 프로세스 시작과 기록된 계획/프로젝트 차단 해제 뒤 그 영향 대상의 실제 작업 시작을 무음 통지한다. 기존 물리 시작 callback·작업별 호출 identity·차단 해제 기록과 outbox를 재사용하고, 차단 메시지 전송 여부에 의존하던 재개 기록을 실제 차단/시작 근거로 분리한다. 선택·예약·단순 해제를 시작으로 간주하지 않는다.

## Acceptance Criteria

- R-053: 같은 계획의 최초 Worker 프로세스 시작을 확인하면 ID·제목·작업 종류·발생 시각을 무음으로 한 번 통지한다. 일반 retry·재호출·session fallback·단계 변경·재시작에서 최초 시작을 반복하지 않는다. spawn 전 실패·선택/예약·준비만의 사건은 0건이다.
- 계획 또는 프로젝트의 기록된 차단이 실제 해제된 뒤 그 영향 대상의 정상 작업이 시작되면 이전 차단·대상·실제 시작을 무음 통지한다. 과거 차단 메시지의 생성/전송·확인 조각 수를 전제하지 않는다. 프로젝트 차단의 영향 대상과 무관한 계획의 시작을 구분하고, 재차단·별도 차단·미해결 질문·미Merge dependency·pause를 우회하지 않는다.
- 같은 실제 시작에 최초 시작과 차단 후 재개가 겹치면 재개만 보낸다. 동일 차단/해제/실제 시작은 실행·재시작을 건너 중복되지 않고 새로운 차단 episode의 실제 재개는 별개로 식별한다. 일반 Planner/Reviewer 호출·유지보수 단계·PR 충돌 수정의 내부 진행에는 별도 시작 알림을 만들지 않는다. 차단 후 실제 재개는 역할명만이 아니라 영향 대상과 정상 재개 전이로 판단한다.
- 기록된 실제 시작은 이후 단계 전환이나 프로세스의 정상 종료만으로 거짓 사건이 되지 않는다. 전송 직전·각 조각에서 시작 identity와 차단/해제 연결·현재 유효성을 대조하고 잘못 연결된 잔여 조각은 취소한다. 이미 취소한 과거 사건을 일괄 재생하지 않으며 원래 payload·cursor·전송/실패·차단 감사는 보존한다.
- 생성·전송 실패는 실제 호출을 재시도하거나 실패로 바꾸지 않는다. 기존 실제 시작·usage/receipt·종료 확인·session·실패/교정 이력과 R-091의 자리 수명을 유지하며 비활성화에서도 실행 판단은 동일하다. 알림을 위한 Agent·Git·외부 조회를 추가하지 않는다. R-076의 pause 해제 자체는 독립 차단 해제나 작업 시작 사건이 아니다.

## Implementation

- [ ] 확인한 `loop_manager_internal/agents/invocation_service.py:observe_cli_process_started()`·`observe_process()`와 `notifications/events.py:record_process_start()`의 실제 callback을 사용한다. 계획 identity와 첫 시작/차단 후 시작의 우선 판정을 결합하고 `resumed=bool(session_id)`만으로 차단 재개를 추정하지 않는다. 실제 호출·receipt/ledger의 원본은 그대로 유지한다.
- [ ] 확인한 `recovery/scoped_blocking.py`의 block 기록/clear, `notifications/incidents.py:release_block()`·`record_work_start()`·`_materialize_resumption()`과 `repository.py`를 연결한다. 현재 `_queue_block()`은 조치 근거가 없으면 기록하지 않고 `_materialize_resumption()`은 전송 확인을 요구한다. 실제 차단·영향 대상·해제·시작의 기존 보존 자료를 우선 사용하고 필요한 최소 호환 기록만 보완해 미통지 차단도 연결한다. blocked 경고의 조치 판정·미전송 취소/감사는 유지하며 과거 근거 부재를 새로운 재개 사실로 합성하지 않는다.
- [ ] 확인한 `notifications/policy.py:is_current()`·`delivery.py`·`rendering.py`의 공통 현재성/조각 claim과 기존 `silent`→`disable_notification` 전달을 재사용한다. 새 일반 방송·polling·별도 전송 계층을 만들지 않는다. 중단된 시작 기록의 복구도 같은 고유 identity로 이어간다.
- [ ] 확인한 `tests/test_notification_incidents.py`·`test_notification_events.py`·`test_notification_delivery.py`, `tests/test_agent_invocation.py`와 `tests/support/notification.py`에 최소 callback/SQLite 회귀를 연결한다. PRODUCT·ARCHITECTURE의 실제 시작/재개와 조각 현재성 설명을 구현과 함께 갱신한다.

## Validation

- Worker는 변경한 notification/물리 시작 callback의 최소 unit만 실행한다. mock provider/process와 실제 SQLite로 spawn 전 실패 0건, 실제 최초 시작 1건·무음, 같은 계획의 재호출/fallback·재시작 중복 0건을 확인한다. 기존 process 시작·종료 receipt의 provider별 회귀를 재사용하고 실제 CLI를 호출하지 않는다.
- 미통지 차단·일부 전송 차단·확인 전송 차단의 해제 뒤 해당 계획/프로젝트 영향 대상이 시작하면 재개 1건이어야 한다. 단순 해제·무관한 시작·다른 차단 유지·선행 미충족·pause에서는 0건이며 최초 시작과 중복되지 않아야 한다. 실제 차단/시작 판단을 성공 mock으로 바꾸지 않는다.
- 기록 전후 중단·재연결·재차단·다른 대상 시작·단계 전환과 늦은 전송 확인을 주입한다. 진짜 과거 시작의 유효성, 무효 잔여 조각 취소와 원문/cursor/감사 보존을 확인한다. 송신 실패/비활성 상태가 invocation·session·실패/자리 반환을 바꾸지 않아야 한다.
- 구정책의 모든 시작/재개 무통지 assertion은 허용 사건과 내부 retry/Planner/Reviewer 무통지로 나누고 기존 사용자 행동·PR·현재 조각/전송 감사 검증을 유지한다. G-236의 pause 구현·G-343의 metadata 해제 판단은 재구현하지 않고 현재 해제/미해제 결과를 입력으로 제공한다.

## Decision Log

- 알림을 위한 차단의 생성·해제나 실행 재개를 추가하지 않는다. R-055의 원인별 해제와 R-091의 실제 배정을 소비하며 G-236의 pause 및 G-343의 재평가를 역방향 선행으로 만들지 않는다. 별도 시작/전송 근거는 현재 호출 경계에서 독립적으로 검증 가능하다.
- complexity medium·최초 level 3: 물리 시작·차단 해제·outbox 경계가 있으나 미통지 차단 연결과 우선 판정이 필요하다. risk medium: 잘못된 영향 연결은 허위 재개·중복/누락을 만들므로 실제 대상·시작 identity·현재성/중단을 검증한다. 실행 권한·소유 예약을 바꾸지 않고 감사를 보존한다. priority normal이며 Model·Effort는 Manager 설정을 따른다.
