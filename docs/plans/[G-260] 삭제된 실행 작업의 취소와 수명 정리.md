## Purpose

확인된 문서 삭제를 실행 이력 있는 작업의 현재 취소와 예약·판단·checkpoint·게시 수명에 반영한다. 무소유 READY만 취소하는 현재 경로를 보완하고, 과거 작업 결과나 관리 브랜치가 취소된 작업·삭제 문서를 되살리지 않게 한다.

## Acceptance Criteria

- G-258의 원격 삭제 증명과 현재 작업·자원 소유권을 안전한 단계 경계에서 재확인한다. 실행 이력·branch·worktree·session 존재만으로 영구 보류하지 않으며 다음 Worker·verify·Review·checkpoint·PR 게시와 저장 결과 소비를 중단한다. 살아 있는 writer·Git operation에 병행 쓰기나 강제 정리를 수행하지 않고 종료·인계를 확인할 때까지 해당 전이를 보존한다.
- 실제 MERGED는 완료로 유지하고 미완료 작업의 확인된 철회만 현재 취소에 반영한다. 마지막 선언·구현·미게시 작업·session·실패·Review level·PR·최초 게시·Merge·ID 예약 감사를 복구 가능하게 보존한다. PR 상태·head는 실제로 관측하며 문서 삭제만으로 Open/Closed PR을 종료·Merge하거나 삭제를 구현 성공으로 기록하지 않는다.
- 현재 실행·draft 판단·수동 준비·완료 대기와 일반/유지보수 작업 집합에서 취소된 작업을 제외한다. 관련 예약·미완료 checkpoint/게시 요청·미전송 알림은 현재 수명에 맞게 정리하고 과거 확정 결과·전송 감사·독립 작업 사건은 보존한다. 수동 작업·제출 묶음은 기존 수동 소유권과 조율을 지키며 문서 삭제를 manual stop/reset 권한으로 사용하지 않는다.
- 취소 전 저장된 Worker·Planner·Review 결과와 publication/복구 snapshot을 재시작 뒤 소비해 작업을 재개·게시하거나 삭제된 원문을 복원하지 않는다. 실제 원격 게시가 이미 확정된 경우 그 결과를 감사로 보존하고 최신 취소와 구분한다. 영향 입력·draft 판단·verify/Review/게시 근거의 무효화는 기존 입력 계약을 따른다.
- 유지하는 관리 브랜치·planning 결과에는 최신 확인 문서 삭제·개정을 기존 동기화·rebase·단계 판단 경계에서 반영한다. 오래된 브랜치·재개 결과로 문서가 재등장하지 않으며 남은 목표가 바뀌면 필요한 Worker 교정·검증·Review를 수행한다. 코드·index·사용자 작업 전체를 reset하지 않는다. 문서 충돌 선택과 최신 조건 재평가는 G-255/G-256을 재사용한다.
- 문서 확인·writer 종료·취소 DB 확정·요청 무효화·브랜치 문서 반영 사이 중단·원격/PR/수동 소유 경쟁에서는 실제 확정 지점부터 멱등 재개한다. 독립 READY와 PR 관측은 계속하며 부분 성공으로 모든 보류·cleanup을 해제하지 않는다. 물리 자원 정리 pending은 취소·문서 반영 결과를 되돌리지 않는다.

## Implementation

`remote_deletions.mutable_row`·`prove_deletions`, `execplan_catalog_state`와 `planning_publication_state`의 현재 취소 경계를 execution의 단계 진입·저장 결과 소비·checkpoint/publication 재개 및 현재 자원 claim에 연결한다. 기존 무소유 READY 삭제 CAS를 전역 완화하지 않고 Manager의 확인된 삭제 처리와 Agent의 문서 편집 권한을 구분한다. 기존 cancellation·snapshot·journal·실행 감사와 호환되는 저장 및 transaction을 사용하고 비호환 상태 모델·데이터 삭제 migration을 도입하지 않는다.

수동 claim·묶음 membership·draft 결정·유지보수 대상 및 notifications의 사건 수명을 현재 취소와 맞춘다. G-238의 명시적 reset/manual stop CLI나 새 백업 명령을 구현하지 않는다. 보존한 작업·실패 근거와 현재 유효 입력을 구분하고 `stage_documents`·G-256의 안전한 문서 반영을 소비한다. G-259의 의미 판단 결과로 게시된 관련 삭제도 같은 취소 경로를 사용하되 그 의미 판단을 실행 handler에서 재작성하지 않는다. 자원 삭제는 승인 대기 G-261에 남기며 그 계획 미실행 때문에 확인된 취소를 완료 대기로 되돌리지 않는다. 실제 수명·보존·재개 계약만 PRODUCT·ARCHITECTURE에 반영한다.

## Validation

- `tests/test_incremental_planning.py`, `tests/test_scoped_blocking.py`의 최소 targeted unit에서 실행/verify/Review/차단 중 삭제, 미종료 writer와 소유권 경쟁, 실제 MERGED·Open/Closed PR 및 동일 ID 재등장을 대조한다. 실제 정책·SQLite·파일 보존을 실행하고 Git·PR·Agent 관측만 mock한다. 현재 started 삭제 보류 회귀는 확인 가능한 취소와 미확인 보존 사례로 나눠 기존 보존 assertion을 유지한다.
- `tests/test_execution_checkpoint_state.py`, `tests/test_published_checkpoint_resume.py`, `tests/test_planning_publication.py`, `tests/test_stage_documents.py`의 관련 fixture에서 취소 전 저장 결과·checkpoint/게시 intent의 재시작, 취소 직전/직후 확정 경쟁, 유지 작업의 삭제 문서 반영을 확인한다. 원격 확인된 게시 감사는 보존되며 미확정 결과는 새 실행·게시를 만들지 않아야 한다.
- `tests/test_manual_concurrency.py`, `tests/test_notification_incidents.py`, `tests/test_notification_delivery.py`의 최소 변경 case로 수동 소유·묶음·draft·미전송 사건 정리와 독립 예약/알림 감사 보존을 확인한다. 실제 브랜치 문서·index·미게시 코드 보존 효과는 기존 managed rebase 통합 fixture를 재사용한다.
- Manager 전체 verify는 R-055 D01/D05/D08/D12의 수명 정리, 독립 실행, 현재 source/dependency·필수 사용자 결정·실제 Merge gate를 유지한다. Reviewer는 실행 중 강제 정리, 취소 뒤 저장 결과 소비·게시, 작업물/감사 손실과 삭제의 성공 합성을 blocking issue로 확인한다.

## Decision Log

- `prove_deletions`는 `mutable_row`의 무소유 READY 자격을 요구하고 `apply_mutable_catalog_changes`의 삭제 CAS도 같은 조건이다. `test_remote_deletion_started_history_and_dependents_are_scoped`는 시작한 작업을 취소하지 않고 보류하며 session을 보존한다. 이 보존은 유지하되 확인된 철회 이후의 현재 취소·후속 요청 정리가 새 요구로 남아 있다.
- G-258은 삭제·역사 구분, G-259는 목표 판단·문서 게시, G-255/G-256은 rebase 문서 충돌·현재 조건 교정이다. 이 작업은 확인된 삭제 결과의 실행 수명과 오래된 결과/문서 재생 방지에 한정하며 기존 구현·계획의 목표를 중복하지 않는다. 운영 SQLite 사건을 직접 조사·수정하지 않는다.
- complexity high: writer 종료·취소 확정·기존 실행 projection·저장 결과·비원자 게시의 중단 지점을 맞춰야 하며 확인된 과거 게시와 미확정 요청을 보존하는 판단이 남아 있다. risk high: 불완전한 취소는 철회된 작업을 계속 게시하고 과도한 정리는 session·작업물·수동 소유·실패 감사를 잃게 할 수 있다. 원형·intent·현재 수명과 실제 결과를 보존해 수동 재개/복구하며 AC·Validation에서 writer·PR 경쟁·저장 결과 재소비와 감사 보존을 확인한다.
