## Purpose

확인된 문서 철회를 실행·요청·checkpoint·알림과 유지 branch/planning snapshot까지 반영한다. 최신 R-055의 삭제 확정 조건에는 대상 기록·사용량·전용 보존 사본을 최종 제거하고 repository·ID 표식만 남긴다. 그 조건 밖의 일반 취소와 실제 MERGED에는 기존 감사 보존을 유지한다. PR close 자체는 작업 보류로만 처리한다.

기존 `deleted_plan_cleanup.py`·`deleted_plan_state.py`의 삭제 판단·소유권/종료 확인·기록 제거·파일 재시도를 row 없는 취소/hold와 공유 기록의 부분 제거로 확장한다. writer 완료 취소·archive 참조 제외·draft/피드백 표식의 비소유 판정을 재사용하고 후속 요청/branch/snapshot의 부활을 막는다. 현재 충족 근거와 구체적인 미완료 전이는 Progress의 최신 대조표에 기록한다. 살아 있는 소유 원격 ref의 실제 정리는 G-261이 맡는다.

## Acceptance Criteria

- R-055: 실제 CLOSED 미Merge PR은 branch 존속/삭제와 관계없이 해당 작업의 자동 Worker·verify·Review·checkpoint/새 PR 게시를 보류한다. 조회 실패는 close가 아니며 run·재시작은 명시적 재개가 아니다. PR reopen 또는 유효한 명시 재개 입력 뒤 현재 PR·명세·소유권을 다시 검사한다. close만으로 기록 삭제·완료·MERGED를 만들지 않는다.
- 목표 철회·관련 참조 개정·원격 ExecPlan 삭제가 확인되면 close/remote branch 삭제 대기보다 삭제 처리를 우선한다. 현재 원격·실제 PR·writer 종료·소유권과 참조 개정의 게시/적용이 확인되기 전에는 필요한 근거를 보존한다. 삭제된 목표를 복원하거나 재시작 질문을 반복하지 않고 실제 MERGED·의미/소유권 불확실·수동 소유는 별도 보호한다.
- 삭제 확정 대상은 활성 row 유무와 관계없이 처리한다. 과거 취소/hold만 남은 ID도 원문·삭제 revision·마지막 선언과 최신 목표의 검증 가능한 근거로 평가한다. 활성 실행·차단·hold·draft·예약·복구·checkpoint·session·실패·취소 감사·호출·로그·사용량과 전용 보존 사본을 완료 시 제거하고 repository·사용한 ID의 재사용 방지 표식만 남긴다. 필수 정리가 남으면 한시적 근거/미완료 상태를 유지하며 전부 제거했다고 보고하지 않는다. 삭제 transaction의 기존 trigger 복원·rollback 보호를 유지한다.
- R-073/R-055: 공유 session·로그·사용량·유지보수/알림·복구 기록은 대상 귀속 부분만 제거한다. 다른 작업·다른 repository·실제 MERGED 근거와 Git/외부 PR/provider 이력은 보존한다. 제거한 호출은 기간/프로젝트/목적 집계에서도 제외하며 익명 합계나 새 삭제 감사로 재보존하지 않는다. 독립 작업의 공통 결함 근거를 소유 작업 삭제만으로 잃지 않게 관계를 대조한다.
- R-094: 새 archive 관측의 `dispatch`·G ID·`git:<intent_id>` scope도 실제 귀속에 따라 위 부분 제거를 적용한다. 삭제 대상의 미확정 Git 판단에서 남은 전용 관측은 확인한 intent 관계와 함께 처리하며, 문자열에 ID가 포함됐다는 이유로 지우지 않는다. 독립 MERGED 후보·공유 실행 관측·다른 intent는 보존한다. 귀속·종료·필수 정리가 미확정이면 기존 pending을 유지하고 최종 제거로 보고하지 않는다. 삭제 보존 기록의 존재만으로 독립 archive를 막거나 미Merge CLOSED/삭제 ID를 archive 후보로 바꾸지 않는다.
- 삭제 확정 조건 밖의 일반 취소는 마지막 선언·미게시 작업·session·실패/level·PR·checkpoint/게시와 소유 자원 근거를 활성 row 밖에서 복구 가능하게 보존한다. 직접 구현된 archive 역사 참조 제외·draft/피드백 비소유 판정·ID 예약을 유지한다. 원문 hash·원래 경로·PR 게시 근거가 일치하는 MERGED archive의 과거 참조는 backfill 전에도 현재 삭제 대상으로 전파하지 않는다. 취소돼 현재 catalog/실행 row가 없는 참조 주체의 과거 hold도 살아 있는 후속 작업으로 만들지 않는다. 원문 불일치·미확인 Merge는 제외하지 않는다. 기록 제거 예외를 일반 취소·manual cancel/reset/stop이나 완료 작업으로 확대하지 않는다.
- R-082: 직접/간접 dependency·본문/구현/검증 참조와 현재 선택·유효 priority·일반/유지보수 집합을 게시된 관계에 맞춘다. 해당 삭제만의 hold·차단·오래된 복구 입력은 제거하되 다른 차단과 필요한 선행은 유지한다. 삭제·철회를 Merge·검증 성공 또는 dependency 충족으로 합성하지 않는다.
- 취소/삭제 뒤 저장 Worker/Planner/Review 결과·stage origin·publication/recovery snapshot·미완료 요청과 유지 branch가 문서/row를 복원하거나 실행·게시하지 않는다. 최신 삭제/개정은 기존 stage_documents·안전 rebase 경계로 반영하며 코드·index·사용자 작업 전체를 reset하지 않는다. 필요한 남은 목표의 실제 교정·검증은 유지한다.
- R-091/R-067: 대기 중 자격 소멸 뒤 미시작 호출의 cursor·RETRY·실패/성공을 소비하지 않는다. 상위와 소유 하위 runner/worker의 실제 종료·시작 identity·최종 응답을 확인하며 살아 있거나 종료 불명인 writer/예약·복사본·예산 오류 근거는 먼저 제거하지 않는다. 기존 순번/관리 대기는 자원 정리 권한이 아니다.
- writer 종료·참조 게시·DB 관계·자원 정리·기록 제거와 파일 정리 사이 중단/원격·소유권 경쟁은 확정 지점부터 멱등 재개한다. 이미 끝난 commit/push·결과 소비·삭제를 반복하지 않으며 작업 부활·타 작업 손실·조기 완료와 중복 알림이 없다. 독립 READY·PR 관측과 안전한 유지보수 종료는 계속한다.

새로 구체화한 잔여 작업은 `recovery/deleted_branch_restart.py:restart`의 별도 보존 자원이다. native intent는 원래 worktree의 형제 `retired/<token>` 사본과 `loop-manager/retired/<G ID>/<token>` ref, 이전 checkpoint·원래 plan/block을 보존한다. 현재 root key 검사에서는 `deleted_branch_restart`를 허용하지 않아 이 기록을 임의로 지우지 않는다. 이 상태를 일반 data-only rebase 역사로 허용하면 전용 사본과 ref가 남거나 소유 근거를 먼저 잃을 수 있다. 다음 구현은 이 native intent의 정확한 경로/ref·원래 owner·복구 상태를 resource inventory에 연결하고 G-261의 실제 물리 정리와 구별해, 그 자원 부재가 확인된 뒤 종결하도록 해야 한다. 같은 이름의 재생성·독립 소유·미확정 journal과 별도 baseline도 재검사해야 한다. 새 reset/수동 stop 정책이나 G-261의 살아 있는 원격 삭제 엔진을 G-260에 복제하지 않는다. 그 뒤 현재 native checkpoint producer의 나머지 역사/자원 필드를 대조해 단순 자료와 실제 보존 자원을 구분하고 누적 diff 전체 검토를 완료한다.

현재 접근법의 재평가: 실행/게시 성공 parser를 범용 삭제 성공 증명으로 쓰지 않는다. native parser는 역사 identity/형식을 읽고, 자원 inventory·실제 부재·종료·소유권·공유 관계가 별도로 제거를 허가한다. 단순히 새 key를 무조건 허용하거나 모든 알려진 과거 기록을 영구 보류하는 양쪽 우회를 피한다. 이번 구현은 이전에 명시했던 acceptance/publication/history 정체를 실제로 해소했으며, 이를 다시 미구현으로 반복하지 않는다. 남은 전용 retired 자원은 위의 구체적 producer/namespace 기준으로 이어간다.

검증은 지정 targeted runner로 실행했다. `DeletedPlanCleanupTest` 78 + `DeletedDiagnosticArtifactTests` 4 + `CancelledCheckpointTests` 26의 108개가 최종 관련 코드에서 PASS했다. native rebase 회귀는 두 차례 native acceptance/게시 전이·과거 요청/결과·부모 단계 출처·중첩 history·별도 보존 baseline을 실제 SQLite로 구성한다. foreign worktree/위조 intent·결과/출처 누락·손상 baseline은 외부 효과와 DB 변경 없이 보존하고, 살아 있는 baseline ref에는 제거를 보류한다. 실제 자원 부재 뒤 DB 제거 trigger 실패에는 전체 원문/호출이 rollback되며 정상 재진입은 ID 표식만 남기고 새 token·호출·게시를 만들지 않는다. 중첩 문서 사본의 native cleanup/recovery와 기존 native manifest 회귀 2개도 PASS였다. 마지막 저장 validator의 타입 검사 보완 뒤 같은 108개 묶음을 다시 실행해 확인했다. 위 소비자 44개와 `git diff --check`도 오류가 없었다. 실제 Agent/CLI·통합 suite·전체 verify는 실행하지 않았다.

새 native rebase 단일 회귀의 최초 두 실행은 fixture의 HEAD/branch ref 관측 불일치와 두 번째 게시의 이전 원격 OID 미갱신으로 native 준비 단계 ERROR였다. 실제 producer에 맞춰 관측/lease를 고친 같은 명령 재실행은 PASS였고, 이후 baseline·부모 출처·rollback assertion 추가 뒤에도 같은 테스트가 PASS였다. FAILED_COMMAND와 RERUN은 모두 `python3 "$LOOP_MANAGER_TARGETED_TEST_RUNNER" --unittest tests.test_deleted_plan_cleanup.DeletedPlanCleanupTest.test_retired_native_rebase_publications_and_history_erase_without_replaying_tokens > "$LOOP_MANAGER_TARGETED_TEST_DIRECTORY/g260-rebase-retirement.log" 2>&1`이다. 현재 미해결 targeted 실패는 없으며 과거 피드백을 새 실패로 누적하지 않았다.

중간 보존 이유: 이번 변경은 제거 자격의 native 형식·중첩 source 전달·별도 baseline ref inventory와 실제 문서 사본 정리를 함께 바꾸며, 독립 자원을 지우지 않는 검증·rollback 근거를 갖춘 복구 경계를 만든다. 이후 별도 retired 사본/ref의 native 소유 계약을 연결하기 전에 이 경계를 보존한다. 전체 구현 완료는 아니며 완료 후보로 인계하지 않는다. 잔여 작업은 위 전용 retired 자원과 native 역사 inventory의 최종 대조, 전체 누적 diff 검토다.

### 진단 소유 자료·과거 게시 checkpoint·baseline의 최종 제거 연결

시작 HEAD `8a2dc17a91bc84b2ead0687f8723c4af5052ebef`, 비교 base `4a46a9ef4d8859573a6ce1f008e82d2b8d677683`에서 현재 계획·sources의 삭제 확정/보존·사용량·종료·archive 경계를 다시 대조했다. 현재 원격 main 대비 누적 변경 목록과 실행/게시/저장/알림/유지보수/자원 정리 경계의 diff를 검토했다. 누적 테스트·문서 diff 전체의 최종 의미 검토는 아직 완료하지 않았으며 전체 verify/Review도 Worker 완료 근거로 대체하지 않는다. 이 절의 현재 판정이 아래 과거 호출의 잔여 목록보다 우선한다.

현재 검증 피드백 `b6c7ef6f6e3759da16a4b17d2150b9b60bbfbb4d5608b4b1febe098221eca4c1`은 현재 코드의 `BlockedCheckpointRefreshUnitTests` 29건으로 재확인해 모두 PASS했다. 지정된 7개 실패 사례가 포함된다. 이전 게시 순서 `test_interruption_before_push_reuses_intent_before_later_base_fetch`와 복구 state_dir `test_blocked_recovery_validates_scope_before_fetch_and_catalog`도 함께 실행해 총 31건 PASS였다. checkpoint 전달·게시를 해결 확인으로 사용하지 않았다.

이번에는 final forget의 `(repo, plan_id)` 열거 밖에 남던 진단 자료를 실제 scope/owner와 ref 관계로 연결했다. 새 `storage/deleted_diagnostic_state.py`는 DB capture/CAS/부분 제거만 맡으며 Git 효과·새 성공 상태를 만들지 않는다. 기존 diagnostic/worktree/Git lease 아래 SQL origin을 고정해 remote/local ref·PR·worktree 경로와 등록의 실제 부재를 확인한다. plan/project scope의 대상 owner 자료, native preparation/attempt와 전용 bundle을 함께 정리한다. 현재 공유 프로젝트 원인·독립 ref 사용자·다른 owner가 섞인 불변 관측은 보호한다. bundle은 기존 native artifact loader로 원문/manifest/tree/commit 귀속을 검증한 뒤 기존 queue로 제거한다. 파일 소비 직전에도 preservation/ref use의 현재 경로를 다시 읽고 관리 루트 아래 부모 symlink 전환을 거부한다. 손상·불완전 자료와 경합은 원본 근거를 보존한 채 pending으로 남는다.

이미 최종 제거 표식만 남았지만 과거 형상의 scope 기반 진단 기록이 잔존하면 그 표식으로 재발견한다. 새 실행/취소/hold/checkpoint 부재·현재 원격 문서·실제 자원·호출/수동/게시 소유·capture CAS를 다시 확인한다. 원래 선언이나 가짜 READY row를 복원하지 않는다. 일반 취소/예약을 삭제 확정으로 승격하지 않으며 cache도 잔존 진단 자료가 해소될 때까지 같은 revision에서 재진입한다. 오래된 DiagnosticPublicationRepository.preserve 호출은 최초 조회와 writer 확보 뒤 취소/삭제 ID를 재검사해 새 자료를 재생하지 못한다.

과거 관리 자원이 실제로 사라진 row 없는 감사에는 native V1 baseline 귀속·tree/OID·stage_trees·원래 GitSnapshot.head로 계산한 ref identity를 검증하고 ref lease 아래 부재를 두 번 관측한다. 이 경로에서 baseline을 직접 지우지 않으며 살아 있거나 다시 생긴 ref는 감사를 보존한다. 저장 URL과 canonical head branch가 일치하는 CLOSED 미Merge PR은 역사로 인정해 삭제를 이어간다. ### 전용 문서 worktree의 실제 정리와 종료된 checkpoint 내용의 제거

### 등록 전 hold·과거 유지보수 연결의 종결 전이와 참조 CAS

복구점 `ef0de89331d18cb2cf835a4796676aa12f7b7134`에서 잔여 항목을 다시 대조했다. 기존 미해결 verify feedback `b6c7ef6f6e3759da16a4b17d2150b9b60bbfbb4d5608b4b1febe098221eca4c1`의 7개를 포함한 `BlockedCheckpointRefreshUnitTests` 29개가 이번 호출의 현재 코드에서 PASS했다. 전달·checkpoint 게시를 해결 근거로 쓰지 않았다. 시작 시 미보존 상태였던 quota 교정 두 파일도 유지하고 관련 4개를 현재 코드에서 다시 실행해 PASS했다.

반복 잔여 항목 중 실제 종결 경로가 없었던 세 항목을 연결했다.

- 등록 전 hold: 기존 `rowless_hold_deletion_evidence`의 원문·원래 선언/hash·원래/삭제 revision과, `resolve_recovery`가 게시 확정 뒤 저장한 approval의 commit·현재 path/hash를 소비한다. 모든 원래 영향 대상의 현재 원격 Decision Log를 기존 reference recovery 검증으로 확인하고 approval commit도 현재 pin의 ancestor인지 검사한다. 실행/취소/호출/checkpoint 이력·Merge 근거가 있으면 이 무실행 경로에서 제외한다. canonical PR/ref·현재 수동/게시 소유권과 hold 전체 CAS를 재검사해 실행 row 없이 기존 forget로 종결한다. 판단 없는 원격 부재나 불완전한 원문은 철회로 추정하지 않는다. cache도 삭제된 hold를 같은 revision의 재진입 대상으로 소비한다.
- 대상 단독 assessment finding: 확인된 최종 제거에서 해당 finding만 제거한다. shared finding은 독립 연결을 확인해 ID 부분만 제거하고, 나머지 발견·coverage·source·성공 기준은 그대로 유지한다. 삭제를 resolved·평가 성공으로 쓰지 않는다. 마지막 cycle 대상 연결은 기존 정상 종료까지 보존하고, 정상 종료 뒤 대상 단독 finding도 빈 findings 목록으로 제거할 수 있음을 native cycle 종료 회귀에서 확인했다.
- 과거 tiered root link: 실제 정상 종료 commit/실제 Merge 수가 있는 IDLE cycle이고 게시·workspace 해제가 끝났으며 링크 cycle이 현재 revision보다 과거일 때 대상 link만 제거한다. 공유 배열의 독립 항목·assessment digest·source·다른 repository를 유지한다. 현재/미종료 cycle과 손상·불명 형식은 보류한다. 대상 전용 link row만 삭제하며 과거 부분 연결을 삭제 전의 완전한 평가로 재사용하지 않는다. 같은 transaction의 rollback과 cycle revision 무효화를 유지한다.
