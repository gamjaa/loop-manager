## Purpose

G-325가 확인한 동일 원인·입력의 무진전 지속 장애를 기존 outbox로 한 번 진단 통지한다. 현재 `notifications/policy.py:is_current()`는 지속 실패 사건을 허용하지 않으며 `tests/test_notification_events.py:test_persistent_failure_stays_diagnostic_without_separate_alert`는 무조건 무통지를 기대한다. 단순 실패·대기 통지 금지는 유지하고 새 R-053의 확인된 정체만 추가한다. 신규 PR 생성 알림의 이번 직접 구현은 재구현하지 않는다.

## Acceptance Criteria

- 같은 작업/자원·단계·원인·유효 입력/진전 identity의 현재 정체가 G-325의 실제 이력으로 확인될 때 사건 하나를 생성한다. 같은 실행/외부 재시작·반복 enqueue·전송 재시도는 중복 사건을 만들지 않는다. 실패 횟수·시간 경과·상태 코드·자동 복구 가능성만으로 전송하지 않는다.
- 전송 직전과 각 조각 claim에서 현재 정체·대상·입력·진전 부재를 재확인한다. 실제 진전·원인 해소·다른 후보이면 남은 조각만 취소하며 원래 payload·고정 본문·확인 cursor·attempt/error·취소/전송 감사는 보존한다.
- 메시지는 프로젝트/작업·영향 범위·실제 반복 횟수와 확인 기간·마지막 상세 원인·보존한 Git 작업물/checkpoint·다음 유효 재평가 조건을 담는다. 확인되지 않은 `recover`·reset·force push·문서 변경이나 가짜 사용자 행동을 해결책으로 만들지 않는다. 정체 진단과 실제 사용자 조치·최종 복구 불가 중단은 구분한다.
- 알림이 복구·재배정·최종 차단·완료를 변경하지 않는다. 비활성화·전송 지연/실패에서도 기존 실행·게시·필수 검증과 G-325의 보존/재개 판단은 동일하다. 추가 Agent·원격 조회·Git 쓰기 없이 저장된 현재 근거를 사용하고 비밀값을 노출하지 않는다.
- 시작/진행/완료/자동 재개·정상 retry·자원/사용량 대기는 계속 일반/무음 전송 0건이다. 구정책의 미전송/부분 사건을 새 정체로 소급 승인하지 않으며 현재 확인한 새 근거만 사용한다. 신규 PR 생성 이력과 기존 후보 갱신의 별도 identity·부분 전송 계약을 유지한다.

## Implementation

- [ ] 확인한 `loop_manager_internal/notifications/events.py`의 기존 persistent 실패 취소·억제와 `repository.py`의 outbox/고유 사건 키를 재사용한다. G-325의 근거를 명시적으로 받아 현재 정체만 enqueue하고 legacy 진단을 자동 승인하지 않는다. 원인에 맞는 별도 사용자 조치가 이미 있으면 그 근거와 진단을 혼동·중복 통지하지 않게 대조한다.
- [ ] 확인한 `notifications/policy.py:is_current()`·`cancel_stale_events()`와 `delivery.py`의 공통 claim에 같은 정체 identity 검증을 연결한다. 전송 여부가 recovery row의 실행 상태를 바꾸지 않으며 기존 partial/cursor·늦은 확인·취소 감사 경계를 유지한다.
- [ ] 확인한 `notifications/rendering.py`의 결정적 rendering·비밀값 제거와 `storage/recovery_state.py`의 기간/횟수·checkpoint 근거를 연결한다. 별도 알림 채널·대시보드·정책 설정이나 임의 조치 안내를 추가하지 않는다.
- [ ] 확인한 `tests/test_notification_events.py`·`test_notification_delivery.py`·`test_recovery_state.py`의 fixture를 확장한다. 무조건 지속 실패 무통지 assertion은 확인된 정체/정상 일시 실패로 나누고 기존 범위·보존·전송 오류 assertion은 유지한다. PRODUCT의 Telegram 사건 표와 ARCHITECTURE의 생성/claim·payload 계약에 실제 구현만 통합한다.

## Validation

- Worker targeted unit은 위 notification 모듈의 변경한 최소 case와 G-325 근거 소비 case다. 한 실행의 여러 묶음·외부 재시작·동일 관측에서 사건 1건, 새로운 원인/입력은 별도 판정, 정상 대기/단순 횟수 소진은 0건인지 실제 SQLite/outbox와 mock 전송으로 확인한다.
- 부분 전송 뒤 진전/해소·후보 교체·재시작·늦은 전송 확인·통신 실패를 주입한다. 오래된 후속 조각은 보내지 않고 기존 payload/cursor/감사는 보존한다. G-325 근거 부재·손상·generation 경쟁에서는 송신을 승인하지 않는다.
- 비활성/실패 송신 전후 실행 단계·소유권·검증/게시 token·복구 판단이 같고 Git/Agent 효과가 0회인지 검사한다. 기존 `PrCreationPublicationTest`와 draft/차단 조치·진행 무통지 회귀는 재사용하며 같은 프로토콜 시험을 복제하지 않는다.
