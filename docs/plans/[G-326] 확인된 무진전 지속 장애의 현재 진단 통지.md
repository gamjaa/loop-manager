## Purpose

G-325가 확인한 동일 원인·입력의 무진전 지속 장애를 기존 outbox로 한 번 진단 통지한다. 현재 `notifications/policy.py:is_current()`는 지속 실패 사건을 허용하지 않으며 `tests/test_notification_events.py:test_persistent_failure_stays_diagnostic_without_separate_alert`는 무조건 무통지를 기대한다. 단순 실패·정상 자원 대기의 별도 경고 금지는 유지하고 R-053의 확인된 정체만 추가한다. 확정 정보 사건은 G-340–G-342가 맡으며 신규 PR 생성 알림의 직접 구현은 재구현하지 않는다.

## Acceptance Criteria

- 같은 작업/자원·단계·원인·유효 입력/진전 identity의 현재 정체가 G-325의 실제 이력으로 확인될 때 사건 하나를 생성한다. 같은 실행/외부 재시작·반복 enqueue·전송 재시도는 중복 사건을 만들지 않는다. 실패 횟수·시간 경과·상태 코드·자동 복구 가능성만으로 전송하지 않는다.
- 작업 ID 없는 planning·publication 적용/해제·정리와 후보가 있는 비오류 WAITING·skip·조기 반환도 G-325가 확인한 원인별 사건으로 소비한다. 원인 소유자·operation/intent·영향 대상·충돌/미확인 자원·남은 단계와 다음 조건을 실제 근거가 있는 범위에서 표시하며 legacy 부재를 추정하지 않는다. 독립 작업 성공·새 run ID·정상 반환만으로 현재 사건/미전송 조각을 취소하지 않는다.
- 전송 직전과 각 조각 claim에서 현재 정체·대상·입력·진전 부재를 재확인한다. 실제 진전·원인 해소·다른 후보이면 남은 조각만 취소하며 원래 payload·고정 본문·확인 cursor·attempt/error·취소/전송 감사는 보존한다.
- 메시지는 프로젝트/작업·영향 범위·실제 반복 횟수와 확인 기간·마지막 상세 원인·보존한 Git 작업물/checkpoint·다음 유효 재평가 조건을 담는다. 확인되지 않은 `recover`·reset·force push·문서 변경이나 가짜 사용자 행동을 해결책으로 만들지 않는다. 정체 진단과 실제 사용자 조치·최종 복구 불가 중단은 구분한다.
- 알림이 복구·재배정·최종 차단·완료를 변경하지 않는다. 비활성화·전송 지연/실패에서도 기존 실행·게시·필수 검증과 G-325의 보존/재개 판단은 동일하다. 추가 Agent·원격 조회·Git 쓰기 없이 저장된 현재 근거를 사용하고 비밀값을 노출하지 않는다.
- R-053이 허용한 신규 문서/draft·실제 시작/재개·안정적 소진/최종 완료는 G-340–G-342의 별도 정보 사건으로 유지한다. 정상 retry·일시 자원/사용량 대기·내부 단계·단순 실패 자체의 별도 일반/무음 경고는 0건이며 정보 사건만으로 지속 장애를 확인하거나 해소하지 않는다. 구정책의 미전송/부분 사건을 새 정체로 소급 승인하지 않고 현재 확인한 근거만 사용한다. 신규 PR 생성 이력과 기존 후보 갱신의 별도 identity·부분 전송 계약을 유지한다.

## Implementation

- [ ] 확인한 `loop_manager_internal/notifications/events.py`의 기존 persistent 실패 취소·억제와 `repository.py`의 outbox/고유 사건 키를 재사용한다. G-325의 근거를 명시적으로 받아 현재 정체만 enqueue하고 legacy 진단을 자동 승인하지 않는다. 원인에 맞는 별도 사용자 조치가 이미 있으면 그 근거와 진단을 혼동·중복 통지하지 않게 대조한다.
- [ ] 확인한 `notifications/policy.py:is_current()`·`cancel_stale_events()`와 G-356의 공통 큐/조각 claim에 같은 정체 identity 검증을 연결한다. 사건 생성은 outbox 확정까지만 수행하고 프로젝트/작업의 inline flush나 전송 완료를 기다리지 않는다. 전송 여부가 recovery row의 실행 상태를 바꾸지 않으며 기존 partial/cursor·늦은 확인·취소 감사를 유지한다. 공통 송신/재시도 조율은 재구현하지 않는다.
- [ ] 확인한 `notifications/rendering.py`의 결정적 rendering·비밀값 제거와 `storage/recovery_state.py`의 기간/횟수·checkpoint 근거를 연결한다. 별도 알림 채널·대시보드·정책 설정이나 임의 조치 안내를 추가하지 않는다.
- [ ] 확인한 `notifications/events.py:suppress_persistent_failure_for_block()`와 `policy.py`의 현재 차단 대조를 G-325의 프로젝트/operation identity에도 연결한다. 이미 같은 원인의 현재 사용자 행동을 통지한 경우만 중복을 억제하고, 작업 ID 부재나 다른 계획의 성공/차단으로 이 사건을 해소하지 않는다. 실제 해당 원인 해소·진전의 저장 근거를 claim 때 다시 확인한다.
- [ ] 확인한 `tests/test_notification_events.py`·`test_notification_delivery.py`·`test_recovery_state.py`의 fixture를 확장한다. 무조건 지속 실패 무통지 assertion은 확인된 정체/정상 일시 실패로 나누고 기존 범위·보존·전송 오류 assertion은 유지한다. PRODUCT의 Telegram 사건 표와 ARCHITECTURE의 생성/claim·payload 계약에 실제 구현만 통합한다.

## Validation

- G-356의 제어된 전송/실제 outbox fixture에 확인된 정체 사건만 연결한다. 원인 작업과 프로젝트가 진행/보류 중이어도 공통 큐에서 사건의 claim/부분 재시도가 진행하고, 송신 지연·DB 결과 확정 재시도가 진전 이력이나 작업 상태를 바꾸지 않아야 한다. 공통 네트워크·큐 공정성 행렬은 선행 회귀를 소비하고 여기서는 정체의 현재성·해소 연결만 추가한다.
- Worker targeted unit은 위 notification 모듈의 변경한 최소 case와 G-325 근거 소비 case다. 한 실행의 여러 묶음·외부 재시작·동일 관측에서 사건 1건, 새로운 원인/입력은 별도 판정, 정상 대기/단순 횟수 소진은 0건인지 실제 SQLite/outbox와 mock 전송으로 확인한다.
- 부분 전송 뒤 진전/해소·후보 교체·재시작·늦은 전송 확인·통신 실패를 주입한다. 오래된 후속 조각은 보내지 않고 기존 payload/cursor/감사는 보존한다. G-325 근거 부재·손상·generation 경쟁에서는 송신을 승인하지 않는다.
- 비활성/실패 송신 전후 실행 단계·소유권·검증/게시 token·복구 판단이 같고 Git/Agent 효과가 0회인지 검사한다. 기존 `PrCreationPublicationTest`와 draft/차단 조치·내부 단계 무통지 회귀를 재사용한다. 허용된 정보 사건과 정체 진단이 함께 있어도 원인/확인 identity가 섞이거나 정체를 초기화하지 않아야 하며 같은 프로토콜 시험을 복제하지 않는다.
- 작업 ID 없는 publication 해제·비오류 대기 정체의 같은 실행/다음 외부 실행·부분 전송을 실제 SQLite/outbox로 연결한다. 독립 성공·WAITING의 정상 코드·다른 operation 해소 뒤에도 원인 사건 1건과 잔여 조각이 유지되고, 실제 해당 복구 진전/해소 뒤만 오래된 조각이 취소돼야 한다. 정상 자원/PR/사용자 판단 대기와 이미 통지한 같은 행동은 새 정체 통지 0건이다.
