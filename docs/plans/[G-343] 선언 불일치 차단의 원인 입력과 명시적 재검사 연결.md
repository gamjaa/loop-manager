## Purpose

소유 rebase의 `plan_input_invalid` 차단 재평가를 원인 관련 입력 변경과 명시적 해제/재개 요청에 연결한다. 원격의 정책 표시에 따른 예외 제거는 재사용하고, 남은 자동 최초 진입의 원인 입력 확인 및 기존 `recover` 요청의 대상별 소비를 보완한다. 같은 상태의 자동 재개와 명시 요청의 영구 억제를 모두 막으며 기존 소유권·원격·보존 검사와 rebase/최종 검증 순서를 유지한다.

## Acceptance Criteria

- 직접 구현된 `unblock`은 사용자 판단/공통 교정 차단의 명시 해제 경계이며 이 계획의 metadata 안전 차단을 우회하지 않는다. metadata의 명시 재검사는 기존 `recover` 요청으로 현재 원인/소유권을 검사한다. 포화만으로 요청 수락을 거부하지 않고 실제 후속 실행의 관리 자격·보존 대기/인계는 R-091의 현행 경계를 따른다.

- R-055: 자동 재평가에서는 ExecPlan 등 해당 원인과 관련된 입력/상태 변화의 실제 근거가 있어야 한다. 코드·검사 정책 변경·과거 `rebase_block_release_policy` 부재/값·재시작이나 단순 재관측만으로 동일 원인·Git 상태의 metadata 차단을 해제하지 않는다. 첫 해제 기록이 없는 과거 차단도 같은 기준이다. 정상 Git 상태가 실제로 안전한 START로 바뀐 경우와 무관한 SHA 변화를 구분하며 근거가 없거나 비교 불가이면 보존한다.
- 기존 명시적 차단 해제/재개 요청은 같은 입력에서도 현재 원인을 다시 검사하는 계기로 전달된다. 계획 지정/프로젝트 요청의 실제 대상·요청 identity·원인·checkpoint generation을 검증하고 한 요청의 동일 원인 재생을 제한한다. 요청은 소유권·writer 종료·원격/PR·dependency·pause·planning/관리 자리 검사를 우회하는 승인이 아니며 metadata 외 독립 차단과 사용자 판단은 유지한다.
- 요청 수락·원인 검사·해제/소비 확정 사이 중단·재시작·경쟁 변경에서 요청과 실행 자료를 보존한다. 이미 소비한 같은 요청/원인은 자동 재개를 반복하지 않고 미완료 적용은 기존 확정 지점부터 이어간다. 새 명시 요청과 단순 재실행·pause `resume`은 구분한다. 직접 SQLite 수정이나 기록 삭제로 재개를 만들지 않는다.
- START/WAITING으로 재개한 소유 rebase는 원래 target·HEAD·파일·index·session·실패 이력·이전 정책 감사를 유지하며 남은 충돌 해결/실행 단계로 이어진다. 이 전이를 rebase 완료·Worker/verify/Review 성공이나 게시 acceptance로 기록하지 않는다. 공식 선언 교정은 R-082의 최신 원격 base 게시·catalog/DB 반영 뒤 작업 rebase로 전달하는 경계를 따르며 Git 완료 후 전체 최종 검사를 유지한다. 새 작업 브랜치 선언 복원 commit을 만들지 않고 이미 저장된 과거 복원 intent의 제한 복구만 보존한다.
- 다른 계획의 실행/복구/투영과 독립 작업은 영향을 받지 않는다. 외부 Git/PR 관측과 대기는 DB 쓰기 구간 밖에서 수행하고 적용 직전에 같은 소유권·원인·generation을 재확인한다. 거부·자료 부족·실제 원격/소유권 변경은 기존 차단과 진단을 보존한다.

## Validation

- 같은 metadata 입력에서 일반 run/unblock과 유효한 recover 요청을 구분한다. unblock은 안전 원인 거부·원문/요청 보존, recover는 현재 소유/원인 검사 뒤 기존 제한 소비로 이어져야 한다. 명령 수락과 실제 재개/검증 성공을 혼합하지 않는다.

- Worker는 변경한 metadata 재평가/요청 연결의 최소 unit만 실행한다. 정책 표시 없음/기존 값, 과거 해제 기록 없음/있음과 동일 입력·Git 상태에서는 자동 해제 0회여야 한다. 기존 `test_metadata_release_policy_does_not_resume_unchanged_block`과 관련 입력 변화 재개 회귀를 재사용하고 실제 새 입력·안전한 START 변화는 현재 검사 뒤 저장 단계로 이어지는지 확인한다.
- 같은 입력의 유효한 명시 요청, 같은 요청 재소비, 새 요청, 다른 계획·원인·stale generation·미충족 dependency·pause·writer/원격/PR 변경을 주입한다. 허용 전이는 한 번, 나머지는 무쓰기/보존이어야 하며 기존 verify 요청의 제한 재검사·소비 계약은 유지한다.
- 요청 소비와 block/checkpoint 적용 전후 중단·rollback·DB 경합/소유권 경쟁을 실제 SQLite로 확인한다. 외부 관측 중 독립 DB 요청이 진행하고 재진입에서 Worker/commit/push·실패 집계·원문 보존 효과를 반복하지 않아야 한다. 실제 Git lifecycle은 기존 소유 rebase 통합 회귀를 유지하고 같은 정책 조합마다 새 repository를 만들지 않는다.
- 재개 뒤 원래 target·파일/index·session/실패 이력·이전 정책 감사와 별도 차단을 비교한다. START/WAITING에 완료 acceptance·verify/Review/게시 token이 없고 실제 Git 완료 뒤 최종 선언·범위 검사는 계속 필요하다. 현재 `tests/test_rebase_definition_boundary.py:test_completed_rebase_does_not_create_a_declaration_repair_commit`을 재사용해 새 선언 복원으로 해제를 만들지 않는다. 공식 base 교정의 게시/적용과 작업 rebase 연결은 G-348이 이 재평가 계약을 소비해 검증하며 이 작업의 새 선행으로 요구하지 않는다. 알림은 G-341의 실제 시작 경계를 소비하며 해제만으로 발송하지 않는다.
