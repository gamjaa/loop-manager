## Purpose

삭제 참조 복구 snapshot의 개정이 기존 선행 작업의 실행 보류 때문에 게시 검증에서 거부되는 경로를 교정한다. R-055의 `### 실행 보류와 Planner 복구 검토 권한`에 따라 복구 판단의 게시와 Worker 실행 가능 여부를 분리한다. 필요한 dependency와 snapshot 밖 문서를 보존하면서 허용된 대상의 참조 판단을 게시할 수 있어야 한다.

## Acceptance Criteria

- 원격 revision·원본 hash·SQLite 실행 근거에 결합된 삭제 참조 복구 snapshot의 대상만 개정할 수 있다. 해당 개정이 원본부터 필요로 하던 선행 작업에 보류가 남아 있어도, 유효한 현재 source·identity·목표 보존과 삭제 목표별 `DEPENDENCY_RECOVERY` 판단을 검증해 게시할 수 있다. 직접 선행과 간접 선행의 보류를 같은 기준으로 처리한다.
- 이 허용은 복구 개정의 기존 선행 보류에 한정한다. 새 계획·일반 개정의 보류 의존성 거부와 새로 추가한 보류 dependency·보류 대체 목표의 거부를 유지한다. 없는 ID·잘못된 source·순환·자기 의존·무근거 목표 제거를 허용하지 않고, 실행 가능성을 얻기 위해 필요한 dependency를 지우지 않는다.
- snapshot 밖·PR 등록·archive·수동 소유 문서는 수정하지 않는다. archive된 선행 파일의 역사 참조 때문에 생긴 보류도 파일 편집·삭제나 수행하지 않은 Merge 합성으로 해소하지 않는다. 기존 실행 상태·Merge 증명·최초 게시 감사·session·작업물·실패·Worker level을 보존한다.
- 복구 판단을 원격에 게시하고 같은 후보의 catalog에 적용한 뒤 해소된 참조 원인만 확정한다. 선행에 남은 보류와 그 의존 범위의 Worker 진입 거부는 계속 유지한다. 복구 개정이 등록됐다는 사실이나 판단 대상 ID를 검사에서 제외했다는 이유로 독립 보류·승인 또는 실행 gate를 없애지 않는다.
- 결과 검증·게시·SQLite 적용·재조정 사이 중단, 원격 전진·PR 출현·수동 소유권 변경에서는 기존 publication intent·snapshot 경계로 재검증하거나 보존한다. 같은 게시 결과의 재관측은 중복 해제하지 않으며, 판단 이후 본문·source·dependency 입력이 바뀌면 그 판단을 무조건 재사용하지 않는다. 독립 계획은 계속 처리한다.

## Implementation

`planning/planner_validation.py`의 새 계획/일반 개정/삭제 참조 복구 개정 분류와 `catalog/project_catalog_refresh.py`의 직접·간접 보류 검사를 대조한다. 기존 snapshot의 dependency 관계·보류 원인과 변경된 관계를 사용해 복구 개정의 게시 유효성을 판단하며, 일반 planning과 유지보수에 사용하는 공통 검사를 통째로 완화하지 않는다. `validated_held_planning_snapshot`도 같은 복구 대상을 검증하도록 맞추되 유효하지 않은 자기 선언과 단순히 선행 보류를 상속한 선언을 구분한다.

`catalog/remote_deletions.py`의 삭제 목표별 의미 판단·hash 결합 참조 승인과 기존 planning publication의 원격 확인·원자 적용·중단 복구를 재사용한다. 개정 가능한 참조 원인의 해소와 선행 보류의 전파를 별도로 확인해 Worker 선택 전에 미해소 gate가 유지되도록 한다. 별도 상태 원본·새 완료 상태·schema나 포괄적인 보류 무시 설정을 추가하지 않는다. 실제 동작에 맞춰 PRODUCT·ARCHITECTURE의 planning 게시·계획별 보류 설명만 필요한 범위에서 갱신한다.

이 작업은 Manager의 복구 결과 검증·게시 계약을 구현한다. Worker가 다른 계획이나 archive 파일을 직접 고치는 작업은 아니다. 교정 Merge 뒤 Manager가 최신 원격에서 새로 제공한 snapshot으로 미게시 영향 계획을 다시 검토한다. 이 작업의 Merge만으로 과거 복구 판단을 적용하거나 전체 차단 감사를 완료로 기록하지 않는다.

## Validation

- `tests/test_incremental_planning.py`의 삭제 목표 복구·게시 fixture를 재사용한다. 실제 parser·validator와 SQLite에서 영향 계획의 기존 직접/간접 선행이 보류된 경우, 허용된 복구 판단은 검증·게시되고 선행 보류와 Worker 선택 거부는 유지되는지 최소 targeted unit으로 확인한다. 일반 계획·일반 개정·새 보류 연결·보류 대체 목표·잘못된 source·순환과 판단 누락은 계속 거부돼야 한다. 정책 조건과 원격/CLI 관측은 기존 mock 경계로 제공한다.
- 같은 fixture에서 snapshot 밖 archive 선행의 bytes와 상태·Merge 감사, 수동 예약, 시작한 계획의 ID·경로·session·실패/level 보존을 확인한다. 보류 검사 순서만 바꿔 다음 catalog 검사에서 다시 실패하거나 게시 직후 Worker가 먼저 실행되는 경우를 함께 검증한다.
- 기존 원자 게시·멱등 적용·snapshot 경쟁 회귀를 확장해 게시 전 보류 유지, push 뒤 적용 전 중단, 재시작, 원격/PR/수동 소유권 경쟁과 개정 입력 변경 뒤 재보류를 확인한다. 실제 Git이 필요한 원격 commit·허용 diff·파일 보존은 기존 통합 fixture를 재사용하고 외부 게시를 불필요하게 반복하지 않는다.
- Manager 전체 verify는 보류 계획의 실행 금지, 독립 READY 지속, 일반/유지보수의 기존 dependency 검사, snapshot 밖 쓰기 거부와 publication intent 복구를 유지한다. Reviewer는 필요한 목표 삭제·미게시 해제·다른 보류 해제·실행 성공 합성을 blocking issue로 확인한다.

## Decision Log

- 관측된 거부는 `G-189 -> G-211`이다. `planner_validation.validate_planner_result`는 개정한 영향 ID만 `recovery_ids`로 제외하고 남은 보류 ID를 `assert_planning_dependencies_unheld`에 전달한다. 이 검사는 기존 dependency와 신규 연결을 구분하지 않아, 영향 계획의 참조 판단을 검증하기 전에 원래 선행의 보류로 개정을 거부한다. 간접 선행에서도 같은 검사가 적용되므로 특정 ID 한 개 제거로 해결할 수 없다.
- G-189의 삭제 참조 복구 개정은 현행 검사에서 게시할 수 없어 이 batch에서 원본 bytes·dependency·Progress를 보존한다. 이전 미게시 수정안은 `/tmp/loop-manager-planning-rejected-g189-867eeac1.md`에 보존했으나 향후 실행·게시의 권한이나 성공 근거로 사용하지 않는다. 교정 뒤에는 새 snapshot과 최신 원문으로 다시 판단해야 한다. snapshot 밖 선행·archive와 수동 G-207은 수정하지 않는다.
- G-189는 R-055의 전체 차단 경로 감사·잔여 교정과 삭제 목표 의미 판단을 유지한다. 이 계획은 그 복구 검토를 막는 확인된 결과 검증·게시 결함만 선행 교정하며, G-255/G-256의 rebase 문서 처리·최신 조건 교정 또는 다른 비종료 계획의 목표를 중복하지 않는다. 아직 게시할 수 없는 G-189를 이 계획의 dependency로 연결하지 않는다.
- 직접 구현된 `recoverable_ids`·source 조회·PR 전 snapshot 보호·명시적 참조 승인·게시 후 원자 적용은 재사용한다. 이 국소 교정과 독립 계획 작성은 전체 R-055 충족 또는 프로젝트 최종 명세 전문 확인을 뜻하지 않는다.
- complexity medium: 기존 snapshot·validator·참조 승인·게시의 명확한 경계에서 기존 선행 보류와 새 연결을 구분하고 원인별 적용을 연결하는 작업이다. risk high: 예외를 과도하게 적용하거나 게시 뒤 선행 보류를 함께 지우면 미충족 선행·권한 경쟁이 있는 작업을 실행하거나 잘못된 선언을 게시할 수 있다. 원본 선언·게시 후보·hash 결합 판단·실행 감사를 남겨 수동 재평가할 수 있어야 하며, 외부 게시를 코드 rollback만으로 복구한다고 가정하지 않는다. 거부·보존·중단/재개와 Worker gate를 AC·Validation·Review에 포함한다.
