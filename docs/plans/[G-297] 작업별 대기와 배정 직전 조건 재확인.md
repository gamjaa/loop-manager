## Purpose

R-091의 직접 구현된 관리·Agent·verify 한도와 배정기를 재사용해, 작업별 대기·예외가 같은 프로젝트의 독립 배정을 막는 잔여 경계를 보완한다. 배정 대기 뒤에는 현재 실행 자격과 후보를 다시 확인하고, 실행 중 관측한 명세 변경은 프로젝트 조율기의 판단을 거쳐 후속 배정 전에 반영한다. 설정·migration·호출 receipt·공정 배정과 이미 Merge된 RETRY 우선 재배정·Planner/runtime 배정 중단 신호와 반환 처리는 재구현하지 않는다.

현재 `run_project_tasks()`의 일반 RETRY·단계 예외 격리·독립 선택과 `managed_count()`의 차단/실제 예약 분리는 구현돼 있다. `slot()`의 rank 갱신, condition 밖 DB 예약/cursor 원자 확정, 반환 확인 뒤 자리 해제와 `scheduled_call()`의 작업 snapshot·프로젝트 차단·catalog/draft 재검사도 재사용한다. verify의 `verify_preflight()`는 slot 배정 뒤 process receipt 준비 전에 기존 targeted gate를 실행하며 미시작 자리 반환으로 연결돼 있다. 남은 범위는 `admission()` 대기 중 현재 자격·rank 갱신, DB 예약 대기 뒤 Planner/runtime 중단 및 dependency·수동 소유·유지보수/후보 입력의 실제 호출 직전 재확인, 실행 불가 대기 항목이 다른 적격 후보를 막지 않는 연결이다.

작업 revision gate의 전체 명세 지문 검사·`planning_required` 연결은 제거돼 있다. 이는 최신 ARCHITECTURE의 프로젝트 소유 판단을 따르는 직접 구현이다. 다만 `run_project_tasks()`의 자식은 `_dispatch_execution()`에 `planning_context`를 전달하지 않으며, 프로젝트 루프에도 실행 중 새 명세를 판단해 배정 중단으로 전달하는 연결이 없다. 현재 단계 전환 회귀는 `pause_project()`를 직접 호출하므로 실제 명세 관측부터의 연결을 보장하지 않는다. R-082/R-091의 미반영 명세 재확인은 이 작업의 기존 배정 직전 검사 범위에서 보완하고, 작업별 전체 지문 검사나 별도 영향 Planner를 복원하지 않는다.

준비·단계·보류 기록 조회의 `DatabaseWaitTimeout` 분류와 독립 배정은 재사용한다. 이번 R-091 delta는 일반 예외 3회·DB 요청 한도 소진·준비/결과 수집 실패를 다음 외부 실행 전용 보류로 남기는 범위를 바꾼다. 실제 차단이 아니면 작업별 재시도 대기 뒤 같은 실행에서 다시 준비하고, 원래 오류·저장 오류·실패 횟수와 이미 수행한 효과를 보존한다. DB 원자 요청은 G-303, self runtime의 30초 TTL·종료 결정 캐싱·안전한 인계 정책은 G-312, 단계별 비차단 사유/교정 예산은 G-313의 책임이다. 이 작업에서는 대기·재배정 및 실제 호출 직전의 기존 공통 gate 소비만 맡는다.

## Acceptance Criteria

- 작업별 일시 대기·호출 종료 불명·독립 실패는 해당 작업과 실제 충돌 자원에만 적용한다. 프로젝트 차단·새 명세의 미반영 범위·planning 배타·runtime handoff처럼 공유 중단이 필요한 경우와 구별하며 기존 보호를 약화하지 않는다.
- 관리 한도 3인 A에서 차단되지 않은 종료 불명 verify 하나가 관리 자리를 유지해도, 독립 READY는 남은 관리·Agent 한도 안에서 실행한다. PLAN_BLOCKED는 미완료 operation·호출 예약이 있어도 관리 개수에서 제외하는 현재 구현을 유지한다. 두 경우 모두 실제 실행 자리·자원 예약·checkpoint와 작업물·실패 이력은 보존하며 같은 verify 자리·같은 후보를 재사용하지 않는다. B의 적격 작업도 계속한다.
- 배정 직전에 현재 작업·단계·관리 소유와 관련 안전 조건을 확인한다. 대기 중 프로젝트 차단, catalog/draft·dependency·수동 소유·유지보수 범위 또는 명세·후보 변경이 생기면 오래된 준비 결과로 Agent·verify를 시작하지 않고 기존 재관측·단계 준비로 돌아간다. pause 지원은 G-236의 기존 계약과 연결하며 이 작업에서 별도 pause 정책을 만들지 않는다.
- R-082/R-091: 병렬 실행 중 관측한 원격 PRODUCT·활성 Requirement·ARCHITECTURE 변경의 planning 필요 여부는 프로젝트 조율기가 판단한다. 필요하면 해당 프로젝트의 신규 편입·Worker·verify·Reviewer·게시 후속 배정을 멈추고 실행 중 호출이 안전하게 반환한 뒤 기존 일반 planning·게시·catalog·DB 적용을 거쳐 보존된 작업을 재배정한다. 작업 전체 완료나 PR 생성을 기다리지 않으며 다른 프로젝트는 진행한다. 관측 실패·불확실을 명세 무변경으로 확정하지 않는다.
- 프로젝트의 유효한 planning 기준에서 이미 반영한 동일 입력, 코드·테스트·설정·ExecPlan 전용 변경과 내용 보존 Requirement archive는 새 명세 planning을 만들지 않는다. 작업 revision gate는 선택된 ExecPlan·dependency·최신 base·후보 결과를 계속 검사하되 전체 명세 지문으로 planning을 재요청하지 않는다. 미확정 planning·종료 불명·보존 rebase·실패 이력을 성공이나 초기 상태로 바꾸지 않는다.
- 수락 수동 제출의 최초 수락 순서 → RETRY 재등록 순서 → 기존 자동 작업 재개 → 일반 신규의 순서를 유지한다. 실행 불가 후보는 다른 적격 후보를 막지 않고, 기본 배정은 실제 Agent 호출 유무로 계산한다. verify만 기다리는 프로젝트의 독립 신규 호출, 재시작 cursor, 전역 유효 priority·숫자 ID 정렬을 유지한다. 이미 구현된 프로젝트 Planner의 배정 중단·안전 반환·게시 후 재개와 runtime 전체 handoff 범위도 유지한다.
- 관리·Agent·verify 자리를 각각 계산하고 이미 관리 중인 단계 전환에는 새 관리 자리가 필요하지 않다. 한도 축소는 신규 배정만 보류한다. 대기는 timeout·실패 횟수를 소진하지 않으며 실제 실행·종료 확인·공유 게시의 기존 조건은 유지한다.
- 같은 입력의 대기 작업을 busy loop로 재호출하거나 정상 결과로 바꾸지 않는다. 조율 종료·재시작에도 작업별 결과·미완료 예약과 독립 성공 근거를 보존한다. 로그는 작업 대기와 공유 중단, 세 종류의 점유·상한·배정 사유를 구분한다.
- R-091: 일반 단계 예외·DB 요청 대기 만료·작업 준비/결과 수집 실패는 짧은 retry 묶음과 작업별 재시도 시점으로 제어한다. 실제 차단이 없으면 같은 실행에서 현재 DB·checkpoint·소유권을 재준비해 재배정하며 완료한 외부 효과를 반복하지 않는다. `visited`나 완료 Future에 남아 다음 외부 실행까지 배제되지 않아야 한다. 대기 중 독립 작업·운영 요청과 사용자 pause·취소·이미 캐시된 runtime 종료 결정을 처리하지만 원격 코드 비교는 수행하지 않는다. 실제 미충족 조건·종료 불명은 해당 조건이 해소되기 전 실행하지 않는다.
- 비차단 재배정의 실제 다음 단계 진입에서 G-312의 공통 30초 TTL 적용 runtime gate를 확인하고 코드 변경이 확정됐거나 종료 결정이 캐시됐다면 추가 원격 조회 없이 전체 gate로 반환한다. 단순 대기·재시도 타이머 만료·슬롯 순번 변경만으로 원격을 비교하지 않는다. 코드 변경이 없으면 형제 verify 완료를 기다리지 않고 수동 제출 다음의 RETRY 순서로 이어가며, 대기/재시작으로 누적 실패·교정 이력·관리 소유권을 초기화하지 않는다. 단계별 Worker/verify/Review 예산과 조건 분류 변경 자체는 G-313이 이 대기 구조를 소비한다.
- PRODUCT의 공유 Git 자원 대기는 실제 프로세스 lease를 재획득하며 진행한다. 대기 중 DB transaction·실제 Agent/verify 호출 자리를 점유하거나 실패 횟수를 소비하지 않고 취소·Planner/runtime 중단을 처리한다. 수동 명령과 계획 소유권의 실제 충돌 거부는 유지한다.
- R-091의 DB 대기/재시도는 일반 단계 예외의 retry 묶음·Worker 교정 횟수를 소비하지 않는다. 작업 준비·재시도 대기·결과 수집·오류 기록은 G-303의 짧은 요청 경계를 사용하며, 실제 단계 오류 뒤 기록도 실패하면 원래 traceback과 저장 오류를 모두 로그에 보존하고 저장 성공을 합성하지 않는다. 해당 요청/작업만 재시도 대기로 두고 독립 완료 수집·신규 배정을 유지하며 실제 차단이 없으면 같은 실행에서 이어간다.

## Implementation

- [ ] 확인한 `loop_manager_internal/application/task_scheduling.py:admission()`과 `storage/project_state_adapter.py:activate_ready_execplan()`의 대기 전 선택·activation SHA를 실제 활성화 직전 자격 재검사에 연결한다. `catalog/project_selection.py`의 자격·priority와 기존 소유권/관리 한도 검사를 재사용하고 대기 중 수동 수락·순위·catalog/dependency/유지보수 변화로 부적격해진 항목만 재선정한다. 현재 `slot()`의 rank 갱신과 condition 밖 DB 처리·단계 예외 격리를 다시 구현하지 않는다.
- [ ] 확인한 `application/task_scheduling.py:run_project_tasks()`와 `application/project_service.py:_run_coordinators()`·`_dispatch_execution()`에 실행 중 명세 관측을 프로젝트 소유 판단으로 전달하는 연결을 보완한다. 확인한 `planning/selection_service.py:_specification_planning_required()`의 현재 지문·성공 기준·archive 예외 판단과 기존 원격 관측을 재사용하고, 필요 판단이 후속 호출·신규 편입보다 먼저 확정되도록 한다. Git·명세 관측 중 DB 쓰기 transaction·배정 condition을 유지하지 않고 같은 원격 입력의 중복 관측·판단을 억제한다. 작업별 전체 지문 비교나 각 자식의 Planner 실행, 새 polling 설정·daemon은 추가하지 않는다. 필요한 port 연결은 기존 이름 있는 effects 조립을 따른다.
- [ ] `scheduled_call()`의 직접 구현된 snapshot·차단·catalog/draft 재검사에 남은 호출 조건을 연결한다. DB 예약 전후 `PlanningDrain`·runtime handoff와 현재 dependency·수동 소유·유지보수·후보/명세 입력을 확인하고 `execution/execution_ports.py`·`application/project_service.py:_dispatch_execution()`·`execution/execution_runtime.py`의 재준비/보류 결과로 반환한다. 기존 `verify_preflight()` callback을 보존해 targeted 원자 차단/수집 대기가 process receipt 준비보다 먼저 처리되게 하며 일반 자격 검사와 별도 배정기를 만들지 않는다. 현재 snapshot 비교만으로 DB 밖 입력이나 예약 중 중단까지 확인됐다고 간주하지 않는다. 미시작 예약은 기존 반환 경계로 해제하고 미종료 호출은 보존한다.
- [ ] 확인한 `storage/task_calls.py`의 예약·종료 receipt와 `runtime/resource_lock.py:resource_locks()`의 자동 Git 대기를 재사용한다. 실행 불가 대기 항목의 제거·재선정, 예약 확정/반환의 DB 대기와 중단을 연결하고 메모리 자리·DB 예약·cursor가 어긋나지 않게 한다. 기존 Git lease 재획득과 수동/계획 충돌 거부를 유지하며 자원 대기만 있는 동안 실제 호출 자리를 붙잡는 소비자가 있으면 그 경계만 보완한다.
- [ ] `run_project_tasks()`·`application/project_runner.py:retry_pause_detail()`·`application/scheduler.py`의 오류 분류·traceback·실패 감사를 재사용해 작업별 재시도 대기/재편입을 연결한다. 현재 3회/`DatabaseWaitTimeout`에서 break하는 경계, `visited`와 setup Future 오류 수집에서도 같은 작업의 실행 가능 시점을 보존한다. 짧은 묶음 집계와 누적 실패 감사를 구별하고 무대기 반복 없이 같은 실행에서 다시 준비한다. DB 요청 재시도는 G-303을 소비하며 완료한 Agent·verify·Git·게시 전체를 replay하지 않는다. 필요 보존값은 기존 recovery/checkpoint 경계에 호환되게 두고 새 daemon·배정 엔진·사용자 설정은 만들지 않는다.
