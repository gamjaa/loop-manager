## Purpose

R-091의 직접 구현된 관리·Agent·verify 한도와 배정기를 재사용해, 작업별 대기·예외가 같은 프로젝트의 독립 배정을 막는 잔여 경계를 보완한다. 배정 대기 뒤에는 현재 실행 자격과 후보를 다시 확인한다. 설정·migration·호출 receipt·공정 배정과 이미 Merge된 RETRY 우선 재배정·Planner/runtime 배정 중단을 재구현하지 않는다.

최신 `run_project_tasks()`는 일반 RETRY를 자식 안에서 재배정하고 PLAN_BLOCKED 뒤 독립 READY를 계속 선택한다. `_dispatch_execution()`은 이미 dispatch의 `CallDeferred`를 작업별 일시 대기로 변환한다. 그 밖의 작업 준비·결과 수집에서 전파되는 예외는 `Future.result()`를 통해 조율 루프를 빠져나가므로, 작업 한정 복구와 실제 공유 중단을 구별하는 경계를 확인·보완한다. `slot()`과 `admission()`은 대기 중 Planner/runtime 중단을 확인하지만 등록 당시 rank·선택을 유지하며, 배정 대기 뒤 실제 효과 직전의 프로젝트 차단·단계·후보·소유권 변화에 대한 재확인 경계는 보완이 필요하다.

## Acceptance Criteria

- 작업별 일시 대기·호출 종료 불명·독립 실패는 해당 작업과 실제 충돌 자원에만 적용한다. 프로젝트 차단·새 명세의 미반영 범위·planning 배타·runtime handoff처럼 공유 중단이 필요한 경우와 구별하며 기존 보호를 약화하지 않는다.
- 관리 한도 3인 A에서 종료 불명 verify 하나가 자리를 유지해도, 독립 READY는 남은 관리·Agent 한도 안에서 실행한다. 같은 verify 자리·같은 후보는 재사용하지 않고 종료 불명 기록·작업물·실패 이력을 보존한다. B의 적격 작업도 계속한다.
- 배정 직전에 현재 작업·단계·관리 소유와 관련 안전 조건을 확인한다. 대기 중 프로젝트 차단, catalog/draft·dependency·수동 소유·유지보수 범위 또는 명세·후보 변경이 생기면 오래된 준비 결과로 Agent·verify를 시작하지 않고 기존 재관측·단계 준비로 돌아간다. pause 지원은 G-236의 기존 계약과 연결하며 이 작업에서 별도 pause 정책을 만들지 않는다.
- 수락 수동 제출의 최초 수락 순서 → RETRY 재등록 순서 → 기존 자동 작업 재개 → 일반 신규의 순서를 유지한다. 실행 불가 후보는 다른 적격 후보를 막지 않고, 기본 배정은 실제 Agent 호출 유무로 계산한다. verify만 기다리는 프로젝트의 독립 신규 호출, 재시작 cursor, 전역 유효 priority·숫자 ID 정렬을 유지한다. 이미 구현된 프로젝트 Planner의 배정 중단·안전 반환·게시 후 재개와 runtime 전체 handoff 범위도 유지한다.
- 관리·Agent·verify 자리를 각각 계산하고 이미 관리 중인 단계 전환에는 새 관리 자리가 필요하지 않다. 한도 축소는 신규 배정만 보류한다. 대기는 timeout·실패 횟수를 소진하지 않으며 실제 실행·종료 확인·공유 게시의 기존 조건은 유지한다.
- 같은 입력의 대기 작업을 busy loop로 재호출하거나 정상 결과로 바꾸지 않는다. 조율 종료·재시작에도 작업별 결과·미완료 예약과 독립 성공 근거를 보존한다. 로그는 작업 대기와 공유 중단, 세 종류의 점유·상한·배정 사유를 구분한다.

## Implementation

- [ ] 확인한 `loop_manager_internal/application/task_scheduling.py:run_project_tasks()`의 `Future.result()` 예외 수집·`visited`·admission을 작업별 대기와 실제 프로젝트 중단으로 구분한다. `application/project_service.py:_dispatch_execution()`의 기존 `CallDeferred` 변환과 `execution/execution_runtime.py`의 outcome·현재 호출 종료 근거를 재사용하고, dispatch 밖의 준비·결과 수집에 필요한 국소 전달만 보완한다. 일반 RETRY의 자식 재배정·기존 세 번의 일시 재시도 한도와 `PlanningDrain`·runtime handoff는 유지하며 예외를 성공이나 무조건 계속으로 처리하지 않는다.
- [ ] 확인한 `TaskScheduler.slot()`·`admission()`·`scheduled_call()`과 `storage/project_state_adapter.py:activate_ready_execplan()`의 대기 전 선택과 실제 효과 시작 경계를 연결한다. `catalog/project_selection.py`의 기존 실행 자격·priority와 `execution/execution_ports.py`의 최신 입력 판단을 재사용하고, DB 쓰기 transaction을 잡은 채 대기하거나 별도 정책 사본을 만들지 않는다.
- [ ] 확인한 `storage/task_calls.py`의 예약·종료 receipt·관리 단위 계산, `storage/runtime_state.py`의 작업 선택과 한도 검사를 유지한다. 실행 불가 대기 항목의 제거·재선정과 새로운 수동 수락 반영을 현재 소유권 검증에 연결한다. 미종료 호출의 자리는 확인 전 해제하지 않는다.
- [ ] 확인한 `application/manual_work.py`·`storage/manual_work_state.py`의 수락 순서·공유 묶음 단위를 유지하고, 조율의 호출별 재개로 구성 G를 중복 실행하지 않게 한다. 수동 수락 자체나 같은 묶음의 직렬 처리 의미는 바꾸지 않는다.
- [ ] 확인한 PRODUCT의 작업 선택·동시 실행과 ARCHITECTURE의 실행 자리 절에 실제 보완한 동작만 반영한다. G-278의 실패 planning 보존·의미 재평가와 G-298의 차단/rebase 대상 교정은 각 담당 작업에 남긴다.

## Validation

- Worker는 `tests/test_task_scheduling.py:TaskSchedulingTests`와 `tests/test_registered_project_scheduler.py`에서 변경한 최소 unit case를 실행한다. 기존 실제 SQLite·제어된 스레드·Event/Barrier·process receipt fixture를 사용하고 모델·Git·외부 프로세스 관측만 mock한다.
- 실제 `run_project_tasks()`의 자식에서 `CallDeferred`와 작업별 예외를 전달한다. A의 verify 종료 불명·관리 1/3에서 A의 독립 Worker 및 B의 Worker가 실행되고, 보존된 verify는 중복 시작되지 않아야 한다. 단순 `slot()` 두 개 성공만으로 조율 전체의 지속을 검증하지 않는다. 자식 오류 뒤 독립 결과·session·실패·예약이 유지되는지도 확인한다. 이미 구현된 `tests/test_task_scheduling.py:test_retry_and_plan_block_progress_while_sibling_verify_is_running`의 RETRY→교정→계획 차단→독립 선택과 `test_manual_precedes_retry_then_resumed_and_new_calls_without_preemption`의 순서는 기존 회귀로 재사용한다.
- 배정 대기 중 프로젝트 차단·후보/단계 변경·수동 수락·catalog 보류를 주입해 effect 직전 재검사를 확인한다. 실행 불가 선두 후보 때문에 다음 적격 후보가 대기하지 않으며 실제 공유 안전 오류에서는 호출 수가 0이어야 한다.
- R-091의 A/B 관리 3씩·Agent 2·verify 1, 한 프로젝트 Agent 3, A/B/C 기본 호출 후 추가 priority, 실행 상한 2의 빠른 완료·나중 적격·재시작 cursor를 실제 admission/호출 연결에서 검사한다. 기존 `_next()` 순수 순서 테스트는 보존하고 동일 assertion을 복제하지 않는다. `verify_concurrency=2`의 두 실행·세 번째 대기, 수동 verify 우선·기존 호출 비선점도 확인한다.
- fake clock으로 순번 대기 30초·실제 실행 2초·상한 10초의 no-timeout과 실제 초과를 구분한다. 상한 축소·관리 중 후속 Review·종료 불명·Manager 재시작에서도 예약 유실·이중 호출·가짜 성공이 없어야 한다. 전체 verify/OS 실측은 이 Planner나 Worker targeted 실행에 포함하지 않는다.

## Decision Log

- 최신 R-091/R-077의 RETRY 우선순위를 완료 기준에 명시하고 직접 Merge된 구현은 재사용한다. 남은 작업은 `Future.result()`에서 전파되는 작업별 예외와 배정 대기 뒤 실제 시작의 재검사이며 기존 ID·경로·metadata·dependency·과거 수행 기록을 보존한다. 공유 planning 중단·runtime handoff를 작업별 예외처럼 삼키거나 종료 불명 자리를 해제하지 않는다.

- complexity high: 여러 작업의 결과·관리 수명·실제 호출 대기를 분리하고 대기 중 자격 변화와 종료 불명 예약을 함께 처리해야 한다. risk high: 잘못된 계속/해제는 미확인 후보의 중복 writer·검증 또는 공유 차단 우회를 만들며 기록 보존과 소유권 재검사 뒤 복구해야 한다. 실제 종료 근거·기존 gate와 중단/경쟁 회귀를 유지한다. priority high는 독립 진행과 안전한 무인 실행을 함께 복구하는 기준이다.
