## Purpose

R-077 수동 complete/submit의 생략과 단계 근거를 실제 실행에 사용하는 운영 설정에 결합한다. 현재 후보 SHA·base·전체 G·환경·공통 및 역할별 지침 결합은 유지하고, 같은 HEAD에서 저장소 밖 config 또는 Reviewer profile이 바뀌어도 이전 생략이 유효한 누락만 보완한다.

## Acceptance Criteria

- 요청 수락, 단계 진입, 최종 게시 및 PR 대기 재평가가 같은 설정 관측 계약을 사용한다. 실제 verify 설정·환경과 Review provider/Model/Effort 및 verify 근거 중 해당 단계의 관련 입력이 바뀌면 오래된 생략·단계 근거를 사용할 수 없다. `--config`로 지정한 저장소 밖 파일도 포함한다.
- HEAD·tree가 같아도 관련 설정 변경은 탐지한다. 실행 구성 이후 단계 진입 전에 설정이 변경되거나 조회·유효성 확인이 실패해도 고정된 실행 인자만으로 생략을 허용하지 않는다. 무효화된 생략은 재제출을 기다리지 않고 해당 단계를 기본 실행하며, 입력 불일치·확인 실패에는 기존 설정 오류·자동 후속 처리 경계를 유지한다.
- 기존 요청·생략 reason·실제 PASS/FAIL/NOT_RUN·SKIPPED_BY_USER 및 제출 묶음 이력을 보존한다. 설정 변경이나 재시작으로 과거 생략을 실제 성공 cache 또는 실행된 Agent 호출로 바꾸지 않는다. 같은 후보의 실제 실패, 다른 계획과 일반 사용자 결정·dependency·소유권 gate를 유지한다.
- 출력·PR·SQLite 근거에는 관련 비밀값이나 config 원문을 노출하지 않는다. 실제 단계의 입력 지문과 무효화 사유만 기록하며, 기존 입력 정보가 부족한 저장 요청은 현재 설정을 당시 입력으로 소급 채택하지 않는다.

## Implementation

- `loop_manager_internal/execution/manual_candidate.py`의 candidate/stage identity와 `storage/manual_work_state.py`의 요청·결과·게시 근거를 재사용한다. 수락 경로와 execution composition, PR 대기 관측에 실제 config와 선택 profile의 비밀값 없는 관측을 전달한다. 별도 설정 파서나 운영 상태 원본을 추가하지 않는다.
- 기존 managed config와 `agents/agent_profiles.py`의 profile resolver, verification 설정 경계에서 실행에 쓰는 값을 얻는다. 단계별 필요한 입력을 구분하고 기존 SHA·전체 구성·환경·공통 및 역할별 원본 묶음 hash·실패 결합을 보존한다. 작업에 저장된 지침 버전 조회를 재사용하며 최신 runtime이나 common 본문으로 대체하지 않는다. 지침 identity 확인에 별도의 지침 변경 승인을 추가하지 않는다.
- 구현된 `ManualStageSnapshot`과 실제 verify timeout·coordinator parallelism 및 Reviewer resolved profile 전달을 유지한다. 수행 당시 결과는 실행 전 snapshot에 결합하고 완료 시 다시 읽은 설정으로 바꾸지 않는다. 생략 적용에는 현재 설정의 확인 가능성과 수락·실행 입력의 동일성도 확인해, snapshot 경로가 현재 설정 관측을 우회하지 않게 한다. 실행 중 입력 변경 뒤에는 당시 결과를 보존하되 현재 입력의 유효한 근거로 사용하지 않는다. 설정 관측과 실제 실행 입력이 어긋난 상태에서 오래된 생략을 반복 적용하지 않으며 기존 재시도·오류 처리 경계를 유지한다.
- 최종 게시와 일반 PR_OPEN 및 닫힌 PR 재개 뒤 재평가가 같은 설정 관측을 사용하도록 기존 연결을 유지한다. ARCHITECTURE의 공통 verify 실행·실제 receipt 보존 경계를 재사용한다.
- 실제 성공 재사용의 목록·생성 요청·rebase 선택은 G-181/G-182/G-183에 남긴다. R-077의 선택적 생략 사유와 감사 표시는 기존 G-254 범위이며 이 작업에 추가하지 않는다. 이 계획은 사용자 생략 및 수동 단계 근거의 설정 결합만 구현한다. 프로젝트 규칙과 공통·역할별 실행 지침, ARCHITECTURE 및 PLANS의 검증·권한·재시도 계약을 따른다.

## Validation

- Worker는 `tests/test_manual_work.py`에서 G-200 관련 기존 case와 보완한 targeted unit case를 지정해 실행한다. 동일 HEAD의 외부 config·verify 설정·Reviewer profile 변경, 입력 조회 실패, legacy 지문 부재와 비밀값 비노출을 확인하며 실제 provider 호출은 대체한다.
- 실행 구성을 만든 뒤 verify 단계에 진입하기 전에 config를 변경하거나 읽을 수 없게 하는 사례를 추가한다. 유효한 저장 지문과 실제 실행 인자가 있는 요청으로 실제 단계 handler·waiver 판정을 실행해 오래된 생략을 적용하지 않는지 확인한다. legacy NULL과 조회 실패를 독립적으로 검사하고 무효화 뒤 기본 실행 또는 기존 설정 오류 처리를 확인한다.
- 유효 생략 Reviewer prompt fixture에는 수락·현재 설정 지문과 단계 snapshot에 필요한 실제 실행 timeout·parallelism을 제공한다. 기존 prompt·redaction·실행 비합성 assertion을 보존하며 legacy 생략 거부를 별도로 유지한다. 실제 verify 호출 인자·Review에 전달한 profile과 기록 지문의 일치, 실행 중 설정 변경 뒤 당시 결과 보존과 현재 근거 거부를 확인한다.
- 같은 입력 및 변경된 입력의 PR_OPEN·닫힌 PR 재개를 기존 실행 fixture와 관측 경계 mock으로 확인한다. G-200 설정 조건만을 검사하는 사례는 실제 Git 저장소 준비·commit·push를 반복하지 않고 실제 판단·SQLite 저장을 유지한다. 기존 Git 소유권·공유 PR·Merge 통합 회귀와 assertion은 보존한다.
- 기존 checkpoint의 unresolved targeted unit test 실패를 확인하고 해소한다. 검증 범위 축소·skip·성공 주장으로 대체하지 않는다.
- Manager 전체 verify는 complete/submit, 두 단계 생략의 네 조합, PR_OPEN 입력 변경과 PR 재개, 기본 요청 전환 및 재시작에서 필요한 실제 단계가 수행되고 오래된 근거로 게시하지 않는지 확인한다. 실제 실패·session·묶음 구성·독립 작업 보존과 일반 자동 Worker 경로의 회귀를 유지한다.
- Reviewer는 수락·단계 진입·게시의 설정 관측과 실제 실행 입력이 일치하는지, 생략 무효화가 실행 전 gate에 적용되는지, 수행 당시 지문·실패 이력 보존 및 비밀값·과거 성공 비합성을 확인한다.

## Decision Log

- 초기 조사에서 `candidate_token`은 HEAD/base/documents·환경·공통 지침만 받았고 수락 서비스 config_path와 Reviewer 설정이 execution composition에 연결되지 않았다. 기존 환경 변수 변경 사례만으로 외부 config 변경을 검증할 수 없었다.
- 2026-10-09 조사에서는 `stage_input_tokens`, 요청의 verify/review 입력 열 및 수락·execution composition·게시·일반 PR_OPEN 연결이 추가된 상태였다. 당시 남은 문제는 완료 시 설정 재관측으로 수행 당시 입력을 바꾸는 기록 경로, 닫힌 PR 재개 뒤 설정 문맥 누락과 유효 waiver fixture의 설정 지문 부재였다.
- Worker 072a2d9cc15676b5aa0adc07ddd016db17add30a는 실제 timeout·coordinator parallelism 및 Reviewer resolved profile을 snapshot으로 고정하고 결과 기록에 전달한다. 일반 PR_OPEN과 닫힌 PR 재개 뒤 관측 모두 config_path·provider·resolver를 전달한다. 유효 verify waiver prompt fixture에는 외부 config와 수락 지문이 추가됐다. 이는 코드·테스트 원문에서 확인한 변경이며 검증 성공 판정이 아니다.
- 남은 단계 gate: `capture_stage()`는 고정 verify 인자를 `stage_input_tokens()`에 모두 전달하므로 verify 단계에서 managed config 조회를 생략한다. `VerifyHandler._verify_once()`의 waiver 판정은 이 snapshot을 사용하지만 Review 근거 확인·게시·PR 대기는 현재 config를 다시 읽는다. 실행 구성 이후 config 변경·조회 실패가 단계 시작의 생략 판정에 반영되지 않을 수 있으므로 수행 당시 snapshot 보존과 현재 생략 유효성 관측을 함께 충족해야 한다.
- 남은 테스트: config 변경 뒤 default 실행 사례는 `step()`이 변경된 config를 먼저 읽어 실행 구성을 새로 만들므로 구성 이후 변경을 검사하지 않는다. 조회 실패 사례는 요청 지문을 NULL로 만든 뒤 config를 삭제해 두 거부 원인을 분리하지 않는다. 유효 prompt fixture의 ManualCandidate에는 snapshot용 timeout·parallelism이 전달되지 않는다. 설정 조건 사례의 실제 Git 반복은 기존 Validation과 최신 ARCHITECTURE의 자체 테스트 Git 경계에 맞게 보완한다.
- Worker 문서에는 `구현 및 관련 targeted unit 검증 (Python 3.12/Linux, 지정 unittest case만 실행)` 완료 주장이 기록돼 있다. 그러나 같은 revision의 checkpoint는 `worker_output_invalid`와 unresolved targeted unit test 실패 보고를 보존한다. 이 수행 기록을 삭제하거나 성공으로 재해석하지 않으며 이번 읽기 전용 대조로 실패를 해소했다고 판정하지 않는다.
- 최신 PRODUCT는 상세 운영 설정 지문 문단을 삭제했고 ARCHITECTURE는 수동 waiver가 실제 run 성공 receipt가 아니며 기존 수동 후보 계약을 유지한다고 정리했다. 최신 R-077의 검증 설정·동일 HEAD 입력 변경 무효화와 최신 G-200의 운영 설정 결합 Acceptance Criteria는 유지돼 있어 계약 철회로 해석하지 않는다. 선택적 reason은 G-254에 남기고 R-066·R-069의 지침 변경 승인 제거를 설정 identity 확인으로 되돌리지 않는다.
