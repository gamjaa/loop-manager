## Purpose

R-077 수동 complete/submit의 생략과 단계 근거를 실제 실행에 사용하는 운영 설정에 결합한다. 현재 후보 SHA·base·전체 G·환경·공통 및 역할별 지침 결합은 유지하고, 같은 HEAD에서 저장소 밖 config 또는 Reviewer profile이 바뀌어도 이전 생략이 유효한 누락만 보완한다.

## Acceptance Criteria

- 요청 수락, 단계 진입, 최종 게시 및 PR 대기 재평가가 같은 설정 관측 계약을 사용한다. 실제 verify 설정·환경과 Review provider/Model/Effort 및 verify 근거 중 해당 단계의 관련 입력이 바뀌면 오래된 생략·단계 근거를 사용할 수 없다. `--config`로 지정한 저장소 밖 파일도 포함한다.
- HEAD·tree가 같아도 관련 설정 변경은 탐지한다. 입력을 읽거나 유효성을 확인할 수 없으면 생략으로 통과하지 않고 기존 설정 오류·자동 후속 처리 경계를 따른다. 무효화된 생략은 재제출을 기다리지 않고 해당 단계를 기본 실행한다.
- 기존 요청·생략 reason·실제 PASS/FAIL/NOT_RUN·SKIPPED_BY_USER 및 제출 묶음 이력을 보존한다. 설정 변경이나 재시작으로 과거 생략을 실제 성공 cache 또는 실행된 Agent 호출로 바꾸지 않는다. 같은 후보의 실제 실패, 다른 계획과 승인·dependency·소유권 gate를 유지한다.
- 출력·PR·SQLite 근거에는 관련 비밀값이나 config 원문을 노출하지 않는다. 실제 단계의 입력 지문과 무효화 사유만 기록하며, 기존 입력 정보가 부족한 저장 요청은 현재 설정을 당시 입력으로 소급 채택하지 않는다.

## Implementation

- `execution/manual_candidate.py`의 candidate/stage identity와 `storage/manual_work_state.py`의 요청·결과·게시 근거를 재사용한다. 수락 경로와 execution composition, PR 대기 관측에 실제 config와 선택 profile의 비밀값 없는 관측을 전달한다. 별도 설정 파서나 운영 상태 원본을 추가하지 않는다.
- `agents/agent_profiles.py`, 기존 managed config와 verification 설정 경계에서 실행에 쓰는 값을 얻는다. 전체 env hash·tracked HEAD만으로 파일 밖 설정 동일성을 증명하지 않는다. 단계별 필요한 입력을 구분하고 기존 SHA·전체 구성·공통 및 역할별 원본 묶음 hash·실패 결합을 보존한다. 작업에 저장된 지침 버전 조회를 재사용하며 최신 runtime이나 common 본문만으로 이를 대체하지 않는다.
- 단계 근거에는 실제 verify에 전달한 timeout·coordinator parallelism과 실제 Review에 선택한 profile을 결합한다. 실행 전후 관측이 달라지면 수행 당시 결과는 보존하되 저장 시점에 다시 읽은 설정을 당시 입력으로 바꾸거나 최신 입력의 성공 근거로 사용하지 않는다. ARCHITECTURE의 공통 verify 실행 경계를 재사용하고, PR 재개 뒤의 대기 재평가에도 일반 PR_OPEN 관측과 같은 config·provider·profile 문맥을 전달한다.
- 실제 성공 재사용의 목록·생성 요청·rebase 선택은 G-181/G-182/G-183에 남긴다. 이 계획은 사용자 생략 및 수동 단계 근거의 설정 결합만 구현한다. 자동 문서·역할·검증 경계는 docs/AGENTS.common.md와 해당 역할의 docs/AGENTS.*.md를, 프로젝트 규칙·계획 작성과 설정·검증·재시도 설계는 AGENTS.md·docs/ARCHITECTURE.md·docs/PLANS.md를 따른다.

## Validation

- Worker는 `tests/test_manual_work.py`의 waiver/receipt unit case를 확장해 동일 HEAD의 외부 config 변경, verify 설정 변경, Reviewer profile 변경, 입력 조회 실패, 기존 근거 부재와 비밀값 비노출의 최소 사례만 실행한다. 실제 provider 호출은 대체한다.
- 유효 생략을 기대하는 기존 Reviewer prompt 테스트에는 수락 당시의 설정 지문과 현재의 유효 설정 관측을 제공하고 기존 prompt·redaction·실행 비합성 assertion을 보존한다. 지문 없는 legacy 요청의 생략 거부는 별도 사례로 유지한다. 실제 verify 인자·Review profile과 기록 지문의 일치, 실행 중 설정 변경, 같은 입력 및 변경된 입력의 PR 재개를 기존 실행 fixture와 관측 경계의 mock으로 확인한다. 판단·저장 로직은 실제로 실행하며 이 설정 판정만을 위해 실제 Git·CLI 반복을 추가하지 않는다.
- Manager 전체 verify는 complete/submit, 두 단계 생략의 네 조합, PR_OPEN의 입력 변경과 PR 재개, 기본 요청 전환 및 재시작에서 필요한 실제 단계가 수행되고 오래된 근거로 게시하지 않는지 확인한다. 실제 실패·session·묶음 구성·독립 작업 보존과 일반 자동 Worker 경로의 회귀를 유지한다.
- Reviewer는 수락과 사용 시점의 실제 설정이 일치하는지, 기록 지문이 수행 당시 verify 인자·Review profile과 일치하는지, 생략 무효화가 실행 전 gate에 적용되는지 및 비밀값·과거 성공 합성이 없는지 확인한다.

## Decision Log

- `candidate_token`은 HEAD/base/documents, platform/Python/env hash와 공통 지침만 받는다. 수락 서비스의 config_path와 실제 Reviewer 설정은 token 및 `ManualCandidate` composition으로 전달되지 않는다. 기존 환경 변경 테스트는 env 변수만 바꾸므로 외부 config 변경을 검증하지 않는다.
- 위 입력 미연결 설명은 초기 조사 기록이다. 현재 구현은 `stage_input_tokens`와 요청의 verify/review 입력 열, 수락·execution composition·게시·일반 PR_OPEN 재평가의 연결을 추가했다. ARCHITECTURE의 Verify 입력 관측 절은 이 설정 결합과 legacy NULL 보존을 명시하며 R-077 및 PRODUCT의 수동 생략 계약과 일치한다.
- 남은 실행 입력 결합: `stage_input_tokens`는 config를 매번 읽고 `ManualCandidate.record`도 완료 시 다시 관측한다. 실제 verify timeout은 execution composition에 미리 전달된 값이며 parallelism은 verification coordinator의 실행 context에서 얻는다. 저장 시점의 config/profile 지문만으로 수행 당시 입력을 증명할 수 없으므로 실제 실행 입력과 실행 전후 변경을 결합해야 한다.
- 남은 PR 관측 연결: `recovery/waiting_pr_service.py`의 일반 PR_OPEN 경로는 config_path·provider·resolve_profile을 전달하지만 닫힌 PR의 재개 뒤 재평가 경로는 이를 누락한다. 같은 설정 계산을 사용하는 기존 계약 안에서 이 연결을 보완한다.
- 남은 테스트 정합성: `test_reviewer_prompt_distinguishes_a_valid_user_verify_waiver`는 config가 없는 ManualCandidate와 설정 지문 없는 accept 요청을 만든 뒤 SKIPPED_BY_USER를 기대한다. 현재 waiver gate는 그 입력을 거부하므로 유효 요청 fixture를 보완해야 한다. 기존 checkpoint의 미해결 targeted unit test 실패 기록은 보존하며 이번 읽기 전용 대조를 검증 성공으로 취급하지 않는다.
- complexity medium: 기존 요청·단계·게시 경계에 명확한 설정 identity를 연결한다. risk high: 오래된 생략은 수동 PR의 필요한 검증·Review를 건너뛰게 할 수 있다. 게시 전 실제 재검증·Review, 보존된 요청과 PR 교정이 복구 수단이며 이미 게시·Merge된 외부 상태를 코드 rollback으로 복구한다고 가정하지 않는다. 해당 시나리오는 Acceptance Criteria·Validation·Review에 포함한다.
