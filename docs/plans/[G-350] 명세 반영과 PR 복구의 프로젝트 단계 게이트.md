## Purpose

명세 반영이 필요한 프로젝트에서는 Planner 결과의 게시·catalog/DB 확정 뒤 필요한 PR 충돌 복구를 선택하고 일반 작업을 배정한다. PR 상태 관측·완료 확정과 충돌 해결 실행을 분리해 필요한 입력은 먼저 확보하며, 변화 없는 입력에서는 독립 작업을 계속한다.

현재 `ProjectService.run()`은 `_synchronize_pull_requests()`를 `_run_coordinators()`보다 먼저 호출하고, `synchronize_waiting_pull_requests()`는 관측 직후 충돌 복구까지 선택한다. 기존 명세 지문 비교·실행 중 drain은 재사용하고 남은 단계 순서만 연결한다.

## Acceptance Criteria

- R-082/R-091: 명세·사용자 판단·유지보수 등 유효한 Planner 조건이 있으면 해당 프로젝트의 새 일반 단계 진입을 멈춘다. 실행 중 호출의 안전 반환 후 게시·catalog/DB 확정을 완료하고 그 최신 입력으로 PR 복구를 재관측한 뒤 일반 작업을 배정한다. 게시 미확정·소유권 불확실에서는 일반 실행을 시작하지 않는다.
- base SHA 전진만으로 Planner나 모든 PR rebase를 호출하지 않는다. 명세 입력이 같고 충돌이 없으면 각각 0회다. base가 같아도 PR head·Merge·Close와 명시적 판단·요청은 별도로 처리한다. PR 관측의 불확실성은 변경 없음으로 소비하지 않는다.
- R-023: Merge·Close 전이와 필수 미완료 operation 관측/확정을 planning 뒤로 미루지 않는다. 최신 PR 상태를 반영한 뒤 로컬 base 부수 동기화를 판단하는 기존 순서와 runtime handoff 경계를 유지한다.
- 같은 자원의 충돌 복구에는 소유 Worker·rebase·검증만 허용한다. G-338의 planning 해제에 필요한 제한된 원인 복구와 G-351의 계획별 최종 차단을 소비하며, 독립 자원·dependency·명세 영향이 없는 계획과 다른 프로젝트는 진행한다. 복구 전체나 차단 해제를 프로젝트 완료 장벽으로 만들지 않는다.
- 단계 사이 base/head·소유권 경쟁이나 재시작에는 현재 입력을 재검사하고 확정된 게시·PR 전이를 반복하지 않는다. 기존 session·후보·checkpoint·실패 및 단계별 성공 근거를 보존한다.

## Implementation

- [ ] 확인한 `application/project_service.py:run()`·`_synchronize_pull_requests()`·`_run_coordinators()`의 조립을 정리한다. `recovery/waiting_pr_service.py:observe_waiting_pull_requests()`와 `select_waiting_pull_request_conflict()`의 기존 분리를 재사용해 관측/확정과 복구 실행의 자격을 명시한다. 별도 전역 상태 머신이나 PR 조회 계층을 만들지 않는다.
- [ ] `planning/selection_service.py`의 Planner 필요성 판단과 `planning/planning_runtime.py`의 결과·게시 경계를 재사용한다. 현재 `application/task_scheduling.py:check_inputs()`의 명세 변화 drain과 G-338의 안전 예외를 단계 게이트에 연결하며 같은 입력의 중복 Planner·복구를 억제한다. G-278의 실패 planning suspend와 G-348의 선언 교정 게시 구현은 확장하지 않는다.
- [ ] `application/project_runner.py`·`storage/runtime_state.py`의 저장된 실행 원본으로 단계 반환/재진입을 연결한다. 외부 관측은 DB 밖, 적용은 현재 입력·소유권·generation의 짧은 CAS로 처리한다. 이후 유한 조율 전환이 소비할 재확인 가능한 단계 결과를 유지한다.
- [ ] 확인한 `tests/test_project_services.py`, `tests/test_planning_selection.py`, `tests/test_pr_conflict_corrections.py`, `tests/test_registered_project_scheduler.py`의 관측 double·실제 SQLite를 확장한다. PRODUCT·ARCHITECTURE의 단계 순서 소유 절을 실제 구현에 맞춰 통합한다.

## Validation

- Worker targeted unit은 위 파일에서 변경한 순서/gate case다. 명세 변경+충돌 PR에 관측 확정 → Planner 게시/DB 반영 → 충돌 복구 → 일반 배정의 호출 순서와 저장 상태를 검사한다. 적용 중단·원격 재전진·실패 planning의 독립성 미확정에는 일반 호출 0회여야 한다.
- base만 전진/충돌 없음, 같은 base의 head·Merge·Close, 명시 요청만 변화한 경우를 분리한다. 불필요한 Planner/rebase는 0회이며 필요한 PR 전이와 기존 local sync·runtime 결정은 누락되지 않아야 한다.
- A의 planning/PR 복구 중 B의 독립 실행, A의 복구 불가 계획 차단 뒤 A의 무관한 작업 진행, 같은 자원 경쟁 거부와 G-338 원인 복구 예외를 검사한다. 기존 rebase/index·lease 실제 효과 회귀를 재사용하고 정책 조합마다 Git 저장소나 전체 lifecycle을 반복하지 않는다.
