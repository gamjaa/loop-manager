## Purpose

프로젝트마다 공통 AGENTS 본문을 복사하는 등록·배포 방식을 모델 호출 설정에 지침을 추가하는 방식으로 전환한다. 프로젝트의 `AGENTS.md`는 유지하고, 실행 원본은 Loop Manager runtime worktree의 `docs/AGENTS.common.md`로 분리한다. 작업 worktree의 공통 파일은 일반 파일로 수정해 PR에서 보고하고, 프로젝트 AGENTS의 사전 승인과 진행 작업의 지침 버전·운영 이력은 보존한다.

호출·버전 보존·등록·공통 변경 보고·프로젝트 승인 경계는 같은 구현 PR에서 검증한다. 이 저장소의 기존 공통 본문 제거는 아래 후속 정리 계획에 따라 사전 승인된 정확한 diff로 별도 작업 worktree에서 수행한다. 주입 기능의 Merge·runtime 검증과 사전 승인 기능의 Merge가 선행돼야 하며, 정리 PR의 완료는 이 주입 계획의 완료 조건에 포함하지 않는다.

## Acceptance Criteria

- 모든 모델 호출이 같은 공통 경계에서 지침을 확정하고 Codex·Claude의 추가 지침 기능으로 전달한다. 신규·재개·읽기 전용·유지보수·복구에서도 기본 지침·기존 추가 지침·프로젝트 규칙·실행 경계를 보존한다.
- ExecPlan 작업의 Worker·Reviewer와 재시도·fallback이 동일한 내용 해시의 snapshot을 사용한다. 독립 planning·점검·유지보수 작업도 각 버전이 보존되며 새 작업만 최신 공통 내용을 사용한다.
- 공통 버전 없는 기존 세션은 최소 문맥으로 복구하고 이전 세션·작업물·실패 기록을 보존한다. 잘못된 파일·snapshot·미지원 기능·설정 충돌은 프로세스 시작 전에 거부되며 최신 내용으로 숨기지 않는다.
- 공통 내용 해시가 관련 planning 입력·Agent 성공 결과의 재사용 기준에 포함된다. 내용이 같으면 새 runtime SHA만으로 재계획하지 않으며 진행 중인 작업을 선점하지 않는다.
- 원격 프로젝트의 `AGENTS.md`에 공통 본문이 없어도 등록·실행할 수 있다. 기존 준비 도구는 프로젝트 지침을 보존하고 새 파일에는 최소 안내만 생성하며 다른 덮어쓰기 보호를 유지한다.
- 작업 worktree의 공통 파일은 별도 guidance 제안·사전 승인 없이 일반 파일 수정 권한으로 처리한다. 현재 Worker·Reviewer의 실행 지침은 runtime 기준의 고정 버전이며 후보 파일 수정·diff 검토로 바뀌지 않는다.
- 공통 파일 변경 PR에는 실제 최종 diff에 맞는 경로·변경 사실·내용·이유·영향과 diff 링크를 남긴다. Manager가 누락을 보완하고 Reviewer가 관련 변경을 검토한다.
- 프로젝트 제안은 self 저장소에서도 루트 `AGENTS.md`와 project scope로 처리하며 ExecPlan 기록·사용자 판단·정확한 patch 적용을 유지한다. 공통 파일을 신규 승인 대상에 넣지 않는다.
- 과거 루트 AGENTS 공통 승인과 승인 대기는 원래 대상·baseline·patch에 결합해 처리하고 새 대상으로 이관하지 않는다. 적용할 수 없는 제안은 해당 판단 대기로 보존한다.
- 기존 공통 본문이 남아 있어도 동작한다. 이 구현은 본문을 제거하거나 기본 checkout을 편집하지 않으며, 이 저장소의 승인된 후속 정리는 아래 별도 계획으로 수행한다. R-064의 문서·검증·게시·완료 계약을 충족한다.

## Implementation

### 1. 호출 입력과 버전 저장

- `loop_manager_internal/agents/invocation_service.py`의 공통 `run_agent` 경계에서 지침을 해결하고, `agent_invocation.py`의 명시적 요청 값으로 provider에 전달한다. provider별 파일 읽기와 전역 가변 지침 cache를 만들지 않는다.
- 신규 작업은 bootstrap이 선택한 immutable runtime의 `docs/AGENTS.common.md`를 읽는다. 한 번 확정한 UTF-8 내용·SHA-256·원본 revision을 작업 identity에 결합한다. Worker·Reviewer가 같은 작업을 다르게 해결하지 않도록 작업 단위의 동일한 참조를 사용하고 독립 planning·유지보수 identity는 기존 상태 경계에 연결한다.
- 지침 원본 해결과 후보 diff 읽기를 분리한다. self 작업 worktree의 공통 파일이 수정됐어도 해당 파일을 재로딩해 주입하지 않으며, 현재 Worker가 바꾼 규칙을 같은 작업의 Reviewer 지침으로 적용하지 않는다. Merge 후 새 runtime·새 작업에서만 수정본을 선택한다.
- 내용 snapshot은 source checkout·프로젝트 밖의 기존 state-dir 아래 Manager 소유 경로에 보존하고 SQLite에는 identity·해시·revision·snapshot 참조를 추가한다. 기존 storage 모듈과 transaction을 재사용하며 내용 hash 검증 없이 경로만 신뢰하지 않는다. 호환되는 추가 저장으로 기존 실행·session·승인·실패 이력을 보존한다.
- process 실행 전에 버전 확정·보존을 완료한다. 중단·재시작의 같은 작업은 같은 snapshot을 다시 사용하고, 기록 없는 기존 세션은 기존 복구 경계에서 최소 문맥의 새 세션으로 이어간다. 보존된 snapshot이 손상됐을 때 새 원본으로 바꿔 성공 처리하지 않는다.

### 2. Provider의 추가 지침 전달

- `provider_adapters.py`의 신규·resume 분기에 Codex `-c developer_instructions=...`를 적용한다. 실제 적용될 기존 developer 지침과 공통 내용을 함께 보존하며 TOML 문자열을 정확히 직렬화한다. `model_instructions_file`로 기본 지침을 교체하지 않는다.
- Claude에는 작업의 고정 snapshot을 `--append-system-prompt-file`로 전달한다. 재개와 압축 후에도 같은 파일·내용을 사용하고 CLI의 system prompt snapshot 동작을 확인한다. 설치된 버전의 미지원 기능을 성공으로 간주하지 않는다.
- 공통 본문은 사용자 turn prompt에 반복 추가하지 않는다. 프로젝트 지침은 기존 CLI 로딩 또는 R-033이 허용한 신규 세션의 한 번 확인 방식으로 유지한다.
- native 설정과 작업 경로·읽기 전용·자동 승인 검토·기존 sandbox 인자는 함께 유지한다. 추가 지침을 전달하려고 사용자 전역 설정, provider transport 또는 쓰기 허용 범위를 바꾸지 않는다. R-050의 별도 실행 방식 변경을 중복 구현하지 않는다.

### 3. 입력 동일성·프로젝트 승인·공통 변경 보고

- `planning/input_fingerprints.py`, catalog·selection 및 기존 성공 결과 재사용 경계에 실제 공통 내용 해시를 포함한다. 프로젝트의 원격 입력과 Manager의 공통 입력을 구분하고, 다른 프로젝트의 파일이나 runtime 경로를 내용 변화로 오인하지 않는다. 공통 내용 변경에는 기존 AGENTS 지침 변경과 같은 계획 판단 경로를 사용한다.
- `documents/guidance_approval.py`, `guidance_service.py`, 역할 prompt 및 `agents/scope_*`의 self 루트 AGENTS를 공통 원본으로 취급하는 가정을 수정한다. 새 제안 대상은 루트 `AGENTS.md`와 project scope로 한정하고 self 프로젝트에도 동일하게 적용한다.
- `docs/AGENTS.common.md`는 일반 작업 파일로 분류한다. 해당 파일 때문에 별도 guidance 제안·승인 기록·사전 중단·특별한 수정 거부를 만들지 않으며, 일반 역할 쓰기 범위와 현재 작업의 목표는 유지한다. 일반 프로젝트의 동명 파일을 수정해도 Manager 실행 원본이 바뀌지 않는다.
- 기존 승인 기록은 저장된 의미로 읽는다. 기존 pending 제안과 새 제안의 대상 규칙을 구분하고, baseline 변경이나 적용 불가로 새 판단이 필요하면 원래 제안·결정·작업을 보존한다. Target 문자열을 새 경로로 치환하거나 원래 승인을 새 파일에 재사용하지 않는다.
- `documents/pr_description.py`와 Worker 결과·문서 보고의 기존 경계를 재사용해 공통 파일 변경을 최종 PR 본문에 명시한다. 실제 diff에서 추가·수정·삭제·rename을 확인하고 경로·요약·이유·영향·diff 링크를 대조한다. rebase·head 변경 뒤에도 최종 후보와 맞추며 새로운 공통 사전 승인 시스템을 만들지 않는다.

### 4. 등록·준비·관련 문서

- `runtime/registration_service.py`의 공통 본문 포함 검사를 제거하고 루트 AGENTS의 존재·UTF-8 및 나머지 필수 문서 검사는 보존한다. 기존 mismatch 승인 필드·기록은 호환 감사로 남기되 새 등록에 요구하지 않는다.
- `scripts/copy-project-files.ps1`과 `.sh`에서 공통 본문 복사를 제거한다. 기존 AGENTS는 건드리지 않고 새 프로젝트에는 최소 프로젝트 안내만 작성한다. 다른 폴더·파일 충돌과 경로 검증은 기존 안전 조건을 유지한다.
- PRODUCT·ARCHITECTURE·PLANS·README의 runtime 공통 원본, 공통 파일 일반 수정·PR 보고, 프로젝트 승인 Target·scope, 등록·설치·snapshot 저장 및 로컬 정리 안내를 R-064와 맞춘다. 해당 문서의 사용자 소유·수정 승인 경계와 현재 작업에 제공된 권한을 따르며 R-061의 무관한 역할 변경까지 구현하지 않는다.
- 이 구현 PR은 기존 루트 `AGENTS.md`나 다른 프로젝트에서 공통 본문을 삭제·재작성하지 않는다. 이 저장소의 후속 정리는 아래 사전 승인 절차로 별도 PR에 게시한다. 자동 분리 모듈과 프로젝트별 배포 작업을 추가하지 않는다.

### 5. 이 저장소 AGENTS.md의 후속 정리

- 사전 승인 수용 기능의 구현이 준비되면 후속 정리 범위와 실행 조건을 이 계획에 기록한다. 로컬 구현 기록은 `docs/plans/manual/[G-151] 게시된 AGENTS 변경 사전 승인 수용.md`에 보존하며 자동 catalog와 SQLite 의존성 대상에서 제외한다. 별도 후속 정리 ExecPlan은 manual에서 먼저 준비·승인할 수 있다. 자동 실행 경로에 게시하기 전에 사전 승인 구현 PR의 사용자 Merge와 G-147 Merge 후 runtime의 공통 지침 주입 검증 통과를 확인하고, 해당 PR·검증 결과·runtime revision을 기록한다. 자동 실행할 후속 계획의 `depends_on`에는 실제 catalog 대상인 G-147을 넣으며 manual G-151을 추가하지 않는다.
- 대상은 이 저장소의 루트 `AGENTS.md` 하나다. 프로젝트 전용 규칙을 보존하는 정확한 삭제 diff와 기준 commit SHA를 후속 ExecPlan의 `Decision Log`에 제안으로 기록하고, `docs/PLANS.md`의 `User Decision` 형식으로 사용자가 승인한다. 승인 내용과 Baseline을 확정하고 위 선행 조건을 확인한 계획을 게시한 뒤 사전 승인 수용 절차를 사용한다. 현재 요청은 후속 정리의 범위·조건을 정한 것이며, 아직 제시하지 않은 patch나 Baseline의 승인 완료 기록으로 대체하지 않는다.
- 사용자가 요청한 승인 조건은 다음과 같다.

  > 이 저장소의 AGENTS.md에서 제거할 정확한 diff를 사전 승인한다.
  > 주입 기능이 Merge되고 runtime 검증이 통과한 뒤 적용한다.
  > 승인 당시 내용이 달라졌다면 재승인을 받는다.
  > 작업 worktree에서 적용하고 변경 내용을 명시한 PR을 남긴다.

- 적용 전에 승인 기준과 현재 파일·제안·결정을 대조한다. 승인 당시 내용이 달라졌거나 승인 patch를 그대로 적용할 수 없으면 정리를 중단하고 정확한 새 diff에 대한 재승인을 받는다. Worker가 변경된 기준이나 넓어진 삭제 범위를 대신 승인하지 않는다.
- 후속 Worker는 별도 작업 worktree에서 승인 patch만 적용하고 프로젝트 전용 규칙 보존을 확인한다. PR 본문에 `AGENTS.md`의 변경 사실·삭제 내용·이유·영향·최종 diff 링크와 선행 runtime 검증 근거를 명시한다. 기본 checkout과 다른 프로젝트는 정리하지 않으며 PR의 사용자 Merge 조건을 유지한다.

## Validation

Worker는 아래 변경과 직접 관련된 새·수정 unit case만 실행한다. 실제 모델 호출은 unit test double로 대체하며 전체 suite·integration·verify는 Manager가 담당한다.

- `tests/test_provider_runtime.py`, `test_agent_invocation.py`, `test_agent_invocation_state.py`: 두 provider의 신규·resume·fallback·읽기 전용 호출, 기존 추가 지침 보존, 따옴표·역슬래시·한글·여러 줄 내용 전달, 모든 역할의 공통 경계 통과와 모델 실행 전 버전 저장.
- snapshot·session 관련 targeted case: Worker·Reviewer 공통 해시 일치, runtime 업데이트 뒤 기존 작업 보존·신규 작업 갱신, 압축·중단·재시작, 과거 세션 최소 문맥 복구, 파일 누락·빈 내용·UTF-8 오류·해시 불일치·저장 실패·기능 미지원에서 process 미시작. 관련 책임에 맞는 기존 test 파일을 우선 사용한다.
- `tests/test_planning_fingerprint.py`, 관련 selection·성공 결과 재사용 case: 공통 내용만 변경했을 때 재평가, 같은 내용의 runtime 갱신에서는 불필요한 반복 없음, 진행 작업·독립 프로젝트와 기존 원격 입력 조건 보존.
- `tests/test_guidance_approval.py`, `test_execution_guidance.py`, 관련 scope case: self 포함 프로젝트 AGENTS의 사전 제안·사용자 판단·정확한 patch 적용, 공통 파일의 일반 Worker 수정에서 guidance 승인 대기 없음, 일반 역할 범위 유지, 신규 공통 제안 불필요, 기존 approve·reject·replace·pending 기록의 원래 대상 유지와 적용 불가 보존.
