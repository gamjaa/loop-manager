## Purpose

G-142가 명시적으로 남긴 계획 작성/게시·실제 Worker 시작·단계 실패·draft 알림과 전송 강도를 구현한다.

## Acceptance Criteria

- 계획 작성 결과와 실제 게시/catalog 반영, 실제 Worker 시작, PR 등록과 단계 실패에 대상·원래 발생 시점·현재 처리 상태를 가진 durable 사건을 만든다. READY 생성/선택·실패한 게시를 시작/생성 성공으로 알리지 않고 PR은 Merge 대기로 표시한다.
- 작업 시작·새 계획 게시의 전송을 뒤따르는 긴 Agent/verify 전에 시도한다. 실패·차단·PR 확정은 같은 실행에서 가능한 즉시 시도하며 늦게 전달되어도 사건 시각을 유지한다.
- 참고·자동 재시도 실패는 Telegram 무음, PR 검토/Merge·승인·최종 조치는 일반 전송이다. draft는 원격 링크·필요한 결정의 일반 알림이며 Worker 시작·planning 오류·프로젝트 차단으로 표시하지 않는다.
- 같은 사건·내부 retry·재시작·같은 질문·변화 없는 no-plan 결과를 중복하지 않는다. 새 시작·별도 실패·대응 변화는 구분하고 blocked-resume과 일반 resume의 중복을 막는다.
- 이미 통지된 계획 차단이 해제되고 해당 계획의 Worker·PR 처리가 실제 시작하면, 별도의 planning 오류가 보존돼 있어도 이전 scope·계획·원인과 새 작업을 담은 재개를 한 번 알린다. 다른 계획의 시작은 그 사건을 재개하지 않으며, 남은 planning 오류의 차단 사건·미해결 상태를 해제하거나 Planner 재개로 표현하지 않는다. 프로젝트 안전 gate나 해당 계획의 실제 차단을 우회해 작업 시작을 합성하지 않는다.
- 전송 실패·부분 전송은 기존 이력에서 재개하고 실제 작업은 계속한다. Telegram 비활성/부분 설정·비밀값 가림과 기존 checkpoint·완료 gate를 보존한다.

## Implementation

- notifications/events·incident·outbox의 기존 dedup·부분 전송·work cycle을 재사용한다. 사건 identity/발생 시점/무음 여부와 transport의 disable_notification을 명시적으로 결합한다.
- planning publication·실제 process 시작·execution 단계 결과·draft 결정 경계에서 사건을 기록하고 긴 다음 단계 전 flush를 연결한다. process 선택만으로 실제 시작을 합성하지 않으며 G-168 원격 보존 위치를 기존 차단 알림에 연결한다.
- 기존 incident의 통지 확인·해제·대상 작업 시작과 일반 재개 사건을 함께 대조한다. 독립 planning 오류 때문에 해제된 계획 사건까지 일괄 억제하는 경계를 대상별로 판단하고, 실행 선택·차단 해제 정책은 유지한다. 기존 outbox·전송 확인·부분 취소 기록을 재사용하며 저장 오류·미시작·재시작에는 확인되지 않은 시작을 성공 처리하지 않는다.
- 자동 역할·권한·검증은 docs/AGENTS.common.md와 해당 역할의 docs/AGENTS.*.md를, 프로젝트 규칙·설계·계획 작성은 AGENTS.md·docs/ARCHITECTURE.md·docs/PLANS.md를 참조한다. 기존 helper·관련 테스트를 재사용하고 지정 루트 경로를 보존한다.

구현 기록 (2026-10-07):

- `notifications/{events,repository,incidents,delivery,transport,rendering}.py`에서 사건 payload의 발생 시각·처리 상태·무음 여부를 저장하고 Telegram `disable_notification`에 연결했다. 기존 outbox의 조각 cursor·취소·재전송을 재사용하며 draft 게시와 안정적 대기는 같은 질문 사건을 공유한다. 해소되거나 변경된 draft의 미전송 조각은 취소한다.
- provider의 실제 Popen 이후, prompt 전달 전에 시작 사건을 기록·전송한다. 선택 단계의 시작 합성을 제거하고 retry sequence identity로 내부 재시도를 묶었다. planning 작성 결과·catalog 게시와 recovery 실패를 저장 경계에 연결하고 scheduler의 프로젝트별 전송 문맥으로 다음 긴 단계 전에 commit된 새 사건을 전송한다. 기존 실패 알림 재시도는 외부 dispatch에 남긴다.
- incident에 시작 시각·시작 identity, recovery record에 실패 episode를 호환 가능한 nullable 열로 추가했다. 남은 planning 오류는 project·Planner 재개만 억제하며, 해제된 해당 계획의 Worker·PR 재개는 별도로 판단한다. 실제 project/plan/draft gate와 planning 차단·오류 기록을 보존하고 일반 시작 알림과 중복하지 않는다.
- targeted unit 검증에서 새 사건·무음 HTTP payload·실제 process 시작 순서·미시작·내부 retry·rollback·부분 전송·재시작·독립 계획 재개·기존 PR/완료/대기 경계를 확인했다. fixture의 outbox 초기화, 시각/상태를 포함한 분할 메시지 기대값, 전달 대상과 명시적 transaction 시작을 수정한 뒤 실패했던 동일 명령을 재실행해 통과했다. 전체 verify·integration·build·lint와 Git 게시 작업은 실행하지 않았다.

교정 기록 (2026-10-08):

- `REVIEWING.last_error` 저장 transaction에서 대상 계획·현재 revision·검증 후보·원인을 기준으로 무음 실패 사건을 만들고 다음 Reviewer 호출 전에 전송한다. 같은 프로토콜 오류의 내부 교정은 중복하지 않으며 다른 원인·검증 후보와 rollback을 구분한다.
- 해제된 차단의 전송 중 조각을 보존해 확인 뒤 재개를 생성한다. 전송된 조각이 없으면 실제 시작 사건을 생성하고, 전송 중 실패하면 저장된 시작 시각으로 일반 시작을 생성한다. 일반 시작 억제는 같은 시작 identity의 실제 전송 중 사건에만 적용한다.
- rebase 충돌의 두 테스트 파일에서 기존 catalog fixture·한국어 PR 본문과 새 사건 기대값을 병합했다. verify 진단의 실패는 실제 Planner 시작을 거치지 않는 기존 fixture였으며 실제 시작 경계로 갱신했다. 부분 전송 fixture의 본문 조건과 Reviewer 예외 fixture, 사건 조회의 실제 revision 열을 교정한 뒤 동일 targeted 명령의 8개 테스트와 추가 사건 identity·transaction 테스트 1개가 통과했다.
- 제공된 verify 진단은 600초 동안 success 3005·skip 2·failure 1을 기록했고 완료된 테스트 ID 중복은 없었다. 종료 직전 1.05초·3.92초 경과한 서로 다른 테스트와 0.14초 Git snapshot이 진행 중이었다. 무한 반복·교착 근거는 확인되지 않았으나 실패도 포함되어 시간 상한만 부족하다고 판정하지 않았다. 검증 항목·상한·verify 스크립트를 변경하거나 전체 verify를 실행하지 않았으며 Git 충돌 확정·rebase 진행은 Manager에 남겼다.

- Manager 검증 피드백 대응: `agents/invocation_service.py`의 시작 callback을 connection-local 알림 세션이 있는 호출로 제한해 독립 문서 Agent와 native provider의 기존 실행 경로를 보존했다. `notifications/events.py`는 비활성 게시 알림에서 payload·draft projection을 읽기 전에 반환한다.

- 여러 사건 발생 경계와 durable 전달을 연결해 complexity high다. risk medium은 잘못된 통지/누락의 영향이며 기존 구현의 outbox·재개 기능은 재작성하지 않는다.
