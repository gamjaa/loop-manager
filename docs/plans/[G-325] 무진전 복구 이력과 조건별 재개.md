## Purpose

동일 원인·입력에서 retry와 대기만 반복하는 작업을 지속 이력으로 구분해 해당 자원만 보존 대기하고, 실제 새 입력·복구 전이·조건 해소 뒤 이어간다. `recovery_records`의 occurrence/진전 표식과 `persistent_execution_failures`의 외부 실행 이력을 재사용한다. `wait_retry()`에는 이미 `REMOTE_SNAPSHOT_RACE`의 pause·attempts 3 이상에서 타이머 재등록을 거부하는 처리가 있고, `GIT_INPUT_UNCERTAIN`은 조건 대기로 분리돼 있다. 남은 범위는 이런 사유별 처리를 실제 입력/진전과 실행 간 이력에 연결해 조건이 달라진 해당 대상만 재개하는 것이다. 일반 recovery 표식은 session/token도 포함하므로 실질 진전과 구별해야 한다. G-297의 같은 실행 재배정·대기 구조를 소비하고, Git 이력 재구성은 G-313, fetch 격리는 G-324, 진단 전송은 G-326에 남긴다.

## Acceptance Criteria

- R-091/R-055: 작업/자원·단계·원인·유효 입력·실질 진전으로 반복을 식별한다. 짧은 retry 묶음의 실제 시도와 외부 실행 간 이력을 구분해 횟수·확인 기간·상세 원인·보존 자료·다음 유효 재평가 조건을 유지한다. 다른 원인·자원·후보를 같은 장애로 합치지 않는다.
- 타이머 만료·로그/진단 생성·같은 checkpoint 재관측·session/runtime 재시작이나 관측 횟수만으로 진전 또는 해소를 만들지 않는다. 실제 새 원격/파일/검증 입력·안전한 복구 단계·외부 조건 해소를 확인한 경우에만 그 원인에 필요한 처리를 재개한다.
- 정상적인 짧은 retry, 슬롯/CPU/DB/Git 순번 대기·사용 한도·종료 확인 대기는 무진전 장애로 추정하지 않는다. 복구 전이 없이 동일 실패가 반복됐다는 현재 근거가 있을 때 같은 실행의 반복 배정과 다음 외부 실행의 동일 실패 재생을 억제한다. 횟수 소진만으로 FINAL_BLOCK·사용자 결정·성공을 만들지 않는다.
- 보존 대기는 해당 작업/자원에 한정하고 독립 작업·결과 수집·운영 요청·pause/취소·확정된 runtime 종료 결정은 계속 처리한다. 대기 중 runtime 원격 조회·유료 probe·새 writer는 만들지 않고 종료 불명 예약과 필수 검증·dependency는 유지한다.
- 새 입력·상태 변화·유효 복구 요청은 현재 원인·소유권·generation·조건을 재검사하는 계기다. 확인된 해소만 같은 작업의 저장 단계로 연결하며 실패·교정·targeted 이력·checkpoint·session·양쪽 Git 작업물은 초기화하지 않는다. 중단/재시작·경쟁 저장에서 관측·외부 효과 중복이나 다른 작업 상태 덮어쓰기가 없다.
- R-053 소비자가 읽을 현재 정체 identity·근거·기간·횟수·재평가 조건을 기존 저장 경계에서 제공한다. 알림 설정·전송 여부와 실행 판단을 분리하고, 기존 legacy 실패 감사의 부재·불완전성을 새 장애 확인으로 소급 변환하지 않는다.

## Implementation

- [ ] 확인한 `loop_manager_internal/recovery/recovery_runtime.py`의 `RecoveryObservation`·`decide()`와 `storage/recovery_state.py:observe()`·`_record_external_failure()`·`defer_retry()`를 재사용해 실질 입력/진전·반복 이력을 연결한다. 기존 retry 한도·외부 실행 집계는 보존하고, 단순 카운터/시간만으로 정체를 결정하거나 새 전역 retry 엔진·비호환 상태 모델을 만들지 않는다.
- [ ] 확인한 `execution/execution_recovery_handler.py:_recover()`의 일반 session/token 표식과 `application/project_runner.py:retry_pause_detail()`의 subject/disposition별 묶음 집계를 실제 원인·입력과 대조한다. Worker 교정의 현재 후보 지문을 재사용하고, Git·verify·원격 복구가 제공한 의미 있는 진행 근거를 보존한다. 새 세션·진단 text만 바뀌어 같은 실패를 새 사건으로 만들지 않는다.
- [ ] 확인한 `application/task_scheduling.py:run_project_tasks()`·`wait_retry()`와 프로젝트 조율/복구 재진입에 동일한 대상별 보류·재평가 판단을 적용한다. 기존 원격 경쟁의 타이머 재등록 거부와 `GIT_INPUT_UNCERTAIN` 조건 대기·프로젝트 준비의 독립 진행을 소비하고, 입력/진전 identity·새 조건 재개·외부 실행 이력이 아직 연결되지 않은 경계만 보완한다. G-297의 대기 뒤 자격·같은 실행 재개를 유지하며 횟수 gate만으로 전체 무진전 판정을 대신하지 않는다. 프로젝트 준비처럼 작업 배정 이전에 실패한 관측도 기존 프로젝트 recovery 경계로 연결한다.
- [ ] DB 처리는 기존 `storage/db_access.py`의 짧은 요청/CAS를 사용하고 외부 관측·대기는 요청 밖에 둔다. 저장 실패에는 원래 오류·저장 오류와 미확정 자료를 남기고 성공/정체 확정을 합성하지 않는다. 기존 레코드에 필요한 호환 정보만 보완한다.
- [ ] 확인한 `tests/test_recovery_state.py`·`test_recovery_runtime.py`·`test_task_scheduling.py`의 실제 SQLite·fake clock/Event와 `tests/test_notification_events.py`의 지속 실패 fixture를 근거 생산 경계에 재사용한다. PRODUCT의 retry/조건 대기와 ARCHITECTURE의 독립 실패 이력 절에 새 보존·재개 계약만 통합한다.

## Validation

- Worker targeted unit은 `tests.test_recovery_state.RecoveryRepositoryTests`·`tests.test_recovery_runtime`와 `tests.test_task_scheduling.TaskSchedulingTests`의 변경한 최소 case다. 같은 실행에서 여러 retry 묶음, DB 재연결·외부 실행 재시작을 연결해 동일 실패의 유한 재배정·계속 보존된 횟수/기간·독립 작업 진행을 확인한다.
- 같은 고정 OID/입력에서 시간·로그·session·runtime identity만 바꾸면 진전하지 않는다. 새 원격/파일/검증 입력, 실제 복구 단계와 조건 해소에서는 현재 소유권 확인 뒤 같은 작업만 재개한다. 다른 단계·원인·작업의 이력은 합산하지 않는다.
- 기존 정상 retry·30초 대기·사용량/DB/실행 자리·종료 불명 case는 정체나 최종 차단으로 바뀌지 않아야 한다. 실제 targeted 3회·사용자 판단과 필수 검증은 계속 유지한다. 대기 중 원격 runtime 조회·동일 외부 effect replay는 0회다.
- 직접 구현된 `tests/test_task_scheduling.py:test_exhausted_remote_race_does_not_restart_from_a_timer`와 `tests/test_recovery_runtime.py:test_unproven_git_history_waits_without_user_action_or_timer_retry`를 재사용한다. 추가 검증은 같은 원인/입력을 외부 실행 뒤에도 보존하는 경우와 실제 새 입력·복구 전이·조건 해소 후 해당 대상만 재개하는 연결에 둔다. 기존 횟수/타이머 gate나 단일 사유 분류 unit을 반복 작성하지 않는다.
- 현재 정체 근거 확정·조건 해소/새 입력 적용 전후 중단, generation 경쟁과 DB 저장 실패를 검사한다. 기존 `test_external_runs_count_once_and_reset_on_progress_or_success`의 외부 실행 1회 집계·실제 성공 해소 assertion은 유지하며, 알림 송신은 G-326의 검증에 남긴다.
