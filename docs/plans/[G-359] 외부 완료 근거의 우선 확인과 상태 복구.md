## Purpose

실제 PR Merge 또는 검증된 원격 archive 완료 근거를 DB의 과거 상태보다 먼저 확인하고, 미반영 상태만 기존 catalog·실행 저장 경계에서 복구한다. 상태에 따른 PR 관측 누락·프로젝트 차단에 의한 완료 수락 생략과 게시 identity 불일치의 선행 거부를 교정해 완료 작업을 다시 실행하지 않게 한다. archive 게시·FIFO·일반 재시도 엔진은 재구현하지 않는다.

현재 `recovery/waiting_pr_service.py:observe_waiting_pull_requests()`의 조회는 READY와 수동 묶음 밖 자동 진행 상태, 일부 PLAN_BLOCKED를 제외하며, Merge를 관측해도 프로젝트 차단이 있으면 완료 처리를 건너뛴다. `CatalogRecoveryService.reconcile()`은 검증된 archive의 SHA 차이는 수용하지만 일부 저장 identity 불일치에서는 외부 완료 근거 재확인 전에 진단한다. `ExecPlanArchiveRepository.merged_candidates()`는 MERGED 행만 발견하므로 누락된 완료 수락이 archive 기회에도 전달된다. 기존 G-189는 후속 전수 감사, G-350은 프로젝트 단계 순서를 맡으며 이 공통 완료 복구는 소유하지 않는다.

## Acceptance Criteria

- R-055/R-093: 원격 catalog·저장된 연결·기존 PR 이력으로 같은 repository·ExecPlan·branch/base·PR identity를 확인할 수 있으면 DB 행 유무나 READY·진행·차단 상태가 완료 근거 조회의 진입 조건이 되지 않는다. 정상적으로 열린 DB의 작업 행 누락은 기존 등록/인수 경계로 복구한다. DB 파일 부재·손상은 자동 초기화하지 않고, 이름이 비슷한 PR이나 임의 branch를 채택하지 않는다.
- R-055: 실제 Merge는 archive가 없어도 완료이며, 유효한 원격 archive 이동은 PR Merge 미관측과 구분한 문서 기반 완료다. 검증된 현재 ID·이동 경로·최종 bytes/mode·원격 revision과 저장 완료 근거가 설명하는 identity를 대조한다. 게시 identity·과거 hash/SHA 불일치는 원래 기록과 교정 근거를 보존해 재평가하고 단순 일치 복원을 요구하지 않는다. 다른 repository/ID/PR·경로·내용의 실제 충돌은 자동 정합화로 덮지 않는다.
- 완료 근거 확인과 DB 확정, worktree/ref 정리·archive 쓰기를 분리한다. 프로젝트 차단·planning 점유·writer/정리 대기가 있어도 확인된 완료를 잃거나 실행을 부활시키지 않는다. 진행 중/종료 불명 호출과 자원 예약·사용자 파일·index·session·retry·원래 성공/실패 감사는 보존하고 새 호출·검증·PR 게시를 시작하지 않는다. 정리·원격 쓰기는 계속 현재 소유권·writer 종료·정확한 lease를 확인하며 독립 차단·다른 작업의 투영을 일괄 해제하지 않는다.
- 외부 조회는 DB writer 밖에서 수행하고 같은 대상·연결·catalog revision·generation을 재확인한 짧은 CAS로 적용한다. DB 실패·경쟁·중단에는 외부 완료 근거의 종류·관측 revision과 미반영 확정을 구분해 기존 복구 자료에 남긴다. 재시작은 다시 확인해 남은 DB/정리만 이어가며 commit·push·PR·완료 알림·Merge 사건을 중복 생성하거나 유실된 최초 게시/실행/검증 성공을 합성하지 않는다.
- OPEN·미Merge CLOSED·조회 실패·불완전/충돌 근거는 Merge 성공이 아니다. 확인 불가 대상과 그 의존 범위만 보류하고 검증된 독립 작업은 진행한다. 실제 PR Merge가 확인된 작업의 archive 충돌은 완료를 되돌리지 않고 해당 archive 쓰기만 보류한다.
- R-094/R-091: 완료 복구 뒤 활성 문서는 기존 archive 후보 발견·공유 Git 순번으로 이어지고 이미 게시된 이동은 DB 확정만 복구한다. 시작·planning/dependency·차단 복구·유지보수/프로젝트 완료가 같은 저장 완료 근거를 소비한다. 복구 자체로 새 planning·작업 주기·유지보수 Merge 수·프로젝트 완료 알림을 만들지 않는다. 읽기 전용 status는 저장된 근거와 DB 반영 대기·실제 근거 충돌을 설명할 수 있게 하되 조회 중 관측/복구/쓰기를 실행하지 않는다. 출력 연결은 G-194가 맡는다.

## Implementation

- [ ] 확인한 `recovery/waiting_pr_service.py:observe_waiting_pull_requests()`·`application/project_service.py:run()`/`_synchronize_pull_requests()`의 기존 PR 관측/충돌 실행 분리를 재사용한다. 완료 확인 대상을 상태·수동 membership으로 먼저 제거하는 경계와 프로젝트 차단 시 Merge 수락 생략을 교정한다. `git/merge_cleanup_service.py:complete_merged_execplan_worktree()`의 대상별 identity CAS·완료 선기록/정리 분리를 사용하고, 완료 관측과 안전하지 않은 정리 효과를 함께 거부하지 않는다. 현재 planning·runtime/pause 제어 및 수동 묶음의 정확한 PR/HEAD 계약은 유지한다.
- [ ] 확인한 `catalog/legacy_migration.py:_LegacyCatalogMergeProof`·`storage/execplan_catalog_state.py:CatalogRecoveryService`/`publication_identity()`·`storage/catalog_migration.py`에서 증거 종류·현재 원격 identity와 과거 DB 값의 책임을 통합한다. 유효한 외부 근거 재확인이 가능한 저장 충돌과 실제 원격 충돌을 구분하고 원문 감사를 보존해 누락 상태만 적용한다. 현재 원격의 `publication_sha != plan_sha` 복구, 로컬 게시 객체 부재의 PR fallback, PLANNING 중 pinned archive 이력 복구는 직접 구현으로 소비한다. 새 DB 원본·범용 journal·병렬 관측 서비스나 중복 완료 엔진은 추가하지 않는다.
- [ ] R-093의 작업 행 누락은 현재 `recovery/plan_recovery.py:remote_adoption()`과 원격 branch/PR 이력 확인을 재사용해 기존 등록·인수 경계에 연결한다. 이미 terminal인 대상은 Worker/후보 검증을 시작하지 않는다. 이전 환경의 session·검증 근거를 추정해 승계하거나 취소/ID 재사용 충돌을 정상 등록으로 바꾸지 않는다.
- [ ] 확인한 `catalog/project_selection.py:prerequisite_validation_rows()`·`storage/execplan_archive_state.py:merged_candidates()`와 `application/project_service.py:_archive_scheduling_boundary()`에 완료 수락 결과를 연결한다. 선행·archive 발견 전에 필요한 복구가 실행되도록 하고 조회·순수 graph 판단에 원격 호출을 숨기지 않는다. 유지보수/프로젝트 완료와 후속 배정은 기존 저장 근거·미확정 게시·소유권 계약을 사용한다. G-350은 이 결과의 프로젝트 순서를, G-313은 미완료 대상의 OID 재개를, G-189는 후속 소비 감사를 맡는다.
- [ ] 아래 기존 SQLite·관측 fixture를 확장해 실제 판정/저장과 실패/경쟁을 검증한다. PRODUCT·ARCHITECTURE의 소유 절에는 구현된 완료/보존/복구 계약만 통합하며 Requirement·다른 ExecPlan은 수정하지 않는다.

## Validation

- Worker는 `tests/test_project_catalog_refresh.py`·`tests/test_archive_recovery_regressions.py`의 실제 SQLite와 제어된 원격/PR 관측을 재사용해 변경한 최소 unit을 실행한다. 연결 PR이 있는 READY·수동 묶음 밖 자동 진행·일반 PLAN_BLOCKED와 프로젝트 차단 소유자의 실제 Merge가 Agent/verify/Reviewer/새 PR 호출 없이 완료로 적용되는지 확인한다. 행 누락은 정상 DB와 고정 원격 문서/정확한 PR 이력으로 복구하며 DB 파일 부재·손상과 구분한다. 상태 조합을 실제 Git 저장소로 반복하지 않는다.
- 유효한 archive 근거와 저장 게시 path/hash/SHA가 다른 경우를 구성해 같은 작업임을 확인할 수 있는 복구와 실제 이동/내용/PR 충돌의 보류를 대조한다. 현재 `test_verified_archive_recovers_stale_status_and_legacy_sha_on_restart`·`test_verified_archive_does_not_accept_changed_bytes_or_move_identity`·`test_planning_migrates_legacy_archive_before_dependency_validation`의 직접 행렬은 유지하고 부족한 identity 경계만 추가한다. mode 변경·다른 repository/ID·로컬 이동·OPEN/미Merge CLOSED·조회 실패는 완료로 수용하지 않는다.
- 완료 관측 후 CAS 경쟁·DB 확정 전 실패·확정 후 정리 실패/재시작을 기존 fixture로 확인한다. 완료 근거·원래 audit·session/retry·미종료 예약·독립 row/Planner phase/session/worktree/publication/error가 보존되고 완료 효과·알림이 중복되지 않아야 한다. 실제 Merge와 archive 기반 수락은 기록 종류로 구별하며 새 성공 receipt를 만들지 않는다.
- `tests/test_project_catalog_refresh.py`·`tests/test_archive_housekeeping_adapter.py`의 기존 archive/dependency fixture에 복구 결과를 연결한다. 선행 충족·archive 후보 발견과 independent 진행이 DB의 과거 상태 때문에 다시 차단되지 않고, 미확인 대상만 의존 범위와 함께 보류돼야 한다. 실제 writer·수동 소유·lease 충돌에서는 새 정리/게시가 0회다. `tests/test_pr_source_synchronization.py`의 실제 게시 후 DB 중단/중복 push 방지와 `tests/test_manual_work_publication.py`의 묶음 Merge·HEAD 보호는 기존 전체 검증에 남기며 같은 실제 lifecycle을 복제하지 않는다.
- 선택 adapter는 `scripts/verify.json`의 unittest/protocol 1·launcher Python·독립 모듈 수집과 필수 compile/runner 통합 단계다. Python 3.11–3.14 지원·일반 자식 guard·실제 통합의 신뢰된 상위 실행을 유지한다. 실제 OS/성능 측정은 이 작업의 새 목표가 아니며 G-187의 범위를 줄이지 않는다.

## Decision Log

- 기존 완료·catalog·PR 관측·정리 경계를 재사용한다. 과거 DB와 현재 외부 완료 근거의 역할을 분리하는 기존 명세의 구현 교정이며 새 완료 정책이나 운영 DB 직접 수정을 요구하지 않는다. G-350의 단계 순서, G-194의 읽기 투영, G-189의 전수 감사와 분리해 공통 복구를 독립 Merge할 수 있게 한다. 선행은 없으며 다른 작업의 검증 성공을 요구하거나 소급 생성하지 않는다.
- complexity high·최초 level 5: 행 누락/저장 충돌·외부 PR/archive 관측·동시 호출·CAS와 중단 이후의 완료/정리 분리를 일치시켜야 한다. risk high: 잘못된 terminal 수락은 필요한 구현을 누락하거나 다른 작업의 자원 정리를 유발할 수 있다. 실제 identity/원격 증명·원문 감사·경쟁 거부·정리 보류와 회귀로 제한하며, 불명확한 기존 적용은 보존된 감사로 수동 진단/복구해야 한다. priority high는 완료 작업 재실행과 선행 정체를 막기 위한 것이다. Model·Effort는 Manager 설정을 따른다.
