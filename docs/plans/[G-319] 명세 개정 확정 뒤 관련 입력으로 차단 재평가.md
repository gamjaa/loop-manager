## Purpose

일반 planning의 원격 게시·catalog·DB 반영이 확정된 뒤 관련 차단 계획의 원인을 최신 작업 본문·적용 명세로 재평가한다. 직접 `sources`에 없는 활성 Requirement도 Planner가 영향 관계를 확인한 경우 판단 입력과 재평가 계기에 포함하고, 실제 해소 근거가 확인된 원인만 기존 단계 재개로 연결한다.

현재 `recovery/checkpoint_recovery.py:_assess_user_decision_cause()`는 현재 질문 인용·동일 입력 평가 재사용·원격 재확인·checkpoint CAS를 갖추었으나 조회 집합은 선언 source·선택 작업·PRODUCT·ARCHITECTURE에 한정된다. `blocked_plan_service.py`의 직접 입력/Review 지문 중심 재평가 진입과 일반 planning 확정 결과의 연결을 함께 보완한다. 대상별 복구 lease·배정, 의미 판단 protocol과 검증 엔진을 새로 만들지 않는다.

## Acceptance Criteria

- R-082: G-318의 일반 차단 계획 개정이 실제 원격·catalog·DB에 확정되기 전에는 그 개정으로 원인 해제를 적용하지 않는다. 반영 확정 뒤 대상별 재평가를 예약하고 중단·재시작·DB 미적용 재처리에서도 미완료 반영과 원인 판단을 구분해 이어간다. 개정·source 추가·질문 삭제·다른 계획 등록은 해소 증거가 아니다.
- 직접 source 외 활성 Requirement 변경도 Planner가 작업 목표·검증·dependency에 실질적 영향을 확인했다면 현재 원문·원격 revision·영향 관계를 해당 대상의 입력에 포함한다. 무관한 변경은 기존 질문/차단을 보존하고 같은 입력의 의미 판단을 반복하지 않는다. 모든 Requirement 변경을 모든 차단 작업에 무차별 적용하거나 runtime/로컬 문서로 원격 근거를 대체하지 않는다.
- R-091/R-061: `user_decision_required`는 원래 질문과 최신 작업 본문·관련 상위 명세의 실제 인용·이유로 구체적 선택이 해소된 경우만 재개한다. 남은 선택·문서 충돌·불확실·원문/인용 불일치에는 보류를 유지한다. 저장된 draft·User Decision은 기존 출처/답변 검증 경로를 사용하고 사용자 승인·거절 원문을 작성·변경하지 않는다.
- 관련 문서 집합·내용·질문·후보·확정 revision을 평가 identity와 감사에 결합한다. 새 관련 입력을 과거 동일 지문의 성공으로 소비하지 않고, 링크/표현만의 변경·이미 확인한 동일 입력의 결과는 기존 기준대로 재사용한다. 새로 추가된 관련 Requirement의 과거 부재와 현재 필수 source의 누락·모호함·조회 실패를 구분하며, 조회 실패를 목표 철회나 해소로 추정하지 않는다.
- `plan_input_invalid`, verify/Review 소진, ownership·scope·timeout·원격 branch 삭제 등은 기존 사유별 해소 조건으로 판단한다. 한 원인의 해소가 다른 승인·안전 차단이나 미Merge dependency를 해제하지 않는다. 기존 작업물·branch·worktree·session·실패/승격·checkpoint·질문 감사를 보존하고 최신 후보에 필요한 Worker·targeted·verify·Review부터 이어간다. 과거 PASS를 새 조건의 성공으로 만들지 않는다.
- R-091: 대상별 실행/복구 lease·현재 writer/종료 불명·공유 planning/게시 소유권을 확인하고, 다른 독립 작업의 투영·후보·예약은 유지한다. 원격/모델 관측은 DB 쓰기 잠금 밖에서 수행하며 짧은 확정 transaction에서 대상·원인·generation·현재 입력을 재검증한다. 경쟁·실패·중단은 기존 보류와 미완료 자료를 보존하고 독립 배정은 계속한다.

## Implementation

- [ ] 확인한 `planning/planner_publication.py:_apply_general_planning_batch()`·`recover_general_planning_batch()`와 `planning/publication_service.py`의 확정/복구 경계를 대조해 관련 작업·현재 명세·실제 반영 revision의 근거를 기존 결과/intent·checkpoint 저장에 연결한다. 필요하면 이 기존 저장 계약에 호환 필드를 추가하되 별도 DB·새 polling·Planner 호출 조건·사용자 답변 protocol은 만들지 않는다. G-318의 snapshot/CAS를 소비하고 G-310의 공통 결함 보고 수집은 구현하지 않는다.
- [ ] 확인한 `recovery/blocked_plan_service.py:_resume_blocked_execplan_if_inputs_changed()`·`blocked_plan_reconciliation.py:_evaluate()`의 원인별 진입과 `planning/planning_document_relevance.py`의 원격 변경/관련 문서 처리를 재사용한다. Planner가 확인한 간접 Requirement 영향이 직접 source 지문 무변경 때문에 소실되지 않게 연결하고, 실제 판단은 원인별 evaluator에 맡긴다. 배정기·대상 lease와 R-091 관리 상한은 기존 경계를 소비한다.
- [ ] 확인한 `recovery/checkpoint_recovery.py:_assess_user_decision_cause()`의 문서 조회 집합·meaning 비교·평가 identity·인용 검증을 관련 활성 입력에 확장한다. `catalog/requirement_sources.py`의 동일 ID rename 조회와 현재 필수 source 오류 처리를 유지하고 과거 부재를 확인한 새 문서는 명시적으로 구분한다. 기존 `user_decision_assessment`·history와 `storage/execution_checkpoint_state.py`의 generation CAS를 재사용해 잘못된 과거 평가 승계와 원래 질문 소실을 막는다.
- [ ] 확인한 `tests/test_task_scheduling.py`의 질문 의미 재평가 unit, `tests/test_plan_block_revalidation.py`의 대상별 원인·lease·중단 fixture와 `tests/test_planning_publication.py`의 게시 확정 fixture를 확장한다. 실제 SQLite·파일·현재 판단을 사용하고 Git/PR·Agent 관측만 mock한다. PRODUCT·ARCHITECTURE의 개정/원인 재평가 소유 절을 실제 구현에 맞춰 통합한다.

## Validation

- Worker는 위 세 모듈에서 변경한 의미 판단·확정 연결의 최소 unit case만 실행한다. A의 직접 source·본문이 그대로여도 Planner가 관련성을 확인한 활성 Requirement B가 원래 질문을 해소한 경우, B 원문·변경/상위 인용·확정 revision을 전달해 한 번 재평가하는지 확인한다. 무관한 C 변경에는 재개·의미 판단 호출이 없어야 한다. B가 새 문서인 경우와 현재 필수 B 누락/ambiguous·Git 조회 오류도 구별한다.
- 기존 `test_user_question_recheck_requires_current_cause_evidence_and_preserves_failed_assessments`의 해소/미해소·링크/선언만 변경·허위 인용·작업 문서만의 인용·probe 실패 assertion을 재사용한다. 관련 집합이 바뀌면 새 identity로, 같은 입력 재처리는 같은 평가로 처리하며 draft 원문·사용자 결정·질문/실패 history를 유지한다.
- 개정 게시 전, push 후 DB 미적용, 전체 반영 확정, 재평가 저장 전후 중단을 구분한다. 확정 전 원인 해제는 0회이고, 확정 뒤에도 남은 질문·검증 부족·독립 승인·미Merge dependency는 계속 보류돼야 한다. 성공 영수증·사용자 답변·Merge를 합성하지 않는다.
- 원격 revision·대상/원인·checkpoint generation·수동/PR 소유권이 관측 중 바뀌면 낡은 결과를 적용하지 않는다. A 재평가 중 B/C의 실제 DB 요청·배정·투영/후보 보존과 같은 대상 중복 평가 거부를 기존 lease/배정 fixture로 확인한다. 실제 Git 통합·게시·복구의 기존 효과 회귀를 같은 조건 조합으로 복제하지 않는다.
- 원인 해소 뒤 현재 작업의 필요한 단계가 선택되고 session·작업물·실패 감사가 보존되는지 확인한다. 원격 branch 삭제의 명시적 재시작, 종료 불명·사용자 operation·독립 safety 차단은 문서 개정으로 우회할 수 없어야 한다. G-310의 실제 공통 교정 Merge/검증 조건은 이 일반 명세 반영 경로와 별도로 유지한다.

## Decision Log

- G-318은 문서 개정을 가능하게 하고 이 작업은 확정 뒤 원인 재평가를 맡는다. G-310은 여러 작업의 공통 결함·교정 목표/실제 Merge 근거를 모아 이 공통 경계에 전달하며, 이 작업을 선행으로 소비한다. G-189는 그 뒤 후속 선택·차단/알림을 감사한다. 기존 구현·기존 계획의 담당 목표를 중복 생성하지 않는다.
- complexity high: 원격 게시·DB 확정과 대상별 의미 판단의 수명, 간접 관련 문서 집합·과거/현재 원문·평가 identity와 중단/경쟁을 함께 보존해야 한다. risk high: 잘못된 인용/과거 평가 승계나 조기 해제는 사용자 선택·필수 검증을 우회한다. 원래 질문·불변 감사·현재 인용·원격/소유권 재관측과 CAS를 유지하고 불확실한 원인은 보류해 복구한다. priority high는 명세가 보완돼도 남는 불필요한 차단을 안전하게 재평가하는 기준이다.
- adapter version 1 unittest·launcher Python 3.11–3.14와 필수 compile·실제 Agent 차단은 유지한다. verify adapter·지원 OS·timeout/병렬 정책을 바꾸지 않는다. 이번 delta는 프로젝트 최종 전문 확인이나 실제 차단 해제·검증 성공 선언이 아니다.
