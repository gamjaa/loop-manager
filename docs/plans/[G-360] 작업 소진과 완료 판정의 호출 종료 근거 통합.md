## Purpose

호출 결과가 수집됐어도 실제 프로세스 종료가 미확인인 동안 작업 소진·진행 불가·프로젝트 완료를 확정하지 않게 한다. 현재 `notifications/work_exhaustion.py:execution_pending()`은 `agent_invocations.finished_at IS NULL`만 검사한다. 반면 `storage/task_calls.py:pending_for_plan()`은 결과 수집과 실행 상태·시작/종료 시각·종료 근거를 구분한다. 이 차이를 기존 저장 계약에 맞춰 공통 판정에서 교정한다.

이번 delta의 `blocked_selection()`·일반 대기 episode·최종 완료와 현재성 검사를 그대로 사용한다. G-341의 실제 시작/재개 사건, G-326의 지속 장애 판정, G-356의 전송 큐와 G-189의 후속 전수 감사는 각 계획에 남긴다. 이미 구현된 진행 불가 알림 전체를 다시 만들지 않는다.

## Acceptance Criteria

- R-053/R-055: 같은 프로젝트에 결과 수집 완료와 별개로 실행 중·종료 미확인 호출이 있으면 안정적 작업 소진·`blocked_selection`·프로젝트 완료를 확정하거나 알리지 않는다. task 예약이 없어도 `finished_at`만 채워진 `executed` 호출, 실행 상태가 불명인 호출과 시작 기록이 모순된 `not_executed` 호출은 기존 호출 보존 계약으로 판단한다.
- 실제 종료가 저장 근거로 확인된 성공·실패·중단·결과 수집 오류는 실패 결과나 오래된 호출이라는 이유로 영구 대기시키지 않는다. 시작하지 않았음이 확인된 호출도 기존 `not_executed` 계약으로 구분한다. 결과 수집이 아직 미완료이거나 예약이 남은 경우의 기존 보류는 유지한다.
- 프로젝트 전체를 검사하므로 작업 ID 없는 Planner 호출·MERGED 작업의 미종료 호출도 빠지지 않는다. 다른 프로젝트의 호출은 해당 프로젝트의 소진/완료를 막지 않는다. `exec_plans`의 비terminal 행만 순회해 호출을 찾지 않는다.
- 생성 시점과 전송 직전/각 조각의 현재성 검사가 같은 판정을 소비한다. 사건 생성 뒤 종료 미확인 호출이 생기면 미전송 잔여분만 취소하고, 이미 확인한 조각·payload·attempt/error·episode/완료 감사를 보존한다. 종료 확인 뒤에는 현재 catalog·선행·최종 전문 확인 등 원래 gate를 다시 만족해야 하며 새 사건이나 완료를 자동 합성하지 않는다.
- 저장 관측만 읽고 schema ensure·migration·receipt 파일 조회·프로세스 종료·예약 회수·원격/Git·Agent·verify를 실행하지 않는다. 선택 table 부재와 과거 schema의 확인 불가 정보는 기존 호환 경계에서 명시적으로 처리하며, 모르는 종료를 성공으로 간주하거나 조회 중 자료를 보완하지 않는다.

## Implementation

- [ ] 확인한 `storage/task_calls.py:pending_for_plan()`과 `storage/agent_invocation_state.py:InvocationRepository`의 `mark_execution_finished()`·`reconcile_execution()`을 기준으로 결과 수집/실제 종료의 공통 저장 판정을 재사용한다. 프로젝트 범위와 작업 범위가 같은 조건을 사용하도록 필요한 최소 순수 조회 경계만 공유하고 SQL 조건을 서로 다른 정책으로 복제하지 않는다. 호출 기록·receipt 형식이나 종료 엔진을 새로 설계하지 않는다.
- [ ] 확인한 `notifications/work_exhaustion.py:execution_pending()`의 모든 소비자 `application/project_outcomes.py:_stable_work_reason()`, `notifications/policy.py:completion_current()`·`waiting_current()`와 `blocked_selection()`을 대조해 같은 저장 근거를 소비시킨다. 이미 구현된 draft/차단/선행 사유·정보성 일반 알림·중복 제거와 실제 종료 후 재평가를 유지한다.
- [ ] 확인한 `tests/test_notification_work_cycles.py:CompletionCycleTest`·`WorkReasonOutboxTest`, `tests/test_task_scheduling.py`의 실제 SQLite/호출 fixture와 `tests/test_project_catalog_refresh.py:test_cleanup_retry_preserves_pending_writer_until_confirmed_release`의 결과 수집/종료 구분을 재사용한다. helper 조건은 한곳에서 검사하고 소비자에는 필요한 연결 case만 둔다. 기존 예약·전송·완료 행렬을 복제하지 않는다.
- [ ] PRODUCT·ARCHITECTURE의 소진/완료 및 호출 종료 소유 절에 실제 교정만 통합한다. Requirement·다른 ExecPlan은 수정하지 않는다.

## Validation

- Worker는 변경한 공통 조회와 알림 연결의 최소 unit을 실행한다. 실제 SQLite에 예약 없는 `finished_at` 완료/`executed`·종료 근거 없음, `unknown`, 모순된 `not_executed`, 정상 미시작, 실제 종료와 수집 모두 완료, 예약 유지와 수집 미완료를 구성해 기대한 보류/허용을 확인한다. 성공·실패 코드로 종료를 추정하지 않는다.
- `WorkReasonOutboxTest`의 draft·차단·선행 fixture에 작업 ID 없는 호출과 MERGED 작업의 종료 미확인 호출을 최소 연결해 `blocked_selection()`이 None인지 확인한다. 실제 종료 근거 저장 후에는 같은 원래 gate가 다시 평가되고 다른 프로젝트의 호출에 영향받지 않아야 한다. `CompletionCycleTest`의 유효 최종 receipt fixture에서도 완료 생성·claim을 같은 조건으로 확인한다.
- 생성 뒤 호출이 미확인 상태로 바뀌는 경합과 부분 전송/재시작을 기존 outbox fixture로 확인한다. 남은 조각 취소·이미 전송한 조각/시도 감사 보존과 동일 episode의 중복 방지를 유지한다. 기존 시작/재개·PR·recover 알림의 허용 사건을 일괄 취소하지 않는다.
- DB/schema/호출·예약·outbox의 원래 기록이 판정 조회로 변경되지 않고 외부 효과가 0회인지 확인한다. optional/legacy schema는 확인한 호환 조건만 검사하며 실제 종료·Git·CLI를 새로 실행하는 fixture를 만들지 않는다. 선택 adapter는 unittest/protocol 1·launcher Python·Python 3.11–3.14이고 필수 compile·신뢰된 runner 통합 범위는 유지한다.

## Decision Log

- 실제 차이는 `finished_at`과 물리 종료 근거의 구분이다. 보고 499·503·515의 TCP 지연·worker 종료 오류나 409의 bootstrap 비용 원인으로 추정하지 않으며 그 미확정 보고를 이 계획에 연결하지 않는다. 결과 수집만으로 종료를 확정하지 않는 기존 R-055/R-091 구현 교정이므로 새 사용자 정책 선택은 필요하지 않다.
- 선행 없이 현재 Merge된 저장 helper·알림 경계에서 독립 검증·Merge할 수 있다. G-189에는 이 결과의 후속 감사를 연결하며 다른 사건 생산·전송 큐를 선행 조건으로 추가하지 않는다. snapshot 밖 계획·기존 사용자 결정·작업 공간/실행 이력은 변경하지 않는다.
- complexity medium·최초 level 3: 프로젝트/작업 범위·ID 없는 호출·선택 schema와 여러 소비자를 같은 명확한 저장 계약에 연결해야 한다. risk medium: 잘못된 판정은 조기 완료 통지 또는 불필요한 소진 보류를 만들 수 있으나 자원/호출을 변경하지 않으며 원래 감사와 조회 교정으로 회복할 수 있다. priority high는 미확인 호출이 남은 프로젝트의 잘못된 완료 확정을 막기 위한 것이다. Model·Effort는 Manager 설정을 따른다.
