# Loop Manager

> **문서 상태 — 재설계 목표 (미구현).** 이 문서는 새 Loop Manager가 보장해야 할 제품 정책의 초안이다. 현재 `main`의 구현·기존 Requirement와 다를 수 있으며, 실제 적용은 별도 구현과 검증 이후에 이루어진다. 기존 문서는 현행 동작 및 이행 검토에 참고하되 **새 설계의 정책과 충돌하면 이 문서의 목표를 우선**한다. 이 브랜치를 자동 실행의 base로 사용하지 않는다.

## Summary

Loop Manager는 사용자가 작성한 Requirement에서 AI Planner가 필요한 ExecPlan을 도출하고, 확정된 작업을 Worker·Verify·Reviewer로 구현·검토한 뒤 GitHub Pull Request를 생성하는 개발 자동화 도구다.

사용자는 제품 목표·중요한 정책·최종 PR Merge를 통제한다. Loop Manager는 계획·구현·검증·충돌 복구·중단 재개와 완료 기록을 맡는다. **안전한 자동화, 예측 가능성, 간단한 운영**을 처리량이나 복잡한 최적화보다 우선한다.

## Target Users and Scope

GitHub 저장소를 운영하는 개인 개발자와 소규모 개발팀.

- **언어·프레임워크·빌드 도구를 제한하지 않는다.** 등록 프로젝트가 정의한 개발 환경·검증 명령을 사용하며, 특정 언어의 테스트 도구나 구조를 모든 프로젝트에 강요하지 않는다.
- 여러 프로젝트를 등록하고 각각의 Requirement·ExecPlan·PR을 관리한다.
- 실행 시점은 외부 스케줄러가 결정한다. 자체 상시 실행 서비스는 만들지 않는다.

## Goals

1. Requirement와 Acceptance Criteria를 기준으로 실제 필요한 작업만 계획한다.
2. 처음 계획할 때 파악 가능한 전체 ExecPlan 및 선행 관계를 제안하고, 변경·누락에는 필요한 범위만 재계획한다.
3. 변경된 Requirement·ExecPlan을 미완료 작업과 기존 PR에 안전하게 반영한다.
4. Worker 구현·관련 테스트, 프로젝트 Verify, 독립 Reviewer를 거쳐 PR을 게시한다.
5. 계획·구현 PR의 Git 충돌을 가능한 경우 자동 Merge 및 Agent 교정으로 복구한다.
6. 장시간 Verify와 독립 작업 실행을 겹쳐 지연을 줄이면서 작업물·실행 근거를 보존한다.
7. GitHub·원격 브랜치를 바탕으로 재시작·환경 이전 후 작업을 이어가고 완료 문서를 보관한다.
8. Telegram으로 주요 진행 사건과 필요한 사용자 조치를 알린다.

## Non-Goals

- 계획 PR이나 구현 PR의 자동 Merge
- 사용자 요청 없는 기능·정책 추가 및 주기적 리팩터링·유지보수 작업 생성
- AI가 독자적으로 중요한 제품 정책·사용자 결정을 확정
- 내장 스케줄러·웹 대시보드·범용 다중 Agent 협업 플랫폼
- 특정 언어별 개발·테스트 플랫폼 구축 또는 복잡한 공통 테스트 병렬 엔진의 의무화
- 자체 코드의 무인 자동 개발·배포
- 충돌 회피를 위한 무단 Force push·Reset·기존 공개 커밋 이력 재작성

## Product Invariants

- **문서 기준**: base의 활성 Requirement와 유효한 ExecPlan이 현재 프로젝트의 확정된 목표·계획이다. 열린 계획 PR은 미확정 제안이며 그 내용만으로 신규 작업을 시작하지 않는다. 사용자는 어느 브랜치에서나 문서를 수정할 수 있고, 각 변경은 출처와 확정 범위에 맞춰 처리한다.
- **Requirement 충돌 우선순위**: 동일 대상·조건에 적용되는 **활성 Requirement 간 내용이 실제로 충돌하면 R-ID 숫자가 더 높은 문서의 해당 규칙을 우선**한다. 파일 수정 시각·최근 커밋 순서보다 R-ID가 우선하며, 낮은 ID 문서의 충돌하지 않는 규칙·Acceptance Criteria는 그대로 적용한다. archive의 과거 Requirement는 현재 목표의 우선순위 경쟁에 포함하지 않는다. 충돌이 아닌 추가·보완 관계를 임의로 덮어쓰거나 불명확한 정책 선택을 ID만으로 추정하지 않는다.
- **사용자 통제**: Planner는 신규 계획을 계획 PR로 제안한다. base의 유효한 ExecPlan은 별도의 계획 PR Merge 이력 없이도 실행 가능하다. 모든 최종 PR Merge는 사용자가 수행하며 Squash and merge를 권장한다.
- **실행 안전**: ExecPlan의 고유 ID, 의존성, 현재 문서 범위와 실제 원격 상태를 확인하고 진행한다. 선행 작업은 연결된 구현 PR의 실제 Merge 후에만 충족된다. 관련 없는 작업·프로젝트는 계속 진행한다.
- **Git 안전**: 작업별 분리된 공간에서 수행하고, 사용자 checkout·다른 작업·기존 원격 커밋을 임의로 덮어쓰지 않는다. Git 통합의 기본 수단은 Merge다.
- **확정된 성공만 신뢰**: Verify·Review·PR 게시·Merge·archive의 성공은 실제 후보와 유효한 근거에 결합한다. 입력이 달라졌거나 근거가 없으면 성공을 추정하지 않는다.
- **완료 불변식**: ExecPlan 완료는 구현 PR의 실제 Merge, Requirement 완료는 최신 Acceptance Criteria의 검증된 충족을 뜻한다. archive 이동·로컬 DB 표식만으로 완료를 합성하지 않는다.

## Product Workflow

### 1. 변경 확인과 작업 선택

Manager는 최신 원격 base, 활성 문서, 관련 PR과 저장된 진행 정보를 동기화한다. 변경되지 않은 입력은 재사용하고 같은 Planner·GitHub 충돌 조회·Verify를 불필요하게 반복하지 않는다.

기본 처리 우선순위는 다음과 같다.

1. Requirement·ExecPlan 변경 확인 및 계획 PR 생성·갱신
2. 기존 작업의 중단 복구·재개, 필요한 계획·구현 PR 충돌 복구
3. 실행 가능한 신규 ExecPlan의 우선순위 기반 구현
4. 검증·Review를 마친 구현 PR 생성·갱신
5. 완료 작업의 확인 및 문서 보관

이는 **선택 우선순위**이지 프로젝트나 모든 Agent를 일괄 직렬로 실행하는 장벽이 아니다. 독립 작업은 실행 자원·Git 안전 조건이 허용하면 동시에 진행한다. 재시작 시 미완료 기존 작업을 우선 잇고, 이어갈 작업이 없거나 실행 불가라면 신규 작업을 선택한다.

### 2. Requirement 작성과 계획 PR

사용자는 Requirement를 작성·수정하고 base에 반영한다. Planner는 최신 Requirement의 전문·Acceptance Criteria, 실제 구현, 활성·완료 ExecPlan, 의존성 및 열린 계획 PR을 비교한다.

- Requirement 변경 시 영향받는 목표를 평가하고 **현재 확인 가능한 전체 작업을 한 번의 계획에 도출**한다. 동일 구현을 중복하는 ExecPlan을 만들지 않는다.
- 신규·변경 ExecPlan과 필요한 선행 관계를 계획 PR로 제안하며 여러 Requirement를 묶을 수 있다.
- 열린 계획 PR이 관련 범위를 다루면 가능한 한 같은 PR에서 갱신하고 사용자 편집을 보존한다.
- 계획 브랜치 이름은 `loop-manager/plans/{short-summary}`를 기본으로 한다.
- 최초 계획의 완전성을 전제하지 않는다. 구현 중 새로운 제약이나 미충족 조건이 발견되면 필요한 계획을 추가한다.

계획 PR을 Merge하지 않고 Close하면 동일한 입력·제안을 자동으로 반복 생성하지 않는다. **그 뒤 관련 문서가 실제 수정되면** 최신 변경을 기준으로 새 계획 PR을 제안한다.

### 3. 계획 확정과 문서 수정

**base의 유효한 ExecPlan을 자동 실행 기준으로 삼는다.** 계획 PR을 사용자에게 검토받아 Merge하는 것이 일반적이지만, 사용자가 base에 직접 반영한 ExecPlan도 실행 가능하다.

사용자는 Requirement·ExecPlan을 base, 계획 PR 브랜치 또는 관련 구현 브랜치 등에서 제한 없이 수정할 수 있다.

- **base 수정**: 최신 확정 목표·계획을 관련 미완료 작업에 반영한다.
- **계획 PR 수정**: 미확정 후보에 반영한다. base에 없는 신규 계획을 그 PR만으로 실행하지 않는다.
- **구현 브랜치 수정**: 해당 G의 사용자 편집과 작업물을 보존하고 구현 조건·검증에 반영한다. 다른 G의 확정 계획은 base가 갱신되기 전에는 변경하지 않는다.
- **기존 실행 중 문서 수정**: 안전한 경계에서 변경 영향을 확인하고 필요한 단계부터 같은 G에서 이어간다. 구현 PR이 있으면 필요한 재작업 동안 Draft로 전환한다.
- **완료된 G의 신규 목표 변경**: 완료 기록을 소급 수정하지 않고 후속 작업을 계획한다.

서로 다른 브랜치의 변경은 가능한 경우 Merge하고 사용자 편집과 유효한 목표를 함께 보존한다. R-ID 우선순위는 **서로 다른 Requirement 내용의 명시적 충돌**에 적용하며, 동일 ExecPlan의 서로 다른 편집을 무조건 높은 ID 규칙으로 해결하지 않는다. 중요한 의미 충돌은 자동 조정할 수 없는 경우만 사용자 판단을 요청한다.

### 4. 구현·검증·PR 게시

base의 유효한 ExecPlan은 의존성과 현재 조건을 충족하면 실행한다.

1. Worker가 구현과 관련 테스트를 작성하고 필요한 targeted test로 교정한다.
2. Manager가 프로젝트에서 정한 필수 Verify를 실행한다.
3. Reviewer가 현재 후보의 코드·명세·검증 결과를 독립적으로 검토한다.
4. 실패·지적 사항은 기존 G의 Worker 교정으로 되돌린다.
5. 유효한 Verify·Review 성공 뒤 구현 PR을 생성하거나 갱신한다.

새로운 제품 목표·중요 정책 선택이 필요하면 사용자의 판단을 받는다. 구현 PR은 사용자가 검토해 Merge하고, 그 실제 Merge를 확인한 뒤 G를 완료 처리한다.

### 5. 완료 확인·보관

구현 PR이 실제 Merge된 ExecPlan은 원본 ID·최종 내용을 보존하며 `docs/plans/archive/`로 이동한다. 작업이 진행 중이어도 독립적으로 이동할 수 있으며 일시 실패 시 완료 사실은 유지하고 보관만 재시도한다.

연결된 ExecPlan이 모두 완료되거나 이미 구현으로 충족되어 더 필요한 G가 없는 Requirement는 Planner가 **최신 Requirement의 전체 Acceptance Criteria와 실제 구현·테스트**를 다시 확인한다.

- **모두 충족**: 해당 R을 완료하고 `docs/requirements/archive/`로 이동한다.
- **미충족**: 필요한 추가 ExecPlan만 계획 PR로 제안한다. 완료된 G를 되살리거나 중복 구현하지 않는다.
- **판단 불충분·사용자 결정 필요**: 완료를 보류하고 근거와 필요한 조치를 보존한다.

각 G Merge 때마다 불필요하게 Planner를 호출하지 않는다. 관련 작업을 모두 소진했을 때 재확인하되, 그 이전에 실제 Requirement 변경·중대한 누락 발견이 있으면 영향받는 범위에 대해 앞당겨 재계획할 수 있다.

보관 문서는 과거 근거이며 새로운 활성 R·G로 자동 복귀하지 않는다. 별도 후속 목표에는 새로운 ID를 사용한다. 보관 이동·이름 변경·일시 조회 실패를 삭제나 취소로 오인하지 않는다.

## Business Rules

### Requirement·ExecPlan 삭제와 취소

활성 Requirement 또는 ExecPlan이 **확실히 삭제·철회**된 경우만 관련 미완료 작업을 취소한다.

- Requirement 철회 시 연결된 G가 다른 유효 목표에도 필요한지 확인하고 공유 작업의 남은 범위를 유지한다.
- G 취소 시 신규 실행·다음 단계 진입을 중단하고 진행 중 Agent·Verify의 안전한 종료 또는 반환을 확인한다.
- 불필요해진 미Merge 구현 PR은 기존 작업물·커밋·이력을 보존하며 안전하게 Close할 수 있다. 이미 Merge된 결과는 취소로 소급 철회하지 않는다.
- 취소된 G-ID는 재사용하지 않는다. 취소된 작업을 단순 재시작만으로 다시 실행하지 않는다.
- 취소 때문에 다른 G의 의존성이 더는 충족될 수 없으면 후속 작업의 유효성·의존성을 다시 계획한다.

원격 조회 실패, 이름 변경, archive 이동, 미확정 PR의 일시적인 내용 차이를 철회로 추정하지 않는다.

### 작업 우선순위와 동시 실행

기존 작업의 복구·교정·재개를 일반 신규 구현보다 우선한다. 차단 원인이 해소된 작업은 계속 진행할 수 있어야 하며, 같은 우선순위의 신규 작업이 무기한 대기하지 않도록 한다.

- Worker와 Reviewer는 전체 프로젝트의 **공통 AI 실행 한도**를 공유한다.
- Verify는 별도 자원으로 전체 프로젝트에서 **동시에 하나만** 실행한다.
- 초기 모델에서 한 프로젝트의 Worker는 동시에 하나로 제한하되, 서로 독립적인 G는 Worker→Verify→Review의 다른 단계에서 겹쳐 진행한다.
- 한 G가 Verify를 대기·실행하는 동안 다른 G의 Worker 또는 Reviewer를 실행할 수 있다.
- 실제 작업·검증 대상은 G별로 격리하며 동일 Git 작업 자원에서 경쟁하는 쓰기는 조율한다.
- PR의 사용자 Merge 대기·차단·순번 대기는 실제 Worker·Reviewer·Verify 실행 자원을 점유하지 않는다.
- 독립 프로젝트와 독립 G를 다른 작업의 실패·충돌 복구 때문에 불필요하게 중단하지 않는다.

### Verify와 Reviewer

**Verify는 등록 프로젝트가 정의한 명령·검증 기준을 사용한다.** Loop Manager는 프로그래밍 언어·프레임워크·테스트 러너의 형식에 종속되지 않는다.

- 해당 프로젝트는 검증에 필요한 명령·환경·의존성을 제공한다. 실행할 수 없거나 필수 결과를 확인할 수 없다면 성공으로 취급하지 않는다.
- Worker의 관련 targeted test 이후 **필수 Verify → 독립 Reviewer**를 기본 순서로 한다. 기본 흐름에 별도의 영향 분석 기반 부분 Verify 또는 선행 Reviewer 단계를 두지 않는다.
- 게시 직전의 후보와 현재 문서·검증 근거가 일치해야 한다. 실제 입력 변경이 없고 유효한 성공 결과가 확인되면 같은 Verify·Review를 반복하지 않는다.
- Verify 명령 자체의 내부 병렬 실행은 프로젝트의 도구에 위임한다. Manager는 전역 Verify 실행 수만 제한하며 공통 테스트 모듈 분산 엔진을 강제하지 않는다.
- 순번·자원 대기 시간과 실제 검증 시간을 구별해 설정된 실행 시간 상한을 적용한다.
- 실패·타임아웃·중단 시 하위 프로세스 종료를 확인하고 불완전한 결과·종료 불명 상태를 PASS로 취급하지 않는다. 실패는 같은 G에서 교정한다.
- Reviewer는 구현·명세·테스트 결과를 읽고 승인 또는 구체적 교정 의견을 반환한다. 새로운 정책 결정은 사용자에게 전달한다.

기존 영향 분석 기반 부분 Verify와 복잡한 공통 병렬 검증 조율은 이 재설계의 기본 필수 조건이 아니다. 필요성과 효과가 확인된 프로젝트별 최적화는 검증 계약 안에서 사용한다.

### 계획·구현 PR 충돌 및 Draft

GitHub가 제공하는 PR의 Merge 충돌 판단을 기준으로 삼는다. **PR 생성 또는 head/base 변경 시에만** 충돌 상태를 새로 조회하며 결과 미확정·실패 때만 필요한 재조회를 한다. PR의 Open·Close·Merged 상태 동기화는 충돌 조회와 별개다.

- 충돌이 확정된 PR만 최신 base를 해당 작업 브랜치에 **Merge**하여 복구한다. 충돌이 없다면 base 전진만을 이유로 Merge·Rebase·Verify를 반복하지 않는다.
- 계획 PR의 문서 충돌은 Planner가, 구현 PR의 코드 충돌은 Worker가 담당한다. 사용자 변경과 상위 명세를 보존하고, 자동 해결이 불가능한 의미 충돌만 사용자에게 전달한다.
- CI 실패·승인 미충족·브랜치 최신화 요구는 실제 Git 충돌과 구분한다.
- 복구 뒤 필요한 검증·Review와 GitHub의 충돌 해소를 확인한다. 안전하게 해결할 수 없으면 영향받은 계획 PR 또는 G만 차단하고 사용자에게 일반 알림을 보낸다.

이미 열린 구현 PR의 **관련 계획 변경·충돌·검증 무효화로 추가 작업이 필요하면 Draft로 전환**한다. 기존 PR과 G를 유지해 보완·검증·Review를 진행하고, 다시 준비되면 Ready for review로 전환하여 신규 검토 요청 일반 알림을 보낸다. 단순 설명 수정이나 충돌 없는 base 변경만으로 Draft로 바꾸지 않는다. 복구 실패 알림은 차단 알림에 통합하며, 동일 후보의 Draft 해제·충돌 해소 사건은 중복 통지하지 않는다.

### Git 안전성

작업 브랜치 통합은 **Merge 우선**이며 게시된 브랜치의 자동 Rebase·Force push·Reset을 기본 복구 수단으로 사용하지 않는다.

- 사용자 checkout·타 G 작업 공간 및 다른 사람의 커밋을 임의로 수정·삭제·덮어쓰지 않는다.
- 각 작업의 원격 브랜치·PR·커밋 소유권과 실제 최신 상태를 확인한 후 게시한다.
- Git이 자동 병합하지 못한 코드 충돌은 Worker가, 계획 문서 충돌은 Planner가 허용 범위 안에서 교정한다.
- 유효한 양쪽 변경을 안전하게 보존할 수 없는 경우에만 해당 작업을 보류하고 사용자 판단을 요청한다.
- 기존 PR 안의 Merge 커밋은 유지하며, 최종 base 반영에는 사용자의 Squash and merge를 권장한다.

### 실패·중단·새 환경 복구

프로그램 재시작 시 저장된 작업 단계·미완료 Git 효과와 실제 원격 브랜치·PR 상태를 대조해 **마지막 확정 지점 이후부터 재개**한다. 이미 완료한 commit·push·PR 생성·Merge를 반복하지 않는다.

- 검증된 성공 근거만 재사용하고 근거 부재·입력 변경에는 필요한 단계부터 재실행한다.
- 일시 오류나 안전한 자원 대기는 상태를 보존하고 이후 재시도한다. 실제 자동 복구 불가·필수 사용자 결정이 확정된 작업만 차단한다.
- 차단 해제 후 기존 자료를 보존해 이어가고, 관계없는 작업은 계속 진행한다.
- 종료 불명 Agent·Verify·Git 효과는 새 실행에 안전하다고 가정하지 않는다.
- 새로운 환경에서 로컬 DB가 없어도 **유효한 원격 관리 브랜치·ExecPlan·GitHub PR 이력**으로 기존 미완료 작업을 연결하고 완료·archive 상태를 다시 확인한다.
- 새 환경은 이전 Agent session 또는 과거 Verify·Review 승인 근거를 임의 복원하지 않는다. 원격에 올리지 않은 로컬 전용 작업물의 복구는 보장하지 않는다.
- 환경 이전은 이전 실행이 멈춘 **순차 인수**를 기본으로 하며 여러 환경의 동시 Writer 실행은 지원하지 않는다.

완료된 G·R의 archive가 일시 지연되어도 사실로 확인한 완료와 독립 작업 진행을 뒤집지 않는다. archive 재시도는 새 작업 실행이나 중복 문서 생성을 일으키지 않는다.

### Telegram 알림

등록된 모든 프로젝트가 **Manager 공통 전송 큐**를 사용하고, 전송은 프로젝트의 단계·차단 여부와 독립적으로 처리한다.

| 사건 | 알림 |
|---|---|
| 신규 ExecPlan 구현 시작 | 무음 |
| 차단된 ExecPlan의 실제 재개 | 무음 |
| 계획 PR 신규 등록 | 일반 |
| 구현 PR 신규 등록 | 일반 |
| 기존 구현 PR의 Draft 해제·재검토 요청 | 일반 |
| 구현 PR의 충돌 자동 해소 | 일반 |
| ExecPlan 또는 프로젝트의 최종 차단 확정 | 일반 |

PR 알림에는 링크와 현재 검토 행동을, 차단 알림에는 실제 원인·보존 상태·필요한 사용자 조치를 포함한다. 자동 재시도 중의 일시 오류·단계 전환은 알리지 않는다. 동일 사건·동일 후보의 재조회나 재시작으로 중복 발송하지 않고, 충돌 복구가 Draft 해제와 같은 사건이면 하나의 일반 알림으로 통합한다. 전송 실패는 개발 작업을 막지 않으며 미전송 메시지는 이후 재시도한다.

### 사용자 통제

사용자는 Requirement·ExecPlan을 직접 수정하고, 프로젝트 자동 실행을 중단·재개하며 현재 작업·차단 원인·PR 링크를 확인할 수 있어야 한다. 중요한 제품 의사결정 및 계획·구현 PR의 최종 Merge는 사용자에게 남는다.

## Completion

- **ExecPlan 완료**: 연결된 구현 PR의 실제 Merge가 확인됐다. 최종 문서는 `docs/plans/archive/`로 보존한다.
- **Requirement 완료**: 관련 작업을 소진한 뒤 최신 유효 Acceptance Criteria가 충족됐다. 최종 문서는 `docs/requirements/archive/`로 보존한다.
- **프로젝트 완료**: 활성 Requirement의 충족이 확정되고 실행할 미완료 작업·미해결 사용자 판단이 없다. 이후 새 목표가 들어오면 다시 계획한다.

보관된 문서는 신규 작업 대상이 아니며, 동일 R-ID·G-ID를 재사용하지 않는다.
