# [R-091] 프로젝트 공정 배정과 우선순위 기반 병렬 작업

## Summary

구현·Review의 실제 동시 실행 수는 전체 프로젝트가 공유하는 한도로, verify 대기까지 포함한 관리 대상 수는 프로젝트별 한도로 제한한다. 프로젝트 DB의 `max_tasks_per_project`는 기본 0으로 config의 같은 이름 기본값을 따르고, 양수이면 개별 상한으로 사용하며 CLI로 변경한다. 명시적 운영 명령은 관리 한도와 무관하게 수락·상태 반영하며 필요한 관리 자리는 현재 작업 순서가 가장 늦은 대상을 보존 대기로 옮겨 확보한다. 실행 중 호출은 안전하게 반환하도록 두고, 수락된 수동 제출과 명시적 차단 해제의 우선 배정 후 RETRY와 기존 자동 작업을 이어가며, 신규 배정은 프로젝트별 한 자리씩 먼저 배정한 뒤 여유 자리를 전역 유효 우선순위로 채운다. verify는 별도 전체 상한을 설정해 기본 1에서 직렬 실행하며 다른 작업과 겹칠 수 있다. 모든 작업의 순번 대기는 timeout에서 제외하고 실제 실행 시간으로 판정하며, 신뢰된 상위 verify와 하위 runner의 확인된 자원 대기를 일관되게 반영한다. 차단 계획은 관리 개수에서 제외하고 개별 작업 실패는 상태를 보존해 같은 실행에서 재개하고 실제 차단·자원 대기와 구분한다. Git 재검사는 해당 작업 자원에 한정하고 외부 관측 중 DB 쓰기 잠금을 유지하지 않는다. 같은 운영 DB의 읽기·쓰기는 공통 접근 경계에서 짧은 처리 단위로 직렬화하고 경합은 실패 횟수를 소비하지 않는 순번 대기로 처리한다. 차단 재평가는 대상 계획의 실행·복구 소유권으로 격리하고 입력 변경은 사유별 재검사의 계기로만 사용한다. 작업별 실행 원본은 planning·프로젝트 대표 투영과 분리해 보존하고 상태 혼선의 복구는 R-055를 따른다. 계획 차단은 독립 작업을 막지 않으며 Planner 필요 시 해당 프로젝트, runtime 교체 시 해당 runtime 전체의 새 배정을 중단하고 실행 중 호출이 반환한 뒤 조율한다. runtime 원격 코드 관측은 대기 중 반복하지 않고 R-023의 최초·30초 TTL이 적용된 실제 단계 진입에서 수행하며 확정된 종료 결정은 재사용한다. 동일 원인·입력에서 재시도와 대기만 반복하는 작업은 진전 부재를 판정해 무의미한 재실행을 보류하고 R-053에 지속 장애 근거를 전달한다. planning·게시 해제와 원인 작업의 복구가 서로의 완료를 기다리는 순환을 막고, 허가된 미완료 복구와 조건 재평가의 실행 경계를 유지한다. 미확정 게시가 없는 유지보수 주기에서도 수락된 수동 제출·명시적 차단 해제의 재진입을 허용하되 확정 범위·완료 판단은 유지한다. 기존 dependency·소유권·필수 검증·게시·중단 복구 조건은 유지한다.

## Context

변경 전에는 프로젝트별 변경 실행을 하나로 제한하고 `max_workers`로 동시 프로젝트 수를 제한했다. verify를 기다리는 동안 같은 프로젝트의 독립 구현·Review도 함께 기다리므로 모델 호출과 로컬 검증을 겹칠 기회가 줄어든다.

단순히 모든 READY를 우선순위순으로 실행하면 높은 우선순위 작업이 많은 프로젝트에 자리가 집중될 수 있다. 일반 신규 작업은 실행 가능한 프로젝트에 먼저 한 자리씩 배정하고, 여유 자리만 전체 작업 우선순위로 채워 프로젝트 간 진행 기회와 처리량을 함께 확보한다. 수락된 수동 제출은 지연될수록 최신 base 반영·충돌 교정·재검증 비용이 커질 수 있으므로 그 배정보다 먼저 처리한다. 또한 verify 대기를 실제 구현·Review 실행으로 계산하면 실행 여력이 있어도 다음 작업을 시작하지 못하므로, 실제 실행 수와 대기를 포함한 관리 대상 수를 따로 제한해야 한다. 이 Requirement는 프로젝트별 단일 변경 실행을 전체 실행 한도와 프로젝트별 관리 한도로, 여러 프로젝트의 동시 verify 허용을 기본 직렬·설정 가능한 실행 상한 정책으로 변경한다.

## Requirement

### 실행 한도와 관리 대상 한도

| 자리 | 계산 대상 | 한도 |
|---|---|---|
| 구현·Review 실행 자리 | 실제 실행 중인 Worker의 구현·교정과 Reviewer 호출. 한 작업에서 두 역할을 동시에 실행하지 않는다. | 전체 프로젝트가 공유하는 실행 상한 하나를 설정한다. |
| 관리 자리 | 관리 대상으로 배정한 뒤 구현·교정·Review의 실행 및 실행 대기, verify 대기·실행과 게시를 이어가는 작업. | 프로젝트 DB의 개별 상한을 사용하며, 저장값 0이면 config 기본값을 따른다. |
| verify 실행 자리 | 실제 실행 중인 부분 또는 전체 verify. | 전체 프로젝트가 공유하는 별도 상한을 설정하며 기본 1이다. 구현·Review 실행 자리는 사용하지 않는다. |

- `[loop].max_workers`는 전체 구현·Review 동시 실행 상한으로 사용하고 기본값 3을 유지한다. `[loop].max_tasks_per_project`는 프로젝트 DB가 기본값 사용을 선택했을 때 적용하는 관리 대상 상한이며 기본 1이다. `[loop].verify_concurrency`는 전체 verify 동시 실행 상한이며 기본 1이다. 세 config 설정은 모두 양의 정수이고 기존 설정 파일도 계속 읽는다. 설정 예시·안내·조회에는 각 상한의 의미와 기본값을 명시하며, 프로젝트별 구현·Review 실행 한도나 전체 관리 대상 한도·별도의 동시 프로젝트 수 제한은 추가하지 않는다.
- 일반 작업은 ExecPlan 하나가 관리 단위 하나이고, 기존 수동 제출 묶음은 공유 후보·branch·worktree를 가진 한 관리 단위다. 묶음 구성 G를 따로 병렬 선택하거나 자리를 중복 계산하지 않는다. 아직 관리 대상으로 선택하지 않은 READY 전체를 관리 자리 점유로 세지 않는다.
- 일반 자동 작업의 새 관리 대상은 그 작업을 포함한 해당 프로젝트의 관리 개수가 상한 안일 때만 배정한다. 명시적 운영 명령의 수락·상태 반영과 관리 자리 확보는 아래 우선 수용 규칙을 따른다. 실제 Worker·Reviewer 호출은 관리 대상 중 해당 단계의 실행 조건을 충족한 작업에 한해 전체 실행 상한 안에서 시작한다. 관리 대상 배정만으로 실행 자리를 예약하거나, 실행 자리가 없다는 이유로 해당 프로젝트의 관리 한도를 넘기지 않는다. 한 프로젝트에 실행 가능한 작업만 남으면 관리 한도 안의 복수 작업이 전체 실행 자리를 사용할 수 있으며 별도 프로젝트별 실행 상한으로 제한하지 않는다.
- 구현·Review 호출의 종료 또는 미시작을 확인하면 해당 실행 자리를 해제한다. 다음 단계나 교정을 기다리는 동안에는 관리 자리만 유지하고, 실행을 재개할 때 실행 자리를 다시 배정받는다. verify 대기·실행과 게시도 구현·Review 실행 자리를 점유하지 않는다. 관리 한도에 도달해도 이미 관리 중인 작업은 새 관리 자리 없이 다음 단계·교정을 이어갈 수 있다.
- 안정된 PR의 Merge 대기, PLAN_BLOCKED와 수동 구현 대기는 관리 자리를 점유하지 않는다. PLAN_BLOCKED는 미완료 rebase 등 checkpoint·호출 예약이 남아 있어도 관리 개수에서 제외한다. 작업물·checkpoint·자원 예약은 보존하며 자동 후속 처리·충돌 복구와 자동 재평가에 따른 차단 해제 후 실행은 다시 관리 한도를 확인해 배정받는다. 사용자가 명시한 차단 해제 자체는 관리 한도와 독립적으로 반영하고, 후속 실행에 필요한 자리는 우선 수용 규칙으로 확보한다. 종료 불명 writer·verify의 실제 실행 자리와 미확정 Git operation·게시의 소유 예약은 보존하며, 차단되지 않은 작업의 관리 자리는 기존 조건을 따른다. 게시·Git 조작은 기존 자원별 소유권과 배타 조건을 별도로 지킨다.
- 상한을 낮춰도 실행 중 호출을 강제 종료하거나 관리 중인 작업을 삭제하지 않는다. 구현·Review 또는 verify 실행 상한을 초과한 동안에는 해당 종류의 새 실행을 보류하고, 관리 상한을 초과한 프로젝트는 새 관리 대상만 받지 않는다. 이미 관리 중인 작업은 각 실행 상한 안에서 계속 진행해 관리 자리를 비울 수 있어야 하며, 한 프로젝트의 관리 한도 초과만으로 다른 프로젝트의 배정을 막지 않는다.

### 명시적 운영 명령의 우선 수용과 관리 자리 교체

- 수동 구현 제출·차단 해제 등 명시적 운영 명령의 유효성 검사·수락·상태 반영은 프로젝트 관리 대상 한도가 가득 찼다는 이유로 거부하거나 다음 Manager 실행까지 미루지 않는다. 조회·pause·취소처럼 실행 관리 자리가 필요 없는 명령에 자리를 요구하지 않는다. 실제 명령의 권한·입력·dependency·소유권·안전 조건과 DB 접근 조율은 유지한다.
- 명령 대상의 후속 실행에 관리 자리가 필요하고 한도가 가득 차면 같은 프로젝트에서 현재 관리 중인 단위 중 작업 순서가 가장 늦은 단위를 보존 대기로 옮긴다. 대상 선택은 현재 배정 정책의 역순으로 하며 수동 제출의 최초 수락 순서, 명시적 차단 해제의 수락 순서, RETRY 순서, 기존 작업·일반 신규 작업의 유효 우선순위와 동순위 결정 규칙을 재사용한다. 다른 프로젝트의 작업은 밀어내지 않고, 공유 수동 묶음은 한 단위로 처리한다.
- 밀려난 단위는 관리 자리만 반납한다. 기존 단계·후보·branch·worktree·session·checkpoint·미완료 rebase·결과·실패·사용량·원래 배정 순서는 보존하며 미착수 READY·취소·실패·차단으로 바꾸지 않는다. 관리 대기 자체는 timeout·교정 횟수를 소비하지 않고 여유가 생기면 기존 배정 순서로 재진입한다. 새로운 요청 없이 재시작 뒤에도 대기와 우선 수용을 이어간다.
- 실행 중인 Worker·Reviewer·verify와 미확정 Git·게시 전이는 강제 종료하거나 실제 실행 자리·소유 예약을 회수하지 않는다. 선택된 단위의 새 후속 배정을 멈추고 현재 호출·전이가 안전하게 반환한 경계에서 관리 자리를 넘긴다. 명령의 수락·차단 해제는 그 반환을 기다리지 않으며, 실제 후속 실행만 자리 인계와 자원 확인을 기다린다. 종료 불명에는 기존 안전 보호와 원인을 보존하고 독립 작업은 계속한다.
- 여러 명령이나 한 명령의 여러 대상은 모두 수락·상태 반영하되 관리 한도 안에서 순서대로 실행한다. 수락된 수동 제출의 기존 우선순위를 유지하고, 명시적 차단 해제의 관리 재진입은 그 다음·일반 RETRY보다 먼저 수락 순서로 배정한다. 반복 명령은 같은 대상을 중복 등록하거나 최초 순서를 바꾸지 않는다. 관리 자리 교체와 명령 반영 중 경합·중단에서는 이중 배정·작업 유실 없이 확정된 지점부터 복구한다.
- 활성 유지보수의 prerequisite·refactoring·후속 확인 범위가 확정됐고 미확정 게시가 없는 안전한 경계이면, 수락된 수동 제출과 명시적 차단 해제 대상은 그 범위 밖에서도 재개할 수 있다. 유지보수 범위·dependency·완료 기준을 바꾸거나 차단된 유지보수 작업을 성공으로 처리하지 않는다. 일반 신규 작업의 범위 제한은 유지하고, 미확정 유지보수 게시·planning 소유권·실제 공유 자원 충돌은 보존한다. 수동 재개는 이미 진행 중인 구현·교정·verify·Review·게시 단계를 저장된 최초 제출 단계로 덮어쓰지 않는다.
- 우선 수용은 관리 자리 배정만 바꾼다. 구현·Review 및 verify의 실제 동시 실행 상한, pause·dependency·필수 검증·실제 차단 원인 확인·Git 소유권 조건을 면제하지 않는다. 현재 명령의 수락 여부, 밀려난 대상과 순서의 근거, 자리 인계 대기와 실제 시작 여부를 조회·로그에서 구분할 수 있어야 한다.

### 프로젝트별 관리 한도 저장과 기본값

- 등록 프로젝트의 운영 DB 정보에 정수 `max_tasks_per_project`를 저장하고 DB 기본값은 0으로 둔다. 저장값이 양수이면 해당 프로젝트의 관리 상한이며, 0이면 Manager가 읽은 `[loop].max_tasks_per_project`를 사용한다. 이하의 프로젝트별 관리 한도는 이렇게 계산한 유효 상한이다. DB의 0은 작업 중지나 무제한을 뜻하지 않고, config의 0·음수·정수가 아닌 값과 DB의 음수·정수가 아닌 값은 거부한다.
- 새 프로젝트와 해당 항목이 없는 기존 DB의 프로젝트는 0으로 초기화한다. 등록·스키마 갱신·실행 때 config의 현재 숫자를 DB에 복사해 고정하지 않으며, 이미 저장된 프로젝트별 양수와 기존 등록 정보·작업·실행 이력은 보존한다. 반복 초기화에서도 개별 설정을 0이나 config 값으로 덮어쓰지 않는다.
- DB 값이 0인 프로젝트는 config를 다시 읽는 실행부터 변경된 기본값을 따르고, 양수인 프로젝트는 config 변경과 관계없이 그 값을 유지한다. 개별 값을 다시 0으로 바꾸면 config 상속으로 돌아간다. 값 변경에 따른 다음 배정은 현재 유효 상한을 사용하며, 상한 축소 시 기존 작업을 보존하는 위 조건을 유지한다.
- 개별값 설정·변경·0 복귀는 [R-076의 프로젝트별 관리 한도 설정 CLI](%5BR-076%5D%20운영%20명령어와%20상태%20조회%20및%20Skill%20지원.md#프로젝트별-관리-한도-설정)로 제공한다. 저장·검증·적용 시점·조회와 추후 Loop Manager 관리 Skill의 안내는 같은 계약을 사용한다.

### 프로젝트별 기본 배정과 추가 배정

- 배정 대상은 해당 실행에서 선택한 등록 프로젝트 중 pause·프로젝트 차단·dependency·draft·catalog·유지보수·소유권·안전 조건을 통과한 후보가 있는 프로젝트다. 선택 범위 밖 프로젝트나 해당 배정 단계의 후보가 없는 프로젝트를 위해 빈 자리를 예약하거나 다른 프로젝트를 기다리게 하지 않는다.
- 안전한 배정의 전제인 종료 확인·미확정 Git operation·게시 결과 확인 등 필수 정리를 먼저 수행한다. 이후 관리 자리·구현/Review 실행 자리·verify 실행 자리마다 실행 가능한 후보를 수락된 수동 제출 → 명시적 차단 해제의 관리 재진입 → RETRY 우선 재배정 → 이미 시작한 일반 자동 작업의 단계 재개·교정·복구 → 일반 신규 작업 순서로 선택한다. 실행 중 호출은 선점하지 않으며, 신규 후보의 우선순위를 이유로 기존 작업을 미착수로 되돌리거나 교체하는 정책은 추가하지 않는다.
- 수동 제출 우선 대상은 [R-077](%5BR-077%5D%20G%20계획%20수동%20구현과%20R·코드%20일괄%20제출.md)의 유효하게 수락된 `manual complete/submit`이며, 프로젝트 구분 없이 제출 묶음의 최초 수락 순서로 선택한다. 반복 요청·교정·단계 전환·재시작으로 순서를 초기화하지 않는다. 우선 배정은 자동 교정·verify·Review·PR 게시까지 유지하고 안정된 PR의 Merge 대기는 실행·관리 자리를 점유하지 않는다. 수락 전 `MANUAL_WORKING`에는 적용하지 않는다.
- 수동 제출은 RETRY 재배정보다 앞서며 아래 일반 신규 작업의 프로젝트별 기본 배정보다 앞선다. 우선 대상이 관리 한도·dependency·자원·단계 조건 때문에 지금 진행할 수 없으면 다른 수동 제출과 일반 자동 작업을 계속 확인하며, 그 대상을 위해 빈 자리를 예약하지 않는다. 관리 한도 때문에 진행할 수 없으면 위 우선 수용 규칙으로 가장 늦은 관리 단위의 자리를 확보하며 한도를 초과해 새 실행을 시작하지 않는다. 구현·Review 자리가 비었지만 수동 제출은 verify만 기다리는 경우에도 독립 작업을 실행할 수 있다.
- 수동 제출과 기존 자동 작업의 실행 가능한 후속 처리를 배정한 뒤 남은 여유에 아래 기본·추가 배정 순서를 적용한다. 관리 배정에서는 현재 관리 작업이 없는 프로젝트를 먼저 선택하고, 신규 실행 배정에서는 지금 구현·Review 호출이 없고 착수 가능한 작업이 있는 프로젝트를 먼저 선택한다. verify 대기·실행 중인 작업만 있는 프로젝트는 관리 자리는 받은 상태지만 구현·Review 실행 자리를 받은 것으로 세지 않는다.
- 자리가 생길 때마다 해당 종류의 기본 자리가 없는 적격 프로젝트에 한 작업씩 먼저 배정한다. 기본 배정은 작업이나 호출의 완료를 기다리는 장벽이 아니며, 배정 가능한 프로젝트에 한 자리씩 배정한 뒤에는 즉시 추가 배정을 진행한다.
- 전체 구현·Review 실행 상한이 적격 프로젝트 수보다 작으면 아직 기본 실행 자리를 받지 못한 프로젝트부터 순환 배정한다. 같은 프로젝트가 호출을 빨리 끝내거나 Manager가 재시작되어도 등록 순서 앞쪽 프로젝트만 반복 선택되지 않게 배정 순서를 이어간다. 실행 중 호출은 다른 프로젝트에 자리를 주기 위해 선점하지 않는다. 관리 대상은 각 프로젝트의 한도 안에서 배정하며 전체 관리 수를 이유로 다른 프로젝트의 기본 배정을 보류하지 않는다.
- 기본 배정 후에는 프로젝트별 관리 한도에 여유가 있는 신규 후보를 프로젝트 구분 없이 유효 우선순위로 선택한다. 신규 관리 대상 선택과 착수 배정에서 프로젝트별로 여유 자리를 똑같이 나누거나 특정 프로젝트의 후보를 먼저 모두 소진하지 않는다. `critical → high → normal → low`와 미Merge dependency를 통한 기존 우선순위 상속을 재사용하고, priority 선언·dependency 자체는 변경하지 않는다.
- 한 프로젝트 안의 일반 신규 후보 선택은 기존 유효 우선순위·숫자 ExecPlan ID 순서를 유지한다. 프로젝트 간 동순위도 같은 후보·배정 상태에서 재현 가능한 순서로 결정한다. 다음 신규 배정의 빈자리가 생겼을 때 해당 종류의 기본 자리가 없는 적격 프로젝트가 있으면 추가 배정보다 먼저 선택한다. 기존 작업의 단계 재개·교정에서 실행 자리는 다시 배정받되 관리 단위는 중복 생성하지 않는다.

### 순번 대기와 실제 실행 시간

- Planner·Worker·Reviewer·verify를 포함한 모든 관리 작업에서 실행 자리·동시 실행 상한·프로젝트 순번·공유 자원 배정이나 예약을 기다리는 순번 대기는 해당 작업의 timeout을 소진하지 않는다. Manager와 runner가 확인한 순번 대기 구간과 실제 실행 구간을 구분해 기록하며, 실행 전 대기만으로 timeout·실패 횟수 증가·승격·차단을 만들지 않는다. 대기 중에도 상태 조회·pause·취소와 기존 안전 검사는 계속 처리한다.
- timeout은 실제 처리를 수행하는 구간의 경과 시간을 기준으로 판정한다. 준비·수집·복사·역할 호출·검증·결과 처리·정리 등 실행 중인 처리와 그 내부의 I/O는 계산한다. 실행 중 처리가 없이 배정만 기다리는 확인된 구간은 제외하며, CPU 사용 시간이나 추정 모델 생성 시간으로 바꾸지 않는다. 일부 자식이나 단계가 실제 실행 중이면 다른 자식의 배정 대기를 이유로 그 실행 시간까지 제외하지 않고, 병렬 자식의 시간을 더해 부모의 경과 시간을 중복 계산하지 않는다. 종료 불명이나 멈춘 처리를 순번 대기로 간주해 timeout을 우회하지 않는다.
- 같은 실행의 중간 순번 대기·재개에서는 이미 사용한 실행 시간을 보존하고 남은 예산을 이어간다. verify의 복사·WSL·Windows 핵심 회귀·정리는 계속 하나의 실행 시간 예산을 공유하며 단계 전환으로 예산을 초기화하지 않는다. 순번 대기 제외를 이유로 설정된 시간 한도를 자동으로 늘리거나 실제 실행 중 무출력·중단·자식 종료 확인의 기존 보호 조건을 제거하지 않는다.
- R-067의 실제 runner 통합 단계에서 상위 verify는 자신과 하위 runner의 동일 검증 범위를 하나의 실제 실행 시간 예산으로 판정한다. 하위 프로세스가 살아 있다는 이유만으로 확인된 순수 배정 대기를 처리 시간에 넣지 않으며, 신뢰된 관측으로 상위·하위 전체가 자원 배정만 기다리고 있음을 확인한 구간만 제외한다. 상위 준비·수집·결과 처리 또는 다른 자식의 실제 실행이 겹치는 시간과 관측 불명·heartbeat 단절·종료 불명은 제외하지 않는다. 상위·하위가 같은 대기 구간을 중복 제외하거나 중간 단계·재개·재시작으로 남은 예산을 늘리지 않는다.
- 배정 대기와 실행 시간의 연결은 신뢰된 상위 조율·진단 경계에서 확인해야 한다. 이를 위해 일반 테스트·예제 자식에 조율 인증값이나 시간 예산 제어 권한을 넘기지 않으며, 하위 runner의 자체 대기 기록·종료 근거와 상위 판정이 일치하지 않으면 성공으로 확정하지 않는다.

### verify 동시 실행 한도와 다른 단계의 병렬 진행

- 같은 Manager 자동 실행이 관리하는 전체 프로젝트의 부분·전체 verify는 공통 대기열에서 수동 제출 우선·RETRY 재배정 순서와 `verify_concurrency` 상한에 따라 실행한다. 기본 1에서는 직렬 처리하고, 2 이상에서는 독립 후보의 verify를 설정한 개수까지 동시에 실행할 수 있다. 공통 runner 연결 여부와 관계없이 Manager의 verify 호출에 적용하며, 각 verify의 종료 또는 미시작을 확인한 뒤에만 그 실행 자리를 다음 요청에 배정한다. 종료 불명에서는 실행 자리를 임의 회수하지 않고 기존 안전 오류·복구 조건을 적용한다.
- 실행 상한과 단계 조건이 허용하면 verify 대기·실행 중에도 관리 대상의 구현·읽기 전용 Review를 진행한다. verify 대기가 구현·Review 실행 자리를 붙잡아 두지 않는다. 같은 후보에 대해서는 기존 단계 순서와 입력 고정을 유지하며, 실행 중인 verify·Reviewer가 읽는 worktree를 Worker나 rebase로 동시에 수정하지 않는다.
- `verify_concurrency`는 verify 호출 수를 제한하며, 한 verify 안의 테스트 병렬도를 정하는 기존 `verify_parallelism`과 구분한다. 테스트의 실제 부하·메모리·예약·자식 종료 확인은 [R-065](%5BR-065%5D%20실제%20부하%20기반%20verify%20병렬%20실행.md)와 [R-067](%5BR-067%5D%20프로젝트%20공통%20verify%20실행%20규약.md)의 실행량 조율을 유지한다. verify 동시 실행 설정을 높여도 기존 자원 보호·예약 조건을 우회하지 않는다. 단독 runner나 다른 Manager·호스트까지 하나의 예약을 공유하는 기능은 추가하지 않는다.
- verify의 timeout은 위의 실제 실행 시간 기준을 따른다. 실패·취소·중단 뒤 요청·후보·진단을 보존하고 대기를 성공·생략으로 바꾸지 않는다. 자체 Windows verify는 WSL·Windows 핵심 회귀 두 단계와 정리 동안 같은 verify 실행 자리 하나를 유지한다. 단계 사이에 자리를 반납하거나 단계마다 중복 점유하지 않으며, 다른 등록 프로젝트의 실행 환경을 일괄 변경하지 않는다.
- [R-086](%5BR-086%5D%20영향%20기반%20부분%20검증과%20일반%20선행%20Review.md)의 부분 verify → 선행 Review → 실제 전체 verify 또는 전체 verify → Review와 성공 근거 조건은 그대로 유지한다. 다른 작업과 단계를 겹친다는 이유로 같은 후보의 verify·Review 순서를 바꾸거나 오래된 결과를 게시 승인에 사용하지 않는다.

### RETRY·계획 차단과 조율을 위한 배정 중단

- 한 단계가 끝나면 다음 실행 가능한 단계를 바로 배정에 연결한다. 일반 RETRY는 진행 중인 같은 작업으로 유지하고 해당 종류의 실행 대기열에서 수락된 수동 제출과 명시적 차단 해제의 관리 재진입 뒤에 재등록한다. 여러 RETRY는 재등록 순서를 따르며 일반 재개·신규보다 먼저 배정한다. 이미 실행 중인 호출을 선점하지 않고 실행 한도·verify 순번·필수 자원·안전 조건은 유지한다. 형제 작업이나 프로젝트 전체의 완료를 기다리는 장벽을 만들지 않는다.
- Worker targeted test 실패, 부분·전체 verify 실패와 Reviewer FAIL은 기존 교정 허용 범위에서 Worker 재시도로 연결한다. 실제 동일 테스트 연속 3회 실패 등 기존 최종 차단 조건은 유지한다. 새 테스트 실행 근거 부재나 실행별 교정·재시도 예산 소진만으로 다음 외부 실행까지 보류하지 않는다. 차단되지 않은 실패는 같은 실행에서 필요한 실제 재검증·교정으로 연결한다. 재시도에서 작업물·session·실패 이력과 관리 자리를 보존하고 새 관리 단위를 만들지 않는다.
- 단계 처리의 일반 예외는 작업별로 종류·상세 메시지·traceback을 보존하고 해당 작업의 DB 상태·checkpoint·소유권을 다시 준비해 RETRY 순서로 재시도한다. 연속 실패는 짧은 재시도 묶음의 한도와 재시도 대기로 제어하되, 실제 차단되지 않았다면 같은 실행에서 자동 재개한다. 단순 횟수 소진을 새 최종 차단으로 바꾸거나 재시작으로 실패 이력을 초기화하지 않는다. 작업 준비·결과 수집의 예외도 해당 작업의 오류로 기록하고 프로젝트 조율과 다른 작업 배정을 계속한다. Planner 배정 중단·runtime handoff·사용자 중단은 일반 예외로 삼키지 않는다.
- R-055의 Git 상태 변경은 단순 OID 불일치·현재 원격 이력 통합·진짜 관측 경쟁·조건 미충족으로 먼저 분류한다. 최신 상태로 재구성하면 진행 가능한 작업을 일시 RETRY/30초 대기로 밀지 않고 바로 다음 검증·게시 단계에 연결한다. 제한 재시도는 원격/PR/lease·자원 조건이 실제로 다시 관측될 수 있는 경우에만 사용한다. 과거 OID와 현재 입력의 고정 불일치, 같은 원인/입력의 무변화 검사, 정상 사용자 push를 반복 transient 실패로 재등록하지 않는다.
- 짧은 실행별 retry 묶음과 외부 실행 간 누적 진단은 분리하되 같은 원인·대상·실질 진행 표식에 대해 반복 횟수와 정체를 지속적으로 판단한다. 재시도 타이머 경과·로그 생성·같은 checkpoint 관측·런타임 재시작은 진전이 아니다. 새로운 원격/파일/검증 입력, 안전한 복구 전이 또는 외부 조건의 실제 해소만 다음 재시도의 근거로 삼는다. 동일 입력에서 무진전 반복이 확인되면 같은 실행 안의 busy loop 및 다음 실행의 동일 실패 재생을 억제해 해당 자원만 보존 대기시키고, R-053의 지속 장애 진단을 한 번 연결한다. 새 입력·상태 변화 또는 유효한 복구 요청이 오면 현재 조건을 확인한 뒤 같은 작업에서 재개하며 기존 실패·checkpoint·session을 임의로 초기화하지 않는다.
- 단계 실패의 비차단 재개는 실제 다음 단계로 진입할 때 R-023의 30초 TTL이 적용된 runtime gate와 캐시된 종료 결정을 확인한 뒤 기존 재배정 순서로 처리한다. runtime 교체가 필요하지 않으면 형제 verify·다른 작업 완료·다음 외부 실행을 기다리지 않는다. 외부 서비스 사용 한도·권한·필수 입력·종료 불명·공유 자원처럼 실제 미충족 조건이 있으면 해당 조건의 재확인 대기로 유지하고 해소 후 같은 실행에서 재개한다. 재시도·자원·호출 자리 대기 중에는 runtime 원격 조회를 반복하지 않되 독립 작업·운영 요청·사용자 pause·취소·이미 확정된 runtime 종료 결정을 계속 처리하고 같은 실패를 무대기 반복하지 않는다.
- PLAN_BLOCKED는 해당 계획만 배정 대상과 관리 개수에서 제외한다. 미Merge dependency 등 각 조건을 통과한 다른 작업은 같은 실행에서 시작·재개한다. PROJECT_BLOCKED와 종료 불명 호출·미확정 Git/게시의 실제 실행 자리·자원 예약 보존은 구분한다.
- 원격 base의 Requirement 등 명세 변경이나 Merge 후 완료 재평가 등으로 Planner가 필요하면 해당 프로젝트의 새 관리 편입과 모든 후속 호출 배정을 중단한다. 실행 중 호출은 강제 중단하지 않고 반환한 안전 경계에서 멈추며, verify·실행 자리 대기만 하는 작업은 새 호출을 시작하지 않고 저장된 단계로 돌려보낸다. PR 게시나 작업 전체 완료를 기다리지 않는다. 다른 프로젝트는 계속 진행할 수 있다.
- 해당 프로젝트의 실행 중 처리가 반환하고 종료·소유 상태가 확인되면 같은 실행에서 Planner를 실행한다. 결과 게시·catalog·DB 반영을 마친 뒤 저장한 작업을 재배정하며, planning 실패·사용자 판단은 기존 R-055·R-082의 독립 작업 허용 조건을 따른다. 작업이 계속 추가되어도 신규 편입으로 이 조율을 뒤로 미루지 않는다.
- R-023의 코드 입력 변경으로 runtime 교체가 필요하면 해당 runtime이 관리하는 전체 프로젝트에서 새 관리 편입·Agent·verify·후속 단계 배정을 중단한다. 실행 중 처리는 안전하게 반환·정리하고 상태를 보존해 handoff하고 주기 실행을 기다리지 않고 최신 runtime으로 자동 재시작한다. 프로젝트 Planner 대기와 runtime 전체 중단을 혼동하지 않고, 종료 불명 호출을 비었다고 추정하지 않는다.

### planning·복구 사이의 상호 대기 방지

- planning 게시·자리 해제의 보류 원인인 작업이 planning 점유 때문에 복구할 수 없는지 확인한다. 정상 단계의 배정 중단과 원인을 해소하는 복구의 허용 조건을 구분하며, planning·복구·게시·정리가 서로의 완료를 요구하는 순환을 만들지 않는다.
- 실제 자원 독립성이 검증되면 R-055·R-082대로 무관한 보류를 분리한다. 충돌 자원이 같으면 원인 작업의 현재 소유권·writer 종료·checkpoint·lease를 검증해 기존 복구를 수행할 안전한 경계를 확보하고, 그동안 경쟁하는 새 호출·게시를 배정하지 않는다. 일반 작업의 명세 반영 순서나 PROJECT_BLOCKED의 기존 복구 허용 범위를 우회하지 않는다. 안전한 복구가 불가능하면 상태를 보존하고 원인 소유자·충돌 자원·서로 기다리는 조건을 진단한다.
- 같은 관측의 중복 해제나 무의미한 호출을 억제해도 이미 허가된 미완료 복구의 다음 단계와 조건 재관측은 남겨 둔다. 관련 자원 반환·writer 종료·복구 전이·원인 교정은 문서 지문 변경 없이도 재평가 계기가 되며, 이 조건과 실제 진전은 R-055·R-053의 동일 원인 정체 판단에 연결한다.

### 운영 DB 공통 접근과 순번 대기

- 같은 운영 DB 파일을 사용하는 Manager의 프로젝트·작업 스레드, 별도 CLI·bootstrap·runtime 및 Agent 호출 기록의 읽기·쓰기는 공통 접근 경계를 따른다. 프로젝트·테이블·row가 달라도 DB 파일 하나의 접근 순서를 공유하며, 경로 표기 차이로 조율이 분리되지 않는다. 별도 상태 루트의 서로 다른 DB와 운영 DB를 읽어 만든 독립 snapshot의 후속 처리는 서로를 기다리지 않는다.
- DB 접근은 필요한 조회와 상태 확정을 묶은 짧은 처리 단위로 한 번에 하나씩 수행한다. SQL 문장 하나마다 차례를 반납해 관련 조회·갱신의 원자성을 깨뜨리지 않고, 처리 경계 밖으로 열린 조회 cursor나 미확정 transaction을 넘기지 않는다. 같은 처리 안의 중첩 호출은 그 소유권·연결·transaction을 이어 쓰며 다른 연결의 차례를 기다리는 자기 대기를 만들지 않는다. 호출 전체에 공유 연결 하나를 강제하거나 작업별 상태·TEMP 정보의 격리를 없애지 않는다.
- Git·원격 조회·Agent·verify·알림 전송과 다른 실행·자원의 배정 대기는 DB 접근 구간 밖에서 수행한다. 외부 처리가 필요하면 조회 결과를 확보하고 DB 차례를 반납한 뒤 수행하며, 결과 적용 때 새로 차례를 받아 현재 상태·소유권·generation을 재확인한다. 경쟁 변경은 보존하고 이미 완료한 외부 효과를 DB 재시도 때문에 반복하지 않는다.
- DB가 사용 중이면 기본적으로 순번을 기다린 뒤 현재 상태로 처리한다. 특정 작업의 반복 요청이 다른 대기 요청을 계속 밀어내지 않게 하고 기존 DB 접근의 제한 시간·취소·종료 요청을 적용한다. 대기나 DB 요청 재시도를 단계 실행 실패·Worker 교정·일반 RETRY 한도에 합산하지 않는다. 실제 Agent·verify가 실행되지 않은 대기는 실행 timeout을 소모하지 않으며, 이미 실행 중인 프로세스의 실제 시간과 기존 종료 확인은 유지한다.
- 접근 차례와 cursor·transaction의 수명을 지킨 뒤에도 생기는 일시적 SQLite 잠금 오류는 요청을 rollback하고 최신 상태에서 제한 재시도한다. 작업 준비·단계 처리·재시도 보류 기록·결과 수집·오류 기록에도 같은 경계를 적용한다. 대기·재시도 한도를 넘기면 해당 요청·작업만 상태를 보존해 재시도 대기로 두고 조율은 계속하며, 실제 차단 조건이 없으면 같은 실행에서 재개한다. 기록 저장도 실패하면 원래 오류와 저장 오류를 로그에 보존하고 저장 성공으로 표시하지 않는다. DB 손상·잘못된 SQL·권한 오류를 잠금 대기로 숨기지 않는다.
- [R-076](%5BR-076%5D%20운영%20명령어와%20상태%20조회%20및%20Skill%20지원.md)의 조회는 공통 경계에서도 읽기 전용 snapshot·부수 효과 금지를 유지하며 DB 생성·migration·journal 변경으로 우회하지 않는다. [R-077](%5BR-077%5D%20G%20계획%20수동%20구현과%20R·코드%20일괄%20제출.md)의 수동 준비·수락은 짧은 DB 사용 순번만 기다리고 같은 명령 실행에서 처리한다. 자동 작업·Agent·verify 전체의 종료나 다음 Manager 실행을 기다리는 장벽으로 바꾸지 않으며, 실제 계획·Git 자원·소유권 충돌의 기존 거부 조건은 유지한다.

### 독립 작업과 복구 경계

- 대상 ExecPlan의 단계·branch·worktree·소유권·session·후보·실패와 성공 근거는 해당 작업의 실행 원본에서 읽고 갱신한다. 프로젝트 대표 투영의 부재·교체나 일반·유지보수 planning의 자원 기록·정리·복원이 다른 작업 원본을 덮어쓰지 않아야 한다. planning 전환·게시·실패·취소·runtime 인계·재시작에서도 재개 대상과 작업별 상태를 보존하며, 대상이 확정되지 않으면 다른 작업이나 planning 값을 대신 사용하지 않는다. 이미 혼선이 생긴 실행 자원과 차단의 복구는 R-055를 따른다.
- 프로젝트에 다른 활성 작업이 있다는 이유만으로 차단 재평가를 미루지 않는다. 각 대상의 실행 중·종료 불명 호출, 같은 계획의 복구 예약, branch·worktree 공유와 실제 planning·공유 게시 소유권을 확인한다. 하나의 계획 재평가는 중복 수행하지 않고 다른 작업의 투영·차단·session·후보를 변경하지 않는다. 차단 해제 후 실행에는 관리 상한과 기존 dependency를 적용한다.
- ExecPlan 또는 Requirement 본문 변경은 재평가를 예약하는 신호이며 차단 해제 증거가 아니다. 병렬 조율 중에도 관리 여유가 생기면 저장된 원인별 재평가를 별도 작업으로 수행한다. 의미 판단의 대기가 다른 신규 배정을 멈추지 않으며 실제 재개는 기존 관리 배정 순서로 확정한다. 재평가 대상이 현재 실행·정리 중이면 소유권이 반환된 뒤 판단한다. 같은 입력은 한 실행에서 불필요하게 반복하지 않는다.
- `user_decision_required`는 최신 명세와 작업 본문을 근거로 기존 질문이 해소됐는지 읽기 전용으로 판단한다. 변경된 source의 현재 원문과 상위 명세의 뒷받침 인용·이유가 확인된 경우에만 재개하며, 필요한 선택·문서 간 충돌·불확실성은 질문과 차단을 유지한다. Planner 수정·질문 삭제·링크나 표현 변경을 사용자 승인으로 간주하지 않는다. 동일 입력의 판단과 원문 근거·기존 질문은 감사로 보존한다. 저장된 draft 판단 대기는 R-061의 사용자 출처·답변 검증 경로를 유지한다.
- 일반 `plan_input_invalid`는 현재 선언·경로·catalog 정합성을 재검증한다. rebase 관련 입력 차단은 새 문서 변경 없이도 checkpoint·실제 Git으로 다시 검사하며, 소유한 원래 HEAD에서 안전하게 시작할 수 있는 상태도 해당 차단 원인을 해소할 수 있다. 이때 미완료 rebase intent를 버리거나 완료·검증 성공으로 기록하지 않고 기존 시작·Worker·검증으로 이어간다.
- ownership·scope·미확정 Git 쓰기는 해당 원인의 현재 증거를, timeout·원격 branch 삭제 등은 기존 사유별 조건을 적용한다. 재평가 실패 시 원인·질문·checkpoint·작업물·감사를 보존하며 한 계획의 복구로 별개 계획·프로젝트 차단을 해제하지 않는다.
- 같은 프로젝트에서 병렬 실행하는 일반 작업은 각각 별도 branch·관리 worktree·후보·session·단계 결과·실패 이력을 가진다. 선행 ExecPlan의 실제 Merge, 수동 제출 묶음, 공유 Git 자원·문서 게시·planning의 배타 조건과 기존 유지보수 gate를 한도나 우선순위로 우회하지 않는다. Planner의 기존 직렬화도 유지한다.
- rebase의 반복 관측은 해당 작업 branch·worktree·등록 관계와 후보·index·명세·원격 PR·공유 config를 검증한다. 다른 작업의 무관한 branch 전진·worktree 등록 변화만으로 현재 작업을 변경된 상태로 판정하지 않는다. 해당 branch의 중복 등록과 현재 작업 자원·입력의 실제 변경은 계속 거부한다.
- rebase 완료·차단 해제의 Git·원격 재관측은 DB 쓰기 잠금 밖에서 수행한다. DB 반영은 짧은 transaction 안에서 작업 소유권·projection·checkpoint generation과 필요한 상태가 관측 전과 같은지 재확인해 원자적으로 적용하며, 경쟁 변경을 덮거나 외부 관측 실패를 성공으로 확정하지 않는다.
- 한 작업의 실패·차단·교정·종료가 다른 작업의 소유권·현재 단계·검증 근거를 덮거나 초기화하지 않는다. 중단·재시작 시 저장된 작업별 관리·실행 상태와 실제 writer·후보·예약을 대조해 같은 작업을 중복 시작하지 않고, 관리 대상·구현/Review 호출·verify 실행을 각각의 한도와 기본 배정에 반영한다.
- 다른 PR Merge나 원격 변경 뒤에는 기존 최신 입력 반영·충돌 복구·verify·Review 재사용·게시 조건을 작업별로 적용한다. 한 작업의 성공을 같은 프로젝트의 다른 후보 성공으로 사용하지 않는다. 수동 준비·요청 수락의 기존 병행 권한을 확대하지 않으며, 수락된 후속 자동 실행은 같은 한도와 배정 규칙을 따른다.
- 배정 판단은 Manager 코드가 수행한다. 로그에서 전체 구현/Review 실행 수와 상한, 프로젝트별 관리 대상 수와 유효 상한, 전체 verify 실행·대기 수와 실행 상한을 구별한다. 프로젝트 설정 조회에는 DB 저장값·유효 상한·config 또는 개별값 중 적용 출처를 표시한다. 수동 제출 우선·기존 작업 재개·신규 기본/추가 배정의 구분, 유효 우선순위와 실행 한도·관리 한도·단계 조건·verify 때문에 대기하는 이유를 확인할 수 있어야 한다.

## Acceptance Criteria

- planning 게시/해제가 다른 작업의 미완료 rebase를 기다리고 해당 복구가 planning 점유 때문에 거부되는 입력에서도, 검증된 원인 복구 또는 독립성에 따른 해제로 다음 단계에 도달한다. 같은 자원의 writer를 겹쳐 실행하거나 보존 근거를 삭제하지 않으며, 실제 안전 미확정이면 순환 관계·범위·다음 조건이 남고 같은 실패를 무진전 반복하지 않는다.
- 관련 자원 반환·writer 종료·복구 결과·원인 교정 후 문서 지문이 그대로여도 해당 원인을 재평가한다. 같은 관측의 중복 처리 억제가 허가된 복구를 영구 배제하지 않고, 독립 작업의 진행·무관한 runtime/branch 변화로 미해소 정체 이력을 초기화하지 않는다.

- 대표 작업 A와 실행 대상 B가 서로 다른 branch·worktree·단계·session·후보·결과를 가진 상태에서 일반·유지보수 planning으로 전환·반환해도 A와 B의 작업별 원본이 보존된다. planning 게시·실패·취소·runtime 인계 전후 중단·재시작과 대표 투영 부재에서도 B의 준비·재개·소유권 검사는 B의 상태를 사용하고, planning의 빈 branch나 worktree가 B에 저장되지 않는다. 대상 미확정·동시 상태 변경에서는 낡은 반영만 거부하고 기존 자원·작업물·기록을 보존한다.
- G-299 verify 중 G-298 Worker가 새 targeted test 근거 없이 실패를 보고해도 실제 차단 조건이 없으면 같은 실행에서 새 테스트 실행·교정을 재배정한다. 다른 작업의 verify 종료나 runtime 재시작을 요구하지 않는다. Worker·부분/전체 verify·Reviewer·게시·복구의 비차단 실패와 반복 일반 예외에도 같은 재개 조건을 적용한다.
- 실제 차단·사용자 판단·사용 한도·종료 불명·자원 대기는 우회하지 않고, 조건 해소 후에는 같은 실행에서 진행한다. 재시도 대기·자동 runtime 재시작에도 실패·교정·테스트 이력과 작업물·session·관리 소유권이 보존되며 무대기 실패 반복·중복 호출이 없다.
- 30초 이상의 순번·retry·사용량·Git 자원·종료 불명 대기 중 runtime 원격 조회는 0회이며, 다음 실제 단계 진입에서만 R-023의 공통 TTL을 적용한다. 별도 스레드에서 runtime 종료 필요 결정이 확정되면 기다리는 작업은 새 원격 조회나 새 호출 없이 안전하게 반환하고 기존 호출의 종료·저장 증거만 보존한다.

- 기존 `max_workers` 설정값을 전체 구현/Review 실행 상한으로 유지하고 생략 시 3을 사용한다. config의 `max_tasks_per_project`와 `verify_concurrency`는 생략 시 각각 1이며, 세 config 설정의 0·음수·정수가 아닌 값은 거부한다. 기존 설정 파일을 읽을 수 있고, 별도의 프로젝트별 구현/Review 실행 상한·전체 관리 대상 상한이 없다.
- 새 프로젝트와 해당 항목이 없는 기존 DB의 프로젝트는 `max_tasks_per_project=0`으로 저장된다. 기존 DB 갱신·반복 초기화가 개별 양수·등록 정보·작업·실행 이력을 덮거나 config의 실제 숫자를 DB에 저장하지 않는다. DB의 0은 유효하며 음수·정수가 아닌 값은 거부한다.
- config의 `max_tasks_per_project=3`에서 A의 DB 값이 0이고 B가 5이면 유효 상한은 각각 3·5다. config를 4로 바꿔 다시 읽으면 A만 4로 바뀌고 DB 값은 계속 0이며 B는 5를 유지한다. B를 0으로 되돌리면 유효 상한 4를 사용하고, 조회에서 각 저장값·유효값·적용 출처를 구별한다.
- R-076의 CLI로 등록 프로젝트의 양수 한도 설정·변경과 0 상속 복귀가 가능하며, 잘못된 값·미등록 대상·저장 실패는 기존 값을 보존한다. 실행 중·pause 중의 설정 변경과 다음 안전한 배정 경계 반영, 관리 Skill의 명령·조회·0 의미 안내가 같은 계약을 따른다.
- 전체 구현/Review 실행 상한 2·프로젝트별 관리 상한 3·verify 상한 1에서 A·B 각각 3개씩 합계 6개를 관리할 수 있다. 예를 들어 구현/Review 2개, verify 1개, verify 대기 3개가 함께 존재할 수 있고, 어느 프로젝트도 관리 3개를 넘지 않는다. A가 가득 차도 B의 관리 배정을 막지 않으며, 각 프로젝트의 추가 READY는 그 프로젝트의 관리 한도 때문에 대기한다.
- Worker·Reviewer가 verify·다음 호출 대기로 전환하면 관리 대상 수는 그대로이고 실제 실행 자리만 비운다. 관리 대상 수가 상한에 도달해도 이미 관리 중인 작업의 Review·교정은 새 관리 자리 없이 실행 한도 안에서 이어진다. 실제 관리 종료·차단 해제·수동 제출 묶음·단계 재개에서 중복 관리·구성 G의 중복 실행이 없다.
- 수동 제출과 기존 자동 작업의 실행 가능한 후속 처리를 배정한 뒤, 일반 신규 관리 대상은 각 프로젝트에 먼저 하나씩 배정하고 관리 한도 안에서 우선순위로 추가 선택한다. 신규 실행 여유가 있고 관리 대상에 충분한 후보가 있는 A·B·C와 전체 실행 상한 5·프로젝트별 관리 상한 3에서는 각 프로젝트의 첫 호출을 먼저 시작하고, A의 추가 후보가 가장 높으면 나머지 두 실행 자리도 A에 배정할 수 있다. B·C의 첫 후보가 낮은 우선순위라는 이유로 기본 실행 배정에서 제외되지 않는다.
- 전체 실행 상한 2에 일반 신규 착수 적격 프로젝트가 3개 이상이면 기본 실행 자리를 받지 못한 프로젝트를 먼저 선택한다. 관리 작업이 있는 것과 실제 구현/Review 호출이 있는 것을 혼동하지 않으며, verify만 대기 중인 프로젝트에 실행 가능한 독립 신규 후보가 생기면 여유 자리의 기본 실행 배정 대상이 된다. 수동 제출과 기존 자동 작업의 Review·교정 재개는 그보다 우선 처리한다. 일반 신규 배정에서는 빠른 완료·동일 입력 반복·재시작·나중에 실행 가능해진 프로젝트에서도 공정 배정이 유지된다.
- 한 프로젝트에만 실행 가능한 작업 3개가 있고 프로젝트별 관리 상한이 3 이상, 전체 실행 상한이 3이면 해당 프로젝트에서 세 호출을 동시에 진행할 수 있다. 관리 대상 선택·실행 조건·공유 자원 보호 외의 별도 프로젝트별 실행 한도가 이를 막지 않는다.
- 실행 불가·pause·선택 범위 밖 프로젝트는 배정을 막지 않는다. 미Merge dependency, draft·catalog 보류, 프로젝트 차단·공유 소유권·활성 유지보수 gate와 명세 변경 반영 조건을 기본·추가 배정 모두에서 유지한다.
- 실행 가능한 수락 수동 제출이 없으면 이미 시작한 일반 자동 작업의 재개·교정을 새 고우선순위 일반 작업보다 먼저 처리한다. 기존 작업이 verify 등으로 대기하면 다른 독립 작업이 여유 자리에서 시작될 수 있다. 신규 우선순위를 이유로 기존 작업을 교체·미착수화하거나 미착수 대상 교체 정책을 추가하지 않는다.
- 전체 실행 상한 1에서 일반 Worker가 실행 중일 때 수동 제출을 수락해도 호출을 중단하지 않는다. 호출 종료 뒤 다음 안전한 배정에서 수동 제출을 일반 작업의 Review·교정 재개나 신규 기본 배정보다 먼저 선택한다. 다른 프로젝트의 일반 후보가 `critical`이어도 같은 규칙을 적용한다. 수동 제출끼리는 최초 수락 순서를 유지하며 앞선 제출이 실행 불가이면 다음 적격 후보를 선택한다.
- 수동 제출의 verify가 대기하면 이미 실행 중인 일반 verify는 계속하고, 다음 빈 verify 자리는 실행 가능한 수동 제출에 먼저 배정한다. 수동 제출의 단계 전환·자동 교정·재시작에서도 우선 배정과 최초 수락 순서가 유지된다. verify만 기다리는 수동 제출이 다른 작업의 구현·Review 실행 자리를 붙잡지 않는다.
- 관리 한도가 가득 찬 프로젝트에서도 수동 제출과 명시적 차단 해제 명령은 같은 명령에서 수락·상태 반영된다. 후속 실행은 현재 관리 단위 중 작업 순서가 가장 늦은 단위의 관리 자리를 넘겨받으며, 밀려난 작업의 단계·작업물·기록·원래 순서를 보존한다. 모든 관리 단위가 실행 중이면 명령 반영은 완료하고 선택된 단위의 안전 반환 뒤 자리를 인계한다. 복수 대상·반복 명령·동순위·공유 묶음·중단 및 재시작에도 한도 초과 실행·중복 배정·기록 유실이 없다. dependency·pause·미확정 유지보수 게시·소유권·종료 불명 안전 조건은 유지하고, 미확정 게시가 없는 유지보수 범위 제한만 명시적 재진입의 예외로 처리한다.
- 기본 배정 후 여유 자리의 일반 신규 후보는 프로젝트 전체의 유효 우선순위로 비교한다. 낮게 선언한 선행 작업도 기존 dependency 상속으로 상향될 수 있고, 같은 프로젝트 내 숫자 ID 순서·프로젝트 간 동순위의 재현 가능성을 확인한다. 선택을 위한 추가 모델 호출이나 priority·dependency 변경이 없다.
- Planner·Worker·Reviewer·verify에서 timeout 10초에 순번 대기 30초·실제 실행 2초인 경우 대기 때문에 timeout이나 실패 집계가 생기지 않는다. 실제 실행이 한도를 넘으면 기존 timeout·종료 확인을 적용한다. 중간 배정 대기·재개와 재시작 기록에서 이미 사용한 실행 시간이 사라지거나 대기 시간이 실행 시간으로 합쳐지지 않는다.
- verify 내부에서 실행 중인 자식이 없이 자원 배정만 기다리면 그 구간은 timeout에서 제외한다. 실제 runner 통합 단계에서는 하위 runner 프로세스가 생존 중이어도 신뢰된 상위 관측에서 실행 트리 전체의 순수 배정 대기가 확인되면 상위 timeout을 소진하지 않는다. 다른 자식이나 상위 단계가 실제 처리 중이면 그 경과 시간은 계산하고 병렬 자식의 시간은 중복 합산하지 않는다. 복사·WSL·Windows 핵심 회귀·정리 단계가 공유 예산을 초기화하지 않으며, 대기 중 pause·취소도 처리된다.
- 상위 verify와 하위 runner의 10초 한도에서 확인된 CPU 배정 대기 30초·실제 실행 2초는 대기만으로 timeout이 되지 않고, 실제 실행 12초는 실패한다. 단계 전환·재개·재시작에도 이전 소비 예산을 보존하며, 조율 인증값 격리·heartbeat 끊김·종료 불명·중복 대기 공제를 이용해 실질 실행 시간 초과를 숨기지 않는다.
- 여러 프로젝트가 부분·전체 verify를 동시에 요청할 때 기본 설정에서는 실제 verify 실행이 최대 하나다. `verify_concurrency=2`에서는 자원·후보 조건이 허용하는 두 verify가 함께 실행될 수 있고 세 번째는 대기한다. 각 경우 다른 작업의 구현·Review가 진행될 수 있으며, verify 내부 테스트 병렬도는 별도로 유지한다. 자체 Windows verify는 두 단계와 정리 전체에서 동일한 자리 하나만 사용한다.
- verify 대기·실행은 관리 자리 하나로 계산하고 구현/Review 실행 자리는 점유하지 않는다. 안정된 PR 대기·PLAN_BLOCKED는 관리 자리를 비운다. 차단 작업에 미완료 rebase·호출 예약이 있어도 관리 개수는 증가하지 않으며, 실제 실행 자리·자원 예약·checkpoint는 보존한다. 빈 관리 자리는 독립 작업에 배정할 수 있고 자동 차단 해제 후에는 관리 한도를 다시 확인하고 명시적 해제 명령은 우선 수용 규칙으로 관리 재진입을 처리한다.
- verify 실패·취소·timeout·시작 실패·종료 불명과 Manager 중단 뒤에는 확인된 종료·미시작만 verify 실행 자리를 해제한다. Worker·Reviewer 호출의 실행 자리와 관리 자리도 각 해제 조건에 따라 별도로 처리한다. 다른 작업의 프로세스·후보·세션·실패 기록은 보존하며 재시작에서 중복 실행·예약 유실·가짜 성공이 없다.
- 관리 상한을 현재 점유보다 낮추면 초과한 프로젝트의 신규 관리 대상만 보류하고 기존 관리 작업은 각 실행 상한 안에서 끝낼 수 있다. 구현/Review 또는 verify 상한을 낮춰도 실행 중 호출은 강제 종료하지 않으며 새 실행이 해당 상한을 넘지 않는다. 세 종류의 상한 차이 때문에 기존 작업이 다음 단계로 진행하지 못하는 교착이 없다.
- 같은 후보의 writer·verify·Review·rebase가 겹치지 않고, 기본·선행 검증 경로와 최신 base·명세·최종 후보의 게시 검증이 유지된다. 다른 작업의 Merge·실패·교정이 기존 성공 근거를 잘못 재사용하거나 독립 작업을 초기화하지 않는다.
- 다른 작업의 verify가 실행 중이어도 독립 차단 계획을 재평가·재개할 수 있다. 같은 대상의 재평가는 lease로 하나만 실행하고, 대상 호출 미종료·공유 branch/worktree·planning 소유권 충돌은 보류한다. 실패와 경쟁 변경은 기존 차단·checkpoint·다른 계획의 투영을 보존한다.
- 질문을 해소한 명세·작업 본문 변경과 결정이 남은 변경을 구분하며, 링크·frontmatter 경로 교정만으로 질문을 해제하지 않는다. 모델 미완료·잘못된 인용·현재 입력 변경은 재개로 처리하지 않는다. 문서 변경 없이 현재 Git이 안전한 rebase 시작 상태가 된 입력 차단도 원인별 재개 전이를 수행한다.
- 다른 작업의 branch 전진·무관한 worktree 등록 변경은 현재 rebase를 실패시키지 않으며 현재 branch·worktree·공유 config 변경은 거부한다. Git·원격 재관측 중 다른 SQLite 연결의 쓰기가 진행되고, 재관측 중 checkpoint 경쟁 변경이 생기면 그 변경을 보존한 채 현재 적용만 거부한다.
- 단계 처리 예외가 발생해도 형제 verify 완료 전에 재시도와 독립 작업의 추가 배정이 진행된다. 반복 예외는 재시도 대기 뒤 같은 실행에서 해당 작업을 재개하며, 오류 종류·메시지·traceback이 남는다. 작업 준비 예외로 Future가 실패해도 프로젝트의 결과 수집과 신규 배정이 계속된다.
- 실제 Git lease·fetch 경쟁은 최신 관측으로 제한 재시도하고, 변경 없이 고정된 DB/OID 비교는 현재 commit 관계의 재구성으로 진행한다. 동일 작업의 짧은 retry 묶음 및 다음 외부 실행에서 같은 원인·입력·진전 없는 상태를 재등록할 때 무한 반복하지 않으며, 지속 장애의 범위·원인·횟수/기간과 다음 유효 재평가 조건이 보존되어 R-053의 중복 없는 진단으로 연결된다. 실제 새 입력이 오면 복구를 이어가고 독립 작업은 계속 진행한다.
- 일반 RETRY 작업은 같은 프로젝트의 다른 verify가 실행·대기 중이어도 먼저 재배정될 수 있고 관리 수가 증가하지 않는다. 실행 자리 하나의 대기열에서 수동 제출 → 명시적 차단 해제의 관리 재진입 → RETRY → 일반 재개 → 신규 순서를 확인하며 실행 중 호출은 중단하지 않는다.
- 하나의 계획이 PLAN_BLOCKED가 되면 독립 작업이 같은 실행에서 시작·재개하고, 해당 계획의 dependency나 프로젝트 차단은 우회하지 않는다.
- 여러 작업의 구현·verify·Review가 진행 중 원격 Requirement 변경이 확인되면 해당 프로젝트의 신규·후속 배정이 멈추고 대기 호출은 미시작으로 반환한다. 실행 중 처리가 안전 경계로 반환한 뒤 Planner를 한 번 조율하고 게시·DB 반영 후 재개한다. 다른 프로젝트의 진행과 종료 불명 자리 보존을 확인한다.
- runtime handoff 뒤 전체 프로젝트의 새 관리 편입·Agent·verify·게시가 시작되지 않으며 이미 실행 중인 호출의 종료·정리 뒤 상태를 보존해 bootstrap으로 넘기고 주기 실행을 기다리지 않고 최신 runtime으로 자동 재시작한다.

- 같은 운영 DB의 여러 작업·프로젝트와 별도 CLI가 읽기·쓰기를 함께 요청해도 공통 처리 구간은 겹치지 않고, 대기한 요청은 앞선 처리 종료 뒤 현재 상태로 실행된다. DB 경로의 별칭도 같은 조율을 사용하며 독립 DB·snapshot 처리는 영향을 받지 않는다.
- 여러 row가 남은 recovery 조회에서 보류 갱신을 수행하고 다른 연결이 동시에 쓰는 경우 열린 cursor의 쓰기 전환 교착이 없다. 보류 기록 중 일시 잠금은 DB 요청의 제한 재시도로 처리되고 원인·identity·generation·실패 이력이 보존된다. 한도 초과·기록 저장 실패가 해당 작업의 오류로 격리되어 독립 작업의 결과 수집·신규 배정이 계속된다.
- 외부 Git·Agent·verify·전송이 대기·실행 중에도 다른 DB 요청이 처리된다. 조회 후 외부 처리 사이에 소유권·generation이 바뀌면 낡은 결과 적용만 거부하고 경쟁 변경을 보존하며 외부 효과를 중복 실행하지 않는다. 중첩 호출·예외·취소 뒤 접근 차례와 cursor·transaction이 남지 않는다.
- DB 순번 대기만 길어진 경우 실제 실행 timeout·일반 실패·교정 횟수가 증가하지 않는다. DB 접근 제한·취소와 이미 실행 중인 호출의 시간·소유 상태는 유지하고, 손상·권한·SQL 오류는 잠금 경합과 구별한다.
- 실행 중 CLI 조회는 쓰기·migration·작업 재개 없이 일관된 snapshot을 반환하고, 충돌 없는 수동 준비·수락은 짧은 DB 대기 뒤 같은 명령에서 완료된다. 실제 공유 자원 충돌은 기존대로 거부하고 자동 작업 전체의 종료를 DB 대기 조건으로 요구하지 않는다.
