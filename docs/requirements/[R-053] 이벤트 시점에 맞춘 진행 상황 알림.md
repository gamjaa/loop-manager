# [R-053] 이벤트 시점에 맞춘 진행 상황 알림

## Summary

Telegram 메시지는 Manager가 자동 복구할 수 없는 실제 최종 중단 또는 사용자의 판단·승인·권한 조치·PR 검토/병합 등 현재 사용자 행동이 필요한 경우에만 보낸다. Git 상태 변화, 일시 실패·재시도·자동 교정·대기와 계획·Worker·유지보수의 진행·완료·재개에는 무음 메시지도 보내지 않는다. 전송 전에 최신 조치 필요성을 재확인하고 기존 outbox·부분 전송·중복 제거·감사를 보존한다.

## Context

기존 Telegram은 새 계획, 시작·완료, PR 충돌 수정 시작, 차단 후 재개, 안정적인 대기도 통지한다. 그러나 진행 상태나 `PLAN_BLOCKED`·`PROJECT_BLOCKED` 자체는 사용자 개입 또는 실제 자동 복구 불가능성을 뜻하지 않는다. 운영 상태와 실패 진단은 로그·DB·읽기 전용 status에서 확인하며 Telegram은 사용자에게 실제 필요한 행동이나 복구 불가 중단에 집중한다.

## Requirement

### 전송을 허용하는 사건

| 사건 | 현재 상태에서 확인할 조건 |
|---|---|
| 사용자 결정·승인·조치 | 유효한 명세·질문·출처·현재 소유권을 대조해 실제 미해결 사용자 결정, 접근 권한/설정 변경 또는 명시적 재시작이 필요하고 Manager가 자체 해결할 수 없다. draft 질문은 프로젝트별 현재 미해결 목록으로 묶는다. |
| PR 검토·Merge | verify·Review와 원격 게시가 완료된 신규 PR 또는 기존 PR의 새로운 검토 후보에 사용자가 검토·Merge할 일이 있다. 같은 후보와 동일 사용자 행동에는 중복 통지하지 않는다. |
| 실제 자동 복구 불가능한 최종 중단 | 동일 계획/프로젝트의 최신 원인에 재관측·재시도·자동 교정·조건 해소 대기·다음 실행 재개·안전한 복구 방법이 남지 않아 진행이 불가능하다. 사용자 행동이 없다면 가짜 행동을 요구하지 않고 복구 불가 사유·범위·보존을 안내한다. |

단순 `BLOCKED`·`PLAN_BLOCKED`·`PROJECT_BLOCKED`·`planning_error`, 실패 횟수나 교정/retry 묶음 소진, 시작 가능한 작업 없음은 전송의 충분조건이 아니다. Git OID/PR head 변경, lease 경쟁, 일시 원격 조회 실패, Git lock, CPU·verify/DB 자원 대기, 외부 CLI 오류, commit/push 기록 중단, rebase/cleanup 보류, 다음 runtime 실행의 자동 복구 가능성이 있으면 해당 작업·자원만 보존/대기하고 Telegram은 보내지 않는다. 실제 타인의 Git 이력 덮어쓰기 위험은 쓰기를 거부하되 자동 확인과 복구 여지가 남은 상태를 사용자 결정으로 위장하지 않는다.

### 메시지를 보내지 않는 사건

새 ExecPlan 생성·게시, Planner/Worker/Reviewer 시작·종료, 유지보수 cycle 시작·종료, 프로젝트 완료, 차단 해제·자동 재개, 기존 PR 충돌 수정의 시작·진행, 일반 단계 실패·targeted test/verify/Review 자동 교정, Git checkpoint 생성/게시·원격 전진, 재시도·조건 대기와 내부 상태 갱신에는 **일반·무음 Telegram 메시지를 생성하지 않는다**. 진행·실패·재시도·복구·검증 이력과 현재 상태는 운영 로그·DB·status에 보존한다.

프로젝트의 실행 가능한 작업이 없어도 별도 `work_waiting` 메시지를 만들지 않는다. 필요한 사용자 행동이 실제 존재하면 해당 결정 또는 PR 검토 요청만 한 번 통지한다. 기존 PR 충돌 수정 완료도 새 검토 후보가 실제 원격 반영됐고 사용자가 다시 검토·Merge해야 할 때만 알린다. 반복 게시·rebase·PR 상태 관측이나 단순 충돌 해결은 통지하지 않는다.

### 현재 사건과 기존 outbox 재검사

실제 미해결 draft 질문만 ID·제목·질문 identity/revision·확인한 원격 링크로 프로젝트별 한 목록에 묶는다. 질문이 자동 해소되거나 사용자 행동이 사라지면 목록의 미전송 메시지/잔여 조각을 취소한다. 링크 변경만으로 새로운 사용자 승인·질문을 만들지 않는다.

사건을 확정한 뒤 다음 장시간 작업 전에 발송을 시도하되, **실제 전송 직전과 각 미전송 조각 앞에서** 현재 사용자 결정·PR head/검토 후보·차단 원인과 자동 복구 가능성을 확인한다. 해소된 상태, 다른 작업의 차단, 오래된 OID/실패, 이전 정책상 진행·무음·대기 메시지는 전송하지 않고 남은 조각을 취소한다. 정책 변경 전 outbox에 쌓였거나 일부 전송된 메시지도 같은 기준을 적용한다. **이미 전송한 조각과 원래 사건·전송·실패·취소 감사는 보존**한다.

현재 필요한 같은 결정·PR 검토/병합·실제 복구 불가 중단은 관측·재시작·조각 전송 재시도에 한 번만 통지한다. 메시지는 프로젝트·대상·발생 시각·현재 원인·필요한 사용자 행동 또는 복구 불가능한 이유, 관련 URL·checkpoint/작업물 보존을 간결히 알리고 검증되지 않은 조치를 만들어 내거나 비밀값을 노출하지 않는다.

기존 durable outbox·조각 전송·중복 제거·재시도·Telegram 설정은 재사용한다. 전송 실패는 작업·검증·복구·게시를 차단하지 않으며, 알림을 위해 추가 Agent 호출·사용자 승인이나 Git 쓰기를 만들지 않는다.

## Acceptance Criteria

- 정상 Git HEAD/OID·PR 전진, lease/lock 경쟁, DB·CPU·verify slot 대기, CLI/네트워크 오류, retry/교정 예산 소진, 다음 외부 실행 재개와 Worker/verify/Review 자동 수정에서 일반/무음 Telegram 전송은 0건이고 원래 실패·복구 근거는 보존된다.
- 새 계획 게시, Worker·Planner·Reviewer·maintenance 시작/종료, 프로젝트 완료, 차단 해제·재개, PR 충돌 수정 시작/진행 및 작업 없음에서 Telegram은 0건이다.
- 실제 미해결 사용자 판단·승인/권한, 신규 또는 기존 PR의 새로운 검토/Merge 요청, Manager가 자동 복구할 수 없는 실제 최종 중단만 대상별 한 번 통지한다. 상태 코드·실패 횟수만으로 조치를 추정하지 않고 행동이 없는 최종 중단에는 복구 불가와 보존 상태를 안내한다.
- 기존 outbox의 미전송/부분 전송된 진행·무음·대기 및 해소된 최종 차단은 발송 전 최신 정책으로 취소하며, 이미 전송한 조각과 감사는 지우지 않는다.
- draft 목록은 현재 미해결 질문과 identity/revision·확인된 링크를 반영한다. 일부 해소·링크만 변경·전송 중단 후에도 불필요한 메시지가 재생성되거나 중복 발송되지 않는다.
- Telegram 비활성화·발송 지연·오류가 실행·원격 게시·검증 상태를 변경하지 않는다.

## Product Impact

- Telegram은 실제 사용자 개입 필요와 자동 복구 불가능한 중단을 알린다. 나머지 운영 진행·대기·실패 이력은 로그와 상태 조회에서 제공한다.

## Non-Goals

- 주기적 상태 방송·무음 진행 메시지·새 알림 채널/대시보드를 만들지 않는다.
- 알림을 위해 사용자 결정·성공 결과·새 자동 실행 제어를 생성하지 않는다.
