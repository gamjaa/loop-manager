# [R-065] 실제 부하 기반 verify 병렬 실행

## Context

Loop Manager 자체 verify는 공통 runner에서 독립 테스트 모듈을 부하에 따라 배정한다. 필수 검증을 유지하면서 허용된 자원을 활용하고, 불필요한 직렬 축소·배정 대기와 한 모듈에 집중된 최초 import 비용을 줄여야 한다. 테스트 시간 기록과 실제 Agent 호출 배제는 기존 보호 조건으로 유지한다.

등록 프로젝트 수나 활성 verify 수로 자원을 균등 분배하면 실제로 검증하지 않는 프로젝트와 대기가 많은 작업까지 같은 몫을 예약하게 된다. 실제 부하를 고려해 여유 자원을 적극 활용하되, 여러 verify의 동시 시작과 메모리 부족을 코드로 조율해야 한다.

[테스트 시간 절감 분석](chatgpt-conversation://6ac824ad-6efc-83e8-b289-d5654a16670a)은 `f810c75ca520c4c1869225be88c1edb7bad10d9c`에서 Windows affinity가 좁으면 계산한 부하를 `None`으로 되돌리는 분기, 모듈 하나 배정 후 50ms 대기와 최초 import의 직렬 집중을 확인했다. 최초 import 표본은 Linux의 Python 3.12.14·Git 2.51.1에서 새 Python 245회·22.66초였으며 한 번의 측정이다. 당시 전체 수집은 205개 모듈·3,287개 테스트였고, 이 수치나 입력 주입 재현은 현재 Windows의 병목 비중·절감률을 뜻하지 않는다. 관련 경계는 2026-10-10 checkout `9244ea61552e95d53c8f61cd009f2c32a9698c7f`에도 남아 있다.

비용 우선순위는 실제 Windows 배정·임시 경로 진단, affinity 직렬 축소 해소와 [R-080](%5BR-080%5D%20Git%20Mock%20Defaults%20for%20Tests.md)의 남은 Git 정책 테스트 전환, 배정 대기 개선, 최초 import 분산, [R-067](%5BR-067%5D%20프로젝트%20공통%20verify%20실행%20규약.md)의 가드·환경 중복 정리 순이다. 실제 느린 모듈 자료로 개선 대상을 선택하며 이 순서가 기존 작업 사이에 새 필수 의존성을 만들지는 않는다.

## Requirement

### 코드가 결정하는 실행량

- 병렬도 계산, 추가 테스트 배정, 실행 예약과 결과 집계는 코드가 수행한다. 실행 중 모델 호출, 실제 Agent CLI·API 또는 모델이 작성한 지시를 자원 배분의 판단 단계로 사용하지 않는다.
- 실행 환경에 허용된 CPU, 실제 CPU 부하와 메모리 여유, 현재 실행 중인 검증과 아직 사용량에 반영되지 않은 예약을 고려한다. 등록 프로젝트 수나 활성 verify 수로 CPU·메모리를 고정 분할하지 않는다.
- 단일 verify는 여유 자원을 충분히 활용할 수 있고, 여러 verify 중 일부가 대기 위주이면 개수만으로 나머지 실행량을 줄이지 않는다. 새로운 모듈 배정 또는 실행량 조정 시 자원을 재평가해 시작 때의 병렬도를 전체 실행에 고정하지 않는다.
- 순간적인 낮은 사용률이나 낡은 관측값만으로 실행량을 급격히 늘리지 않는다. CPU·메모리 제한과 보호용 여유를 지키고, 부하 증가 시 신규 배정을 제한하거나 기다렸다가 여유가 회복되면 늘린다. 부하 조절을 위해 실행 중인 테스트를 강제 종료하지 않는다.
- 여러 verify가 같은 여유 자원을 동시에 가져가지 않도록 추가 실행의 확인·예약을 조율한다. 한 작업의 정상 종료·실패·취소 뒤 자식 종료를 확인하거나 시작 실패에서 프로세스 미시작을 확인한 경우 그 작업의 예약을 회수하며 다른 작업의 예약은 유지한다. 종료 불명의 예약을 임의 해제해 여유 자원으로 계산하지 않는다. 대기 중인 verify가 계속 뒤로 밀리지 않게 한다.
- 사용자 병렬도 설정은 기존 설정 체계의 한 곳에서 검증한다. 기본값 `auto`는 환경과 부하에 따라 계산하고, 양의 정수는 각 verify의 최대 병렬도이며 `1`은 직렬 실행이다. 사용자 상한으로 자원 제한을 우회하지 않는다.
- 관측값을 얻을 수 없거나 신뢰할 수 없으면 추가 병렬 확대를 중단하고 사유를 기록한 채 직렬 실행으로 축소한다. 메모리 부족 등 확인된 제한에서는 직렬 실행도 신규 배정을 기다릴 수 있다. 설정 오류와 테스트 실패를 관측 실패로 간주하지 않는다.
- Windows는 유효한 CPU 시간 차이와 메모리 관측이 있을 때 프로세스 affinity가 시스템 범위보다 좁다는 이유만으로 직렬 실행에 고정되지 않아야 한다. 시스템 부하와 허용 CPU 범위를 구분하고 허용 범위의 부하를 과소평가하지 않는 보수적 추정으로 판단하며, 관측 범위·추정 방식과 affinity를 진단에 남긴다. 첫 샘플처럼 차이를 계산할 수 없는 경우와 Linux cgroup 사용량 관측 실패는 기존 직렬 축소를 유지한다.

### 배정 대기와 최초 import 비용

- 완료된 모듈을 수집한 뒤 coordinator가 허용하는 동안 여러 독립 모듈을 연속 배정한다. 매 배정마다 기존 확인·예약을 거쳐 자원·사용자 상한과 여러 verify 사이의 공정성을 유지한다. 바로 수집·배정할 일이 있는데도 모듈마다 고정 대기를 끼우지 않으며, 진행 가능한 일이 없거나 배정이 거절되면 대기해 과도한 polling을 피한다.
- 비교 가능한 과거 모듈 시간이 있으면 오래 걸리는 모듈을 먼저 배정하고 동률은 수집 순서를 따른다. 자료가 없거나 불완전·손상·비교 불가능하면 수집 순서로 실행하며 없는 시간을 합성하지 않는다. 배정 큐만 바꾸고 manifest·테스트 identity·필수 단계 순서와 fixture 계약을 보존한다.
- 최초 import 검사 대상을 여러 독립 테스트 모듈로 나눠 기존 coordinator의 자원 예산 안에서 실행한다. 각 대상은 계속 새 interpreter에서 처음 import하며 entry point 선행 로딩 금지, 순환 의존성 검사와 import 중 SQLite 연결·프로세스 생성 금지를 유지한다. 이미 import한 프로세스 재사용이나 worker 내부 독립 프로세스 풀로 이 계약·배정 상한을 우회하지 않는다.
- 최초 import 대상은 현재 코드에서 수집하며 조사 당시의 245개를 고정하지 않는다. 분할 전후 대상 집합이 같고 누락·중복이 없어야 하며 새 구현 모듈도 포함한다. 실패 시 대상과 새 interpreter의 오류를 식별할 수 있어야 한다.

### 검증 범위와 복구 보존

- 우선 적용 대상은 Loop Manager 자체 unittest다. 다른 등록 프로젝트의 테스트 프레임워크·verify 스크립트를 일괄 변경하지 않으며 그 작업이 만드는 실제 부하는 자원 관측에 반영한다.
- 직렬·병렬 모드에서 기존 필수 테스트와 compile 검증을 유지한다. 테스트 수집과 fixture 계약을 보존하고 테스트 누락·중복, 수집 오류, 결과 누락과 자식 프로세스 비정상 종료를 성공으로 처리하지 않는다.
- 테스트별 Git 저장소·SQLite·임시 경로와 필요한 포트의 격리를 유지한다. 실제 Git·SQLite·운영체제의 실패·중단·복구 검증을 편의를 위해 모두 mock으로 바꾸지 않는다.
- 자원 대기 시간도 기존 전체 verify timeout에 포함한다. timeout·취소·runner 실패에서는 해당 verify의 자식 프로세스 종료를 확인하고 R-058의 완료 기록과 중단 위치를 보존한다. 종료 불명은 기존 안전 오류로 처리하며 다른 verify의 프로세스를 종료하지 않는다.
- 환경 관측, 계산된 실행량, 사용자 상한, 제한·확대 이유와 예약 회수를 진단할 수 있어야 한다. 이전 실행 자료는 비용 추정에만 사용하며 현재 revision의 테스트 결과나 검증 성공을 대신하지 않는다.
- 첫 `run_start`의 `busy=None`과 이후 반복되는 관측 실패를 구분한다. `resource_wait`에는 정상적으로 실행 상한에 도달한 대기도 포함되므로 전체를 유휴 시간으로 보고하지 않는다. R-067의 모듈 결과·자식 종료·배정 시점과 당시 실행량을 함께 확인한다.

### 효과 확인

기존 시간·Git 계측으로 준비 비용과 반복 작업을 먼저 개선하고, 같은 실행 환경·검증 범위에서 직렬 실행과 부하 기반 병렬 실행을 비교한다. revision, Python·Git 버전, 대상 집합, 계측·캐시 조건, 병렬도 설정·실제 worker 수, affinity·메모리 제한·관측 가능한 메모리 사용량·동시 부하·실제 임시 경로·전체 경과 시간을 함께 기록한다. 최초 import 분할은 테스트 ID 변경과 기존 검사 대상의 대응도 남긴다.

완료된 전체 기준 검증이 있으면 변경 전후 비용 비교는 영향 모듈과 필수 연관 회귀를 같은 조건에서 반복 측정해 중앙값을 비교한다. 전체 검증 기록은 기준 확인과 최종 검증에 사용하고 국소 비교마다 전체 suite를 반복하지 않는다. Worker 최소 targeted test → Manager 전체 verify → Reviewer 읽기 전용 검토의 역할을 유지한다. Git·fixture·자식의 누적 시간과 전체 경과 시간을 더하거나 모듈 개선을 전체 절감률로 환산하지 않는다.

Windows와 WSL은 같은 PC·비교 코드·검증 범위에서 한 번에 하나씩 측정한다. checkout과 실제 임시 파일시스템, 프로세스 시작·작업 시간, 배정·자식 정리를 구분한다. 파일 필터·동기화·색인 등은 지연이 확인된 모듈에서만 추가 조사하며 Defender 한 가지 원인이나 미확인 환경 요인을 확정하지 않는다. 실행 환경이 다른 시간만 비교해 절감률을 확정하지 않는다.

Manager는 비교에 필요한 시간·자원 집계를 코드로 생성하고 관련 구현·검토에 제공할 수 있게 한다. 이 집계는 진단 자료이며 검증 성공 출력 전체를 Worker에게 전달하거나 과거 성공 결과를 재사용하는 근거가 아니다. 실제 전체 verify는 Manager가 Agent 밖에서 수행한다.

## Acceptance Criteria

- 병렬도·배정·예약·결과 집계 과정에 모델 호출이 없으며 동일한 관측 snapshot, 실행·예약 상태와 설정에는 같은 결정과 근거가 나온다.
- 등록 프로젝트가 많아도 verify 하나만 실행 중이면 여유 자원을 활용한다. 활성 verify 개수가 같아도 CPU·메모리 부하가 다른 입력에서 신규 배정이 달라진다.
- CPU 제한과 메모리 여유 감소 시 신규 배정을 제한하고, 여유가 회복되면 다시 늘린다. 낮은 순간 부하와 낡은 관측값은 무제한 확대의 근거가 되지 않는다.
- 동시 시작에서 같은 자원을 중복 예약하지 않는다. 실패·취소 후 자식 종료 또는 시작 실패의 미시작을 확인한 예약만 회수하고 다른 verify의 실행과 예약은 보존된다. 종료 불명은 여유 자원으로 계산하지 않으며 대기 작업이 계속 뒤로 밀리지 않는다.
- `auto`, 양의 정수 상한과 `1`이 유효하고 잘못된 설정은 거부한다. 관측 실패 시 직렬 실행으로 축소한 이유를 확인할 수 있다.
- Windows 관측 입력의 시스템 8 CPU·허용 4 CPU에서 유효한 후속 저부하 샘플이면 추가 worker 배정이 가능하다. 첫 샘플·낡은 값·관측 오류·높은 부하·메모리 부족·예약 압력과 Linux cgroup usage 부재는 기존 보호 결과를 유지한다.
- 자원이 허용하는 복수 pending 모듈을 모듈별 고정 sleep 없이 배정한다. 각 배정의 acquire·예약·상한·공정성과 거절 후 대기가 확인되며 짧은 모듈·즉시 완료 입력에서도 불필요한 50ms 간격이 누적되지 않는다.
- 비교 가능한 시간 자료에서는 긴 모듈을 먼저 배정하고 동률은 수집 순서를 따른다. 자료 부재·오류에서는 수집 순서로 실행하며 manifest와 필수 단계 순서는 변하지 않는다.
- 최초 import 분할 전후 대상 집합이 같고 모든 대상이 새 interpreter에서 검사된다. 새 모듈 포함·누락/중복 거부·순환 import 및 resource effect 거부를 유지하고 실행량이 coordinator 예산을 넘지 않는다.
- 직렬·병렬 모드가 같은 수집 범위와 fixture 계약을 지키며 성공·실패·오류·skip·expected failure·unexpected success와 종료 코드의 의미가 유지된다. 누락·중복·수집 오류·비정상 자식 종료는 실패로 드러난다.
- 병렬 테스트 간 Git·SQLite·경로·포트가 격리되고 timeout·취소 후 자식 종료 확인, 중단 기록과 다른 verify의 보존을 확인할 수 있다. 자원 대기로 시간 상한을 자동 늘리지 않는다.
- 같은 환경과 범위의 전후 비용 기록과 최종 전체 verify 근거가 있으며 Git 호출 감소·국소 시간 변화·전체 경과 시간을 각각 보고한다. 측정하지 않은 Windows 효과나 서로 다른 환경의 결과를 확정된 개선으로 제시하지 않는다.

## Product Impact

- verify가 실제 부하와 사용자 상한에 따라 코드로 실행량을 조절하며 여유 자원을 활용한다.
- 동시에 실행하는 검증의 자원 예약과 실패 정리가 조율되고 기존 전체 검증·timeout·복구 보장이 유지된다.

## Non-Goals

- 같은 프로젝트에서 여러 ExecPlan·Worker를 동시에 실행하는 정책 변경.
- 다른 등록 프로젝트의 verify·테스트 프레임워크 일괄 전환 또는 여러 호스트 간 자원 조율.
- 새로운 외부 모니터링 서비스, 상주 자원 관리 서비스 또는 범용 작업 스케줄러 도입.
- 새 runner·IPC 체계·worker 내부 독립 프로세스 풀 도입과 Defender·동기화·색인 설정의 자동 변경.
- 동일 SHA만으로 자체 verify를 생략하는 변경. 입력 증명과 성공 재사용은 [R-072](%5BR-072%5D%20Reuse%20Successful%20Candidate%20Results%20with%20Proven%20Inputs.md)의 별도 범위다.
- 매 verify마다 여러 병렬도를 시험하는 탐색, 필수 테스트 skip, timeout 자동 증가 또는 특정 절감률 보장.
- Python 캐시 정책 변경은 R-059에서 별도로 다루며 이 요구사항의 필수 선행 조건으로 삼지 않는다.

## Open Questions

- 없음. 실제 Windows의 affinity 제한·파일시스템·외부 부하와 최종 절감량은 측정 항목이며 미확인 값으로 보호 조건이나 검증 범위를 바꾸지 않는다.
