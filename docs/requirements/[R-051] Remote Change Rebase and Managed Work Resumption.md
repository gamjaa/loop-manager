# [R-051] 원격 변경 반영과 관리 작업 재개

## Context

Loop Manager의 자동 작업 기준은 최신 원격 base이며, 구현 작업에는 관리 worktree의 rebase와 변경된 후보의 재검증이 이미 적용된다. 그러나 일반·유지보수 planning은 원격 기준이 바뀌면 작업 공간을 정리하고 다시 계획하는 경로가 있다. 재개 과정에서는 이전 Planner가 수정한 READY ExecPlan을 시작 revision의 원본과 다시 비교해 `READY ExecPlan 파일이 평가 기준 revision과 다릅니다` 오류로 중단할 수도 있다.

원격 변경은 진행 중인 작업을 보존하면서 최신 기준으로 이어갈 계기여야 한다. 원격이 그대로이고 이전 Planner 변경만 남았다면 그 결과를 검증·게시하는 단계로 재개해야 한다.

## Requirement

### 적용 범위와 원격 기준

- 일반·유지보수 planning의 작성·평가·교정·검증·게시, Worker 구현·교정, 전체 verify, Review, 구현 게시 및 차단 복구의 어느 단계에서든 원격 변경을 관측하면 해당 관리 작업에 반영한다. Agent나 검증 프로세스가 같은 worktree를 사용 중이면 종료 후 다음 안전한 경계에서 반영하고, 오래된 후보의 결과를 게시 승인으로 사용하지 않는다.
- 기준은 등록된 origin과 base branch의 현재 원격 commit이다. 로컬 base branch, 기본 checkout의 미커밋 변경과 로컬 전용 commit을 자동 작업 입력으로 사용하지 않는다. rebase는 소유권이 확인된 관리 worktree에서만 수행한다.
- 원격 base가 정상적으로 전진하면 진행 중인 로컬 변경과 세션을 보존하고 최신 base로 rebase한 뒤 필요한 단계부터 재개한다. 같은 변경을 다시 관측하거나 이미 반영한 base를 확인한 경우에는 rebase를 반복하지 않는다.
- 원격 작업 branch의 변경도 관측했으면 기존 동일 branch 복구 조건에 따라 채택 가능한 후속 변경을 먼저 반영한다. 삭제·재작성·분기, origin 불일치 또는 소유권 불명확을 무조건 rebase하거나 덮어쓰지 않고, 작업물과 원인을 보존하며 기존 복구·사용자 조치 정책을 적용한다. 원격 base의 삭제·재작성도 같은 원칙으로 처리한다.

### 작업 보존과 재개

- 미커밋·staged·untracked 변경을 포함한 허용 작업물을 손실 없이 보존한 뒤 rebase한다. 작업 보존 자체를 결과 검증 통과나 게시 승인으로 간주하지 않는다.
- 일반·유지보수 Planner의 재개는 시작 revision의 원본, 허용된 대상 snapshot, 보존된 작성 결과와 현재 원격 입력을 구분한다. 기존 세션의 허용된 READY 개정 결과가 남았다는 사실만으로 원본 불일치 오류를 만들지 않는다.
- 원격이 그대로이면 보존된 단계·세션·결과를 확인해 미완료 단계부터 재개한다. 이미 완료된 Agent 호출이나 확정된 게시를 반복하지 않는다. 임의 변경, 범위 위반 또는 소유권 불명확은 정상 Planner 결과로 채택하지 않는다.
- Planner 단계에서 원격이 바뀌면 기존 작성 결과를 최신 기준으로 옮기고 새 catalog와 현재 SQLite 상태·소유권을 대조해 변경 권한을 다시 확인한다. snapshot 밖 계획, 이미 착수한 계획 또는 더 이상 허용되지 않는 대상에 이전 권한을 그대로 적용하지 않는다.
- Planner 단계에서 원격과 로컬이 같은 ExecPlan을 변경했거나 새 ID가 겹치거나 dependency가 달라졌으면 기존 결과를 보존한 채 정합성을 재검토한다. 최신 원격 선언과 SQLite 실행 상태를 임의로 덮어쓰지 않으며, 필요한 개정은 해당 Planner의 기존 권한 안에서 수행한다.
- 충돌은 해당 작업의 기존 역할과 권한으로 해결한다. planning 충돌 해결을 위해 Planner에 코드·설정 변경 권한을 부여하거나 Reviewer에게 쓰기 권한을 부여하지 않는다. 권한 안에서 해결할 수 없으면 작업물과 충돌 상태를 보존하고 실제 조치 대상을 안내한다.
- 원격 변경이나 rebase 완료만으로 기존 planning 오류, 사용자 승인 대기, Review 실패 또는 독립적인 차단 원인을 해제하지 않는다. 해당 원인이 실제로 해소되고 필요한 재검증이 완료된 경우에만 해제한다.

### 재검증과 게시

- 문서 재확인은 단계별 관련 문서의 실제 내용 변경이 있을 때만 수행한다. 무관한 문서 변경, 내용 보존 이동 또는 revision 전진만으로 재확인하지 않는다. 재확인 범위는 변경된 관련 문서와 그 변경이 현재 작업에 미치는 영향으로 한정한다.
- Planner 단계의 관련 문서는 현재 작성·평가 중인 계획의 근거·목표·범위·검증 조건·dependency에 영향을 주는 PRODUCT, 활성 Requirement, ARCHITECTURE와 active ExecPlan이다. 이 문서가 바뀌면 영향받은 계획의 정합성을 다시 확인한다. 다른 설계·계획 문서가 바뀌었다는 이유만으로 전체 설계·계획 검토를 반복하지 않는다. rebase 성공만으로 전체 미충족 작업 검토나 유지보수 평가가 성공했다고 기록하지 않는다.
- Planner 평가 결과는 변경된 입력과의 관계에 따라 적용 가능성을 다시 판단한다. 유효성이 확인된 변경 없는 유지보수 파일의 검토 근거는 재사용할 수 있다.
- Worker·Reviewer 단계의 문서 재확인 대상은 현재 진행 중인 ExecPlan이다. 그 내용이 변경된 경우 해당 변경을 확인하고, 진행 중인 구현·검증·Review가 변경된 목표·범위·Acceptance Criteria·dependency에 맞는지 판단한 뒤 재개한다. 내용 보존 이동이나 revision 전진만으로 이 확인을 반복하지 않는다. 변경으로 필요한 교정과 검증은 기존 역할·권한 및 dependency·승인 규칙을 따른다.
- 현재 진행 중인 ExecPlan이 그대로이면 Worker·Reviewer 단계에서 다른 설계·계획 문서 변경을 이유로 추가 명세 재확인, 계획 정합성 재검토 또는 Planner 인계를 요구하지 않는다. rebase 후 진행 중인 구현·검증·Review를 이어가며, 기존 충돌 해결·사용자 승인·범위 검사는 유지한다.
- 구현 후보 HEAD가 바뀌면 기존 전체 verify와 Review 승인을 무효화한다. Worker의 필요한 targeted unit test, Manager 전체 verify와 읽기 전용 Review가 최종 후보에서 통과해야 게시를 이어간다. 이는 후보 코드의 검증이며 설계·계획 문서 변경에 따른 추가 재확인과 구분한다.
- 게시 직전에 원격과 후보를 다시 확인한다. 원격이 다시 전진하면 작업을 보존한 채 같은 반영·재검증 경로를 사용한다. 한 실행에서 원격이 안정되지 않으면 상태를 보존해 일시 중단하고 다음 실행에서 이어간다.
- planning의 base 직접 게시는 계속 fast-forward만 허용한다. 구현 branch의 기존 lease·PR·중간 checkpoint 규칙을 유지하며, rebase가 원격 덮어쓰기나 자동 Merge 권한을 추가하지 않는다.
- push 뒤 SQLite 확정 전에 중단됐으면 실제 원격 게시 결과를 먼저 대조해 멱등하게 확정한다. 이미 게시된 결과를 다시 rebase·push하거나 중복 catalog로 적용하지 않는다.

### 기존 정책과의 관계

- 변경된 원격 입력을 이유로 복구 가능한 planning worktree를 폐기하고 처음부터 계획하던 동작은 작업 보존·rebase·재검증 후 재개로 변경한다. 해결되지 않은 planning 오류는 입력 변경이나 Git 반영만으로 지우지 않는다.
- 프로젝트별 단일 변경 자리, 실행 중인 작업의 비선점, dependency, 유지보수 cycle·장벽, 사용자 승인과 Agent 범위 제한은 유지한다. PR_OPEN 상태의 원격 변화는 실제 Merge·Close 및 PR head를 먼저 확인해 이미 종료된 작업을 재개하지 않는다.

## Acceptance Criteria

- 일반·유지보수 Planner가 READY를 수정한 뒤 중단되고 원격은 그대로인 경우, 허용된 결과를 원본 불일치로 거부하지 않고 미완료 검증·게시부터 재개한다. 범위 밖 수정과 출처가 불명확한 수정은 계속 거부한다.
- planning 작성·교정·검증·게시 각각에서 원격 base가 전진하면 기존 변경·세션을 보존하고 최신 base를 반영한다. 현재 작성·평가 중인 계획에 관련된 설계·계획 문서가 바뀌면 영향받은 계획의 정합성을 재확인하고, 관련 문서가 그대로이면 문서 재확인을 건너뛴다. 새 planning 호출을 위해 기존 결과를 자동 폐기하지 않는다.
- Planner 단계에서 무관한 Requirement나 ExecPlan만 변경된 경우 현재 작업의 문서 재확인을 실행하지 않는다. 관련 근거·검증 조건·dependency 문서가 변경된 경우에는 해당 변경의 영향만 확인하며 전체 문서 검토를 반복하지 않는다.
- staged·unstaged·untracked 작업물이 있는 관리 worktree에서도 rebase 전후 변경이 보존된다. 충돌 또는 중단 시 작업물과 복구 단계가 남고, 기본 checkout의 파일·index·HEAD는 이 처리로 변경되지 않는다.
- 원격과 Planner가 같은 READY를 바꾸거나 새 ID·dependency가 충돌하면 최신 catalog와 상태에 맞게 재검토한다. 재개 사이 대상이 착수·소유·종료된 경우 과거 snapshot 권한으로 개정하지 않는다.
- 유지보수 barrier·사후 재검증에서 원격 입력이 바뀌어도 mode별 변경 제한과 제품 목표 보존이 유지된다. 변경된 파일의 과거 검토 근거를 최신 성공 증거로 적용하지 않는다.
- Worker·Reviewer 단계에서 현재 진행 중인 ExecPlan이 바뀌면 변경된 내용과 현재 작업의 적합성을 확인하고 필요한 교정·검증 후 재개한다. 변경된 Acceptance Criteria를 확인하지 않은 채 기존 구현 결과나 Review 승인을 적용하지 않는다. 같은 내용을 재관측하거나 내용 보존 이동만 일어난 경우 이 확인을 반복하지 않는다.
- 현재 진행 중인 ExecPlan이 그대로이고 다른 설계·계획 문서만 바뀌면 Worker·Reviewer는 rebase 후 기존 작업을 이어가며, 그 변경을 이유로 추가 명세 재확인·계획 정합성 재검토·Planner 호출을 요구하지 않는다. 다른 문서와 코드가 함께 바뀌어도 문서 재확인 의무를 추가하지 않는다.
- Worker·verify·Review·게시 단계에서 후보 HEAD가 바뀌면 최종 후보의 필요한 targeted test·Manager 전체 verify·Review를 거친다. Reviewer가 파일을 수정하거나 테스트를 실행하지 않는다.
- Agent·verify 실행 중 원격 변경을 관측해도 worktree를 동시에 rebase하지 않으며, 종료 뒤 최신 기준을 반영하고 오래된 성공 결과로 게시하지 않는다.
- rebase 시작·충돌·완료 및 push 전후의 중단·재시작이 같은 작업을 보존해 재개한다. 이미 반영된 base, 완료된 단계와 확인된 원격 게시를 중복 처리하지 않는다.
- 반복 원격 전진과 게시 경쟁은 작업물을 보존하는 일시 재시도로 처리한다. fetch 실패, 원격 재작성·삭제, 소유권·범위 불명확은 오래된 기준으로 게시하거나 원격을 덮어쓰는 결과를 만들지 않는다.
- 기존 planning 오류·승인 대기·Review 실패·독립 차단은 해당 원인의 해소 검사 없이 지워지지 않는다. rebase 후 PR의 실제 종료를 확인한 경우 구현 재개 대신 기존 종료 처리를 따른다.
- 로그에서 관리 작업, 이전·새 base, 후보 HEAD, 반영·재검증·재개 단계 또는 남은 원인을 확인할 수 있다. 로컬 base ref만 바뀌는 경우에는 원격 변경으로 처리하지 않는다.

## Product Impact

- 원격 변경을 반영할 때 일반·유지보수 planning을 포함한 진행 중 작업과 세션을 보존하고 최신 기준에서 재개한다.
- 보존된 Planner 작성 결과와 비교 기준의 원본을 구분하며, 원격이 그대로인 재개에도 허용된 기존 변경을 검증·게시할 수 있다.
- 작업 재개와 게시 승인을 구분하고 최종 입력·후보에서 유효한 검증 결과만 적용한다.
- 문서 재확인은 단계별 관련 문서의 실제 내용 변경이 있을 때만 수행한다. Planner는 현재 작성·평가 중인 계획에 영향을 주는 설계·계획 문서, Worker·Reviewer는 현재 진행 중인 ExecPlan의 변경을 확인하고 나머지 문서 변경은 건너뛴다.

## Non-Goals

- 기본 checkout에서 rebase하거나 사용자 로컬 변경을 자동 게시하지 않는다.
- Planner·Worker·Reviewer의 파일 변경 권한, mutable READY 대상 또는 유지보수 mode 권한을 확대하지 않는다.
- force push 허용 범위를 확대하거나 branch protection을 우회하거나 PR을 자동 Merge하지 않는다.
- archive-only 임시 작업이나 관리 runtime checkout을 사용자 변경 작업과 같은 재개 대상으로 바꾸지 않는다.
- 같은 프로젝트의 병렬 Git 변경, 실행 중 Agent 선점, 새로운 외부 서비스 또는 비호환 저장 형식 변경을 도입하지 않는다.
