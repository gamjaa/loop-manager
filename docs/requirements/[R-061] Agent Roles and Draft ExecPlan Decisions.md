# [R-061] Agent 역할·문서 권한과 draft ExecPlan 사용자 판단

## Context

Planner는 필요한 근거를 읽어 계획하고, Worker는 구현에 필요한 코드·설계·계획을 함께 수정하며, Reviewer는 관련 변경이 요청한 목표를 충족하는지 확인한다. 저장소를 읽을 수 있는 범위와 각 역할이 수정할 수 있는 범위를 구분한다.

현재 Planner는 FUTURE_IDEAS도 작성할 수 있고, Worker는 ARCHITECTURE와 일반 Requirement 수정을 거부하는 경로가 있다. 모호한 설계·계획을 사용자 판단 대기용 ExecPlan으로 게시하는 draft 흐름은 없다. 이런 문서·권한 제한 때문에 개별 작업의 판단 대기가 프로젝트 전체 차단으로 확대되지 않도록 변경한다.

이 Requirement는 PRODUCT·ARCHITECTURE·공통 및 역할별 실행 지침·PLANS의 해당 역할 제한과 초안 없는 계획 정책을 대체한다. R-049의 역할 선택과 R-057의 변경 중심 검토·최종 확인은 유지하되, 작성 권한과 모호한 계획의 처리에는 아래 정책을 적용한다. 정적 역할 권한은 R-064의 해당 역할 instruction과 실제 범위 검사에 함께 반영하며, 사용자 prompt만 고쳐 상위 권한 제한을 우회하지 않는다. 현재 구현이 완료됐다는 뜻은 아니다.

## Requirement

### 역할별 접근과 작업 범위

| 역할 | 읽기 | 쓰기와 책임 |
|---|---|---|
| Planner | 프로젝트 저장소 전체를 읽을 수 있다. | 허용된 ExecPlan을 작성·개정하고 범위 밖 아이디어를 `docs/FUTURE_IDEAS.md`에 생성·수정할 수 있다. 설계·제품 문서·코드·설정·공통 및 역할 지침은 수정하지 않는다. |
| Worker | 프로젝트 저장소 전체를 읽을 수 있다. | 현재 작업에 필요한 저장소 작업 파일 전체를 수정할 수 있다. 설계·계획·제품 문서와 공통 및 역할 지침도 포함한다. |
| Reviewer | 프로젝트 저장소 전체를 읽을 수 있다. | 파일을 수정하지 않고 현재 작업에 관련된 문서·diff·기존 검증 결과를 중심으로 검토한다. |

전체 저장소 접근은 선택한 프로젝트의 관리 작업 공간을 기준으로 한다. 기본 checkout·다른 프로젝트·다른 작업 공간 또는 Manager의 실행 상태·Git 소유권을 변경할 권한으로 확대하지 않는다. 읽기 권한은 매 호출에서 모든 파일을 읽어야 한다는 뜻이 아니며, 관련 영향의 확인에 필요한 범위를 선택한다.

Planner의 기존 계획 개정은 미착수·무소유 대상과 허용된 snapshot·유지보수 mode의 보호 조건을 유지한다. 사용자 판단 대기 draft도 미실행·무소유가 확인된 대상만 개정할 수 있으며, 다른 계획의 실행 이력을 변경하거나 이미 실행한 계획을 draft로 돌리지 않는다. R-049의 빠른 점검은 계속 읽기 전용이다.

일반 Planner는 현재 PRODUCT·Requirement 범위 밖이지만 보존 가치가 있는 아이디어를 `docs/FUTURE_IDEAS.md`에 생성·수정할 수 있다. 유지보수 Planner는 일반 계획 작성을 허용한 mode에서만 같은 권한을 가진다. 파일 삭제는 허용하지 않으며, 그 항목을 같은 계획 주기의 ExecPlan 범위나 현재 미충족 작업의 근거로 사용하거나 자동 승격하지 않는다.

파일 수정 권한과 제품 목표를 구분한다. Worker는 합의된 목표와 현재 작업을 구현하기 위해 관련 문서를 수정할 수 있지만, 무관한 새 기능이나 다른 계획의 목표를 추가 구현하지 않는다. 별도 사용자 승인이 필요한 목표·Non-Goal·비가역 변경 등의 결정을 문서 수정으로 대신 승인하지 않는다. commit·fetch·rebase·push·PR 생성은 계속 Manager가 담당한다.

코드·설계·계획 변경 때문에 다른 문서의 경로·계약·dependency·구현·검증 설명도 달라져야 하면 Worker는 필요한 문서를 함께 갱신하고 변경 이유·영향을 남긴다. Planner는 영향받는 ExecPlan을 허용된 미착수·무소유 snapshot에서 개정하며 제품·설계 문서까지 수정하지 않는다. 다른 실행 작업·미해결 사용자 결정·기존 목표를 덮어쓰지 않고, 변경된 문서·구현·관계의 정합성을 검증한다.

### 모호한 계획의 draft 작성과 게시

- Planner가 설계·계획의 모호함이나 상충 때문에 구현 방향을 확정할 수 없으면, 확정된 목표·근거·범위와 미결정 사항을 기록한 draft ExecPlan을 작성한다. 임의의 가정을 확정 계획으로 만들거나 그 모호함만으로 프로젝트 planning 오류를 만들지 않는다.
- draft에는 사용자가 판단할 질문, 확인한 사실, 가능한 선택과 작업에 미치는 영향을 적는다. 알 수 없는 구현 세부는 미결정으로 표시할 수 있지만 ID·sources·dependency 등 catalog 식별·연결 정보는 유효해야 한다.
- 계획 파일의 `draft: true`는 미실행 계획의 작성 준비도 선언으로 사용한다. 실행 phase·retry·session·workspace·PR 상태는 계속 SQLite가 관리한다. 기존 draft 표시가 없는 계획은 종전의 작업 가능한 계획으로 해석한다.
- Planner 종료 후 Manager는 유효한 draft를 해당 planning 주기의 다른 게시 대상 문서·계획과 함께 검증·push한다. 사용자 답변이나 Worker 실행까지 게시를 미루지 않는다. 다른 문서와 함께 게시한다는 이유로 Planner의 문서 수정 권한을 확대하거나 기본 checkout의 무관한 변경을 포함하지 않는다.
- 게시된 draft는 사용자 판단 대기로 등록하고 Worker 선택·workspace 예약·구현 branch·구현 PR 생성에서 제외한다. 독립적인 작업 가능 계획은 같은 planning 결과에서 정상 등록하고 계속 진행한다.
- draft 표시와 미결정 사항 자체는 `PROJECT_BLOCKED`·프로젝트 planning 오류의 원인이 아니다. 질문과 원격 계획 링크를 알려 사용자가 다른 환경에서도 판단할 수 있게 한다. 같은 미결정 입력의 반복 실행에서 같은 draft와 질문·알림을 중복 생성하지 않는다.

### 사용자 판단과 작업 가능 전환

사용자가 원격 Requirement 또는 ExecPlan을 수정해 선택을 명시하거나 명세를 명확히 하여 기존 질문을 해소하면, 해당 변경을 사용자 판단 근거로 재검토하고 draft 대기를 해제한다. ExecPlan의 `draft` 표시 제거와 정해진 `User Decision` 형식의 반복 작성을 필수로 요구하지 않는다. 명시적인 `User Decision`도 사용자 판단을 전달하는 방법으로 유지한다.

Planner는 변경 전 질문과 최신 사용자 문서의 원격 revision·변경 내용을 대조해 어떤 선택 또는 명세가 질문을 해소했는지, 남은 판단이 있는지와 작업 목표·완료 조건에 미치는 영향을 반환한다. Manager는 사용자 변경 근거와 현재 입력·계획 identity·허용된 개정 범위를 검증하고, 해소가 확인된 동일 ExecPlan의 draft 표시·저장된 판단 대기와 필요한 문서 개정을 정합하게 게시·반영한다. 이 전환을 Agent의 임의 draft 해제나 자기 승인으로 거부하지 않는다. Planner·Worker는 사용자 대신 선택·승인을 만들거나 자신의 문서 수정만으로 사용자 결정을 합성할 수 없다. 사용자 변경의 출처 또는 질문 해소를 확인할 수 없으면 대기로 보존한다.

질문에 답하지 않은 내용 수정, 무관한 문서 변경과 시간 경과는 승인으로 해석하지 않는다. 결정이 불완전하거나 이후 목표·선택에 영향을 주는 변경으로 판단 근거가 달라졌으면 해당 계획은 대기로 보존하고 필요한 질문을 갱신한다. 거절되거나 보류된 계획은 자동 실행하지 않으며 다른 계획은 계속 처리한다. 아직 시작하지 않은 작업 가능 계획에 새 모호함이 생기면 허용된 개정 과정에서 draft로 전환할 수 있다.

질문·선택 영향·판단 근거와 알림 링크는 같은 원격 입력에 결합한다. 최신 문서에서 질문이 해소되거나 바뀌었으면 과거 질문에 최신 링크만 붙여 재통지하지 않는다. 해소 확인 전에는 필요한 남은 질문과 확인하지 못한 근거를 표시하고, 해소 뒤에는 과거 질문과 사용자 변경·전환 근거를 감사 이력으로 보존한다. 원격 입력 경쟁이나 게시·상태 반영 중단은 동일 판단의 재검증·복구로 처리하며, 유효한 해소 근거가 있는 개정을 자기 승인 오류로 반복시키거나 프로젝트 planning 오류로 확대하지 않는다.

작업 가능 전환 뒤에도 모든 `depends_on`의 MERGED 확인과 기존 실행 gate를 충족해야 Worker를 시작한다. draft에 직접·간접으로 의존하는 계획은 대기하지만 독립 계획과 다른 프로젝트를 막지 않는다. draft가 남아 있는 프로젝트는 사용자 판단 대기로 표시하고 완료로 처리하지 않는다. 관련 Requirement도 draft가 미완료로 남아 있으면 완료된 것으로 archive하지 않는다.

### Worker의 문서 수정과 PR 보고

- Worker는 구현에 필요한 PRODUCT·ARCHITECTURE·Requirement·ExecPlan·공통 및 역할 지침·사용 안내·설정·테스트 등을 수정할 수 있다. 설계·계획 문서라는 경로 분류나 기존 문서의 사용자 소유라는 이유만으로 허용된 수정을 범위 위반·작업 차단으로 처리하지 않는다.
- 문서 수정은 현재 작업의 목표와 구현에 맞게 이유·동작·설계·계획·검증을 정합하게 유지하기 위한 것이다. 실패를 숨기려고 Acceptance Criteria를 바꾸거나 사용자 요청·필수 검증을 삭제해 성공으로 만들지 않는다. 다른 ExecPlan을 수정해도 ID·실행 이력·필요한 dependency와 관련 사용자 결정을 보존한다.
- PR 본문에는 실제로 변경된 문서별 경로, 주요 변경 내용, 수정 이유와 제품 동작·설계·계획에 미치는 영향을 요약한다. 새 파일·삭제·이름 변경도 포함하며 파일명 목록이나 일반적인 구현 Summary만으로 대신하지 않는다.
- 각 문서 요약에서 해당 PR의 문서 diff를 바로 열 수 있는 링크를 제공한다. PR head나 diff가 바뀌면 요약과 링크도 최종 변경에 맞게 갱신하고, 변경하지 않은 문서를 수정했다고 보고하지 않는다.
- Manager는 실제 diff와 Worker 보고를 대조해 PR 본문을 완성한다. 누락되거나 오래된 문서 요약·링크는 해당 작업에서 보완하며, 다른 작업의 중단 사유로 확대하지 않는다.

### AGENTS 사용자 판단과 개별 작업 대기


공통·역할별 `docs/AGENTS.*.md`는 R-064의 일반 작업 파일 권한과 PR 보고를 따르며 루트 승인 대상에 포함하지 않는다. 작업 중 파일을 수정해도 고정된 원본 묶음과 현재 instruction은 바뀌지 않는다. 과거 common 승인은 원래 루트 대상·baseline·patch에만 유효하고 새 파일로 이관하지 않는다. 이 경로 구분으로 Planner·Reviewer의 일반 쓰기 제한이나 실행 중 runtime 편집 금지를 완화하지 않는다.

개별 작업의 사용자 판단 대기·중단·차단은 그 작업물과 session을 보존하고 변경 실행 자리를 비운다. 문서 수정·AGENTS 판단 대기·계획의 draft 또는 해당 작업의 검증·Review 문제를 다른 계획의 계획 생성·실행·원격 관측과 다른 프로젝트의 중단 조건으로 전파하지 않는다. 명시적인 dependency 대기와 실제 공유 저장소·소유권·안전 문제가 있는 경우는 별도로 판단하며, 앞의 개별 사유를 그런 프로젝트 안전 문제로 오인하지 않는다.

### Reviewer의 관련 변경 검토

Reviewer는 현재 작업의 목표·승인된 사용자 결정·근거 문서, 구현·문서 diff와 전달받은 검증 결과를 우선 확인한다. 변경 영향이 이어지는 관련 코드는 필요한 범위까지 읽을 수 있지만, 매 Review에서 저장소 전체 또는 무관한 문서 전문을 다시 검토하도록 요구하지 않는다.

Worker가 수정한 설계·계획도 검토 대상이다. 수정 전 요청과 목표, 수정 이유·새 문서·구현의 정합성 및 PR의 문서 요약·diff 링크를 함께 확인한다. 허용된 문서 수정 자체를 blocking issue로 삼지 않고 실제 목표 불충족·회귀·잘못된 설계·검증 약화를 판단한다. Reviewer는 문서·코드를 수정하거나 테스트·전체 verify를 재실행하지 않으며 기존 Worker targeted test와 Manager 전체 verify 결과로 검토한다.

## Acceptance Criteria

- 일반·유지보수 Planner와 Reviewer는 저장소 전체를 읽을 수 있다. Planner는 허용된 ExecPlan을 작성·개정하고, 일반 Planner와 일반 계획 작성을 허용한 유지보수 mode는 `docs/FUTURE_IDEAS.md`도 생성·수정할 수 있다. FUTURE_IDEAS 삭제·자동 작업 승격과 제품·설계 문서 쓰기는 거부되며 빠른 점검은 읽기 전용이다.
- 설계·계획의 판단이 필요한 경우 유효한 draft에 목표·근거·질문·선택 영향을 기록하고 Planner 종료 시 다른 게시 대상과 함께 원격에 게시한다. 이 draft 때문에 독립 계획 batch를 거부하거나 프로젝트를 차단하지 않는다.
- draft에는 Worker·workspace 예약·구현 branch·PR을 시작하지 않는다. 기존 draft 표시 없는 계획은 정상 처리되고 draft 선언과 실제 실행 상태의 원본이 구분된다.
- 사용자 Requirement 또는 ExecPlan 변경이 선택을 명시하거나 기존 질문을 해소하면 Planner의 영향 판단과 Manager 검증 뒤 동일 계획의 draft 표시·저장된 대기를 해제한다. Requirement만 명확해진 경우와 `User Decision` 형식 없이 ExecPlan 본문으로 선택한 경우에도 반복 승인을 요구하지 않는다. 명시적 `User Decision` 경로는 유지하며, 불완전한 답변·Agent의 자기 승인·표시만 제거한 변경·무관한 변경·재시작은 해소로 처리하지 않는다. 목표에 영향을 준 새 변경은 판단 근거를 다시 확인한다.
- 질문 해소·부분 해소·새 모호함·명시적 거절/보류·변경 출처 불확실과 원격 입력 경쟁을 구분해 전환 또는 대기를 확인할 수 있다. 질문이 없거나 변경된 최신 문서 링크로 과거 질문을 통지하지 않으며, 사용자 변경 revision·질문별 판단·전환 감사는 게시와 상태 반영의 중단·재시작에도 보존된다.
- draft 또는 개별 차단이 남아 있어도 독립 계획과 다른 프로젝트가 진행한다. 직접·간접 dependency 대기, 사용자 판단 대기 표시, 프로젝트 완료와 Requirement archive 조건은 유지된다.
- Worker가 현재 작업에 필요한 ARCHITECTURE·Requirement·PRODUCT·기존 ExecPlan을 수정해도 경로 제한만으로 범위 위반·차단하지 않는다. 합의된 목표·필수 검증·다른 작업 상태와 사용자 변경을 보존한다.
- 코드·설계·계획 변경으로 함께 바뀌어야 하는 관련 문서는 Worker가 갱신하고, Planner는 영향받는 허용 대상 ExecPlan만 개정한다. 최종 문서의 경로·계약·dependency·검증 설명이 구현과 일치하며 관련성만으로 목표·승인·실행 권한을 확대하지 않는다.
- 변경된 모든 문서의 요약·이유·영향과 해당 PR diff 링크를 최종 PR 본문에서 확인할 수 있다. 추가·삭제·rename·rebase·PR head 갱신 뒤에도 실제 최종 diff와 일치한다.
- Reviewer는 관련 문서·구현·문서 변경을 중심으로 읽기 전용 검토하고, 변경 전 목표와 변경 후 결과·PR 보고를 대조한다. 문서 수정만으로 FAIL하지 않으며 파일 쓰기·테스트 재실행을 수행하지 않는다.
- 게시·사용자 판단 반영·작업 가능 전환·PR 보고 갱신의 중단·재시작에서 같은 계획과 결정·작업물을 보존하고 중복 게시·알림·승인 적용을 방지한다.
- 역할 instruction·작업 prompt·계획 형식·catalog·범위 검사·PR 보고가 같은 정책으로 동작한다. 정적 역할 권한은 해당 지침 파일에 반영하고 사용자 prompt에 중복하지 않는다. 실행 이력·Git 쓰기·최종 검증·사용자 Merge의 기존 책임은 유지된다.

## Product Impact

- Planner는 ExecPlan을 작성하고 범위 밖 아이디어는 FUTURE_IDEAS에 보존한다. 모호한 계획은 원격에 게시한 draft로 사용자 판단을 기다린다.
- Worker는 현재 작업에 필요한 설계·계획 문서를 함께 수정하며 사용자가 PR에서 그 변경을 바로 확인할 수 있다.
- Reviewer는 관련 변경을 중심으로 검토하고 개별 판단 대기·차단은 독립 작업을 막지 않는다.

## Non-Goals

- Planner에 제품·설계·AGENTS 수정 권한을 주거나 사용자 판단을 Agent가 대신 승인하지 않는다.
- 저장소 쓰기 권한을 무관한 목표·외부 작업 공간·Manager 실행 상태 변경 권한으로 확대하지 않는다.
- dependency·AGENTS 승인·실제 공유 안전 문제·최종 검증·사용자 Merge를 생략하지 않는다.
- 실행된 계획을 draft로 되돌려 기존 실패·실행 이력을 없애거나 draft를 구현 PR의 Draft 상태와 혼동하지 않는다.
- 같은 프로젝트의 병렬 변경 또는 새로운 외부 서비스를 추가하지 않는다.
