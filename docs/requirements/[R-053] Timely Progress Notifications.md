# [R-053] 이벤트 시점에 맞춘 진행 상황 알림

## Context

현재 Telegram 알림은 PR 생성, 최종 차단, 지속 실행 실패, 차단 후 재개, 안정적인 작업 대기와 프로젝트 완료를 다룬다. 새 PR은 상태 확정 직후 전송하는 경로가 있지만, 일반 작업 시작과 새 계획 생성은 알림 대상이 아니며 나머지 이벤트는 실행 경계까지 전송이 늦어질 수 있다. 전송 시 무음 여부도 구분하지 않는다.

사용자가 알림만으로 무엇이 진행 중이고 어떤 대응이 필요한지 알 수 있도록, 실제 이벤트에 가까운 시점에 필요한 정보를 전달한다.

## Requirement

### 이벤트와 내용

- 신규 ExecPlan 작성이 끝나면 프로젝트, 작성 결과와 다음 진행 상태를 알린다. 작성한 계획의 ID·제목, 새 계획 없음과 작성 실패를 구분한다. 미게시 작성 결과는 실행 가능한 계획 생성 성공으로 표현하지 않는다. 작성과 게시가 같은 전송 시점에 확정됐으면 하나의 알림으로 묶을 수 있다.
- 새 ExecPlan이 원격에 게시되고 catalog에 반영되면 프로젝트, 생성된 계획의 ID·제목과 다음 진행 상태를 알린다. 같은 batch의 여러 계획은 하나의 알림으로 묶을 수 있다. R-061의 draft는 게시된 사용자 판단 대기로, 작업 가능한 계획은 실행·dependency 대기로 구분한다. 검증 전 초안이나 게시 실패를 계획 생성 성공으로 알리지 않는다.
- 게시된 draft에 사용자 판단이 필요하면 질문·선택 영향과 원격 ExecPlan 링크를 포함한 조치 알림을 보낸다. draft를 작업 시작·planning 실패·프로젝트 차단으로 알리지 않으며, 같은 판단 대기를 계획 생성과 승인 요청 두 알림으로 중복 강조하지 않는다.
- 각 계획의 Worker 작업이 실제 시작되면 프로젝트, 계획 ID·제목, 시작 시점과 작업 종류를 알린다. 최초 시작과 중단 뒤 실제 재개를 구분하고, READY 선택만으로 시작을 알리지 않는다. 유지보수 평가처럼 아직 계획 ID가 없는 작업은 해당 단계의 시작임을 표시한다.
- 계획의 검증·Review와 PR 등록이 끝나면 PR 링크와 함께 PR Merge 대기로 전환됐음을 알린다. 이를 구현 작업 종료로 표현하되, 계획의 MERGED 또는 프로젝트 완료와 구분한다.
- 작업 단계가 실패하면 대상 계획 또는 planning 단계, 실패 시점, 확인된 원인과 현재 처리 상태를 알린다. 자동 교정·재시도 예정, 다음 외부 실행에서 재개, 사용자 조치 필요를 구분한다. 같은 실패 사건의 변화 없는 재관측과 내부 재시도마다 알림을 반복하지 않는다.
- 기존 차단·재개·대기·완료 알림에도 실제 상태와 확인된 사용자 행동을 표시한다. PR은 프로젝트·ExecPlan·작업 내용·URL·Merge 대기를, 차단은 확인된 조치·차단 작업·원인·대상/질문·복구/Checkpoint를 우선순위대로 구성한다. 대기는 사용자 행동이 필요한 항목을 먼저 두되 나머지 사유도 보존한다. 자동 복구 가능한 오류만으로 사용자 조치를 요구하거나 확인되지 않은 수정 경로·복구 성공을 추측하지 않는다.
- 진행 알림에는 현재 프로젝트가 작업 중인지, 자동 재개를 기다리는지, PR Merge 또는 사용자 조치를 기다리는지 알 수 있는 정보를 포함한다. 발생 시점을 표시해 전송이 늦어진 과거 이벤트를 현재 상태로 오인하지 않게 한다.

### 시점과 주의 수준

이벤트가 확정된 뒤 가능한 한 빨리 같은 실행에서 전송을 시도한다. 다음 장시간 Agent 호출, 전체 verify 또는 프로젝트 실행 종료까지 알림을 의도적으로 모아 두지 않는다. 상태가 확정되기 전 성공을 전송하지 않으며, 기존 차단 알림은 최종 차단과 checkpoint 결과가 확정된 뒤 전송한다.

계획 작성·생성, 작업 시작, 자동 재개·교정·재시도와 프로젝트 완료처럼 사용자의 대응이 필요 없는 참고 알림은 무음으로 보낸다. draft 판단·AGENTS 승인 요청, PR 검토·Merge 요청과 사용자가 해결해야 하는 최종 실패·차단은 일반 알림으로 보낸다. 실패 또는 계획 생성이라는 사건명만으로 주의 수준을 정하지 않고 실제 조치 필요성을 기준으로 구분한다.

전송 실패와 지연은 계획·프로젝트의 실행 상태나 검증 결과를 바꾸지 않는다. 기존 durable outbox, 실패 재시도, 중복 제거와 분할 메시지 전송 이력을 재사용하고, 전송 때문에 프로젝트의 진행이 무기한 대기하지 않게 한다. 재시작 뒤 전송하는 알림도 원래 사건의 발생 시점과 무음 여부를 유지한다. 이미 해소된 차단의 미전송 알림은 기존 취소 정책을 유지한다.

## Acceptance Criteria

- 계획 작성 결과, 새 계획 batch 게시·catalog 반영, 계획의 실제 Worker 시작, PR 등록과 단계 실패 각각에서 대상·발생 시점·현재 처리 상태를 식별할 수 있는 알림이 생성된다. 같은 전송 시점의 작성·게시 완료는 합칠 수 있다.
- 작업 시작과 새 계획 생성 알림은 뒤따르는 장시간 Agent·verify 실행 전에 전송을 시도한다. 실패·차단·PR 등록도 확정 후 같은 실행에서 가능한 즉시 전송을 시도한다.
- READY 생성이나 선택만으로 Worker 시작을 알리지 않고, 실패한 계획 게시를 생성 성공으로 알리지 않는다. PR 등록은 Merge 대기이며 MERGED·프로젝트 완료로 표시하지 않는다.
- 참고용 이벤트는 무음으로 전송되고 PR 검토·Merge, 승인과 최종 사용자 조치는 일반 알림으로 전송된다. 자동 재시도 중인 실패도 무음이다.
- draft 게시·판단 요청은 원격 링크와 필요한 결정을 알리는 일반 알림이며 Worker 시작·planning 오류·프로젝트 차단으로 표시되지 않는다. 같은 질문의 재관측과 변화 없는 새 계획 없음은 알림을 반복하지 않는다.
- 같은 사건의 반복 관측·내부 재시도·재시작은 알림을 중복 생성하지 않는다. 실제 새 시작, 별도 실패 사건 또는 대응 상태 변화는 구분할 수 있다. 기존 차단 후 재개 알림과 일반 재개 알림은 같은 재개를 중복 통지하지 않는다.
- 전송 실패·부분 전송·재시작 뒤 기존 전송 이력으로 재개하며, 실제 작업은 계속할 수 있다. 늦게 전송된 이벤트는 원래 발생 시점을 유지한다.
- PR·차단·대기 알림은 확인된 조치와 작업 상태를 먼저 보여주고 원인·질문·나머지 대기 사유·복구·Checkpoint를 보존한다. 긴 메시지에도 정보가 누락되지 않으며 Telegram 비활성화·일부 설정 오류·비밀값 비노출·완료 판단 조건은 유지된다.

## Product Impact

- 알림이 실제 이벤트 시점에 가까워지고 계획 생성부터 작업 시작·실패·PR 대기까지 진행을 파악할 수 있다.
- 사용자의 행동이 필요한 알림과 참고용 무음 알림을 구분한다.

## Non-Goals

- 이벤트 없이 반복하는 상태 방송, 실시간 대시보드 또는 새로운 알림 서비스를 추가하지 않는다.
- Telegram의 네트워크·서비스 지연까지 포함한 절대 전송 시간을 보장하지 않는다.
- 내부 재시도마다 같은 실패를 알리거나 알림 실패로 작업을 차단하지 않는다.
- 메시지 생성에 LLM·외부 의존성·새 상태 저장 구조를 추가하지 않는다. 표시 순서 개선만으로 알림 유형·전송 조건·deduplication·outbox 계약을 변경하지 않는다.
