# [R-053] 이벤트 시점에 맞춘 진행 상황 알림

## Context

Telegram 알림만으로 진행 상황과 필요한 대응을 파악할 수 있도록, 알림 대상·주의 수준·전송 시점을 정리한다. 사용자가 인지할 필요 없는 내부 자동 처리에는 무음 알림도 보내지 않는다.

## Requirement

### 알림 대상과 주의 수준

| 이벤트 | 전송 | 확정 조건과 내용 |
|---|---|---|
| 새 ExecPlan 생성 | 무음 | 원격 게시와 catalog 반영이 완료되면 새 계획의 ID·제목과 실행·dependency 대기를 알린다. draft는 사용자 판단 알림으로 통합한다. |
| Worker 작업 시작 | 무음 | 실제 최초 시작과 대상 계획·작업 종류를 알린다. READY 생성·선택만으로 알리지 않는다. |
| 프로젝트·작업 차단 해제 후 작업 재개 | 무음 | 아래 사건 연결 조건을 충족한 실제 재개와 이전 차단 원인·시작한 작업을 알린다. |
| 유지보수 시작·종료 | 무음 | 실제 cycle 시작과 후속 작업까지 포함한 정상 종료를 알린다. 계획 ID가 없어도 대상 범위·시작 또는 종료 사유·다음 진행 상태를 포함한다. |
| 프로젝트 완료 | 무음 | 기존 프로젝트 완료 조건을 충족했을 때 알린다. PR 등록·개별 계획 Merge·유지보수 종료만으로 완료를 알리지 않는다. |
| 작업 완료(PR 등록) | 일반 | 검증·Review와 PR 등록 완료 후 PR 링크와 검토·Merge 요청을 알린다. 계획의 MERGED와 구분한다. |
| 프로젝트·작업 최종 차단 | 일반 | 최종 차단과 checkpoint 결과 확정 후 확인된 원인·사용자 조치·보존 상태를 알린다. |
| 사용자 판단 필요 | 일반 | 게시된 draft의 질문·선택 영향·원격 ExecPlan 링크 등 확인된 판단 대상과 필요한 결정을 알린다. |
| 지속 실행 실패로 사용자 조치 필요 | 일반 | 기존 지속 실패 판정과 실제 조치 필요성을 충족한 경우 원인·처리 상태·확인된 조치를 알린다. 같은 최종 차단과 중복 통지하지 않는다. |
| 대기로 시작 가능한 작업 없음 | 일반 | 프로젝트 차단을 제외하고 미완료 작업의 대기로 시작 가능한 작업이 없을 때 알린다. PR Merge·작업 차단·사용자 판단·dependency·활성 Requirement의 대기 사유를 포함한다. |
| Planner 시작·Reviewer 시작/종료 | 전송하지 않음 | 일반·빠른·유지보수 Planner의 개별 호출 시작과 Reviewer의 시작·종료는 별도로 알리지 않는다. 차단 후 실제 재개와 최종 사용자 조치는 해당 알림 조건을 따른다. |
| 단순 단계 실패·자동 교정·재시도·자동 재개 | 전송하지 않음 | 다음 외부 실행의 자동 재개도 포함한다. 실행 결과·로그·실패 이력은 보존한다. 사용자 판단이나 최종 차단으로 전환되면 해당 이벤트를 알린다. |

알림에는 프로젝트·대상 계획 또는 단계, 사건의 발생 시점과 현재 처리 상태를 포함한다. 작업 중·자동 재개 대기·PR Merge 대기·사용자 조치 대기를 구분하고, 늦게 전송된 과거 이벤트를 현재 상태로 오인하지 않게 한다.

### 예외와 중복 통지

- 생성 알림은 같은 batch의 여러 새 계획을 묶을 수 있다. 작성 완료·미게시·검증 전 초안·게시 실패, 새 계획 없음 또는 기존 계획 개정·삭제만으로는 생성 알림을 보내지 않는다. 작성·게시 실패는 사용자 조치·최종 차단 기준을 따른다. 새 계획이 없어도 다른 확정된 알림 대상은 해당 기준을 따른다.
- 같은 draft의 생성과 판단 요청은 하나의 일반 알림으로 통합한다. draft를 작업 시작·planning 실패·프로젝트 차단으로 표시하지 않는다.
- 재개는 BLOCKED 알림의 한 조각 이상 전송이 확인된 사건에서 해당 계획 또는 프로젝트의 정상 작업이 실제 시작된 경우에만 사건당 한 번 알린다. 단순 해제·다른 계획 시작·미전송 차단에는 만들지 않으며, 동일 재개에 Worker 시작 알림을 추가하지 않는다.
- 유지보수 종료는 R-074의 이번 범위 계획·필요한 dependency의 실제 Merge와 상태 반영을 마친 시점이다. 계획이 없으면 평가 결과 검증과 필요한 게시·등록을 마친 시점이다. 평가만 끝났거나 실패·중단·PR 대기인 상태는 정상 종료가 아니며, 내부 모듈 묶음 평가·교정·재시도를 별도 cycle 사건으로 세지 않는다.
- 대기는 프로젝트별 안정적인 작업 선택 결과를 기준으로 한다. 프로젝트 차단 중이거나 독립적인 실행 가능 작업·진행 또는 복구 중인 단계·일시 실패의 자동 처리만 기다리는 상태에는 별도 대기 알림을 보내지 않는다. 그 외에는 개별 PR·작업 차단·사용자 판단 알림을 이미 보냈어도, 그 대기 때문에 시작 가능한 작업이 없으면 프로젝트 대기 알림을 보낸다.
- 동일 사건·같은 질문·같은 안정적 대기는 반복 관측·재실행·재시작 뒤 중복 통지하지 않는다. 실제 작업 진행 또는 관련 입력·원인이 바뀐 새 대기는 한 번 다시 알릴 수 있다.

### 표시 내용

PR은 프로젝트·ExecPlan·작업 내용·URL·Merge 대기 순으로, 차단은 확인된 조치·차단 작업·원인·대상/질문·복구/Checkpoint 순으로 표시한다. 대기는 확인된 사용자 행동을 먼저 두고 나머지 사유도 보존한다. 사건명이나 실패 횟수만으로 조치를 추측하거나 자동 복구 가능한 오류만으로 조치를 요구하지 않으며, 확인되지 않은 수정 경로·복구 성공을 안내하지 않는다.

### 전송 시점과 실패 처리

이벤트가 확정된 뒤 가능한 한 빨리 같은 실행에서 전송을 시도한다. 다음 장시간 Agent 호출, 전체 verify 또는 프로젝트 실행 종료까지 의도적으로 모아 두거나 상태가 확정되기 전 성공을 전송하지 않는다.

전송 실패와 지연은 계획·프로젝트의 실행 상태나 검증 결과를 바꾸지 않는다. 기존 durable outbox, 실패 재시도, 중복 제거와 분할 메시지 전송 이력을 재사용하고, 전송 때문에 프로젝트의 진행이 무기한 대기하지 않게 한다. 재시작 뒤에도 원래 사건의 발생 시점과 무음 여부를 유지한다.

정책 적용 전에 outbox에 저장된 미전송·부분 전송 알림은 새 정책의 제외 대상이어도 기존 전송 이력에 따라 그대로 전송한다. 알림 대상 변경만을 이유로 취소·재작성·주의 수준 변경을 하지 않는다. 이미 해소된 차단 등 기존 상태 해소에 따른 취소 정책은 유지한다.

## Acceptance Criteria

- 표의 알림 대상에 해당하는 사건을 확정하면 지정된 일반·무음 수준과 대상·발생 시점·처리 상태로 알리고, 다음 장시간 Agent·verify 실행 전에 전송을 시도한다.
- 작성 완료만 있거나 게시가 실패한 경우, 새 계획이 없거나 기존 계획 개정·삭제만 있는 경우에는 생성 알림이 없다. 새 일반 계획과 draft가 함께 게시되면 각 계획의 준비도와 필요한 판단을 구분하며 같은 draft를 중복 강조하지 않는다.
- 일반·빠른·유지보수 Planner가 호출되거나 Reviewer가 시작·종료돼도 별도 알림이 없다. 단계 실패·내부 재시도와 다음 외부 실행의 자동 재개에도 새 알림이 없다. 실패가 지속 실패 판정의 사용자 조치 또는 최종 차단으로 전환되면 해당 알림을 만들고 기존 실패 이력은 보존한다.
- 통지된 차단이 해제된 뒤 해당 작업이 실제 재개되면 한 번만 알린다. 단순 해제·다른 계획 시작·미전송 차단과 동일 재개의 Worker 시작에는 별도 알림이 없다.
- 유지보수 cycle 시작 알림은 개별 Planner 호출과 구분해 한 번만 보낸다. 평가 완료 뒤 후속 계획이 남으면 종료 알림이 없고, 마지막 실제 Merge·상태 반영 뒤 종료를 알린다. 후속 계획이 없으면 평가 결과 검증·필요한 게시·등록 뒤 종료를 알린다. 반복 실행에서 내부 평가나 cycle 종료를 중복 통지하지 않는다.
- 프로젝트가 차단되지 않은 상태에서 PR Merge·작업 차단·사용자 판단 대기로 실행 가능한 작업이 없어지면, 개별 조치 알림의 전송 여부와 관계없이 일반 대기 알림이 있다. 동일 대기를 재시작 뒤 반복하지 않고, 프로젝트 차단·실행 가능 작업·진행 또는 복구 중인 단계·일시 실패의 자동 처리만 기다리는 경우에는 대기 알림이 없다.
- 정책 적용 전 제외 대상 알림이 미전송·부분 전송 상태이면 기존 내용·주의 수준·전송 이력으로 이어 보낸다. 전송 실패·재시작에도 실제 작업은 진행할 수 있고, 기존 상태 해소의 취소와 중복 제거는 유지된다.
- 긴 PR·차단·대기 메시지에도 원인·질문·나머지 대기 사유·복구·Checkpoint가 누락되지 않는다. Telegram 비활성화·일부 설정 오류·비밀값 비노출과 기존 프로젝트 완료 판단 조건을 유지한다.

## Product Impact

- 계획 생성·작업 시작·차단·PR 대기·유지보수·완료를 실제 사건 시점에 가까운 알림으로 파악할 수 있다.
- 일반·무음·알림 제외를 구분하고, 프로젝트 차단 외의 대기로 실행 가능한 작업이 없어진 상태를 알린다.

## Non-Goals

- 이벤트 없이 반복하는 상태 방송, 실시간 대시보드 또는 새로운 알림 서비스를 추가하지 않는다.
- Telegram의 네트워크·서비스 지연까지 포함한 절대 전송 시간을 보장하지 않는다.
- 알림을 위해 실행 상태·복구·checkpoint·완료 조건을 변경하거나 알림 실패로 작업을 차단하지 않는다.
- 메시지 생성에 LLM·외부 의존성·새 상태 저장 구조를 추가하지 않는다. 알림 대상·주의 수준 조정에 필요한 범위를 넘어 기존 outbox·전송 이력·중복 제거 계약을 변경하지 않는다.
