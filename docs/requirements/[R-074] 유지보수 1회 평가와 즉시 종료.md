# [R-074] 유지보수 1회 평가와 즉시 종료

## Summary

유지보수 cycle은 한 번의 평가로 범위를 확정하고 필요한 dependency·작업의 실제 Merge와 상태 반영 뒤 추가 사후 재검증 없이 종료한다. 최초 실행은 일반 모드로 시작하며 자동 주기는 최초 실행 또는 직전 종료 이후 Merge 수와 설정값으로 계산하고, 0은 자동 전환만 끈다. 명시적 요청·활성 cycle·실패 복구는 유지하고 미검토 원본의 성공 근거를 합성하지 않는다.

## Context

유지보수에서 확정한 리팩터링 계획을 구현하고 테스트·전체 verify·Review와 사용자 Merge까지 마쳤는데도, 별도 사후 재검증이나 수정된 코드의 정밀 평가가 이어진다. 실제로 cycle 완료 직후 같은 유지보수가 만든 변경을 근거로 새 targeted 평가가 시작돼 일반 작업으로 복귀하지 못했다.

각 계획의 구현 검증과 Review가 끝난 뒤 유지보수 전용 검증을 추가하면 일반 작업이 밀리고, 새 개선점이 계속 발견되는 동안 종료 시점을 예측하기 어렵다. 유지보수는 한 번 평가해 처리 범위를 확정하고, 그 범위의 작업이 Merge되면 종료해야 한다.

프로젝트 최초 실행도 유지보수 평가로 시작해 일반 작업이 밀리지 않도록, 일반 모드로 시작하고 이후 주기 도달이나 사용자의 명시적 요청에 따라 유지보수를 시작해야 한다.

Merge 수에 따른 자동 주기와 `maintenance-review <repo>`의 명시적 요청은 기존 기능을 재사용한다. 이 문서는 기준값을 변경할 수 있는 기존 설정에 자동 전환 비활성화 값을 추가하고, 자동 주기를 끈 상태에서도 CLI로 유지보수 전환을 요청할 수 있도록 하는 변경을 포함한다.

## Requirement

### 한 주기에 한 번 평가

- 유지보수 cycle마다 평가를 한 번 수행하고, 발견을 새 계획·기존 계획·근거 있는 제외에 연결해 이번 처리 범위를 확정한다. 종료를 위해 발견이 0개가 될 때까지 평가하지 않는다.
- 한 번의 평가는 선택한 범위의 모듈 묶음 검토와 필요한 결과 종합·계획 작성을 포함한다. 모델 호출 한 번이나 모듈 묶음 하나만을 뜻하지 않는다. 기존 원본에 결합된 검토 결과 재사용과 범위 선정은 유지한다.
- 이번 범위에는 평가에서 확정한 prerequisite·리팩터링 계획과 실행에 필요한 미충족 선행 dependency를 포함한다. prerequisite의 Merge나 리팩터링 변경을 이유로 새로운 평가를 시작해 처리 범위를 계속 늘리지 않는다.
- 평가·결과 검증·게시의 일시 실패와 중단은 같은 cycle의 미완료 작업으로 재개한다. 원본이 바뀐 경우 해당 결과의 유효성을 확인하고 필요한 관련 범위만 다시 확인한다. 오래된 결과를 현재 원본의 성공 근거로 사용하거나 저장소 전체 개선 탐색을 반복하지 않는다.

### 마지막 계획 Merge 뒤 종료

- 확정한 계획은 기존 dependency·승인·작업 공간·게시 규칙을 따라 구현한다. 각 계획의 targeted test·전체 verify·Reviewer blocking issue 해소와 사용자 Merge를 유지한다. 검증 실패와 Review 교정은 해당 계획에서 해결한다.
- 리팩터링 뒤 별도의 유지보수 사후 재검증 단계나 재검증 Planner를 실행하지 않는다. 기존 READY 계획의 구조 참조 개정을 별도 유지보수 종료 조건으로 요구하지 않는다.
- 이번 범위의 마지막 계획이 실제 Merge됐음을 확인하면 cycle을 종료하고 유지보수 장벽을 해제한다. 해당 Merge의 원격 관측과 catalog 반영 등 객관적 상태 처리는 완료해야 하지만, 추가 모델 검토를 종료 조건으로 두지 않는다.
- 수정할 계획이 없으면 평가 결과의 검증과 필요한 게시·등록을 마친 뒤 바로 cycle을 종료한다.
- 종료 후에는 기존 일반 Planner·READY 선택 정책으로 돌아간다. 실행 가능한 일반 작업이 없으면 정상 대기·완료 판단으로 진행하며, 작업이 없다는 이유로 유지보수를 다시 시작하지 않는다. 일반 작업의 기존 dependency는 보존한다.
- 유지보수 종료는 프로젝트 전체 완료 판단을 대신하지 않는다. 일반 계획의 입력 변경 처리와 최종 제품 충족 확인은 기존 역할·조건을 따른다. 일반 Planner를 유지보수 재검증의 대체 단계로 추가 호출하지 않는다.

### 다음 평가 시작 조건

- 프로젝트 최초 실행은 일반 모드의 Planner·READY 선택으로 시작한다. 유지보수 평가·전체 점검 성공 이력이 없다는 이유만으로 자동 유지보수 cycle이나 정밀 검사를 시작하지 않는다. 일반 작업이 없으면 기존 대기·완료 판단으로 진행한다.
- 유지보수 이력이 없는 프로젝트는 최초 실행 시 확인한 MERGED 수를 첫 자동 주기의 기준으로 보존한다. 첫 자동 유지보수는 그 기준 이후 새로 확인한 MERGED 수가 `refactoring_review_interval`에 도달했을 때 시작하며, 이후에는 직전 cycle 정상 종료 기준을 사용한다. 첫 전체 정밀 점검은 최초 실행에 강제하지 않고 첫 유지보수 cycle에서 수행한다.
- 자동 주기의 기준값은 `config/config.ini`의 `[loop] refactoring_review_interval`에서 변경한다. 기본값 20을 유지하고 0 이상의 정수를 허용한다. 양수 n이면 기준 이후 새로 확인한 MERGED 작업이 n개 이상일 때 다음 안전한 작업 선택 경계에서 자동 유지보수로 전환한다. 음수·정수가 아닌 값은 오류로 거부한다.
- 기준값 0은 자동 유지보수 전환을 끈다. Merge 수·평가 이력 부재·코드 영향·완료 후보를 이유로 자동 cycle이나 유지보수 Planner를 시작하지 않는다. 일반 작업·계획 수립·프로젝트 최종 확인은 계속하며, 명시적 유지보수 요청과 이미 시작한 cycle의 정상 진행·종료는 유지한다.
- 기준값을 변경해도 저장된 최초 실행·직전 정상 종료 기준과 Merge 수를 초기화하지 않는다. 다음 안전한 선택 경계에서 변경한 값으로 판단한다. 0에서 양수로 바꿨을 때도 비활성화 기간의 Merge를 포함한 같은 기준을 사용하며, 이미 기준값에 도달했으면 기존 안전 조건을 만족할 때 전환한다.
- 종료 기준에는 마지막 유지보수 계획까지 반영한 MERGED 수를 사용한다. 이번 cycle에서 처리한 계획의 Merge는 다음 평가 주기를 즉시 도래시키지 않는다. 평가 시작 시 이미 도래했던 주기를 종료 직후 다시 처리하지 않는다.
- 주기 도달 전에는 코드 변경·정적 분석의 영향 발견·성공 평가 원본과 최신 코드의 차이·프로젝트 완료 후보만으로 새 유지보수 cycle이나 정밀 검사를 시작하지 않는다. 최초 자동 유지보수에도 같은 조건을 적용하며, 사용자의 명시적 요청은 예외로 둔다.
- 사용자의 새 명시적 유지보수 요청은 주기 도달 전이나 기준값 0에서도 새 cycle을 시작할 수 있다. [R-076](<[R-076] 운영 명령어와 상태 조회 및 Skill 지원.md>)의 `maintenance-review <repo>`를 유지보수 전환 요청으로 사용한다. 등록 대상·요청·대기 사유를 확인하고 다음 안전한 작업 선택 경계에서 적용하며, 활성 cycle이나 실행 중 작업을 선점하지 않는다. 같은 요청을 종료·재시작마다 반복 적용하지 않는다.
- 실제 평가 성공 근거와 cycle 종료에 따른 다음 실행 주기 기준을 구분한다. 수정 뒤 재검증을 생략했다는 이유로 수정된 원본에 대한 정밀 검토 receipt를 만들거나 과거 전체 점검 성공 원본을 최신 원본으로 바꾸지 않는다.

### 중단·기존 cycle·안전 조건

- 최초 실행의 주기 기준, 평가 범위, 확정한 계획, 종료 여부와 처리한 사용자 요청을 재시작 뒤에도 보존한다. 재시작마다 최초 실행 기준을 다시 설정해 유지보수를 계속 미루지 않으며, 기준 초기화를 평가 성공이나 cycle 정상 종료로 기록하지 않는다. 마지막 Merge 확인과 cycle 종료 도중 중단돼도 중복 평가·중복 종료·주기 기준의 반복 전진이 발생하지 않아야 한다.
- 정책 적용 시 기존 cycle에 확정된 처리 범위가 있으면 그 작업과 미확정 게시를 보존한다. 필요한 계획이 모두 Merge된 cycle은 별도 사후 재검증 없이 종료하고, 남은 계획이 있으면 해당 범위를 마친 뒤 종료한다.
- 기존 사후 재검증 단계에 머무른 cycle도 마지막 계획의 실제 Merge와 미확정 게시 여부를 확인해 새 평가 없이 종료한다. 이미 작성한 결과·실행 이력은 보존하며, 저장된 게시 작업은 실제 원격 결과와 대조해 확정한다.
- 정상 종료 이력이 있는 기존 유휴 cycle은 그 종료 경계를 다음 주기의 기준으로 사용한다. 기준을 안전하게 확정할 수 없는 경우 임의의 성공 이력을 만들지 않고 해당 불확실성을 기존 복구·사용자 판단 절차로 처리한다.
- 실제 `PROJECT_BLOCKED`, 필요한 계획의 차단, dependency 미충족, 검증 실패와 미확정 게시를 종료로 덮어쓰지 않는다. PR 조회 실패나 Close를 Merge로 취급하지 않으며 자동 Merge도 도입하지 않는다.
- 로그와 진행 알림에서 평가 시작 사유, 이번 처리 범위, 마지막 Merge에 따른 종료와 일반 작업 복귀, 다음 주기 대기 사유를 식별할 수 있어야 한다.

### 기존 정책과의 관계

이 Requirement는 PRODUCT·ARCHITECTURE와 R-054·R-071이 요구하는 유지보수 전용 사후 재검증, prerequisite 이후의 새 평가, 최초 실행의 자동 전체 점검, 마지막 전체 정밀 점검 이후 Merge 수에 따른 자동 시작 기준과 주기 사이 코드 영향에 따른 자동 정밀 평가를 위 규칙으로 대체한다. R-082의 해당 Requirement 즉시 재확인 뒤 due 유지보수의 일반 작업 대비 우선순위, 첫 cycle의 전체 점검, 평가 안의 범위 선정·검토 결과 재사용, 개별 계획의 검증·Review·승인과 실제 공유 안전 gate는 유지한다. PRODUCT·ARCHITECTURE에는 이 변경 목표를 명시하고, 문서 갱신과 실제 구현·운영 검증 완료를 구분한다.

## Acceptance Criteria

- 유지보수 이력과 명시적 요청이 없는 프로젝트의 최초 실행에서는 유지보수 Planner·정밀 평가·유지보수 장벽을 시작하지 않고 기존 일반 Planner·READY 선택을 수행한다. 일반 작업이 없으면 기존 대기·완료 판단을 따른다.
- 최초 실행 시 MERGED 수가 N이고 설정값이 20이면 N+19까지 첫 자동 cycle이 시작되지 않고, N+20에서는 기존 안전·PR 대기 조건을 만족한 다음 선택 경계에서 유지보수를 시작한다. 기존 MERGED 이력이 20개 이상이어도 최초 실행 즉시 주기가 도래한 것으로 처리하지 않는다. 첫 cycle에서는 전체 정밀 점검을 수행한다.
- 최초 실행 뒤 재시작해도 첫 자동 주기 기준은 보존되며, 기준 초기화·보존만으로 평가 성공·cycle 정상 종료·전체 점검 receipt가 생성되지 않는다. 명시적 요청이 있으면 최초 실행에도 기존 안전 조건을 지키며 유지보수를 시작할 수 있다.
- 설정 생략 시 20을 사용하고 0과 양수를 허용하며, 음수·정수가 아닌 값은 오류로 거부한다. 양수 n은 최초 실행·직전 정상 종료 기준 이후 n-1개 Merge까지 기다리고 n개 이상에서 기존 안전 조건을 만족한 다음 선택 경계에 자동 전환한다.
- 기준값 0에서는 Merge가 누적되거나 최초 실행·코드 변경·프로젝트 완료 후보가 발견돼도 자동 cycle·유지보수 Planner·장벽이 시작되지 않는다. 명시적 요청이 없으면 일반 작업과 완료 판단을 계속한다.
- 0에서도 CLI의 새 명시적 요청을 저장하고 기존 안전 조건을 만족한 다음 선택 경계에서 한 cycle을 시작한다. 같은 요청을 재시작·종료 뒤 재적용하지 않으며, 실행 중 작업·pause·PR 대기·프로젝트 차단을 우회하지 않는다.
- 양수의 증감과 0 전환·재활성화 뒤에도 저장된 주기 기준과 Merge 수가 보존된다. 0으로 바꿔도 활성 cycle을 중단·취소하거나 완료로 기록하지 않으며, 양수로 되돌릴 때 이미 누적한 Merge 수를 변경한 기준값에 적용한다.
- 한 cycle에서 여러 모듈 묶음을 검토해 계획을 확정해도 하나의 평가로 처리한다. prerequisite·리팩터링 계획의 Merge 뒤에는 새 평가를 시작하지 않는다.
- 계획이 없는 평가가 정상 확정되면 일반 작업 선택으로 돌아간다. 발견을 기존 계획이나 근거 있는 제외로 처리한 경우에도 발견 0개를 얻기 위한 추가 평가는 없다.
- 확정한 모든 계획의 테스트·전체 verify·Review와 실제 사용자 Merge가 확인되면 별도 유지보수 사후 재검증 호출 없이 cycle을 종료한다. dependency를 충족한 일반 READY가 있으면 다음 정상 선택에서 실행할 수 있다.
- cycle 종료 직후 정적 분석이 공개 계약·저장·복구·관계·루트 배치 변경을 감지하거나 평가 원본과 코드가 달라도, 주기가 아직 도래하지 않았으면 새 정밀 검사를 시작하지 않는다. 동일 조건은 다음 외부 실행에서도 유지된다.
- 종료 시 MERGED 수가 N이고 설정값이 20이면, 명시적 요청 없이 N+19까지 새 자동 cycle이 시작되지 않는다. N+20에서는 기존 안전·PR 대기 조건을 만족한 다음 선택 경계에서 due 유지보수를 시작한다. 주기 중 코드 변경을 이유로 추가 평가를 만들지 않는다.
- 사용자의 새 명시적 요청은 주기 전에도 평가를 시작하며, 같은 요청은 재시작이나 해당 cycle 종료 뒤 재적용되지 않는다. 활성 작업은 선점하지 않는다.
- 실패한 테스트·blocking Review·Close된 PR·PR 조회 실패·미확정 게시·필요한 dependency 대기·실제 프로젝트 안전 차단이 성공이나 정상 종료로 바뀌지 않는다.
- 평가·계획 게시·마지막 Merge 확인·cycle 종료의 각 경계에서 중단 후 재시작해도 작업물과 상태를 보존하며, 이미 확정한 평가의 반복·처리 범위 확장·중복 종료가 없다. 입력 변경으로 무효화된 관련 근거는 필요한 범위에서만 다시 확인한다.
- 기존 리팩터링·사후 재검증 cycle과 정상 종료된 유휴 cycle이 새 종료·주기 규칙으로 이어진다. 미Merge 계획이나 미확정 게시를 버리지 않고, 과거 정밀 검토 성공 기록을 수정 뒤 원본의 검토 성공으로 바꾸지 않는다.
- 종료·복귀·대기 이유와 다음 주기 기준을 로그에서 확인할 수 있다. 일반 Planner의 정상 입력 변경 처리와 프로젝트 최종 완료 확인은 유지되며, 유지보수 재검증을 대신하는 의무 호출은 추가되지 않는다.

## Product Impact

- 유지보수는 평가 1회, 확정한 계획의 구현·검증·Review·사용자 Merge, 일반 작업 복귀로 끝난다.
- 각 계획의 검증과 Review가 완료된 뒤 유지보수 전용 사후 재검증을 요구하지 않는다.
- 프로젝트 최초 실행은 일반 모드로 시작한다. 첫 자동 유지보수 주기는 최초 실행 기준 이후, 다음 주기는 직전 cycle 종료 이후의 Merge 수로 계산한다. 사용자가 기준값을 변경할 수 있고, 0이면 자동 전환 없이 명시적 CLI 요청으로 유지보수를 시작한다.
- cycle 종료와 평가 성공 근거를 구분해, 수정 뒤 검토하지 않은 원본에 성공 이력을 만들지 않는다.

## Non-Goals

- 프로젝트별 targeted test·전체 verify·Review·사용자 Merge·기존 dependency를 생략하지 않는다.
- 유지보수 종료를 프로젝트 전체 완료로 간주하거나 실제 안전 차단을 자동 해제하지 않는다.
- 실행 중 작업의 강제 중단, 새로운 수동 생략 명령이나 운영 DB 직접 수정 절차를 추가하지 않는다.
- 일반 Planner 실행 조건·Requirement 재확인은 R-082를 따르고 이 문서에서 별도로 재정의하지 않는다. 코드 리팩터링의 동작·공개 계약·저장 형식 보존 범위를 변경하지 않는다.
- 새 Agent 역할·외부 서비스·병렬 변경 실행을 도입하지 않는다.
