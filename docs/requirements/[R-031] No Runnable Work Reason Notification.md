# [R-031] No Runnable Work Reason Notification

## Context

현재 프로젝트 완료 알림은 마지막 작업만 알려주고 완료 이유를 설명하지 않는다. ExecPlan이 남아 있지만 dependency, `PR_OPEN` 또는 `PLAN_BLOCKED` 때문에 다음 계획을 시작할 수 없으면 프로젝트는 대기하지만 그 이유를 한눈에 알려주는 알림도 없다. 반복 실행되는 스케줄러가 같은 대기 상태를 매번 알리면 운영 알림이 소음이 된다.

## Requirement

Loop Manager는 PR 상태 동기화, 안전한 자동 복구, 유지보수 및 일반 Planner 필요 여부 확인을 마친 안정적인 작업 선택 시점에 더 이상 시작할 수 있는 ExecPlan이 없으면 프로젝트별로 원인을 포함한 알림을 한 번 보낸다. 아직 시작하거나 재개할 수 있는 Worker·Planner·유지보수 작업이 있거나 일시적 오류 뒤 재시도만 기다리는 중에는 작업 소진으로 판단하지 않는다.

현재 설계와 활성 Requirement에 필요한 작업이 모두 완료되고 남은 활성 Requirement 및 비종료 ExecPlan이 없으면 기존 프로젝트 완료 알림으로 알린다. 알림에는 Planner가 추가 작업이 없음을 확인했고 활성 Requirement가 남지 않았다는 완료 이유와 마지막 완료 작업을 포함한다. 활성 Requirement가 남아 있으면 그 사실을 표시하고 "남은 Requirement 없음"으로 표현하지 않는다.

완료 조건을 충족하지 못했고 시작 가능한 계획이 없으면 별도의 대기 요약 알림을 보낸다. 알림에는 프로젝트명, 남은 ExecPlan의 ID·제목과 계획별 시작 불가 이유를 포함한다. 예를 들어 미충족 `depends_on`의 선행 ID·현재 상태, `PR_OPEN`의 Merge 대기, `PLAN_BLOCKED`의 확인된 원인과 필요한 사용자 조치를 구분한다. 비종료 ExecPlan 없이 활성 Requirement가 남았으면 해당 ID와 archive 또는 추가 계획을 기다리는 이유를 표시한다. 프로젝트 안전 차단 또는 `planning_error`가 작업 선택을 막으면 그 원인도 포함하고 완료로 표현하지 않는다. 알림 내용은 현재 확인된 원인에 한정하며 미확정 원인을 추측하지 않는다.

같은 작업 소진·대기 상태의 반복 실행은 알림을 다시 만들지 않는다. 이후 시작 가능한 작업이 생겨 진행하거나 입력·차단 원인이 바뀌어 새로운 안정 상태가 되면 다음 별도 사건을 한 번 알릴 수 있다. 기존 PR·BLOCKED 알림과 프로젝트 완료 알림의 전송 및 중복 방지 계약을 유지하고, Telegram이 꺼져 있어도 원인을 실행 결과와 로그에서 확인할 수 있어야 한다.

## Acceptance Criteria

- Planner 필요 여부와 자동 복구를 확인한 뒤 시작 가능한 ExecPlan이 없고 다른 자동 작업도 남지 않은 안정 상태에서 정확한 이유를 포함한 알림이 한 번 생성된다.
- Planner가 추가 작업이 없음을 확인하고 활성 Requirement, 비종료 ExecPlan, 미해결 planning error·프로젝트 차단 및 활성 유지보수 작업이 없으면 기존 완료 알림 한 건이 전송된다. 설계상 작업 완료와 남은 활성 Requirement 없음, 마지막 완료 작업을 명시한다.
- 활성 Requirement가 남아 있거나 비종료 ExecPlan이 있으면 완료 알림에 "남은 Requirement 없음"을 표시하거나 프로젝트 전체를 완료로 오인시키지 않는다.
- 비종료 ExecPlan 중 시작 가능한 계획이 없으면 각 계획의 ID·제목과 해당하는 미충족 dependency의 ID·상태, PR Merge 대기, 계획 차단 원인·필요 조치 등 실제 시작 불가 이유를 대기 요약 알림 한 건에 담는다.
- 비종료 ExecPlan은 없지만 활성 Requirement가 남은 경우에도 완료로 표현하지 않고 남은 Requirement ID와 확인된 대기 이유를 한 번 알린다.
- 프로젝트 차단 또는 `planning_error`로 선택이 막힌 경우 해당 원인을 포함하고 완료 알림은 보내지 않는다. 동일 원인의 기존 BLOCKED 알림을 새 대기 알림으로 재생성하지 않는다.
- 동일한 안정 상태를 반복 관측하거나 프로세스가 재시작돼도 같은 대기·완료 사건의 알림은 중복 생성되지 않는다. 새로운 작업 진행 또는 관련 입력·원인 변경 뒤의 별도 사건은 다시 한 번 알릴 수 있다.
- 실행 가능한 READY, 진행 중인 Worker·Planner, PR 충돌·유지보수 복구, 일시 오류로 보존된 실행이 있으면 작업 소진 알림을 조기에 생성하지 않는다.
- Telegram이 비활성화되거나 전송에 실패해도 작업 상태는 바뀌지 않으며 이유는 실행 결과와 로그에 남는다. 전송 실패는 기존 outbox 재시도 계약을 따른다.

## Product Impact

- 더 이상 시작할 작업이 없는 프로젝트의 완료 또는 대기 이유를 한 번 확인할 수 있다.

## Non-Goals

- 대기 중인 PR을 자동 Merge하거나 차단된 계획을 알림 때문에 해제하지 않는다.
- 알림을 위해 새 Agent 호출, 추가 Planner 주기 또는 별도 감시 서비스를 시작하지 않는다.
- 순간적인 일시 오류나 아직 진행 중인 작업마다 상태 알림을 보내지 않는다.
