# [R-072] 입력 동일성이 증명된 구현 후보 성공 결과 재사용

## Context

Archive된 [R-063](archive/%5BR-063%5D%20Manager-Owned%20Deterministic%20Work%20and%20Minimal%20Model%20Use.md)의 미완료 목표인 구현 후보 성공 결과 재사용을 구체화한다. 현재 rebase 채택은 Worker·verify·Review의 후보 검증 근거를 일괄 무효화하므로, 충돌 없는 rebase나 검증과 무관한 변경에도 실행을 반복할 수 있다.

Manager가 실제 입력과 기존 성공 근거를 비교해 필요한 단계만 실행한다. 프로젝트별 verify 입력 목록으로 검증 입력을 확인하고, Review는 검증 입력에 해당 작업의 명세·diff·검토 기준을 더해 보수적으로 판단한다. 자체 검증의 문서 원본 의존성과 과도한 경로 포함을 제거하고 일반 verify에서도 입력 동일성을 증명해, 문서만의 변경이나 검증과 무관한 문서 변경을 포함한 rebase가 전체 verify를 반복시키지 않게 한다.

## Requirement

### Rebase와 Worker

- Manager가 소유권·작업물 보존 조건을 확인하고 먼저 rebase를 시도한다. 충돌 없이 완료되면 rebase나 commit SHA 변경만을 이유로 Worker를 다시 호출하거나 완료한 targeted test를 반복하지 않는다.
- Requirement·ExecPlan 충돌의 최신 base 자동 채택·파일 전체 교체와 그 외 파일 충돌의 Worker 복귀는 [R-082](%5BR-082%5D%20단계별%20원격%20문서%20반영과%20PR%20전%20ExecPlan%20갱신.md#rebase-충돌과-구현-조건-변경)를 따른다. Worker 교정은 작업물·진행 상태·기존 세션을 보존해 수행하고 수정한 코드에 필요한 targeted unit test를 실행한다. 해결 이후 전체 verify와 Review의 필요성은 아래 조건으로 각각 판단한다.
- 검증 실패·Review issue·구현 수정·명세나 역할 입력 변경 등 별도 교정 사유는 기존 Worker 흐름으로 처리한다. rebase 실패·미완료·소유권 불확실성은 정상 완료로 취급하지 않으며 기존 재시도·차단·복구 정책을 유지한다.

### ExecPlan 구현 입력과 기록 변경

rebase 중에도 실제 구현 조건과 순수 기록 변경을 구분한다. 목표·Acceptance Criteria·source·의존 관계·허용 범위·구현/검증 조건·적용 지침·사용자 결정은 구현 판단에 반영한다. 구현 조건이 같다는 것을 확인한 `Progress` 체크 상태와 기존 수행·검증 사실만의 기록 변화는 그 사실만으로 Worker를 다시 호출하거나 `ExecPlan 구현 입력 변경`의 최종 차단을 만들지 않는다. 같은 session과 작업물을 보존해 기존 충돌 해결을 이어간다.

절 이름이나 문서 위치만으로 내용을 제외하지 않는다. `Progress`·`Decision Log` 안의 새 목표·제약·검증 조건·승인 변경도 실제 입력으로 검사한다. 변경의 의미를 안전하게 구분할 수 없으면 작업물과 과거 근거를 보존하고 필요한 명세 재확인·Worker 확인을 수행하며, 해결하지 못한 충돌이나 실제 새 조건과 결합할 수 없는 작업은 기존 차단으로 처리한다. 누락된 과거 입력을 현재 기록으로 합성하지 않는다.

Worker 구현 입력에서 순수 기록을 구분해도 verify·Review·사용자 승인 입력을 함께 제외하지 않는다. 해당 문서가 실제 verify 입력이면 지문에 반영하고, Review는 아래의 문서·diff·검토 기준 변경 조건을 그대로 적용한다. 기록 변경을 새 실행 성공·승인이나 실패/교정 이력 초기화로 취급하지 않는다.

### 프로젝트별 verify 입력 목록

프로젝트는 `scripts/verify-inputs.json`에 전체 verify의 실제 입력 경로를 관리한다. 형식은 다음과 같으며 예시 경로는 프로젝트의 실제 언어·구조·검증 명령에 맞게 작성한다.

```json
{
  "version": 1,
  "paths": [
    "src/**",
    "tests/**",
    "scripts/verify.sh",
    "scripts/verify.ps1",
    "pyproject.toml",
    "uv.lock"
  ]
}
```

- 목록은 저장소 상대 경로와 glob으로 소스·테스트·fixture·의존성 파일·검증 설정·스크립트 등 실제 입력을 포함한다. 경로 해석 규칙은 명시하고 지문에 결합하며, 지원하지 않는 형식·버전·경로 또는 저장소 밖 입력을 안전하게 확인할 수 없는 경우 재사용하지 않는다.
- 문서와 `.agents/`는 기본적으로 제외한다. verify가 해당 파일을 실제로 읽거나 결과에 영향을 받으면 명시적으로 포함한다. 디렉터리 전체를 준비 편의나 파일 종류만으로 포함하지 않고 실행·검증에 필요한 경로로 좁힌다. 입력 목록 자체는 항상 지문에 포함한다.
- Worker가 verify 스크립트와 목록을 함께 생성·유지하고 코드 경로·의존성·검증 방식 변경 시 목록도 갱신한다. Reviewer는 실제 입력 누락과 목록 변경에 따른 재사용 범위 약화를 검토한다.
- Manager는 목록을 읽고 지문과 재사용 여부를 계산한다. 중앙 설정에 프로젝트별 경로 목록을 중복 저장하지 않는다. 공통 verify runner 도입을 목록 사용의 필수 조건으로 만들지 않는다.

### 자체 verify의 문서 원본 의존성 제거

- Loop Manager 자체 verify에서 `AGENTS.md`, `README.md`, `docs/**`, `.agents/**`의 정책·안내 문구를 검사하는 테스트를 제거한다. 문서 내용을 읽고 파싱·해시·조립·등록·보존하는 기능의 동작 검증은 유지한다.
- 테스트 저장소 준비·프로젝트 파일 복사·문서 소비 기능은 `tests/**` 안의 고정 샘플을 사용한다. 복사 테스트는 실제 `copy-project-files.*`를 실행하고 샘플 원본과 결과의 바이트, 대상 경로, 기존 파일 보존과 덮어쓰기 거부를 확인한다. 원본 Skill·문서·템플릿 변경에 맞춰 샘플을 자동 복사하거나 갱신하지 않는다.
- `config/config.ini.example`의 원본 값·문구 일관성 검사는 전체 verify에서 분리하고, 설정 파서·역할별 profile·유효성 검사는 고정 샘플로 유지한다. 예제와 사용자 운영 설정 `config/config.ini`는 목록에서 제외한다. 운영 설정 파일의 내용·존재·부재만으로 verify를 무효화하지 않으며, 결과 유효성에 영향을 주는 실제 실행값·인자·환경만 별도 입력으로 판단한다.
- 자체 목록은 소스·테스트·고정 샘플·의존성 파일, `verify.*`·`copy-project-files.*`와 테스트가 소비하는 `run.sh`·`run.ps1`을 포함한다. `scripts/setup.*`, `.gitignore`, `.gitattributes`는 실제 검증 의존성이 없는 한 제외한다. checkout 규칙 때문에 실제 스크립트 바이트가 바뀌면 해당 스크립트 입력 변경으로 판단한다.
- 원본 의존성 제거와 실제 입력 관측을 마치기 전에는 축소된 목록만으로 완전성이나 재사용 가능성을 인정하지 않는다. 고정 샘플 전환은 준비·복사 기능의 assertion이나 전체 verify의 동작 검증 범위를 약화하는 근거가 아니다.

### 목록 부재와 생성 계획

- 현재 후보에 목록이 없거나 유효하지 않으면 전체 verify를 실행한다. 목록 부재만으로 해당 작업의 Worker를 호출하거나 Planner를 즉시 실행하지 않는다.
- 다음 일반 Planner 실행 시 Manager는 최신 원격 base에서 목록 부재를 확인하고 생성 계획을 요청한다. 최신 base에 목록이 있으면 낡은 작업 branch의 부재를 새 생성 요청으로 취급하지 않는다.
- Manager 요청에 따라 새로 생성하는 목록 생성 ExecPlan은 `priority: critical`로 작성한다. 반복적인 전체 verify 비용을 줄이는 기반 작업을 우선 확보하기 위한 명시적 우선순위 조건이다. Manager는 생성 요청에 이 조건을 전달하고 새 계획의 최초 등록 시 다른 priority를 거부한다. 실행 중 작업을 선점하지 않고 기존 dependency gate와 유지보수 장벽을 유지한다.
- 정책 적용 전에 등록된 미완료 계획·draft·미Merge PR은 기존 선언 priority와 실행 상태를 보존한다. 새 priority 조건만으로 기존 요청·계획을 무효화하거나 교체 계획을 생성하지 않는다.
- 같은 프로젝트·목적의 미완료 ExecPlan·사용자 판단 대기 draft·미Merge PR이 있으면 추가 생성 계획을 요청하지 않는다. 생성 계획의 중단·실패 동안 기존 계획을 보존하고 중복 생성하지 않는다.
- Planner는 전체 프로젝트 구조와 실제 verify 스크립트를 기준으로 목록 생성 계획을 작성한다. rebase 변경 파일만으로 전체 입력을 정하지 않는다. 계획이 Merge돼 목록과 유효한 성공 기준이 확보되기 전까지 기존 작업은 전체 verify를 실행한다.

### Manager 요청 작업의 예약어 source

`sources`는 기존 PRODUCT·Requirement 경로에 더해 Manager가 명시적으로 등록한 공통 작업의 예약어를 허용한다. 목록 생성 계획에는 다음 값을 사용한다.

```yaml
sources:
  - manager:verify-inputs
```

- `manager:verify-inputs`는 Manager의 verify 입력 목록 유지 규칙을 근거로 하는 작업이다. Manager가 전달한 해당 프로젝트의 실제 누락 요청과 생성 계획의 목적·범위가 일치해야 한다. 일반 Planner가 임의의 제품 작업을 예약어로 정당화하지 않는다.
- 예약어는 명시적 허용 목록으로 검증하며 미등록 값은 거부한다. 빈 sources나 존재하지 않는 문서 경로로 대체하지 않는다. 일반 제품 작업의 문서 source 규칙은 유지한다.
- 예약어는 파일 조회·문서 존재 검사·Requirement 충족 판단과 archive 대상에서 제외한다. 공통 규칙의 내용·버전을 source 지문과 Review 근거에 결합하고 관련 규칙 변경 시 영향을 받는 성공 근거를 재평가한다.
- 이 예외는 등록 프로젝트에 Loop Manager Requirement를 복사하도록 요구하지 않으며, 일반 Planner의 파일 편집 권한·사용자 승인·작업 범위를 확대하지 않는다. 기존 source의 추적·dependency·복구 의미를 보존한다.

### 전체 verify 실행과 재사용

Manager는 실제 전체 verify 성공 결과와 입력 지문을 SQLite에 저장한다. 지문은 다음 입력을 포함한다.

- 입력 목록 자체와 형식·경로 해석 규칙
- 목록에 해당하는 파일의 경로·내용·종류·실행 권한
- 검증 명령·설정과 결과에 영향을 주는 실행 환경 정보
- verify가 사용하는 Git HEAD·이력·revision 생성 값이나 그 밖의 실제 외부 입력

파일 생성·삭제·이름 변경, 파일 종류·실행 권한 변경, 미커밋 변경과 목록에 해당하는 untracked 파일도 반영한다. 비교는 새 main 대비 PR diff가 아니라 이전에 성공한 후보와 현재 후보의 verify 입력을 기준으로 하며, rebase로 들어온 main의 코드·의존성·검증 설정 변경도 포함한다.

- 현재 지문이 같은 프로젝트·ExecPlan·작업 주기의 유효한 이전 성공 결과와 같으면 전체 verify를 생략하고 해당 결과를 재사용한다. SHA 변경만으로 무효화하지 않지만 Git revision 의존 검증에서는 해당 변경도 실제 입력으로 비교한다.
- 일반 verify도 실제 실행 명령·유효 환경·runtime·Git·외부 의존성과 목록 완전성을 관측해 위 재사용 조건을 적용한다. 제한된 isolated compile 계약만 재사용할 수 있는 상태를 완료로 취급하지 않는다. 일반 verify의 관측이 불가능한 프로젝트는 전체 verify를 유지한다.
- 검증과 무관한 문서만 바뀌거나 그러한 변경을 포함한 rebase라도 위 입력이 같고 목록 밖 변경의 비영향이 확인되면 verify를 재사용한다. 같은 rebase에서 실제 코드·테스트·의존성·검증 설정이나 실제 Git 입력이 바뀌면 전체 verify를 실행한다. verify 목록에서 제외된 문서도 Worker 구현 입력과 Review 입력의 판단에서는 각 역할의 조건을 따른다.
- 입력이 다르거나 성공 기록·목록·비교 근거가 없거나 유효하지 않으면 전체 verify를 실행한다. 파일·환경·외부 입력의 동일성을 안전하게 확인할 수 없는 경우도 실행하며 tree 동일성만으로 재사용하지 않는다.
- 실행·지문 계산·재사용 판정 중 관련 입력이 바뀌면 그 근거를 현재 후보의 성공으로 채택하지 않고 다시 판단한다. 새 verify 실패를 과거 성공으로 덮지 않고 기존 Worker 교정 흐름으로 처리한다.

### 입력 누락 방지

- Manager는 목록 밖에 새 코드·설정 파일이 생기거나 기존 파일이 목록 밖으로 이동하면 Worker에게 목록 확인을 요청한다. 목록 자체가 없는 경우는 위 생성 계획 흐름을 따르고 branch별 즉시 생성 요청으로 바꾸지 않는다.
- 감지할 파일 종류·경로와 판정 근거를 문서화한다. 코드·설정 여부나 검증 영향을 확정할 수 없으면 전체 verify를 실행한다. 누락 의심이 해소되기 전에는 지문이 같아도 재사용하지 않는다.
- 확인 결과는 해당 경로·내용·검증 설정에 결합하며 관련 입력이 바뀌면 재확인한다. 전체 verify 성공만으로 목록의 완전성이 증명됐다고 처리하지 않는다.
- 목록 밖 파일이 바뀌면 현재 경로·내용과 실행 context에 맞게 제외 근거를 재확인한다. 검증과 무관한 문서임을 확인한 경우 전체 verify 없이 현재 완전성 근거를 갱신하고 이전 성공 결과를 비교할 수 있어야 한다. 확장자·폴더명만으로 모든 문서의 비영향을 인정하거나 과거 completeness token을 새 내용에 그대로 적용하지 않는다. 검증 영향·완전성을 확인하지 못하면 전체 verify를 실행한다.

### Reviewer 실행과 재사용

초기 판정은 전체 verify의 재사용 조건에 해당 작업의 명세·diff·Review 기준을 더한다. 다음 중 하나라도 해당하면 Reviewer를 실행한다.

1. 전체 verify 성공 결과를 재사용할 수 없다. 입력 목록 부재·오류·누락 의심·비교 불가도 포함한다.
2. 해당 ExecPlan 또는 sources의 목록·내용이 바뀌었다. 예약어 source는 해당 공통 규칙의 내용·버전을 비교한다.
3. 마지막으로 승인한 후보와 현재 후보의 PR diff가 달라졌다. 검증 입력 목록에서 제외된 작업 변경도 포함한다.
4. 적용되는 PRODUCT·ARCHITECTURE·사용자 결정·공통 및 역할별 원본 묶음·실제 Reviewer instruction·Review provider·Model·Effort가 바뀌었거나 이전 승인 근거가 없거나 불완전하다.

- 비교 기준은 직전 rebase가 아니라 마지막 Review 승인 당시의 verify 입력·명세·diff·검토 기준이다. 이번 실행의 새 verify 성공만으로 이전 Review를 유효하게 만들지 않는다.
- 지침 비교는 R-064의 작업에 고정된 전체 원본 묶음 해시와 실제 Reviewer 합성 내용 해시를 사용한다. common 본문만 비교해 역할 파일 변경을 놓치거나 최신 runtime 내용을 진행 중 작업의 원본으로 소급 채택하지 않는다. 기존 단일 Markdown snapshot도 원래 전달 내용을 기준으로 비교한다.
- 프로젝트 지침의 해석은 R-066에 따라 Agent CLI에 맡긴다. Manager는 루트 `AGENTS.md`의 존재·내용·해시를 별도 수집·대조하거나 과거 파일 승인을 Review 재사용 조건으로 사용하지 않는다. 작업의 실제 PR diff 또는 확인된 일반 verify 입력에 포함되는 파일 변경에는 기존 검증·Review 조건을 적용한다.
- 위 조건이 없고 이전 승인이 유효하면 Review를 재사용한다. 검증 입력은 같지만 명세가 바뀌면 verify만 재사용하고 Reviewer를 실행한다. 목록이 없으면 verify와 Reviewer를 모두 실행한다.
- 충돌 해결로 실제 입력이나 diff가 바뀌면 재검토하며 충돌 발생 사실만으로 실행을 확정하지 않는다. verify 지문 동일성만으로 Review를 재사용하지 않는다.

### 기록·복구·게시

- 역할별 실제 성공 결과와 동일성 확인 근거를 현재 후보 revision에 연결해 SQLite에 기록한다. 실행·생략 이유와 원래 결과를 확인할 수 있어야 하며 과거 SHA의 성공 token 복사만으로 후보를 통과시키지 않는다.
- 실패·timeout·미완료·출처 불명 또는 다른 프로젝트·계획·작업 주기의 결과는 재사용하지 않는다. 작업물·session·검증 원문·실패 및 승격 감사를 보존하고 재사용 판정만으로 실패 이력을 초기화하지 않는다.
- 중단·재시작에서 연결 근거와 현재 입력을 재검증하며 저장이 불완전하거나 입력이 달라졌으면 필요한 단계부터 재개한다. 생략은 새 실행 성공으로 기록하지 않고 수행하지 않은 invocation·토큰 사용량이나 측정하지 않은 시간·비용 절감을 만들지 않는다.
- 최종 후보에 유효한 관련 테스트·전체 verify 성공과 Review 승인 근거가 있어야 PR 생성·기존 PR branch 갱신을 허용한다. 최신 원격 base·branch·PR identity·lease·소유권·dependency·사용자 승인과 게시 gate는 매번 확인한다.
- 기존 정적 코드맵·유지보수 모듈 재사용과 완료 후보의 문서 전문 확인을 유지한다. Requirement 최종 충족 판단은 R-068에 따라 실제 Merge된 최신 원격 구현을 확인하며 후보 재사용으로 대신하지 않는다.

## Acceptance Criteria

- 충돌 없는 rebase나 SHA 변경만으로 Worker·완료한 targeted test를 반복하지 않는다. R-082의 계획·작업 문서 충돌 자동 처리 후에는 단계별 재점검을 적용하고, 그 외 파일 충돌은 보존된 Worker 세션에서 해결·수정·관련 targeted test를 수행하며 이후 verify·Review를 각각 판단한다.
- rebase 충돌 중 구현 조건이 동일한 Progress 체크·기존 수행/검증 기록만 바뀌면 같은 Worker session·작업물·rebase 진행 상태를 유지하고, 그 변경만으로 구현 입력 변경 차단·Worker 재호출·교정 횟수 증가를 만들지 않는다.
- 같은 기록 절의 목표·Acceptance Criteria·source·제약·검증 조건·지침·사용자 결정 변경은 실제 입력으로 구분한다. 분류 불확실성·과거 비교 근거 부재와 실제 새 조건에 맞지 않는 작업은 자동 수용하지 않으며, 필요한 재확인·차단과 verify·Review·게시 gate를 유지한다.
- 목록이 없는 작업은 전체 verify를 실행하고 목록 생성만을 위한 Worker·Planner 즉시 호출을 하지 않는다. 다음 일반 Planner는 최신 원격 base와 기존 미완료 계획·draft·PR을 확인해 생성 계획을 중복 요청하지 않는다.
- `manager:verify-inputs` 계획은 실제 Manager 누락 요청에 근거해 등록·실행된다. 미등록 예약어·범위 불일치는 거부되고 문서 조회·Requirement archive와 혼동되지 않으며 규칙 변경이 source 지문에 반영된다.
- Manager의 목록 생성 요청은 `priority: critical`을 명시하고 Planner는 새 ExecPlan을 해당 값으로 작성한다. 다른 priority로 생성한 새 계획은 최초 등록되지 않으며, 실행 가능한 후보 안에서 기존 유효 우선순위·숫자 ID 정렬을 따른다. 정책 적용 전 등록된 미완료 계획·draft·PR의 선언 priority와 실행 상태는 보존하고 새 조건만으로 기존 요청·계획을 무효화·중복 생성하지 않는다. 목록이 확보되기 전에도 전체 verify를 계속 실행하고 진행 중 작업·dependency·유지보수 경계를 보존한다.
- Worker가 실제 전체 검증 입력을 목록으로 유지하고 Reviewer가 누락을 검토한다. 문서·`.agents/`도 실제 입력이면 포함하며 중앙 설정에 경로 목록을 중복 저장하지 않는다.
- 자체 verify는 문서·Skill·템플릿·README의 원본 문구를 검사하지 않으며 저장소 준비·복사·문서 소비 기능은 고정 샘플로 검증한다. 실제 복사 스크립트·launcher·샘플 변경은 입력으로 반영하고, 복사 바이트·경로·기존 파일 보존·덮어쓰기 거부와 문서 소비 기능의 동작 assertion을 유지한다.
- 예제 설정 원본의 일관성 검사와 파서·profile 동작 검증이 분리돼 예제 변경만으로 전체 verify를 반복하지 않는다. 예제·사용자 운영 설정은 목록에서 제외하며 운영 설정 변경만으로 전체 verify를 반복하지 않는다. 결과 유효성에 영향을 주는 실제 실행값·환경 변경은 판정에 반영된다.
- 일반 자체 verify의 실제 성공 뒤 같은 프로젝트·ExecPlan·작업 주기에서 입력이 같으면 성공 결과를 재사용한다. 문서만 변경한 후보와 검증과 무관한 문서 변경을 포함한 rebase 후보 모두 전체 verify를 재실행하지 않으며, 제한된 compile 계약만으로 이 조건을 통과시키지 않는다.
- 목록 밖 문서가 바뀌면 현재 내용에 맞는 제외·완전성 근거를 재확인한 뒤 재사용한다. 실제 새 코드·설정·문서 의존성이나 비교 불가 입력은 재사용을 막고 전체 verify를 실행하며, 과거 token이나 verify 성공만으로 제외를 승인하지 않는다.
- 이전 성공 후보와 현재 후보의 입력이 같으면 verify를 재사용하고 main의 실제 입력 변경에는 실행한다. 파일 생성·삭제·이름·종류·권한·미커밋·untracked 변경과 목록·명령·환경·Git revision 의존성이 판정에 반영된다.
- 성공 기록·목록 부재·오류·계산 불확실성과 목록 밖 코드·설정 누락 의심에서는 verify를 생략하지 않는다. 누락 의심을 verify 성공만으로 해소하지 않는다.
- Reviewer는 verify 재사용 불가, ExecPlan·sources·PR diff·Review 기준 변경과 승인 근거 부재·불완전에서 실행된다. 입력 목록이 없으면 verify·Reviewer를 모두 실행한다.
- 모든 검토 입력이 같은 승인 후보는 Review를 재사용한다. 공통 또는 역할 지침만의 변경도 비교에 반영하며 검증과 무관한 명세 변경에는 verify를 재사용하되 재검토한다. 새 verify 성공으로 오래된 Review 승인을 승격하지 않는다.
- CLI 지침의 유무·내용·과거 파일 승인만을 위한 별도 읽기·지문·승인 gate가 없다. 실제 PR diff·verify 입력과 고정된 공통·역할별 원본 묶음·실제 Reviewer instruction의 변경 판정은 유지한다.
- 실행·판정 중 입력 변경, 저장 중단·재시작과 게시 직전 원격 경쟁에서 오래된 근거로 게시하지 않는다. 원래 성공·현재 후보 연결과 생략 이유를 확인할 수 있고 작업물·session·실패 감사를 보존한다.
- 실패·timeout·미완료·출처 불명과 다른 작업 주기의 결과는 재사용하지 않는다. 최신 ref·lease·ownership·dependency·승인·게시 gate, 최종 문서 확인과 Merge 뒤 Requirement 충족 판단을 유지한다.
- 실제 모델을 호출하지 않는 검증으로 호출 감소와 필요한 교정·verify·Review 수행을 확인한다. 재사용은 실제 실행·사용량과 구분하며 허위 성공·invocation·절감량을 기록하지 않는다.

## Product Impact

- Manager가 rebase와 입력 동일성 판정을 맡고 필요한 Worker·verify·Reviewer만 실행한다.
- 프로젝트가 실제 verify 입력을 관리하며 목록 부재는 기존 검증과 중복 없는 생성 계획으로 처리한다.
- Manager 공통 작업은 등록된 예약어 source를 사용하고 현재 후보의 검증·Review와 게시 안전 조건을 유지한다.

## Non-Goals

- 필수 검증·Review의 유효한 성공 근거를 없애거나 실패를 성공으로 바꾸지 않으며 사용자 Merge를 자동화하지 않는다.
- 다른 계획·작업 주기의 최종 판단을 가져오거나 미반영 후보로 Requirement 완료를 선언하지 않는다.
- 기존 코드맵·모듈 검토 재사용과 Worker 세션 feedback 축소를 재구현하지 않는다.
- Agent 격리·권한 정책이나 비호환 상태 모델을 변경하지 않는다.
- Progress·Decision Log 또는 본문 전체를 일괄 무시하거나 실제 구현 조건·승인 변경을 기록으로 숨기지 않는다.
- 무관한 코드 변경의 Review 생략을 위한 별도 의존성 분석이나 범용 예약어 작업 체계를 추가하지 않는다.
