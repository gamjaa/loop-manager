# [R-055] 차단 경로 전수 조사와 불필요한 작업 중단 축소

## Summary

시작부터 planning·Agent·검증·게시·복구·정리까지 모든 차단 경로를 조사해 불필요한 중단을 줄인다. 접근 권한은 sandbox로 강제하고 정상 Git OID·HEAD 변경은 최신 원격 commit과 후보의 관계로 수용·통합한다. 실제 쓰기 대상·작업물 보존·정확한 lease만 안전 조건으로 삼고, 과거 snapshot 불일치에 의한 오탐은 제거한다. 사용자 메시지는 실제 자동 복구 불가·사용자 조치 또는 실질적 진전이 없는 지속 장애로 제한한다. rebase 시작에는 대상·소유권·보존만 확인하고 오래된 시작 HEAD·공유 Git snapshot과의 일치를 요구하지 않는다. Worker 종료 후 해당 변경을, rebase 완료 후 최종 선언·전체 결과를 검증한다. targeted test의 동일 테스트 연속 5회 실패, 원격 작업 branch 삭제 뒤 명시적 재시작, 복구 불가 파일의 제한적 재작업과 문서 삭제의 관계·DB·소유 자원 반영을 구분하고 작업물·감사를 보존하고 rebase 이력의 자기 중첩을 금지한다. 유지보수는 모든 대상의 실제 Merge 또는 안전한 취소 반영으로 할 일이 없어지면 R-074에 따라 정상 종료한다. 여러 작업에서 확인된 범위 밖 공통 결함은 기존 명세의 미충족 목표로 모아 자동 planning·교정하고, 영향 작업을 근거에 따라 재평가·재개한다. 독립 작업은 R-091의 실행·관리 한도와 배정 순서 안에서 계속 진행한다. RETRY 우선 재배정·계획 차단 후 독립 작업 진행·대상별 차단 재평가와 조율 중단 경계는 R-091을 따른다.
Manager가 생성한 예약 workspace는 실행 기준 SHA와 생성 HEAD를 구분하고 승인된 생성·변경 근거로 소유권을 확정해 작업물을 보존하며 재개한다. 소유권 오류와 기존 차단은 실제 영향 범위와 현재 증거로 재평가한다. planning·대표 투영과 대상 작업의 실행 상태가 섞인 경우에는 실제 Git 소유권 위반과 구분하고, 검증된 작업별 근거로 실행 자원 정보를 복구한다. 해소된 소유권 차단은 미완료 Manager rebase의 완료를 기다리지 않고 해제하며, 남은 Git 처리는 Manager가 이어간다. 명시적인 오류뿐 아니라 조기 반환·조건 대기·중복 억제로 생기는 정체도 조사하고, 미확정 Git 기록의 실제 충돌 범위·복구 간 상호 대기·게시 후 해제와 정리·원인별 재평가 조건을 검증한다.

## Context

현재 제품은 일시 재시도, 상태 재구성, Agent 교정과 최종 사용자 조치를 구분하고 계획·프로젝트 차단을 분리한다. 각 작업은 별도 관리 worktree와 작업 ID를 포함한 브랜치를 사용하지만, Agent 호출 전후 Git 상태 비교가 다른 작업의 정상 변경이나 Manager의 동기화 결과를 접근 권한 위반으로 오인할 수 있다. 접근 권한 강제는 sandbox가 담당하도록 하고, Git 관측은 Manager의 동기화·게시·작업물 보존과 후보 검증에 필요한 조건으로 한정한다. 이 변경과 기존 Git 오탐 차단의 자동 복구는 구현 목표다.

원격 작업 브랜치 OID가 로컬 HEAD 또는 저장된 게시 OID와 다르다는 이유로 `external_remote_oid`를 만들거나, 같은 PR의 head 전진을 대상 PR 변경과 함께 거부하는 경로도 남아 있다. 로컬 미게시 commit, 원격 추가 작업, 정상 rebase와 게시 후 기록 중단 모두 이 불일치를 만들 수 있다. OID·ref의 값 차이는 변경 관계를 판단할 입력이며, 그 자체로 작업 소유권 불명이나 사용자 조치 필요를 뜻하지 않는다. 고정된 저장값과 최신 원격의 차이는 시간이 지나도 해소되지 않을 수 있으므로 이를 관측 경쟁으로 분류해 같은 비교를 반복해서는 안 된다. 이 Requirement는 이러한 잔여 판정을 아래 정상 처리와 보류 경계로 변경한다.

개별 계획 문제는 기본적으로 그 계획의 차단으로 처리한다. 이 요구사항은 catalog 전체 유효성 gate 등 개별 오류가 프로젝트 전체 중단으로 확대되는 기존 동작을, 영향받는 범위의 격리와 검증된 독립 작업의 진행으로 변경한다.

계획(Requirement)과 작업(ExecPlan)의 원격 삭제도 정상적인 입력 변경이다. Manager와 일반 Planner가 삭제의 의미와 영향을 확인해 관련 문서·현재 DB 상태·소유 작업 브랜치까지 자동 반영하고, 해소할 수 있는 삭제·참조 오류를 사용자 판단 대기로 남기지 않도록 한다.

검증이나 Review가 여러 작업의 구현 범위 밖에 있는 동일 공통 결함을 드러낼 때, 각 Worker에게 범위 밖 수정을 요구하거나 구현 교정 여부를 사용자 선택으로 넘기면 동일 실패와 결정 대기가 반복된다. 기존 명세로 정해진 공통 계약의 구현 부족은 독립 교정 목표로 수렴시키고, 실제 제품 정책 선택만 사용자에게 요청해야 한다.

예약 workspace의 생성 기준을 실행 기준 `active_sha`로 검사하면 두 SHA의 역할이 다른 정상 작업도 소유권 오류로 중단될 수 있다. 생성 후 DB 소유권 확정 전에 중단된 workspace가 남아 있다는 이유로 복구를 거부하면 Manager가 생성한 자원도 재개하지 못한다. 생성 journal과 실제 HEAD의 일치는 검증 근거의 일부이며, 생성·변경 경위나 소유권 전체를 증명하지는 않는다.

G-331 적용 뒤 planning 게시 완료의 `validate_planning_release()`가 별도 작업 G-297의 오래된 미확정 rebase 기록을 프로젝트 전체 gate로 소비해 게시 완료와 후속 실행을 막는 경로를 코드와 실행 로그에서 확인했다. 아래 경계에서도 같은 종류의 정체가 가능한 구조를 확인했으며, 모두 실제 운영 장애로 재현됐다는 뜻은 아니다. 이 Requirement는 그 경계의 조사와 회귀 검증을 포함한다. 표의 모듈 경로는 `loop_manager_internal/` 기준이다.

## Requirement

일반 RETRY는 R-091대로 해당 실행 대기열의 수동 제출 다음에 다시 배정하고 형제 작업 전체의 완료를 기다리지 않는다. PLAN_BLOCKED는 그 계획만 제외해 같은 실행에서 독립 작업을 시작·재개한다. 실제 최종 차단·조건 대기·PROJECT_BLOCKED와 종료 불명 자원 보존은 유지하며 Planner·runtime 조율의 배정 중단은 별도로 적용한다.

### 전수 조사와 판단

차단과 통지는 별도의 판단이다. 현재 실행·Git·사용자 입력에 안전한 재관측·상태 재구성·자동 교정·조건 대기·다음 외부 실행 재개가 가능하면 해당 작업이나 자원만 보존·보류하고 정상적인 일시 실패를 통지하지 않는다. 재시도 횟수/교정 예산 소진, 차단 상태 코드, 실행 가능한 작업 부재는 그 자체로 사용자 조치의 근거가 아니다. 실제 복구 수단이 없는 최종 중단·사용자 결정/권한/설정/PR 행동과, 복구 가능성이 남았더라도 동일 원인·입력에서 실질적 진전 없이 지속되는 운영 장애는 구별해 R-053에 따라 현재성을 확인하고 각각 한 번 알린다. 지속 장애를 사용자 최종 차단이나 임의의 Git 수정 요청으로 승격하지 않는다. 과거 오탐 해소와 이전 정책의 미전송 진행·무음·대기 알림 취소를 연결하며 원래 전송·실패 감사는 보존한다.

Manager commit/push 후에는 저장된 intent·최신 checkpoint·현재 PR identity·원격 ref/OID를 같은 관측으로 재구성한다. `candidate_changed`는 원격 통합으로 후보가 바뀐 결과이며 `pushed`는 실제 게시 효과로 구분한다. 정상 Worker 파일 수정과 기록된 Manager HEAD/OID 전진·lease 경쟁·DB 갱신 지연을 과거 `remote_oid`·`publication_remote_oid`로 다시 검사해 `publication_ownership_uncertain`·`remote_oid_uncertain` 최종 차단으로 만들지 않는다. 실제 다른 origin/branch/PR·타인의 작업을 덮어쓰는 Git 쓰기는 정확한 소유권·lease 확인으로 거부하되 관련 자원만 보류하고 자동 재확인을 유지한다.

Git 결과의 불일치는 원인별로 구분한다. 저장된 OID·checkpoint가 최신 원격보다 뒤처졌거나 정상 사용자 commit·push로 원격이 전진한 경우에는 fetch한 commit의 조상·후속 관계와 보존해야 할 양쪽 이력을 판단해 현재 입력으로 재구성·통합한다. Git push/조건부 lease가 관측 뒤 실제로 실패하거나 fetch·PR 조회 중 대상 ref가 바뀐 경우에만 최신 관측을 얻는 제한 재시도를 사용한다. 일정 시간이 지나거나 같은 검사를 반복하는 것만으로 해소되지 않는 고정 불일치·비선형 이력·손상된 기록은 `remote_snapshot_race` 등 일시 경쟁으로 포괄 분류하지 않는다. 확인 가능한 변경 관계에는 통합·필요한 검증을 적용하고, 안전 관계가 불명확하면 그 대상의 쓰기만 보류해 기존 작업물과 진단을 보존한다. 재시도는 항상 새 관측·복구 단계 등 진전 가능성을 수반해야 하며 과거 OID로 돌아오기를 기다리지 않는다.

원격 게시 시 현재 검증 후보의 commit·branch·PR과 실제 게시 대상이 일치해야 한다. 일반 fast-forward 게시와, 검증된 이력 재작성에 필요한 정확한 이전 원격 OID의 `--force-with-lease`를 구별한다. lease 일치만으로 이전 사용자 commit의 보존을 증명하지 않으며, 재작성 게시 전에 원격 commit·사용자 변경의 보존 또는 명시적으로 허용된 변경 이력과 필요한 재검증 근거를 확인한다. 이미 성공한 Manager commit·push는 journal·현재 원격으로 확인해 재수행하지 않고 DB/checkpoint의 누락 확정만 복구한다. 다른 origin/branch/PR이나 미커밋 사용자 파일·index·심볼릭 ref의 실제 쓰기 대상 밖 변경은 기존 보호 조건을 유지하며, 검증과 무관한 과거 전체 Git snapshot 일치 검사를 추가하지 않는다.

차단 재평가는 R-091의 작업별 복구 예약·투영과 실행·관리 한도를 따른다. 다른 활성 작업의 존재를 전역 장벽으로 사용하지 않고 대상 호출·소유 자원·공유 planning·게시 충돌을 확인한다. ExecPlan·Requirement 변경은 사유별 재검사의 계기이며, 사용자 질문은 최신 명세의 의미와 실제 해소 근거로 판단한다. 문서 수정 자체를 사용자 승인으로 간주하지 않는다. 일반 입력 오류는 현재 선언을, rebase 입력 오류는 현재 Git·checkpoint를 다시 검사하며 코드 수정으로 안전한 시작이 가능해진 경우에는 새 문서 변경을 요구하지 않는다. 실패 시 기존 원인·작업물·checkpoint·감사를 보존하고 별개 차단은 유지한다.

설정·시작·bootstrap, 원격 관측·catalog, 일반·유지보수 planning, workspace·Agent 범위, Worker·verify·Review, rebase·게시·PR 및 정리·archive에서 실행을 중단하거나 `planning_error`, `PLAN_BLOCKED`, `PROJECT_BLOCKED`를 만드는 모든 코드 경로와 공통 호출 경로를 조사한다. 차단의 재평가·해제·재개 경로도 함께 확인한다.

각 경로는 발생 조건, 보호하는 실제 불변식, 원인 소유자·자원과 영향받는 단계, 자동 복구 가능 여부, 재개 조건과 필요한 사용자 행동을 확인한다. 명시적 예외·차단 저장뿐 아니라 후보가 있는데 `return`·`False`·`WAITING`·skip·지문 cache·중복 억제로 후속 처리를 건너뛰는 경로를 포함한다. 공통 helper의 모든 호출자와 결과를 소비하는 조율·완료·알림 경계까지 추적하고, 정상적인 일시 대기와 개별 문제·실제 프로젝트 안전 문제를 구분한다. 조사 목록에는 현재 명세와의 차이, 차단을 해소할 처리의 진입 조건, 이유·진전·재평가 조건의 관측 가능성도 남긴다. 기존 안전 차단도 포함하되 유지할 불변식과 이유를 명시한다.

### 미확정 Git 기록과 숨은 진행 장벽

- 미확정 journal·checkpoint·게시·cleanup 기록은 복구해야 할 효과의 근거이며, 존재 자체를 프로젝트 전체 쓰기 금지로 해석하지 않는다. 소유자·operation·branch/ref·worktree·공유 설정·게시 대상을 현재 관측과 결합해 이번 단계와 실제로 충돌하는 범위를 판단한다. 작업 ID가 다르거나 경로 문자열이 다르다는 사실만으로 독립성을 승인하지 않으며, 공유 안전을 확인할 수 없거나 writer 종료가 불명확하면 영향 자원과 필요한 프로젝트 gate를 보존한다.
- 독립성이 확인된 다른 작업의 미완료 rebase는 그 작업·의존 작업·충돌 자원만 보류한다. 해당 기록의 완료를 별도 planning 게시 확정·자리 해제·독립 작업의 전제 조건으로 요구하지 않는다. 단순 오래됨·원인 작업의 MERGED/차단 상태·worktree 부재만으로 active intent를 삭제하거나 완료로 합성하지 않는다. 실제 완료한 효과의 미확정 기록은 현재 결과를 검증해 누락 확정만 복구한다.
- 실패 입력의 동일성은 해당 원인에 필요한 입력으로 판단한다. 관련 writer 종료·자원 반환·원격 게시 확인·checkpoint 전이 또는 해당 원인을 교정한 runtime 반영으로 조건이 달라졌으면 Requirement 본문이나 과거 시작 지문이 그대로여도 재평가한다. 무관한 branch 전진·runtime SHA 변경·새 run ID만으로 새 입력·진전을 만들지 않는다. 같은 관측의 중복 처리 억제는 이미 허가된 미완료 복구를 실행 불가로 만드는 근거가 아니다.
- planning·복구·게시·정리 사이의 대기 관계는 R-091에 따라 검사하고, 원인을 해소할 안전한 처리가 자신의 완료를 기다리는 gate 때문에 영구 배제되지 않게 한다. 게시 적용·최종 해제와 보존 가능한 잔여 정리의 구분은 R-082, MERGED 문서 archive는 R-094를 따른다. 확인되지 않은 적용이나 writer 종료를 생략해 순환을 해소하지 않는다.
- 후보·미완료 결과가 있는데 진행하지 못하면 기존 로그·읽기 전용 status에서 원인 소유자와 영향 대상, operation/intent 식별자, 충돌 자원·불확실한 안전 조건, 마지막 실제 진전과 다음 재평가 조건을 확인할 수 있어야 한다. `미확정 Git 쓰기`·`WAITING`·`다음 run에서 재실행`만으로 이유를 대신하지 않는다. 기존 구조화된 관측을 사용하고 legacy 근거 부재는 미확인으로 표시하며, 로그 문구 파싱으로 실행 판단을 만들거나 조회 중 복구·Git/원격 호출을 수행하지 않는다.
- 정상 대기의 반복 출력은 억제하되 원인 변경·실제 시도 결과·해소는 보존한다. 오류 저장 경로를 거치지 않는 조기 반환과 planning/프로젝트 단위 대기도 R-053·R-091의 지속 정체 판단에서 빠지지 않아야 한다. 독립 작업의 성공·부분 DB 적용·정상 반환 코드로 미해소 원인의 이력과 미전송 진단을 해소하지 않는다.

### 불필요한 중단의 수정

새 rebase의 이전 operation 이력은 각 operation을 한 번만 보존하며 이전 이력 전체를 새 이력 항목 안에 다시 넣지 않는다. 현재 HEAD·target·원격 lease·미완료 intent·검증 및 사용자 결정의 근거를 유지하며 이력 때문에 checkpoint가 재시도마다 배증하지 않아야 한다.

관리 rebase의 시작에는 repository·계획·canonical worktree·branch·시작 HEAD·target revision·원격/PR 연결과 소유권, writer 경합·index 안전 조건·작업물 보존 가능 여부를 확인한다. 파일·index·선언은 이후 변경 구분과 복구를 위한 기준으로 기록하며, 역할별 전체 diff·최종 문서/archive 내용·현재 worktree 선언과 target 선언의 일치를 시작 조건으로 요구하지 않는다. 과거 definition snapshot 부재나 정합화할 오래된 frontmatter, 누락되거나 오래된 checkpoint 시작 HEAD만으로 소유 rebase 진입을 막지 않는다. target을 아직 포함하지 않은 현재 소유 branch는 rebase 전 입력으로 판단하고, 작업 변경을 관측할 때는 target과의 공통 조상을 기준으로 삼아 base에만 추가된 변경을 Worker의 삭제·되돌림으로 해석하지 않는다. 실제 Git operation이 진행 중이면 현재 operation의 시작 HEAD·target 연결은 계속 확인한다. 실제 target의 작업 identity·유효성·필수 사용자 결정과 dependency는 유지한다.

충돌 해결 Worker가 종료하면 호출 전후 실제 Worker 변경과 역할별 허용 결과를 검사한다. provider sandbox는 호출 중 계속 적용한다. Git rebase가 진행 중인 형상은 전체 최종 후보로 판정하지 않으며 문서 재생·일부 stage·autostash 복원 상태만으로 최종 범위 위반을 만들지 않는다. Git 완료 후 Manager가 고정 target의 선택 ExecPlan frontmatter를 본문·mode·다른 작업물을 보존해 복원한 다음 최신 선언·전체 최종 diff·보호 문서·archive·복원 결과를 검증한다. 정상 Worker 완료도 해당 Worker 변경과 최종 선언·결과를 검사한다. 재시작·수동 해결·차단 재평가에 같은 시점을 적용하고 보조 Git 표식만으로 완료·정리를 보류하지 않는다.

Git의 정상 변경 수용·현재 입력·게시 분리에 대한 공통 변경 기준은 아래 절에서 정의한다. 로컬 원본 동기화는 R-056, exact-SHA runtime 귀속은 R-020, 원격 실행·self handoff와 호출 격리는 R-023, 단계별 문서 갱신은 R-082, ignored 파일은 R-022, 성공 근거 재사용은 R-072를 따른다. 해당 문서에서 공통 Git 기준을 반대로 정의하지 않는다.

- 최신 원격 입력과 현재 작업의 소유권·범위·Git 상태로 안전한 다음 단계를 확정할 수 있으면, 낡은 비교 기준이나 복구 기록의 형식 차이만으로 차단하지 않고 기존 작업을 보존해 재구성·재개한다.
- 일시적 네트워크·외부 CLI·Git 경쟁, R-091에 따라 재시도 대기 뒤 같은 실행에서 이어갈 실행별 재시도 예산와 부수적인 정리·알림·로컬 동기화 실패는 해당 원인에 맞는 재시도·일시 대기·pending으로 처리한다. 그 이유만으로 사용자 수정이 필요한 최종 차단을 만들지 않는다.
- 한 계획에 국한된 실패는 계획 범위로 제한하고, 독립 계획과 다른 프로젝트가 계속 진행할 수 있게 한다. 프로젝트 전체 차단은 실제 공유 자원·안전 조건이 해결되지 않아 해당 프로젝트의 새 작업도 안전하지 않은 경우에 한정한다.
- 개별 ExecPlan의 선언·의존성 오류, 작업 branch·worktree 문제와 승인 대기는 그 계획과 영향받는 의존 계획에 한정한다. catalog 오류라는 분류나 복구 경로의 부재만으로 프로젝트 차단으로 확대하지 않는다. 오류 선언은 유효한 입력으로 채택하지 않고 마지막 검증 선언·작업물·진단을 보존한다. 식별자·의존 관계가 불확실한 범위는 실행하지 않되 독립성과 유효성을 확인한 계획은 진행한다. 프로젝트 전체의 식별·공유 소유권·안전을 확정할 수 없을 때만 근거를 명시해 프로젝트 gate를 유지한다.
- 이미 해소된 원인으로 남아 있는 차단은 현재 근거를 확인한 뒤 그 원인만 해제한다. 입력 지문 변화가 없는 오탐도 재평가할 수 있어야 하며, 다른 차단·승인·실패 이력을 함께 지우지 않는다.
- 상태·작업물·branch·worktree·Agent session과 미해결 피드백을 보존한다. 복구가 후보를 바꾸면 필요한 Worker 확인·targeted test·Manager verify·Review를 다시 거친다.
- 재시도는 일시적 경쟁·외부 조건 변화로 새로운 결과를 얻을 수 있을 때만 수행한다. 동일 원인·입력·진전 표식으로 대기와 재시도가 반복되면 R-091의 무진전 중단/조건 재확인과 R-053의 지속 장애 진단을 적용한다. 최종 검증 실패, 실제 범위 위반·소유권 불확실성, 손상 또는 사용자 결정 필요를 무한 재시도로 바꾸지 않되 정상 원격 변경을 그 범주로 오판하지 않는다.
- 시작 오류처럼 차단 상태를 만들기 전 중단하는 경로도 필요한 조건과 오류 범위를 확인한다. 실제 원격 기준이나 필수 설정을 검증할 수 없는 상황을 성공으로 취급하지 않는다.

아래 공통 Git 기준을 Agent 결과, 저장 단계 재개, 계획/프로젝트 복구와 정상·진단 checkpoint에 동일하게 적용한다. 다른 소비자가 폐지한 Git 상태 비교를 다시 실행해 접근 권한 위반을 만들지 않는다. runtime 선택·재개는 R-020·R-023, rebase 중 구현 입력과 순수 기록 변경의 구분은 R-072를 따른다.

checkpoint의 저장 요청과 현재 차단 사유·evidence·상태가 달라지면 게시 전에 같은 repository·계획·branch·worktree·현재 원인을 다시 읽는다. 해결된 원인의 요청은 취소하고, 같은 소유 작업의 새 원인이면 그 원인에 결합된 요청으로 갱신해 안전 검사를 다시 수행한다. 오래된 요청의 identity 불일치만으로 별도 프로젝트 차단이나 Worker 교정 횟수를 만들지 않는다. 실제 자원·원격 lease·소유권 변화는 거부하며, 중단·재시작과 SQLite 확정 경쟁에서도 다른 차단·승인을 해제하거나 낡은 작업물을 게시하지 않는다.

### Worker targeted test의 반복 실패 기준

Worker의 미해결 targeted test는 완료 보고의 교정 횟수 대신 같은 테스트의 실제 연속 5회 실패로 해당 작업을 차단한다. 다른 테스트의 실패는 합산하지 않고, 해당 테스트가 성공하거나 skip·예상된 실패이면 연속 실패 횟수와 차단 도달 표식을 모두 초기화한다. 연속 다섯 실패 뒤 같은 turn에서 성공한 경우도 동일하다. 후보·commit·세션 변경은 실패 이력을 초기화하지 않는다. 같은 세션 안의 재실행을 포함하고 중복 보고·중단 후 재관측은 한 실행으로 센다.

실행·수집 실패나 테스트 identity를 확인할 수 없는 보고만으로 5회 실패를 확정하지 않는다. 새 실행 근거 없는 실패 보고는 실제 테스트 실패 횟수에 더하지 않고 작업물·세션을 보존해 R-091대로 같은 실행에서 실제 재검증·교정으로 연결한다. 완료 보고·문서 형식 오류와 Manager 전체 verify·Review의 기존 정책은 유지한다.

### Agent writer 종료와 무응답

프로세스 종료 관측과 호출 결과 처리를 구분한다. 종료가 확인된 실패·중단·결과 수집 오류 호출은 Requirement 교정을 계속 보류시키지 않는다. 결과 저장 누락 뒤 재시작해도 호출별 writer 종료 근거를 재확인하고 보존하며, 결과 분류·실제 종료 코드·실패 이력을 성공으로 바꾸거나 성공 근거로 재사용하지 않는다. 재시작 정리, 후속 호출 성공이나 임의의 종료 코드만으로 미확인 writer를 해제하지 않는다. 확인 근거가 없는 과거 호출은 보존한다.

Codex 신규·재개 호출은 Agent의 새 이벤트·출력 수신을 기준으로 10분 무출력을 감지한다. Manager heartbeat와 로그 저장량·수정 시각은 활동 근거가 아니다. 실행 중인 명령이 남으면 기존 전체 실행 제한을 유지하고, 그렇지 않은 무응답은 종료 확인 후 기존 제한 재시도로 전달한다. 완료된 턴이나 이미 종료한 프로세스의 출력 대기는 결과 수집 대기로 구분한다. Reviewer의 출력 제한·생략과 줄바꿈 전 부분 출력도 수신 활동을 잃지 않아야 한다.

### Agent 접근 권한과 Manager Git 작업

Agent의 파일·명령 접근 권한은 provider의 sandbox와 역할별 쓰기 정책으로 강제한다. source checkout·다른 worktree·shared Git metadata 쓰기를 제한하고 Reviewer의 작업 공간은 읽기 전용으로 유지한다. 신규·재개·fallback 호출에서 실제 적용 정책을 확인할 수 없거나 제한 적용이 실패하면 해당 호출을 중단한다. 격리 미확인이나 실패를 사후 Git 상태 비교로 대체하지 않는다.

Agent 호출 전후 refs·worktree·Git config·HEAD·index·파일 상태의 차이를 접근 권한 위반으로 추정하는 Git 범위 검사를 제거한다. 이러한 차이만으로 `agent_scope_violation`, `planning_error`, `PLAN_BLOCKED`, `PROJECT_BLOCKED`를 만들지 않는다. 과거 격리 ledger의 부재·불완전성, 실패한 호출·재시도·session 재개나 실행 단계 전환을 이유로 전체 또는 선택 자원의 snapshot 범위 비교를 되살리지 않는다. sandbox의 실제 거부·정책 오류 기록과 Git 관측 차이를 구분한다.

Manager는 작업 ID와 생성·등록 규칙으로 정한 worktree·브랜치에서 Git 작업을 수행한다. 대상 확인은 실제 생성·재사용·변경·정리에 필요한 현재 연결과 작업물 보존 조건으로 한정하며, 다른 브랜치로 바뀔 가능성을 가정해 매 Agent 호출의 과거 snapshot과 계속 비교하지 않는다. 역할별 문서 변경 권한, 계획 목표와 최종 diff·결과의 유효성 검증은 유지한다.

### 실행 상태 혼선의 복구

대상 작업의 branch가 비어 있거나 worktree에 planning·다른 작업의 경로가 저장된 경우, 실제 Git 대상의 변경과 Manager 실행 상태의 혼선을 구분한다. 신규·재개·planning 반환·runtime 인계와 기존 차단 재평가 모두 R-091의 작업별 실행 원본을 사용하며, 프로젝트 대표 투영의 값만으로 대상 작업의 소유권을 부정하거나 그 값을 작업 원본에 덮어쓰지 않는다.

기존 작업 원본까지 잘못 기록됐으면 해당 작업의 checkpoint·승인된 자원 생성/변경 기록과 현재 repository·branch·worktree 등록·HEAD·작업물의 연결을 확인해 검증 가능한 실행 자원 정보만 자동 복구한다. 이미 소유권이 확정된 작업도 포함하며, 이름이나 경로의 존재만으로 자원을 채택하지 않는다. writer 종료·자원 소유와 상태의 동시 변경을 확인하고, 중단·재시작에도 파일·index·commit·session·실패 이력과 유효한 성공 근거를 보존한다. 소유권 확인을 우회하거나 작업 공간을 reset·재생성하지 않으며, 복구만으로 수행하지 않은 단계의 성공을 기록하지 않는다. 근거 부족·복수 대상·실제 자원 연결 불일치이면 해당 작업과 충돌 자원의 쓰기를 보류하고 진단을 보존한다. 독립 작업의 진행과 기존 프로젝트 차단의 해제·축소는 위의 영향 범위 기준을 따른다. 문서 변경·사용자의 Git 원상복구·수동 DB 수정을 재평가의 전제로 요구하지 않는다.

### 예약 workspace의 소유권 확정과 자동 복구

기존 DB에 남은 ExecPlan의 예약 workspace는 생성과 소유권 확정 사이에 중단됐더라도 Manager의 승인된 생성·변경 이력과 현재 자원의 연결이 검증되면 작업물을 보존해 자동 확정·재개한다. DB가 없는 새 환경의 원격 작업 인수는 R-093을 따르며, 기존 예약 복구를 새 인수로 취급하지 않는다.

- 예약의 생성 기준과 해당 작업의 실행·검증 기준 `active_sha`를 구분해 보존한다. 실행 기준 갱신이 생성 기준을 덮어쓰거나 두 SHA의 불일치만으로 소유권을 부정하지 않아야 한다. 소유권 검사를 통과시키려고 `active_sha`를 실제 HEAD로 바꾸지 않는다.
- 생성 journal의 소유자·repository·작업 ID·canonical worktree·branch·생성 HEAD를 예약·checkpoint 및 현재 Git 등록·HEAD·index·파일·operation과 대조한다. 원격 인수를 거쳤다면 저장된 인수 자격과 대상도 확인한다. 생성 이후 HEAD가 바뀌었으면 승인된 변경 이력으로 현재 상태까지 설명돼야 한다. journal HEAD와 현재 또는 원격 branch HEAD의 일치, 경로·branch 이름, 예약 값만으로 소유권을 확정하지 않는다.
- 이전 writer 종료와 해당 작업·자원의 복구 소유권 및 작업물 보존을 확인한 뒤 기존 예약을 확정한다. worktree나 branch가 존재한다는 이유만으로 복구를 거부하거나 중복 생성·삭제·reset·강제 checkout으로 우회하지 않는다. 진행 중인 사용자 Git operation은 임의 완료·abort하지 않고, 미완료 Manager operation은 기존 복구 경계로 이어간다. 최신 base 반영·필요한 rebase와 후보 검증은 소유권 복구 뒤 정상 실행 흐름에서 판단한다.
- 생성·변경 증거가 부족하거나 현재 대상과 맞지 않으면 자원·작업물·감사를 보존하고 확정하지 않는다. 문제가 특정 작업에 한정되고 독립 자원의 안전이 확인되면 해당 작업·영향받는 dependency·충돌 자원만 보류한다. 공유 Git 설정·ref 소유권·다른 worktree 쓰기 등 프로젝트 전체 안전을 확정할 수 없을 때만 근거를 명시해 프로젝트 차단을 유지한다. 오류 코드만으로 차단 범위를 일괄 축소하지 않으며 독립 작업의 배정은 R-091을 따른다. 보류 기록은 원인 작업·자원과 그 영향으로 호출을 기다리는 작업을 구분한다.
- 기존 `workspace_ownership_uncertain` 프로젝트 차단도 현재 증거로 재평가한다. 원인 해소가 검증되면 예약 확정과 해당 차단·대기 확인 요청 해소를 중단·재시작 뒤에도 멱등하게 반영한다. 문제가 작업 범위에만 남으면 그 차단을 유지하고 해소된 프로젝트 차단만 축소한다. 확정 직전에는 현재 작업·자원·차단 원인·checkpoint가 검증 당시와 같은지 다시 확인하며, 경쟁 변경과 독립 차단·승인·실패·session·감사를 보존한다. 예약 복구만으로 Worker·verify·Review·rebase·게시의 성공을 만들지 않는다. 이미 소유권이 확정된 작업에도 동일한 writer 종료·자원 소유·원인별 재검증을 적용한다. 현재 차단 원인이 해소되고 저장된 원래 HEAD·target·현재 작업물과 연결된 Manager rebase가 확인되면, 아직 시작 전이거나 진행 중이라는 이유만으로 해제를 보류하지 않는다. rebase checkpoint·파일·index·session·실패 이력과 원래 저장 단계를 보존해 Manager가 정상 실행에서 필요한 Git 처리를 이어가며, 별개 승인·Review·공유 안전 차단은 유지한다.

### 정상 Git 변경과 실행 입력

사용자는 원격 원본·로컬 원본·원격 작업 branch에 언제든 push하거나 정상 Git 작업을 수행할 수 있다. Manager와 다른 프로세스의 fetch도 모든 단계에서 발생할 수 있다. 다른 작업의 commit·fetch·worktree 생성·정리, remote-tracking ref·`FETCH_HEAD`·파생 `origin/HEAD`의 갱신은 현재 작업의 Agent 위반이나 차단 사유가 아니다. 실제 사용 원격 ref의 변화는 동기화·게시 판단의 새 입력으로 처리한다.

Planner·Worker·verify·Reviewer의 단계 처리에서도 fetch·pull·rebase가 필요할 수 있다. 실제 Git 쓰기는 기존 Manager 경계에서 수행하고 역할별 파일 권한과 Reviewer의 읽기 전용은 유지한다. 같은 자원의 Agent·verify·Git writer가 실행 중이면 Manager의 동기화를 겹치지 않는다. 안전한 단계 경계에서 갱신하고 실제 경합은 현재 상태를 다시 관측해 제한 재시도·대기로 처리한다.

일반 verify는 실행한 후보와 실제 검증 입력을 확인하고, source checkout·다른 작업의 자원·정상 외부 fetch 때문에 후보가 불변인 성공을 무효화하지 않는다. Agent preflight는 해당 호출의 sandbox·역할 정책과 실행 입력을 확인하며 전체 GitSnapshot digest나 과거 Git 상태의 일치를 시작 조건으로 요구하지 않는다.

후보 HEAD·index·tracked 파일이 바뀌면 단계별 입력과 성공 근거를 다시 판단한다. verify는 R-072의 저장소 코드 입력이 달라졌을 때 필요한 전체 실행으로 돌아가며 SHA·환경/외부 입력 변화만으로 무효화하지 않는다. Review·게시 근거는 각자의 명세·diff·승인·후보 조건을 따로 확인한다. 정상 원격 변경을 수용했다는 사실은 오래된 성공을 재사용할 근거가 아니다. 단계마다 관측한 immutable OID를 사용하며 게시 직전에는 실제 원격을 다시 확인한다.

### 과거 Git snapshot과 BLOCKED 수동 작업

과거 실행의 Agent 시작·결과·Manager snapshot과 격리 기록은 감사 자료로 보존하며 현재 Git 상태의 접근 권한 판정 기준으로 사용하지 않는다. 격리 성공을 과거 기록에 합성하지 않는다. 현재 작업 대상의 연결이나 필요한 Git 작업 조건을 확인할 수 없으면 해당 동작만 보류하고, 실제 sandbox 정책 오류와 별도 승인·검증 실패는 독립적으로 처리한다.

차단으로 사용자에게 작업을 인계한 뒤 파일 수정·staging·commit·rebase·충돌 해결은 현재 작업의 새 입력으로 수용한다. 재개 전에 이전 Agent·verify·Git writer의 종료, 동일 repository·계획·canonical worktree·branch 연결, 현재 HEAD·index·파일·operation을 확인한다. 진행 중인 사용자 Git operation은 완료됐다고 추정하거나 임의 abort하지 않는다.

과거 Agent 시작·결과 snapshot과 현재 파일·index·HEAD의 완전 일치를 재개 조건으로 요구하지 않는다. 재개 중 작업물 보존 확인은 현재 선택 후보의 HEAD·branch·index·파일·진행 중 operation에 한정하며, 다른 ref·worktree·무관한 Git 설정이나 snapshot 감사 식별자의 차이 때문에 보존을 거부하지 않는다. 현재 작업물이 확인 구간에서 바뀌면 새 입력을 재관측하고 이전 검사 결과로 쓰기를 진행하지 않는다. 역사 snapshot은 진단·감사로 보존하고 현재 사용자 작업을 과거 기준선으로 되돌리지 않는다. `read-tree --reset -u`·reset·checkout 등의 복구도 보존 가능한 인계 뒤 변경을 덮어쓰지 못해야 한다. 충돌 복구가 불가능한 파일에는 아래 파일별 원본 복원·재작업 정책을 적용한다. 이전 실패의 감사와 다른 차단·승인을 유지하며 필요한 Worker 확인·targeted test·verify·Review를 새 후보에 결합한다.

### 기존 Git 차단의 자동 복구

정상 실행의 시작·재시작과 차단 재평가에서 기존 Git 이슈를 자동으로 다시 판단한다. 폐지한 Git 상태 비교, 다른 worktree·ref의 정상 변경, Manager의 정상 fetch·rebase·runtime 전이와 낡은 기준선, 원격 관측 경쟁으로 남은 `agent_scope_violation`·planning 오류·계획/프로젝트 차단·지속 실행 실패를 대상으로 한다. 입력 지문 변경, 추가 사용자 승인, 수동 DB 수정이나 과거 snapshot과의 일치를 복구 진입 조건으로 요구하지 않는다.

이전 writer의 종료와 현재 작업·runtime·원격 상태를 확인한 뒤 필요한 원격 동기화, 미완료 Manager Git 작업의 재개와 후보 검증으로 연결한다. 현재 동작 조건이 충족되면 해당 차단과 대기 중 확인 요청만 자동 해소하고 저장된 단계부터 이어간다. 정상 변경을 허용받기 위한 반복 Worker 교정이나 새 session 생성을 요구하지 않는다. 해소된 과거 원인의 retry 소진이 재개를 막지 않게 하되 실패·retry·해제 감사와 작업물·session·PR 이력은 보존한다.

현재도 남아 있는 실제 충돌·원격 접근 실패·미확정 게시·작업 대상 불일치는 기존 자동 복구·제한 재시도 또는 해당 동작의 보류로 처리한다. sandbox 적용 실패·실제 거부 기록, 독립적인 Review 실패·사용자 결정·승인은 Git 오탐 해제와 함께 지우지 않는다. 후보가 바뀌면 이전 성공을 무효화하고 필요한 검증부터 수행한다. 복구 확정 사이에 중단되거나 같은 입력으로 재실행해도 해소된 원인을 다시 차단·통지하거나 Git 작업을 중복 수행하지 않는다.

`publication_ownership_uncertain`·`remote_oid_uncertain`·PR 충돌 선검증 실패와 그 지속 실패도 원인과 현재 변경 관계로 재평가한다. `external_remote_oid`·`external_pr_head`, 과거 게시 OID·receipt 부재나 lease 경쟁만으로 남은 차단은 아래 조건을 만족하면 입력 지문 변경·retry 초기화·수동 DB 수정 없이 해제하고 동기화·후보 검증 또는 게시 결과 확인으로 이어간다. 같은 코드에 저장된 실제 origin·PR·작업 대상 불일치나 보존 불가 원인을 일괄 해제하지 않는다. 해소된 원인과 대기 확인 요청만 종료하고 session·작업물·과거 게시 및 실패 감사와 독립 원인은 보존한다.

### 원격 원본 동기화와 작업 브랜치 게시

원격 원본 `origin/<base-branch>`와 원격 작업 브랜치의 마지막 commit을 서로 다른 목적으로 관측한다. 원격 원본이 전진하면 작업 브랜치를 그 최신 원본 위로 rebase하고 바뀐 후보를 재검증한다. 로컬을 원격 원본 위로 정상 rebase한 `A → C → B'`는 원격 작업 tip `A → B`를 조상으로 포함하지 않아도 수용할 수 있다. 과거 Agent 시작 OID·checkpoint HEAD·Manager 표식의 완전 일치를 수용 조건으로 요구하거나 수행하지 않은 rebase·게시 성공을 합성하지 않는다.

원격 작업 브랜치와 로컬의 관계는 등록 repository·origin, 현재 작업·worktree·정확한 ref와 연결 PR을 확인한 뒤 판단한다. 작업 ID가 들어간 이름은 대상을 찾는 규칙이며, OID 차이는 다른 소유자의 자원이라는 근거가 아니다. 단순 일치·불일치 대신 공통 이력, 양쪽에만 있는 commit과 실제 변경, 현재 rebase·push intent를 확인한다. 과거 게시 receipt는 미완료 게시의 확인 자료이며 현재 원격 작업을 읽고 통합하기 위한 필수 허가증으로 사용하지 않는다. receipt 부재를 게시 완료나 덮어쓰기 권한으로 합성하지 않는다.

| 관측한 OID·ref 상태 | 정상 처리와 필요한 조건 |
|---|---|
| 다른 작업의 branch·tag·worktree ref 또는 `FETCH_HEAD`·remote-tracking ref·파생 `origin/HEAD`가 변경됨 | 현재 작업의 실제 입력과 사용하는 원격 기준만 재확인한다. 후보가 불변이면 계속하고, 무관한 ref의 과거 값을 복원하거나 Agent 위반으로 처리하지 않는다. |
| 원격 원본이 전진하고 로컬 원본 또는 실행 runtime의 OID는 이전 값임 | 작업 branch는 최신 원격 원본에 필요한 rebase·재검증을 수행한다. 선택 runtime은 R-020·R-023, 로컬 원본 동기화는 R-056을 따르며 세 OID의 일치를 요구하지 않는다. |
| 로컬 작업 branch만 새 commit을 포함하고 원격은 그 조상임 | 미게시 로컬 작업을 보존하고 필요한 후보 검증 후 게시한다. 원격 OID가 로컬 HEAD와 다르다는 이유로 통합이나 실행을 차단하지 않는다. |
| 원격 작업 branch만 새 작업을 포함함 | 정확한 ref를 fetch해 사용자 commit을 받아오고 후보·문서·검증 입력 변화에 필요한 단계부터 수행한다. 과거 checkpoint 게시가 없다는 이유만으로 수용을 거부하지 않으며, 실제 대상 연결과 작업물 보존을 확인한다. |
| 로컬·원격 양쪽에 새 commit이 있고 공통 이력 및 변경 관계를 확인할 수 있음 | 양쪽 commit·staged·unstaged·untracked 작업물을 보존해 기존 통합 경로로 연결한다. 실제 충돌은 해당 작업의 교정·복구로 처리하고 보존 가능한 작업을 reset이나 강제 push로 버리지 않는다. 충돌 복구가 불가능한 파일만 아래 원본 복원·재작업으로 연결한다. |
| 최신 원본 위 rebase로 로컬 이력이 재작성돼 과거 원격 작업 tip이 조상이 아님 | 현재 작업·rebase 결과와 원격의 추가 작업 여부를 확인한다. 새 원격 작업이 있으면 먼저 보존·통합하고, 기존 게시 이력만 재작성했으며 원격 작업을 잃지 않을 때 정확한 lease의 조건부 force push로 게시한다. |
| 같은 repository·연결 PR·head branch·base branch에서 PR head OID만 전진함 | 원격 branch와 실제 PR head를 다시 관측해 동일 후보인지 확인하고 새 작업을 받아온다. PR URL·대상 변경과 head 전진을 구분하며, 새 후보에는 필요한 검증·Review를 수행한다. PR 등록 이후 ExecPlan 갱신 권한은 확대하지 않는다. |
| 정상 rebase 등 원격 원본·작업 branch의 이력 재작성 뒤에도 동일 작업의 변경 관계와 양쪽 작업 보존을 확인할 수 있음 | 현재 원격 원본의 명세·목표를 확인하고 보존·통합·재검증으로 처리한다. OID나 단순 조상 관계만으로 영구 차단하지 않는다. 삭제된 내용의 의도나 어느 결과를 채택할지 불명확한 경우는 아래 보류 조건을 따른다. |
| 관측 후 push 전에 원격 tip이 바뀌거나 부재였던 ref가 생성됨 | 해당 push를 중단하고 새 ref의 대상·변경 관계부터 재관측한다. 필요한 통합·재검증 뒤 새 게시를 판단하며 원격 조회 실패를 부재로 취급하지 않는다. |
| push가 끝났거나 진행 중에 중단돼 원격 OID와 저장된 게시 결과가 다름 | 현재 실제 원격과 보존된 게시 대상·후보·intent를 대조해 완료 또는 미완료를 확인한다. 이미 완료된 push를 반복하지 않고, 원격이 그 뒤 다시 전진했으면 자신의 게시 확인과 후속 작업 통합을 구분한다. |
| 관련 ref·PR·Git 조회가 일시 실패하거나 서로 다른 시점의 OID가 관측됨 | 필요한 관측을 제한 재시도·대기로 처리한다. 안정된 입력을 확인하기 전에는 Git 쓰기나 성공 확정을 하지 않고, 관측 경쟁 자체를 소유권 위반이나 사용자 판단으로 바꾸지 않는다. |
| 과거 원인·checkpoint 요청·확정 journal의 OID가 최신 입력과 다름 | 과거 완료는 감사로 보존하고 미완료 전이와 현재 후보를 다시 판단한다. stale 요청을 그대로 실행하거나 확정 기록을 현재 권한으로 사용하지 않는다. 이미 해소된 원인은 종료하고 최신 입력의 필요한 처리를 이어간다. |

게시 대상 브랜치의 expected OID는 최신 원격을 보존·통합한 이번 push의 전제이며 과거 Agent 시작 OID를 고정하는 gate가 아니다. 관측 뒤 실제 push 사이의 경쟁은 명시적 expected OID 또는 정확한 부재에 결합된 `--force-with-lease`로 확인한다. `stale info`·`fetch first`·`non-fast-forward` 등은 현재 변경 관계를 다시 판단할 계기이며, 새 OID만 lease에 넣어 같은 후보로 덮어쓰거나 원문 메시지만으로 영구 실패·사용자 조치를 확정하지 않는다. 반복 경쟁에는 실행별 한도로 대기하고 다음 실행에서 재관측한다. 중간 checkpoint 게시 실패는 미게시 작업을 보존하고 로컬 수용·구현 재개와 분리한다. 미완료 게시 결과의 관측·확정은 안전한 다음 쓰기 전에 해결한다.

### Manager 소유 원격 작업 브랜치 삭제와 명시적 재시작

Manager는 생성·게시한 원격 작업 branch의 정확한 repository·ref·작업 연결과 생성·게시 결과를 보존한다. 해당 branch가 실제 원격에서 삭제됐고 연결 PR이 Merge되지 않았다면 삭제 의도를 추정해 자동 재생성하거나 계속 게시하지 않고 그 작업을 중단해 명시적 재시작 요청을 기다린다. PR이 아직 생성되지 않은 작업도 같은 규칙을 적용한다. 원격 조회 실패는 삭제로 처리하지 않으며, 실제 PR Merge 후 branch 정리 삭제는 기존 완료·cleanup 처리로 연결한다.

중단은 안전한 실행 경계에서 현재 writer 종료와 작업물·session·실패 및 게시 감사를 보존한 뒤 확정한다. 해당 작업의 자동 Worker·verify·Review·push와 낡은 게시·복구 요청을 계속 실행하지 않고, 독립 작업·프로젝트와 실제 PR 관측은 유지한다. 삭제 사유·원격 관측·PR 상태와 필요한 재시작 요청을 안내한다. Manager 프로세스 재시작·일반 `run`·pause 해제나 같은 이름의 branch 재생성을 작업 재시작 요청으로 간주하지 않는다.

사용자가 해당 작업의 재시작을 명시적으로 요청하면 그 요청 자체를 새 작업 시작의 승인으로 사용한다. 현재 유효한 명세·목표와 최신 원격 원본에서 기존 작업 ID의 새 실행을 준비하고 이전 후보·session·게시 이력은 과거 감사로 남긴다. 이전 단계·성공 token·삭제된 branch의 게시 intent를 새 실행의 완료 근거로 재사용하지 않는다. 새 실행은 Worker·필요한 검증·Review·게시의 정상 경로를 따르며 필요한 원격 작업 branch는 생성 규칙에 따라 새로 준비한다.

재시작 준비 전에 실제 PR이 Merge됐다면 완료 처리를 우선한다. 같은 이름의 원격 ref가 이미 재생성됐으면 현재 대상·새 원격 작업을 확인하고 다른 작업물을 덮어쓰지 않는다. 이전 writer 종료·실제 자원 연결·독립 사용자 결정·dependency·pause 조건은 그대로 적용하며, 재시작 접수·새 실행 준비 중 중단돼도 같은 요청을 중복 실행하지 않는다. 기존 PR의 실제 상태와 연결·감사는 보존하고 새 후보의 게시 시 현재 PR 경계를 다시 확인한다.

### 충돌 복구가 불가능한 파일의 원본 복원과 재작업

로컬·원격의 변경을 보존하며 충돌을 복구할 수 없는 파일은 보존 실패 자체로 사용자 조치 대기를 유지하지 않고, 확인한 `origin/<base-branch>`의 복구 기준 revision에서 해당 파일만 원본 상태로 복원해 재작업한다. 단순 OID 차이·일반 충돌만으로 복원을 시작하지 않고 복구가 불가능한 경로와 사유를 파일별로 확인한다. 현재 작업의 유효한 명세·목표와 확인 가능한 기존 수정 내용을 Worker에게 전달해 해당 파일의 구현을 보완하고 필요한 targeted test·verify·Review를 수행한다.

복원 범위는 선택한 관리 worktree의 해당 파일 내용과 그 경로의 index entry에 한정한다. 충돌이 없는 파일과 이미 복구된 파일의 내용·staged·unstaged·untracked 상태, 다른 경로의 충돌 단계와 기존 commit·HEAD·branch는 유지한다. worktree·branch·index 전체 reset이나 일괄 clean으로 실행 조건을 만들지 않는다. 기본/source checkout·다른 worktree·원격 원본 및 작업 branch·PR도 유지한다. 복구 기준 원본에서 파일이 삭제·이동됐다면 확인한 부재·새 경로를 반영하고 낡은 파일을 임의로 되살리지 않는다.

복원 전 현재 작업·worktree·경로 연결, 이전 writer 종료와 원격 원본을 확인한다. 해당 파일의 복원 전후 상태·기준 revision·실패 사유와 확보 가능한 자료를 감사로 남기지만 복구 불가 파일의 완전한 형상 보존을 필수 조건으로 요구하지 않는다. 그 파일의 이전 변경은 재작업으로 대체할 수 있으며 다른 파일을 대체 범위에 포함하지 않는다. 바뀐 후보의 성공 근거는 R-072에 따라 실제 입력으로 다시 판단하고 session·실패·재시도·재작업 사유와 독립 차단은 보존한다.

진행 중인 현재 소유 Manager Git 작업에서는 기존 target·원본 revision을 유지한 복구 단계에서 해당 파일만 처리하고, 사용자 operation이나 다른 writer는 종료될 때까지 기다린다. 현재 작업 대상·경로 또는 복구 원본을 확인할 수 없으면 그 준비만 보류한다. 파일 복원·상태 저장 중 중단돼도 완료된 파일을 다시 되돌리거나 새 교정 결과를 덮지 않고 남은 파일·단계부터 이어간다. 최종 게시에서는 재작업한 파일과 이후 새 원격 작업을 대조해 필요한 입력을 반영하고 정확한 lease로 게시한다. 파일 복원만으로 원격 덮어쓰기 권한이나 게시 성공을 만들지 않는다.

### OID·ref 판정에서 자동 쓰기를 보류할 조건

아래 조건은 단순 값 차이와 구분해 현재 근거로 확인한다. 보류 사유에는 실제 대상·관계·보존·접근 문제와 해소에 필요한 조건을 기록한다. Git 권한 강제는 sandbox에 맡기며 과거 snapshot 일치 검사를 되살리지 않는다.

| 현재 확인한 조건 | 보류·복구 범위 |
|---|---|
| 등록 origin·repository, 작업·canonical worktree·branch 연결 또는 실제 PR의 repository·URL·head/base branch가 다른 대상임 | 해당 대상의 Git 쓰기·게시를 중단하고 연결을 재확인한다. 다른 소유자의 branch·PR을 자동 인수하거나 잘못된 origin으로 보내지 않는다. PR close·Merge는 실제 PR 상태 처리로 연결한다. |
| 이력 재작성·서로 무관한 이력에서 실제 삭제 의도·작업 목표 또는 필수 사용자 결정을 확정할 수 없음 | 해당 판단에 필요한 통합·게시를 보류하고 구체적인 선택을 요청한다. 작업 목표와 원본이 확인된 복구 불가 파일은 위 재작업으로 연결하며, 보존 실패만으로 사용자 판단을 요구하지 않는다. |
| Manager가 생성·게시한 원격 작업 branch가 실제 삭제됐고 연결 PR이 Merge되지 않음 | 해당 작업을 중단해 명시적 재시작 요청을 기다린다. 일반 실행·pause 해제·같은 이름의 ref 재생성으로 자동 재개하지 않고 이전 작업물·PR·감사를 보존한다. 재시작 요청 후 최신 원본에서 새 실행을 준비한다. 원격 조회 실패·Merge 후 정리 삭제는 이 중단으로 처리하지 않는다. |
| 같은 자원의 writer가 미종료·종료 불명, 사용자 Git operation 진행 중, 또는 미완료 Manager 전이의 대상·원형이 현재 작업과 맞지 않음 | 해당 자원의 새 Git 쓰기를 대기 또는 보류한다. 현재 소유 Manager 작업은 기존 journal로 이어가고 사용자 operation을 임의 abort하거나 원형을 폐기하지 않는다. 완료 여부가 불명확한 전이를 성공으로 표시하지 않는다. |
| 인증·게시 권한·branch protection이 실제 쓰기를 거부함 | 해당 원격 동작을 보류하고 필요한 설정·권한 조치를 안내한다. 다른 원격·무조건 force push로 우회하지 않는다. 네트워크 실패·관측 경쟁과 구분하고 안전한 로컬 작업과 독립 작업은 보존한다. |
| immutable 진단 ref에 다른 OID가 있거나 cleanup 대상 ref가 저장한 소유 대상·OID와 다름 | 해당 진단 ref 갱신·삭제만 보류하고 기존 자료를 보존한다. 진단 ref는 `loop-manager/diagnostics/<작업 ID>/<해시>` 형태의 충돌·실패 자료 보존용 원격 branch다. Reviewer가 검토하는 작업 후보와 구분하며 이 불일치를 verify·Review 진입 조건으로 사용하지 않는다. R-083의 원격 삭제 lease를 최신 관측 OID로 바꿔 삭제하지 않고 완료 결과와 정상 작업을 유지한다. |

Reviewer 진입 전 후보 HEAD가 이전 verify·Review의 OID와 달라도 최신 문서·코드·diff와 실제 검증 입력으로 필요한 단계를 판단한다. R-072에 따라 검증 입력 동일성과 성공 근거가 유효하면 verify를 재사용하고 현재 후보의 Review를 진행한다. 필요한 검증이 바뀌었거나 근거가 부족하면 verify를 수행하거나 R-082·R-086의 선행 Review에서 구현·검증의 미충족 범위를 확인해 필요한 검증으로 연결한다. OID 차이나 진단 ref 게시 실패만으로 Reviewer 진입을 막거나 Worker 재구현을 일괄 요구하지 않는다. Reviewer는 문서·코드·실제 검증 근거를 읽고 판단하며 테스트·verify를 직접 실행하지 않는다.

Review 실행 중 후보가 바뀌었으면 이전 후보의 verdict를 새 후보의 승인으로 사용하지 않고 현재 입력에서 필요한 verify·Review를 다시 판단한다. 구현 보완이 필요한 경우에만 Worker 교정으로 돌아간다. 최종 게시 전에는 실제 최종 후보의 필요한 verify와 유효한 Review를 확인하며 오래된 승인으로 바뀐 HEAD를 게시하지 않는다. 현재 ref와 worktree의 연결을 확인할 수 없거나 필요한 commit 객체·원형이 없어 관계를 판단할 수 없으면 읽기·복구 가능한 근거를 먼저 확보하고 그 동작만 보류한다.

프로젝트 전체 안전 차단은 현재 문제 때문에 프로젝트의 모든 변경 자원을 안전하게 구분하거나 보호할 수 없는 경우에만 적용한다. 개별 작업 branch·PR·push·cleanup의 OID 문제는 그 동작에 한정하며, 실제 독립 Review·사용자 결정·승인·sandbox 오류는 함께 해제하지 않는다.

### 동기화·journal·cleanup·변경 없음

실행 중 runtime 파일은 선택 revision으로 고정하며 외부 fetch로 덮어쓰지 않는다. 단계 경계의 원격 변경 확인·안전한 자동 재시작은 R-023을 따르고 로컬 동기화 실패와 runtime 소유권 오류를 구분한다. Git journal은 실제 미완료 전이·자원·소유자에만 적용하며 무관한 ref/worktree의 기록으로 다른 작업을 막지 않는다.

Merge 확인 뒤 cleanup 실패는 `cleanup_pending`으로 보존·재시도하고 완료 결과나 독립 작업을 되돌리지 않는다. 이미 원격 확인된 문서 게시의 성공 근거는 해당 게시 revision으로 유지하고, 이후 사용자가 수정한 최신 문서는 새로운 입력으로 평가한다. 미확정 게시를 byte 불일치만으로 성공 처리하지 않는다.

원격 변경으로 후보 diff가 사라지면 기존 PR의 실제 Merge, 외부 변경에 의한 목표 충족, 구현 부족과 대체 필요를 구분한다. `NO_CHANGE`만으로 계획 입력 오류·최종 차단을 만들지 않는다. 외부 목표 충족은 최신 명세·구현·검증 근거로 Planner가 기존 미충족 목표와 관계를 정리하며, 연결 PR Merge 없이 ExecPlan을 `MERGED`로 만들거나 dependency를 충족했다고 기록하지 않는다.

중복 snapshot·ancestry·checkpoint 복구 판정은 기존 공통 경계로 통합하고 불필요한 이전 검사·복원 분기를 제거한다. 새 예외·상태 테이블·복구 계층을 계속 추가하는 방식으로 구현하지 않는다.

### 계획·작업 문서 삭제의 자동 반영

Manager는 검증한 원격 revision의 삭제·이동과 마지막 채택 선언·실행·게시 이력을 대조해 대상 identity와 영향 범위를 확인한다. 일반 Planner는 최신 PRODUCT·Requirement와 보존된 원문을 근거로 목표의 철회·유지·대체와 관련 문서의 수정안을 판단한다. Manager는 허용 범위·목표 보존·실제 PR·소유권을 재검증하고 문서 게시, DB 반영과 브랜치 정리를 수행한다. 명확한 경우에는 별도 사용자 결정을 기다리지 않으며, 의미·소유권·보존을 확정하지 못한 영향 범위만 이유와 근거를 남겨 보류한다.

기본 checkout에만 있는 삭제, 원격 조회 실패, active·archive 이동, 같은 identity의 rename과 실제 삭제를 구분한다. Requirement의 rename·archive는 기존 source resolver로 연결하고 삭제로 인한 취소를 만들지 않는다. 삭제와 새 ID의 동시 발생만으로 같은 문서의 ID 변경이라고 추정하지 않는다. 여러 문서를 함께 삭제했거나 등록 전에 삭제했거나 DB 실행 row 없이 예약·보류·완료 감사만 남은 경우도 현재 부재와 확인 가능한 이력을 복구 입력으로 제공한다. 과거 원문이나 삭제 이력을 얻지 못하면 추측으로 취소·복원하지 않고 그 범위만 재관측·검토한다.

| 삭제 대상과 조건 | 자동 처리 |
|---|---|
| 미착수·무소유 또는 draft ExecPlan의 확인된 삭제 | 현재 실행 대상에서 취소하고 삭제 revision·원본 identity와 취소 감사를 보존한다. 연결된 draft 판단·예약도 활성 대기에서 제외한다. 남아 있는 제품 목표는 Planner가 다른 작업 또는 새 ID의 대체 작업으로 연결한다. |
| 실행 이력·소유 브랜치·worktree가 있는 ExecPlan의 삭제 | 안전한 단계 경계에서 해당 작업의 새 Worker·verify·Review·게시를 멈춘다. 마지막 선언·코드·session·실패·PR 이력을 보존한 뒤 확인된 철회를 현재 취소로 반영하고 소유 자원을 정리한다. 실행 이력이 있다는 이유만으로 삭제 처리를 영구 보류하지 않으며 실제 Merge가 확인된 작업의 완료는 취소로 바꾸지 않는다. |
| Requirement 삭제로 연결 작업의 목표 전체가 불필요해짐 | 직접 `sources`뿐 아니라 목표·Acceptance Criteria·본문 참조를 확인해 관련 활성 작업의 삭제안을 함께 게시하고 각 작업의 DB·브랜치에 반영한다. 이미 구현된 코드나 과거 완료를 문서 삭제만으로 되돌리지 않는다. |
| 복수 Requirement 또는 PRODUCT에 연결된 작업에서 일부 근거·Acceptance Criteria만 삭제됨 | 남은 현행 목표에 필요한 작업·공유 구현을 유지하고 삭제 조건에만 필요한 체크리스트·파일별 변경 목적·검증 지시·source·링크를 개정한다. 부분 목표와 근거 관계는 R-082·R-090을 따른다. PRODUCT나 다른 Requirement가 유지하는 목표를 제거하지 않으며 단순히 source 경로만 지워 유효한 것으로 취급하지 않는다. |
| 삭제된 작업이 다른 작업의 선행·구현·검증 근거임 | 직접·간접 의존 관계와 본문·경로 참조를 함께 재평가한다. 현행 근거에서 불필요한 선행은 문서와 DB에서 제거하고, 필요한 목표는 유효한 대체 작업의 dependency로 연결한다. 다른 후속 작업도 더 이상 필요 없으면 같은 삭제 절차를 적용한다. |
| 실제 MERGED 작업·archive 문서 또는 완료 Requirement의 삭제 | 완료·최초 게시·PR Merge·ID 예약과 감사는 보존하고 해당 문서 부재를 현재 선언에 반영한다. 확인된 Merge 이력은 기존 선행 충족 근거로 유지한다. 역사적 source·링크 부재를 활성 작업의 오류나 새 계획 등록으로 바꾸지 않으며 과거 기록을 참조 정리 목적으로 편집하지 않는다. |

삭제 자체는 목표 충족이나 PR Merge의 증거가 아니다. 필요한 선행 목표를 dependency 제거만으로 우회하지 않고, 아직 필요한 목표의 개정·대체 뒤에는 전체 관계의 유효성·순환 부재와 기존 실행 준비 조건을 확인한다. 사용한 ExecPlan ID는 재사용하지 않으며 번호 공백을 누락으로 추정하지 않는다. 취소·완료·예약 이력과 현재 파일의 관측을 구분해 삭제된 ID를 신규로 재등록하거나 `unknown-plan-id` 예약 충돌을 만들지 않는다. 실제 재사용·identity 충돌은 계속 거부하고, 같은 ID의 파일이 재등장해도 취소를 자동 해제하거나 READY로 복원하지 않는다.

### 삭제의 DB·브랜치 반영과 중단 복구

관련 문서의 유효한 최종 변경을 원격에서 확인한 뒤 현재 DB의 source·dependency·선택 자격·유효 우선순위와 영향받는 일반·유지보수 작업 집합을 같은 관계로 반영한다. 삭제·취소된 ExecPlan은 문서에서만 없어지는 것으로 끝내지 않고 활성 실행 row에서 제거하며 draft 판단·수동 준비·완료 대기에서도 제외한다. 삭제 ID·마지막 선언·삭제 revision·취소 이유·완료·실패·session·PR·소유 자원과 복구 근거는 활성 실행과 분리한 DB 감사에 보존한다. 제거와 취소 감사·관련 관계의 적용은 같은 transaction에 결합한다. 수동 소유 작업의 취소·편집·정리는 기존 수동 권한과 자원 조율을 따른다.

유지보수 대상의 안전한 취소·철회 반영 뒤 남은 대상과 필요한 dependency가 없으면 R-074에 따라 필요한 게시·상태 반영을 마치고 cycle을 정상 종료한다. 모든 대상의 실제 Merge, 전체 취소, 일부 Merge·나머지 취소와 처음부터 작업이 없는 경우에 같은 종료 원칙을 적용하며, 종료를 위한 새 평가나 사용자 판단은 요구하지 않는다. 대상의 단순 부재를 취소 확정으로 추정하거나 취소를 Merge·구현·검증 성공으로 기록하지 않고, 종료 시 실제 MERGED 수를 다음 주기의 기준으로 보존한다.

활성 row 제거는 필요한 감사를 지우거나 실행 중 소유권을 무조건 폐기한다는 뜻이 아니다. 시작한 작업은 writer 종료·안전한 단계 경계와 작업물·소유권·이력 보존을 확인한 뒤 현재 취소·활성 row 제거를 확정한다. 확인 전에는 실행 보류와 기존 row·소유권을 보존하고 신규 실행을 막는다. 자원 정리 pending은 별도 보존·복구 기록에서 이어가며 활성 row 제거 뒤에도 소유 증거를 잃지 않는다. 문서 부재를 이유로 실제 MERGED나 완료 감사를 삭제·취소로 재기록하지 않는다.

catalog, Planner 입력·복구 snapshot, source 해석·문서 읽기, Requirement 충족 판단·archive, 단계별 실행 입력, dependency·우선순위 선택과 조회는 동일한 삭제 반영 결과를 사용한다. 남아 있는 역사적 source를 무조건 조회해 전체 planning을 실패시키지 않는다. 삭제로 의미가 바뀐 입력 지문·Planner 판단·draft 결정·verify·Review·게시 근거는 각 기존 재사용 조건에 따라 무효화하고, 취소된 작업의 미완료 실행·checkpoint·게시 요청과 미전송 알림을 현재 수명에 맞게 정리한다. 이미 확정된 게시·검증·알림은 감사로 보존한다.

유지하는 작업의 관리 브랜치는 최신 문서 삭제·개정을 안전한 동기화·rebase 경계에서 반영한다. 낡은 작업 브랜치·planning 결과·재개 snapshot으로 삭제된 문서를 되살리거나 취소된 작업을 계속 게시하지 않는다. 실행 중 writer·Git operation을 겹치지 않으며 문서 교정은 Manager가 허용한 snapshot·수정안 게시 경계를 사용한다. 다른 코드·index·사용자 작업 전체를 reset하지 않고, 유지하는 목표가 바뀌면 필요한 Worker 교정·검증·Review를 거친다.

문서 삭제를 반영한 취소·완료 작업의 Loop Manager 소유 로컬·원격 작업 브랜치와 worktree는 자동 정리 대상이다. 삭제 전에 해당 repository·작업·자원의 소유권, 실행 writer의 종료, 실제 원격 head와 PR 상태, 다른 작업·수동 소유자의 사용 여부를 재확인한다. 미게시 commit·사용자 변경·실행 및 실패 근거는 복구 가능한 위치에 보존하고, 삭제할 정확한 ref와 기대 OID에 결합한 정리 결과를 확인한다. 등록 base·사용자 브랜치·다른 작업 자원은 이 삭제 권한에 포함하지 않는다. 원격 후속 commit·재생성·소유권 변경은 낡은 삭제 요청으로 제거하지 않고 재관측한다.

연결 PR의 실제 Open·Closed·Merged 상태와 head는 삭제 처리에서도 보존·관측한다. 문서 삭제만으로 PR을 자동 Merge·종료하거나 실제 MERGED를 취소하지 않는다. PR head의 보존·현재 사용과 브랜치 정리가 양립하는지 확인할 수 없으면 해당 정리만 보류한다. 권한·보호 정책·소유권·작업물 보존 문제로 자원을 정리하지 못해도 확인된 문서·DB 반영을 되돌리지 않으며, 보존 위치·미정리 대상·실제 이유를 pending으로 남겨 독립 작업을 계속한다.

문서 게시·DB transaction·브랜치 정리는 하나의 원자 작업으로 가정하지 않는다. 처리 intent·관측 revision·관계 변경과 자원별 기대값·실제 결과를 보존하고, 원격 게시 뒤 DB 미반영, DB 반영 뒤 브랜치 미정리, 원격 브랜치 삭제 뒤 결과 미기록에서 확정 지점부터 멱등하게 이어간다. 이미 사라진 정확한 소유 자원은 완료로 대조하되 같은 이름으로 재생성된 자원은 별개로 검증한다. 미게시 수정안이나 일부 자원 정리만으로 관계 복구·보류 해제를 성공 처리하지 않으며 같은 입력·결과의 Planner 호출·게시·삭제·알림을 반복하지 않는다.

### 실행 보류와 Planner 복구 검토 권한

catalog의 실행 보류는 유효하지 않은 작업의 Worker 진입을 막는 조건이며, 일반 Planner의 원인 조사·복구 검토를 금지하는 조건으로 사용하지 않는다. 아래 오류와 관련 source·참조·삭제 이력 보류는 자동 복구 입력이며 오류 코드만으로 사용자 결정을 요구하지 않는다. 일부 삭제 취소 기록에 연결되지 않았다는 이유만으로 복구 검토에서 제외하지 않는다.

| 보류 원인 | Manager와 Planner의 처리 |
|---|---|
| `missing-plan-reference` | Manager가 참조 대상의 rename·archive·실제 삭제와 영향 문서를 확인하고 Planner가 source·dependency·구현·검증·본문 참조의 유지·제거·대체를 판단한다. 검증한 개정·삭제를 게시하고 DB 관계에 반영한다. |
| `missing-plan` | Manager가 파일 부재와 삭제·실행·예약 이력을 대조해 삭제 반영 또는 추가 관측으로 연결한다. Planner는 보존된 원문과 현재 목표로 잔여 작업·후속 관계를 정리한다. 원문 부재를 복구 검토 전체의 조회 실패로 만들지 않는다. |
| `deleted-goal` | 삭제된 선행 목표의 명시적 판단은 일반 Planner가 최신 근거와 제거·대체 이유를 반환해 충족할 수 있다. Manager는 필요한 목표의 유효한 대체 dependency 또는 선행이 불필요해진 근거를 검증한 뒤 문서·DB를 갱신한다. 판단이 불확실한 관계만 보류한다. |

Planner에는 보류 원인·대상 ID와 경로·관측 revision·마지막 검증 선언과 삭제·참조 이력·관련 명세를 제공한다. Planner는 최신 목표에 따라 source·dependency·본문 참조의 개정·삭제나 대체 작업을 제안할 수 있고, 직접 편집은 Manager가 허용한 원격 revision·소유권에 결합된 snapshot의 문서로 제한한다. 실행 이력이 있는 작업의 취소·자원 정리는 Manager가 보존·소유권을 확인해 수행하며 Planner의 직접 삭제 권한으로 확대하지 않는다. 실행 보류 자체를 교정 권한의 거부 근거로 삼지 않되 PR 등록·archive·실행 중 writer·사용자 판단과 문서 소유권 경계는 유지한다. 삭제된 ID·파일을 임의로 복원하거나 필요했던 목표를 참조 삭제만으로 충족했다고 판단하지 않는다.

작업 전체의 철회·삭제 판단은 마지막 source와 삭제 revision·현재 목표의 관계를 근거로 검증한다. 이미 삭제된 Requirement를 현재 문서로 다시 읽거나 남아 있지 않은 source를 유지해야만 삭제안을 제출할 수 있도록 요구하지 않는다. 계속 실행하거나 새로 만드는 작업에는 유효한 현행 source가 있어야 한다.

Planner의 복구 결과만으로 실행 보류를 해제하지 않는다. Manager는 최신 원격 내용, 변경 권한과 실제 PR·작업 소유권, 문서·source·dependency의 전체 관계와 목표 보존, 원격 게시·catalog 적용 결과를 다시 검증한 뒤 해소된 원인의 영향 범위만 해제한다. 미게시 수정안, 문구만 삭제한 결과, 불완전한 근거 또는 검토 중 원격·소유권 변경은 기존 보류를 유지하고 재검토한다. 중단 후에도 게시·적용·해제의 실제 확정 지점부터 이어가며 다른 보류·승인·실패 이력을 지우지 않는다.

### 작업 범위 밖 공통 결함의 자동 교정과 재개

- Worker·Manager verify·Review에서 선택된 ExecPlan 밖의 공통 구현·검증 기반 결함이 발견되면 Manager는 영향 작업의 실패·질문·현재 후보와 진단을 보존하고, 실제 코드·검증 근거·적용 명세로 동일 원인과 영향 범위를 확인한다. 원인이 확인된 여러 작업의 보고는 하나의 미충족 공통 목표로 묶되, 유사한 증상만으로 다른 원인이나 독립 차단을 합치지 않는다. 원인 미확정은 증거 수집·재검증 대상으로 보존하고 성공·일시 부하·사용자 판단으로 추정하지 않는다.
- 기존 PRODUCT·활성 Requirement가 원하는 동작과 안전 조건을 정하고 있으면 이를 source로 사용해 [R-082](%5BR-082%5D%20단계별%20원격%20문서%20반영과%20PR%20전%20ExecPlan%20갱신.md)의 일반 Planner가 기존 작업의 허용 개정 또는 하나의 공통 교정 ExecPlan으로 미충족 목표를 계획한다. 동일 원인·source·완료 기준을 맡은 유효한 계획은 재사용하고 중복 생성·무관한 작업 재구현을 피한다. 공통 결함 보고나 코드·ExecPlan 변경만으로 R-082의 별도 Planner 호출 조건을 새로 만들지 않으며, 명세 변경·기존 복구/완료 재평가의 허용된 planning 경계에서 보존된 미충족 근거를 반영한다.
- 발견한 Worker는 선택 작업 밖의 코드·Requirement·다른 ExecPlan을 직접 변경하지 않고 공통 원인·실패 증거·보존 자료를 Manager에 인계한다. Manager가 승인되지 않은 범위 확대·조율 인증값 전달·안전 검사 우회 없이 별도 작업의 소유권·dependency·게시·전체 검증을 적용한다. 기존 명세로 결정 가능한 구현·실행 경계의 교정과 공통 결함을 별도 작업으로 분리할지 여부는 사용자 결정으로 승격하지 않는다. 명세 사이 실제 충돌, 사용자만 정할 수 있는 정책 선택 또는 필요한 변경 권한·보존 대상의 의미를 확정할 수 없는 경우에만 근거와 선택 영향을 명시해 해당 범위를 보류한다.
- 공통 교정의 검증된 반영 뒤 Manager는 영향 작업별 현재 원격·명세·후보·원래 차단 질문과 원인을 재평가한다. 현재 명세가 질문의 구체적 선택을 해소한 근거가 있을 때에만 R-091의 `user_decision_required` 재평가로 그 원인을 해제하며, 문서 변경·Planner의 선언·질문 삭제를 사용자 승인으로 합성하지 않는다. 기존 Worker 작업물·branch·session·실패와 검증 이력을 보존하고 실제 후보 변화에 필요한 verify·Review를 재실행한 뒤 기존 단계에서 재개한다. 미Merge 교정·미확인 검증·별도 승인·진짜 소유권/안전 문제는 보류하며 독립 작업은 계속 진행한다. 같은 원인에 대한 무진전 재호출·중복 질문·계획·알림은 만들지 않는다.

### planning 오류와 기존 계획의 실행

- 계획 생성·교정 오류는 새 Planner 주기의 시작과 프로젝트 완료 선언을 보류하되, 이미 게시된 유효한 독립 ExecPlan의 구현·검증·Review·기존 PR 처리를 막지 않는다. 실행·관리 한도와 배정 순서는 [R-091](%5BR-091%5D%20프로젝트%20공정%20배정과%20우선순위%20기반%20병렬%20작업.md)을 따르며 프로젝트 전체에 단일 변경 실행을 요구하지 않는다. 변경된 코드·구조에도 해당 계획의 목표·dependency·검증 기준이 유효한지 먼저 확인하며, 유효성을 확정하지 못한 계획은 그 영향 범위만 보류한다.
- 오류가 난 planning worktree·session·입력 지문·미게시 결과·진단은 실행 상태와 독립적으로 보존하고 변경 실행 자리를 안전하게 비운다. 다른 계획의 실행·PR Merge가 오류를 지우거나 planning 결과를 성공으로 확정하지 않는다. 진행 중 Git operation·미확정 게시·실제 공유 자원 불확실성은 기존 안전 경계에서 먼저 정리·확정하며 planning 기록을 강제로 덮어쓰지 않는다.
- 같은 실패 입력의 Planner 호출은 반복하지 않는다. 관련 원격 입력, 위 Git·writer·자원·복구 조건의 변화 또는 R-062의 로컬 환경 재검사 요청이 생기면 보존된 planning 작업을 재평가하고, 실제 원인이 해소된 뒤에만 오류를 해제한다. 재평가는 새 Planner 호출과 구분하며 유효한 저장 결과·게시 intent는 재사용한다. 상태 재구성·중단·재시작에서도 기존 계획의 진행과 planning 오류 보존을 함께 유지한다.

폐지 대상인 Agent Git 범위 검사와 필요한 sandbox 정책·후보 검증·Manager Git 작업 조건을 구분한다. 같은 원인이 여러 경로에서 발생하면 공통 경계에서 제거·교정하고 실제 정책 적용 실패와 작업물 유실을 막는 회귀 조건을 검증한다. 조사 결과와 수정·유지 이유는 관련 ExecPlan에 남기며, 현재 범위 밖의 구조 개선은 이 조사의 구현으로 확대하지 않는다.

## Acceptance Criteria

- 여러 rebase를 연속 시작해도 이전 operation 이력이 자기 자신을 재귀적으로 포함하지 않는다. 각 과거 operation과 현재 acceptance·target·원격 lease의 근거는 보존된다.

- 현재 Git/CLI/DB/CPU 자원 경쟁·정상 remote/PR HEAD 전진·Manager push 뒤 stale OID·cleanup pending·retry 묶음 소진은 자동 재구성·조건 대기가 유효하면 최종 사용자 차단이나 정상 알림을 만들지 않는다. 재구성 없이 같은 입력을 반복하는 지속 장애는 R-091에서 감지해 사용자 조치 요청과 구분하여 R-053 기준으로 한 번 진단 통지한다. 실제 자동 복구 불가 또는 사용자 결정·승인·권한·PR 검토/Merge의 기존 알림도 유지한다.
- G-285형 정상 Worker 변경 → Manager 범위/frontmatter 검사 → commit/push → DB·checkpoint 반영 → 원격 소유권 재검사에서 혼합 시점의 `remote_oid`로 PROJECT_BLOCKED를 만들지 않는다. 실제 다른 저장소/작업·PR과 타인 OID 덮어쓰기는 계속 안전하게 거부한다.
- 동일한 과거 `publication_remote_oid`·PR head·checkpoint와 최신 원격 OID의 고정 불일치는 반복 RETRY가 아니라 이력 관계에 따른 재구성·통합 또는 근거 있는 대상별 보류로 귀결된다. 정상 사용자 push→원격 추가 commit→rebase/필요 검증→안전한 게시에서 로컬·원격 양쪽 작업이 보존되고 불필요한 최종/프로젝트 차단이 없다. 실제 push·fetch·PR 관측 중 경쟁만 제한 재시도하며 새 원격 입력 없이 동일 관측을 되풀이하지 않는다.
- 일반 fast-forward·재작성 lease 게시, 실패한 lease 뒤 현재 원격 재조회, push 성공/DB 확정 중단, 비선형 원격 이력·손상 기록, 다른 origin/PR·미커밋 파일·심볼릭 ref를 구분한다. 다른 작업을 덮어쓰는 Git 쓰기 0회, 이미 확인된 push 반복 0회, 필요한 후보 검증 보존, 독립 작업 진행을 실제 Git 효과와 저장 상태로 확인한다.
- 계획·Worker·유지보수 시작/완료·PR 충돌 수정 시작·자동 재개·단순 대기에서 Telegram 발송 0건이며, 오래된 미전송 진행·무음·대기·해소된 차단 알림은 취소하고 기존 감사는 보존한다.

- 최신 base에만 Requirement·다른 ExecPlan의 추가·수정·삭제·rename/archive가 있고 작업 branch의 checkpoint 시작 HEAD가 없거나 오래돼도 정상 rebase를 시작할 수 있다. 완료 뒤 target 기준으로 실제 남은 금지 문서 변경·잘못된 선언을 거부하며 원격/PR·현재 operation 불일치를 우회하지 않는다. 차단 복구 중 무관한 공유 Git 변경은 작업물 보존을 막지 않고 실제 선택 후보 변경은 재관측한다.

- 실행 종료 관측 뒤 예외·최종 결과 저장 누락·재시작 정리가 발생해도 확인된 writer 종료 때문에 Requirement 교정이 계속 보류되지 않는다. 종료 근거 없는 호출·실행 중인 writer는 보존하고, 실패·중단 결과나 NULL 종료 코드를 성공·임의 코드로 바꾸지 않는다.
- Codex 신규·재개에서 10분 무출력과 새 이벤트·부분 출력의 타이머 갱신, heartbeat 제외, 병렬 명령 실행 대기와 턴 완료 후 수집 대기를 검증한다. Reviewer 저장량 제한이 수신 관측을 끊지 않으며, 종료 미확인 상태에서는 다음 교정으로 넘어가지 않는다.

- 코드의 모든 차단·중단 생성 경로와 재개 경로, 후보가 있는데 후속 처리를 생략하는 비오류 반환·대기·cache 경로를 추적 가능한 목록으로 정리한다. 공통 helper의 호출자·상위 소비자와 조건·원인 소유자/자원·영향 범위·보호 규칙·자동 복구·재평가/사용자 조치·관측 근거 및 유지/수정 이유를 관련 ExecPlan에서 확인할 수 있다.
- 오탐과 과도한 차단으로 판정한 경로에는 재현 가능한 코드·테스트 근거, 수정 동작과 실제 위반을 유지하는 회귀 검증이 있다. 문제가 없는 경로도 검토 근거를 남긴다.
- 자동 복구 가능한 비차단 실패와 실행별 재시도 예산 소진은 R-091대로 작업을 보존하는 재시도 대기 뒤 같은 실행에서 재개한다. 같은 입력에서 진전 없는 무제한 호출·Git 쓰기·중복 알림은 발생하지 않는다.
- 서로 다른 두 작업에서 동일한 범위 밖 공통 verify 결함을 재현하면 독립 작업의 후보·실패 근거는 보존되고, 현재 활성 명세·공통 완료 조건에 근거한 하나의 자동 교정 목표로 계획된다. 기존 동등 계획이 있으면 재사용하며 Worker의 범위 밖 수정, 중복 계획·사용자 질문, 관계없는 작업의 차단을 만들지 않는다. 원인이 불확실하거나 서로 다르면 하나의 목표로 임의 병합하지 않는다.
- 현재 명세가 실행 경계·검증 정책을 이미 결정한 공통 결함은 별도 사용자 정책 판단 없이 기존 일반 planning 조건에서 교정된다. 공통 교정이 실제 검증·반영된 뒤에만 해당 차단을 근거별 재평가하고, 원래 질문·작업물·session·실패 기록과 별도 승인·안전 차단을 보존한 채 필요한 후보 검증·Review를 거쳐 재개한다. 단순 Requirement 수정이나 계획 게시만으로 질문 승인·검증 성공·차단 해제를 합성하지 않는다.
- 계획별 실패가 독립 READY와 다른 프로젝트를 막지 않으며, 실제 공유 자원·소유권·범위 문제는 적절한 프로젝트 안전 차단을 유지한다.
- 한 계획의 잘못된 선언·의존성, 전용 작업 공간 문제와 승인 대기에서 해당 계획과 영향받는 의존 계획은 중단되고 독립성이 검증된 계획의 선택·planning과 PR 관측은 계속된다. 식별·공유 안전이 실제로 불확실한 경우에는 관련 작업을 실행하지 않고 차단 근거를 확인할 수 있다.
- Requirement·ExecPlan의 삭제를 rename·archive·원격 조회 실패·로컬에만 있는 삭제와 구분하고, 일괄 삭제·등록 전 삭제·실행 row 없는 예약 및 보류 이력도 같은 복구에 연결한다. 번호 공백·확인된 정상 삭제만으로 프로젝트를 차단하거나 ID를 추측·재사용하지 않는다.
- Requirement 또는 일부 Acceptance Criteria 삭제 시 연결 ExecPlan의 목표 전체 철회와 일부 근거·조건만 제거할 경우를 구분해 삭제·개정안을 자동 게시하고 현재 DB 관계에 반영한다. 부분 철회의 체크리스트·관련 파일·검증·참조가 갱신되고 남은 PRODUCT·Requirement 목표·공유 구현·다른 source·필수 검증은 보존한다.
- 삭제된 선행 작업의 직접·간접 dependency와 본문·구현·검증 참조는 함께 갱신된다. 필요한 목표는 유효한 대체 dependency로 연결하며, 검증된 실제 Merge 이력은 보존한다. 삭제만으로 MERGED나 선행 충족을 합성하지 않는다.
- 확인된 작업 삭제는 실행 이력 유무와 무관하게 현재 수명에 반영하고, 취소된 작업의 신규 실행·재개·게시와 오래된 판단·요청을 중단한다. 최종 원격 변경과 안전한 취소가 확인되면 활성 실행 row를 제거하고 관련 선택·대기·관계 변경 및 취소 감사를 같은 transaction에 반영한다. 마지막 선언·작업물·소유권·session·실패·PR·완료·취소·ID 예약·복구 감사와 수동 소유 권한은 보존하며, 안전 조건 미확인 때는 row·소유권을 성급하게 지우지 않는다.
- 유지하는 관리 브랜치에 문서 삭제·개정을 반영하고 삭제를 반영한 취소·완료 작업의 소유 로컬·원격 브랜치·worktree를 안전 검증과 보존 후 자동 정리한다. 원격 기대 OID 경쟁·재생성·PR head 보존·권한 또는 보호 정책 실패는 해당 정리 pending으로 남고 독립 실행을 막지 않는다.
- 완료 Requirement와 MERGED 작업이 함께 삭제돼도 역사 source 조회 실패나 삭제 감사의 신규 ID 오판으로 전체 planning·catalog가 실패하지 않는다. 실제 identity 재사용은 거부하며 확인된 취소·완료 identity를 자동 READY로 재등록하지 않는다.
- `missing-plan`·`missing-plan-reference`·`deleted-goal`과 관련 source 오류가 일반 Planner의 자동 삭제·참조 복구 입력으로 제공된다. Planner의 근거 있는 판단과 Manager의 검증으로 해소하고, 의미·관계·소유권을 확정하지 못한 범위만 보류한다.
- Planner의 복구 교정 뒤 Manager가 최신 원격·실제 PR·소유권·유효한 source와 dependency·목표 보존·게시 및 catalog 적용을 재검증해 해소된 보류만 해제한다. 근거 없는 참조 제거·미게시 결과·원격 또는 소유권 경쟁·재시작은 수행하지 않은 해제를 만들지 않고 작업물과 독립 보류를 보존한다.
- planning 오류가 남아도 안전하게 실행 자리를 비운 뒤 기존의 유효한 독립 READY·리팩터링 계획을 R-091의 실행·관리 한도와 배정 순서 안에서 진행하고 기존 PR 관측·충돌 복구를 계속한다. 프로젝트 전체의 직렬 실행을 요구하지 않으며 같은 후보의 단계 순서와 공유 자원 보호는 유지한다. 같은 입력의 신규 Planner 반복과 프로젝트 완료 선언은 보류되며, 오류·session·미게시 결과는 다른 계획 진행·중단·재시작 뒤에도 보존된다.
- Agent의 접근 권한은 sandbox로 강제되고, 신규·재개·fallback 호출의 정책 적용 실패는 해당 호출에서 처리된다. Git 상태 차이로 접근 권한 위반을 추정하는 결과·저장 선검증·복구·checkpoint 경로가 제거된다.
- 격리 ledger 부재·실패한 호출·성공한 재시도·Reviewer에서 Worker로의 단계 전환 뒤에도 Git snapshot 비교가 재활성화되지 않는다. 역할별 문서·최종 diff·결과 검증과 실제 후보 변경에 따른 성공 무효화는 유지된다.
- 기존 Git 오탐 차단·planning 오류·지속 실행 실패는 입력 지문 변경이나 수동 DB 수정 없이 자동 재평가·해제되고 저장된 작업을 재개한다. pending 확인 요청은 실제 해소 상태에 맞춰 종료되며 실제 sandbox 오류·독립 차단·승인은 유지된다.
- 복구와 재시작 전후 보존 가능한 작업물·session·실패 피드백이 보존된다. 충돌 복구가 불가능한 파일만 확인된 원격 원본 상태로 복원해 재작업하고, 다른 파일의 내용·staging과 기존 commit은 유지한다. 변경된 후보는 기존 최종 검증·Review·게시 조건을 다시 만족해야 한다.
- R-020·R-023의 정상 외부 base 전진·runtime 재사용·파생 HEAD 변화는 결과·재개·계획/프로젝트 복구·정상 및 진단 checkpoint에서 Agent 위반을 만들지 않는다. 현재 runtime·Git 작업 조건과 실제 sandbox 오류는 각각 확인하며 선행 함수별 성공만으로 전체 경로 충족을 선언하지 않는다.
- 원격 원본 전진의 rebase와 원격 작업 브랜치의 추가 작업 통합·기존 게시 이력 재작성에 대한 조건부 force push가 구분된다. 게시 경쟁은 재관측·통합·재검증으로 복구하고 원격의 새 작업을 덮어쓰지 않는다.
- OID·ref의 정상 처리 표는 planning·유지보수·실행 게시와 수락된 수동 작업의 자동 실행에서 최초 진입·단계 전환·PR 유무·차단 재평가·중단 후 재개에 동일하게 적용된다. 기존 역할·수락·사용자 승인 권한을 확대하지 않고, 단순 OID 불일치·과거 receipt 부재·같은 PR의 head 전진이 `publication_ownership_uncertain`이나 사용자 조치 대기로 확대되지 않는다.
- OID·ref 보류는 실제 대상 불일치·필수 사용자 판단·접근 거부·미완료 자원 조건에 연결되고 영향받는 동작에 한정된다. 작업 목표와 원본이 확인된 충돌 복구 불가 파일은 파일별 원본 복원·재작업으로 처리하며, 실제 대상 변경·사용자 삭제 의도·진단 ref 충돌·원격 삭제 lease를 우회하지 않는다.
- Manager가 생성·게시한 작업 branch가 실제 삭제됐고 PR이 Merge되지 않았으면 해당 작업만 명시적 재시작 대기로 중단한다. 새 요청이 있으면 최신 원본에서 새 실행을 준비하며 일반 `run`·프로세스 재시작·pause 해제·같은 이름의 ref 생성으로 옛 작업을 자동 재개하지 않는다. PR Merge 뒤 삭제와 조회 실패는 구분한다.
- 차단 원인 갱신·해제·재차단과 checkpoint 요청/게시/SQLite 확정 사이의 중단에서 오래된 요청은 취소 또는 현재 원인으로 재검증된다. stale identity만으로 새 최종 차단·Worker 호출·교정 횟수가 생기지 않고, 실제 소유권 경쟁과 다른 차단·승인은 보존된다.
- rebase 시작·재시작에서 현재 소유권·target·원격·작업물 보존은 확인하되 오래된 frontmatter나 과거 definition snapshot 부재만으로 최종 선언 불일치 차단을 만들지 않는다. Worker 종료 시 해당 Worker 변경을 검사하고 Git 완료·선언 복원 후 전체 결과를 검증한다. 완료 후 남은 금지 변경·잘못된 선언은 채택하지 않는다.
- rebase 중 R-072가 구분한 순수 진행·검증 기록 변경은 구현 입력 변경 차단을 만들지 않는다. 실제 목표·범위·source·승인 변경과 분류 불확실성은 작업을 보존해 필요한 재확인·재검증을 거친다.
- 로컬 base 동기화와 Python 캐시는 각각 R-056·R-059의 구체적인 정책을 따르며 중복된 상충 정책을 만들지 않는다.
- 조사는 코드와 테스트를 기준으로 수행하며 운영 SQLite 사건의 개별 수정·삭제 또는 그 기록을 근거로 한 운영 발생 빈도 주장을 포함하지 않는다.

### Git 회귀 기준

관리 rebase의 시작·재개는 현재 대상·소유권·보존 조건으로 판단하고, 최종 선언 일치·전체 diff 검사는 Git 완료 후에 수행한다. 시작 전 오래된 frontmatter·definition snapshot 부재, commit 재생 중 다른 작업 문서·일부 stage·문서 이동/archive·autostash 복원은 최종 범위 위반으로 차단하지 않는다. 동일 상태에서 잘못된 소유권·대상·원격·경로·index flags 및 충돌 해결 Agent가 새로 만든 금지 변경은 계속 거부하고, 완료 후 남은 금지 변경도 채택하지 않는다. 완료 후 보조 Git 표식만 남은 깨끗한 worktree는 소유권·PR head·commit 관계 검증을 거쳐 정리할 수 있다.

아래 시나리오는 성공뿐 아니라 관측 경쟁·중단·재시작에서도 작업물·session·독립 원인 보존을 확인한다. 판단·상태 조합은 관측 경계를 mock으로 제공하고 실제 판단·SQLite를 실행한다. shared ref·worktree·rebase·index·lease의 실제 효과만 필요한 통합 회귀로 확인한다.

| ID | 시나리오와 완료 조건 |
|---|---|
| T01 | Planner 중 다른 작업의 commit·fetch·worktree 생성·정리와 공유 ref 변화가 있어도 Agent 위반으로 차단하지 않는다. |
| T02 | Worker의 실패·재시도·session 재개나 저장 ledger 부재 뒤에도 외부 fetch·무관한 Git 변화의 snapshot 범위 비교를 재활성화하지 않는다. |
| T03 | verify 중 외부 fetch에서 실제 검증 입력이 불변이면 정상 완료한다. |
| T04 | Reviewer 중 외부 fetch에서 후보가 불변이면 정상 완료한다. Reviewer에서 Worker로 전환하거나 중단된 Manager 작업을 재개할 때 낡은 Reviewer snapshot으로 현재 파일 변경을 위반 처리하지 않는다. |
| T05 | remote-tracking ref·FETCH_HEAD 갱신만으로 프로젝트를 차단하지 않는다. |
| T06 | pull/rebase로 실제 후보·검증 입력이 바뀌면 이전 성공을 무효화하고 필요한 단계부터 수행한다. |
| T07 | dirty 원본은 FF-only만 시도하며 실패하면 staged·unstaged·untracked를 보존한다. |
| T08 | clean diverged 원본은 로컬 commit을 보존해 안전한 rebase를 시도한다. |
| T09 | Manager 소유 rebase 충돌은 안전한 abort 뒤 원래 HEAD·index·tracked 파일 보존을 검증한다. |
| T10 | BLOCKED 인계 뒤 사용자 파일 수정·staging을 수용하고 과거 snapshot으로 복원하지 않는다. |
| T11 | BLOCKED 인계 뒤 사용자 commit의 새 HEAD를 입력으로 수용한다. |
| T12 | 원격 작업 tip이 조상이 아닌 정상 원격 원본 기준 로컬 rebase를 수용하고 기존 게시 이력의 재작성은 조건부 force push로 연결한다. |
| T13 | 로컬·원격 양쪽의 새 작업을 보존해 통합하거나 실제 충돌 범위만 보류한다. |
| T14 | 이번 push의 예상 원격 OID 이후 사용자 push가 있으면 조건부 push가 거부되고 다시 관측·통합·검증한다. Agent 위반이나 영구 차단을 만들지 않는다. |
| T15 | Planner 단계 사이 원격 ExecPlan·명세 수정은 R-082대로 반영한다. |
| T16 | 진행 중 단계의 runtime 파일은 유지하고, R-023대로 단계 경계에서 원격 전진을 확인해 후속 배정을 멈춘다. |
| T17 | 진행 중 단계 반환·상태 보존 후 주기 실행을 기다리지 않고 최신 원격의 안전한 새 runtime으로 재시작한다. |
| T18 | index-free ignored-only 변화는 scope·dirty 오탐 차단을 만들지 않는다. |
| T19 | ignored와 들어오는 tracked 경로 충돌은 파일을 보존하고 해당 Git 쓰기만 보류한다. |
| T20 | Merge 뒤 cleanup 실패는 완료 결과를 보존하고 cleanup만 재시도한다. |
| T21 | 원격 확인된 과거 문서 게시 뒤 사용자 수정은 과거 완료와 최신 재평가로 분리한다. |
| T22 | sandbox가 source·다른 worktree·shared Git metadata 쓰기를 거부한다. Manager는 실제 Git 작업의 대상·동일 자원 writer·origin 조건을 확인하며 실패를 Git snapshot 기반 Agent 위반으로 바꾸지 않는다. |
| T23 | 원격 삭제·재작성·재생성은 미게시 로컬 작업을 보존하고 무검증 덮어쓰기를 막는다. |
| T24 | 외부 변경으로 diff가 없으면 목표 충족·구현 부족·실제 PR Merge를 구분하고 NO_CHANGE만으로 차단하지 않는다. |
| T25 | 기존 Git 오탐의 계획·프로젝트·planning·지속 실패 차단은 같은 입력의 시작·재시작에서 자동 해소된다. retry 소진과 낡은 snapshot이 재개를 막지 않고 작업물·session·감사·독립 원인을 보존한다. |
| T26 | 차단 해제·대기 확인 요청 종료·Manager Git 복구 확정 사이의 중단·재실행은 멱등하며, 실제 충돌·접근 실패·sandbox 오류·별도 승인이나 Review 실패가 함께 있으면 해당 원인만 계속 처리한다. |
| T27 | 로컬 미게시 commit 또는 원격 추가 commit 때문에 작업 branch OID가 달라도 각각 검증 후 게시 또는 원격 반영으로 처리한다. 과거 checkpoint·receipt 부재가 수용을 막지 않고 정상 입력을 `external_remote_oid`로 최종 차단하지 않는다. |
| T28 | 같은 PR의 repository·URL·head/base branch가 유지된 head 전진은 새 원격 작업으로 처리한다. 실제 다른 PR·branch·origin은 해당 쓰기를 보류하고 이전 후보의 승인으로 새 HEAD를 게시하지 않는다. |
| T29 | 일반 게시·PR 충돌 게시·중간 rebase checkpoint에서 lease 경쟁 또는 부재 ref의 동시 생성이 발생하면 재관측·통합·재검증으로 돌아간다. 새 lease만 끼워 넣은 push·무한 재시도·프로젝트 전체 차단은 없다. |
| T30 | push 성공 후 SQLite 확정 중단과 push 뒤 원격 후속 commit 전진을 구분해 자신의 완료를 확인하고 후속 작업을 보존한다. 반복 push·완료 합성·과거 OID 고정 때문에 정상 재개가 막히지 않는다. |
| T31 | 기존 `publication_ownership_uncertain`·`remote_oid_uncertain`·PR 선검증 차단 중 정상 OID 변화·낡은 기록만 원인인 건은 같은 입력에서 재평가·해제하고 pending 요청을 종료한다. 같은 코드의 실제 대상·권한·보존 문제와 별도 원인은 유지한다. |
| T32 | 확인 가능한 동일 작업의 원격 원본·작업 branch 이력 재작성은 현재 명세·목표와 양쪽 작업을 확인해 보존·통합·재검증한다. 관계 불명·삭제 의도 불명·원격 삭제 후 재생성은 자동 덮어쓰기하지 않고 해당 게시만 보류한다. |
| T33 | immutable 진단 ref의 다른 OID와 cleanup 삭제 직전 원격 변화는 해당 갱신·삭제만 보류한다. 최신 OID로 삭제 lease를 교체하거나 자료를 버리지 않고 완료 결과·독립 작업은 계속된다. |
| T34 | 관련 OID 조회 실패·branch/PR 관측 시점 차이·미완료 작업의 원형 부재를 실제 대상 변경과 구분한다. 조회 실패를 ref 부재로 확정하거나 사용자 operation을 abort하지 않고 제한 재관측·자원 보류로 처리한다. |
| T35 | 현재 작업 목표·소유 대상·복구 원본이 확인되면 충돌 복구가 불가능한 파일만 원본 상태로 복원해 재작업한다. 다른 파일·이미 해소된 충돌·staged·unstaged·untracked 상태와 기존 commit·HEAD를 유지한다. 복구 기준의 파일 삭제·이동을 반영하고, 중단 후 완료된 파일을 다시 되돌리거나 새 교정 결과를 덮지 않는다. |
| T36 | Reviewer 진입 전 OID가 달라도 실제 문서·코드·검증 입력으로 verify 재사용·필요한 verify·선행 Review를 선택한다. 진단 ref의 다른 OID는 해당 자료 게시·삭제만 보류하며 verify·Review를 막지 않는다. Review 중 후보가 바뀌면 새 후보의 필요한 verify·Review를 진행하고 실제 구현 부족인 경우에만 Worker 교정으로 돌아간다. |
| T37 | Manager가 생성·게시한 원격 작업 branch의 실제 삭제를 PR 미생성·미Merge 상태에서 확인하면 해당 작업만 중단하고 작업물·session·PR·감사를 보존한다. 일반 재실행·프로세스 재시작·pause 해제·ref 재생성은 재개하지 않으며, 명시적 재시작 요청 뒤 최신 원본에서 새 실행을 한 번 준비한다. PR Merge 후 삭제·조회 실패와 구분하고 새 실행에 이전 성공·게시 intent를 재사용하지 않는다. |
| T38 | 소유권이 확정된 작업의 실제 branch·worktree와 작업별 근거는 유효하지만 저장된 branch가 비거나 planning·다른 작업의 경로가 섞이면, 현재 자원 연결을 검증해 실행 자원 정보를 자동 복구하고 기존 프로젝트 차단을 해제·축소한다. 문서 변경·수동 DB 수정 없이 저장 단계에서 필요한 처리를 이어가고 파일·index·commit·session·실패·유효한 성공 근거를 보존하며 미수행 단계의 성공을 만들지 않는다. |
| T39 | 같은 상태 혼선에서 근거 부족·복수 후보·현재 자원 불일치·종료 불명 writer 또는 복구 확정 중 상태 변경이 있으면 낡은 복구를 적용하지 않는다. 이름·경로만으로 채택하거나 reset·재생성하지 않고 작업물·경쟁 변경·독립 차단을 보존한다. 작업 범위로 확인된 문제는 독립 작업을 막지 않고 실제 공유 안전이 미확정인 경우만 프로젝트 차단을 유지한다. 복구 확정 전후 중단·재시작에도 중복 실행·진전 없는 동일 복구 반복을 만들지 않는다. |

### 진행 장벽 회귀 기준

아래 기준은 정상 경로와 중단·재시작 경로에 함께 적용한다. 정책 조합은 Git·원격 관측을 mock으로 제공하고 실제 판단·SQLite 상태를 확인하며, 자원 효과가 필요한 최소 Git 회귀만 추가한다.

| ID | 시나리오와 완료 조건 |
|---|---|
| B01 | 별도 작업의 미완료 rebase가 있어도 해당 planning 게시·해제와의 자원 독립성이 검증되면 완료하고 독립 작업을 재개한다. 원인 작업의 active intent·파일·index·checkpoint·차단은 보존한다. 최초 게시와 `recover_publication` 재진입에 같은 기준을 적용한다. |
| B02 | 같은 branch/worktree·게시 ref·공유 설정의 실제 충돌, 종료 불명 writer·손상/불충분한 근거에는 해당 쓰기·해제를 거부한다. 무관한 기록의 격리가 실제 보호 조건의 우회가 되지 않고 원인과 영향 범위를 확인할 수 있다. |
| B03 | 원격 push 뒤 DB 미확정, DB 적용 뒤 해제 전, worktree 정리 전후의 중단을 구분한다. 확인된 효과는 재실행하지 않고 누락된 확정만 수행한다. 분리 보존 가능한 cleanup 대기는 R-082대로 재시도하고, 실제 원격 결과·DB identity·writer 종료가 미확인인 작업은 완료로 합성하지 않는다. |
| B04 | planning 해제는 원인 작업의 복구를, 복구는 planning 자리 반환을 기다리는 입력에서도 검증된 소유 복구가 실행 가능한 경계를 갖는다. 실제 공유 안전 때문에 진행 불가이면 그 의존 관계와 재평가 조건이 남으며 동일 경로만 무진전 반복하지 않는다. |
| B05 | 문서·기존 지문이 그대로여도 관련 writer 종료·자원 반환·미확정 효과의 완료 확인·원인 교정 runtime 반영 후 자동 재평가한다. 동일 관측의 중복 해제는 하지 않지만 앞서 허가된 미완료 복구는 이어간다. 무관한 변경은 성공·재호출·정체 이력 초기화의 근거가 아니다. |
| B06 | 후보가 있는 조기 반환·WAITING·skip·planning_error와 상세 없는 상위 결과에서도 원인 소유자·영향 대상·자원/intent·진전·다음 조건을 조회할 수 있다. 기존 구조화된 근거 부재는 미확인이고, 진단 생성·조회가 Git 쓰기·복구·추가 Agent 호출을 만들지 않는다. |
| B07 | 같은 원인·입력의 비오류 대기/외부 실행 반복도 지속 정체로 연결된다. 독립 작업의 성공·새 run ID·같은 관측의 재저장은 이력을 지우지 않고, 실제 원인 해소 뒤에만 해당 진단을 해소한다. 정상 조건 대기와 R-053의 일회 진단을 구분한다. |
| B08 | 공통 안전 helper를 다른 완료·복구 단계에서 재사용하거나 DB 경계를 옮겨도, 무관한 pending 작업이 있는 진행 허용과 실제 공유 충돌의 거부를 모두 검증한다. 해당 안전 판단을 무조건 성공하는 mock으로 대체하지 않고 관측만 제공해 실제 판단과 소비자의 후속 단계 도달·독립 작업 진행을 확인한다. |

### 예약 workspace 복구 회귀 기준

| ID | 시나리오와 완료 조건 |
|---|---|
| W01 | `workspace_owned=2`이고 실제 HEAD와 생성 journal HEAD는 같지만 `active_sha`가 다른 경우, 작업·repository·경로·branch·예약·checkpoint와 필요한 인수·변경 근거가 모두 검증되면 기존 예약을 확정해 재개한다. 실행 기준을 실제 HEAD로 덮어쓰거나 최신 base 포함을 소유권 확정 조건으로 요구하지 않는다. |
| W02 | 생성 직후 중단, 생성 후 실행 기준 갱신, 예약 확정의 DB 반영 실패·재시작에서도 같은 자원을 중복 생성하거나 reset하지 않고 한 번 확정한다. HEAD·commit·staged·unstaged·untracked 작업물과 session·실패 감사를 보존하며 이후 필요한 rebase·검증은 정상 경로로 이어진다. |
| W03 | 다른 소유자·repository·경로·branch, 생성·변경 이력으로 설명되지 않는 journal/HEAD 불일치, 증거 부족 또는 외부 자원 변경은 이름·원격 HEAD 일치만으로 승인하지 않는다. 확인 중 자원·checkpoint가 바뀌거나 writer 종료가 불명확하면 낡은 검증으로 확정·해제하지 않는다. 사용자 Git operation을 임의 abort하지 않는다. |
| W04 | 한 작업의 예약 소유권 문제만 남고 독립성이 검증되면 해당 작업·의존 작업·충돌 자원만 보류하고 다른 적격 작업은 R-091의 한도·배정 순서로 진행한다. 실제 공유 Git 안전이 불확실하면 프로젝트 차단을 유지한다. 보류 기록에서 원인 작업과 호출 대기 중인 영향 작업을 구별할 수 있다. |
| W05 | 기존 프로젝트 차단의 원인이 해소되거나 작업 범위로 한정됨을 확인하면 새 문서 변경·수동 DB 수정 없이 해당 프로젝트 차단을 해제·축소한다. 소유권이 확정된 작업의 시작 전·진행 중 Manager rebase가 남아 있어도 현재 소유권과 원인 해소가 확인되면 rebase를 완료 처리하지 않고 그 checkpoint·원래 HEAD·target·파일·index·저장 단계를 보존해 재개한다. writer 종료 불명·현재 rebase 대상 불일치와 관측 중 checkpoint·차단 원인·독립 계획 차단·복구 기록 변경에는 해제를 적용하지 않는다. 예약 확정·차단 해제 사이의 중단·재실행에서도 중복 실행과 해소된 원인의 재차단·반복 통지를 만들지 않고 미해소 작업 차단과 별개 승인·Review 실패를 유지한다. |
| W06 | 소유권 복구와 차단 해제는 수행하지 않은 Worker·verify·Review·rebase·게시 성공을 만들지 않는다. 필요한 단계는 저장된 상태와 실제 후보·유효한 성공 근거로 판단하고 과거 진단·session·retry 감사를 보존한다. |

### Targeted test 회귀 기준

- 같은 테스트의 연속 다섯 실패는 다섯 번째 실제 실패를 기록한 Worker 종료·재개 경계에서 차단하고, 서로 다른 테스트의 다섯 실패나 동일 실행 결과의 다섯 재관측은 차단하지 않는다.
- 연속 다섯 실패 이후 같은 테스트의 성공을 관측하면 실패 횟수는 0이고 도달 표식은 해제되어야 한다.
- 실패·성공·실패·실패와 실패·skip·실패·실패는 연속 5회로 차단하지 않는다. 후보 코드·세션을 바꾸거나 Manager를 재시작해도 미해결 동일 테스트의 이력은 이어진다.
- 한 Worker 세션 안의 다섯 실행과 여러 Worker turn에 걸친 다섯 실행을 같은 기준으로 처리한다. 실제 결과는 실행별로 보존하며 불완전한 기록·수집 오류와 새 근거 없는 완료 보고는 테스트 실패로 누적하지 않는다.
- 문서 보고 오류의 기존 한도, Manager verify·Review gate와 독립 안전·사용자 결정 차단을 유지한다.

## Product Impact

- 차단을 실제 사용자 조치와 안전 문제에 맞게 한정하고 자동 복구 가능한 작업을 보존해 이어간다.
- 차단·복구 정책을 모든 실행 경로에서 일관되게 적용한다.
- 계획·작업 삭제가 관련 문서·현재 DB 관계·소유 로컬 및 원격 작업 브랜치에 자동 반영되고, 작업물·완료·취소 감사는 보존된다.

## Non-Goals

- 이번 조사를 위해 현재 운영 SQLite의 개별 차단 기록을 직접 조사·변경·삭제하거나 운영 데이터 migration을 수행하지 않는다. Manager의 정상 실행에서 검증된 삭제를 현재 DB 상태에 자동 반영하는 요구는 포함한다.
- 안전·승인·최종 검증을 생략하거나 모든 실패에 무제한 재시도를 적용하지 않는다.
- 새로운 복구 서비스·Agent 역할이나 범위 밖의 저장소 전체 리팩터링을 추가하지 않는다.
