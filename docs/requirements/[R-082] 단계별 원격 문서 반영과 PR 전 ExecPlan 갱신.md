# [R-082] 단계별 원격 문서 반영과 PR 전 ExecPlan 갱신

## Summary

명세 변경의 작업 구성·개정은 프로젝트 일반 Planner에 모으고 원격 게시·catalog·DB 반영을 현재 작업 재개보다 먼저 확정한다. ExecPlan·코드 변경만으로 Planner를 호출하지 않으며 관련 작업은 PR 등록 전까지 같은 ID·작업물·기록을 보존해 갱신한다. Worker는 선택 작업 본문과 허용 설계 문서만 수정하고, 최신 조건·진행 기록·문서 충돌을 구분해 필요한 구현·검증·Review를 이어간다. 마지막 연결 작업 Merge 뒤에는 해당 Requirement를 바로 재확인한다. 병렬 작업의 신규·후속 배정을 중단하고 실행 중 호출이 반환한 뒤 planning을 반영한다.

## Context

프로젝트 전체 planning과 개별 작업 실행은 별도의 반영 기준을 사용한다. 같은 명세 변경의 관련성과 개정을 작업마다 Planner에게 판단시키면 프로젝트 검토와 중복되고, 개정·DB 반영이 끝나기 전에 이전 조건으로 다음 실행 단계에 진입할 수 있다.

명세 변경의 작업 구성·개정 판단을 프로젝트 일반 Planner로 모으고, 안전한 단계 경계에서 게시·DB 반영을 현재 작업 재개보다 먼저 끝내야 한다. 개별 작업은 마지막으로 반영한 ExecPlan과 최신 작업 문서의 구현 조건을 비교해 필요한 실행 대응을 선택한다. 자체 진행 기록을 새 구현 조건으로 오인하지 않으면서 미확인 조건을 소비하지 않는 기준 갱신도 필요하다. 같은 ID·작업물·기록 보존, 발견 단계별 대응과 정상 사용자 rebase 수용은 유지한다.

ExecPlan·코드·테스트·설정 변경마다 예정 작업이나 구현 적합성을 Planner에게 확인시키는 호출도 최신 조건을 읽는 Worker와 중복된다. Planner는 아래 계획 작성·사용자 판단·Requirement 완료 확인에 집중하고, 개별 작업의 구현 판단은 Worker가 맡는다. 관련 ExecPlan이 모두 Merge된 Requirement는 다음 안전한 경계에서 바로 재확인해 미충족 조건을 놓치지 않는다.

원격 확인과 문서 관련성 판단은 후보 검증과 구분한다. ref 갱신만으로 차단하지 않고 실제 문서·후보·검증 입력 변화에 해당하는 단계만 다시 수행해야 한다.

현재 구현에는 진행 중 rebase 충돌과 Worker 구현 입력 변경이 함께 발견되면 기존 작업을 보존하고 최종 차단하는 경로가 남아 있다. 아래 충돌 복구 정책은 이 경로를 최신 base의 계획·작업 문서 자동 반영과 필요한 Worker 교정·재검증으로 연결하려는 변경 요구이며, 이미 구현된 동작이나 운영 문제의 해소를 뜻하지 않는다.

진행 중 작업은 최신 원격 문서에 맞춰 갱신하되, 문서 변경만으로 구현을 반복하지 않아야 한다. 이 Requirement는 [R-049](archive/%5BR-049%5D%20Input-Specific%20Planner%20Roles.md)의 미착수 READY 갱신 제한·ExecPlan 변경 재계획·코드 전용 점검과 [R-051](archive/%5BR-051%5D%20Remote%20Change%20Rebase%20and%20Managed%20Work%20Resumption.md)의 Worker·Reviewer 문서 재확인 범위를 아래 정책으로 변경한다. [R-072](%5BR-072%5D%20%EC%9E%85%EB%A0%A5%20%EB%8F%99%EC%9D%BC%EC%84%B1%EC%9D%B4%20%EC%A6%9D%EB%AA%85%EB%90%9C%20%EA%B5%AC%ED%98%84%20%ED%9B%84%EB%B3%B4%20%EC%84%B1%EA%B3%B5%20%EA%B2%B0%EA%B3%BC%20%EC%9E%AC%EC%82%AC%EC%9A%A9.md)의 입력 증명·성공 근거 재사용은 유지하되, 관련 문서 변경에 따른 단계 선택은 이 Requirement를 따른다.

## Requirement

명세 변경의 선행 planning은 R-091의 프로젝트 배정 중단을 사용한다. 새 작업 편입과 Worker·verify·Reviewer·게시의 후속 호출을 멈추고 실행 중 호출이 안전하게 반환한 뒤 Planner·게시·catalog·DB 반영을 수행한다. verify·실행 자리 대기는 새 호출 없이 저장된 단계로 반환하며 작업 전체 완료까지 기다리지 않는다. 다른 프로젝트는 진행하고, 반영 후 보존된 작업을 다시 배정한다.

### Planner 실행 조건

| 조건 | 호출 목적 |
|---|---|
| 최초 계획 수립 등 비교 가능한 전체 planning 성공 기준 부재 | 현재 명세·구현·catalog를 대조해 미충족 작업을 계획한다. |
| 최신 원격 PRODUCT·활성 Requirement·ARCHITECTURE의 추가·변경·삭제 | 변경된 목표·조건과 영향받는 작업을 확인해 필요한 새 작업·개정을 반영한다. |
| draft 질문에 사용자 답변이 들어와 의미 판단 필요 | R-061에 따라 답변·남은 질문을 판단한다. 일반 ExecPlan 변경을 이 조건으로 취급하지 않는다. |
| 명시적 수동 제출에서 새 ExecPlan 생성 필요 | R-077에 따라 제출 범위와 기존 작업의 중복을 확인해 추적 작업을 생성한다. |
| 자동 유지보수 주기 도래 또는 명시적 CLI 요청 | R-074·R-076의 기준값과 요청·안전 gate를 적용해 유지보수 평가·계획을 수행한다. |
| 한 Requirement에 연결된 모든 ExecPlan의 실제 Merge 확인, 최신 입력의 유효한 완료 판단 부재 | 아래 Requirement 완료 재확인을 바로 수행한다. |
| 프로젝트 완료 후보의 최신 입력에 유효한 최종 전문 확인 부재 | 전체 활성 명세와 구현·검증을 대조해 누락된 작업·사용자 판단을 확인한다. |

ExecPlan의 추가·본문·선언 변경, 코드·테스트·설정 변경, 저장소 SHA 전진과 문서 수정본 승인 자체는 독립적인 Planner 실행 조건이 아니다. 미착수 READY가 있든 없든 코드 변경만을 이유로 점검 Planner나 일반 Planner를 호출하지 않으며, 점검 결과의 일반 Planner 인계도 제거한다. Manager가 catalog의 ID·source·dependency·사용자 결정·실행 자격을 검증하고 Worker가 선택된 최신 ExecPlan과 현재 코드에 맞춰 구현한다. 승인된 수정본과 적용할 기존 작업이 확정됐다면 유효성을 확인해 해당 Worker에 전달한다. 승인된 내용에 따라 PRODUCT·Requirement·ARCHITECTURE가 실제 변경된 경우는 위 명세 변경 조건을 적용한다.

중단·재시작·원격 관측은 새로운 계획 호출 사유로 취급하지 않는다. 위 목적의 미완료 단계와 유효한 결과·게시 intent를 먼저 재사용하며, 실제 입력 변경으로 결과를 적용할 수 없거나 결과 오류·계획 작성 범위의 충돌 교정이 필요한 경우에만 해당 세션의 필요한 판단을 재호출한다. 명확한 형식·ID·경로 교정과 객관적 상태 확인은 R-071의 Manager 처리를 재사용한다. 같은 경계의 여러 호출 목적은 필요한 판단과 목적별 근거를 보존한 한 호출로 처리할 수 있다.

### Requirement 완료 재확인

- Manager가 해당 Requirement에 연결된 마지막 ExecPlan의 실제 Merge를 원격에서 확인하고 catalog·DB를 반영하면 다음 안전한 작업 선택 경계에서 해당 Requirement를 바로 재확인한다. 다른 Requirement의 READY·Merge 대기·완료나 프로젝트 전체 종료까지 미루지 않으며, 독립된 새 작업·유지보수 cycle 선택 전에 확인한다. 실행 중 writer·소유 Git operation·실제 프로젝트 안전 차단은 기존 완료·복구 경계를 따른다.
- Worker 완료·verify PASS·Review PASS·PR 생성·Close를 Merge로 취급하지 않는다. source 관계가 유효하고 연결된 모든 ExecPlan이 실제 MERGED이며 미해결 관련 draft·사용자 판단이 없어야 완료 확인 대상이 된다. 하나의 ExecPlan이 여러 Requirement에 연결되면 각각의 남은 작업과 완료 조건을 확인한다.
- 일반 Planner는 최신 Requirement의 각 Acceptance Criterion을 관련 PRODUCT·ARCHITECTURE, Merge된 구현·테스트와 실제 검증 근거에 대조해 충족·미충족·불확실로 판단한다. ExecPlan의 목적·조건이 원래 Requirement를 빠짐없이 다뤘는지도 확인하며, 작업이 전부 Merge됐다는 사실만으로 Requirement 전체 충족을 추정하지 않는다.
- 전체 충족과 유효한 근거가 확인되면 Manager가 완료 판단을 기록하고 원문 그대로 archive한다. 미충족 조건은 해당 Requirement에 연결된 후속 ExecPlan으로, 필수 사용자 판단은 draft로 남긴다. 불확실·검증 근거 부재는 완료·archive를 보류하고 원인과 재개 조건을 보존한다.
- 같은 입력의 유효한 Requirement 판단은 재사용한다. 원문·관련 명세·source 관계·구현·검증 근거가 바뀌면 이전 성공으로 완료하지 않는다. 여러 Requirement가 같은 경계에서 대상이 되거나 명세 변경 검토·프로젝트 최종 확인도 필요하면 한 Planner 호출로 처리하되 Requirement별 판단과 프로젝트 전체 확인의 근거를 구분해 기록한다.
- 관련 Requirement 재확인만 필요한 경우 대상 조건과 관련 근거에 집중하며 무관한 전체 명세 검토를 반복하지 않는다. archive 게시·DB 반영은 기존 publication·소유권·원격 재확인 경계를 따르고, 이동 자체로 Planner 호출·새 작업 주기·완료 알림을 다시 만들지 않는다.

### Requirement 변경과 작업·DB 동기화

일반 Planner는 검증한 최신 원격의 Requirement 변경 전후 동작·조건·Acceptance Criteria를 현재 구현·테스트·기존 ExecPlan·PR과 비교한다. 파일 내용이나 source 목록이 바뀌었다는 사실만으로 새 작업을 생성하지 않고 실제 미충족 목표와 영향받는 작업을 식별한다. 직접 sources뿐 아니라 적용 제품 규칙·작업 항목·본문·공유 구현·검증·dependency의 의미를 확인한다.

| 변경 | 계획 반영 |
|---|---|
| 신규 Requirement | 이미 구현되거나 기존 작업이 담당하는 목표는 중복 생성하지 않는다. 관련 미착수 작업으로 처리할 수 있으면 개정을 우선하고 독립적인 미충족 목표에만 새 ExecPlan을 만든다. 필요한 source·dependency를 연결한다. |
| Requirement 수정 | 변경·추가·삭제된 조건과 완료 기준을 구분한다. 기존 작업의 목표 안이면 허용된 같은 ID 개정으로 반영하고 독립 목표는 새 작업으로 분리한다. 달라진 작업 체크리스트·관련 파일과 변경 목적·Validation·sources·dependency를 함께 갱신한다. |
| 일부 Acceptance Criteria 삭제 | 삭제 조건에만 필요한 미구현 항목·테스트·참조를 제거하고 남은 조건·다른 Requirement·PRODUCT 목표와 공유 구현은 보존한다. 모든 현행 목표가 불필요해진 작업의 삭제·취소는 R-055를 따른다. |
| Requirement 전체 삭제 | 전체 철회·일부 근거 삭제·남은 목표를 R-055에서 판단하고 관련 문서·DB의 취소·개정을 반영한다. 경로 부재만으로 취소하지 않는다. |
| 완료 Requirement archive·같은 identity의 rename | 완료 보관·경로 변경으로 구분한다. R-071의 source resolver와 기존 경로 문자열 호환을 유지하고 목표 철회·중복 작업을 만들지 않는다. |
| 이미 구현·Merge한 기능의 새 변경 | 현재 구현과 달라져야 하는 범위만 새 변경으로 계획한다. 기존 완료·Merge·검증 기록을 초기화하지 않는다. 제품 동작의 되돌림도 명세가 요구하는 새 변경으로 다룬다. |
| 원격 조회 실패·revision 불일치·관련성 불확실 | 부재·변경 없음·동기화 완료로 확정하지 않는다. 영향 범위의 근거를 보존해 재관측·보류하고 유효한 독립 작업은 기존 정책대로 계속한다. |

여러 Requirement가 하나의 ExecPlan에 연결되면 작업 항목·공유 구현·관련 완료 기준과 근거 ID의 관계를 최소한의 본문 참조로 식별한다. 한 근거의 조건이 바뀌거나 삭제돼도 다른 근거에 필요한 작업·테스트·공통 구현은 보존한다. 단순 source 경로 삭제로 부분 변경의 의미를 처리하지 않는다. 전체 Requirement에 새 기준 ID나 metadata를 일괄 추가하지 않으며 변경하는 작업에 필요한 관계만 명확히 한다.

일반 Planner는 아래 갱신 경계가 허용한 관련 미착수·진행 중 작업을 함께 확인한다. 새 목표를 기존 미착수 작업으로 처리할 수 있으면 개정을 우선하되, 현재 작업의 조건 갱신을 다른 작업의 선택까지 미루지 않는다. 문서 갱신은 이미 구현한 결과와 기존 검증 근거를 무조건 초기화하거나 새 조건의 성공으로 바꾸는 근거가 아니다. 미충족 조건과 유효한 과거 근거를 구분하고, 필요한 선행 목표를 dependency 제거만으로 우회하지 않는다. source·dependency의 최종 graph와 실제 선행 PR Merge gate를 유지한다.

Manager는 기존 snapshot·원격 revision·content hash·현재 실행 및 소유권의 CAS 검증과 publication intent를 재사용한다. 원격 최종 변경을 확인한 뒤 같은 결과의 새 계획 등록·개정 선언·source·dependency·선택 자격·입력 지문을 SQLite transaction에 반영한다. 삭제·취소 row와 감사는 R-055, 판단 대기·결정 입력 정리는 R-061을 따른다. PR·수동 예약·writer·소유권이 바뀌면 오래된 수정안을 적용하지 않으며 snapshot 밖의 변경 권한을 만들지 않는다.

문서 게시와 DB 적용 사이 중단은 실제 원격 결과와 저장된 intent를 대조해 미완료 반영부터 재개한다. 원격 게시 또는 DB 일부 변경만으로 전체 동기화를 확정하지 않고, 같은 변경 재처리에서 중복 계획·취소·실행·지문 성공을 만들지 않는다. 변경의 의미를 판단하는 Planner와 검증·게시·원자 적용을 담당하는 Manager의 경계를 유지한다.

현재 `planning/input_fingerprints.py`, `planning/planner_validation.py`, `planning/planner_publication.py`, `storage/planning_publication_state.py`, `storage/execplan_catalog_state.py`의 변경 감지·개정·원자 적용을 재사용하는 것이 기준이다. 경로는 `loop_manager_internal/` 아래다. 관련 `tests/test_incremental_planning.py`, `tests/test_execplan_catalog_state.py`, `tests/test_planning_publication.py`, `tests/test_planning_requirement_moves.py`에는 변경 감지·선언 delta·transaction·경합·archive 회귀가 있다. 이 기존 보장은 의미별 작업 동기화 전체의 완료 증거와 구분한다. 새 구현은 이미 있는 G-242·G-243·G-257~G-261과 중복하지 않는 미충족 범위만 계획한다.

### ExecPlan 갱신 경계

- Worker는 선택된 ExecPlan의 구현·검증 기록 등 본문만 수정한다. frontmatter와 다른 ExecPlan, 활성·archive를 포함한 모든 Requirement는 수정하지 않는다. Worker는 현재 작업에 필요한 PRODUCT·ARCHITECTURE·FUTURE_IDEAS를 수정할 수 있다. Requirement 추가·삭제·rename·이동과 archive 후보 지정에 따른 Worker 수정 예외도 허용하지 않는다. frontmatter 변경은 Planner·Manager가 검증하고 공식 선언·catalog·DB에 반영한 뒤 실행 입력으로 사용한다.
- 기존 source 경로의 rename 조회 호환은 R-071대로 유지한다. 누락·모호한 source나 잘못된 선언은 Worker 시작 전에 Manager가 확정 가능한 규칙으로 정합화하고, 확정할 수 없으면 원인과 작업을 보존해 기존 사용자 판단·복구 경로로 보류한다. ExecPlan 변경만으로 Planner를 호출하거나 Worker의 경로 수정·metadata 비교 완화로 우회하지 않는다. 교정은 기존 구현·문서·테스트·실행 기록을 보존하며 완료·verify 성공·차단 해제를 뜻하지 않는다.
- 일반 Planner는 PR 등록 전인 ExecPlan을 관련 Requirement 변경에 맞춰 갱신한다. 최초 실행 여부, READY 복귀, 기존 branch·worktree·세션 또는 원격 checkpoint 존재만으로 갱신 대상에서 제외하지 않는다.
- 진행 중 작업의 갱신은 같은 ExecPlan ID와 작업물·세션·실행 및 실패 이력을 보존한다. 이미 수행한 구현·검증 기록과 새 조건의 미충족 부분을 구분하며, 문서 갱신 자체를 작업 완료나 과거 실패 해소로 기록하지 않는다.
- PR 등록 후 Merge를 기다리는 ExecPlan은 새 요구사항을 반영하기 위해 수정하지 않는다. 추가·변경 요구사항의 미충족 범위는 새 ExecPlan으로 작성하며 기존 작업과의 중복·dependency는 기존 카탈로그 규칙으로 확인한다.
- PR 경계는 연결 PR의 실제 등록 여부로 판단한다. SQLite에 아직 반영되지 않은 PR도 갱신 금지에 포함한다. 갱신 결과 적용 전에 PR이 등록됐으면 이전 갱신 권한으로 기존 작업을 덮어쓰지 않고 새 ExecPlan 경로로 다시 판단한다.
- 진행 중 Agent나 검증 프로세스를 중단하거나 같은 worktree를 동시에 수정하지 않는다. 종료 후 다음 단계 진입 전의 안전한 경계에서 필요한 갱신·게시·작업 branch 반영을 완료하고 최신 작업 문서를 입력으로 사용한다.

### Worker 범위 밖 문서 변경의 복원 목표

선택된 ExecPlan의 frontmatter는 Worker 종료 후 정상 작업 경계에서 Worker 시작 선언·공식 원본·본문 구분자가 확인될 때만 부분 복원한다. 본문 전체·mode·선택된 구현과 테스트는 보존하며, 사전 수정·동시 수정·진행 중 rebase·원본 또는 구분자 불확실성에서는 덮어쓰지 않는다. 변경 전후 선언과 본문 hash를 감사로 유지하고 Worker에게 복원 사실을 전달해 현재 문서 보고를 갱신한다. 새로운 선언 교정·DB 반영이나 검증 성공을 이 복원으로 대신하지 않는다.

아래 다른 문서의 파일·index 복원은 추가할 후속 요구이며, 선택된 frontmatter 부분 복원과 구분한다.

- rebase로 유입된 문서는 원본 브랜치와의 비교로 구분해 그대로 보존한다. Worker가 선택된 작업 외의 ExecPlan 또는 활성·archive를 포함한 모든 Requirement를 직접 변경했는지는 호출 전후 형상과 원본을 함께 대조한다. 경로 차이만으로 변경 주체를 확정하지 않는다.
- Manager는 Worker와 관련 writer가 종료한 뒤 실제 Worker 변경으로 확인된 경로만 복원한다. Worker 이전부터 존재한 수정·동시 외부 수정·소유권 불확실성이 있으면 덮어쓰지 않고 근거와 작업물을 보존해 기존 차단·복구 경계로 연결한다.
- 복원 전에 대상 경로·기준 revision·변경 사유와 확보한 수정 내용을 보존한다. 복원은 해당 파일과 index entry에 한정하며 선택된 ExecPlan 본문·구현·테스트·다른 파일·HEAD·branch·실행 이력은 유지한다. 중단 뒤에도 보존한 입력과 현재 형상을 대조해 남은 복원만 처리하며 새로운 수정을 덮어쓰지 않는다.
- 복원 성공은 차단 사유로 남기지 않는다. Manager가 같은 Worker 세션 또는 재개 문맥에 복원한 경로·원인을 전달해 현재 최종 diff와 문서 보고를 갱신하도록 한다. 복원 사실을 구현 완료·targeted test·전체 verify·Review 성공으로 취급하지 않으며 독립적인 실패는 유지한다.

### 프로젝트 planning과 현재 작업 재개 순서

Manager는 최신 원격의 PRODUCT·활성 Requirement·ARCHITECTURE 변경을 프로젝트의 마지막으로 원격 적용한 전체 planning 성공 기준과 비교하고 위 Planner 실행 조건을 적용한다. ExecPlan 변경 자체는 프로젝트 재계획을 시작하지 않으며 Manager의 선언 검증·catalog 반영과 해당 작업의 실행 대응으로 처리한다. 저장소 SHA 전진이나 기본 worktree의 equal 여부만으로 명세 변경·반영 완료를 판단하지 않는다.

1. Worker·Manager verify·Reviewer가 실행 중이면 종료를 기다린다. 같은 worktree를 동시에 수정하거나 프로세스를 강제 중단하지 않고, 결과와 현재 작업의 재개 단계·작업물·세션·실행 및 실패 이력을 보존한다.
2. 다음 Worker·verify·Review·게시 진입 전 안전한 경계에서 필요한 프로젝트 전체 planning을 현재 작업 재개보다 먼저 수행한다. 현재 작업을 다른 작업으로 교체하거나 READY로 초기화하지 않는다. 소유 Git operation이 진행 중이면 기존 operation의 완료·복구를 먼저 처리하고 최신 명세를 반영한다.
3. 일반 Planner는 변경된 명세와 영향받는 작업·구현·검증·dependency부터 확인하고 불확실하면 범위를 넓힌다. 관련성을 직접 sources 목록만으로 제한하지 않으며, 무관한 작업까지 같은 명세 전문을 반복 검토하지 않는다. 실제 미충족 조건은 허용된 관련 ExecPlan의 작업 항목·완료 조건·Validation·관계에 반영한다.
4. Manager가 허용된 개정의 원격 게시와 catalog·DB·프로젝트 planning 성공 기준의 반영을 완료한 뒤 현재 작업을 재개한다. 개정이 필요 없다는 유효한 전체 planning 결과도 같은 성공 기준에 확정해 동일 입력의 호출을 반복하지 않는다. Planner 자신의 검증된 게시 delta를 새로운 외부 명세 변경으로 재소비하지 않는다.
5. 현재 작업 branch에 최신 ExecPlan을 반영하고 아래 실행 대응을 적용한다. 새 dependency가 있으면 실제 Merge gate를 다시 확인하며, dependency 대기를 피하려고 개정을 무시하거나 선행 관계를 삭제하지 않는다. PR 등록·수동 소유·사용자 판단·독립 차단은 기존 갱신 권한을 유지한다.

프로젝트 전체 planning은 작업 구성과 명세의 관련성을 판단한다. 개별 작업의 실행 대응 확인은 Worker·Reviewer와 Manager의 검증 책임으로 처리하며, 같은 명세 변경의 관련성이나 ExecPlan의 구현 적합성을 별도 Planner에게 다시 맡기지 않는다. 이 실행 대응을 프로젝트 전체 planning 성공으로 기록하지 않는다. Requirement 완료 재확인 뒤 일반 작업 간 우선순위와 유지보수의 대상·안전 제한은 유지한다.

### 원격 확인과 ExecPlan 변경에 따른 실행 대응

Planner도 최초 입력을 전체 주기 동안 고정하지 않고 진입·종료·교정·게시 전의 안전한 경계에서 최신 원격 원본을 확인한다. Agent와 같은 worktree에 pull/rebase를 겹치지 않으며 갱신된 명세·ExecPlan으로 기존 ID와 작업 결과를 보존해 재평가한다. 단계 중 동시 원격 변경은 종료 후 재관측하고 오래된 판단을 그대로 게시하지 않는다.

Manager는 Worker, Manager verify, Reviewer 진입 전에 등록된 origin의 최신 원본 branch와 현재 작업 branch를 확인한다. 재시도·교정·중단 후 재개도 같은 진입 기준을 따른다. 로컬 원본 branch와 기본 checkout의 미커밋 변경을 원격 기준으로 대신하지 않는다.

로컬 작업 수용·원격 작업 통합·게시 권한은 R-055대로 분리한다. 로컬을 원격 원본 위로 정상 rebase했으면 과거 원격 작업 tip의 조상 관계만으로 거부하지 않는다. 새 원격 작업은 기존 통합·보존 경계로 연결하며 바뀐 후보·문서·검증 입력을 대조해 아래와 같이 처리한다.

원격 작업 branch 또는 같은 PR의 head OID 전진은 R-055의 OID·ref 정상 처리 표에 따라 새 입력으로 반영한다. 로컬 HEAD·과거 게시 OID·PR head의 단순 불일치나 게시 receipt 부재만으로 사용자 조치를 요구하지 않는다. 관련 문서·후보가 실제로 바뀌면 아래 단계별 대응을 적용하며, PR 등록 후 기존 ExecPlan 갱신 금지와 실제 PR·repository·head/base branch의 대상 확인은 유지한다. 미완료 rebase의 target·원형을 새 관측값으로 덮어쓰지 않고 현재 전이를 완료·복구한 뒤 남은 원격 입력을 처리한다.

| 변경 종류 | 처리 |
|---|---|
| PRODUCT·활성 Requirement·ARCHITECTURE 변경 | 위 프로젝트 planning을 먼저 확정한다. 현재 작업과 무관해도 프로젝트의 변경 검토는 수행하며, 개별 작업별 명세 영향 Planner 호출은 반복하지 않는다. |
| ExecPlan 추가·본문·선언 변경만 있음 | Manager가 catalog·source·dependency·사용자 판단을 검증해 실행 입력에 반영한다. 프로젝트 재계획·점검 Planner·작업별 영향 Planner는 호출하지 않는다. |
| 현재 ExecPlan의 구현 조건이 그대로이거나 수행 기록만 변경 | 필요한 rebase 후 하던 단계를 계속한다. SHA·문서 변경 사실만으로 Worker를 다시 호출하지 않는다. |
| 현재 ExecPlan의 구현 관련 조건 변경 | 마지막으로 실제 반영한 ExecPlan과 최신 문서를 비교하고 현재 후보·발견 단계에 맞춰 아래 대응을 적용한다. |
| 코드·테스트·설정 등 구현·검증 입력 변경 | Planner를 호출하지 않고 기존 rebase·충돌 복구·Worker의 현재 코드 확인·후보 검증 무효화와 증명된 결과 재사용 규칙을 적용한다. |
| 문서와 코드 변경이 함께 있음 | 필요한 프로젝트 planning·ExecPlan 실행 대응과 코드 변경의 기존 검증 규칙을 함께 적용한다. |

작업의 문서 변경 비교 기준은 직전 fetch·rebase나 저장소 전체 SHA가 아니라 해당 작업이 마지막으로 실제 반영한 ExecPlan이다. 목표·범위·완료 기준·구현/검증 조건·sources·dependency·사용자 결정 등 구현 관련 내용을 R-072의 순수 기록 구분과 함께 비교한다. 절 이름만으로 Progress·Decision Log를 통째로 제외하지 않는다. 조건 변경도 Worker 재호출의 충분조건이 아니며 현재 구현의 부족과 발견 단계로 대응한다.

새 조건에 대한 구현 충족 여부를 기존 Worker 결과·검증 근거로 확정할 수 없으면 해당 Worker 세션에 최신 ExecPlan·변경 delta·유효한 과거 근거를 전달해 판단과 필요한 구현·targeted test를 함께 수행한다. Worker 진입 때의 동일 판단을 별도 호출로 선행하지 않으며, 구현 부족이 없다는 유효한 근거가 있으면 현재 verify·Review를 계속한다. Worker는 frontmatter·다른 작업·Requirement를 수정하지 않고 Manager의 dependency·사용자 판단 gate를 우회하지 않는다.

연결 Requirement·적용 PRODUCT·ARCHITECTURE의 변경 의미는 프로젝트 Planner가 관련 ExecPlan에 반영한다. 현재 ExecPlan이 그대로이고 유효한 전체 planning 결과가 현재 조건의 유지를 확인했다면 개별 작업이 상위 명세 영향 판단을 다시 시작하지 않는다. 전체 planning의 미완료·불확실을 ExecPlan 무변경으로 대신 확정하지 않는다. verify·Review의 실제 입력·명세·후보 비교는 R-072대로 별도로 유지한다.

작업별 SHA·definition snapshot·checkpoint는 Git 복구·소유권·검증·Review·게시 근거에도 사용하므로 일괄 삭제하지 않는다. 프로젝트 planning 성공 기준과 작업의 마지막 반영 ExecPlan 기준을 구분하며, 원격 관측·문서 개정·진행 기록만으로 실제 구현·검증 성공 기준을 갱신하지 않는다.

### 진행 기록 커밋과 마지막 반영 기준

Worker 또는 Manager가 해당 작업의 Progress·기존 수행/검증 사실을 커밋하면 실제 반영한 기록 변경만 마지막 반영 ExecPlan 기준에 함께 반영한다. 자신의 기록을 새 구현 조건으로 재판단하거나 동일 입력의 Planner·Worker 호출을 만들지 않는다. 기록 변경은 새로운 성공·승인·실패 해소의 근거가 아니다.

기준 갱신은 확인한 변경 전 내용과 실제 커밋 결과에 결합한다. 같은 파일·커밋에 아직 확인하지 않은 사용자·Planner의 목표·제약·완료 조건 변경이 섞이면 그 조건을 함께 소비하지 않는다. 기록 delta만 안전하게 분리할 수 없으면 이전 기준과 미반영 조건을 보존하고 필요한 실행 대응을 남긴다. 프로젝트 planning 기준의 자체 게시·기록 delta 처리도 확인한 변경만 반영하며 새 전체 planning 성공을 합성하지 않는다.

커밋 이후 기준 저장 전에 중단돼도 재개 시 보존된 변경 전 근거·실제 커밋·현재 문서를 대조해 같은 갱신을 완료할 수 있어야 한다. 이미 갱신한 결과는 반복 적용하지 않으며, 후속 원격 변경이나 원격에서 제거된 커밋을 최신 문서 전체 채택으로 우회하지 않는다. 기존 구현·verify·Review·게시 성공과 실패 이력은 독립적으로 보존한다.

### 발견 단계별 대응

| 변경 확인 시점 | 처리 |
|---|---|
| Worker 진입 전 | 프로젝트 planning이 필요한 경우 먼저 확정하고 최신 ExecPlan과 rebase 결과를 Worker 입력으로 전달한다. 기존 세션을 재개할 때도 변경된 조건을 반영하며, 완료한 구현은 조건 변경 사실만으로 반복하지 않는다. |
| Manager verify 진입 전 | 변경된 ExecPlan 조건과 현재 구현을 대조한다. 구현 범위·완료 조건을 충족하려면 구현 보완이 필요한 경우 Worker로 돌아가 교정한 뒤 verify한다. 구현 보완이 필요 없으면 Worker를 반복하지 않고 최신 조건에 필요한 verify를 진행한다. |
| Reviewer 진입 전 또는 승인 후 게시 전 | 변경된 ExecPlan을 반영한 뒤 최신 작업 문서·현재 구현·실제 verify 근거로 Reviewer를 먼저 진행한다. 구현 부족은 Worker 교정으로, 검증 부족은 필요한 테스트·검증 근거 보완과 Manager verify로 연결한다. 문서 변경이나 이전 verify 근거의 유효성 상실만으로 Reviewer를 건너뛰어 Worker를 무조건 호출하지 않는다. |

Reviewer에는 기존 verify가 확인한 후보·입력·조건과 새 조건에 대한 검증 여부를 구분해 전달한다. 이전 문서 기준의 PASS만 남아 있으면 참고 근거로 제공하되, 변경된 조건의 검증 성공으로 표시하지 않는다. 검증만 부족한 결과를 구현 부족으로 일괄 처리하지 않으며, 필요한 테스트 작성·수정·실행은 기존 역할의 권한과 책임을 따른다.

Reviewer 진입 전 OID가 바뀌었거나 별도 진단 ref 게시가 보류돼도 최신 문서·코드·diff와 실제 검증 근거를 대조해 필요한 verify 또는 Review를 진행한다. 검증 입력이 같고 성공 근거가 유효하면 R-072대로 verify를 재사용할 수 있고, 검증 부족을 선행 Review에서 확인했으면 필요한 verify로 연결한다. Review 중 후보 변경도 새 후보의 verify·Review 판단으로 처리하며 실제 구현 부족 없이 Worker 재구현으로 일괄 되돌리지 않는다. 최종 게시에는 최종 후보의 유효한 검증·Review 근거를 요구한다.

이 문서의 선행 Review는 관련 원격 문서 변경에 대한 판단이다. PASS/VERIFY_REQUIRED는 검증 보완 이후에도 자동으로 최종 승인으로 승격하지 않는다. R-086의 영향 기반 부분 verify 뒤 일반 선행 Review와 증거·수명을 구분하며, 일반 선행 승인 재사용 조건을 이 문서 변경 결과에 적용하지 않는다.

### rebase 충돌과 구현 조건 변경

Worker의 최초 진입·재개·교정 진입은 필요한 일반 Planner 갱신·게시 후 최신 base의 작업 조건을 작업 branch에 반영하는 순서로 진행한다. Manager가 rebase를 수행하고 아래 기준으로 충돌을 분리한다. 계획·작업 문서는 Requirement·ExecPlan을 뜻하며 PRODUCT·ARCHITECTURE·공통 지침과 그 밖의 문서·코드·테스트·설정은 그 외 파일에 속한다.

| 충돌 대상 | 처리 |
|---|---|
| Requirement·ExecPlan | Manager 코드가 관측한 최신 base의 내용·경로·삭제를 채택한다. 작업 branch의 오래된 조건을 병합해 되살리지 않는다. 문서 처리가 복잡하거나 진행 기록을 안전하게 병합하기 어려우면 대상 파일 전체를 최신 base 원문으로 교체할 수 있다. |
| 그 외 파일 | 기존 단계가 verify·Review·게시여도 Worker 충돌 교정으로 돌아간다. Manager가 base나 작업 형상을 일괄 선택해 해결하지 않는다. Worker가 최신 조건에 맞춰 양쪽 형상을 검토하고 해결·수정·targeted test를 수행한다. |

최신 base는 필요한 Planner 갱신이나 사용자 변경이 이미 원격에 반영된 immutable revision으로 확인한다. rebase의 ours/theirs 명칭만으로 어느 쪽이 이 기준인지 판단하지 않는다. 문서 채택·전체 교체는 해당 계획·작업 파일에 한정하며 branch·코드·index 전체를 reset하지 않는다. 충돌 복구가 불가능한 파일만 R-055의 파일별 원본 복원·재작업 정책을 따른다. 교체 전 문서와 보존 가능한 작업 형상은 기존 checkpoint·복구 근거로 남기고 branch·worktree·session·실행 및 실패 이력을 유지한다. 작업 branch에만 있던 문서 진행 표시는 최신 base 원문으로 대체될 수 있지만, 이전 수행 사실을 지우거나 base의 체크 표시를 현재 후보의 성공 증거로 채택하지 않는다. 삭제·archive·rename, source·dependency와 실제 PR 경계를 확인하고 삭제된 문서를 임의로 복원하지 않는다. 현재 작업의 유효성을 확정하지 못하면 해당 범위의 기존 판단·보존 경로를 따른다.

Worker는 이미 채택된 Planner·사용자의 최신 계획·작업 문서를 입력으로 최신 base와 보존된 작업 형상을 대조한다. 코드 충돌은 한쪽 형상 전체를 관례적으로 선택하지 않고 최신 목표·제약·완료 조건에 맞춰 필요한 변경을 선택·결합한다. 이전 조건으로 문서를 되돌리거나 Planner 갱신·문서 교체만으로 기존 코드의 적합성을 확정하지 않는다. 계획·작업 문서 충돌만 코드로 해소됐다면 문서 충돌 자체를 이유로 Worker를 호출하지 않고 위 발견 단계별 대응을 따른다. Worker·Reviewer는 각자의 단계에서 실제 구현·검증 근거로 진행 상황과 미충족 조건을 재점검하며, Reviewer의 읽기 전용 권한은 유지한다.

소유한 rebase에서 ExecPlan 본문·sources·연결 명세·archive 범위·공통 지침 등 구현 입력이 바뀌었다는 사실만으로 최종 차단하지 않는다. Manager가 변경된 조건·문서 교체·적용 revision·남은 충돌과 유효한 과거 근거를 구분해 전달하고 필요한 Worker 교정·검증으로 연결한다. dependency 미충족은 실행 준비 조건으로 별도 처리하며 충돌 교정을 이유로 우회하지 않는다. SHA만 바뀌거나 확인 가능한 진행 기록만 바뀐 경우에는 R-072의 입력 비교·재사용 정책을 유지한다.

진행 중 rebase의 target을 새 원격 OID로 덮어쓰거나 두 번째 rebase를 겹치지 않는다. 기존 소유 operation과 원형을 보존해 완료·복구한 뒤 남은 최신 base 반영을 이어간다. 이전 정의 snapshot이 없어도 현재 작업의 identity·소유권·최신 조건과 보존된 작업을 확인할 수 있으면 과거 성공은 재사용하지 않고 교정·검증으로 연결한다. 실제 소유권·범위·문서 유효성·필수 사용자 결정이 불확실하거나 허용된 교정에서 진전이 없으면 기존 한도에 따라 영향받는 작업만 최종 차단한다. 사용자 operation을 임의 중단하거나 원형을 폐기해 복구하지 않는다.

이 사유로 이미 차단된 작업도 같은 현재 근거로 재평가한다. 안전한 교정 경로가 확인되면 해당 차단 원인만 해제하고 기존 branch·worktree·session·실패 이력을 이어간다. 입력 변화 없이 같은 불일치를 다시 검사해 차단하는 순환이나 무한 Worker 호출을 만들지 않는다. 최신 조건의 targeted test·필요한 Manager verify·최종 후보 Review와 기존 게시 안전 조건이 충족되기 전에는 구현 완료나 PR 게시를 승인하지 않는다.

### 검증 근거와 완료 조건

문서 변경은 단계별 영향 판단의 입력이며 Worker 재호출의 충분조건이 아니다. 반대로 구현 코드나 verify 명령이 같다는 사실만으로 이전 성공을 새 완료 조건의 성공으로 간주하지 않는다. 변경된 조건까지 기존 검증이 충족한다는 근거가 없으면 필요한 검증을 보완한다.

이전 성공을 재사용하려면 R-072의 실제 입력·작업 주기·후보 연결 조건과 최신 완료 조건에 대한 근거가 충족돼야 한다. 무관한 문서 변경 뒤에도 후보나 실제 검증 입력이 바뀌면 기존 검증 규칙을 적용한다. 문서 관련성이 없다는 판단이 후보 검증을 면제하지 않는다.

Reviewer를 먼저 진행한 결과가 구현 부족이면 Worker 교정 후 필요한 verify·Review를 거친다. 검증 부족이면 필요한 검증을 보완하고 최종 후보의 Review 근거를 다시 판단한다. 최신 조건의 구현·검증과 최종 후보의 유효한 Review가 충족되기 전에는 PR 게시를 승인하지 않는다. 게시 직전의 원격 재확인과 기존 PR·lease·checkpoint 안전 조건도 유지한다.

### 실패와 중단 후 재개

- 원격 확인·갱신·rebase·관련성 판단에 실패하거나 적용 조건을 확정할 수 없으면 무관한 변경 또는 반영 완료로 간주하지 않는다. 현재 작업과 원인을 보존하고 기존 재시도·복구·사용자 판단 경로를 따른다.
- 프로젝트 planning 중단·실패에서는 보존된 planning 입력·세션·게시 intent·현재 작업 재개 정보를 유지한다. 같은 실패 입력의 Planner 호출을 반복하지 않고, 변경 영향을 확정하지 못한 현재 작업은 다음 실행 단계 진입을 보류한다. 공유 operation·게시가 안전하게 정리된 뒤 검증된 독립 작업을 계속하는 R-055 정책은 유지한다.
- 문서 갱신·반영 중 원격 내용이나 대상 PR 경계가 바뀌면 오래된 판단을 적용하지 않고 최신 상태에서 다시 확인한다. 충돌은 위 충돌 교정 절차로 연결하고, 문서 부재·불명확한 source 또는 dependency는 기존 검증과 차단 규칙을 따른다.
- 원격 게시 뒤 DB 반영 전의 중단은 같은 게시 결과의 미완료 반영부터 복구한다. 원격 재전진이 있으면 그 결과의 적용과 새 변경 검토를 구분하고, 최신 명세에 대한 planning 완료 없이 현재 작업을 재개하지 않는다. 이전 작업별 문서 판단·개정 checkpoint도 보존된 게시 사실과 미완료 단계를 확인해 복구하며 새 전체 planning 성공으로 소급하지 않는다.
- 중단 후에는 반영한 원격 기준, 갱신된 작업 문서, 남은 보완과 실제 완료 근거를 대조해 필요한 단계부터 재개한다. 이미 확정된 갱신·게시·rebase를 반복하지 않으며, 원격이 그대로라는 이유로 남은 구현·검증 보완을 건너뛰지 않는다.
- 문서 변경 또는 rebase 완료만으로 사용자 승인 대기, 명세 충돌, 독립적인 차단·실패 원인이나 실패·Worker level 이력을 초기화하지 않는다.

## Acceptance Criteria

- 위 Planner 실행 조건만 자동 호출을 시작한다. 다른 독립적인 호출 조건이 없는 ExecPlan 변경만의 경우와 코드·테스트·설정 전용 변경의 READY 있음·없음·dependency 대기 조합에서 일반·점검·작업별 문서 영향 Planner가 호출되지 않으며, Manager 선언 검증과 Worker의 최신 코드·작업 조건 반영이 유지된다.
- 조건이 바뀐 ExecPlan의 구현 적합성은 기존 Worker 세션에서 필요한 보완과 함께 확인한다. 순수 수행 기록·이미 확인한 조건은 재호출하지 않고 새 조건을 확인하지 않은 채 과거 verify·Review 성공으로 게시하지 않는다.
- 새 Requirement·상위 명세 변경, draft 사용자 답변, 추적 ExecPlan이 필요한 명시적 수동 제출, R-074의 자동 주기·수동 유지보수 요청, Requirement 완료 재확인과 프로젝트 최종 확인은 목적에 맞는 Planner 호출을 유지한다. 결과 재사용·오류 교정·중단 재개·원격 경쟁에서는 필요한 미완료 판단만 재호출하고 같은 입력의 중복 호출을 만들지 않는다.
- Requirement의 마지막 연결 ExecPlan Merge를 실제 확인한 뒤, 다른 Requirement의 READY·Open PR·차단이나 프로젝트 전체 완료를 기다리지 않고 다음 안전한 경계에서 해당 Requirement를 재확인한다. 실행 중 writer·소유 operation·실제 프로젝트 안전 gate는 준수하며, 완료 확인 뒤 독립 작업·새 유지보수 선택을 계속한다.
- 모든 연결 작업이 MERGED여도 원래 Acceptance Criteria에 누락·새 조건·검증 근거 부재가 있으면 완료·archive하지 않는다. 충족은 Manager의 판단 기록·원문 archive로, 미충족은 후속 ExecPlan으로, 사용자 결정은 draft로, 불확실은 보류·재개 조건으로 반영한다. 공유 ExecPlan의 각 Requirement 판단과 같은 입력 재사용·다중 대상 호출 통합을 확인한다.
- 선택된 ExecPlan의 본문 기록과 PRODUCT·ARCHITECTURE·FUTURE_IDEAS의 관련 수정은 허용하고 모든 Requirement 변경은 거부한다. archive 후보 지정으로 Worker 쓰기 권한이 확대되지 않는다. Worker가 변경한 frontmatter는 위 부분 복원 조건을 충족하면 본문을 보존해 공식 선언으로 되돌리고, 조건을 확인할 수 없는 선언 불일치는 검증·Review 전에 거부하며, 범위 밖 문서 수정은 위 복원 목표에 따라 최종 후보에서 제거하거나 안전을 확인할 수 없으면 거부한다. 원본 브랜치에서 rebase로 유입된 문서는 범위 밖 변경에서 제외하며 실제 오류에는 비교 원본·후보 revision과 경로·변경 종류를 확인할 수 있다. source 경로 교정은 원격 공식 선언과 catalog·DB가 같은 결과를 채택한 뒤 보존된 Worker 구현·기록으로 재개하며, rename 조회 호환을 선언 일치로 오인하지 않는다.
- 신규 Requirement의 목표가 이미 구현됐거나 기존 작업으로 충족되면 중복 ExecPlan이 생성되지 않는다. 기존 미착수 작업의 허용 개정과 독립적인 미충족 목표의 신규 생성이 구분되며 source·dependency와 DB 관계가 일치한다.
- Requirement 수정의 변경 전후 동작·조건·완료 기준과 관련 작업을 확인할 수 있다. 변경·삭제된 항목의 체크리스트·관련 파일·변경 목적·Validation·source·dependency가 함께 갱신되고 이미 구현한 결과·유효한 검증·세션·실패·PR 이력은 보존된다.
- 복수 Requirement의 일부 조건 또는 완료 기준만 삭제되면 그 부분의 작업·검증·참조만 제거된다. 다른 Requirement·PRODUCT의 목표와 공유 구현은 유지되고 필요한 선행 목표는 유효한 dependency로 남는다. 전체 철회만 R-055의 삭제·취소로 연결된다.
- 실제 삭제·완료 archive·rename·일부 조건 삭제·Merge 뒤 새 변경·조회 실패·revision 경쟁을 구분한다. 보관·경로 부재나 조회 실패로 취소하지 않고, 완료한 기능의 새 변경은 과거 MERGED를 초기화하지 않는 미충족 작업으로 계획한다.
- 원격 게시 확인 뒤 새 등록·개정·source·dependency·선택 관계가 같은 SQLite transaction으로 반영된다. snapshot·원격 또는 DB 소유권 경쟁에서는 오래된 반영이 거부되며, push 뒤 DB 미적용·transaction 중단·재시작은 저장 근거로 멱등하게 복구된다. 동일 입력의 중복 계획·취소·실행과 수행하지 않은 성공 기록이 없다.
- Planner의 진입·종료·교정·게시 경계마다 최신 원격 명세·ExecPlan을 확인한다. 작성 중 갱신은 writer 종료 뒤 반영하며 기존 ID·결과·실패 이력을 불필요하게 폐기하지 않는다.

- 실행 이력이 있는 READY와 IMPLEMENTING·VERIFYING·REVIEWING 상태의 PR 미등록 ExecPlan은 관련 Requirement 변경에 따라 같은 ID로 갱신할 수 있다. 기존 branch·worktree·세션·원격 checkpoint만으로 대상에서 제외되지 않으며 작업물과 실행 이력이 보존된다.
- PR 등록 후 Merge 대기 중인 ExecPlan에는 추가·변경 요구사항을 덧붙이지 않는다. 미충족 범위는 새 ExecPlan으로 작성하고 기존 계획·PR과의 중복·dependency를 확인한다.
- 갱신 대상 선정 뒤 실제 PR이 등록되거나 SQLite에 미기록인 연결 PR이 발견되면 기존 ExecPlan 갱신을 적용하지 않고 PR 이후 정책을 따른다.
- Worker·Manager verify·Reviewer의 최초 진입, 교정 재진입과 중단 후 재개에서 최신 원본·작업 branch를 확인한다. 실행 중인 프로세스와 worktree 변경을 겹치지 않는다.
- 원격 작업 branch 변경과 정상 원격 원본 기준 로컬 rebase를 R-055대로 수용·통합·게시로 나눠 판단한다. 같은 PR의 head 전진과 확인 가능한 이력 재작성은 새 입력으로 반영한다. Manager가 생성·게시한 branch의 실제 삭제를 PR 미Merge 상태에서 확인하면 해당 작업을 중단하고 명시적 재시작 요청 뒤 최신 원본에서 새 실행한다. 다른 대상·재작성 관계·필수 결정을 확정할 수 없으면 해당 원격 통합·게시만 보류하며 무검증 덮어쓰기를 허용하지 않는다.
- 명세 변경 없는 실행과 유효한 전체 planning 결과를 확정한 동일 입력의 재개에서는 Planner가 반복 호출되지 않는다. Worker·verify·Reviewer 실행 중 명세가 바뀌면 종료 후 다음 실행·게시 경계에서 프로젝트 전체 planning이 먼저 수행되고, 실제 원격 게시·DB 반영 뒤 동일 작업의 필요한 단계로 이어진다. PR·수동 소유·실행 및 실패 이력은 보존된다.
- 명세 변경으로 여러 작업이 영향받으면 프로젝트 일반 Planner가 관련 ExecPlan·구현·검증·dependency를 함께 확인한다. 현재 작업과 무관한 명세 변경도 이 검토를 거치되, 개정할 필요가 없는 현재 작업은 rebase 후 해당 단계를 계속한다. 개별 작업별 상위 명세 영향 Planner 호출과 무관한 변경의 Worker 재호출은 없다.
- ExecPlan이 그대로여도 연결 Requirement·적용 상위 명세가 현재 작업 조건을 바꾸면 프로젝트 planning에서 관련 ExecPlan을 갱신한 뒤 재개한다. 다음 작업 선택까지 미루거나 직접 sources 나열 여부로 제외하지 않는다. 유효한 변경 없음 결과와 planning 미완료·불확실을 구분한다.
- 저장소 전체 SHA 전진·기본 worktree equal·직전 rebase를 작업 조건 반영의 증거로 사용하지 않는다. 마지막 반영 ExecPlan과 최신 문서의 구현 조건을 비교하며, 순수 Progress 체크·기존 기록 변화와 실제 조건 변경을 같은 절 안에서도 구분한다. 작업별 Git·검증·Review snapshot은 보존된다.
- Worker·Manager의 순수 기록 커밋은 실제 반영한 delta만 작업 기준에 반영해 재호출을 만들지 않는다. 같은 파일·커밋의 미확인 사용자·Planner 조건, 커밋 뒤 원격 재전진과 비교 불가능한 delta는 함께 소비하지 않는다. 커밋 뒤 기준 저장 전 중단·재시작과 갱신 완료 뒤 재중단에서도 같은 갱신이 멱등 완료되고 새 성공·승인·실패 초기화가 없다.
- Worker 진입 전 관련 문서가 변경되면 최초·재개 Worker 모두 갱신·rebase가 완료된 최신 문서를 입력으로 구현한다.
- verify 진입 전 새 조건에 필요한 구현이 부족하면 Worker 교정 후 verify하며, 구현이 이미 충족된 문서 변경이면 Worker를 호출하지 않고 필요한 verify를 진행한다.
- Reviewer 진입 전 관련 문서가 변경되면 최신 문서·현재 구현·기존 verify가 확인한 범위와 새 조건의 검증 상태를 제공해 Reviewer를 먼저 진행한다. 과거 verify의 유효성 상실만으로 이 Review를 생략하지 않는다.
- 위 Review에서 구현 부족이 확인되면 Worker 교정으로 연결한다. 구현 부족 없이 검증만 부족하면 필요한 검증 보완으로 연결하며, 검증 부족을 무조건 구현 교정으로 처리하지 않는다. Reviewer 자체는 테스트·verify를 실행하거나 파일을 수정하지 않는다.
- 후보 OID 차이·진단 ref 게시 실패만으로 Reviewer 진입을 거부하지 않는다. 현재 문서·코드·검증 입력과 성공 근거로 verify 재사용·실행 또는 선행 Review를 선택하고, Review 중 바뀐 후보에 오래된 verdict를 승인으로 적용하지 않는다.
- 완료 조건만 추가되고 코드·verify 명령이 같아도, 추가 조건의 검증 근거가 없으면 이전 PASS를 새 조건의 성공으로 재사용하거나 PR을 게시하지 않는다. 기존 성공을 재사용한 경우에는 최신 조건 충족과 R-072의 입력 증명 근거를 확인할 수 있다.
- 관련 문서와 코드가 함께 변경됐거나 rebase 충돌이 발생하면 단계별 문서 대응과 기존 코드 검증·충돌 복구를 함께 적용한다. 최신 후보에 필요한 구현·검증·Review가 끝나기 전에 PR을 게시하지 않는다.
- Worker 최초·재개·교정 진입 전에 필요한 Planner 갱신·게시와 최신 base 반영을 수행한다. Requirement·ExecPlan 충돌은 Manager 코드로 최신 base를 채택하고, 그 외 파일 충돌은 이전 단계와 관계없이 Worker 교정으로 연결한다. Git operation의 계속 진행·완료는 Manager가 수행한다.
- rebase 중 구현 입력이 달라져도 안전한 소유권·유효한 최신 조건을 확인할 수 있으면 최종 차단 대신 기존 코드를 보존한 Worker 교정·targeted test·필요한 verify·Review를 수행한다. 본문·sources·연결 명세·archive 범위·공통 지침 변화와 코드 충돌이 함께 있는 경우를 포함한다.
- Requirement·ExecPlan 충돌에서 필요한 Planner 갱신 또는 사용자 변경이 반영된 최신 base의 내용·경로·삭제를 채택한다. 병합이 어렵다면 해당 파일 전체를 base 원문으로 교체해도 보존 가능한 이전 문서 원형·코드·세션·실행 및 실패 이력이 남는다. branch·코드·index 전체 reset을 하지 않고 충돌 복구가 불가능한 파일에만 R-055의 파일별 원본 복원·재작업을 적용한다. 삭제·archive·rename·dependency·PR 경계는 기존 유효성 검사로 확인한다.
- 계획·작업 문서 충돌만 자동 해소되면 문서 충돌 자체로 Worker를 반복하지 않고 단계별 재점검을 적용한다. 그 외 파일과의 혼합 충돌은 Worker로 돌아가 최신 문서를 기준으로 양쪽 형상을 검토·선택·결합하고 관련 targeted test를 수행한다. base 문서의 진행 표시를 현재 후보의 성공으로 간주하지 않으며 필요한 verify·Review 없이 게시하지 않는다.
- 이전 snapshot이 없으면 과거 성공을 재사용하지 않되 현재 소유권·조건이 확인된 작업은 교정·검증으로 이어간다. 소유권 불확실·문서 무효·사용자 결정·진전 없는 반복은 안전 차단하고 dependency 미충족과 사용자 operation을 우회하지 않는다.
- 충돌 교정·문서 반영·차단 재평가 중 재시작하거나 원격이 다시 전진해도 진행 중 rebase target과 원형을 보존한다. 같은 불일치의 반복 차단·무한 교정·중복 반영 없이 남은 단계부터 이어가며 독립적인 차단·승인을 해제하지 않는다.
- 갱신·rebase·단계 판단 후 중단돼도 재시작 시 작업물·세션·실패 이력을 보존해 필요한 단계부터 이어간다. 동일한 원격 변경을 중복 적용하거나 미완료 보완을 완료로 기록하지 않는다.
- 원격 확인 실패·판단 불확실·갱신 중 원격 변경에서는 오래된 입력으로 다음 단계를 시작하지 않는다. 기존 복구·차단 정책을 따르며 승인 대기와 독립적인 실패 원인을 보존한다.
- 프로젝트 planning의 시작·종료·게시·DB 적용·현재 작업 재개 사이의 중단, push 실패와 원격 재전진에서 미완료 반영부터 복구한다. 같은 입력의 중복 Planner·개정·실행을 만들지 않고 새로운 조건은 놓치지 않는다. planning 오류가 남아도 유효성이 증명된 독립 작업의 진행은 R-055·R-091대로 유지한다.

최소 회귀는 위 정상·실패 시나리오의 역할별 호출 횟수·순서와 실제 저장 상태를 함께 확인한다. 명세 무변경, 여러 작업에 적용되는 명세 변경, 현재 작업과 무관한 변경, 구현 부족/충족·검증 부족의 단계별 대응, 순수/혼합 기록 커밋과 기준 저장 전 중단, planning 중단·실패·게시 후 DB 미반영·원격 재전진을 포함한다. 정책 조합은 Git 관측·Agent 호출을 mock으로 제공하고 실제 판단·SQLite 반영을 검사하며, 실제 Git은 커밋·게시·rebase 효과의 연결 확인에 필요한 최소 회귀로 제한한다. 실제 모델 호출이나 전체 verify를 반복하는 측정은 완료 조건으로 추가하지 않는다.

## Product Impact

- Planner는 명세의 작업 구성·사용자 판단·전체 충족 확인을 담당하고 Worker는 선택된 작업의 최신 코드 적용·구현 적합성 판단·필요한 보완을 함께 담당한다. ExecPlan·코드 변경만의 점검·재계획 호출은 없다.
- 한 Requirement의 모든 작업이 실제 Merge되면 다음 안전한 경계에서 해당 조건을 바로 재확인하며, 다른 Requirement의 종료나 프로젝트 전체 완료까지 미루지 않는다.
- Requirement의 추가·수정·부분 철회가 실제 미충족 작업·공유 목표·문서와 현재 DB 관계에 일치하고 완료된 구현·감사는 보존된다.
- ExecPlan 갱신 가능 여부는 실행 이력보다 PR 등록 경계를 기준으로 판단한다.
- 명세 변경은 안전한 단계 경계에서 프로젝트 planning·게시·DB 반영을 먼저 완료하며, 현재 작업은 마지막 반영 ExecPlan의 조건 변경과 부족한 구현·검증에 맞춰 필요한 단계로 연결된다.
- 자체 진행 기록은 확인한 변경만 반영 기준에 포함하고 미확인 조건·기존 실행 근거와 구분해 중단 후에도 복구한다.
- 계획·작업 문서 충돌은 최신 base를 코드로 채택하고, 그 외 파일 충돌은 Worker가 최신 조건에 맞춰 해결한다.
- 변경된 완료 조건의 검증 근거와 최종 후보의 Review 없이 PR 게시를 승인하지 않는다.

## Non-Goals

- Merge 대기 ExecPlan의 요구 범위를 확장하거나 PR을 자동 Merge·Close하지 않는다.
- 진행 중 프로세스를 강제 중단하거나 같은 프로젝트의 작업·Planner를 병렬 실행하지 않는다.
- 일반 Planner에 코드·설정 수정 권한을 주거나 Reviewer의 읽기 전용·테스트 미실행 원칙을 바꾸지 않는다.
- 명세 변경의 선행 planning과 Requirement 완료 재확인 시점 외의 일반 작업 간 우선순위·사용자 승인 정책을 변경하지 않는다. 유지보수 주기는 R-074, CLI 요청은 R-076, 공통 Git 수용·통합·게시 분리는 R-055를 따른다.
