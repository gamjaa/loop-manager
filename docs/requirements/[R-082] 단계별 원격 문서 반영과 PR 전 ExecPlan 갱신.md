# [R-082] 단계별 원격 문서 반영과 PR 전 ExecPlan 갱신

## Context

PR 전 ExecPlan 개정과 stage_documents의 단계별 문서 반영은 이미 구현됐다. 같은 ID·작업물·기록 보존과 발견 단계별 대응을 유지하고 Planner 단계 경계의 갱신·정상 사용자 rebase 수용에 남은 조건만 보완한다.

원격 확인과 문서 관련성 판단은 후보 검증과 구분한다. ref 갱신만으로 차단하지 않고 실제 문서·후보·검증 입력 변화에 해당하는 단계만 다시 수행해야 한다.

현재 구현에는 진행 중 rebase 충돌과 Worker 구현 입력 변경이 함께 발견되면 기존 작업을 보존하고 최종 차단하는 경로가 남아 있다. 아래 충돌 복구 정책은 이 경로를 최신 base의 계획·작업 문서 자동 반영과 필요한 Worker 교정·재검증으로 연결하려는 변경 요구이며, 이미 구현된 동작이나 운영 문제의 해소를 뜻하지 않는다.

진행 중 작업은 최신 원격 문서에 맞춰 갱신하되, 문서 변경만으로 구현을 반복하지 않아야 한다. 이 Requirement는 [R-049](archive/%5BR-049%5D%20Input-Specific%20Planner%20Roles.md)의 미착수 READY 갱신 제한과 [R-051](archive/%5BR-051%5D%20Remote%20Change%20Rebase%20and%20Managed%20Work%20Resumption.md)의 Worker·Reviewer 문서 재확인 범위를 아래 정책으로 변경한다. [R-072](%5BR-072%5D%20Reuse%20Successful%20Candidate%20Results%20with%20Proven%20Inputs.md)의 입력 증명·성공 근거 재사용은 유지하되, 관련 문서 변경에 따른 단계 선택은 이 Requirement를 따른다.

## Requirement

### ExecPlan 갱신 경계

- 일반 Planner는 PR 등록 전인 ExecPlan을 관련 Requirement 변경에 맞춰 갱신한다. 최초 실행 여부, READY 복귀, 기존 branch·worktree·세션 또는 원격 checkpoint 존재만으로 갱신 대상에서 제외하지 않는다.
- 진행 중 작업의 갱신은 같은 ExecPlan ID와 작업물·세션·실행 및 실패 이력을 보존한다. 이미 수행한 구현·검증 기록과 새 조건의 미충족 부분을 구분하며, 문서 갱신 자체를 작업 완료나 과거 실패 해소로 기록하지 않는다.
- PR 등록 후 Merge를 기다리는 ExecPlan은 새 요구사항을 반영하기 위해 수정하지 않는다. 추가·변경 요구사항의 미충족 범위는 새 ExecPlan으로 작성하며 기존 작업과의 중복·dependency는 기존 카탈로그 규칙으로 확인한다.
- PR 경계는 연결 PR의 실제 등록 여부로 판단한다. SQLite에 아직 반영되지 않은 PR도 갱신 금지에 포함한다. 갱신 결과 적용 전에 PR이 등록됐으면 이전 갱신 권한으로 기존 작업을 덮어쓰지 않고 새 ExecPlan 경로로 다시 판단한다.
- 진행 중 Agent나 검증 프로세스를 중단하거나 같은 worktree를 동시에 수정하지 않는다. 종료 후 다음 단계 진입 전의 안전한 경계에서 필요한 갱신·게시·작업 branch 반영을 완료하고 최신 작업 문서를 입력으로 사용한다.

### 원격 확인과 변경 관련성

Planner도 최초 입력을 전체 주기 동안 고정하지 않고 진입·종료·교정·게시 전의 안전한 경계에서 최신 원격 원본을 확인한다. Agent와 같은 worktree에 pull/rebase를 겹치지 않으며 갱신된 명세·ExecPlan으로 기존 ID와 작업 결과를 보존해 재평가한다. 단계 중 동시 원격 변경은 종료 후 재관측하고 오래된 판단을 그대로 게시하지 않는다.

Manager는 Worker, Manager verify, Reviewer 진입 전에 등록된 origin의 최신 원본 branch와 현재 작업 branch를 확인한다. 재시도·교정·중단 후 재개도 같은 진입 기준을 따른다. 로컬 원본 branch와 기본 checkout의 미커밋 변경을 원격 기준으로 대신하지 않는다.

로컬 작업 수용·원격 작업 통합·게시 권한은 R-055대로 분리한다. 로컬을 원격 원본 위로 정상 rebase했으면 과거 원격 작업 tip의 조상 관계만으로 거부하지 않는다. 새 원격 작업은 기존 통합·보존 경계로 연결하며 바뀐 후보·문서·검증 입력을 대조해 아래와 같이 처리한다.

| 변경 종류 | 처리 |
|---|---|
| 현재 작업과 무관한 문서 변경 | rebase 후 하던 단계를 계속한다. 문서가 변경됐다는 이유로 재계획하거나 Worker를 다시 호출하지 않는다. |
| 현재 작업 대상 문서 변경 | 변경 내용을 최신 작업 문서에 반영하고 아래 단계별 대응을 적용한다. |
| 코드·테스트·설정 등 구현·검증 입력 변경 | 기존 rebase·충돌 복구·후보 검증 무효화 및 증명된 결과 재사용 규칙을 적용한다. |
| 문서와 코드 변경이 함께 있음 | 관련 문서의 단계별 대응과 코드 변경의 기존 검증 규칙을 함께 적용한다. |

작업 대상 문서는 현재 ExecPlan, 연결된 Requirement와 현재 작업에 적용되는 PRODUCT·ARCHITECTURE 등 상위 명세를 포함한다. ExecPlan 파일이 그대로이거나 상위 명세가 `sources`에 직접 나열되지 않았다는 이유로 적용 규칙의 변경을 무시하지 않는다. 파일 위치만으로 관련성을 확정하지 않고 실제 변경이 현재 작업의 목표·구현 범위·제약·완료 조건에 미치는 영향을 판단한다.

새 명세 변경의 현재 작업 영향을 다음 작업 선택 경계까지 일괄 미루지 않는다. 현재 작업에 필요한 갱신과 다음 단계 판단을 먼저 수행하되, 다른 작업의 선택·우선순위와 일반적인 신규 작업 계획 순서는 기존 정책을 유지한다.

### 발견 단계별 대응

| 변경 확인 시점 | 처리 |
|---|---|
| Worker 진입 전 | 필요한 ExecPlan 갱신과 rebase를 마친 최신 작업 문서를 Worker 입력으로 전달한다. 기존 세션을 재개할 때도 변경된 조건을 반영한다. |
| Manager verify 진입 전 | 최신 문서와 현재 구현을 대조한다. 변경된 구현 범위·완료 조건을 충족하려면 구현 보완이 필요한 경우 Worker로 돌아가 교정한 뒤 verify한다. 구현 보완이 필요 없으면 Worker를 반복하지 않고 최신 조건에 필요한 verify를 진행한다. |
| Reviewer 진입 전 | 문서 변경을 반영한 뒤 최신 문서·현재 구현·실제 verify 근거로 Reviewer를 먼저 진행한다. 구현 부족은 Worker 교정으로, 검증 부족은 필요한 테스트·검증 근거 보완과 Manager verify로 연결한다. 문서 변경이나 이전 verify 근거의 유효성 상실만으로 Reviewer를 건너뛰어 Worker를 무조건 호출하지 않는다. |

Reviewer에는 기존 verify가 확인한 후보·입력·조건과 새 조건에 대한 검증 여부를 구분해 전달한다. 이전 문서 기준의 PASS만 남아 있으면 참고 근거로 제공하되, 변경된 조건의 검증 성공으로 표시하지 않는다. 검증만 부족한 결과를 구현 부족으로 일괄 처리하지 않으며, 필요한 테스트 작성·수정·실행은 기존 역할의 권한과 책임을 따른다.

### rebase 충돌과 구현 조건 변경

Worker의 최초 진입·재개·교정 진입은 필요한 일반 Planner 갱신·게시 후 최신 base의 작업 조건을 작업 branch에 반영하는 순서로 진행한다. Manager가 rebase를 수행하고 아래 기준으로 충돌을 분리한다. 계획·작업 문서는 Requirement·ExecPlan을 뜻하며 PRODUCT·ARCHITECTURE·공통 지침과 그 밖의 문서·코드·테스트·설정은 그 외 파일에 속한다.

| 충돌 대상 | 처리 |
|---|---|
| Requirement·ExecPlan | Manager 코드가 관측한 최신 base의 내용·경로·삭제를 채택한다. 작업 branch의 오래된 조건을 병합해 되살리지 않는다. 문서 처리가 복잡하거나 진행 기록을 안전하게 병합하기 어려우면 대상 파일 전체를 최신 base 원문으로 교체할 수 있다. |
| 그 외 파일 | 기존 단계가 verify·Review·게시여도 Worker 충돌 교정으로 돌아간다. Manager가 base나 작업 형상을 일괄 선택해 해결하지 않는다. Worker가 최신 조건에 맞춰 양쪽 형상을 검토하고 해결·수정·targeted test를 수행한다. |

최신 base는 필요한 Planner 갱신이나 사용자 변경이 이미 원격에 반영된 immutable revision으로 확인한다. rebase의 ours/theirs 명칭만으로 어느 쪽이 이 기준인지 판단하지 않는다. 문서 채택·전체 교체는 해당 계획·작업 파일에 한정하며 branch·코드·index 전체를 reset하지 않는다. 교체 전 문서와 작업 형상은 기존 checkpoint·복구 근거로 보존하고, branch·worktree·session·실행 및 실패 이력을 폐기하지 않는다. 작업 branch에만 있던 문서 진행 표시는 최신 base 원문으로 대체될 수 있지만, 이전 수행 사실을 지우거나 base의 체크 표시를 현재 후보의 성공 증거로 채택하지 않는다. 삭제·archive·rename, source·dependency와 실제 PR 경계를 확인하고 삭제된 문서를 임의로 복원하지 않는다. 현재 작업의 유효성을 확정하지 못하면 해당 범위의 기존 판단·보존 경로를 따른다.

Worker는 이미 채택된 Planner·사용자의 최신 계획·작업 문서를 입력으로 최신 base와 보존된 작업 형상을 대조한다. 코드 충돌은 한쪽 형상 전체를 관례적으로 선택하지 않고 최신 목표·제약·완료 조건에 맞춰 필요한 변경을 선택·결합한다. 이전 조건으로 문서를 되돌리거나 Planner 갱신·문서 교체만으로 기존 코드의 적합성을 확정하지 않는다. 계획·작업 문서 충돌만 코드로 해소됐다면 문서 충돌 자체를 이유로 Worker를 호출하지 않고 위 발견 단계별 대응을 따른다. Worker·Reviewer는 각자의 단계에서 실제 구현·검증 근거로 진행 상황과 미충족 조건을 재점검하며, Reviewer의 읽기 전용 권한은 유지한다.

소유한 rebase에서 ExecPlan 본문·sources·연결 명세·archive 범위·공통 지침 등 구현 입력이 바뀌었다는 사실만으로 최종 차단하지 않는다. Manager가 변경된 조건·문서 교체·적용 revision·남은 충돌과 유효한 과거 근거를 구분해 전달하고 필요한 Worker 교정·검증으로 연결한다. dependency 미충족은 실행 준비 조건으로 별도 처리하며 충돌 교정을 이유로 우회하지 않는다. SHA만 바뀌거나 확인 가능한 진행 기록만 바뀐 경우에는 R-072의 입력 비교·재사용 정책을 유지한다.

진행 중 rebase의 target을 새 원격 OID로 덮어쓰거나 두 번째 rebase를 겹치지 않는다. 기존 소유 operation과 원형을 보존해 완료·복구한 뒤 남은 최신 base 반영을 이어간다. 이전 정의 snapshot이 없어도 현재 작업의 identity·소유권·최신 조건과 보존된 작업을 확인할 수 있으면 과거 성공은 재사용하지 않고 교정·검증으로 연결한다. 실제 소유권·범위·문서 유효성·필수 사용자 결정이 불확실하거나 허용된 교정에서 진전이 없으면 기존 한도에 따라 영향받는 작업만 최종 차단한다. 사용자 operation을 임의 중단하거나 원형을 폐기해 복구하지 않는다.

이 사유로 이미 차단된 작업도 같은 현재 근거로 재평가한다. 안전한 교정 경로가 확인되면 해당 차단 원인만 해제하고 기존 branch·worktree·session·실패 이력을 이어간다. 입력 변화 없이 같은 불일치를 다시 검사해 차단하는 순환이나 무한 Worker 호출을 만들지 않는다. 최신 조건의 targeted test·필요한 Manager verify·최종 후보 Review와 기존 게시 안전 조건이 충족되기 전에는 구현 완료나 PR 게시를 승인하지 않는다.

### 검증 근거와 완료 조건

문서 변경은 단계별 영향 판단의 입력이며 Worker 재호출의 충분조건이 아니다. 반대로 구현 코드나 verify 명령이 같다는 사실만으로 이전 성공을 새 완료 조건의 성공으로 간주하지 않는다. 변경된 조건까지 기존 검증이 충족한다는 근거가 없으면 필요한 검증을 보완한다.

이전 성공을 재사용하려면 R-072의 실제 입력·작업 주기·후보 연결 조건과 최신 완료 조건에 대한 근거가 충족돼야 한다. 무관한 문서 변경 뒤에도 후보나 실제 검증 입력이 바뀌면 기존 검증 규칙을 적용한다. 문서 관련성이 없다는 판단이 후보 검증을 면제하지 않는다.

Reviewer를 먼저 진행한 결과가 구현 부족이면 Worker 교정 후 필요한 verify·Review를 거친다. 검증 부족이면 필요한 검증을 보완하고 최종 후보의 Review 근거를 다시 판단한다. 최신 조건의 구현·검증과 최종 후보의 유효한 Review가 충족되기 전에는 PR 게시를 승인하지 않는다. 게시 직전의 원격 재확인과 기존 PR·lease·checkpoint 안전 조건도 유지한다.

### 실패와 중단 후 재개

- 원격 확인·갱신·rebase·관련성 판단에 실패하거나 적용 조건을 확정할 수 없으면 무관한 변경 또는 반영 완료로 간주하지 않는다. 현재 작업과 원인을 보존하고 기존 재시도·복구·사용자 판단 경로를 따른다.
- 문서 갱신·반영 중 원격 내용이나 대상 PR 경계가 바뀌면 오래된 판단을 적용하지 않고 최신 상태에서 다시 확인한다. 충돌은 위 충돌 교정 절차로 연결하고, 문서 부재·불명확한 source 또는 dependency는 기존 검증과 차단 규칙을 따른다.
- 중단 후에는 반영한 원격 기준, 갱신된 작업 문서, 남은 보완과 실제 완료 근거를 대조해 필요한 단계부터 재개한다. 이미 확정된 갱신·게시·rebase를 반복하지 않으며, 원격이 그대로라는 이유로 남은 구현·검증 보완을 건너뛰지 않는다.
- 문서 변경 또는 rebase 완료만으로 사용자 승인 대기, 명세 충돌, 독립적인 차단·실패 원인이나 실패·Worker level 이력을 초기화하지 않는다.

## Acceptance Criteria

- Planner의 진입·종료·교정·게시 경계마다 최신 원격 명세·ExecPlan을 확인한다. 작성 중 갱신은 writer 종료 뒤 반영하며 기존 ID·결과·실패 이력을 불필요하게 폐기하지 않는다.

- 실행 이력이 있는 READY와 IMPLEMENTING·VERIFYING·REVIEWING 상태의 PR 미등록 ExecPlan은 관련 Requirement 변경에 따라 같은 ID로 갱신할 수 있다. 기존 branch·worktree·세션·원격 checkpoint만으로 대상에서 제외되지 않으며 작업물과 실행 이력이 보존된다.
- PR 등록 후 Merge 대기 중인 ExecPlan에는 추가·변경 요구사항을 덧붙이지 않는다. 미충족 범위는 새 ExecPlan으로 작성하고 기존 계획·PR과의 중복·dependency를 확인한다.
- 갱신 대상 선정 뒤 실제 PR이 등록되거나 SQLite에 미기록인 연결 PR이 발견되면 기존 ExecPlan 갱신을 적용하지 않고 PR 이후 정책을 따른다.
- Worker·Manager verify·Reviewer의 최초 진입, 교정 재진입과 중단 후 재개에서 최신 원본·작업 branch를 확인한다. 실행 중인 프로세스와 worktree 변경을 겹치지 않는다.
- 원격 작업 branch 변경과 정상 원격 원본 기준 로컬 rebase를 R-055대로 수용·통합·게시로 나눠 판단한다. branch 삭제·재작성은 로컬 작업을 보존하고 해당 원격 통합·게시를 보류하며 무검증 덮어쓰기를 허용하지 않는다.
- 각 진입 시점에서 현재 작업과 무관한 문서만 변경됐으면 rebase 후 해당 단계를 계속하며, 문서 변경만을 사유로 Planner·Worker를 반복하지 않는다. 실제 후보·검증 입력 변경은 기존 검증 규칙을 따른다.
- ExecPlan이 그대로여도 연결 Requirement 또는 적용 상위 명세가 현재 작업의 조건을 바꾸면 각 단계에서 반영한다. 다음 작업 선택 경계까지 미루거나 `sources` 직접 나열 여부만으로 제외하지 않는다.
- Worker 진입 전 관련 문서가 변경되면 최초·재개 Worker 모두 갱신·rebase가 완료된 최신 문서를 입력으로 구현한다.
- verify 진입 전 새 조건에 필요한 구현이 부족하면 Worker 교정 후 verify하며, 구현이 이미 충족된 문서 변경이면 Worker를 호출하지 않고 필요한 verify를 진행한다.
- Reviewer 진입 전 관련 문서가 변경되면 최신 문서·현재 구현·기존 verify가 확인한 범위와 새 조건의 검증 상태를 제공해 Reviewer를 먼저 진행한다. 과거 verify의 유효성 상실만으로 이 Review를 생략하지 않는다.
- 위 Review에서 구현 부족이 확인되면 Worker 교정으로 연결한다. 구현 부족 없이 검증만 부족하면 필요한 검증 보완으로 연결하며, 검증 부족을 무조건 구현 교정으로 처리하지 않는다. Reviewer 자체는 테스트·verify를 실행하거나 파일을 수정하지 않는다.
- 완료 조건만 추가되고 코드·verify 명령이 같아도, 추가 조건의 검증 근거가 없으면 이전 PASS를 새 조건의 성공으로 재사용하거나 PR을 게시하지 않는다. 기존 성공을 재사용한 경우에는 최신 조건 충족과 R-072의 입력 증명 근거를 확인할 수 있다.
- 관련 문서와 코드가 함께 변경됐거나 rebase 충돌이 발생하면 단계별 문서 대응과 기존 코드 검증·충돌 복구를 함께 적용한다. 최신 후보에 필요한 구현·검증·Review가 끝나기 전에 PR을 게시하지 않는다.
- Worker 최초·재개·교정 진입 전에 필요한 Planner 갱신·게시와 최신 base 반영을 수행한다. Requirement·ExecPlan 충돌은 Manager 코드로 최신 base를 채택하고, 그 외 파일 충돌은 이전 단계와 관계없이 Worker 교정으로 연결한다. Git operation의 계속 진행·완료는 Manager가 수행한다.
- rebase 중 구현 입력이 달라져도 안전한 소유권·유효한 최신 조건을 확인할 수 있으면 최종 차단 대신 기존 코드를 보존한 Worker 교정·targeted test·필요한 verify·Review를 수행한다. 본문·sources·연결 명세·archive 범위·공통 지침 변화와 코드 충돌이 함께 있는 경우를 포함한다.
- Requirement·ExecPlan 충돌에서 필요한 Planner 갱신 또는 사용자 변경이 반영된 최신 base의 내용·경로·삭제를 채택한다. 병합이 어렵다면 해당 파일 전체를 base 원문으로 교체해도 이전 문서 원형·코드·세션·실행 및 실패 이력이 보존된다. branch·코드·index 전체 reset은 하지 않으며 삭제·archive·rename·dependency·PR 경계는 기존 유효성 검사로 확인한다.
- 계획·작업 문서 충돌만 자동 해소되면 문서 충돌 자체로 Worker를 반복하지 않고 단계별 재점검을 적용한다. 그 외 파일과의 혼합 충돌은 Worker로 돌아가 최신 문서를 기준으로 양쪽 형상을 검토·선택·결합하고 관련 targeted test를 수행한다. base 문서의 진행 표시를 현재 후보의 성공으로 간주하지 않으며 필요한 verify·Review 없이 게시하지 않는다.
- 이전 snapshot이 없으면 과거 성공을 재사용하지 않되 현재 소유권·조건이 확인된 작업은 교정·검증으로 이어간다. 소유권 불확실·문서 무효·사용자 결정·진전 없는 반복은 안전 차단하고 dependency 미충족과 사용자 operation을 우회하지 않는다.
- 충돌 교정·문서 반영·차단 재평가 중 재시작하거나 원격이 다시 전진해도 진행 중 rebase target과 원형을 보존한다. 같은 불일치의 반복 차단·무한 교정·중복 반영 없이 남은 단계부터 이어가며 독립적인 차단·승인을 해제하지 않는다.
- 갱신·rebase·단계 판단 후 중단돼도 재시작 시 작업물·세션·실패 이력을 보존해 필요한 단계부터 이어간다. 동일한 원격 변경을 중복 적용하거나 미완료 보완을 완료로 기록하지 않는다.
- 원격 확인 실패·판단 불확실·갱신 중 원격 변경에서는 오래된 입력으로 다음 단계를 시작하지 않는다. 기존 복구·차단 정책을 따르며 승인 대기와 독립적인 실패 원인을 보존한다.

## Product Impact

- ExecPlan 갱신 가능 여부는 실행 이력보다 PR 등록 경계를 기준으로 판단한다.
- 현재 작업에 적용되는 원격 문서는 각 단계 진입 시 반영되고, 부족한 구현·검증에 맞춰 필요한 단계로 연결된다.
- 계획·작업 문서 충돌은 최신 base를 코드로 채택하고, 그 외 파일 충돌은 Worker가 최신 조건에 맞춰 해결한다.
- 변경된 완료 조건의 검증 근거와 최종 후보의 Review 없이 PR 게시를 승인하지 않는다.

## Non-Goals

- Merge 대기 ExecPlan의 요구 범위를 확장하거나 PR을 자동 Merge·Close하지 않는다.
- 진행 중 프로세스를 강제 중단하거나 같은 프로젝트의 작업·Planner를 병렬 실행하지 않는다.
- 일반 Planner에 코드·설정 수정 권한을 주거나 Reviewer의 읽기 전용·테스트 미실행 원칙을 바꾸지 않는다.
- 다른 작업의 선택·우선순위, 유지보수 주기와 사용자 승인 정책을 변경하지 않는다. 공통 Git 수용·통합·게시 분리는 R-055를 따른다.
