# [R-071] 남은 규칙 기반 작업의 Manager 처리

## Context

확정된 ID·dependency·파일명·형식·객관적 사실은 Manager 코드가 처리하고 의미 판단은 기존 Agent 역할에 남긴다. 이런 정보를 모델에게 다시 작성시키면 불필요한 호출과 교정이 발생한다. 새 ExecPlan 충돌 교정, 유지보수 barrier 추가와 결과 형식 처리뿐 아니라 Requirement의 중복 R ID·제목·파일명 교정에도 같은 원칙을 적용한다.

이 문서는 archive된 [R-063](archive/%5BR-063%5D%20Manager-Owned%20Deterministic%20Work%20and%20Minimal%20Model%20Use.md)의 목표 중 이후 명세로 대체되지 않은 범위를 유지한다. 관련 계획의 Merge만으로 전체 기준 충족을 추정하지 않으며, Requirement 완료 판단과 이동은 [R-068](archive/%5BR-068%5D%20Planner%20Judgments%20and%20Manager-Owned%20Requirement%20Retirement.md)의 정책을 따른다. 파일명 교정 뒤에도 기존 ExecPlan의 source 조회와 Requirement 보관 관계가 유지돼야 한다.

## Requirement

### ExecPlan·barrier·결과 형식과 확정 사실

- Manager는 아직 게시·등록하지 않은 새 ExecPlan batch의 ID·경로 충돌을 고유 ID·경로로 교정하고, 그 batch 안에서 대상이 확정된 구조적 dependency를 함께 갱신한다. 활성·archive·등록·취소·예약된 ID를 재사용하지 않는다. 기존 게시·등록·실행 계획과 사용자 변경은 보존한다.
- 서로 다른 목표가 같은 ID로 제시되거나 본문 참조의 대상을 확정할 수 없으면 기계적 교정으로 의미를 선택하지 않는다. 해당 모호함만 기존 Planner 판단 또는 사용자 결정 절차에 남긴다.
- 유지보수 Planner는 리팩터링 필요성·범위와 DAG를 판단한다. Manager가 검증된 DAG의 모든 말단을 활성 barrier mode의 적격 미착수·무소유 READY snapshot에 dependency로 추가한다. 기존 ID·경로·본문·다른 metadata와 dependency 순서는 보존한다. 사후 구조 변경에 맞춘 의미 있는 계획 개정은 기존 Planner 역할로 남긴다.
- Worker·Reviewer·Planner·모듈 검토의 실제 결과 경로에서 의미가 하나로 확정되는 표식 배치·구분자·공백 차이는 Manager가 정규화한다. 확정된 대상·ID·revision·manifest·digest·링크는 검증된 호출 입력으로 결합한다. 이 형식 처리만을 위한 모델 호출이나 구현·Review 실패 횟수 증가, Worker level 승격을 만들지 않는다.
- 상충하는 verdict, 명시적 대상 identity 불일치, 누락된 판단·issue·원본 인용·필수 검증 근거는 성공 결과로 보충하지 않는다. 실제로 부족한 의미 판단은 기존 해당 역할의 교정 절차로 처리한다.
- 기존 증분 코드맵과 읽기 전용 조회를 재사용한다. 남아 있는 빈 파일·공백 chunk의 객관적 사실 설명과 이미 계산된 관계·manifest·digest·링크의 재작성만을 위한 모델 호출을 제거한다. 미지원 형식·파싱 실패·동적 또는 미확인 관계는 확정된 사실로 만들지 않는다. 빈 파일을 포함하는 의미 있는 모듈 검토는 유지한다.

### Requirement 번호 배정과 중복 문서 선택

Manager는 최신 원격 기본 브랜치의 문서와 작업 관계를 확인한 안전한 처리 경계에서 활성 Requirement의 중복 R ID를 검사한다. 이 검사·선택·교정과 제목에 따른 파일명 변경은 코드만으로 수행하며, 이 처리를 위해 Planner나 다른 모델을 호출하지 않는다.

- 새 번호는 활성·archive 전체에서 사용 중인 가장 큰 R 번호 다음부터 배정한다. 여러 대상에는 파일명 텍스트 오름차순으로 다음 번호를 차례로 배정한다. 중간 빈 번호를 채우거나 기존 고유 ID를 재번호화하지 않으며, 번호가 연속되지 않는다는 이유로 오류를 발생시키지 않는다.
- 기존 ExecPlan이 source로 참조한 Requirement는 ID를 우선 보존한다. 작업의 초안·미착수·실행·완료·보관 여부만으로 참조를 무시하지 않으며, 게시된 작업 문서와 저장된 작업 관계를 대조한다. 관계를 확인하지 못한 문서를 참조 없는 문서로 간주하지 않는다.
- archive된 Requirement는 번호 배정과 참조 확인에 포함하지만 자동 교정 대상으로 수정·rename·복원하지 않는다. 이미 보관된 ExecPlan도 수정하지 않는다.

중복 문서의 선택은 다음 우선순위를 따른다.

| 조건 | 처리 |
|---|---|
| archive 문서와 참조 없는 활성 문서가 중복 | archive를 보존하고 활성 문서에 새 ID를 배정한다. |
| 활성 중복 문서 중 하나만 기존 작업에서 참조됨 | 나중에 푸시됐어도 참조된 문서의 ID를 유지하고 참조 없는 문서를 변경한다. |
| 여러 중복 문서가 기존 작업에서 참조됨 | 참조된 문서의 ID와 정확한 경로 관계를 보존한다. 참조 없는 문서는 새 번호로 교정할 수 있으나 참조된 문서끼리 임의로 재번호화하지 않는다. |
| 어느 활성 중복 문서도 기존 작업에서 참조되지 않음 | 원격 기본 브랜치에 해당 ID로 먼저 반영된 문서를 유지하고 나중에 반영된 문서를 변경한다. |
| 참조가 없고 원격 반영 순서도 구분되지 않음 | 파일명을 텍스트 오름차순으로 정렬해 첫 문서를 유지하고 뒤의 문서를 변경한다. |

원격 반영 순서는 기본 브랜치에 실제 포함된 이력을 기준으로 하며, 작성 시각·로컬 파일 수정 시각을 푸시 순서로 간주하지 않는다. 파일명 정렬은 실행 환경의 언어나 locale에 따라 달라지지 않는다. archive끼리의 과거 중복은 문서를 변경하지 않고 아래 source 조회 규칙으로 구분한다.

### Requirement 제목과 파일명 동기화

활성 Requirement의 첫 제목 `# [R-ID] 제목`을 기준으로 파일명을 `[R-ID] 제목.md`에 맞춘다. 제목만 바뀌면 R ID는 유지하고 파일명만 변경한다. 중복 교정으로 ID를 바꾸면 첫 제목의 ID와 파일명에 같은 새 ID를 반영하고, 요구사항·Acceptance Criteria의 내용은 보존한다.

수정 가능한 문서에서 대상이 확정된 상대 링크는 rename과 함께 갱신한다. 문서의 의미나 모호한 본문 참조를 추론해서 바꾸지 않는다. 제목이 파일명으로 사용할 수 없거나 목적지에 다른 파일이 있으면 덮어쓰거나 임의 제목으로 대체하지 않고 해당 변경과 이유를 보존한다. 제목 누락·형식 오류도 모델로 보충하지 않는다. 기존 source를 rename 뒤에도 같은 문서로 고유하게 연결할 수 없으면 원래 경로를 보존하고 해당 rename만 보류한다.

### 기존 Requirement source 조회와 작업 관계 보존

ExecPlan의 `sources`에는 기존 경로 문자열을 유지한다. 조회 시에는 다음 순서로 실제 Requirement를 확인하며, R ID를 추출할 수 없는 기존 source는 종전의 정확한 경로 조회를 유지한다.

1. 기록된 활성 경로에 유효한 문서가 있으면 그 문서를 사용한다. R ID가 중복이어도 정확한 경로를 임의의 다른 문서로 바꾸지 않는다.
2. 활성 경로가 없고 기존 작업의 archive 조회가 허용되는 경우에는 같은 파일명의 archive 경로를 확인한다.
3. 제목 변경으로 위 경로에서 찾지 못하면 source 파일명에서 R ID를 추출해 같은 ID의 문서를 찾는다. 후보가 하나로 확정된 경우에만 현재 경로로 연결하며, archive 후보는 기존 작업에 허용된 조회에서만 사용한다.
4. 후보가 없으면 문서 부재로, 둘 이상이면 모호한 참조로 처리한다. 파일명 정렬이나 최신 문서라는 이유로 source 대상을 선택하지 않는다. 기존에 정확한 경로로 확인된 참조는 유지하고 구분되지 않는 참조에만 기존 오류·보류 정책을 적용한다.

이 규칙을 source 유효성 검사, 실제 문서 읽기, 관련 작업의 연결, 입력 지문과 Requirement 최종 판단·archive 자격 확인에 일관되게 적용한다. rename 뒤에도 기존 비종료 작업이 같은 Requirement를 참조한다는 사실을 유지하며, 파일명 변경만으로 관련 작업이 없는 것으로 판단하거나 Requirement를 완료·보관하지 않는다.

R ID 추출은 기존 경로 형식·일반 파일·허용 범위 검증을 대체하지 않는다. 새 ExecPlan은 계속 활성 Requirement만 source로 사용한다. 실제 문서 내용 변경에는 기존 영향 판단·입력 지문·검증 결과 재사용 조건을 적용하며, 같은 R ID라는 이유로 과거 성공을 재사용하지 않는다.

### 게시와 중단 후 재개

- 자동 편집은 허용된 관리 작업 공간과 최신 snapshot에서 수행한다. 원격·snapshot·소유권이 바뀌거나 cycle·대상 이탈이 발견되면 게시를 보류하고 작업물을 보존한다. 중단 뒤 실제 파일·Git 결과와 저장 상태를 대조해 같은 ID 배정·dependency 추가·게시를 중복 적용하지 않는다.
- Requirement의 확정된 ID·제목·파일명 교정과 필요한 링크 변경은 같은 문서 교정 commit으로 원격 기본 브랜치에 push한다. 기본 checkout의 사용자 수정과 실행 중인 작업을 덮어쓰지 않으며, 관련 ExecPlan의 ID·branch·세션·실행 이력·기존 차단과 사용자 결정을 보존한다.
- 게시 직전 원격 기준, 문서 내용, 작업 참조와 목적지 충돌을 다시 확인한다. 새 참조나 원격 변경이 발견되면 오래된 번호 배정·rename을 게시하지 않고 현재 기준으로 재검사한다. push 실패나 중단에서는 작업물과 게시 근거를 보존하고 기존 재시도·복구 경로를 따른다. 강제 push로 원격을 덮어쓰지 않는다.
- 이미 원격에 반영된 교정을 다시 번호 배정하거나 빈 commit·중복 push로 반복하지 않는다. 원격 게시를 확인하기 전에는 로컬 rename만으로 source 변경·교정 완료를 확정하지 않는다.
- 기존 fast·targeted·full 유지보수, 성공 모듈 결과 재사용, 필요한 일반 계획·최종 문서 전문 확인·Review·사용자 승인과 게시 검증을 유지한다. 자동 변경은 해당 게시 절차의 실제 diff와 검증·검토 대상에 포함한다.

## Acceptance Criteria

### ExecPlan·barrier·결과 처리

- 게시 전 새 batch의 ID·경로 충돌과 확정된 내부 dependency가 추가 Planner 호출 없이 교정된다. 기존·취소·예약 ID와 사용자 변경은 보존되며, 경쟁 게시에서도 중복 ID가 등록되지 않는다.
- 모호한 본문 참조와 서로 다른 목표의 충돌은 임의로 해소되지 않고 필요한 의미 판단으로 남는다.
- 검증된 리팩터링 DAG의 모든 말단이 적격 READY snapshot에 Manager 코드로 반영된다. 기존 dependency 순서·본문·metadata가 보존되고, 소유된 계획·cycle·범위 밖 편집은 거부된다.
- 의미가 명확한 결과 형식 차이는 추가 모델 호출 없이 처리된다. 상충 verdict·누락·identity 불일치·허위 근거는 성공으로 바뀌지 않으며 실제 내용 교정이 유지된다.
- 빈 파일·공백 chunk의 사실 설명과 확정된 정형 정보 재작성만을 위한 모델 호출은 없다. 필요한 모듈 의미 검토와 불확실한 분석의 보수적 처리는 유지된다.

### Requirement ID·파일명·참조

- 활성·archive의 최대 번호가 R-010이고 R-002 등이 비어 있어도 오류 없이 기존 ID를 유지하며, 중복 교정에는 R-011부터 배정한다. 여러 대상에는 같은 파일명 정렬 순서로 R-011, R-012 등을 배정한다.
- 나중에 푸시된 중복 문서만 기존 ExecPlan에서 참조된다면 그 ID를 유지하고 먼저 푸시된 참조 없는 문서를 변경한다. 참조 확인 실패를 참조 부재로 간주하지 않는다.
- 참조 없는 중복 문서는 원격 반영 순서로 선택하며, 같은 반영 시점 또는 순서 불명확에서는 locale과 무관한 파일명 텍스트 정렬로 뒤의 문서를 변경한다.
- 양쪽 모두 기존 작업에서 참조되거나 archive끼리 중복이면 ID·문서를 보존한다. 정확한 기존 경로는 계속 조회되며, 후보가 여러 개인 ID 조회만 모호한 참조로 남는다. 기존 참조를 같은 문서로 유지할 수 없는 rename은 해당 문서에 한해 보류한다.
- 활성 Requirement의 제목 변경은 ID를 유지한 파일명 변경과 push로 이어진다. 중복 ID 교정에서는 첫 제목과 파일명이 같은 새 ID를 사용하며 나머지 요구사항 내용은 보존된다. 제목 누락·사용 불가 파일명·목적지 충돌을 임의 보충이나 덮어쓰기로 해소하지 않는다.
- rename 뒤에도 기존 `sources`를 수정하지 않고 고유한 R ID로 현재 문서를 읽을 수 있다. 제목이 바뀐 문서의 source 검증·읽기·관련 작업 조회·입력 지문·archive 판단이 같은 문서를 사용한다.
- 보관된 ExecPlan과 Requirement는 수정되지 않는다. 기존 작업의 archive 조회는 유지되고, 새 ExecPlan의 archived source는 계속 거부된다.
- 파일명 변경만으로 작업 연결·세션·실패 이력을 초기화하거나 비종료 작업이 연결된 Requirement를 archive하지 않는다. 내용 변경은 기존 검증·재사용 기준으로 확인한다.

### 공통 게시·복구와 모델 호출

- 재시작·중복 처리·원격 경쟁에서 기계적 편집이 중복 적용되지 않고, 기존 작업물·사용자 결정·독립 차단과 최신 게시 gate가 보존된다.
- 원격 경쟁과 새 작업 참조 발견에서 보호 대상과 번호 배정을 다시 확인하며, push 실패·게시 전후 중단·재시작에도 작업물을 보존하고 중복 번호 배정·commit·push를 만들지 않는다.
- 실제 모델을 호출하지 않는 검증으로 생략된 호출과 필요한 호출의 유지, 실제 자동 diff의 검증·Review 포함 여부를 확인할 수 있다.
- Requirement 번호 검사·선택·ID 교정·제목 기반 rename과 source 해석에 실제 모델 호출이 없다.

## Product Impact

- 확정된 ID·dependency·파일명·형식·객관적 사실은 Manager가 처리하고 의미 판단은 기존 Agent 역할에 남긴다.
- Requirement 번호의 중간 공백을 허용하고 기존 작업의 참조를 보호하며, 파일명이 제목에 맞게 바뀌어도 근거 조회와 보관 관계를 유지한다.
- 규칙 기반 처리 때문에 작업물 보존·필수 검증·Review·사용자 판단을 약화하지 않는다.

## Non-Goals

- R-063의 마지막 구현 PR에서 Requirement를 archive하던 조건을 복원하지 않는다.
- 기존 ExecPlan의 목표·ID와 Requirement의 의미·완료 조건을 변경하거나 AGENTS의 Agent 쓰기 권한을 확대하지 않는다. Requirement의 ID 변경은 위에서 정한 참조 없는 중복 문서 교정으로 제한한다.
- 중간 빈 번호 채우기, 전체 Requirement 재번호화와 보관 문서의 수정·복원을 하지 않는다.
- 종전 파일·관계·종합 평가 단계를 새 기본 유지보수 흐름으로 복원하지 않는다.
- 새 Agent·외부 서비스·병렬 실행을 추가하지 않는다.
- 기존 활성 Requirement가 다루는 세션 feedback 축소·권한·draft 정책을 중복 구현하지 않는다.
