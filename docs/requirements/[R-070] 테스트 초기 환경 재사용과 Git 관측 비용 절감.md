# [R-070] 테스트 초기 환경 재사용과 Git 관측 비용 절감

## Context

Loop Manager 자체 verify에서 느린 테스트들이 반복하는 공통 준비·관측·복구 경로의 비용을 줄인다. 기존 조회 통합과 일부 시나리오 축소 뒤에도 오류 변형마다 넓은 lifecycle을 반복하고, 한 처리 구간의 하위 함수들이 같은 상태를 다시 관측한다. 전체 snapshot은 선택된 worktree 외에 다른 등록 worktree의 상태도 수집하므로 호출 하나가 여러 Git 명령을 발생시킨다.

현재 Git snapshot은 상태 비교를 위한 관측 기록이며 수정 파일의 내용 등은 해시로 저장한다. 그 기록만으로 환경 전체를 복원할 수는 없다. 복원 가능한 테스트 시작 상태의 재사용과 이미 얻은 관측 결과의 재사용을 구분해야 한다. 일부 초기 저장소 복사와 게시 경계 직전 준비는 이미 구현돼 있으므로, 남아 있는 반복 실행을 줄이는 데 집중한다.

[R-058](%5BR-058%5D%20Test%20Timing%20and%20Agent-Free%20Test%20Execution.md)의 시간 기록·검증 범위 보존을 구체화한다. [R-065](%5BR-065%5D%20실제%20부하%20기반%20verify%20병렬%20실행.md)와 [R-067](%5BR-067%5D%20프로젝트%20공통%20verify%20실행%20규약.md)의 자원 배정·runner 확장과 별도로, 준비·관측 자체의 비용을 줄이는 요청이다.

## Requirement

### 적용 범위와 우선 대상

대상은 Loop Manager 자체 테스트와 그 테스트들이 사용하는 실제 Git 관측 경로다. 느린 테스트 하나마다 임시 우회 처리를 추가하기보다 공통 fixture·관측·복구 준비를 개선한다. 공통 경로라는 이유만으로 검사를 줄이지 않고 실제 호출 횟수·비용과 보호하는 계약을 확인해 우선순위를 정한다.

| 우선 검토할 테스트 범위 | 줄일 반복 작업 | 유지할 핵심 검증 |
|---|---|---|
| managed rebase lifecycle의 journal·legacy·수동 복구 변형 | 검사 경계에 도달하기 위한 다중 충돌 해결과 공통 전 과정 | journal·checkpoint 관계, 중단 재개, 완료 단계의 중복 실행 방지 |
| publication rebase와 PR conflict의 Agent pause·명령 중단 변형 | 오류 종류마다 충돌 준비부터 재개·게시까지 반복 | session·복구 marker·작업물 보존, 원격 lease, 기존 PR과 기본 checkout 보존 |
| Reviewer 프로토콜 오류 변형 | 출력 형식마다 Worker·verify 준비부터 반복 | Reviewer 교정 횟수·session·prompt, Worker 재호출 방지, 실패·승격 이력 보존 |

개별 모듈 최초 import 검사는 Git 준비·snapshot과 별도 비용으로 분류한다. 이미 수행한 import 중복 정리를 반복 과제로 삼지 않으며, 새 interpreter에서 최초 import를 검증하는 계약을 유지한다. 추가 import 최적화나 병렬 배정 변경은 이 요구사항의 필수 목표가 아니다.

### 테스트 시작 상태와 공통 준비 재사용

- 공통 초기 저장소뿐 아니라 충돌 해결 대기, journal 완료 후 SQLite 반영 전, 게시 전후 또는 Review 시작 등 검사할 경계 직전의 유효한 상태를 준비해 재사용한다. 각 변형은 그 경계의 실패 주입·판정·재개에 집중하고 필요한 차이만 적용한다. 기존 공통 fixture와 준비 경계를 우선 사용한다.
- 대표적인 정상·다중 충돌·수동 복구의 실제 전체 흐름은 유지한다. 앞부분을 축소한 테스트별로 기존 assertion과 보호 계약이 어느 전체 흐름 또는 집중 검증에 남았는지 대응 근거를 기록한다. 준비 상태는 실제 흐름에서 도달 가능한 상태와 일치해야 하며, 테스트해야 할 전이를 미리 성공한 상태로 바꿔 검사를 생략하지 않는다.
- 준비 상태는 필요한 실제 파일 내용·mode·Git 객체와 이력·ref·index·설정·DB·checkpoint·journal을 재현할 수 있어야 한다. 관측 snapshot의 해시나 이전 테스트 성공 결과를 복원 자료로 대신 사용하지 않는다. Git 효과가 필요한 실패·경쟁·복구 경계는 실제 Git으로 검증하고, 출력 형식·판정만 다른 변형은 같은 계약을 검증하는 최소 입력과 범위로 확인할 수 있다.
- 준비 자료의 생성 입력과 현재 테스트 revision·설정·시나리오가 맞을 때만 재사용한다. 원본은 테스트가 변경하지 않으며, 각 테스트의 Git·원격 저장소·worktree·SQLite·임시 경로와 연결·프로세스는 독립적이어야 한다. 이전 테스트의 수정·실패·중단·정리 결과가 다음 테스트나 병렬 테스트에 섞이지 않는다.
- 재현 시 절대 경로, worktree 등록, 원격 주소와 DB의 작업 identity를 해당 테스트에 맞게 설정하고 checkpoint·journal의 identity·digest와 실제 상태의 일치를 확인한다. 이전 receipt의 경로만 치환하거나 기존 관측 snapshot을 새 경로의 현재 증거로 사용하지 않는다. 재사용은 테스트 준비에만 적용하며 실제 제품 작업을 과거 상태로 되돌리지 않는다.
- 준비 자료가 없거나 현재 입력과 맞지 않으면 독립 초기화로 실행할 수 있어야 한다. 재현 실패나 불완전한 시작 상태는 성공·skip으로 처리하지 않고, 해당 테스트 소유 자원만 정리해 재생성하거나 실패로 보고한다. 준비 자료의 생성·복사·복원·identity 확인·정리 비용도 시간 진단에 남긴다.

### 같은 검사 구간의 관측 결과 재사용

- 같은 대상과 입력을 판정하는 한 검사 구간에서는 이미 얻은 관측 결과와 판정을 하위 소비자에 전달해 중복 전체 snapshot 수집을 줄인다. rebase 상태 판정 뒤 소유권 검사 내부에서 같은 관측을 다시 시작하는 경로 등을 포함한다. 각 소비자의 별도 소유권·허용 범위 조건은 계속 확인한다.
- 재사용 결과는 repository·worktree·branch·후보 HEAD·target base·원격 lease와 PR identity·계획 입력·허용 범위·checkpoint generation에 결합한다. 단순히 HEAD가 같거나 일정 시간이 지나지 않았다는 이유로 같은 상태라고 간주하지 않는다.
- Git 변경, Agent·verify 실행, 입력·checkpoint 변경 또는 실행 중단·재시작을 넘어 관측을 재사용하지 않는다. 현행 두 차례 관측의 안정성 검사, push 전후 확인과 SQLite 확정 시 재검증을 유지한다. 재사용 범위 밖이거나 증거가 불완전하면 현재 상태를 새로 관측한다.
- 기록할 활성 journal이 없는 등 결과를 사용하지 않고 반환하는 경로에서는 그 기록만을 위한 선행 snapshot 수집을 하지 않는다. 실제 상태 채택·복구·게시의 필수 검사를 불필요한 기록 수집으로 분류해 생략하지 않는다.

### snapshot 안의 Git 조회 통합

- 한 snapshot에 필요한 HEAD·branch·변경 경로·index 등의 증거를 여러 명령이 중복 수집하면 같은 의미의 묶음 조회로 통합한다. 같은 결과로 만족할 수 있는 하위 조회는 그 결과를 사용하며, 선택된 worktree와 다른 등록 worktree의 반복 상태 수집에도 적용한다.
- 변경 전과 같은 상태·범위·소유권 판정을 유지한다. index stage·보안 flags, 파일 내용·mode·부재, staged·unstaged·untracked·ignored 변경, ignore 규칙 변화, submodule·symlink, ref·worktree 등록·config·Git operation에 필요한 증거를 보존한다. 특수 문자가 있는 경로와 조회 실패·불완전한 출력도 기존처럼 처리한다.
- 조회는 관측 대상의 파일·index·ref·config를 변경하지 않아야 한다. 사용 중인 자원의 감시 범위를 단순 성능 이유로 축소하거나 다른 worktree의 관측을 일괄 제거하지 않는다.

### 효과 확인과 검증 보존

기존 진단에서 테스트·변형·처리 단계와 관측 이유를 연결해 최초 판정, 소유권 확인, 게시 전후와 transaction 확정의 필수 재검증, 사용하지 않는 기록 수집을 구분할 수 있어야 한다. 직접 snapshot을 수집한 함수만 같다는 이유로 호출들을 하나의 비용으로 합쳐 반복 원인을 숨기지 않는다.

준비 비용, 단계별 snapshot 횟수, snapshot 내부와 영향을 받는 준비·관측 경로 전체의 Git 명령 수·시간을 비교한다. snapshot 밖으로 명령을 옮겨 집계에서 숨기지 않는다. 고정된 대표 시나리오에는 중복 snapshot과 Git 명령 수가 다시 증가하면 드러나는 회귀 검증을 남기되, 필요한 새 재검증이나 지원 환경의 정상 차이를 단일 시간 상한으로 제한하지 않는다.

같은 시나리오·보호 계약과 비교 가능한 환경에서 변경 전후 기록을 남긴다. 테스트 revision·Python·Git 버전·병렬도·동시 부하 및 준비 자료의 첫 생성과 재사용 여부를 식별한다. 개별 테스트와 모듈의 누적 비용, 전체 verify 경과 시간을 구분하고 상위 몇 개의 개별 테스트만으로 모듈 전체 비용을 판단하지 않는다. 병렬 작업의 누적 시간 감소를 전체 시간 감소로 제시하지 않으며, 미완료 단계의 경과 시간을 완료 시간이나 timeout·교착의 증거로 대신 사용하지 않는다. 재사용 관리 비용까지 포함해 효과를 확인하고 실측 전 특정 절감률을 보장하지 않는다.

실제 Git·SQLite·운영체제가 필요한 정상·실패·경쟁·중단·재시작 검증과 전체 verify 범위를 유지한다. Worker는 관련 최소 targeted unit test만 실행하고 전체 비교 verify는 Manager가 Agent 밖에서 수행한다. 실제 AI Agent 호출 금지와 timeout·결과 판정은 R-058을 따른다.

## Acceptance Criteria

- 반복 준비가 큰 대표 복구·게시·Review 시나리오에서 공통 시작 상태와 경계 직전 준비를 재사용하며, 기존의 동일 계약을 보호하는 실행 대비 준비·앞부분 반복의 Git 명령과 snapshot 수가 감소한다. 첫 생성·재사용·복사·복원 및 유효성 확인의 실제 비용을 확인할 수 있다.
- 축소한 테스트마다 기존 assertion과 보호 계약의 대응 근거가 있고, 대표 실제 전체 흐름과 경계별 검증을 합쳐 정상·실패·경쟁·중단·재시작을 보존한다. session·marker·작업물, journal·SQLite 관계, 중복 rebase·push 방지, 원격 lease·기본 checkout·다른 차단, Reviewer 교정·prompt·실패 이력과 필요한 이벤트 순서가 누락되지 않는다.
- 직렬·병렬 실행과 한 테스트의 실패·중단 뒤에도 다음 테스트는 유효한 독립 시작 상태에서 실행한다. 원본과 다른 테스트의 파일·Git·원격·DB·작업 identity는 변경되지 않는다. 자료 부재·입력 불일치·재현 실패 또는 checkpoint·journal의 identity·digest 불일치에서도 누락이나 거짓 성공이 없다.
- 중첩된 rebase 판정·소유권 검사 등 대표 동일 검사 구간에서 같은 증거의 중복 snapshot 수집이 감소하고, 기존 허용·거부 결과와 소유권 조건이 유지된다.
- 관측 도중 파일·index·ref·등록·config·operation·원격·PR·입력이 바뀌거나 checkpoint generation이 달라지면 낡은 결과로 상태 채택·차단 해제·게시가 승인되지 않는다. Git·Agent·verify 전후와 재시작 이후 필요한 새 관측 및 SQLite 확정 재검증이 확인된다.
- 기록할 활성 journal이 없는 경로는 기록만을 위한 snapshot을 수집하지 않는다. 활성 journal의 기록과 중단 복구·실제 완료 판정은 유지된다.
- 동일 상태의 snapshot은 조회 통합 전과 동등한 증거·판정을 제공하면서 내부 Git 명령 수가 감소한다. index flags·충돌 stage·특수 경로·ignore 변화·submodule·symlink·파일 mode와 조회 실패 회귀를 보존하며 관측 자체가 대상 Git 상태를 변경하지 않는다.
- 테스트·변형·단계·관측 이유별 비용과 준비·관측 경로 전체의 Git 명령 수, snapshot 횟수·내부 명령 수·실제 시간의 변경 전후 기록이 있다. 같은 수집 함수 안의 중첩 호출 원인을 구분할 수 있고, 고정된 대표 시나리오에서 불필요한 호출 수 증가를 잡는 회귀 검증이 있다.
- 집계 경계 이동만으로 절감을 표시하지 않고, 필수 검증 축소·무근거 skip·전체 mock 전환·timeout 증가로 개선을 달성하지 않는다. 개별·모듈 누적·전체 경과 시간과 완료·미완료를 구분하며, import 검사의 독립 최초 실행 계약은 유지된다.
- 현재 후보의 관련 targeted test와 Manager 전체 verify가 통과하고, 실제 Git 경쟁·중단·복구 및 테스트 격리 검증이 유지된다. 기존 테스트 결과를 재사용해 현재 검증 성공을 대신하지 않는다.

## Product Impact

- 반복 테스트 준비와 Git 관측 비용을 줄이면서 현재 후보에 대한 검증·범위·소유권·복구 보장을 유지한다.
- 복원 가능한 테스트 시작 상태와 현재 상태의 관측 기록을 구분하며, 재사용은 각 자료의 유효 범위 안에서만 허용한다.

## Non-Goals

- 실제 사용자 저장소·관리 작업을 테스트 초기 상태로 복원하거나 사용자 데이터를 삭제하는 기능.
- 실행 단계·재시작을 넘는 Git 관측 cache, TTL만으로 현재 상태를 승인하는 정책 또는 이전 verify 성공 결과 재사용.
- 기존 두 차례 관측·게시 전후·transaction 재검증의 제거, Git·PR·Agent 권한 또는 감시 범위 완화.
- 범용 fixture framework, 별도 snapshot·cache 서비스, 새로운 dependency나 외부 infrastructure 도입.
- 다른 등록 프로젝트의 테스트 일괄 변경, 추가 import 최적화·병렬 배정·공통 runner 정책 변경 또는 특정 시간·절감률 보장.
