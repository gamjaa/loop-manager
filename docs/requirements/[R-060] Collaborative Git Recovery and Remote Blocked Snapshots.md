# [R-060] 사용자 변경과 함께 동작하는 Git 복구와 차단 작업 원격 보존

## Context

사용자는 Loop Manager가 작업 중이거나 차단된 동안에도 코드와 문서를 수정할 수 있다. 이런 변경은 자동 작업과 합쳐서 이어갈 입력이며, 로컬 base의 상태나 정상적인 작업 branch 분기만으로 프로젝트·계획을 중단해서는 안 된다.

현재 원격 기준 실행, 관리 rebase와 차단 checkpoint가 있지만, 원격 작업 branch의 후속 commit만 채택하는 경로는 로컬·원격 양쪽에 새 commit이 생기면 거부할 수 있다. 기존 PR이 있거나 rebase 충돌이 남아 있는 작업은 원격 게시가 제한돼 사용자가 다른 환경에서 현재 형상과 실패 지점을 확인하기 어렵다.

원격 base와 원격·로컬 작업 branch를 기준으로 자동 복구를 먼저 시도하고, 최종 차단에는 작업물·진단을 원격에 보존한다. 사용자는 원격 작업 branch를 수정해 push하고 Manager는 이를 가져와 원인을 재검사한 뒤 같은 작업을 재개한다. 이 Requirement는 현재 명세와 R-051의 작업 branch 반영·checkpoint 제한을 아래 범위에서 변경하며, R-055의 전수 조사와 R-056의 로컬 base 동기화에 적용할 구체적인 Git 정책이다.

기존의 PR 없는 후속 commit 전용 복구, 충돌 중 local-only 보존과 PR 없는 동일 branch에 한정된 rebase lease 예외를 각각 정상 분기의 rebase 통합, 충돌 자료의 별도 원격 보존과 확인된 동일 PR·작업 branch의 checkpoint 게시로 확장한다. 다른 원격 ref의 덮어쓰기와 원격 base의 force push 권한은 추가하지 않는다.

## Requirement

### 작업 기준과 사용자 변경

- 자동 작업의 Git 입력과 복구 기준은 등록된 저장소의 검증한 최신 원격 base, 선택한 원격 작업 branch와 그에 대응하는 로컬 관리 작업 branch·worktree다. 로컬 base ref·기본 checkout의 HEAD·index·파일·dirty·ahead·behind·diverged·detached 상태는 작업 선택, 입력 지문, Agent 범위 비교 또는 차단 해제의 성공 조건으로 사용하지 않는다.
- 로컬 base의 사용자 변경과 R-056의 동기화 실패·충돌은 관리 작업을 차단하지 않는다. 과거 scope snapshot·journal·차단 기록에 로컬 base 상태가 들어 있어도 현재 작업에 대한 안전 판정을 그 상태의 복원에 결합하지 않는다. 실제 사용 중인 origin·작업 ref·worktree·index·Git config·operation의 안전 검사는 유지한다.
- branch 처리 대상은 등록된 base와 소유권을 확인한 Loop Manager 생성 branch로 제한한다. 그 밖의 사용자 branch의 생성·수정·삭제만으로 복구·동기화·범위 위반·계획 또는 프로젝트 차단을 만들지 않고, 해당 ref를 되돌리거나 게시·삭제하지 않는다. 이름의 prefix만으로 관리 소유권을 인정하지 않으며 실제 사용 중인 공유 자원·관리 worktree의 영향은 별도로 검증한다.
- 원격 base와 원격 작업 branch의 사용자 commit·문서 수정, 로컬 작업 branch의 사용자 commit·미커밋·staged·untracked 작업물을 보존해 함께 처리한다. 사용자 변경을 Manager 또는 Agent가 만든 결과로 기록하지 않으며, 확인된 사용자 변경을 Agent의 범위 위반으로 귀속하지 않는다. 실제 Agent의 허용 범위 밖 쓰기와 사용자 승인은 계속 별도로 판단한다.
- Agent·verify가 같은 worktree를 사용 중이면 동시에 rebase·checkout·stage하지 않는다. 새 변경을 관측·보존하고 다음 안전한 경계에서 반영한다. 사용자가 작업 파일을 동시에 바꾸면 최신 작업물을 다시 확인하며 오래된 결과로 덮어쓰거나 검증·게시 승인을 적용하지 않는다.

### 반영과 자체 복구 우선

- 원격 작업 branch의 변경을 먼저 반영하고 최신 원격 base를 결합한다. 작업 branch가 behind이면 안전하게 가져오고, 로컬 전용 commit과 사용자 원격 commit이 함께 있으면 로컬 작업을 원격 작업 branch 위로 rebase해 양쪽 변경을 보존한다. 그 뒤 필요한 최신 base 반영을 수행하며 이미 포함된 commit·변경을 중복 재생하지 않는다.
- 동일한 저장소·작업 branch와 비교 가능한 기준이 확인되는 정상 분기는 자동 통합 대상으로 처리한다. 원격이 현재 로컬 HEAD의 후속이 아니라는 이유만으로 최종 차단하지 않는다. 원격 ref 삭제·재작성, origin 변경 또는 소유권 불확실성은 정상 분기와 구분하고 임의 덮어쓰기나 commit 누락 없이 현재 근거로 복구 가능성을 판단한다.
- 로컬 commit뿐 아니라 staged·unstaged·untracked 작업물이 있는 경우에도 반영 전 보존하고, 충돌·실패·중단 뒤 원형과 위치를 확인할 수 있게 한다. 반영을 위해 사용자 변경을 reset·clean하거나 설명 없이 버리지 않는다.
- Git lock·원격 경쟁·일시적 fetch·push 실패, 낡은 비교 기준, 중단된 Manager 작업과 정상 충돌은 기존 상태 재구성·재시도·허용된 역할의 교정으로 먼저 복구한다. 첫 실패나 원격 OID 변화만으로 사용자 조치 차단을 확정하지 않는다.
- Manager가 소유한 rebase의 시작·충돌·완료를 현재 Git 상태와 보존된 작업에 맞게 재개한다. 재시작을 이유로 완료된 반영·사용자 해결을 반복하거나 기존 작업·session을 폐기하지 않는다. 필요한 경우 원형을 보존한 뒤 실패한 소유 operation을 안전하게 되돌려 새 사용자 수정 기준에서 다시 반영할 수 있다. 사용자 operation을 임의 abort하지 않는다.
- 현재 입력에서 진전이 없고 허용된 자동 복구·교정으로 해소할 수 없거나 실제 사용자 결정·안전 문제가 남은 경우에만 최종 차단한다. 반복 경쟁과 실행별 한도는 기존 일시 대기 정책을 적용하고, 같은 입력의 무한 rebase·Agent 호출을 만들지 않는다.

### 차단 작업의 원격 보존

- 최종 `PLAN_BLOCKED`, 계획에 연결된 `PROJECT_BLOCKED`와 planning 실패에서는 현재 작업물과 실패 지점을 원격에 보존하는 것을 기본으로 한다. 차단 원인을 기록한 뒤 원격 보존을 시도하며, 차단 상태라는 사실만으로 모든 보존 경로를 금지하지 않는다.
- 원래 작업 branch의 현재 소유권·내용·원격 OID를 검증할 수 있고 미해결 충돌이 없으면 허용된 현재 작업을 checkpoint commit·push한다. 이미 원격에 같은 형상이 있으면 그 commit을 보존 결과로 재사용한다. 빈 commit·중복 push·새 PR 또는 Draft PR을 만들지 않는다.
- 기존 PR이 있다는 이유만으로 원격 보존을 생략하지 않는다. 같은 계획·PR head·작업 branch가 확인된 경우 기존 branch에도 checkpoint를 게시할 수 있다. 검증된 rebase 결과로 이력 갱신이 필요하면 PR 유무와 관계없이 정확히 관측한 원격 OID에 대한 lease를 사용한다. 원격이 바뀌면 사용자 commit을 덮지 않고 다시 반영·보존한다. 원격 base에 force push하지 않으며 branch protection을 우회하지 않는다.
- checkpoint는 구현 완료·검증 성공·Review 승인·차단 해제가 아니다. 기존 PR head를 바꾸면 이전 후보에 대한 승인을 무효화하고, 원격 진단과 알림에 차단 중·검증 미완료임을 표시한다. 새 PR 생성은 계속 최종 Worker 확인·targeted test·Manager verify·Review 뒤에만 허용한다.
- 원래 branch를 안전하게 갱신할 수 없거나 원래 작업 branch가 없는 planning 단계라면, 검증 가능한 작업물·diff·진단을 별도 진단 branch에 게시한다. 실패한 원래 ref를 덮어쓰지 않고 이 보존에 필요한 경로·내용·게시 권한을 독립적으로 확인한다. 진단 보존을 위해 원래 작업의 소유권이나 Agent의 변경 권한을 확대하지 않는다.
- 원격 보존물에는 프로젝트·계획 또는 planning identity, 작업 단계, 차단 원인, 원격 base·작업 branch와 로컬 작업 기준, 수정 대상, 자동 복구 시도와 남은 문제를 담는다. 사용자가 원격 링크만으로 실패 지점·현재 작업물·수정할 branch를 확인할 수 있어야 한다. 실행 상태의 원본은 계속 SQLite이며 ExecPlan frontmatter에 상태를 쓰지 않는다.
- 원격 보존의 ref·commit·포함 범위와 작업 기준을 기록한다. 게시 전후 원격 확인 및 push 후 SQLite 확정 전 중단에서도 같은 결과를 대조해 재개한다. 알려진 게시 실패는 pending으로 보존해 다음 실행에서 재시도하고 작업물과 원인을 잃지 않는다.
- 권한·네트워크·게시 대상 불확실성 또는 안전하게 수집할 수 없는 파일 때문에 원격 보존이 불가능하면 로컬 원형을 보존하고 실제 이유와 누락 범위를 알린다. 비밀값·ignored 운영 입력·무관한 사용자 파일·다른 프로젝트 상태를 통째로 수집하거나 push하지 않는다.

### 해결하지 못한 충돌의 별도 보존

충돌을 자동 해결하지 못해 차단하더라도 작업을 local-only로만 남기지 않는다. 원래 rebase와 index를 보존한 채 별도 진단 branch에 충돌 자료를 일반 파일로 commit·push한다. 충돌 marker가 남은 파일의 복사본도 진단 자료로 보관할 수 있으며, 이를 해결된 구현이나 유효한 ExecPlan 선언으로 채택하지 않는다.

충돌 자료에는 다음을 포함한다.

- 원격 base·작업 branch·로컬 시작 HEAD, 현재 재생 중인 commit과 실패 단계
- 충돌 경로와 가능한 base·ours·theirs 내용, 현재 충돌 marker·수동 수정이 포함된 파일 원형
- 차단 시점까지의 로컬 작업·미게시 변경·충돌 diff와 이미 처리한 변경, 아직 반영해야 하는 변경의 구분
- 사용자에게 필요한 수정 위치·원래 작업 branch와 진단 commit 링크, 자동 반영을 다시 시도할 기준

필요한 원형은 문자열 요약만으로 손실시키지 않는다. rename·delete·binary 충돌도 원래 경로·파일 내용 또는 blob과 mode·부재를 식별할 수 있게 보존한다. 수집 중 사용자가 수정하면 불일치 자료를 하나의 확정 snapshot으로 게시하지 않고 다시 확인한다.

진단 자료의 내용과 링크는 원격에서 읽을 수 있는 작업 기록에 남긴다. 기존 ExecPlan의 기록 절에 연결할 수 있지만 active catalog의 목표·dependency·형식을 충돌 marker로 훼손하지 않는다. 충돌 자료는 정상 코드 실행·verify·catalog 입력에 포함하지 않으며, 자료 저장만으로 원래 rebase를 완료시키거나 차단을 해제하지 않는다. 같은 차단과 같은 작업 형상의 보존물은 재사용한다.

### 사용자 push 이후 재검사와 재개

- 원격 수정으로 해결할 수 있는 원인은 다음 정상 실행에서 자동 재평가·복구하는 것을 기본으로 한다. 사용자가 원격에 반영한 뒤 SQLite를 직접 고치거나 별도 복구 명령을 실행해야만 재개하는 절차를 요구하지 않는다. 설정·인증·도구 등 로컬 환경만 수정한 경우의 명시적 재검사 명령은 [R-062](%5BR-062%5D%20Local%20Environment%20Recovery%20Command.md)를 따른다.
- 차단 중에도 원격 base와 해당 작업 branch 변경을 관측한다. `PROJECT_BLOCKED` 또는 다른 계획의 실행 때문에 관측 자체를 막지 않고, 저장소 변경은 기존 단일 변경 자리가 허용하는 안전한 경계에서 수행한다.
- 사용자는 안내된 원래 원격 작업 branch에서 코드·문서를 수정해 push할 수 있다. Manager는 새 commit을 가져와 보존된 로컬 작업과 반영하고 원래 차단 원인을 재검사한다. 원격 작업 branch의 수정만으로도 재평가하며 PRODUCT·Requirement 또는 로컬 base 변경을 별도 해제 조건으로 요구하지 않는다. 원래 작업 branch가 없는 planning의 수정 입력은 안내된 원격 base를 사용한다.
- 충돌 상태에서는 기존 자료·로컬 작업을 보존한 뒤 사용자 수정이 반영된 원격 작업 branch와 최신 base로 반영을 재시도하거나 이어간다. 과거 충돌 index가 남아 있다는 사실만으로 새 사용자 수정의 채택을 영구 거부하지 않는다. 진단 diff·파일 복사본을 정상 구현에 무조건 적용하지 않는다.
- 새 원격 commit만 관측했다는 이유로 해제하지 않는다. 실제 충돌·코드·문서·검증·승인 등 원인별 조건이 해소됐으면 그 원인만 해제하고 기존 branch·worktree·session으로 필요한 단계부터 재개한다. 다른 차단·Review issue·사용자 결정·dependency와 PR Merge·Close 조건은 유지한다.
- 변경된 후보에는 R-051의 관련 문서 재확인과 Worker 확인·targeted test·Manager 전체 verify·읽기 전용 Review를 적용한다. 차단 형상 게시나 사용자 push를 게시 승인으로 간주하지 않는다.
- 수정이 문제를 해결하지 못했으면 남은 원인과 최신 작업물을 원격 보존 결과로 갱신한다. 동일 원격·로컬 작업 형상과 원인에는 재검사·rebase·알림을 반복하지 않고, 관련 branch·파일·원인이 바뀌면 다시 평가한다. 진단 자료만 바뀐 것은 정상 작업 branch 수정과 구분한다.

## Acceptance Criteria

- 작업 중·차단 중 기본 checkout의 코드·문서·index·HEAD·로컬 base ref와 ahead·behind·diverged 상태가 바뀌어도, 원격 기준과 선택 작업 자원이 유효하면 작업·복구를 계속한다. legacy 비교 기준 복원을 요구하지 않는다.
- 원격 base와 작업 branch가 동시에 전진하고 로컬에도 commit·staged·unstaged·untracked 작업이 있는 경우, 양쪽 작업을 보존해 원격 작업 branch와 최신 base를 반영한다. 정상 분기를 후속 commit 부재만으로 차단하지 않는다.
- 원격 및 로컬 작업 branch의 확인된 사용자 코드·문서 변경을 Agent 범위 위반으로 오인하지 않는다. 실제 Agent 위반·origin·사용 자원·범위 불확실성은 계속 검증하고 사용자 변경을 덮어쓰지 않는다.
- 사용자가 등록 base와 Manager 소유 branch 밖의 branch를 생성·수정·삭제해도 그 변화에 개입하거나 작업을 차단하지 않는다. 유사한 branch 이름만으로 소유권을 채택하지 않으며, 실제 공유 자원 위반은 계속 거부한다.
- 첫 충돌·일시 오류·중단 상태는 자동 복구·재시도·허용 역할 교정을 먼저 수행하며, 동일 입력의 진전 없는 무한 반복을 만들지 않는다. 이미 완료된 반영과 수동 해결은 중복하지 않는다.
- 최종 계획·연결 프로젝트 차단과 planning 실패에서 현재 작업물·단계·원인을 원격에 보존한다. 원래 branch에 게시할 수 없으면 검증 가능한 별도 진단 보존을 시도하고, 실제 게시 불가 사유와 누락 범위를 기록한다.
- PR이 이미 있는 작업에도 checkpoint를 게시할 수 있고, 검증된 동일 branch rebase는 정확한 원격 lease와 PR identity를 확인한다. 동시 사용자 push·PR 종료·게시 경쟁에서 예상 밖 원격 commit을 덮지 않는다. 바뀐 후보의 기존 승인은 무효화된다.
- 자동 해결하지 못한 충돌에서도 원격 진단 commit에서 diff·파일 원형·base·ours·theirs·관련 commit·남은 반영 작업을 확인할 수 있다. rename·delete·binary와 수동 수정이 손실되지 않으며 원래 index·rebase는 자료 게시로 변형되지 않는다.
- 차단 알림과 원격 작업 기록에서 작업 branch·진단 ref·commit·수정 위치·남은 원인 또는 실제 게시 불가 이유를 확인할 수 있다. checkpoint·진단 보존으로 새 PR·Draft PR을 생성하지 않는다.
- 사용자가 원격 작업 branch에 충돌 해결 또는 코드·문서 수정을 push하면, 별도 로컬 base·명세 지문 변경 없이 가져와 원인을 재검사한다. 충돌 중 로컬 변경도 보존해 재반영하고 해결된 원인만 해제한다.
- 사용자의 원격 base·작업 branch 수정 뒤 정상 실행과 재시작에서 자동 복구가 진행되며, 수동 SQLite 수정이나 별도 복구 명령을 요구하지 않는다. 실제 원인과 관련 입력이 그대로이면 무한 재시도하지 않는다.
- 해결되지 않은 원인·독립 차단·승인·dependency는 유지되고 최신 형상과 이유를 확인할 수 있다. 해제 후 기존 작업·session을 이어가며 최종 후보의 기존 검증·Review·PR 조건을 충족한다.
- 관측·반영·충돌 자료 수집·commit·push·SQLite 기록·해제의 중단·재시작에서 같은 작업과 사용자 변경을 보존한다. 같은 입력의 중복 게시·복구·알림과 비밀값·무관한 파일 게시가 발생하지 않는다.

## Product Impact

- 사용자 코드·문서 수정과 정상 작업 branch 분기를 반영하며, 로컬 base 상태가 자동 작업·차단 복구에 영향을 주지 않는다.
- 자체 Git 복구를 우선하고 최종 차단의 현재 작업물·실패 지점·충돌 자료를 원격에서 확인할 수 있다.
- 원격 작업 branch의 사용자 수정·push로 원인을 재평가하고 기존 작업을 재개할 수 있다.

## Non-Goals

- 로컬 base 동기화의 성공을 요구하거나 기본 checkout의 미게시 변경을 자동 작업 입력·원격 checkpoint에 포함하지 않는다.
- 원격 base의 force push, 예상 밖 원격 commit의 덮어쓰기, branch protection 우회 또는 자동 Merge를 수행하지 않는다.
- 진단 branch의 보존물을 구현 완료·소유권 증거·정상 catalog·검증 통과로 채택하지 않는다.
- 실제 Agent 범위 위반·비밀정보 보호·사용자 승인·최종 검증을 생략하지 않는다.
- 운영 SQLite의 차단 기록을 직접 수정·삭제하거나 새로운 복구 서비스·Agent 역할을 추가하지 않는다.
