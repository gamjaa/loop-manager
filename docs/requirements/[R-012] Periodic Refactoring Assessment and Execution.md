# [R-012] Periodic Refactoring Assessment and Execution

## Context

Worker는 선택된 ExecPlan의 Current Goals를 구현하면서 그 변경을 안전하게 수용하는 데 필요한 리팩터링만 함께 수행한다. 이 경계는 계획 밖의 구조 변경과 회귀 위험을 막지만, 여러 ExecPlan이 같은 핵심 파일에 계속 책임을 추가하는 경우에는 각 작업이 자신의 범위만 최소 수정하고 끝나기 쉽다. 그 결과 파일과 함수가 점차 비대해지고, 책임과 상태 전이가 섞이며, 테스트 가능한 경계와 후속 변경의 가독성이 약해질 수 있다.

`AGENTS.md`에 현재 변경에 필요한 리팩터링과 책임 분리를 요구해도, 누적된 구조 문제 자체가 선택된 ExecPlan의 목표가 아니면 Worker가 이를 별도 개선으로 확장할 수 없다. 반대로 모든 Worker에게 계획 밖 리팩터링을 허용하면 범위 통제, 비용 예측과 독립 Review가 약해진다.

이 문제는 특정 언어, 프레임워크나 저장소에 한정되지 않는다. 다만 파일 길이 같은 하나의 고정 임계값만으로는 생성 코드, 선언형 설정, 작은 모듈을 많이 사용하는 프로젝트의 차이를 설명할 수 없으므로, 공통 주기와 프로젝트 문맥을 함께 사용하는 유지보수 평가가 필요하다.

현재 계획 입력이 바뀌지 않으면 Planner를 다시 실행하지 않고, READY ExecPlan이 남아 있는 동안에는 새 계획 주기를 시작하지 않는다. 따라서 주기적 평가는 기존 작업을 선점하지 않으면서도 입력 지문과 별개의 결정적인 실행 조건을 가져야 한다.

## Requirement

Loop Manager는 프로젝트별로 성공한 리팩터링 필요성 평가 이후 새로 Merge가 확인된 ExecPlan 수를 추적하고, 설정된 주기에 도달하면 다음으로 허용되는 계획 주기에서 유지보수 평가를 수행해야 한다. 주기는 스케줄러 실행 횟수나 commit 수가 아니라 Loop Manager가 SQLite에서 `MERGED`로 확인한 ExecPlan 수로 계산한다.

공통 설정 `refactoring_review_interval`은 모든 등록 프로젝트에 적용하는 양의 정수이며 기본값은 5다. 평가 이력이 없는 신규·기존 프로젝트는 활성 작업과 READY 카탈로그가 모두 소진된 첫 계획 주기에 최초 평가를 수행한다. 실행 중이거나 Merge 대기·BLOCKED 상태인 작업과 남아 있는 READY ExecPlan은 유지보수 평가가 선점하지 않으며, 의존성을 충족하지 못한 READY 계획도 평가를 앞당기기 위해 무시하지 않는다.

평가 주기가 도래하면 현재 계획 입력 지문이 이전과 같더라도 Planner를 한 번 실행할 수 있어야 한다. 같은 시점에 일반 계획 입력도 바뀌었다면 별도의 Planner를 두 번 호출하지 않고 하나의 계획 주기에서 미충족 제품 작업과 리팩터링 필요성을 함께 평가한다.

Planner는 현재 코드와 테스트, 비종료 ExecPlan 카탈로그 및 직전 평가 이후의 bounded Git 변경 이력을 사용해 다음 신호를 프로젝트 문맥에 맞게 검토해야 한다.

- 한 파일이나 함수에 서로 다른 책임, 상태 전이 또는 외부 연동이 계속 누적되는지
- 최근 ExecPlan들이 같은 핵심 경로를 반복해서 수정해 변경 집중도와 충돌 범위를 키우는지
- 기능 경계, 저장소 계층, 외부 도구 연동 또는 플랫폼별 구현을 독립적으로 테스트하기 어려운지
- 이름, 제어 흐름, 결합도와 오류 복구 경계 때문에 코드를 이해하거나 안전하게 변경하기 어려운지
- 중복 구현이나 불필요한 전역 가변 상태가 후속 작업을 어렵게 만드는지

파일 길이, 줄 수 또는 최근 변경 횟수 하나만으로 리팩터링 계획을 만들지 않는다. 구체적인 구조 문제, 영향을 받는 경계와 기대 효과를 코드에서 확인할 수 있을 때만 동작 보존 전용 ExecPlan을 작성한다. 리팩터링이 필요하지 않으면 새 ExecPlan을 만들지 않고 해당 평가를 성공한 것으로 기록한다.

리팩터링 ExecPlan은 누적된 구조 개선 자체를 Current Goal로 삼아 Worker가 필요한 새 모듈·파일·테스트 경계를 만들 수 있게 해야 한다. 각 계획은 검토 가능한 작은 책임 경계를 대상으로 하고, 기존 사용자 동작과 공개 계약을 보존하며, 보존할 동작을 검증하는 targeted unit test와 전체 verify 회귀 조건을 포함해야 한다. 여러 경계를 정리해야 하면 독립적으로 검증·Merge 가능한 계획으로 나누고, 같은 핵심 경로를 순서대로 바꿔야 하는 계획에는 `depends_on`을 기록한다.

리팩터링 계획의 기본 priority는 필수 유지보수에 해당하는 `normal`이다. 데이터 손실, 보안, 자동 실행 차단 또는 반복적인 수동 복구처럼 기존 priority 규칙이 더 높은 등급을 요구하는 구체적인 문제가 함께 확인된 경우에만 그 규칙에 따라 상향한다. 선택적 정리나 미세 최적화만으로 더 높은 priority를 사용하지 않는다.

평가 없음 결과 또는 생성한 ExecPlan batch가 검증돼 `origin/<base-branch>`에 게시되고 SQLite에 등록된 경우에만 평가 기준을 현재 Merge 수와 원격 commit으로 전진시킨다. Planner 실행, 결과 검증 또는 게시가 실패하면 기준을 전진시키지 않고 기존 planning error와 재시도 정책으로 같은 평가를 복구한다. 성공한 한 평가 주기는 일반 계획 입력 평가와 유지보수 평가를 모두 충족할 수 있다.

이 정책은 Worker가 임의로 현재 ExecPlan 밖의 대규모 리팩터링을 수행하도록 허용하지 않는다. 주기 사이에도 현재 Goal을 안전하게 수용하는 데 필요한 국소 리팩터링은 기존 규칙대로 함께 수행하고, 누적 구조 개선은 주기적 평가가 만든 별도 ExecPlan에서만 실행한다.

## Acceptance Criteria

- 프로젝트별로 마지막 성공한 유지보수 평가 이후 새로 `MERGED`가 확인된 ExecPlan 수를 결정적으로 계산한다.
- `refactoring_review_interval`은 모든 등록 프로젝트에 적용되는 양의 정수 설정이며, 생략하면 5를 사용하고 유효하지 않은 값은 작업 시작 전에 설정 오류로 보고한다.
- 평가 이력이 없는 프로젝트는 활성 작업과 READY ExecPlan이 없는 첫 계획 주기에 최초 유지보수 평가를 수행한다.
- 새로 Merge된 ExecPlan 수가 설정값보다 작으면 유지보수 평가만을 이유로 Planner를 호출하지 않는다.
- 새로 Merge된 ExecPlan 수가 설정값 이상이어도 IMPLEMENTING, VERIFYING, REVIEWING, PUBLISHING, PR_OPEN 또는 BLOCKED 작업이 있거나 READY ExecPlan이 하나라도 남아 있으면 기존 작업을 먼저 처리하거나 대기한다.
- 의존성을 충족하지 못한 READY ExecPlan도 유지보수 평가를 실행하기 위해 숨기거나 무시하지 않는다.
- 평가 주기가 도래하고 활성 작업과 READY ExecPlan이 모두 없으면 계획 입력 지문이 바뀌지 않았어도 Planner를 정확히 한 계획 주기 실행한다.
- 일반 계획 입력 변경과 유지보수 평가 주기가 동시에 도래하면 하나의 Planner 호출에서 두 범위를 함께 평가한다.
- Planner는 직전 성공 평가의 원격 commit부터 현재 원격 commit까지의 bounded 변경 문맥과 현재 코드·테스트를 기준으로 구조 문제를 검토한다.
- 평가 prompt는 책임 혼합, 변경 집중도, 테스트 경계, 결합도, 오류 복구와 후속 변경 충돌 범위를 검토하되 보편적인 단일 파일 크기 임계값을 강제하지 않는다.
- 구체적인 구조 문제와 개선 경계를 확인하지 못하면 리팩터링 ExecPlan을 만들지 않고 평가 없음 결과를 정상 완료로 기록한다.
- 리팩터링이 필요하면 기존 사용자 동작을 보존하는 독립 ExecPlan을 작성하며, 문제 근거, 대상 책임 경계, 동작 보존 조건, targeted unit test와 전체 verify 회귀 조건을 포함한다.
- 리팩터링 ExecPlan은 필요에 따라 기존 파일을 분리하고 새 모듈·파일·테스트 경계를 만들 수 있으며, 기존 파일만 계속 확장하는 방식으로 제한하지 않는다.
- 광범위한 구조 개선은 독립적으로 검증·Merge 가능한 작은 계획으로 분리하고, 순서가 필요한 계획은 `depends_on`으로 직렬화한다.
- 리팩터링 ExecPlan은 기본적으로 `priority: normal`을 사용하며, 기존 priority 정의에 해당하는 구체적인 안전·자동화 문제가 있을 때만 상향한다.
- 리팩터링 계획은 사용자 동작, 공개 API, 저장 형식 또는 Architecture Change Policy 대상 경계를 함께 바꾸지 않는다. 그런 변경이 필요하면 별도 Requirement와 사용자 승인을 요구한다.
- Planner가 추가 계획 없음으로 정상 종료하거나, 생성한 전체 batch가 검증·게시·등록된 뒤에만 마지막 평가 Merge 수와 원격 기준 commit을 갱신한다.
- Planner·검증·push 실패, planning error 또는 프로세스 중단에서는 평가 기준을 갱신하지 않고 다음 실행에서 기존 상태와 세션으로 복구한다.
- 평가로 생성된 리팩터링 ExecPlan도 일반 Worker, targeted unit test, 전체 verify, 읽기 전용 Review, PR과 사용자 Merge 절차를 동일하게 거친다.
- 주기 사이의 Worker는 현재 ExecPlan을 수용하는 데 필요한 국소 리팩터링만 수행하며, 주기적 평가가 아직 만들지 않은 범위 밖 구조 변경을 임의로 포함하지 않는다.
- 기본값, 사용자 설정값, 최초 평가, 주기 미도달, 정확한 경계 도달, READY·활성 작업에 의한 지연, 동일 지문 재평가, 일반 계획과의 단일 호출 결합, 평가 없음, 복수 리팩터링 계획, 실패 후 복구와 프로젝트별 독립 카운터를 자동 테스트로 검증한다.

## Product Impact

- 모든 등록 프로젝트는 완료된 작업 수에 따라 누적 구조 문제를 주기적으로 점검한다.
- 계획 입력이 바뀌지 않아도 정해진 작업 주기에 도달하면 다음 안전한 계획 시점에 리팩터링 필요성을 평가한다.
- 필요한 리팩터링은 별도 Current Goal과 검증 가능한 ExecPlan이 되어 기존 Worker 범위 규칙 안에서 실제로 실행된다.
- 비대한 핵심 파일, 책임 혼합과 반복 수정 집중을 작은 모듈과 테스트 가능한 경계로 정리할 수 있다.
- 기존 READY 작업과 진행 중인 작업은 유지보수 평가에 선점되지 않는다.

## Non-Goals

- 모든 주기마다 리팩터링 ExecPlan이나 코드 변경을 반드시 만들지 않는다.
- 파일 줄 수, 함수 길이 또는 변경 횟수 하나만으로 자동 리팩터링을 결정하지 않는다.
- Worker가 선택된 ExecPlan 밖의 대규모 구조 변경을 임의로 수행하도록 허용하지 않는다.
- 리팩터링을 이유로 사용자 동작, 공개 API, 데이터 형식 또는 Architecture Change Policy 대상 경계를 함께 변경하지 않는다.
- 진행 중인 작업, PR_OPEN, BLOCKED 또는 READY 카탈로그를 중단·삭제·우회하지 않는다.
- 같은 프로젝트의 ExecPlan을 병렬 실행하지 않는다.
- 외부 코드 품질 SaaS, 별도 vector database 또는 새로운 infrastructure를 도입하지 않는다.
