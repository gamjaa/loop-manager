# [R-075] 높은 우선순위 목표의 선행 작업 우선 처리

## Context

현재 실행 가능한 READY의 선언된 `priority`만 비교하면, 높은 우선순위 목표가 낮은 우선순위 선행 작업을 기다리는 동안 무관한 작업이 먼저 선택될 수 있다. 목표의 우선순위가 실제 처리 순서에 반영되려면 그 목표를 실행 가능하게 만드는 선행 작업도 우선 처리해야 한다.

예를 들어 `critical`인 G-177은 G-170과 G-176의 Merge를 기다린다. G-170의 선언된 우선순위가 `high`여도 G-177의 선행 작업이라는 이유로 `critical` 수준에서 선택 순서를 비교해야 한다.

이 Requirement는 G-177의 선행 작업을 빠르게 처리하기 위해 필요한 최우선 작업이다. Planner는 이를 구현하는 ExecPlan에 `priority: critical`을 명시한다.

## Requirement

### 선행 작업에 목표 우선순위 반영

- 원격에 게시되고 catalog 검증을 통과한 같은 프로젝트의 미완료 ExecPlan을 기준으로, 각 계획의 선택에 사용할 유효 우선순위를 판단한다. 목표는 높은 우선순위의 미완료 ExecPlan이며, 선행 작업은 그 목표의 `depends_on`으로 연결된 직접·간접 dependency다.
- 유효 우선순위는 자신의 선언된 `priority`와 자신을 미Merge 선행 작업으로 필요로 하는 모든 목표의 우선순위 중 가장 높은 값이다. `critical`, `high`, `normal`, `low` 순서와 기존 계획의 priority 생략 시 `normal` 해석을 유지한다.
- 아직 MERGED가 아닌 dependency 관계를 따라 우선순위를 전파한다. 여러 단계의 선행 작업과 여러 목표가 공유하는 선행 작업에도 적용하고, 이미 MERGED인 계획에서 전파를 끝낸다.
- 기존 선택 단계가 허용한 실행 가능한 후보 집합 안에서, 선언된 priority를 비교하던 선택은 유효 우선순위를 비교한다. 같은 유효 우선순위에서는 기존 숫자 ExecPlan ID 오름차순을 유지한다. priority를 비교하지 않는 유지보수 리팩터링 DAG의 숫자 ID 선택 규칙은 변경하지 않는다.
- 선행 작업의 문서나 SQLite의 선언된 `priority`를 목표의 값으로 덮어쓰지 않는다. 선택 시 적용하는 우선순위와 사용자가 선언한 값은 구분한다.

### 변경 반영과 실행 보호

- 목표의 priority·dependency 변경, 실제 Merge와 유효한 catalog 추가·삭제가 반영되면 다음 안전한 선택 경계에서 유효 우선순위를 다시 판단한다. 더 이상 미완료 목표의 선행 작업이 아니면 해당 목표에서 받은 우선순위를 제거한다. 재시작 뒤에도 같은 catalog와 실행 상태에서는 같은 선택 결과를 얻는다.
- 높은 우선순위 전파는 Worker 시작 자격이나 차단 해제가 아니다. 모든 직접 dependency가 실제 MERGED이고 기존 안전·승인 조건을 충족한 READY만 시작한다. `PLAN_BLOCKED`, 사용자 결정 대기 draft와 `PR_OPEN`을 우선순위만으로 READY나 MERGED로 바꾸지 않는다.
- 높은 우선순위 경로에 지금 시작할 수 있는 선행 작업이 없으면, 기존 정책이 허용한 독립 작업을 계속 선택한다. 선행 작업의 차단이나 Merge 대기를 프로젝트 전체 차단으로 확대하지 않는다.
- 실행 중인 작업의 재개, 확정 PR 충돌 복구, Planner 입력 처리와 [R-054](%5BR-054%5D%20Due%20Refactoring%20Priority.md)·[R-074](%5BR-074%5D%20Single-Pass%20Maintenance%20Cycle.md)의 유지보수 우선 처리·후보 범위·장벽은 유지한다. 우선순위 전파로 활성 작업을 선점하거나 허용된 집합 밖 계획을 시작하지 않는다.
- 선택 사유에서 선언된 우선순위, 유효 우선순위와 우선순위를 높인 목표·dependency 관계를 확인할 수 있어야 한다. 존재하지 않는 ID나 순환 dependency 등 유효하지 않은 catalog는 기존 검증·복구 규칙을 따르며 임의의 우선순위 전파로 실행하지 않는다.

## Acceptance Criteria

- `critical` 목표 A가 실행 가능한 `low` 선행 작업 B에 의존하고 무관한 `high` READY C가 있으면, B를 먼저 선택한다. B가 실제 Merge되기 전에는 A를 시작하지 않는다.
- A(`critical`) → B(`normal`) → D(`low`) 의존 관계에서 B가 D의 Merge를 기다리고 D는 실행 가능하면, D가 무관한 `high` READY보다 먼저 선택된다. D Merge 뒤 B, B Merge 뒤 A가 dependency gate를 따라 실행 가능해진다.
- `critical`과 `high` 목표가 같은 선행 작업을 공유하면 그 작업의 유효 우선순위는 `critical`이다. 원래 선언이 더 높은 선행 작업은 낮은 목표에 의해 우선순위가 내려가지 않는다.
- 서로 다른 경로의 실행 가능한 선행 작업이나 독립 작업의 유효 우선순위가 같으면 숫자 ID가 작은 계획을 선택한다. dependency 없는 catalog에서는 기존 priority·ID 선택 결과를 유지한다.
- G-177이 `critical`이고 미Merge G-170이 `high`이면 G-170은 `critical` 수준에서 비교된다. 문서와 SQLite의 G-170 선언값은 `high`로 보존되며 G-177은 G-170·G-176 모두의 실제 Merge를 기다린다.
- 목표의 priority 하향·dependency 제거·유효한 계획 삭제나 Merge 반영 뒤, 더 이상 필요하지 않은 우선순위 전파가 사라진다. 다른 미완료 목표가 공유하는 선행 작업의 우선순위는 계속 반영하며 재시작에도 같은 결과를 얻는다.
- 높은 우선순위 경로의 선행 작업이 `PLAN_BLOCKED` 또는 `PR_OPEN`이고 다른 실행 가능한 선행 작업이 없으면, 허용된 독립 READY를 선택한다. 해당 경로의 대기를 Merge나 차단 해제로 처리하지 않는다.
- 활성 작업·프로젝트 안전 차단·사용자 승인 대기·유지보수 장벽과 due 평가의 우선 처리 규칙이 유지된다. 무관한 높은 우선순위 목표가 있다는 이유로 유지보수 후보 집합 밖 작업을 시작하지 않는다.
- 선택 기록에서 선언값·유효값과 우선 처리의 근거 목표·선행 관계를 확인할 수 있다. 없는 ID·자기 의존·순환 관계를 우회해 Worker가 시작되지 않는다.
- 이 Requirement의 구현 ExecPlan에는 `priority: critical`이 명시된다.

## Product Impact

- 높은 우선순위 목표에 필요한 미Merge 선행 작업은 그 목표의 우선순위를 반영해 선택한다.
- 우선순위는 처리 순서를 정하며, 실제 Merge·dependency·안전·승인 조건을 대체하지 않는다.
- 선언된 우선순위를 보존하면서 현재 dependency 관계에 맞는 선택 순서를 적용한다.

## Non-Goals

- 새로운 priority 값, 실행 상태나 사용자 설정을 추가하지 않는다.
- 목표의 중요도를 모델이 다시 판단하거나 선행 작업의 선언된 priority를 자동 편집하지 않는다.
- 실행 중인 작업 선점, 같은 프로젝트 병렬 실행과 자동 Merge를 도입하지 않는다.
- dependency 추가·제거 또는 차단 해제를 우선순위 조정의 수단으로 수행하지 않는다.
- 유지보수 시작·종료와 기존 작업 단계의 상위 선택 순서를 변경하지 않는다.
