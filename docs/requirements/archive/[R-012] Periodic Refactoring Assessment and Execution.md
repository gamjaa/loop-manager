# [R-012] Periodic Refactoring Assessment and Execution

## Context

Worker는 선택된 ExecPlan의 Current Goals를 구현하면서 그 변경을 안전하게 수용하는 데 필요한 리팩터링만 함께 수행한다. 이 경계는 계획 밖의 구조 변경과 회귀 위험을 막지만, 여러 ExecPlan이 같은 핵심 파일에 계속 책임을 추가하는 경우에는 각 작업이 자신의 범위만 최소 수정하고 끝나기 쉽다. 그 결과 파일과 함수가 점차 비대해지고, 책임과 상태 전이가 섞이며, 테스트 가능한 경계와 후속 변경의 가독성이 약해질 수 있다.

`AGENTS.md`에 현재 변경에 필요한 리팩터링과 책임 분리를 요구해도, 누적된 구조 문제 자체가 선택된 ExecPlan의 목표가 아니면 Worker가 이를 별도 개선으로 확장할 수 없다. 반대로 모든 Worker에게 계획 밖 리팩터링을 허용하면 범위 통제, 비용 예측과 독립 Review가 약해진다.

이 문제는 특정 언어, 프레임워크나 저장소에 한정되지 않는다. 다만 파일 길이 같은 하나의 고정 임계값만으로는 생성 코드, 선언형 설정, 작은 모듈을 많이 사용하는 프로젝트의 차이를 설명할 수 없으므로, 공통 주기와 프로젝트 문맥을 함께 사용하는 유지보수 평가가 필요하다.

평가만 수행하고 기존 READY 작업을 모두 처리한 뒤 리팩터링하면 평가 당시의 코드와 실제 작업 시점의 코드가 달라질 수 있다. 반대로 이미 게시된 ExecPlan을 그대로 둔 채 파일을 분리하거나 합치면 그 계획의 파일 경로, 구현 경계, 테스트 대상과 `depends_on`이 낡을 수 있다. 따라서 주기적 리팩터링은 다음 일반 작업 선택보다 먼저 실행하고, 아직 시작하지 않은 계획의 의존성과 내용을 통제된 방식으로 최신 구조에 맞춰야 한다.

## Requirement

Loop Manager는 프로젝트별로 성공한 리팩터링 필요성 평가 이후 새로 Merge가 확인된 ExecPlan 수를 추적해야 한다. 설정된 주기에 도달하면 진행 중인 작업이 끝난 다음 안전한 선택 경계에서, 기존 READY ExecPlan을 선택하기 전에 유지보수 평가를 수행해야 한다. 주기는 스케줄러 실행 횟수나 commit 수가 아니라 Loop Manager가 SQLite에서 `MERGED`로 확인한 ExecPlan 수로 계산한다.

공통 설정 `refactoring_review_interval`은 모든 등록 프로젝트에 적용하는 양의 정수이며 기본값은 5다. 평가 이력이 없는 신규·기존 프로젝트는 활성 작업이 없는 첫 선택 경계에서 최초 평가를 수행한다. 실행 중이거나 Merge 대기·BLOCKED 상태인 작업은 중단하거나 선점하지 않지만, READY ExecPlan의 존재는 주기가 도래한 유지보수 평가를 막지 않는다. 이는 일반적인 입력 변경보다 READY 실행을 우선하는 정책에 대한 유지보수 전용 예외다.

평가 주기가 도래하면 현재 계획 입력 지문이 이전과 같더라도 Planner를 한 번 실행할 수 있어야 한다. 같은 경계에서 일반 계획 입력도 바뀌었고 READY 계획이 없다면 하나의 Planner 호출로 일반 계획과 유지보수 평가를 함께 수행한다. READY 계획이 남아 있으면 해당 호출은 유지보수 평가, 중복 리팩터링 방지와 의존성 장벽 구성에만 사용하고, 새로운 일반 기능 계획 작성은 기존 READY 카탈로그가 소진될 때까지 미룬다.

Planner는 현재 코드와 테스트, 비종료 ExecPlan 카탈로그 및 직전 평가 이후의 bounded Git 변경 이력을 사용해 다음 신호를 프로젝트 문맥에 맞게 검토해야 한다.

- 한 파일이나 함수에 서로 다른 책임, 상태 전이 또는 외부 연동이 계속 누적되는지
- 최근 ExecPlan들이 같은 핵심 경로를 반복해서 수정해 변경 집중도와 충돌 범위를 키우는지
- 기능 경계, 저장소 계층, 외부 도구 연동 또는 플랫폼별 구현을 독립적으로 테스트하기 어려운지
- 이름, 제어 흐름, 결합도와 오류 복구 경계 때문에 코드를 이해하거나 안전하게 변경하기 어려운지
- 중복 구현이나 불필요한 전역 가변 상태가 후속 작업을 어렵게 만드는지

파일 길이, 줄 수 또는 최근 변경 횟수 하나만으로 리팩터링 계획을 만들지 않는다. 기존 비종료 ExecPlan이 이미 같은 구조 문제를 해결하는지도 먼저 확인한다. 구체적인 구조 문제, 영향을 받는 경계와 기대 효과를 코드에서 확인할 수 있을 때만 동작 보존 전용 ExecPlan을 작성한다. 리팩터링이 필요하지 않으면 기존 READY 계획과 파일을 변경하지 않고 해당 평가를 성공한 것으로 기록한 뒤 일반 선택을 계속한다.

리팩터링이 필요하지만 현재 코드에서 시작하려면 기존 READY 계획의 구현이 먼저 필요한 경우에는 리팩터링 ExecPlan을 미리 확정하지 않는다. Planner는 필요한 최소 dependency-closed READY 선행 집합만 기록하고, Loop Manager는 그 집합 밖의 READY 계획을 시작하지 않은 채 선행 계획을 처리한다. 선행 집합이 모두 Merge되면 다음 READY 선택 전에 최신 코드에서 유지보수 평가를 다시 실행한다. 선행 집합을 결정할 수 없거나 순환 관계가 필요하면 변경을 게시하지 않고 진단 가능한 planning error로 중단한다.

현재 코드에서 바로 시작할 수 있는 리팩터링 계획이 확정되면 Planner는 새 리팩터링 ExecPlan과 아직 시작하지 않은 기존 READY ExecPlan 사이에 유지보수 장벽을 구성해야 한다. 기존 READY 계획에는 마지막 리팩터링 계획 또는 리팩터링 DAG의 모든 말단 계획을 `depends_on`으로 추가한다. 장벽 구성은 branch, worktree, Agent 세션과 PR이 없고 상태가 READY인 계획에만 허용한다. 유지보수 Planner는 해당 계획의 ID, 경로, sources와 제품 목표를 바꾸거나 기존 의존성을 제거하지 않고 리팩터링 장벽에 필요한 `depends_on`만 추가할 수 있다. 새 리팩터링 계획과 수정된 READY 계획은 하나의 계획 commit으로 전체 카탈로그·순환 검증을 통과한 뒤 `origin/<base-branch>`에 fast-forward 게시하며, 게시가 확인된 경우에만 SQLite의 dependency, content hash와 plan revision SHA를 원자적으로 갱신한다.

확정된 첫 리팩터링 계획은 다음 작업으로 즉시 선택한다. 유지보수 장벽에 따른 실행 순서는 priority 정렬보다 먼저 적용하며, 활성 Worker나 PR_OPEN 작업을 중단하지 않는다. 선행 READY 집합을 처리하는 동안에는 리팩터링 평가가 계속 도래한 상태로 남고, 마지막 선행 계획 Merge 후 재평가가 성공하기 전까지 다른 READY 계획을 선택하지 않는다.

리팩터링 ExecPlan은 누적된 구조 개선 자체를 Current Goal로 삼아 Worker가 필요한 새 모듈·파일·테스트 경계를 만들 수 있게 해야 한다. 각 계획은 검토 가능한 작은 책임 경계를 대상으로 하고, 기존 사용자 동작과 공개 계약을 보존하며, 보존할 동작을 검증하는 targeted unit test와 전체 verify 회귀 조건을 포함해야 한다. 여러 경계를 정리해야 하면 독립적으로 검증·Merge 가능한 계획으로 나누고 실행 순서를 `depends_on`으로 명시한다.

리팩터링 계획의 기본 priority는 필수 유지보수에 해당하는 `normal`이다. 데이터 손실, 보안, 자동 실행 차단 또는 반복적인 수동 복구처럼 기존 priority 규칙이 더 높은 등급을 요구하는 구체적인 문제가 함께 확인된 경우에만 그 규칙에 따라 상향한다. 장벽의 즉시 실행은 priority를 인위적으로 높여 구현하지 않는다.

마지막 리팩터링 계획이 Merge되면 Loop Manager는 장벽 뒤에 남은 READY 계획을 시작하기 전에 최신 `origin/<base-branch>`에서 유지보수 재검증 Planner를 실행해야 한다. 재검증은 리팩터링 전 코드 구조를 전제로 한 파일 경로, 구현 경계, 테스트 대상과 의존성을 최신 구조에 맞게 수정할 수 있다. ID, 경로, sources와 원래 제품 목표는 유지하며 사용자 동작의 의미나 계획 범위를 바꾸지 않는다. 같은 목표를 보존한 안전한 개정인지 판단할 수 없으면 낡은 계획을 실행하지 않고 진단 가능한 planning error로 중단한다.

재검증 대상도 여전히 READY이며 branch, worktree, Agent 세션과 PR이 없는 장벽 뒤 계획으로 제한한다. 변경된 계획 batch는 전체 카탈로그를 검증하고 fast-forward 게시한 뒤에만 SQLite의 content hash, dependency와 plan revision SHA를 원자적으로 바꾼다. 재검증 결과 변경이 필요 없는 계획은 그대로 유지한다. 게시 또는 SQLite 복구가 완료되기 전에는 어떤 장벽 뒤 Worker도 시작하지 않는다.

평가 없음 결과는 즉시 평가 기준을 현재 Merge 수와 원격 commit으로 전진시킨다. 리팩터링 장벽을 게시한 경우에는 별도의 활성 유지보수 주기로 기록하고, 마지막 리팩터링 Merge와 사후 READY 재검증이 성공한 뒤 그 시점까지 Merge된 리팩터링 계획을 포함해 평가 기준을 전진시킨다. 활성 유지보수 주기 동안에는 그 주기의 리팩터링 Merge 수만으로 새 주기 평가를 중첩 실행하지 않는다. Planner 실행, 결과 검증 또는 게시가 실패하면 기준을 전진시키지 않고 기존 planning error와 재시도 정책으로 같은 평가를 복구한다. 선행 집합 처리, 리팩터링 실행과 사후 계획 재검증의 진행 상태도 프로세스 중단 뒤 동일한 유지보수 주기에서 복구해야 한다.

이 정책은 Worker가 임의로 현재 ExecPlan 밖의 대규모 리팩터링을 수행하도록 허용하지 않는다. 주기 사이에도 현재 Goal을 안전하게 수용하는 데 필요한 국소 리팩터링은 기존 규칙대로 함께 수행하고, 누적 구조 개선은 주기적 평가가 만든 별도 ExecPlan에서만 실행한다.

## Acceptance Criteria

- 프로젝트별로 마지막 성공한 유지보수 평가 이후 새로 `MERGED`가 확인된 ExecPlan 수를 결정적으로 계산한다.
- `refactoring_review_interval`은 모든 등록 프로젝트에 적용되는 양의 정수 설정이며, 생략하면 5를 사용하고 유효하지 않은 값은 작업 시작 전에 설정 오류로 보고한다.
- 평가 이력이 없는 프로젝트는 활성 작업이 없는 첫 선택 경계에서 최초 유지보수 평가를 수행한다.
- 새로 Merge된 ExecPlan 수가 설정값보다 작으면 유지보수 평가만을 이유로 Planner를 호출하지 않는다.
- 새로 Merge된 ExecPlan 수가 설정값 이상이어도 IMPLEMENTING, VERIFYING, REVIEWING, PUBLISHING, PR_OPEN 또는 BLOCKED 작업은 중단하거나 선점하지 않는다.
- 평가 주기가 도래하고 활성 작업이 없으면 READY ExecPlan이 남아 있거나 계획 입력 지문이 같아도 다음 READY 선택 전에 Planner를 정확히 한 유지보수 계획 주기 실행한다.
- READY 계획이 남은 유지보수 호출은 새 일반 기능 계획을 추가하지 않고 구조 평가, 중복 방지와 장벽 구성으로 범위를 제한한다.
- 일반 계획 입력 변경과 유지보수 평가 주기가 동시에 도래하고 READY 계획이 없으면 하나의 Planner 호출에서 두 범위를 함께 평가한다.
- Planner는 직전 성공 평가의 원격 commit부터 현재 원격 commit까지의 bounded 변경 문맥과 현재 코드·테스트를 기준으로 구조 문제를 검토한다.
- 평가 prompt는 책임 혼합, 변경 집중도, 테스트 경계, 결합도, 오류 복구와 후속 변경 충돌 범위를 검토하되 보편적인 단일 파일 크기 임계값을 강제하지 않는다.
- 비종료 ExecPlan이 같은 구조 개선을 이미 계획한 경우 중복 리팩터링 계획을 만들지 않는다.
- 구체적인 구조 문제와 개선 경계를 확인하지 못하면 기존 계획을 변경하지 않고 평가 없음 결과를 정상 완료로 기록한다.
- 리팩터링이 필요하면 기존 사용자 동작을 보존하는 독립 ExecPlan을 작성하며, 문제 근거, 대상 책임 경계, 동작 보존 조건, targeted unit test와 전체 verify 회귀 조건을 포함한다.
- 리팩터링 ExecPlan은 필요에 따라 기존 파일을 분리하고 새 모듈·파일·테스트 경계를 만들 수 있으며, 기존 파일만 계속 확장하는 방식으로 제한하지 않는다.
- 현재 코드에서 리팩터링을 시작하기 전에 필요한 기존 READY 계획이 있으면 리팩터링 ExecPlan을 미리 게시하지 않고 최소 dependency-closed 선행 집합만 기록한다.
- 선행 READY 집합 밖의 계획은 시작하지 않으며, 마지막 선행 계획 Merge 직후 최신 코드에서 리팩터링 필요성과 계획을 다시 평가한다.
- 현재 코드에서 바로 실행할 리팩터링 DAG가 확정되면 기존 READY 계획 앞에 삽입한 전체 `depends_on` 그래프가 유효하고 비순환인지 검증한다.
- 장벽 구성에서 기존 READY 계획의 ID, 경로, sources, 제품 목표와 기존 dependency는 유지하며 리팩터링 말단 계획 dependency만 추가한다.
- READY라도 branch, worktree, Agent 세션 또는 PR이 있는 계획과 READY 이외 상태의 계획은 유지보수 Planner가 수정하지 않는다.
- 안전한 선행 집합을 결정할 수 없거나 dependency cycle이 생기면 변경을 게시하거나 Worker를 시작하지 않고 planning error로 중단한다.
- 새 리팩터링 계획과 기존 READY dependency 변경은 하나의 fast-forward 계획 commit으로 게시하고, 원격 확인 뒤 SQLite catalog를 원자적으로 갱신한다.
- 확정된 리팩터링 계획은 priority와 무관하게 다음 작업으로 즉시 선택한다.
- 광범위한 구조 개선은 독립적으로 검증·Merge 가능한 작은 계획으로 분리하고, 순서가 필요한 계획은 `depends_on`으로 직렬화한다.
- 리팩터링 ExecPlan은 기본적으로 `priority: normal`을 사용하며, 기존 priority 정의에 해당하는 구체적인 안전·자동화 문제가 있을 때만 상향한다.
- 마지막 리팩터링 Merge 뒤 장벽 뒤 READY 계획을 시작하기 전에 최신 원격 기준으로 유지보수 재검증 Planner를 실행한다.
- 재검증은 기존 계획의 ID, 경로, sources와 제품 목표를 유지하면서 파일 경로, 구현·테스트 경계와 dependency를 최신 구조에 맞게 수정하거나 변경 없음으로 확정한다.
- 재검증으로 같은 제품 목표를 안전하게 유지할 수 없으면 해당 Worker를 시작하지 않고 planning error와 진단 내용을 보존한다.
- 재검증 계획 commit의 원격 게시와 SQLite content hash, dependency, plan revision SHA 갱신이 완료되기 전에는 장벽 뒤 Worker를 시작하지 않는다.
- 리팩터링 계획은 사용자 동작, 공개 API, 저장 형식 또는 Architecture Change Policy 대상 경계를 함께 바꾸지 않는다. 그런 변경이 필요하면 별도 Requirement와 사용자 승인을 요구한다.
- 평가 없음이면 즉시 평가 기준을 갱신하고, 리팩터링 장벽을 만들었으면 마지막 리팩터링 Merge와 사후 READY 재검증이 성공한 뒤 해당 주기의 리팩터링 Merge까지 포함해 기준을 갱신한다.
- 활성 유지보수 주기 동안에는 그 주기에서 Merge된 리팩터링 ExecPlan 수 때문에 다른 주기 평가를 중첩 시작하지 않는다.
- Planner·검증·push 실패, planning error 또는 프로세스 중단에서는 평가 기준과 장벽 상태를 안전하게 보존하고 다음 실행에서 같은 단계로 복구한다.
- 평가로 생성된 리팩터링 ExecPlan도 일반 Worker, targeted unit test, 전체 verify, 읽기 전용 Review, PR과 사용자 Merge 절차를 동일하게 거친다.
- 주기 사이의 Worker는 현재 ExecPlan을 수용하는 데 필요한 국소 리팩터링만 수행하며, 주기적 평가가 아직 만들지 않은 범위 밖 구조 변경을 임의로 포함하지 않는다.
- 기본값, 사용자 설정값, 최초 평가, 주기 미도달, 활성 작업 지연, READY 존재 중 평가, 장벽 없는 평가, 선행 READY 집합 후 재평가, cycle 거부, 즉시 리팩터링 선택, 사후 READY 재검증, 유지보수 주기 중첩 방지, 동일 지문 재평가, 실패 후 복구와 프로젝트별 독립 카운터를 자동 테스트로 검증한다.

## Product Impact

- 모든 등록 프로젝트는 완료된 작업 수에 따라 누적 구조 문제를 주기적으로 점검한다.
- 정해진 주기에 도달하면 진행 중인 작업이 끝난 직후 기존 READY 작업보다 리팩터링 필요성을 먼저 평가한다.
- 필요한 리팩터링은 dependency graph에 안전하게 삽입돼 가능한 가장 이른 순서에 실행된다.
- 리팩터링 뒤 기존 READY 계획은 최신 파일 구조와 테스트 경계에 맞게 재검증된 뒤 실행된다.
- 필요한 리팩터링은 별도 Current Goal과 검증 가능한 ExecPlan이 되어 기존 Worker 범위 규칙 안에서 실행된다.
- 비대한 핵심 파일, 책임 혼합과 반복 수정 집중을 작은 모듈과 테스트 가능한 경계로 정리할 수 있다.

## Non-Goals

- 진행 중인 Worker, PR_OPEN 또는 BLOCKED 작업을 중단하거나 선점하지 않는다.
- 모든 주기마다 리팩터링 ExecPlan이나 코드 변경을 반드시 만들지 않는다.
- 파일 줄 수, 함수 길이 또는 변경 횟수 하나만으로 자동 리팩터링을 결정하지 않는다.
- Worker가 선택된 ExecPlan 밖의 대규모 구조 변경을 임의로 수행하도록 허용하지 않는다.
- READY 이외 상태이거나 작업 공간·세션·PR이 생성된 ExecPlan을 자동 수정하지 않는다.
- 기존 READY 계획의 제품 목표, sources 또는 식별자를 리팩터링에 맞춰 다른 작업으로 바꾸지 않는다.
- 리팩터링을 이유로 사용자 동작, 공개 API, 데이터 형식 또는 Architecture Change Policy 대상 경계를 함께 변경하지 않는다.
- 같은 프로젝트의 ExecPlan을 병렬 실행하지 않는다.
- 외부 코드 품질 SaaS, 별도 vector database 또는 새로운 infrastructure를 도입하지 않는다.
