# [R-032] Focused Verify Failure Feedback

## Context

전체 verify가 실패하면 Worker에게 전달하는 출력은 현재 길이가 제한된 로그 끝부분에 의존한다. 실패 원인이 앞이나 중간에 있고 뒤에 성공 로그가 길게 이어지면 중요한 진단을 놓칠 수 있다. 프로젝트마다 테스트 도구와 출력 형식이 다르므로 모든 형식을 정확히 해석할 수는 없다.

## Requirement

Loop Manager는 전체 verify 실패를 Worker에게 전달할 때 식별 가능한 실패 구간을 우선 사용해야 한다. 실패한 테스트·검사 이름, 오류 메시지와 인접한 진단, 최종 실패 요약을 수정에 필요한 범위로 전달하고 무관한 성공 로그는 제외해야 한다. 복수의 실패가 식별되면 제한된 크기 안에서 실패별 요점을 우선 전달하며, 생략된 내용이 있으면 잘린 사실을 표시해야 한다.

출력 형식을 안전하게 해석할 수 없으면 원인을 추측하지 않고 종료 코드, 잘림 여부와 길이가 제한된 출력 끝부분을 전달해야 한다. 프로젝트마다 별도 로그 파서를 설정하도록 요구하지 않아야 한다. Worker에게 전달할 진단을 축약해도 기존 verify 원문 보존, 실패 지문 및 재시도·차단 판단은 바뀌지 않아야 한다.

## Acceptance Criteria

- 실패 구간이 출력의 앞이나 중간에 있고 뒤에 긴 성공 로그가 이어져도, 식별 가능한 실패 이름·메시지·인접 진단과 최종 실패 요약을 Worker에게 전달한다.
- 복수의 실패가 식별되면 크기 제한 안에서 실패별 요점을 우선 전달하고, 일부를 생략해야 하면 출력이 잘렸음을 표시한다.
- 실패 구간을 식별할 수 있는 형식에서는 Worker 피드백에 수정과 무관한 성공 로그를 포함하지 않는다.
- 형식을 식별할 수 없는 실패 출력에는 종료 코드와 길이가 제한된 출력 끝부분을 전달하며, 실제로 잘린 경우 그 사실을 표시한다. 식별하지 못한 실패 원인을 만들어 내지 않는다.
- Worker용 진단 축약 전후에 저장된 verify 원문과 실패 지문, 동일 실패의 재시도·차단 결과가 달라지지 않는다.
- verify 성공 출력은 기존과 같이 Worker에게 전달하지 않는다.

## Product Impact

- Worker는 프로젝트의 로그 형식에 관계없이 제한된 실패 진단을 받고, 식별 가능한 형식에서는 실제 실패 부분을 먼저 확인한다.

## Non-Goals

- 모든 프로젝트의 테스트 도구 출력에 대한 완전한 파싱을 보장하지 않는다.
- 프로젝트별 verify 스크립트의 출력 형식을 변경하거나 별도 파서 설정을 필수로 만들지 않는다.
- 전체 verify 실행, 실패 지문, 재시도 횟수 또는 차단 정책을 변경하지 않는다.
