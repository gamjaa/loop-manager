# [R-063] 규칙 기반 작업의 Manager 처리와 모델 사용 최소화

## Context

정해진 규칙으로 판단하거나 변환할 수 있는 작업을 모델에게 맡기면 호출 시간·비용이 늘고 출력 형식이나 파일 이동 오류 때문에 불필요한 교정과 차단이 생긴다. 현재 Requirement archive 이동, 새 ExecPlan의 ID 충돌 교정, 유지보수 barrier dependency 추가와 결과 형식 교정은 여전히 모델에 맡기는 경로가 있다. 관리 rebase 채택은 Worker·verify·Review의 성공 근거를 무효화하므로, commit ID 변경과 실제 입력 변경을 구분할 여지도 점검해야 한다.

현재 정적 코드맵은 파일 내용·mode·분석 버전에 결합된 사실을 저장하고 변경된 파일만 다시 분석한다. Python 심벌·import·직접 관계 등의 수집과 읽기 전용 코드 조회는 이미 코드가 담당한다. 유지보수는 모델 없는 `fast` 점검, 영향받은 모듈의 `targeted` 정밀 검토와 초기·주기·명시 요청의 `full` 정밀 검토를 구분하며, 같은 모듈 묶음의 성공 근거를 재사용한다. 유효한 모듈 검토에서 발견이 없고 일반 계획을 함께 수행할 필요도 없으면 별도 종합·계획 호출을 생략한다. 이 기능들을 재구현하거나 정적 사실을 의미 검토 완료로 바꾸지 않는다.

현재 Codex·Claude의 JSON 사용량 파싱과 호출별 SQLite 저장·기본 집계도 존재한다. 다만 세션을 보존하지 않는 일회 실행은 사용량을 포함하지 않은 결과를 반환하는 경로가 있고, Codex의 해당 실행은 구조화된 사용량 출력도 요청하지 않는다. 기존 집계에는 작업 목적·기간별 조회와 호출 로그 연결이 부족하다. 이 누락을 보완하고 호출 감소가 실제 토큰 사용·소요 시간·재시도 감소로 이어지는지 확인할 수 있어야 한다.

CLI 사용량 출력은 [Codex 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)와 [Claude 사용량 문서](https://code.claude.com/docs/en/agent-sdk/cost-tracking)를 근거로 하되, 사용 중인 CLI 버전·출력 mode의 실제 필드와 집계 범위를 확인한다.

Manager가 규칙·상태·Git과 파일의 객관적 사실을 처리하고, 모델은 목표 해석·설계·구현·내용상 충돌 해결·검토처럼 의미 판단이 필요한 부분에 집중하도록 바꾼다. 기존에 코드로 처리하는 기능은 유지하며, 모델 호출 감소와 필요한 호출의 입력·출력 감소를 구분해 확인한다.

## Requirement

### Manager와 모델의 책임

- 일반·빠른 점검·유지보수 Planner, Worker, Reviewer와 교정·복구를 포함한 운영 코드의 모든 모델 호출 경로를 점검한다. 각 호출의 목적에서 규칙으로 확정할 수 있는 부분을 Manager로 옮기고, 남는 의미 판단과 그 입력을 명확히 한다. 조사 대상은 코드 경로이며 실제 SQLite의 개별 차단 기록 조사는 포함하지 않는다.
- 실행 선택·dependency gate·상태 전이·Git 관측과 통합·게시·archive eligibility·검증 실행·알림·PR의 정형 정보 작성은 Manager가 담당한다. 모델에게 Manager가 이미 확정한 상태·경로·ID·revision·digest를 다시 판단하거나 그대로 반환하도록 요구하지 않는다. 자동 결합은 검증한 호출·대상 입력에 한정하며, 응답의 명시적인 대상·identity 불일치를 덮어써 수용하지 않는다.
- 요구사항 충족 여부, 변경의 의미와 영향, 설계, 구현, 실제 내용 충돌의 해결 및 코드·문서의 정합성 검토는 필요한 모델 판단으로 남긴다. 규칙으로 확정할 수 없는 결정을 추측·키워드 일치·파일 크기만으로 대신하지 않는다.
- 같은 계획·작업 주기와 동일한 입력에서 같은 작업을 이미 성공적으로 처리했으면 재시작·반복 실행·게시 재시도 때문에 모델을 다시 호출하지 않는다. 최신 원격 입력, 소유권과 각 단계의 실행 조건은 Manager가 다시 확인한다.
- Git·네트워크·권한·로컬 환경 오류는 먼저 해당 코드의 복구·재검사 경로로 처리한다. 명령 재실행이나 상태 설명만을 위해 Agent를 호출하지 않으며, 실제 코드 수정 또는 의미 판단이 필요해졌을 때만 관련 맥락을 전달한다. 복구와 작업물 보존은 R-055·R-056·R-060·R-062의 범위를 유지한다.

### 규칙으로 확정되는 변경의 자동 처리

| 대상 | Manager가 처리할 동작 | 의미 판단이 필요한 경계 |

| Agent 결과 형식 | Worker·Reviewer·Planner·모듈 검토 등 실제로 도달하는 모든 결과 경로를 구조적으로 검증하고, 의미가 하나로 확정되는 배치·구분자 등 형식 차이는 직접 정규화한다. ID·경로·revision 등 Manager가 가진 정형 정보는 직접 결합한다. | 상충하는 verdict, 대상 identity 불일치, 누락된 판단·issue·원본 인용·필수 검증 근거는 성공 결과로 보충하지 않는다. 부족한 실제 판단에 한해서 해당 역할에 교정을 요청한다. |

Manager의 자동 변경은 허용된 관리 작업 공간과 최신 snapshot 안에서 수행한다. 다른 작업물·사용자 수정·실행 이력을 덮어쓰지 않으며, 원격 경쟁이나 처리 도중 입력 변경이 있으면 최신 상태에서 조건을 다시 확인한다. 중단 뒤에는 실제 파일·Git 결과와 저장된 상태를 대조해 이미 완료한 이동·배정·dependency 추가·게시를 중복 적용하지 않는다.

PR에 포함되는 자동 변경은 최종 전체 verify와 Reviewer에게 전달되는 실제 diff에 포함한다. 기계적 변경만을 이유로 Worker를 다시 호출하지 않지만, 동작·목표·검증 조건에 영향을 준 변경에는 필요한 구현 확인과 검증을 수행한다. archive 이동은 별도 선행 게시로 활성 Requirement를 제거하거나 관련 PR의 Merge 전에 완료 처리하는 수단으로 사용하지 않는다.

### 필요한 모델 호출의 범위 축소

Manager가 비교 기준·변경·대상 snapshot과 객관적 사실을 준비하고 모델에는 해당 단계에서 해결해야 할 의미 판단을 요청한다. 같은 유지보수 주기에서 이미 확정된 사실·판단을 이후 단계마다 다시 생성하지 않는다. 사실 수집, 의미 검토, 미충족 작업 판단과 계획 작성의 완료 근거를 구분해, 준비 자료가 존재한다는 이유로 필요한 검토를 생략하지 않는다.

기존 유지보수 `fast`·`targeted`·`full` 선택, 증분 분석, 검증된 모듈 묶음 결과의 재사용과 발견 없는 경우의 추가 호출 생략을 유지한다. 정적 점검을 R-049의 읽기 전용 Planner 빠른 점검과 혼동하거나 이를 위해 새 모델 호출을 추가하지 않는다. 일반 계획도 필요한 주기·발견의 처리·기존 결과 재개에 쓰이는 종전 경로만 확인해 보완하며, 파일·관계·종합 단계 전체를 새 기본 흐름으로 복원하지 않는다. 정적 점검·부분 검토가 전체 정밀 주기의 성공 기준을 전진시키거나 완료 후보의 문서 전문 최종 확인을 대신하지 않는다.

R-049의 역할 선택·읽기 전용 빠른 점검과 인계, R-057의 변경 중심 검토·최초 점검·완료 후보 문서 전문 확인, R-061의 역할 권한·draft 사용자 판단 및 관련 변경 중심 Review를 유지한다. 모델 호출을 줄인다는 이유로 Planner의 목표 해석, 최종 문서 전문 점검, 실제 변경의 Reviewer 검토와 사용자 승인을 기계적 gate로 대체하지 않는다. 결정이 모호하면 R-061의 draft로 남기며 Manager도 사용자 판단을 대신하지 않는다.

R-061의 Agent 쓰기 권한과 Manager의 규칙 기반 변경은 구분한다. 유지보수 Planner에게 barrier의 기계적 편집을 요구하거나 Worker에게 archive 이동·정형 결과 보정만을 위한 turn을 요구하는 정책은 이 Requirement로 대체한다. Worker는 필요한 구현 turn에서 실제 변경 이유와 검증 근거를 작성하고, Manager가 실제 diff와 대조해 PR 본문·링크를 완성한다. 모델의 정형 출력 오류만으로 구현 실패·Review 교정 실패나 R-052의 level 승격 횟수를 늘리지 않는다.

### 입력이 동일한 성공 결과의 재사용

commit ID 변경과 역할별 실제 입력 변경을 구분한다. 관리 rebase 등으로 ID만 바뀌었고 해당 단계의 입력이 동일함을 Manager가 증명할 수 있으면 성공한 Worker 판단·targeted test·전체 verify·Reviewer 결과 중 조건을 충족한 것만 재사용한다. 역할별 코드·문서 내용과 파일 mode, ExecPlan·사용자 결정·지침, 기준 내용과 최종 diff, 사용한 검증 command·설정·환경 및 역할·모델 설정 등 판단·실행에 영향을 주는 입력을 대조한다. 전체 verify에는 전체 검증 대상과 실행 입력의 동일성이 필요하다. 검증이 Git HEAD·이력·revision에서 생성한 값 등을 사용하면 SHA 변경도 실제 입력 변경으로 처리하며, tree 동일성만으로 통과시키지 않는다. 관련 내용이 바뀌거나 비교 자료가 불완전하면 필요한 단계부터 다시 수행한다.

재사용 시 과거 SHA에 결합된 성공 token을 그대로 복사하지 않고, 동일성 확인 근거와 원래 성공 결과를 현재 후보 revision에 연결한다. 실패·시간 초과·미완료·출처 불명 결과와 다른 계획·작업 주기의 결과를 성공으로 사용하지 않는다. 새로운 Review issue·사용자 결정·검증 실패·역할 설정 변경이 있으면 해당 결과의 재사용 여부를 다시 판단한다. 최신 원격 base·작업 branch·PR identity·lease·소유권·dependency·사용자 승인과 게시 gate는 재사용 대상이 아니다.

현행 PRODUCT·ARCHITECTURE의 후보 revision 변경 후 재검증 정책은 위의 입력 동일성이 증명된 경우에 한해 완화한다. 실제 변경이 발생했거나 증명할 수 없는 경우의 재검증과 R-057의 최종 확인 범위는 유지한다.

이 절의 신규 재사용 대상은 구현 후보의 Worker·test·verify·Reviewer 결과다. 이미 구현된 정적 코드맵과 유지보수 모듈 결과의 재사용은 각각의 원본·분석 버전·묶음 identity·평가 및 게시 검증을 유지한다. 관련 명세·지침 변경의 영향을 확인하지 않은 과거 의미 판단을 현재 성공으로 승격하거나, 다른 작업 주기의 최종 확인으로 R-057의 새 주기 확인을 대신하지 않는다.

### 호출별 토큰 로그와 비효율 확인

- Manager는 모든 실제 Agent CLI 실행의 종료·실패·timeout·중단 시점에 사용량 관측 결과를 기존 호출 기록에 연결하고 실행 로그에 남긴다. 성공한 작업 전체가 끝날 때까지 기록을 미루지 않으며, 일회 실행·세션 시작·재개·교체·fallback·교정·복구도 포함한다. 세션 보존 여부와 사용량 전달을 분리해, 일회 실행에서도 구조화된 사용량을 수집하고 기존 호출 저장 경계까지 보존한다. 사용량은 CLI의 구조화된 이벤트에서 코드로 수집하고 모델에게 계산·보고시키거나 수집만을 위한 추가 호출을 하지 않는다.
- 모델 실행 준비 기록과 실제 실행을 구분한다. 설정·격리·프로세스 생성에서 실행 전에 거부된 시도는 실제 모델 호출 수에 포함하지 않으며, 실행 여부를 확정할 수 없으면 미확인으로 표시한다. 모델을 사용하지 않는 버전 조회·sandbox 점검도 모델 호출·사용량에서 제외한다. 이 구분을 위해 기존 실패·격리 감사 기록을 삭제하거나 필수 실행 전 검사를 생략하지 않는다.
- 기존 기록에 새 목적·실행 여부·사용량 범위의 확인 근거가 없으면 미확인으로 보존한다. 새 분류를 과거 기록에 추측해서 채우거나 현재 수집의 완전한 기록처럼 집계하지 않는다.
- 호출 식별자, 프로젝트·가능한 경우 ExecPlan과 대상 batch·파일, 역할, 작업 목적, 실제 선택한 provider·Model·Effort와 CLI 버전, 세션 전이·재시도 사유와 횟수, 시작·종료·소요 시간 및 결과 분류를 사용량과 연결한다. 일반 계획·최종 확인·유지보수 모듈 검토·발견 처리와 계획 작성·남아 있는 종전 파일 검토·관계 검토·종합 및 Worker 구현·검증 실패 교정·Review 교정·충돌 해결 등을 목적별로 구분해 같은 Planner·Worker 역할 안의 반복 비용도 찾을 수 있게 한다. 목적 분류 때문에 이미 생략하는 단계를 다시 실행하지 않는다.
- 제공되는 input, cache read, cache write, output과 reasoning token을 구분하고, 제공되지 않은 값·부분 수집·형식 오류는 알 수 없음 또는 수집 상태로 표시한다. 보고된 수치의 의미를 보존하며 input에 포함된 cache read나 output에 포함된 reasoning을 합계에 다시 더하지 않는다. Claude처럼 일반 input과 cache read·write가 분리된 경우와 Codex처럼 input에 cache read가 포함된 경우를 구분한다. 캐시를 무료로 간주하거나 provider가 보고하지 않은 청구 비용을 만들어내지 않는다.
- 사용량의 범위가 현재 turn·실제 호출·세션 누적 중 무엇인지와 하위 Agent 포함 여부를 확인할 수 있게 한다. 제공되는 모델별 사용량도 보존하되 중간 이벤트·최종 결과·모델별 집계의 같은 사용량을 중복 합산하지 않는다. 재개 시 누적 수치를 받으면 비교 가능한 이전 수치와 범위·reset 여부가 확인된 경우에만 이번 호출 증가분을 계산하고, 불확실하면 누적 원본과 증가분 미확인을 구분한다. 사용량 누락·오류·중단 뒤의 불완전한 수치를 0이나 완전한 호출 합계로 처리하지 않는다.
- 기존 저장 기록과 기본 집계를 확장해 기간·프로젝트·역할·목적·Model·Effort·세션 전이별 실제 호출 수, 토큰 분류별 합계·호출당 사용량, 소요 시간과 재시도·실패 비중 및 수집 누락을 코드로 조회할 수 있게 한다. 사용량이 알려진 호출 수와 누락 수를 함께 보여 부분 합계를 전체 사용량이나 전체 호출의 평균으로 표시하지 않는다. input의 캐시·비캐시 비중은 같은 범위의 알려진 수치로 계산한다. 토큰 사용·소요 시간이 큰 목적·호출·반복 교정을 식별하고 원래 호출 로그·계획과 연결해 확인할 수 있어야 한다. 토큰이 많다는 사실만으로 불필요한 호출이나 목표 불충족으로 판정하지 않는다.
- 호출을 생략하거나 성공 결과를 재사용한 경우에는 대상 입력과 이유·근거를 남기고 실제 invocation 수와 사용량을 새로 만들지 않는다. 규칙 기반 처리로 없앤 호출, 필요한 호출에서 줄인 입력·출력, 새 의미 판단 때문에 유지한 호출을 구분하며 측정하지 않은 시간·비용 절감을 주장하지 않는다.
- 사용량 수집·로그·집계 실패만으로 성공한 Agent 결과를 실패로 바꾸거나 작업을 차단·재호출하지 않는다. 수집 문제와 실제 Agent 실패를 구분해 기록하며, 이 예외로 필수 Agent 격리·소유권·검증 증거 저장을 생략하지 않는다. 사용량 로그에는 인증 자료·비밀값·prompt나 코드·문서 전문을 추가하지 않는다.

R-058에 따라 테스트는 Agent CLI·API 경계를 mock으로 처리하고 실제 모델을 호출하지 않는다. 기존 코드맵·단계별 유지보수·사용량 파싱·저장 테스트를 재사용하고, 남은 호출 제거와 두 provider의 일회 실행·완료·실패·중단·실행 전 거부·누락·중복 이벤트·누적 재개 결과의 검증을 보완한다. 새 측정 서비스·별도 Agent·상시 benchmark 시스템은 도입하지 않는다.

## Acceptance Criteria

- 운영 모델 호출 경로와 교정·복구 경로의 목적을 확인할 수 있고, 규칙 기반 처리와 남는 의미 판단의 경계가 구현·검증 근거에 명시된다.
- 적격 Requirement의 정상 archive 이동과 규칙으로 확정되는 이동 교정은 추가 Worker 호출 없이 마지막 구현 PR에 반영된다. draft·비종료 계획·불확실한 source·archive 충돌에서는 이동을 보류하며 원문을 보존한다.
- 게시 전 새 계획의 ID·경로 충돌과 새 batch의 확정된 구조적 참조는 추가 Planner 호출 없이 교정된다. 기존 등록·실행 계획과 사용자 수정은 보존되고 동시 게시 경쟁에서도 중복 ID를 등록하지 않는다.
- 검증된 리팩터링 DAG의 모든 말단 dependency가 적격 READY에 Manager 코드로 반영된다. 대상 밖 파일·본문 변경·소유된 계획·cycle은 허용하지 않으며 이 편집만을 위한 모델 출력과 교정 호출은 없다.
- 의미가 명확한 결과 형식 차이는 Worker·Reviewer·Planner·모듈 검토의 필요한 결과 경로에서 추가 호출 없이 처리된다. 상충·누락된 판단·identity 불일치·가짜 원본 인용이나 검증 근거는 성공으로 만들어내지 않고 필요한 내용 교정과 형식 오류를 구분한다.
- 기존 증분 코드맵·읽기 전용 조회·모델 없는 유지보수 fast 점검·targeted/full 정밀 점검과 성공 모듈 결과 재사용이 유지된다. 정적·부분 점검이 전체 정밀 기준이나 최종 문서 전문 확인을 대신하지 않으며, 발견·일반 계획이 필요하지 않은 주기에서 종전 종합·계획 호출을 복원하지 않는다.
- 남아 있는 빈 파일·공백 chunk의 객관적 사실 설명과 이미 계산된 manifest·digest·링크 재작성만을 위한 모델 호출은 없다. 의미 검토가 필요한 모듈과 사실만 수집한 대상을 구분해 누락을 숨기지 않는다.
- 코드·문서의 의미 변경에는 필요한 Planner·Worker·Reviewer가 실행되며, 모호한 결정의 draft 처리와 완료 후보의 문서 전문 점검이 유지된다. PR에는 실제 자동 변경과 문서 변경 요약·diff 링크가 반영된다.
- ID만 바뀌고 역할별 입력 동일성이 증명된 후보에서는 해당 성공 결과를 재사용한다. 코드·mode·diff·지침·검증 환경 변경, Git revision을 사용하는 검증과 비교 근거 누락에서는 필요한 재검증을 수행하고, 과거 token·실패 결과만으로 현재 후보를 통과시키지 않는다.
- 재시작·같은 입력 반복·원격 경쟁에서 기계적 변경과 호출을 중복 실행하지 않는다. 새 원격 입력과 소유권·게시 gate를 확인하고 기존 작업물과 다른 차단·사용자 결정을 보존한다.
- 실제 모델 없는 테스트에서 archive·ID 충돌·barrier·결과 형식·빈 파일·ID만 변경된 후보의 호출 횟수 감소와 내용 변경·불확실성에서 필요한 호출 유지를 함께 검증한다. 호출 생략·결과 재사용 근거를 로그에서 확인할 수 있다.
- Codex·Claude의 모든 실제 CLI 실행이 종료 직후 호출 식별자·역할·목적·실제 profile·결과·시간과 제공된 토큰 사용량을 로그·기존 기록에서 연결해 확인할 수 있다. 교정·재개·fallback·실패 호출도 빠뜨리지 않으며 같은 호출은 재시작 뒤 중복 기록·집계하지 않는다.
- 세션 없는 일회 실행에서도 제공된 사용량이 반환·저장 경계에서 유실되지 않는다. 실행 전 거부·프로세스 생성 실패·실행 여부 미확인은 실제 실행된 호출과 구분되고, 버전 조회·모델 없는 sandbox 점검은 모델 호출 수에 포함되지 않는다.
- provider별 input·cache read·cache write·output·reasoning의 포함 관계, 세션 누적·이번 호출 증가분 및 하위 Agent 포함 범위를 구분한다. 중복 이벤트·누락 필드·형식 오류·중단·누적 reset fixture에서 중복 합계·가짜 0·알 수 없는 증가분을 만들지 않는다.
- 기간·프로젝트·역할·목적·Model·Effort·세션 전이별 실제 호출 수·사용량·시간·재시도와 수집 누락을 코드로 조회할 수 있다. 부분 수집의 알려진 합계·평균과 누락 수를 구분하며, 사용량·시간이 큰 목적·호출과 반복 교정에서 원래 로그·관련 계획을 확인할 수 있다.
- 사용량 수집·로그·집계 실패는 작업 결과·상태를 바꾸거나 추가 Agent 호출을 만들지 않는다. 호출 생략·결과 재사용은 새 사용량으로 집계하지 않고, 로그에 비밀값·prompt·코드·문서 전문이 추가되지 않는다.

## Product Impact

- 정해진 규칙과 객관적 사실로 처리할 수 있는 작업은 Manager가 직접 수행한다.
- 모델은 필요한 의미 판단에 집중하며, 입력이 동일한 성공 결과는 근거를 확인해 재사용한다.
- 모델 사용량은 호출 종료 직후 기록하고 목적·profile·재시도별로 비교해 비효율의 근거를 확인할 수 있다.
- 호출 절감 때문에 작업물 보존·사용자 판단·필수 검증·Review와 최종 확인을 약화하지 않는다.

## Non-Goals

- 모델의 모든 의미 판단을 없애거나 규칙 기반 검사를 코드 Review·제품 충족 판단의 대체물로 만들지 않는다.
- 새로운 Agent 역할·외부 서비스·모델 라우팅 infrastructure 또는 같은 프로젝트의 병렬 실행을 추가하지 않는다.
- 테스트를 생략하거나 시간 제한을 늘려 성공 처리하지 않으며 자동 Merge·승인 대행·AGENTS 무승인 수정과 범위 밖 목표 추가를 허용하지 않는다.
- Agent 격리·provider 권한 정책이나 비호환 SQLite 상태 모델을 변경하지 않는다.
