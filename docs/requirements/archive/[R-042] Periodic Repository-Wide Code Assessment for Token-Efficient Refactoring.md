# [R-042] Periodic Repository-Wide Code Assessment for Token-Efficient Refactoring

## Context

현재 주기적 유지보수 평가는 현재 코드·테스트와 직전 성공 평가 이후의 제한된 Git 변경 문맥을 읽고 구조 문제를 찾는다. 하지만 어떤 파일을 실제로 검토했는지 파일별로 남기지 않아, 오래된 기존 파일의 검토 누락과 변경 없는 파일의 반복 검토를 구분할 수 없다. Loop Manager 자체 저장소의 일회성 전수 평가는 별도 경로이며 다른 등록 프로젝트에 배포 직후 전수 검사를 추가할 근거는 아니다.

여러 작업을 거치며 중복 구현과 책임이 섞인 비대한 파일이 남으면 코드의 가독성이 떨어지고, 후속 작업의 Planner·Worker·Reviewer가 관련 없는 코드까지 반복해서 읽어야 한다. 이는 변경 충돌과 회귀 위험뿐 아니라 필요한 문맥의 토큰 사용량도 늘린다. 파일 길이 하나만으로 분리하면 파일과 추상화가 늘어 오히려 탐색 비용이 커질 수 있으므로, 실제 책임·중복·참조 관계를 확인해야 한다.

## Requirement

Loop Manager는 모든 등록 프로젝트의 주기적 코드·테스트 유지보수 평가에서 첫 파일별 평가 전에는 아래의 새 시작 기준값, 그 뒤에는 마지막 성공한 파일별 평가 이후 새로 `MERGED`된 ExecPlan 수를 사용한다. 공통 `refactoring_review_interval`의 기본값을 5에서 20으로 변경하되 양의 정수 설정과 기존 안전한 선택 경계, 활성 작업 우선, READY 장벽, prerequisite 처리, 사후 재검증 및 사용자 Merge 절차를 유지한다. 기존 성공 평가 이력은 감사와 복구를 위해 보존한다. 모든 기존 프로젝트는 이 정책을 처음 적용하는 안전한 시점에, 새 등록 프로젝트는 등록 시점에 확인된 `MERGED` 수를 첫 파일별 평가의 시작 기준값으로 한 번 보존한다. 기존 유지보수 주기가 진행 중이면 이를 먼저 완료하거나 복구한 뒤 시작 기준값을 확정한다. 과거 평가 성공 여부와 관계없이 첫 파일별 평가는 이 기준값 이후 새로 `MERGED`된 ExecPlan이 설정된 주기(기본 20개)에 도달한 뒤에만 시작한다. 배포나 등록만을 이유로 최초 전수 평가를 시작하지 않는다.

설계 문서의 현재 목표가 모두 충족되고 일반 Planner가 추가 작업이 없다고 확인했으며, 진행 중이거나 대기·차단된 ExecPlan과 프로젝트 차단이 없는 완료 후보 중 성공한 파일별 평가 이력이 있는 프로젝트에는 안정화 평가 기회를 제공한다. 마지막 성공한 파일별 평가 이후 새로 `MERGED`된 ExecPlan이 10개 이상이고 설정된 정기 주기에는 못 미친다면, 아래의 파일별 규칙으로 검토 대상이 있을 때 완료 알림 전에 평가한다. 설정된 주기에 도달했다면 정기 평가 한 번으로 충족한다. 10개 미만이거나 검토 대상이 없다면 완료 알림을 보류하지 않는다. 날짜 경과나 같은 파일 내용만으로 추가 평가를 반복하지 않는다.

프로그램은 평가 시점의 최신 `origin/<base-branch>` 한 revision에서 Git이 추적하는 실제 제품 코드, 테스트, 실행·검증 스크립트의 전체 목록을 결정적으로 만든다. 언어 또는 확장자를 고정한 목록 때문에 대상이 빠져서는 안 된다. 문서와 ExecPlan, archive, 생성물, 캐시 및 외부 의존성은 평가 대상에서 제외한다. PRODUCT·Requirement·ARCHITECTURE와 AGENTS.md는 제품 계약을 이해하기 위한 입력으로 읽을 수 있지만, 이 평가에서 문서 개선 발견이나 문서 수정 계획을 만들지 않는다. 대상 여부가 불분명한 추적 파일은 근거 없이 제외하지 않고 분류 근거를 기록하며, 분류를 확정할 수 없으면 평가를 완료 처리하지 않는다.

프로젝트의 평가 대상 파일마다 마지막으로 성공적으로 검토한 시점과 source revision, 경로, 내용 지문 및 실행 모드를 보존한다. 현재 원격 파일 목록에서 기록이 없는 파일과 기록된 경로·내용 지문·실행 모드가 달라진 파일만 새 평가 대상으로 선정한다. 내용이 그대로인 파일은 마지막 평가 이후 시간이 지났거나 다른 ExecPlan이 Merge됐다는 이유만으로 다시 검토하지 않는다. 대상 선정에 commit 이력 범위나 작업 공간의 파일 수정 시간을 사용하지 않는다. 경로가 바뀐 파일은 새 경로에서 미검토 파일로 취급하고, 삭제된 파일은 현재 검토 대상에서 제외하되 이전 기록 때문에 누락 또는 반복 평가가 생기지 않게 정리한다.

기존 프로젝트에 파일별 기록이 없더라도 등록 또는 배포 시 특별 검사를 시작하지 않는다. 첫 파일별 평가가 설정된 정기 주기로 도래하면 기록이 없는 기존 파일을 모두 검토 대상으로 포함한다. 첫 파일별 평가 성공 전에는 과거 유지보수 평가 이력만을 근거로 완료 후보의 10개 기준을 적용하지 않는다. 이전에 검토한 파일 중 내용이 그대로인 파일은 건너뛰고, 새로운 파일과 변경된 파일을 함께 검토한다. 선정된 파일이 하나도 없으면 유지보수 검토를 위한 Agent 호출 없이 그 시점의 대상 목록을 확인하고 평가 기준값을 갱신할 수 있다.

유지보수 Planner는 선정된 파일의 원본을 읽고 검토하는 같은 과정에서 짧은 코드맵을 작성한다. 코드맵을 먼저 만들기 위한 별도 파일 읽기·Agent 호출·평가 단계는 두지 않는다. 성공적으로 검토한 파일의 코드맵은 파일별 검토 기록과 별도로 보존한다. 코드맵은 파일의 책임, 주요 진입점·공개 심벌, 직접 참조하는 파일·심벌과 관련 테스트 경로를 찾아볼 수 있게 하며 원본 경로·내용 지문·실행 모드에 결합한다. 선정된 파일과 관련된 기존 파일을 찾을 때 유효한 코드맵을 활용하되, 코드맵을 완전한 관계 목록으로 간주하지 않고 참조가 현재 원격 revision에서도 유효한지 확인하며 필요한 원본 코드를 읽는다. 내용·경로·실행 모드가 바뀐 파일의 코드맵은 현재 근거로 사용하지 않는다. 코드맵이 없거나 참조가 확인되지 않으면 현재 원본에서 필요한 관계를 찾는다. 코드맵만 읽거나 코드맵을 갱신한 사실만으로 파일 검토를 완료했다고 인정하지 않으며, 검토하지 않은 파일의 기록과 코드맵을 갱신하지 않는다. 배포·등록 시 코드맵 작성을 위한 별도 전수 검사를 시작하지 않는다.

유지보수 Planner는 선정된 파일의 실제 내용을 크기가 큰 저장소에서도 중단·재개 가능한 단위로 검토하고, 필요하면 변경되지 않은 관련 파일을 문맥으로 읽어 중복 구현과 호출·상태 전이 관계를 확인한다. 문맥으로 읽은 파일을 실제 검토한 대상처럼 기록하거나, 변경되지 않았다는 이유만으로 선정된 파일의 관계 분석을 생략하지 않는다. 평가는 책임·외부 연동의 혼합, 이름과 제어 흐름, 오류 복구, 테스트 경계, 반복 변경 집중과 후속 충돌을 살핀다. 특히 중복 구현의 통합, 서로 다른 책임이 혼합된 비대한 파일의 분리, 불필요한 전역 상태와 추상화의 제거를 검토한다. 각 개선 후보는 후속 작업에서 읽거나 전달해야 하는 관련 없는 코드 문맥과 중복을 어떻게 줄일지 설명한다. 단순 줄 수·파일 수·토큰 수의 임계값만으로 변경을 강제하지 않으며, 분리로 늘어나는 탐색·연동 비용도 함께 판단한다.

선정된 파일을 읽는 동안 파일별 검토 결과와 새 코드맵은 잠정 상태로 두고, 아직 읽지 않은 파일을 향하는 참조나 다른 파일과 비교해야 할 책임·구현 후보를 남긴다. 선정된 파일을 모두 읽은 뒤에는 새 코드맵과 유효한 기존 코드맵을 함께 대조해 참조·역참조와 유사한 책임·구현 후보를 종합한다. 뒤에 읽은 파일에서 앞서 읽은 파일과의 관계가 발견되면 해당 관계와 필요한 원본 부분을 다시 확인한다. 기존 코드맵이 없는 관련 파일도 현재 원본에서 찾아 확인한다. 관계별로 검증 결과 또는 제외 근거를 기록하고, 검토에 필요한 관계가 미확인 상태이면 평가를 성공 처리하지 않는다. 이 종합도 중단·재개 가능한 단위로 진행하고 관련 부분만 다시 확인하며, 선정된 모든 파일의 원본을 다시 읽는 별도 전수 단계는 아니다. 같은 대상과 원본 revision이라면 파일 읽기 순서가 달라도 검토 완료 조건과 확인해야 할 파일 간 관계가 같아야 한다.

평가 결과는 선정된 각 파일의 검토 완료 근거와 발견별 대상 경로·원본 지문, 구체적 코드 근거, 처리 상태 및 관련 ExecPlan ID를 보존한다. 같은 문제를 다루는 비종료 계획이 있으면 연결만 하고 중복 계획을 만들지 않는다. 구조 개선이 필요하면 사용자 동작·공개 계약·저장 형식을 보존하는 독립적인 리팩터링 ExecPlan으로 연결하며, 중복 제거 또는 책임 분리의 기대 효과와 targeted unit test·전체 verify 회귀 조건을 명시한다. 확인된 문제가 없으면 근거 있는 평가 없음 결과로 끝내고 코드나 ExecPlan을 형식적으로 변경하지 않는다.

실제로 검토하지 않은 파일의 마지막 검토 기록은 전진시키지 않는다. 선정된 대상의 검토, 결과 검증 및 필요한 계획 게시가 성공한 뒤에만 파일별 기록·코드맵과 프로젝트의 평가 기준값을 함께 확정한다. 중단되면 같은 revision의 검증된 진행 결과를 복구하고, 원격 파일 내용이나 경로가 바뀌면 현재 목록과 파일별 기록·코드맵을 다시 대조해 오래된 결과를 성공으로 처리하지 않는다. 평가와 리팩터링 작업은 기존 작업 공간 소유권, 차단 상태, 검증·Review·PR 안전 경계를 그대로 따른다.

## Acceptance Criteria

- 공통 `refactoring_review_interval`의 기본값은 20이며, 기존 양의 정수 설정과 `MERGED` ExecPlan 수 계산을 유지한다. 첫 파일별 평가 전에는 별도 시작 기준값, 그 뒤에는 마지막 성공한 파일별 평가를 기준으로 센다.
- 성공한 파일별 평가 이력이 있는 완료 후보에서는 마지막 성공한 파일별 평가 이후 10개 이상이 Merge됐고 정기 주기에는 못 미치며 새 검토 대상 파일이 있을 때만 안정화 평가를 한 번 실행한다. 정기 평가와 중복 실행하지 않고, 10개 미만이거나 검토 대상이 없으면 완료 알림을 보류하지 않는다.
- 기존 성공 평가 이력은 보존한다. 모든 기존 프로젝트는 정책을 처음 적용하는 안전한 시점, 새 프로젝트는 등록 시점의 MERGED 수를 별도의 시작 기준값으로 보존하고, 그 뒤 설정된 주기만큼 새로 Merge된 뒤 첫 파일별 평가를 수행한다. 진행 중인 기존 유지보수 주기를 먼저 완료하거나 복구한다. 배포·등록만으로 검사하거나 과거 평가 이력만으로 첫 파일별 평가 전에 완료 후보의 10개 기준을 적용하지 않는다. 파일별 기록이 없는 기존 파일은 첫 정상 평가에서 빠짐없이 선정한다.
- 현재 원격 revision의 코드·테스트·실행·검증 스크립트 목록을 언어에 관계없이 결정적으로 만들고, 제외 대상과 불확실한 파일 분류의 근거를 확인할 수 있다.
- 프로젝트별로 파일의 마지막 성공 검토 시점·source revision·경로·내용 지문·실행 모드를 보존한다. 검토 기록이 없거나 경로·내용·실행 모드가 달라진 파일만 선정하며, Git commit 이력 탐색이나 작업 공간 수정 시간을 선정 기준으로 사용하지 않는다.
- 경로 변경은 새 파일 검토를 요구하고 삭제 파일은 현재 대상에서 제외한다. 내용이 같은 파일은 다른 파일이나 문서가 바뀌어도 새 평가 대상으로 선정하지 않는다.
- 선정된 파일이 없으면 유지보수 평가만을 위한 Agent 호출 없이 평가 기준값을 전진시킬 수 있다. 현재 파일 목록 검증이 실패하면 성공으로 기록하지 않는다.
- 선정된 파일의 원본을 읽고 검토하는 과정에서 책임, 주요 진입점·공개 심벌, 직접 참조와 관련 테스트 경로의 짧은 코드맵을 함께 작성하고 성공 시 원본 지문에 결합해 보존한다. 코드맵을 먼저 만들기 위한 별도 읽기·Agent 호출·평가 단계는 없다. 변경되거나 경로가 바뀐 파일의 오래된 코드맵은 현재 근거로 사용하지 않는다. 코드맵이 없거나 참조가 확인되지 않으면 현재 원본을 조회하며, 배포·등록 시 코드맵만을 만들기 위한 전수 검사를 하지 않는다.
- 선정된 파일의 실제 내용과 관련된 파일 간 중복·책임·연동 관계를 검토한다. 코드맵으로 찾은 관계도 현재 원격 revision에서 확인한다. 변경되지 않은 파일은 필요한 문맥으로 읽을 수 있지만 검토 대상에 자동 추가하거나 그 파일의 마지막 검토 기록·코드맵을 근거 없이 갱신하지 않는다.
- 파일별 잠정 결과에 나중에 확인할 참조·유사 책임 후보를 남기고, 모든 선정 파일을 읽은 뒤 새 코드맵과 유효한 기존 코드맵의 참조·역참조 및 유사 구현을 종합한다. 뒤에 읽은 파일 때문에 앞서 읽은 파일의 판단을 다시 확인해야 하면 관련 원본 부분을 재검토한다. 필요한 관계를 확인하거나 제외 근거를 기록하기 전에는 완료 처리하지 않는다.
- 평가가 여러 단위로 나뉘어도 선정된 파일의 누락·중복을 검증할 수 있고, 중단 뒤 같은 source의 검증된 결과를 재사용한다. 실제로 검토하지 않은 파일의 기록·코드맵과 프로젝트 성공 기준값은 전진시키지 않으며, 성공한 결과의 파일별 기록·코드맵·기준값을 함께 확정한다.
- 평가 기준에 가독성, 중복 구현 제거, 책임이 혼합된 비대한 파일의 분리와 후속 작업의 관련 코드 문맥 축소가 포함된다. 줄 수·파일 수·토큰 수 하나만으로 리팩터링을 강제하지 않는다.
- 구조 문제 발견은 대상과 원본 지문, 코드 근거, 기대하는 책임 경계와 후속 문맥 감소 이유를 포함하고 새 리팩터링 계획 또는 같은 문제를 해결하는 기존 비종료 계획에 연결된다. 문제가 없으면 근거를 기록하고 코드·계획 변경 없이 평가를 완료한다.
- 새 리팩터링 ExecPlan은 독립적으로 검증·Merge 가능하고 기존 사용자 동작·공개 계약·저장 형식을 보존하며 관련 targeted unit test, 전체 verify, 읽기 전용 Review와 사용자 PR Merge를 거친다.
- 대상 분류 불확실성, 검토 누락, 잘못된 결과, source 변경 또는 계획 게시 실패는 파일별 기록이나 성공 기준값을 전진시키지 않는다. 기존 유지보수 복구 흐름에서 다시 진행한다.
- 일회성 Loop Manager 전수 평가의 self-only 완료 기록과 문서 수정본 승인 경로는 다른 프로젝트에 적용되지 않는다.
- 기본 주기와 완료 후보의 10개 기준, 과거 평가 이력이 있거나 없는 기존 프로젝트의 시작 기준값·첫 주기, 진행 중인 기존 평가의 복구, 기존 미검토 파일, 새 파일·내용 변경·mode 변경·rename·삭제, 동일 내용 건너뛰기, 빈 선정 집합, 다중 언어, 코드맵의 생성·재사용·무효화·부재 시 원본 조회, 앞뒤 읽기 순서에서의 동일한 관계 발견·미확인 관계 차단, 중단·재개, 발견의 계획 연결과 실패 복구를 자동 테스트로 확인한다.

## Product Impact

- 등록 프로젝트는 새 기준 적용 뒤 기본값 20개의 MERGED ExecPlan에서 첫 파일별 평가를 하고, 이후 20개마다 또는 성공한 파일별 평가 뒤 완료 시 10개 이상의 작업이 쌓였을 때 새로 생기거나 바뀌었거나 아직 검토하지 않은 코드·테스트 파일을 점검한다.
- 기존 파일도 다음 정상적인 평가에서 한 번 검토하되, 내용이 그대로면 후속 평가에서 반복해서 읽지 않는다.
- 검토한 파일의 짧은 코드맵으로 관련된 기존 파일과 테스트를 찾아 후속 평가에서 필요한 문맥을 좁힌다.
- 근거가 확인된 중복과 책임 혼합을 줄여 후속 작업이 읽어야 하는 관련 없는 코드 문맥을 줄이고, 가독성과 변경·검증 경계를 개선한다.

## Non-Goals

- 배포나 프로젝트 등록을 이유로 기존 프로젝트의 모든 파일을 즉시 전수 평가하지 않는다.
- 변경되지 않은 파일을 주기마다 다시 전수 검토하지 않는다.
- 코드맵 구축만을 이유로 배포·등록 시 전체 파일을 읽거나 별도 대형 코드 색인을 운영하지 않는다.
- 제품 문서나 AGENTS.md의 평가, 수정본 작성 또는 자동 수정을 주기적 유지보수에 추가하지 않는다.
- 모든 주기마다 코드 변경이나 리팩터링 ExecPlan을 반드시 만들지 않는다.
- 파일 길이, 줄 수, 토큰 수 또는 최근 변경 횟수의 단일 임계값으로 파일 분리·삭제를 강제하지 않는다.
- 사용자 동작·공개 API·데이터 형식·Architecture Change Policy 대상 변경을 리팩터링으로 묶지 않는다.
- MERGED ExecPlan을 세는 방식, 기존 Worker·PR·차단 상태의 우선순위 또는 사용자 Merge 권한을 변경하지 않는다.
- 외부 분석 서비스나 새로운 주요 infrastructure를 도입하지 않는다.
