# [R-008] Progress-Aware Verification and Review Recovery

## Context

현재 전체 verify와 Review는 단계별 누적 실패 횟수가 3회의 수정·재시도 한도를 넘으면 실패 원인과 진행 여부에 관계없이 ExecPlan을 `BLOCKED`로 전환하도록 정의돼 있다. Worker가 앞선 오류를 수정한 결과 숨어 있던 다음 오류가 드러나거나 Reviewer가 새로운 blocking issue를 발견해도 같은 단계의 실패로 합산되므로, 실제로는 계속 진전 중인 작업이 사용자 조치를 요구하는 상태로 멈출 수 있다.

2026-09-19 G-012 실행에서도 전체 verify가 여러 테스트의 새로운 소유권 검사를 실패시켰지만, 상태와 실패 출력은 정상 보존됐고 다음 Worker 실행에서 수정을 계속할 수 있었다. 수정 가능한 실패는 작업 중 발견된 피드백이며, 서로 다른 피드백의 개수만으로 자동 복구를 중단해서는 안 된다. 반대로 Worker 수정 후에도 같은 실패가 반복되거나 이전 실패로 되돌아가는 경우에는 무한 반복과 비용 소진을 막아야 한다.

## Requirement

Loop Manager는 전체 verify와 Review에 단계별 고정 누적 재시도 한도를 적용하지 않아야 한다. 실패 결과에서 결정적인 실패 지문을 만들고, verify와 Review를 서로 다른 지문 영역으로 관리해야 한다. 서로 다른 실패 지문은 횟수를 합산하지 않으며, 새로운 실패가 드러나는 동안에는 총 실패 횟수와 관계없이 같은 ExecPlan과 Worker 세션에서 수정과 검증을 계속해야 한다.

실패 지문은 시각, 임시 경로, 출력 순서처럼 실행마다 달라질 수 있는 잡음을 제외하고 실패한 테스트·검사와 Reviewer의 actionable blocking issue를 식별해야 한다. 오류가 제거되거나 다른 오류로 바뀌면 별개의 지문으로 취급한다. AI에게 지문 동일성 판단을 맡기지 않고 프로그램 코드가 동일한 입력에서 같은 지문을 생성해야 한다.

각 실패 지문의 반복 횟수는 SQLite에 저장한다. 같은 지문이 Worker 수정 후 세 번 다시 발생하면 해당 실패에서 진전이 없다고 판단해 ExecPlan을 원인과 지문 정보와 함께 `BLOCKED`로 전환한다. 중간에 다른 실패가 발생해도 이전 지문의 횟수를 지우지 않아 A→B→A 같은 순환을 탐지한다. verify 성공은 verify 지문 이력을, Review 성공은 Review 지문 이력을 초기화하며 정상적인 BLOCKED 입력 변경도 모든 검증 지문 이력을 초기화한다.

Review 실패를 수정한 뒤 실행하는 verify에서 발생한 실패는 verify 지문에만 기록한다. verify가 성공해 Review에서 같은 blocking issue가 다시 발견됐을 때만 해당 Review 지문의 반복 횟수를 증가시킨다. 재시도 가능한 실패는 상태와 지문 이력을 먼저 저장한 뒤 가능한 동안 같은 프로그램 실행에서 계속 처리하며, 그 자체를 최상위 프로세스 오류로 반환하지 않는다.

## Acceptance Criteria

- 서로 다른 verify 실패 지문이 네 번 이상 차례로 발생해도 하나의 누적 단계 한도로 합산하지 않고 Worker 수정과 verify를 계속한다.
- 서로 다른 Review blocking issue가 네 번 이상 차례로 발생해도 하나의 누적 단계 한도로 합산하지 않고 Worker 수정, verify와 Review를 계속한다.
- 같은 verify 지문이 Worker 수정 후 세 번 다시 발생하면 현재 ExecPlan을 `BLOCKED`로 전환한다.
- 같은 Review 지문이 Worker 수정·verify 후 세 번 다시 발생하면 현재 ExecPlan을 `BLOCKED`로 전환한다.
- A verify 실패, B verify 실패, A verify 실패처럼 이전 실패가 다시 나타나면 A의 기존 반복 이력을 이어서 계산하며 B의 횟수와 합산하지 않는다.
- verify와 Review의 실패 지문 및 반복 횟수는 서로 독립적이다.
- Review 수정 뒤 verify가 실패하면 verify 지문만 갱신하고 해당 Review 지문의 반복 횟수는 Review를 다시 실행해 같은 issue가 확인되기 전까지 증가시키지 않는다.
- 시각, 관리 worktree의 절대 경로, 임시 디렉터리와 출력 순서만 달라진 동일 실패는 같은 지문으로 판정한다.
- 실패한 테스트·검사 또는 actionable blocking issue가 달라지면 별개의 지문으로 판정한다.
- 지문 생성은 결정적인 프로그램 코드가 수행하며 지문 비교를 위한 추가 AI 호출을 하지 않는다.
- 실패 지문과 반복 횟수는 프로세스 중단 후에도 보존돼 다음 실행에서 같은 값으로 재개된다.
- verify 성공은 이전 verify 실패 지문 이력을 초기화하고 Review 성공은 이전 Review 실패 지문 이력을 초기화한다.
- ExecPlan 또는 근거 문서 변경으로 정상적으로 BLOCKED가 해제되면 저장된 verify와 Review 실패 지문 이력을 모두 초기화한다.
- 재시도 가능한 verify 또는 Review 실패는 같은 프로그램 실행에서 다음 Worker 수정으로 이어지며 중간 종료 코드 1의 원인이 되지 않는다.
- AI 사용 한도 소진, 외부 CLI의 일시 실패, 복구 불가능한 작업 공간과 사용자 결정이 필요한 기존 BLOCKED 조건은 검증 실패 지문 횟수와 별도로 기존 중단 정책을 따른다.
- 서로 다른 실패의 장기 진행, 동일 실패 반복, A→B→A 순환, 단계 간 독립성, 출력 잡음 정규화, 프로세스 재실행과 성공·BLOCKED 해제 초기화를 자동 테스트로 검증한다.

## Product Impact

- 수정 과정에서 새로운 오류나 Review issue가 계속 발견되는 작업은 고정 누적 횟수 때문에 중단되지 않는다.
- verify와 Review 및 서로 다른 실패는 각각 독립적으로 추적된다.
- 같은 실패가 반복되거나 이전 실패로 되돌아가는 진전 없는 작업은 제한된 횟수 뒤 사용자 확인이 가능한 `BLOCKED` 상태가 된다.

## Non-Goals

- 동일한 실패가 반복돼도 무제한으로 Agent를 호출하지 않는다.
- Planner 결과 형식 검증의 기존 최대 3회 정책을 변경하지 않는다.
- 외부 CLI 실패, timeout, 사용 한도 소진과 설정 오류의 재시도 정책을 변경하지 않는다.
- 안전 검증, 사용자 승인 또는 복구 불가능한 작업 공간 때문에 필요한 `BLOCKED` 전환을 우회하지 않는다.
- 실패 지문을 분류하기 위해 추가 AI Agent나 외부 서비스를 사용하지 않는다.
