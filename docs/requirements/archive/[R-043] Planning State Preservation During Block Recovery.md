# [R-043] Planning State Preservation During Block Recovery

## Context

2026-09-25 22:38~23:49 UTC에 같은 planning worktree 소유권 오류의 BLOCKED 알림이 약 1분 간격으로 반복됐다. SQLite에는 같은 원인의 별도 차단 사건 72건이 남았으며, 각 알림은 전송 시도 1회로 성공 처리됐다. 전송 실패로 같은 이벤트를 재시도한 기록이 아니라, 해결되지 않은 오류를 반복해서 새 사건으로 기록한 결과다.

차단된 ExecPlan의 해제 조건을 확인하는 과정에서 해당 계획을 project 실행 상태에 투영하고, 복구되지 않으면 project 상태를 정리했다. 이 정리에 planning 오류와 입력 지문, worktree 소유 기록도 포함돼 기존 planning 차단 사건이 해제됐다. 이후 같은 입력으로 새 planning 시도를 시작했지만 기존 worktree는 남아 있어 소유권 오류가 다시 발생했고, 새 차단 사건과 알림이 생성됐다. 최초에 worktree와 소유 기록이 어긋난 계기까지는 확정되지 않았으므로 경로 존재만으로 소유권을 추정해서는 안 된다.

PRODUCT는 각 ExecPlan의 차단 해제와 planning 오류의 입력 변경을 독립적으로 판정하고, 같은 planning 입력에서는 미해결 오류를 유지하며 같은 차단 사건의 알림을 중복 전송하지 않도록 요구한다. 이 변경은 다른 계획의 복구 과정이 planning 상태를 잃게 만드는 결함과 그에 따른 반복 알림을 해결한다.

## Requirement

Loop Manager는 일반·유지보수 planning의 진행 상태와 오류를 다른 ExecPlan의 차단 재검토·해제, PR 상태 동기화 및 실행 상태 정리와 독립적으로 보존해야 한다. 다른 계획의 상태를 조회하거나 갱신했다는 이유로 planning의 기준 revision, 입력 지문, worktree 경로와 예약·소유 기록, Agent session·작업물, 재시도·검증·게시 진행 또는 미해결 오류를 덮어쓰거나 지우지 않아야 한다.

planning이 실행 자리를 사용하거나 오류로 보존돼 있는 동안 다른 ExecPlan의 복구 작업이 그 자리를 선점해서는 안 된다. 허용된 PR 상태 조회와 계획별 해제 조건 판정은 기존 안전 규칙에 따라 수행할 수 있지만, planning 상태를 임시 실행 상태로 교체하거나 정리하는 근거가 되지 않는다. 실제 실행 자리 변경이 필요한 복구는 planning이 기존 정책에 따라 종료되거나 유효하게 정리된 뒤 다시 선택한다. planning이 없는 정상 상태에서 차단된 ExecPlan을 복구하는 동작은 유지한다.

해결되지 않은 planning 오류는 같은 관련 입력에서 반복 실행하거나 프로세스를 재시작해도 유지한다. 다른 계획의 차단 해제, 안정된 PR의 상태 변경, 단순 원격 base 전진 또는 project 실행 상태 정리만으로 planning 오류가 해결됐다고 판정하지 않는다. 기존 planning 정책이 허용하는 관련 입력 변경, 검증된 게시 복구 또는 명시적인 운영 복구가 있을 때만 해당 planning 오류의 해제를 확정한다. 해제에 필요한 소유권 검증이나 정리가 실패하면 오류와 보존 상태를 유지한다.

planning 오류의 실제 해제와 차단 사건의 해제는 함께 일치해야 한다. 미해결 오류의 반복 관측은 같은 사건으로 취급하고, 이미 전송된 BLOCKED 알림을 다시 만들지 않는다. 단순 상태 초기화나 다른 ExecPlan의 작업 시작은 planning 차단의 해제·재개 사건을 만들지 않는다. 전송이 확인된 차단이 유효하게 해제되고 해당 Planner 작업이 실제로 시작되면 기존 정책에 따라 재개 알림을 사건당 한 번 생성한다. 이후 다시 발생한 차단은 별도 사건으로 알릴 수 있으며, 정상적인 알림 전송 실패 재시도는 유지한다.

기존 경로에 planning worktree가 있으나 예약·소유 근거를 확인할 수 없는 경우에는 해당 경로와 Git 등록·파일을 보존하고 진단을 유지한다. 반복 알림을 멈추기 위해 경로를 자동 삭제하거나 소유권을 채택하거나 기존 차단·알림 감사 이력을 삭제해서는 안 된다.

## Acceptance Criteria

- `PLANNING`과 하나 이상의 `PLAN_BLOCKED`가 함께 있는 상태에서 차단 계획을 재검토해도 planning의 기준 revision, 입력 지문, worktree 경로·예약·소유 기록, session, 재시도 및 검증·게시 진행이 보존된다. 정상 진행, 예약 뒤 중단 및 검증·게시 결과 보존 상태를 포함한다.
- 같은 planning 입력의 미해결 `planning_error`와 다른 `PLAN_BLOCKED`가 함께 있을 때 외부 실행을 최소 3회 반복하고 프로세스를 재시작해도 오류·오류 지문·작업 공간 기록과 기존 차단 사건이 유지되고 Planner가 다시 호출되지 않는다.
- 기존 planning 경로는 존재하지만 소유 기록이 없는 오류를 위 반복 시나리오로 검증한다. worktree의 Git 등록·HEAD·index·파일 상태는 보존되고, 같은 오류의 새 차단 사건이나 추가 BLOCKED 알림은 생성되지 않는다.
- 차단 계획이 여러 개이며 해제 조건 미충족, 소유권 검증 실패 또는 다른 계획의 유효한 해제가 섞여 있어도 각 계획의 결과가 다른 계획과 planning의 상태를 지우지 않는다. planning의 실행 자리를 사용하는 동안 다른 계획의 Worker·verify·Review·게시 또는 Git 변경 복구를 시작하지 않는다.
- 허용된 PR 상태 확인과 Merge·Close 기록은 기존 안전 gate를 따른다. 관련 없는 PR이나 ExecPlan의 상태 변경은 planning 오류의 해제 근거가 되지 않고 planning 차단의 재개 알림을 만들지 않는다.
- 관련 planning 입력이 그대로인 원격 base 전진이나 ExecPlan 상태 변화만으로 미해결 planning 오류를 초기화하거나 같은 오류를 다시 통지하지 않는다. 일반·유지보수 planning의 기존 입력 및 복구 정책을 각각 적용한다.
- 기존 정책이 허용하는 planning 입력 변경 또는 게시 복구에서 필요한 소유권 검증·진단 보존·정리가 성공하면 정상 재계획 또는 게시 적용을 이어간다. 그 과정이 실패하면 기존 planning 오류·작업 공간과 미해결 차단 사건을 보존한다.
- 실제 planning 오류 해제와 차단 사건 해제 기록 사이에 중단돼도 재시작 뒤 둘이 어긋나거나 허위 해제·새 차단 사건이 만들어지지 않는다.
- planning 차단의 BLOCKED 전송이 확인된 뒤 유효하게 해제되고 Planner가 실제로 시작하면 재개 알림을 한 번 생성한다. 실제 재개 후 같은 원인의 오류가 새로 발생하면 새 BLOCKED 알림을 한 번 생성하며 이후 반복 관측에서는 추가하지 않는다.
- planning이 없는 상태의 정상 ExecPlan 차단 해제, PR Merge·Close 처리, 알림 전송 실패 재시도·부분 전송 재개와 Telegram 비활성화 동작이 유지된다.
- 배포 전부터 소유권 오류와 중복 차단 사건이 남아 있는 상태에서도 과거 사건·전송 감사 이력을 보존하면서 현재 미해결 사건을 더 분할하지 않는다. 존재하는 worktree를 근거 없이 자동 삭제하거나 채택하지 않는다.

## Product Impact

- 다른 계획의 복구와 상태 동기화가 진행 중이거나 오류로 보존된 planning 작업의 상태와 소유권 기록을 훼손하지 않는다.
- 해결되지 않은 동일 planning 차단은 재실행·재시작 뒤에도 같은 사건으로 남으며, 실제 해제·작업 재개·이후 재발에만 알림 사건이 전이한다.

## Non-Goals

- 차단된 모든 계획을 자동 해제하거나 planning worktree의 소유권 검증을 완화하지 않는다.
- 소유 근거가 없는 worktree의 자동 삭제·채택, 과거 알림 이력 삭제 또는 SQLite의 비호환 migration을 추가하지 않는다.
- 시간 간격 제한이나 모든 같은 오류의 영구 알림 억제로 실제 재발을 숨기지 않는다.
- 같은 프로젝트의 병렬 실행, planning 우선순위, PR Merge 권한 또는 새로운 알림 채널을 추가·변경하지 않는다.
