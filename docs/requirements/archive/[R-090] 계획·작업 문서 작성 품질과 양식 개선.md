# [R-090] 계획·작업 문서 작성 품질과 양식 개선

## Context

사용자가 Requirement에서 원하는 동작과 완료 조건을 쉽게 이해하고, Worker가 ExecPlan에서 실제 수행할 일과 관련 파일·테스트를 바로 찾을 수 있어야 한다. 중요한 조건을 생략하지 않으면서 반복 설명과 불필요한 양식을 줄인다.

Specification Skill의 Quality Guidance·Ready Check와 활성 Requirement 재사용 원칙은 이미 존재한다. 현재 Requirement 템플릿은 선택적인 Product Impact·Non-Goals·Open Questions도 고정 항목으로 제시하고, Planner·PLANS의 Implementation 기준은 체크리스트·확인한 파일별 변경 목적을 충분히 요구하지 않는다. 실제 G-244·G-258·G-259에는 일반 verify·Review 절차와 조사 시점·SHA·snapshot 기록이 반복된다. 기존 원칙을 재구현하거나 모든 문서를 다시 쓰기보다 작성 절차·양식·갱신 기준의 부족한 부분을 보완한다.

변경 동기화는 [R-082](<[R-082] 단계별 원격 문서 반영과 PR 전 ExecPlan 갱신.md>), 삭제·취소는 [R-055](<[R-055] 차단 경로 전수 조사와 불필요한 작업 중단 축소.md>), 사용자 판단과 결정 입력 정리는 [R-061](<[R-061] Agent 역할·문서 권한과 draft ExecPlan 사용자 판단.md>)에서 정의한다. 이 문서는 그 기능을 중복 정의하지 않고 작성 품질과 필요한 근거 연결을 담당한다. 아래 내용은 후속 구현 목표이며 현재 지침·템플릿·실행 코드의 적용 완료를 뜻하지 않는다.

## Requirement

### 공통 작성과 갱신

Requirement와 ExecPlan은 첫 부분에 변경 목적 또는 구현 결과를 설명한다. 적용 조건·정상 결과·예외·실패 결과·상태 전이·권한·데이터 보존·복구·판단 근거·완료 조건 중 실제 변경에 필요한 정보를 보존하며, 간결화를 이유로 생략하지 않는다.

같은 규칙은 책임을 가진 문서의 관련 절에 모으고 다른 문서에서는 필요한 요약·참조로 연결한다. 문서 수정은 관련 절의 통합·재작성을 우선하며 대체된 설명과 중복을 정리한다. 순서가 중요한 흐름은 단계, 조건별 결과는 짧은 항목이나 표, 수행할 일은 체크리스트로 표현한다. 비어 있거나 중복인 절은 강제하지 않되 기존 형식·파싱·실행 계약이 요구하는 항목은 유지한다. 줄 수·항목 수·토큰 수 제한을 두거나 요청 밖 기능·설정·추상화를 추가하지 않는다.

[i-have-adhd](https://github.com/ayghri/i-have-adhd)의 행동·결과 우선 설명과 단계 구분을 참고한다. 필요한 정보를 먼저 보여 주고 상세 근거를 연결하는 Progressive Disclosure로 문맥 전환을 줄이되, 일반 대화의 응답 형식·마무리 문구·강제 길이 제한을 문서 규칙으로 옮기지 않는다. 필수 안전 조건을 참조만 남겨 찾기 어렵게 숨기지 않는다.

### 활성 Requirement 재사용과 명세 확정

Specification Skill은 신규 작성 전에 활성 Requirement 전체를 대상으로 관련 내용을 탐색한다. 제목·키워드뿐 아니라 변경 목적·제품 규칙·동작 시나리오·영향 범위로 관련성을 확인한다. 관련 활성 문서가 있으면 그 문서를 갱신하고 여러 문서가 영향을 받으면 필요한 문서들을 함께 갱신한다. 기존 문서로 다룰 수 없거나 독립적인 목표를 결합하기 부적절할 때만 새 Requirement를 만든다. 조회 실패·내용 확인 불가는 관련 계획이 없다는 증거가 아니다.

사용자의 의도·정상 및 실패 시나리오·참고 자료·기존 제품 규칙을 대조하고, 변경에 필요한 입력·결과·상태·권한·불변식·보존·복구·재시도·변경하지 않을 범위와 완료 기준을 구체화한다. 이 점검 항목을 모든 문서에 그대로 나열하지 않는다. 기존 문서·코드로 확인할 사실은 먼저 조사하고 구현자가 안전하게 선택할 내부 기술 사항은 과도하게 고정하거나 질문하지 않는다.

제품 정책이나 사용자 동작의 의미를 바꾸는 미결정 사항은 구현 전에 사용자에게 배경·선택지·영향·합리적인 권장안을 간결하게 제시한다. 답변이 확정되면 해당 본문을 직접 수정·통합한다. 확정 전 질문은 대화나 검토용 초안에서 관리하고, 구현자가 임의로 정책을 정할 필요가 없어야 활성 Requirement로 저장·게시한다. Ready Check는 작성 완료 전 품질 검사이며 모든 점검 항목을 문서의 절로 추가하는 양식이 아니다.

### Requirement 양식

| 항목 | 작성 기준 |
|---|---|
| Context | 필수. 문제와 변경 목적을 설명한다. |
| Requirement | 필수. 원하는 제품 동작·정책·제약과 필요한 예외를 정의한다. |
| Acceptance Criteria | 필수. 충족 여부를 객관적으로 확인할 결과를 적는다. Requirement와 합치지 않는다. |
| Product Impact | 장기 제품 규칙을 별도로 식별할 필요가 있을 때만 둔다. Requirement 문장을 그대로 반복하지 않는다. |
| Non-Goals | 범위 오해나 불필요한 확장을 막을 필요가 있을 때만 둔다. |
| Open Questions | 작성 과정의 미결정 사항을 관리한다. 확정 후 빈 절·해결된 질문을 남기도록 강제하지 않는다. |

참고 자료는 근거 추적이 필요한 링크·경로만 간단히 기록하고 긴 복사나 무관한 출처 목록을 넣지 않는다. 템플릿의 설명·HTML 주석은 작성에 필요한 만큼만 제공하며, 운영 절차나 긴 안내가 사용자 문서에 관성적으로 복사되지 않게 한다.

Requirement ID·안정적인 경로·전용 ID 조회 명령·활성/archive 구분·불필요한 frontmatter 및 실행 상태 배제는 유지한다. PRODUCT의 지속적인 제품 규칙, ARCHITECTURE의 설계 계약, Requirement의 변경 목표를 구분한다. Skill의 수정 권한·정책 확정 원칙·Quality Guidance·Ready Check와 실제 Merge 및 전체 충족 확인 뒤 archive하는 Lifecycle을 유지한다. 완료·보관 문서를 현재 변경을 위해 재활성화하지 않는다. 식별·rename·source 호환성은 R-071의 기존 규칙을 따른다.

### ExecPlan의 실제 작업과 근거

Planner는 현재 명세·관련 Requirement·코드·테스트·기존 작업과 PR을 대조해 실제 미충족 범위만 계획한다. 기존 helper·테스트·공통 구조를 먼저 재사용하고, 독립적으로 구현·검증할 수 있는 목표로 분할한다. 과도한 세분화·무관한 목표 결합·이미 충족한 작업의 중복 생성을 피한다. 관련 미착수 ExecPlan이 있으면 신규 생성보다 개정을 우선한다. 다른 계획의 목표·검증·dependency 영향도 확인하되 변경 권한은 R-061·R-082와 Manager가 제공한 snapshot·mode를 따른다.

`id`, `title`, `sources`, `depends_on`, `complexity`, `risk`, `priority`와 필요한 `draft`의 형식·의미를 유지하며 실행 상태는 SQLite에 둔다. complexity·risk는 R-052의 남은 설계·추론 난도와 실제 실패 영향·복구 가능성으로 판단하고 중요한 근거를 간결하게 설명한다. 파일 수·코드 길이만으로 높이지 않는다.

| 본문 | 작성·갱신 기준 |
|---|---|
| Purpose | 이 작업의 범위와 구현 결과를 짧게 설명한다. 상위 Requirement 전체를 반복하지 않는다. |
| Acceptance Criteria | 현재 작업이 책임지는 구체적인 완료 결과를 적는다. 상위 목표·범위를 축소하거나 그대로 전부 복사하지 않는다. |
| Implementation | 완료 여부를 판단할 작업 체크리스트, 주요 구현 방향·책임 경계, 실제 확인한 코드·테스트·설정·문서 경로와 파일별 변경 목적을 포함한다. 필요한 순서·계약·안전 조건을 명시하고 기존 구조 재사용을 우선한다. 안전하게 결정할 함수별 절차는 불필요하게 고정하지 않는다. |
| Validation | 이 작업과 직접 관련된 추가·수정 테스트, 회귀 조건, 필요한 정상·실패·경계·동시성 시나리오와 기대 결과·확인한 테스트 경로만 적는다. 일반 전체 verify 실행 순서·스크립트 경로·실행 책임·Reviewer 승인 절차는 반복하지 않는다. |
| Progress | 핵심 완료·잔여 체크리스트와 중요한 진행 상태를 유지한다. 매 Planner 실행의 조사 기록·날짜별 SHA·snapshot token·재시도를 누적하지 않는다. 복구에 필요한 정보는 보존하거나 실행 이력으로 연결한다. 미확인 검증을 완료로 표시하지 않는다. |
| Decision Log | 유지보수에 의미 있는 선택·중요 대안·핵심 이유·위험 완화·향후 제약을 남긴다. 다른 절이나 상세 실행 로그를 반복하지 않는다. |

기존 여섯 본문 제목은 유지한다. 관련 파일은 실제 조사로 확인하며 예정된 신규 파일은 예정임을 구분한다. 존재하는 것처럼 경로를 추측하지 않는다. Implementation과 Progress는 작업 정의와 수행 현황의 역할을 구분하고 같은 설명을 중복 복사하지 않는다.

여러 Requirement를 참조하면 `sources`를 유지하면서 각 작업 항목과 관련 완료 조건의 근거를 Requirement ID와 조건의 짧은 설명·참조로 연결한다. 공유 구현은 여러 근거를 연결해 부분 변경·삭제 때 남은 목표를 식별할 수 있게 한다. 모든 Requirement에 새 기준 ID나 복잡한 metadata를 일괄 추가하지 않는다. 의미 연결과 변경 반영은 R-082, 삭제 영향 판단은 R-055를 따른다.

### 적용 범위와 우선순위

새 작성·실제 개정 대상부터 적용한다. 기존 활성·archive 문서 전체를 양식 변경만으로 일괄 재작성하지 않는다. 필드·제목을 읽는 코드·fixture가 있으면 실제 사용을 확인해 호환성을 함께 보존하고, 문서 외형 변경만으로 기존 파싱·진행·검증 근거를 깨뜨리지 않는다. 일반 verify와 최종 Review·Merge 책임 및 실행 흐름은 Manager의 코드와 R-086 등 기존 계약을 유지한다.

| 우선순위 | 이 문서의 개선 목표 | 연관 기능의 원본 |
|---|---|---|
| P0 | 활성 Requirement 재사용·명세 완성도, Implementation 체크리스트·파일, 작업별 Validation | 변경 동기화 R-082, 삭제·취소 R-055, 사용자 판단·입력 정리 R-061 |
| P1 | Requirement 항목 역할·선택 절, Progress·Decision Log, 최소 근거 연결, 관련 절 통합·Ready Check | 공유 작업의 변경·삭제 시 목표 보존은 R-082·R-055 |
| P2 | Skill·Planner·공통 지침·PLANS의 중복 제거, 템플릿 설명, 참고 자료·용어·참조 정리 | 기존 권한·메타데이터·운영 안전 계약 유지 |

우선순위는 중요도이며 실행 dependency가 아니다. 후속 Planner는 이미 구현된 범위와 기존 미완료 작업을 확인한 뒤 실제 분할·순서를 결정한다. 관련 기능은 G-244와 G-257~G-261의 목표를 먼저 대조하며 새 중복 작업으로 대체하지 않는다.

후속 변경 영향은 다음 확인 지점에서 검토한다. 이 표는 코드 구현 절차나 이번 세션의 수정 권한을 추가하지 않는다.

| 범위 | 확인한 원본·관련 파일 | 필요한 변화·보존 |
|---|---|---|
| 작성 절차·양식 | `.agents/skills/specification-docs/SKILL.md`, `docs/REQUIREMENT.template.md`, `docs/AGENTS.planner.md`, `docs/PLANS.md`, `docs/AGENTS.common.md` | 작성 절차·본문 기준을 책임 원본에 모으고 다른 파일은 필요한 참조로 연결한다. Skill 권한·Ready Check·Lifecycle과 Planner 권한은 보존한다. |
| 제품·설계 | `docs/PRODUCT.md`, `docs/ARCHITECTURE.md` | 구현 뒤 지속할 규칙·책임·호환 계약만 반영한다. 현재 동작과 미구현 목표를 구분한다. |
| 형식·근거·변경 감지 | `loop_manager_internal/catalog/execplan_catalog.py`, `frontmatter.py`, `requirement_sources.py`; `loop_manager_internal/planning/input_fingerprints.py`, `planner_validation.py` | 실제 파싱 의존성과 source·본문 영향 판단을 확인한다. 외형 개선만으로 metadata·ID·graph·입력 지문 계약을 바꾸지 않는다. |
| 실행 DB·게시·결정 | `loop_manager_internal/storage/execplan_catalog_state.py`, `planning_publication_state.py`, `execplan_draft_state.py`; `loop_manager_internal/catalog/remote_deletions.py`, `execplan_drafts.py` | R-082·R-055·R-061이 기능 변경을 담당한다. 이 문서의 양식 개선만으로 실행 상태·소유권·감사를 초기화하지 않는다. |
| 테스트·fixture | `tests/test_requirement_id_query.py`, `tests/test_execplan_catalog.py`, `tests/test_requirement_sources.py`, `tests/test_execplan_drafts.py`, `tests/test_incremental_planning.py`, `tests/test_execplan_catalog_state.py`, `tests/test_planning_publication.py`, `tests/test_planning_requirement_moves.py` | 실제 문서 원본을 강제 비교하는 검사와 파서 fixture를 확인한다. 문서 예시·호환·source·draft·원자 적용·archive의 의미 있는 회귀를 보존하고 운영 원문·문장 수를 기계적으로 고정하지 않는다. |

## Acceptance Criteria

- 제목·키워드가 달라도 목적·제품 규칙·시나리오가 같은 활성 Requirement를 찾아 기존 ID·경로의 관련 절을 갱신한다. 여러 활성 문서가 영향을 받으면 필요한 문서들을 갱신하며 중복 Requirement를 생성하지 않는다. 조회 실패·내용 확인 불가에서는 무관하다고 단정해 신규 생성하지 않는다.
- 관련 활성 문서가 없거나 독립 목표를 결합하기 부적절한 경우에만 전용 ID 명령의 새 ID로 작성한다. archive 문서의 수정·복원·ID 재사용은 없다.
- 필요한 정상·실패·예외·권한·상태·보존·복구·완료 조건이 편집 전후에 유지된다. 미결정 제품 정책은 질문과 영향으로 구분하며 해소 전 확정된 활성 명세로 게시하지 않는다. 답변 뒤에는 본문에 통합되고 불필요한 질문 절이 남지 않는다.
- Context·Requirement·Acceptance Criteria로 목적·동작·확인 결과를 구분할 수 있다. Product Impact·Non-Goals가 필요 없는 문서는 빈 절 없이 작성할 수 있고, 필요한 장기 규칙·범위 제한은 생략되지 않는다. Ready Check의 점검을 별도 본문 절로 모두 복사하지 않는다.
- 문서의 첫 부분에서 결과를 이해할 수 있고 중복 규칙·대체된 설명·불필요한 안내가 정리된다. 간결화를 위해 중요한 조건을 삭제하거나 줄·항목·토큰 수 제한을 적용하지 않는다.
- 기존 코드·테스트·helper와 미착수 작업으로 충족 가능한 범위는 재사용·개정하고 이미 충족한 목표를 새 작업으로 만들지 않는다. 작업마다 독립적으로 구현·검증할 목표가 있으며 무관한 목표 결합이나 의미 없는 세분화가 없다.
- ExecPlan의 Implementation만 읽어 수행할 체크리스트·주요 책임 경계·확인한 관련 파일과 각 변경 목적을 파악할 수 있다. 필요한 안전 순서가 있고 예정 파일과 실제 파일을 구별하며 근거 없는 경로·함수 절차를 고정하지 않는다.
- Validation은 해당 작업의 테스트 시나리오·기대 결과·확인한 경로와 관련 회귀 조건에 집중한다. 일반 전체 verify 명령·운영 순서·승인 절차가 없어도 기존 Manager 검증·Review·Merge gate는 유지된다.
- Progress에서 실제 완료한 핵심 항목과 잔여 작업을 구별할 수 있다. 단순 조사·SHA·재시도 기록의 누적 없이 필요한 복구 근거는 보존·연결되고 미실행 검증은 완료로 표시되지 않는다.
- Decision Log에는 의미 있는 기술 선택과 이유·위험·제약이 남고 Implementation·Acceptance Criteria·상세 실행 로그의 반복은 없다.
- 복수 Requirement 작업의 항목·공유 구현·관련 완료 조건을 각 근거로 연결할 수 있어 한 근거의 변경·삭제 영향과 남은 목표를 구분할 수 있다. 전체 Requirement의 새 식별자·metadata 일괄 도입은 없다.
- 기존 metadata의 값·의미와 여섯 본문 제목, source·dependency 파싱, SQLite 실행 상태·소유권·실패·검증·PR 이력이 보존된다. complexity·risk의 근거는 실제 남은 난도·실패 영향·복구 가능성으로 설명된다.
- 새 문서와 필요한 개정에 개선된 양식을 적용하고, 기존 활성·archive 문서는 양식만을 이유로 일괄 재작성하지 않는다. 필수 파서·fixture 호환과 안정적인 경로·ID를 확인할 수 있다.
- Skill·Planner·공통 지침·PLANS에서 같은 규칙을 중복 관리하지 않고 책임 원본·필요한 참조를 확인할 수 있다. 지침 축소가 역할 쓰기 권한·snapshot·사용자 판단·선행 Merge·복구·최종 검증 경계를 약화하지 않는다.

## Non-Goals

- 기존 검증된 운영 구조·ID 체계·SQLite 실행 모델·Agent 역할을 전면 교체하지 않는다.
- 작성 품질 개선을 별도 Agent·설정·외부 서비스나 문서 길이 자동 제한 기능으로 확장하지 않는다.
