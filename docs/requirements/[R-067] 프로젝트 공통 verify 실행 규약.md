# [R-067] 프로젝트 공통 verify 실행 규약

## Summary

프로젝트가 명시적으로 선택하는 버전 있는 공통 verify 규약과 언어별 adapter 경계를 제공해 수집·결과 의미는 프로젝트가, 부하 배정·예약·프로세스·진단은 공통 runner가 맡는다. unittest와 비Python 도구 예제를 같은 기반으로 검증하되 실제 runner의 standalone·coordinated 통합 검증은 일반 테스트 자식 밖의 신뢰된 전체 verify 단계에서 수행한다. Manager·단독 실행의 필수 범위와 OS별 종료·임시 경로·가드 전파를 보존하고 순번·자원 배정 대기는 timeout에서 제외해 실제 실행 시간으로 판정한다. 미도입 경로와 부분/전체 결과를 구분하며 잘못된 연결이나 불완전 결과를 성공으로 우회하지 않는다.

## Context

Loop Manager가 공통 verify 실행 규약과 runner를 제공해, 규약에 연결한 프로젝트가 시간 기록·부하 기반 병렬 배정·프로세스 정리를 함께 사용하게 한다. 프로젝트마다 자원 조율 기능을 복사하지 않고 테스트 도구별 수집·실행·결과 변환만 연결한다.

기존 시간 기록·실제 Agent 호출 배제와 [R-065](%5BR-065%5D%20실제%20부하%20기반%20verify%20병렬%20실행.md)의 자원 조율 원칙을 재사용하되, 다른 프로젝트의 선택적 연결은 이 Requirement에서 별도로 정의한다. 일부 구현이나 문서 변경만으로 전체 규약·OS 격리·실측의 완료를 선언하지 않는다.

공통 runner의 실효 동작을 확인하는 예제를 일반 guard 적용 테스트 자식 안에서 중첩 실행하면 자식의 조율 인증·예산 환경 격리로 하위 자원 대기가 상위 timeout에 반영되지 않을 수 있다. 테스트 격리를 약화하거나 CPU 배정을 강제하지 않고, runner 통합 검증의 신뢰된 실행 경계와 대기 관측 책임을 명확히 한다.

[테스트 시간 절감 분석](chatgpt-conversation://6ac824ad-6efc-83e8-b289-d5654a16670a)은 가드의 `runpy` 로딩과 일반 import가 별개 캐시를 사용해 중복 설치될 수 있고, Windows 자식 종료 대기와 실제 임시 경로의 진단이 부족함을 확인했다. 자체 Windows 스크립트는 임시 경로를 사용자 프로필 아래 기본값으로 덮어쓰므로 checkout 이동이나 실행 전 `TEMP` 변경만으로 테스트 디스크를 선택할 수 없다. 조사와 정적 코드 확인은 실제 Windows의 지연 비중·절감량 측정을 대신하지 않는다.

## Requirement

### 선택적 도입과 호환성

- 프로젝트는 버전이 있는 명시적 실행 규약으로 공통 runner 사용을 선택한다. Loop Manager 내부 파일의 존재나 테스트 도구 추측만으로 적용하지 않는다.
- 선택하지 않은 프로젝트는 기존 verify 실행·timeout·종료 코드 처리를 유지한다. 기존 프로젝트 전체를 자동 전환하지 않는다.
- 연결한 프로젝트의 규약 오류, 지원하지 않는 버전·adapter, 필수 실행 도구 부재는 실패로 진단한다. 이를 미도입으로 취급해 기존 경로로 조용히 우회하거나 필수 검증을 생략하지 않는다.
- Manager 실행과 개발자의 단독 실행은 같은 필수 검증·결과 의미를 유지한다. 단독 실행에는 공통 runner의 설치·호출 방법을 제공하며, Manager와의 자원 조율 여부를 기록한다. 실행 기반이 없으면 성공으로 처리하지 않는다.

### 공통 실행과 프로젝트 책임

- Manager는 실제 허용 CPU·부하·메모리와 미반영 예약으로 신규 실행량을 코드로 결정한다. 등록 프로젝트 수·활성 verify 수로 고정 분할하지 않으며 모델을 자원 배분에 사용하지 않는다. `auto`·양의 정수 상한·직렬 `1`은 한 설정 경계에서 검증한다.
- 같은 Manager 실행 인스턴스의 여러 연결 프로젝트는 같은 예약 조율을 사용한다. 기존 verify 등 규약 밖 작업의 부하도 관측에 반영한다. 단독 실행과 별도 Manager 인스턴스 사이의 예약 공유를 보장한다고 표시하지 않는다.
- 프로젝트 adapter는 현재 후보 revision에서 전체 수집 범위, 실행 단위와 테스트 결과를 제공한다. 공통 runner는 배정·프로세스 실행·시간 및 결과 집계·중단 진단을 맡는다. 테스트 언어를 Python으로 제한하지 않으며, 테스트 환경과 의존성은 프로젝트가 선택한 것을 사용한다.
- 공통 규약은 프로세스의 명령·입출력·실행 identity·결과·중단 계약을 정의한다. 테스트 파일 형식, assertion·fixture API와 테스트 작성 언어를 통일하지 않는다. adapter는 테스트 도구의 기존 수집·실행·reporter 또는 구조화된 결과를 이 계약으로 변환한다.
- adapter는 지원 도구·버전과 수집 범위 확인·테스트별 결과 및 시간·독립 단위 실행·내부 병렬 제어·중단 기록의 지원 근거를 명시한다. 도구의 기능을 추측하거나 자유 형식 stdout에서 임의로 성공을 판정하지 않는다. 필수 계약을 확인할 수 없는 도구는 연결 완료로 처리하지 않는다.
- 독립 실행을 보장한 단위만 병렬로 배정한다. fixture·DB·경로·포트의 격리는 프로젝트가 보장하고, 공유 자원이나 순서 의존이 있는 단위는 직렬 단계로 선언한다. 필수 compile·lint·build 등의 순서와 검증 범위도 보존한다.
- 내부 병렬 실행은 adapter가 공통 배정 예산에 포함해 제어할 수 있어야 한다. 초기 지원 adapter는 내부 병렬을 끄고 독립 프로세스를 배정한다. 이를 제어할 수 없는 도구는 병렬 지원으로 선언하지 않는다.
- 관측 실패는 이유를 기록하고 추가 확대를 중단한 뒤 직렬로 축소한다. 확인된 자원 부족에서는 신규 배정을 기다릴 수 있다. 실행 중인 테스트를 부하 조절 목적으로 종료하거나 timeout을 자동 늘리지 않는다.

### 가드와 자체 테스트 환경

- 같은 프로세스에서 다른 로딩 경로로 가드 설치를 반복 호출해도 한 번만 설치돼야 한다. 동일 subprocess 환경을 wrapper와 audit 경로에서 불필요하게 반복 준비하지 않으며, 검증할 보안 검사 자체를 캐시하거나 생략하지 않는다.
- 명시적 `env`와 상속 `env` 모두 실제 자식에 전달되는 환경에서 Agent/API 차단·가드 전파와 조율 인증값 제외를 유지한다. 부모 환경과 호출자가 제공한 환경을 보존하며 중첩 Python 자식의 보호와 다른 worktree의 package 선택을 깨뜨리지 않는다. 정제·시작 실패와 중단에서도 기존 종료 확인·예약 처리를 유지한다.
- 자체 Windows의 단독·Manager verify에서 테스트 임시 경로를 명시적으로 선택할 수 있어야 한다. 미지정 시 현재 기본값 `%USERPROFILE%\.cache\loop-manager\verify\tmp`를 유지하고 상대 경로는 실행 checkout 기준으로 해석한다. 최종 절대 경로를 Python 시작 전에 `TEMP`·`TMP`·`TMPDIR`에 적용하고 진단에 기록한다. 다른 등록 프로젝트의 테스트 환경을 일괄 변경하지 않는다.
- 지정 경로 생성·사용이 실패하면 경로 오류로 종료하며 다른 경로로 조용히 대체하지 않는다. 정상·실패·예외 뒤 부모 환경·인코딩·작업 경로를 복원하고 공유 임시 루트 전체를 삭제하지 않아 다른 실행의 파일을 보존한다.

### 실제 runner 통합 검증의 실행 경계

- 실제 공통 runner를 검증하는 Python·비Python 예제의 standalone·coordinated 정상 및 도구 고유 실패 검증은 일반 guard 적용 unittest 자식 안의 중첩 runner가 아니라 전체 verify를 소유하는 신뢰된 상위 오케스트레이션의 별도 필수 통합 단계에서 실행한다. 일반 테스트의 가드 안에 명령만 추가해 다시 runner를 호출하는 것은 실행 경계 분리로 인정하지 않는다.
- Manager 전체 verify와 단독 전체 verify는 지원 플랫폼·도구에 따른 동일한 필수 단계와 결과 계약을 실행한다. 통합 단계도 기존 전체 verify의 단계 순서·한도·입력 revision에 귀속되고 부분 verify나 별도의 선택 실행만으로 전체 성공을 대체하지 않는다. 미지원 플랫폼의 명시적 skip과 지원 환경의 필수 도구 부재·실행 실패를 구분한다.
- 신뢰된 상위 단계만 실제 runner 시작·조율 접속·예산 관측을 소유한다. 일반 테스트 자식과 예제 실행 자식에는 Agent/API 거부, 가드 전파, 조율 인증값·예산 제어값 격리를 그대로 적용한다. 실제 coordinated 실행을 확인하려고 인증값을 일반 자식에게 전달하거나 guard를 해제하지 않는다.
- 전체 manifest·단계 결과·진단에서 standalone과 coordinated의 실제 실행 identity, runner·adapter와 검증 범위, 단계 완료와 결과, 조율 session·예약·해제 등 실제 접속·배정 근거를 대조한다. 조율을 요청했다는 선언만으로 coordinated 성공으로 처리하지 않으며, 예제의 의도된 native 실패와 인프라·timeout 실패를 구분한다. 실패·취소·timeout 때 하위 진단과 종료 근거를 임시 경로 정리 전에 보존하되 비밀값을 노출하지 않는다.

### 결과·시간·복구

- 실행 revision·규약 및 adapter 버전·테스트 도구·명령·실행 단위와 수집 범위를 결합해 기록한다. 테스트 결과와 단위 완료 결과를 대조하고 누락·중복·수집 오류·비정상 종료·불완전한 결과를 성공으로 처리하지 않는다.
- 도구 고유의 성공·실패·오류·skip·expected failure 등의 의미를 adapter가 보존한다. 테스트가 없는 것이 정상인 단계와 테스트 수집 누락을 구분한다. 일반 compile·build 명령의 종료 코드만으로 테스트별 결과를 갖춘 것으로 표시하지 않는다.
- 테스트와 실행 단위의 시작·종료·결과·소요 시간, fixture·수집·공통 준비·자원 대기·정리 비용을 확인할 수 있어야 한다. 강제 중단 전 완료 기록과 진행 위치를 보존하며, 미종료 항목의 완료를 합성하지 않는다. 이전 결과는 현재 후보 성공을 대신하지 않는다.
- 모듈 결과 파일 확인, 해당 worker의 남은 자식 종료 확인과 다음 모듈 배정 시점을 같은 실행·worker·모듈에 연결해 기록한다. Windows Job의 자식 대기도 테스트 본체·배정 대기와 구분하며 자식 생존·종료 불명 동안 worker 재사용과 예약 회수를 앞당기지 않는다.
- 자체 verify는 기존 기록 경로를 재사용한다. 단독 실행의 `.cache/verify/<실행 ID>/summary.json`, Manager 실행의 `<state-dir>/logs/verify/<실행 ID>/summary.json`에서 배정 변화·선택 임시 경로·Git 호출 수와 누적 시간·테스트/수집/준비/정리·전체 경과 시간을 대조할 수 있어야 한다. 비밀값이나 전체 환경은 출력하지 않는다. 비용 비교는 R-065의 같은 환경·범위와 누적/경과 시간 구분을 따른다.
- 순번·자원 배정 대기를 제외한 수집·준비·검증·정리의 실제 경과 시간을 verify 시간 상한에 적용한다. 제외 가능한 구간, 실행 중 자식과 병렬 시간의 계산, 같은 실행의 남은 예산 보존은 [R-091의 실제 실행 시간 기준](%5BR-091%5D%20프로젝트%20공정%20배정과%20우선순위%20기반%20병렬%20작업.md#순번-대기와-실제-실행-시간)을 따른다. 실패·timeout·취소·runner 또는 통신 오류에서는 해당 자식 종료나 미시작을 확인한 예약만 회수한다. 종료 불명은 안전 오류와 예약으로 남기며 다른 verify의 프로세스·예약은 보존한다.
- 실행 명령·경로·결과 파일·통신은 선택된 worktree와 verify identity에 연결한다. 임의 shell 문자열 해석, 다른 작업의 제어, 설정·자격 증명의 일반 전달과 비밀값 진단 노출을 허용하지 않는다.

### 부분 실행과 전체 검증의 구분

R-086의 명시적 부분 unittest 실행은 같은 discovery manifest·project interpreter·core/adapter·자원 예약·종료 정책을 사용한다. 선택 모듈의 필수 결과를 모두 검사하며 미선택 모듈은 NOT_SELECTED로 기록한다. 부분 PASS/FALLBACK은 전체 verify 성공이나 필수 command 완료를 만들지 않는다. 이후 전체 실행은 기존 전체 manifest와 필수 command를 유지한다. 전체/부분 또는 서로 다른 선택 범위의 시간 자료를 동일 검증 범위의 비용 개선으로 해석하지 않는다.

### 지원 범위와 자동 작업

- 공통 기반과 Loop Manager 자체 unittest 연결을 먼저 제공하고, 비Python adapter와 프로젝트 연결을 후속 확장한다. 자체 연결만으로 언어 독립성과 전체 Requirement의 완료를 확정하지 않는다. 후속 작업에서도 같은 규약·자원 조율·검증 기준을 사용한다.
- Python unittest와 비Python 언어의 실제 테스트 도구 하나를 최소 지원 범위로 삼는다. 도구 선택은 이미 쓰는 환경·의존성과 공식 수집·reporter 기능을 확인해 확정한다. 서로 다른 언어의 독립 소규모 예제를 같은 core에 연결해 공통화의 효과와 한계를 검증한다. 이후 도구는 동일 규약과 적합성 검증을 통과한 adapter를 추가해 연결한다.
- 연결 프로젝트의 Worker는 새로 작성·변경하는 테스트가 adapter의 수집 범위와 격리 계약을 지키도록 유지한다. 실행량·시간 기록·예약 로직을 테스트마다 작성하지 않는다. 실제 Agent CLI·API 호출은 mock·stub·고정 출력으로 검증하고 필요한 실제 Git·DB·운영체제 검증은 유지한다.
- 정적 adapter 작성·검토·연결 판단 기준은 R-064의 기존 `docs/AGENTS.worker.md`·`docs/AGENTS.reviewer.md`·`docs/AGENTS.planner.md`에 각각 반영한다. 모든 역할에 적용되는 경계만 common에 유지하며 common+해당 역할을 instruction으로 전달하는 기존 방식을 재사용한다. 작업 prompt에는 프로젝트의 선택 adapter·도구 버전·참조 문맥만 연결한다. 프로젝트별·언어별 사본이나 별도 배포 경로를 만들지 않고 합친 파일은 저장소 밖 실행용으로만 사용하며 커밋하지 않는다. adapter 변경 시 진행 작업의 고정 원본 버전과 성공 재사용 조건을 지킨다.
- 지원하지 않는 도구를 쓰는 프로젝트는 기존 verify를 유지한다. 신규 adapter나 기존 프로젝트 연결 작업이 필요하면 해당 작업 범위에서 계획하며, 무관한 기능 작업에 전체 테스트 개편을 포함하지 않는다.

## Acceptance Criteria

- 명시적으로 연결한 프로젝트만 공통 runner를 사용한다. 미연결 프로젝트의 기존 verify가 유지되고, 잘못된 연결·버전·도구 부재는 성공 또는 무언의 fallback으로 처리되지 않는다.
- Loop Manager 자체 unittest와 서로 다른 두 언어·테스트 도구의 독립 예제가 자원 조율 코드 복사 없이 같은 runner로 실행된다. core는 unittest·프로젝트 언어의 타입에 의존하지 않으며 adapter 추가 경계와 규약 적합성 검증을 제공한다.
- 일반 unittest 자식의 가드를 유지한 채 Python·비Python 실제 runner 예제를 신뢰된 별도 필수 통합 단계에서 standalone·coordinated 각각 정상·native 실패로 검증한다. Manager와 단독 전체 verify의 manifest에 해당 단계가 포함되고 필수 단계 누락·실패·timeout은 전체 PASS가 아니다.
- 실제 coordinated 검증은 조율 session·예약·PID 연결 및 해제의 관측 근거를 확인하며, 조율 요청값만으로 성공을 합성하지 않는다. 신뢰된 상위 단계 밖 자식의 Agent/API 차단·인증값 격리와 종료 진단은 유지되고, 실패 시 하위 manifest·실행/대기·종료 기록을 정리 전에 확보한다.
- 직렬·병렬 실행의 수집 범위·fixture 계약·필수 단계·결과 및 종료 코드가 일치한다. 공유 자원·순서 의존 단계는 직렬이고 내부 병렬 실행이 배정 예산을 우회하지 않는다.
- 두 연결 프로젝트의 동시 시작·서로 다른 실제 부하·여유 회복에서 코드 배정과 공유 예약이 확인된다. 관측 실패·낡은 값·사용자 상한·자원 부족의 처리 이유를 기록한다.
- 잘못된 manifest·결과 형식, 결과 누락·중복, 수집 실패·자식 비정상 종료·통신 단절이 실패로 드러나고 다른 프로젝트의 작업을 손상하지 않는다.
- Windows·Linux에서 timeout·취소·시작 실패 뒤 자식 종료 또는 미시작 확인과 해당 예약 회수가 확인된다. 종료 불명은 성공이나 여유 자원으로 계산하지 않는다.
- 테스트·fixture·준비·대기·정리와 중단 위치의 진단이 보존된다. Worker의 제한된 실패 피드백으로 해당 자료를 찾을 수 있고 비밀값은 포함하지 않는다.
- 결과 확인·자식 종료 확인·다음 배정의 시점과 대기 시간을 구분한다. 자식 생존·종료 불명 동안 재사용·예약 회수가 없으며 실패·timeout·취소에서도 기존 종료·보존 회귀가 통과한다.
- Manager·단독 runner와 각 adapter에서 순번·자원 배정 대기만으로 timeout이 생기지 않는다. 실제 처리의 시간 초과는 계속 실패하며 중간 대기·재개로 실행 시간 예산을 초기화하거나 병렬 자식의 시간을 중복 합산하지 않는다.
- `runpy` 로딩과 일반 import를 함께 사용하는 새 프로세스에서 중복 hook·wrapper 설치와 동일 환경의 반복 준비가 없다. 명시/상속 환경·중첩 자식·Agent/API 거부·다른 worktree import·부모와 호출자 환경 보존·실제 전달 인증값 제외 및 정제/시작 실패 회귀가 통과한다.
- 자체 Windows의 미지정 기본값과 명시적 절대/상대 임시 경로가 실제 Python의 임시 파일 선택에 적용되고 최종 경로가 진단에 남는다. 경로 오류는 실패하며 정상·실패·예외 후 환경·인코딩·cwd와 기존 공유 파일이 보존된다.
- Manager와 단독 전체 실행이 같은 필수 범위를 검증한다. 명시적 부분 실행은 R-086에 따라 별도 결과로 구분하고 전체 필수 검증을 대체하지 않는다. 조율 부재와 runner 부재를 구분하며, 불완전한 과거 결과를 재사용하지 않는다.
- 두 언어의 테스트가 각각 기존 assertion·fixture·도구를 유지하면서 공통 manifest·결과·진단 계약을 지킨다. 실제 common+해당 역할 instruction에서 필요한 adapter 작성·검토·계획 지침을 확인할 수 있고 작업 prompt에는 정적 규칙이 중복되지 않는다. 정상 테스트에서 실제 Agent 호출을 하지 않으며 지원 근거 없는 기능이나 일반 명령의 종료 코드만으로 테스트 계약 충족을 표시하지 않는다.
- 같은 환경·revision·검증 범위에서 직렬·병렬, 단일·동시 verify의 시간·메모리·예약 및 결과를 실제 비교한다. 실측 전 절감률을 확정하지 않는다.

## Product Impact

- 공통 verify는 프로젝트가 선택적으로 연결하는 Loop Manager 기능이 된다.
- 자원 조율·실행·진단은 Manager가 제공하고, 수집·결과 의미·격리는 프로젝트와 adapter가 책임진다.
- Worker는 연결 계약에 맞는 테스트·verify를 유지하고 Manager는 Agent 밖에서 전체 검증한다.

## Non-Goals

- 기존 등록 프로젝트의 일괄 전환, 모든 테스트 도구 adapter의 동시 구현.
- R-091이 정하는 동일 프로젝트의 여러 ExecPlan·Worker 병렬 배정 정책 자체의 변경 또는 여러 호스트·Manager 인스턴스·단독 runner 사이의 예약 공유.
- 새 상주 서비스·외부 모니터링·범용 작업 DAG·adapter 배포 marketplace·새 sandbox infrastructure.
- 기존 전체 검증 축소, 필수 테스트 skip, 자동 timeout 증가, 특정 절감률·프로세스의 CPU 사용량에 대한 새로운 OS 강제 제한 보장.
- Git·게시·Review·Merge 경계의 완화.
- Defender·다른 보안 제품 설정의 자동 변경과 사용자 설정·다른 등록 프로젝트의 테스트 환경 일괄 변경.
