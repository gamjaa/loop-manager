# [R-067] 프로젝트 공통 verify 실행 규약

## Context

Loop Manager가 공통 verify 실행 규약과 runner를 제공해, 규약에 연결한 프로젝트가 시간 기록·부하 기반 병렬 배정·프로세스 정리를 함께 사용하게 한다. 프로젝트마다 자원 조율 기능을 복사하지 않고 테스트 도구별 수집·실행·결과 변환만 연결한다.

PR #138은 Loop Manager 자체 unittest용 구현을 준비했으며 아직 Merge·전체 검증·실측 완료의 근거가 아니다. R-058의 시간 기록·실제 Agent 호출 배제와 R-065의 자원 조율 원칙을 재사용하되, 다른 프로젝트의 선택적 연결은 이 Requirement에서 별도로 정의한다.

## Requirement

### 선택적 도입과 호환성

- 프로젝트는 버전이 있는 명시적 실행 규약으로 공통 runner 사용을 선택한다. Loop Manager 내부 파일의 존재나 테스트 도구 추측만으로 적용하지 않는다.
- 선택하지 않은 프로젝트는 기존 verify 실행·timeout·종료 코드 처리를 유지한다. 기존 프로젝트 전체를 자동 전환하지 않는다.
- 연결한 프로젝트의 규약 오류, 지원하지 않는 버전·adapter, 필수 실행 도구 부재는 실패로 진단한다. 이를 미도입으로 취급해 기존 경로로 조용히 우회하거나 필수 검증을 생략하지 않는다.
- Manager 실행과 개발자의 단독 실행은 같은 필수 검증·결과 의미를 유지한다. 단독 실행에는 공통 runner의 설치·호출 방법을 제공하며, Manager와의 자원 조율 여부를 기록한다. 실행 기반이 없으면 성공으로 처리하지 않는다.

### 공통 실행과 프로젝트 책임

- Manager는 실제 허용 CPU·부하·메모리와 미반영 예약으로 신규 실행량을 코드로 결정한다. 등록 프로젝트 수·활성 verify 수로 고정 분할하지 않으며 모델을 자원 배분에 사용하지 않는다. `auto`·양의 정수 상한·직렬 `1`은 한 설정 경계에서 검증한다.
- 같은 Manager 실행 인스턴스의 여러 연결 프로젝트는 같은 예약 조율을 사용한다. 기존 verify 등 규약 밖 작업의 부하도 관측에 반영한다. 단독 실행과 별도 Manager 인스턴스 사이의 예약 공유를 보장한다고 표시하지 않는다.
- 프로젝트 adapter는 현재 후보 revision에서 전체 수집 범위, 실행 단위와 테스트 결과를 제공한다. 공통 runner는 배정·프로세스 실행·시간 및 결과 집계·중단 진단을 맡는다. 테스트 언어를 Python으로 제한하지 않으며, 테스트 환경과 의존성은 프로젝트가 선택한 것을 사용한다.
- 공통 규약은 프로세스의 명령·입출력·실행 identity·결과·중단 계약을 정의한다. 테스트 파일 형식, assertion·fixture API와 테스트 작성 언어를 통일하지 않는다. adapter는 테스트 도구의 기존 수집·실행·reporter 또는 구조화된 결과를 이 계약으로 변환한다.
- adapter는 지원 도구·버전과 수집 범위 확인·테스트별 결과 및 시간·독립 단위 실행·내부 병렬 제어·중단 기록의 지원 근거를 명시한다. 도구의 기능을 추측하거나 자유 형식 stdout에서 임의로 성공을 판정하지 않는다. 필수 계약을 확인할 수 없는 도구는 연결 완료로 처리하지 않는다.
- 독립 실행을 보장한 단위만 병렬로 배정한다. fixture·DB·경로·포트의 격리는 프로젝트가 보장하고, 공유 자원이나 순서 의존이 있는 단위는 직렬 단계로 선언한다. 필수 compile·lint·build 등의 순서와 검증 범위도 보존한다.
- 내부 병렬 실행은 adapter가 공통 배정 예산에 포함해 제어할 수 있어야 한다. 초기 지원 adapter는 내부 병렬을 끄고 독립 프로세스를 배정한다. 이를 제어할 수 없는 도구는 병렬 지원으로 선언하지 않는다.
- 관측 실패는 이유를 기록하고 추가 확대를 중단한 뒤 직렬로 축소한다. 확인된 자원 부족에서는 신규 배정을 기다릴 수 있다. 실행 중인 테스트를 부하 조절 목적으로 종료하거나 timeout을 자동 늘리지 않는다.

### 결과·시간·복구

- 실행 revision·규약 및 adapter 버전·테스트 도구·명령·실행 단위와 수집 범위를 결합해 기록한다. 테스트 결과와 단위 완료 결과를 대조하고 누락·중복·수집 오류·비정상 종료·불완전한 결과를 성공으로 처리하지 않는다.
- 도구 고유의 성공·실패·오류·skip·expected failure 등의 의미를 adapter가 보존한다. 테스트가 없는 것이 정상인 단계와 테스트 수집 누락을 구분한다. 일반 compile·build 명령의 종료 코드만으로 테스트별 결과를 갖춘 것으로 표시하지 않는다.
- 테스트와 실행 단위의 시작·종료·결과·소요 시간, fixture·수집·공통 준비·자원 대기·정리 비용을 확인할 수 있어야 한다. 강제 중단 전 완료 기록과 진행 위치를 보존하며, 미종료 항목의 완료를 합성하지 않는다. 이전 결과는 현재 후보 성공을 대신하지 않는다.
- 수집·자원 대기·검증·정리는 기존 전체 verify 시간 상한에 포함한다. 실패·timeout·취소·runner 또는 통신 오류에서는 해당 자식 종료나 미시작을 확인한 예약만 회수한다. 종료 불명은 안전 오류와 예약으로 남기며 다른 verify의 프로세스·예약은 보존한다.
- 실행 명령·경로·결과 파일·통신은 선택된 worktree와 verify identity에 연결한다. 임의 shell 문자열 해석, 다른 작업의 제어, 설정·자격 증명의 일반 전달과 비밀값 진단 노출을 허용하지 않는다.

### 지원 범위와 자동 작업

- 공통 기반과 Loop Manager 자체 unittest 연결을 먼저 제공하고, 비Python adapter와 프로젝트 연결을 후속 확장한다. 자체 연결만으로 언어 독립성과 전체 Requirement의 완료를 확정하지 않는다. 후속 작업에서도 같은 규약·자원 조율·검증 기준을 사용한다.
- Python unittest와 비Python 언어의 실제 테스트 도구 하나를 최소 지원 범위로 삼는다. 도구 선택은 이미 쓰는 환경·의존성과 공식 수집·reporter 기능을 확인해 확정한다. 서로 다른 언어의 독립 소규모 예제를 같은 core에 연결해 공통화의 효과와 한계를 검증한다. 이후 도구는 동일 규약과 적합성 검증을 통과한 adapter를 추가해 연결한다.
- 연결 프로젝트의 Worker는 새로 작성·변경하는 테스트가 adapter의 수집 범위와 격리 계약을 지키도록 유지한다. 실행량·시간 기록·예약 로직을 테스트마다 작성하지 않는다. 실제 Agent CLI·API 호출은 mock·stub·고정 출력으로 검증하고 필요한 실제 Git·DB·운영체제 검증은 유지한다.
- 정적 adapter 작성·검토·연결 판단 기준은 R-064의 기존 `docs/AGENTS.worker.md`·`docs/AGENTS.reviewer.md`·`docs/AGENTS.planner.md`에 각각 반영한다. 모든 역할에 적용되는 경계만 common에 유지하며 common+해당 역할을 instruction으로 전달하는 기존 방식을 재사용한다. 작업 prompt에는 프로젝트의 선택 adapter·도구 버전·참조 문맥만 연결한다. 프로젝트별·언어별 사본이나 별도 배포 경로를 만들지 않고 합친 파일은 저장소 밖 실행용으로만 사용하며 커밋하지 않는다. adapter 변경 시 진행 작업의 고정 원본 버전과 성공 재사용 조건을 지킨다.
- 지원하지 않는 도구를 쓰는 프로젝트는 기존 verify를 유지한다. 신규 adapter나 기존 프로젝트 연결 작업이 필요하면 해당 작업 범위에서 계획하며, 무관한 기능 작업에 전체 테스트 개편을 포함하지 않는다.

## Acceptance Criteria

- 명시적으로 연결한 프로젝트만 공통 runner를 사용한다. 미연결 프로젝트의 기존 verify가 유지되고, 잘못된 연결·버전·도구 부재는 성공 또는 무언의 fallback으로 처리되지 않는다.
- Loop Manager 자체 unittest와 서로 다른 두 언어·테스트 도구의 독립 예제가 자원 조율 코드 복사 없이 같은 runner로 실행된다. core는 unittest·프로젝트 언어의 타입에 의존하지 않으며 adapter 추가 경계와 규약 적합성 검증을 제공한다.
- 직렬·병렬 실행의 수집 범위·fixture 계약·필수 단계·결과 및 종료 코드가 일치한다. 공유 자원·순서 의존 단계는 직렬이고 내부 병렬 실행이 배정 예산을 우회하지 않는다.
- 두 연결 프로젝트의 동시 시작·서로 다른 실제 부하·여유 회복에서 코드 배정과 공유 예약이 확인된다. 관측 실패·낡은 값·사용자 상한·자원 부족의 처리 이유를 기록한다.
- 잘못된 manifest·결과 형식, 결과 누락·중복, 수집 실패·자식 비정상 종료·통신 단절이 실패로 드러나고 다른 프로젝트의 작업을 손상하지 않는다.
- Windows·Linux에서 timeout·취소·시작 실패 뒤 자식 종료 또는 미시작 확인과 해당 예약 회수가 확인된다. 종료 불명은 성공이나 여유 자원으로 계산하지 않는다.
- 테스트·fixture·준비·대기·정리와 중단 위치의 진단이 보존된다. Worker의 제한된 실패 피드백으로 해당 자료를 찾을 수 있고 비밀값은 포함하지 않는다.
- Manager와 단독 실행이 같은 필수 범위를 검증한다. 조율 부재와 runner 부재를 구분하며, 불완전한 과거 결과를 재사용하지 않는다.
- 두 언어의 테스트가 각각 기존 assertion·fixture·도구를 유지하면서 공통 manifest·결과·진단 계약을 지킨다. 실제 common+해당 역할 instruction에서 필요한 adapter 작성·검토·계획 지침을 확인할 수 있고 작업 prompt에는 정적 규칙이 중복되지 않는다. 정상 테스트에서 실제 Agent 호출을 하지 않으며 지원 근거 없는 기능이나 일반 명령의 종료 코드만으로 테스트 계약 충족을 표시하지 않는다.
- 같은 환경·revision·검증 범위에서 직렬·병렬, 단일·동시 verify의 시간·메모리·예약 및 결과를 실제 비교한다. 실측 전 절감률을 확정하지 않는다.

## Product Impact

- 공통 verify는 프로젝트가 선택적으로 연결하는 Loop Manager 기능이 된다.
- 자원 조율·실행·진단은 Manager가 제공하고, 수집·결과 의미·격리는 프로젝트와 adapter가 책임진다.
- Worker는 연결 계약에 맞는 테스트·verify를 유지하고 Manager는 Agent 밖에서 전체 검증한다.

## Non-Goals

- 기존 등록 프로젝트의 일괄 전환, 모든 테스트 도구 adapter의 동시 구현.
- 여러 ExecPlan·Worker의 동일 프로젝트 동시 실행 또는 여러 호스트·Manager 인스턴스·단독 runner 사이의 예약 공유.
- 새 상주 서비스·외부 모니터링·범용 작업 DAG·adapter 배포 marketplace·새 sandbox infrastructure.
- 기존 전체 검증 축소, 필수 테스트 skip, 자동 timeout 증가, 특정 절감률·프로세스의 CPU 사용량에 대한 새로운 OS 강제 제한 보장.
- Git·게시·Review·Merge 경계의 완화.

## Open Questions

- 없음. 최소 지원은 unittest와 기존 사용 환경에서 선택한 비Python 테스트 도구 하나이며, 선택적 연결·같은 Manager 인스턴스의 조율로 한정한다. 구체적인 도구 선택은 기존 의존성과 공식 계약을 확인하는 구현 판단이다.
