# [R-076] 운영 명령어와 상태 조회 및 Skill 지원

## Context

운영자는 간략한 목록에서 대상을 고르고 상세 상태·로그에서 진행 상황과 다음 조치를 확인할 수 있어야 한다. 수동 구현 대상을 고를 때 선행 조건과 특정 Requirement에 연결된 작업을 확인할 수 있어야 한다. 전체 또는 특정 프로젝트를 중단·재개하고, 지정 프로젝트만 실행하며, 작업 초기화·수동 제출 취소·유지보수 전환 요청을 상태 DB 직접 수정 없이 수행할 수 있게 한다. 명령어 Skill과 수동 구현용 프롬프트는 이 명령을 안내한다.

이 문서는 원하는 변경을 정의한다. 아래 기존 명령어와 구현 목표를 구분하고, 구현 시작 시 최신 원격 코드에서 같은 기능의 추가 여부를 다시 확인한다.

현재 CLI의 공통 진입 경로는 실행 잠금과 Git 기반 bootstrap·runtime 준비를 수행한다. 일반 DB 연결과 일부 Repository 생성자는 schema 초기화·migration을 수행하고, 실행 명령은 중단된 invocation을 정리한다. 조회 명령은 이 부수 효과를 일으키지 않아야 한다.

호출·사용량의 기본 집계는 `loop_manager_internal/storage/agent_invocation_state.py`의 `summary()`에 있고, 복구 판단은 `loop_manager_internal/recovery/recovery_runtime.py`가 소유한다. [R-073](%5BR-073%5D%20%ED%98%B8%EC%B6%9C%20%EB%AA%A9%EC%A0%81%EA%B3%BC%20%EC%82%AC%EC%9A%A9%EB%9F%89%20%EB%B2%94%EC%9C%84%20%EA%B8%B0%EB%A1%9D%20%EB%B0%8F%20%EC%A1%B0%ED%9A%8C.md)의 호출 목적·실행 여부·사용량 범위 수집 확대와 기간별 분석은 별도 요구사항이다. 이 요구사항은 이미 저장된 정보의 조회를 제공하며 R-073 전체 구현을 선행 조건으로 삼지 않는다.

## Requirement

### 기존 명령어와 변경 범위

현재 CLI의 명령이다. 아래 표에서는 `python loop_manager.py`를 생략한다. 공통 옵션 `--state-dir <dir>`, `--config <path>`는 명령 앞에 지정하며 상세 인자는 각 명령의 `--help`로 확인한다.

| 기존 명령 | 용도 |
|---|---|
| `config init` | 상태 DB 초기화 |
| `config list` | 등록 프로젝트 목록 조회 |
| `config add <repo> [--base <branch>] [--provider <provider>]` | 프로젝트 검증·등록 |
| `config remove <repo>` | 프로젝트 등록 해제 |
| `run [--skip-if-running]` | 등록 프로젝트 처리. 옵션 지정 시 다른 실행이 있으면 성공 종료 |
| `recover <repo> [--plan <id>]` | 로컬 환경 원인의 제한 재검사 요청 |
| `manual start <repo> <id>` | 기존 G의 수동 구현용 브랜치·작업 공간 준비 |
| `manual complete <repo> <id>` | 기존 G의 수동 구현 제출·검증·PR 연결 |
| `manual submit <repo> --branch <branch> --requirement <R 경로>` | G 없이 구현한 원격 R·코드 제출. `--requirement`는 반복 가능 |
| `maintenance-review <repo>` | 다음 안전한 경계에서 전체 정밀 점검을 포함한 유지보수 전환 요청 |
| `document-drafts <repo> <subcommand> ...` | 문서 수정본 관리. `list`, `generate`, `create`, `show`, `decide`, `approved` 지원. Loop Manager 저장소 전용 |

이번 변경에서는 `config list`를 요약 조회 `list`로, `config add/remove`를 `add/remove`로 바꾼다. `add/remove`의 인자·검증·등록 해제 조건은 유지하고 `config init`과 나머지 기존 명령은 유지한다. 기존 이름의 호환 별칭은 제공하지 않으며 도움말·사용 예시·Skill도 새 이름만 안내한다. 이후 명령 변경에서는 호환성을 유지한다. 상세 조회는 `status`로 통합하고 별도 `explain` 명령을 추가하지 않는다.

### 실행 대상 선택과 일시중지

```text
python loop_manager.py run [--skip-if-running] [repo...]
python loop_manager.py pause [repo]
python loop_manager.py resume [repo]
```

- `run`은 repo 생략 시 모든 등록 프로젝트를, 지정 시 해당 프로젝트만 처리한다. 경로는 정규화한 뒤 중복을 제거하며 공백이 있는 경로는 따옴표로 입력한다. 지정 경로 전체의 등록 여부를 실행 시작 전에 검증하고 하나라도 미등록이면 프로젝트 처리를 시작하지 않는다.
- 선택한 프로젝트는 기존 `max_workers`·프로젝트별 단일 변경 자리·dependency·작업 선택·복구 조건을 유지한다. 한 프로젝트의 실행 실패는 나머지 처리를 막지 않는다. `--skip-if-running`의 중복 자동 실행 처리 의미도 유지한다.
- `pause`는 같은 상태 디렉터리를 사용하는 Manager 전체, `pause <repo>`는 해당 등록 프로젝트의 진행 작업을 중단하고 이후 자동 처리를 막는다. 프로젝트 중단은 다른 프로젝트를 중단하지 않는다. 다른 기기의 수동 구현 세션까지 종료했다고 보고하지 않는다.
- 실행 중에도 중단 요청을 접수할 수 있어야 한다. 먼저 pause를 저장해 새 작업 시작을 막고 해당 범위의 Agent·verify와 자식 프로세스를 종료·확인한다. Git 작업과 게시 결과는 실제 관측과 기존 소유권·복구 근거로 확인하며 성공·실패를 추측해 확정하지 않는다. 중단 직전 단계·세션·작업물·진단은 보존하고 차단이나 초기화로 바꾸지 않는다.
- 종료·저장·게시 결과를 유한 시간 안에 확인하지 못하면 pause는 유지하고 미확인 대상과 오류를 알린다. 중단 완료를 보고하거나 같은 자원에 새 작업·초기화를 시작하지 않는다. 재시작 뒤에도 pause와 미완료 중단 확인을 유지한다.
- 전체 pause 중 `run`은 일시중지 안내만 출력하고 종료 코드 `0`으로 끝난다. Agent·verify·bootstrap·runtime 준비·원격 조회·알림 전송을 시작하지 않는다. 프로젝트 pause는 그 프로젝트의 제외 사유를 출력하고 다음 대상으로 넘어간다. 명시한 repo도 pause를 우회하지 않는다.
- `resume`은 전체 pause만, `resume <repo>`는 해당 프로젝트 pause만 해제한다. 전체 재개가 프로젝트 pause를 지우거나 프로젝트 재개가 전체 pause를 지우지 않는다. 재개 명령 자체는 작업을 시작하지 않으며 다음 실행에서 보존된 단계와 기존 gate를 다시 확인한다.
- pause 중에도 조회·설정·제어 명령과 기존 수동 준비·요청 접수는 가능하다. 접수된 복구·수동 제출·유지보수의 자동 후속 처리는 pause를 준수한다. 사용자 결정·독립 차단·사용 한도·dependency·PR 대기는 `resume`으로 해제하지 않는다.

### 유지보수 전환 요청

```text
python loop_manager.py maintenance-review <repo>
```

- 기존 명령을 유지보수 전환 요청에 재사용한다. 자동 주기의 기준값·기준 Merge 수·cycle 종료는 [R-074](<[R-074] 유지보수 1회 평가와 즉시 종료.md>)를 따른다. 주기 도달 전이나 `refactoring_review_interval = 0`에서도 명시적 요청을 접수한다.
- 요청 대상은 등록된 프로젝트이며, 경로를 정규화하고 등록 여부를 확인한 뒤 요청을 저장한다. 명령 자체는 Planner·Worker·verify를 실행하지 않으며 다음 정상 실행의 안전한 작업 선택 경계에서 전환한다. 요청 저장 성공을 실제 유지보수 시작·평가 완료로 표시하지 않는다.
- 실행 중 Worker·verify·Review·Git 작업과 활성 유지보수 cycle을 중단하거나 중복 시작하지 않는다. pause·실제 Open PR·프로젝트 안전 차단 등 기존 전환 gate를 준수하며, 접수된 요청과 대기 이유를 저장된 상태와 출력에서 구분한다.
- 미등록 대상·유효하지 않은 설정·요청 저장 실패는 오류로 보고한다. 같은 저장 요청은 재시작·cycle 종료 뒤 다시 실행하지 않으며 처리한 요청·cycle·기존 작업 이력을 보존한다.
- 도움말·사용 예시·명령어 Skill은 자동 주기가 꺼져 있어도 이 명령으로 전환을 요청할 수 있고, 실제 전환은 다음 안전한 경계에서 이루어진다는 의미를 안내한다.

### 작업 초기화와 수동 제출 취소

```text
python loop_manager.py reset <repo> <id>
python loop_manager.py manual cancel <repo> <id>
python loop_manager.py manual stop <repo> <id>
```

[R-077](%5BR-077%5D%20G%20%EA%B3%84%ED%9A%8D%20%EC%88%98%EB%8F%99%20%EA%B5%AC%ED%98%84%EA%B3%BC%20R%C2%B7%EC%BD%94%EB%93%9C%20%EC%9D%BC%EA%B4%84%20%EC%A0%9C%EC%B6%9C.md)의 시작·제출·자동 후속 처리 계약은 유지하며 아래 명시적 취소·중단·수동 대상 해제를 추가한다. PR 생성·연결은 수동 제출 처리의 종료 경계이고, ExecPlan 완료는 계속 실제 Merge를 기준으로 한다.

| 명령·대상 | 변경 결과 |
|---|---|
| 자동 작업의 `reset` | 진행 작업 종료와 백업을 확인하고 관리 rebase를 취소한다. 로컬·원격 소유 작업 브랜치를 최신으로 확인한 원격 base로 초기화하고 현재 실행 근거를 초기화해 READY로 전환한다. |
| 수동 작업의 `reset` | `manual cancel`과 같은 조건으로 유효한 제출 요청만 취소한다. 브랜치·작업물·세션·실행 근거를 초기화하지 않고 수동 구현 대기로 돌아가며 READY로 전환하지 않는다. 초기화가 필요하면 `manual stop`을 안내한다. |
| `manual cancel` | 자동 후속 처리에 착수하지 않은 현재 유효한 제출 요청만 취소한다. 브랜치·작업물·현재 후보·단계 결과와 과거 제출 감사는 그대로 보존하고 수동 구현 대기로 돌아간다. |
| `manual stop` | 수동 대상과 제출의 유효성을 해제한다. 진행 중인 후속 처리는 종료·보존을 확인한 뒤 자동 작업 reset과 같은 브랜치·실행 상태 초기화를 수행하고 READY로 전환한다. |

- 취소 가능한 요청은 수락됐지만 검증·Review·교정·게시 등 후속 자동 처리에 착수하지 않은 미완료 요청이다. 과거 제출 이력을 삭제해 취소로 표시하지 않는다. 이미 취소됐거나 유효 요청이 없으면 변경 없이 그 사실을 안내하며 수동 `reset`도 같은 결과를 따른다.
- 이미 검증 등 후속 처리에 착수한 제출에는 `manual cancel`과 수동 `reset`을 거부하고 필요하면 `pause <repo>`를 안내한다. pause는 요청을 취소하거나 이미 시작된 제출을 미착수로 되돌리지 않는다. 취소된 요청은 `run`·재시작·원격 push로 자동 복구하지 않으며 사용자가 `manual complete` 또는 기존 제출 경로로 새 요청을 수락시켜야 한다.
- PR을 이미 생성·연결한 작업에는 `reset`·`manual cancel`·`manual stop`을 적용하지 않는다. PR·브랜치·연결 기록을 유지하고, 추가 변경은 Requirement를 수정·게시해 새 ExecPlan으로 진행하도록 안내한다. 기존 PR의 실제 Merge 추적은 유지한다.
- R-055의 예외로, Manager가 생성·게시한 원격 작업 branch가 실제 삭제됐고 연결 PR이 Merge되지 않아 중단된 자동 작업은 `reset <repo> <id>`를 명시적 재시작 요청으로 받을 수 있다. 기존 PR 생성 여부만으로 이 요청을 거부하지 않고 현재 작업·writer 종료·PR 상태와 독립 gate를 확인한 뒤 최신 원격 원본에서 새 실행을 준비한다. 과거 작업물·PR 연결·실패·게시 감사는 보존하고 이전 성공 token·삭제된 branch의 게시 intent를 재사용하지 않는다. 재시작 전에 실제 Merge가 확인되면 완료 처리하며, `run`·프로세스 재시작·pause 해제는 이 요청을 대신하지 않는다. 일반 수동 제출 취소·중단의 PR 경계는 유지한다.
- 브랜치·PR을 공유하는 제출 묶음은 구성 G 하나를 지정해도 저장된 관계로 확인한 묶음 전체에 적용한다. 모든 구성 ID·공유 자원·허용 여부를 변경 전에 확인·출력하고 하나라도 조건을 충족하지 못하면 전체 요청을 거부한다. 부분 취소·일부 G만 READY 전환·공유 브랜치 반복 초기화를 하지 않는다.
- 초기화는 등록 프로젝트의 유효한 비종료 작업과 확인된 Manager 소유 브랜치·worktree에만 적용한다. MERGED·archive된 비활성 계획, 미해결 사용자 결정·독립 안전 차단, 사용자 Git operation·외부 브랜치·불명확한 소유권이나 PR 게시 결과를 우회하지 않는다. 공유 자원의 실제 실행 종료와 사용권 해제를 확인하기 전에는 변경하지 않는다.
- 자동 `reset`과 `manual stop`은 미커밋·미게시 변경을 포함한 작업물과 현재 상태를 복구 가능하게 보존하고 백업 위치를 출력한다. 백업에 실패하면 초기화하지 않는다. 관리 rebase만 취소하고 source checkout·사용자 source branch는 변경하지 않는다. 원격 쓰기는 확인한 OID의 정확한 lease를 사용하고 예상 밖 후속 commit을 덮어쓰지 않는다.
- 세션·현재 차단·checkpoint·verify·Review 결과 등 새 후보에 사용할 수 없는 실행 근거만 초기화한다. 계획·Requirement·사용자 결정·원본 snapshot·과거 감사와 묶음 관계는 보존한다. 아직 base에 없는 수동 R·G 정의도 잃지 않으며 유효한 source와 초기화 결과를 확인할 수 없으면 초기화를 완료하지 않는다. READY 전환은 dependency 충족이나 독립 차단 해제를 뜻하지 않는다.
- 중단·Git 변경·원격 게시·상태 확정 사이에 실패하거나 재시작하면 대상·백업·원래 상태·이미 확인한 결과를 보존해 같은 요청의 미완료 단계부터 확인한다. 묶음 전체의 성공을 확인하기 전에는 READY 전환과 성공을 보고하지 않는다. 취소와 후속 처리 시작은 원자적으로 조율해 취소 성공 뒤 같은 요청을 실행하지 않는다.

### 명령과 조회 범위

기존의 `--state-dir`·`--config` 전역 옵션, repository 경로 인자와 ExecPlan ID를 사용한다. 작업의 식별자는 repository와 plan ID의 조합이며 제목이나 파일명으로 추측해 선택하지 않는다.

```text
python loop_manager.py [--state-dir <dir>] list [repository] [--source <requirement-path>] [--order priority|id] [--all] [--json]
python loop_manager.py [--state-dir <dir>] status <repository> [<id>] [--json]
python loop_manager.py [--state-dir <dir>] usage <repository> [--plan <id>] [--json]
python loop_manager.py [--state-dir <dir>] logs <repository> --plan <id> [--tail N]
```

- `list`는 간략한 목록, `status`는 지정한 프로젝트 또는 작업 하나의 상세 조회다. repository는 `status`에서 필수이며 명시한 작업은 종료 상태여도 조회할 수 있다.
- `usage`는 해당 프로젝트의 저장된 호출 전체를 집계하며, `--plan`이 있으면 그 계획에 연결된 호출만 집계한다. 계획 연결이 없는 Planner·유지보수 호출은 프로젝트 집계에 포함하고 특정 계획의 사용량으로 배분하지 않는다.
- 기본 출력은 사람이 읽기 쉬운 간결한 형식이다. `list`·`status`·`usage`의 `--json`은 같은 사실과 미확인·부분 수집의 의미를 기계가 읽을 수 있게 제공한다.

### list

- repo를 생략하면 등록 프로젝트를 한 줄씩 보여준다. 프로젝트 경로·저장된 phase·pause 여부·활성 작업 수를 표시하고 전체 pause 여부도 함께 안내한다.
- repo를 지정하면 작업을 한 줄씩 보여준다. G ID·제목·저장된 status·유효 우선순위·선행 조건 요약·짧은 대기 사유를 제공하며 복수 사유와 미충족 선행 작업의 상세 내용은 `status <repo> <id>`로 안내한다.
- 기본 범위는 실행 중인 작업 외에 READY·PLAN_BLOCKED·PR_OPEN·수동 구현 대기를 포함한 비종료 작업이다. `--all`은 보존된 MERGED 작업도 포함한다. 제출 요청 취소 후의 수동 구현 대기도 활성 작업으로 남으며, 계획 자체의 삭제·취소·비활성 이력은 현재 활성 작업으로 집계하지 않는다.
- 작업 정렬은 유효 우선순위가 높은 순서, 동률이면 숫자 G ID 오름차순이 기본이다. `--order id`는 숫자 G ID만 사용한다. 기존 검증된 catalog의 우선순위 전파를 재사용하고 판단 근거가 없으면 미확인으로 표시한다. 정렬은 실제 실행 순서를 보장하지 않는다.
- 작업 필터·정렬 옵션인 `--source`·`--all`·`--order`는 repo가 없으면 인자 오류다. 목록 출력 때문에 새로운 상태·활동 판단·전환 이력을 만들지 않는다.

### 선행 조건과 Requirement 연결 작업

- 작업별 목록의 선행 조건은 검증된 현재 `depends_on` 선언과 같은 조회 snapshot의 저장된 실행·Merge 근거로 표시한다. 선행 작업이 없으면 `없음`, 모두 확인됐으면 `충족`, 확인된 미충족 작업이 있으면 `미충족`, 필요한 선언·상태·근거를 확인할 수 없으면 `미확인`으로 구분한다.
- 확인된 충족 수와 전체 선행 작업 수를 함께 표시하고 미확인 수를 드러낸다. 미충족과 미확인이 공존하면 모두 표시한다. 선언이 누락·손상됐거나 미존재 ID·순환·보류 관계로 유효성을 확인할 수 없을 때는 선행 작업 없음이나 충족으로 채우지 않는다. 중복된 동일 선행 ID를 중복 집계하지 않는다.
- 충족 표시는 마지막으로 저장된 확인 기준이다. `MERGED` 문자열·계획 본문의 완료 표시·브랜치 존재만으로 실제 Merge를 확정하지 않으며 기존 검증된 Merge·archive identity 근거를 재사용한다. 근거가 부족하면 미확인으로 남기고 관측 시각·출처를 상세 조회에서 보여준다.
- `status <repo> <id>`는 선행 G별 ID·제목·상태·충족 여부·확인 근거와 미충족/미확인 사유를 보여준다. 선행 조건 충족과 수동 인계 가능 여부는 구분하며 확인된 draft·사용자 결정·차단·실행 중 상태·소유권 제약도 기존 정책에 따라 설명한다. 실제 `manual start`는 R-077대로 현재 원격 Merge와 소유권·안전 gate를 다시 확인한다. 조회를 시작 허가나 실행 예약으로 사용하지 않는다.
- `list <repo> --source <requirement-path>`는 해당 Requirement 경로를 현재 검증된 `sources`에 직접 포함하는 작업만 같은 목록 형식으로 보여준다. 선택은 같은 프로젝트 안에서 정확한 문서 경로를 기준으로 하며, 공통 PRODUCT·다른 Requirement·`depends_on`·본문 내용의 유사성으로 연결을 추정하지 않는다. ExecPlan 문서를 새 source 유형으로 허용하지 않는다.
- `--source`는 `docs/requirements/<파일명>.md` 또는 그 archive 대응 경로 하나를 받으며 공백이 있는 경로는 따옴표로 입력한다. 구분자를 정규화하고 기존 Requirement의 active/archive 대응 규칙을 재사용한다. PRODUCT·ExecPlan·절대 경로·경로 이탈 입력은 인자 오류다. 같은 파일명이 archive로 이동해도 원래 source 관계를 유지하며 제목·R 번호만 같은 다른 파일이나 다른 프로젝트 문서를 합치지 않는다. 관계를 확정할 수 없으면 경고와 미확인으로 표시한다.
- source 필터도 기본 비종료 범위·`--all`·정렬·읽기 전용·JSON 계약을 그대로 따른다. 저장된 해당 범위에 직접 참조 작업이 없으면 0건으로 표시하되 문서가 존재하지 않거나 요구사항이 완료됐다고 추정하지 않는다. 조회 때문에 원격 문서·새 초안·기록을 읽어 들여 catalog를 갱신하거나 새 계획을 만들지 않는다.
- 기본 출력과 JSON은 같은 source 범위·선행 조건·확인/미확인 수를 제공한다. 상세 조회에 필요한 ID와 실제 경로를 함께 안내하고 목록 조회에서 원격 확인이나 추가 Agent 호출을 하지 않는다.

### status

`status <repo>`는 해당 프로젝트의 base·provider·phase, 전체 및 프로젝트 pause, planning 오류와 작업 진행·대기 현황을 상세히 보여준다. `status <repo> <id>`는 작업 하나의 상태·브랜치·worktree·PR과 아래 근거·다음 조건을 상세히 보여준다. 두 범위 모두 다음을 확인할 수 있어야 한다.

| 정보 | 표시 규칙 |
|---|---|
| 단계와 상태 | 저장된 프로젝트 phase와 ExecPlan status를 구분한다. 표시를 위해 기존 상태를 변경하거나 새 실행 상태를 저장하지 않는다. |
| 마지막 실제 진전 | 해당 작업의 실제 진전을 식별할 수 있는 저장된 사건의 시각과 출처를 표시한다. 근거가 없으면 미확인이다. |
| 대기·일시정지·실패 사유 | 기존 구조화된 사유와 복구 기록을 이용하고 관련 프로젝트 차단·planning 오류도 함께 표시한다. |
| 관련 대상 | 선행 dependency별 충족 여부와 미충족·미확인 ID/상태, 선언된 Requirement source 경로, 연결된 PR URL과 저장된 관측값, 확인된 사용자 조치 대상을 표시한다. |
| 다음 진행 조건 | 기존 판단에서 확인되는 재시도·재검사·의존 작업 Merge·PR 처리·사용자 결정 등의 조건을 표시한다. |

프로세스 존재, 실제 작업 활동, 재개 가능성과 관측 신선도는 구분한다. 실행 잠금이나 미종료 invocation이 있다는 사실만으로 프로세스 생존이나 작업 진행을 확정하지 않는다. 프로세스가 종료됐다는 사실만으로 작업 실패를 확정하지 않는다. 관련 정보가 없으면 각각 미확인으로 표시한다.

사용량 제한에 따른 일시정지, 일시적 오류에 따른 재시도 대기, 사용자 판단 대기, dependency 대기, PR 대기를 구분한다. 프로젝트 차단과 개별 계획 차단도 구분하며 한 계획의 대기만으로 프로젝트 전체가 중단됐다고 표시하지 않는다. 여러 사유가 동시에 있으면 확인된 사유를 함께 보여준다. 구조화된 근거가 없는 legacy 오류 문구를 새로 해석해 사유를 확정하지 않는다.

### 작업별 상세 근거

작업별 `status`는 요약과 같은 원본을 이용해 다음 상세 근거를 제공한다.

- 마지막 단계 전환의 이전·이후 단계, 시각과 사유를 저장된 근거가 있는 범위에서 표시한다. 전환 이력이 없으면 현재 상태만으로 전환 이력을 만들지 않고 미확인으로 표시한다.
- 적용된 복구 disposition·pending action·원인 code·scope, 재시도와 반복 횟수, 최종 차단 근거와 남은 불확실성을 표시한다. 저장된 결정과 다음 실행에서 필요한 재판정을 구분한다.
- 현재 후보 commit·plan revision·검증된 base와 연결된 verify·Review 결과, 저장된 결과 식별자·지문·token·checkpoint 등의 기존 근거 식별자를 표시한다. 다른 후보나 입력에 대한 성공 결과를 현재 후보의 통과 근거로 사용하지 않는다.
- 자동 재시도 또는 조건 충족 후 재평가 대상인지, 무엇을 기다리는지, 필요한 사용자 행동과 실제 대상이 확인되는지 설명한다. 근거가 없으면 자동 재개 가능성이나 수정 대상을 추측하지 않는다.
- 진단은 필요한 요약과 기존 식별자로 제공한다. 인증 정보·비밀값·prompt·코드·문서 전문을 새로 출력하지 않고 기존 진단의 비밀값 제거 규칙을 따른다.

### usage

기존 `summary()`의 집계와 provider별 token 의미를 재사용한다. 작업 필터나 수집 누락 표시가 필요하면 기존 집계 경계를 확장하되 별도의 중복 집계 규칙을 만들지 않는다.

- provider·Model·역할별 호출 수와 재시도 수를 보여준다. 기존 집계가 구분하는 Effort와 session 전이도 보존한다.
- 기록된 input·cached input·cache write input·output·reasoning output token과 소요시간을 제공되는 범위에서 표시한다. token의 포함 관계를 보존하며 cache와 reasoning을 다시 더해 총량을 부풀리지 않는다.
- 각 사용량·시간 값은 알려진 부분 합계와 알려진 호출 수·미수집 호출 수를 함께 표시해 완전한 합계와 구분한다. 전부 미수집이면 미확인으로, 일부만 수집되면 부분 합계로 표시한다. 실제로 기록된 0은 미수집과 구분한다.
- 수집 상태와 진행 중·중단·실패 호출의 누락을 드러낸다. 호출 기록이 없는 정상 범위는 호출 0건으로 표시할 수 있지만 미수집 token·시간을 0으로 채우지 않는다.
- 현재 `summary()`의 호출 수는 ledger 행 수이고 재시도 수는 `attempt > 1`인 행 수다. 이 의미를 문서화하고 실제 모델 실행 또는 청구된 호출 수로 단정하지 않는다. 과거 기록에 실제 실행 여부·목적·범위 근거가 없으면 추측해 채우지 않는다. 이후 R-073에서 실행 여부가 구분돼도 해당 의미를 명시적으로 유지·구분한다.
- 금액 비용 계산과 예산 제한은 제공하지 않는다.

### logs

- 해당 작업에 연결된 최근 실행·verify·Review의 저장된 로그를 찾아 단계·실행 ID·경로와 내용을 구분해 제공한다. `--tail N`은 선택한 각 로그의 마지막 N줄로 제한하며 N은 양의 정수여야 한다.
- 로그가 수집되지 않았거나 선택 정보가 없으면 미확인으로 안내하고, 기록된 원문을 읽을 수 없으면 읽기 오류와 대상을 알린다. 조회 때문에 작업을 재실행하거나 원문을 새로 생성하지 않는다.
- 기존 비밀값 제거 규칙을 로그 본문에도 적용한다. 다른 작업의 로그를 같은 작업의 근거로 출력하지 않고 로그·작업 상태·전송 기록을 변경하지 않는다.

### 명령어 Skill과 수동 구현용 프롬프트

- 명령어 Skill은 Loop Manager 자체 저장소에서만 사용한다. 등록 프로젝트로 복사·설치하지 않고 프로젝트 파일 준비 스크립트에도 배포 대상으로 추가하지 않는다. 이번 변경의 명령·범위·거부 조건·결과 확인 방법을 안내하며 호환 명령은 사용·안내하지 않는다.
- `manual start`가 원격 브랜치·작업 공간 준비를 완료하면 사용자가 다른 AI 세션에 복사할 수 있는 짧은 프롬프트를 정해진 형식으로 코드에서 생성한다. 생성용 Agent 호출은 하지 않는다. 준비 실패·미완료 결과를 구현 준비 완료로 안내하지 않는다.
- 복사용 프롬프트에는 G ID·작업 경로, 소유 브랜치·base, 프로젝트 안의 PRODUCT·Requirement·ARCHITECTURE 등 작업 문서 상대 경로와 해당 프로젝트의 verify 명령을 포함한다. 구현·검증·문서 기준 재검증 후 소유 브랜치에 push하는 단계까지 지시하며 PR 생성은 지시하지 않는다. `manual start` 출력은 복사용 프롬프트와 별도로 사용자에게 push 후 Manager에서 `manual complete <repo> <id>`를 실행하도록 안내하며, Manager 명령 실행 위치와 프로젝트 구현 위치를 구분한다.
- Review 안내는 별도 CLI를 요구하지 않고, "작업 후 해당 계획과 PRODUCT·활성 Requirement·ARCHITECTURE를 기준으로 구현과 검증 결과를 재검증하고 누락·모순을 수정하라"는 자연어 지시를 포함한다. 이 자체 점검을 Manager의 verify·독립 Reviewer 통과나 실제 Merge 근거로 기록하지 않는다.
- 명령어 Skill과 수동 완료 안내는 `manual complete/submit`에서 검증·Review 생략을 선택할 때 실제 수행 내용·결과 등 생략 근거를 짧게 작성해 `--skip-reason`으로 함께 전달하도록 안내한다. CLI에서는 R-077대로 선택 옵션임을 명시하고 사유 작성 안내를 생략 강제나 추가 수락 조건으로 바꾸지 않는다. 수행하지 않은 검증·Review를 완료했다고 작성하지 않는다.

### 관측 시각과 정책 재사용

- 조회 시각과 정보의 저장된 관측 시각을 분리한다. 시각이 있는 관측값은 원본 출처와 관측 후 경과시간을 함께 확인할 수 있게 하고 시각이 없는 값은 시각 미확인으로 표시한다.
- 관측값이 오래됐다는 사실을 경과시간으로 드러낸다. 기존 정책에 유효기간이나 신선도 기준이 있으면 그대로 사용하고, 없으면 새로운 시간 기준으로 활동·실패·재개 여부를 판정하지 않는다. 조회 시각을 관측 시각으로 채우지 않는다.
- invocation 시작·종료, 단순 DB 갱신, 복구 재시도·오류 관측 시각을 그 자체만으로 마지막 실제 진전 시각으로 사용하지 않는다. 현재 데이터가 실제 진전을 증명하지 못하면 해당 값은 미확인으로 남긴다.
- SQLite에 저장된 PR·원격 OID·프로세스 관련 정보는 마지막 저장 관측값으로 표시한다. 조회 과정에서 GitHub나 provider를 호출해 실시간 상태를 보충하지 않는다.
- 다음 실행 시각, 사용량 제한 해제 시각과 재개 조건은 기존 데이터·정책으로 확인되는 범위만 표시한다. cron 주기나 provider 제한 reset 시각을 추측하지 않는다. 다음 외부 실행에서 재검사한다는 조건은 성공적으로 재개된다는 보장이 아니다.
- 기존 저장·상태 투영·작업 선택·알림 사유·복구·재시도 정책을 재사용한다. 저장된 결정을 우선하고 설명에 필요한 순수 판단은 실행 경로와 공유한다. 조회용 차단·해제·dependency·재시도 정책을 중복 구현하지 않는다. 조회에 필요한 원격 검증이나 상태 변경이 있으면 실행하지 않고 재검사 필요 또는 미확인으로 표시한다.

### 읽기 전용 실행과 오류 처리

- `list`·`status`·`usage`·`logs`는 에이전트·verify·runtime 자식을 시작하거나 작업을 재개하지 않는다. Git 명령, branch·worktree·PR 변경, 원격 조회, 알림 생성·전송, retry 기록·중단 invocation 정리, 작업 상태·관측·완료 기록 갱신을 하지 않는다. 이 읽기 전용 계약은 위 상태 변경 명령과 구분한다.
- 조회는 실행 잠금·bootstrap·runtime 준비 및 실행용 초기화·migration 경로를 거치지 않는다. DB가 없는 경우 state directory나 빈 DB를 만들지 않는다.
- SQLite는 읽기 전용 연결을 기본으로 사용한다. schema 생성·migration·journal mode 변경·checkpoint를 하지 않는다. 플랫폼의 WAL·읽기 전용 연결 제약으로 안전하게 읽을 수 없으면 쓰기 연결로 전환하지 않고 조회 오류를 반환한다.
- 필수 table·column을 읽기만으로 검사한다. 지원하지 않는 schema는 migration하지 않고 명확한 오류로 종료한다. 지원 범위 안에서 선택 정보만 없으면 해당 값을 미확인으로 표시한다.
- 다른 Loop Manager가 실행 중이어도 같은 실행 잠금을 획득하지 않고 일관된 DB 읽기 snapshot을 조회한다. DB 잠금에는 유한한 대기 한도를 두고 한도 내에 읽을 수 없으면 오류를 반환한다. 여러 시점의 읽기를 섞어 하나의 확정 상태처럼 표현하지 않는다.
- DB 없음·손상·접근 불가, 알 수 없는 프로젝트·plan ID, 지원하지 않는 schema, 읽기 잠금 실패를 명확하게 구분한다. 조회 실패 때문에 복원·초기화·복구를 자동 수행하지 않는다.

### JSON·종료 코드와 문서화

`list`·`status`·`usage`의 `--json` stdout에는 JSON 문서 하나만 출력하며 운영 로그·장식 문자열을 섞지 않는다. 식별자와 사유 code는 안정적으로 제공하고, 알 수 없는 값은 `null`, 확인된 빈 목록은 `[]`, 실제 수집된 0은 숫자 `0`으로 구분한다. 수집 범위·미수집 개수와 경고를 보존하고 `null`의 이유를 확인할 수 있게 한다.

| 공통 JSON 필드 | 의미 |
|---|---|
| `schema_version` | CLI JSON 출력 계약의 버전. DB schema 버전과는 별개다. |
| `command` | `list`, `status`, `usage` 중 실행한 조회 명령. |
| `queried_at` | 조회 시각. 저장된 정보의 관측 시각을 대신하지 않는다. |
| `repository`, `plan_id` | 요청한 조회 범위. 전체 프로젝트 또는 작업 필터 없음은 `null`이다. |
| `source` | `list --source`에서 요청한 정규화된 Requirement 상대 경로. source 필터가 없거나 다른 명령이면 `null`이다. |
| `data` | 해당 명령의 조회 결과. 값별 관측 시각·출처, 미확인·부분 수집 의미를 포함한다. 조회 실패 시 `null`이다. |
| `warnings` | 읽기는 성공했으나 선택 정보 누락·낡은 관측·부분 수집 등으로 해석에 제한이 있는 경우의 설명. 없으면 빈 목록이다. |
| `error` | 정상 조회는 `null`. 실패는 기계 판독 가능한 code와 설명을 가진다. |

| 종료 코드 | 의미 |
|---|---|
| `0` | 조회 성공. 작업의 일시정지·차단·실패, 정상적인 빈 결과나 선택 정보 미확인은 조회 오류가 아니다. |
| `1` | 요청 범위를 조회할 수 없음. DB 없음·손상·접근 실패·잠금 실패·지원하지 않는 schema·알 수 없는 프로젝트 또는 plan ID를 포함한다. |
| `2` | 기존 인자 파서의 잘못된 명령·옵션·필수 인자 누락. |

코드 `1`의 오류는 JSON에서 `db_not_found`, `db_unreadable`, `db_busy`, `unsupported_schema`, `unknown_project`, `unknown_plan` 등 안정적인 원인 code로 구분한다. 인자 파서가 처리하는 코드 `2`는 기존 stderr 사용법 안내를 따르며 JSON 결과를 요구하지 않는다. 런타임 조회 오류는 `--json`에서도 공통 오류 계약을 따른다.

상태 변경 명령은 적용 완료 또는 유효 제출 요청 없음·이미 해제됨 같은 정상 무변경 확인에 `0`, 안전 거부·중단 미확인·초기화 실패에 `1`, 잘못된 인자에 `2`를 반환한다. 대상·묶음 구성·적용 여부·보존/백업 위치·남은 조치를 알리고 요청 저장과 실제 완료를 구분한다. 기존 `run`·`recover`·수동 제출 명령의 대기·오류 결과는 유지한다.

구현 문서에는 실제 명령·범위, JSON의 모든 필드·자료형·단위·nullable 의미와 버전 호환 규칙, token 포함 관계·집계 의미, 종료 코드·오류 code, 정상·미확인·부분 수집·오류 출력 예시를 기록한다. 완료 보고에는 변경 파일, 명령 사용 예시와 대표 출력, 실행한 검증과 남은 한계를 정리한다.

## Acceptance Criteria

- 최신 원격 코드에서 같은 기능의 추가 여부를 확인하고 기존 구현이 있으면 재사용한다. `list`·`status`·`usage`·`logs`와 상태 변경 명령의 도움말·범위 선택이 위 계약을 따르며 `add/remove`의 등록 조건과 유지하는 기존 명령이 변하지 않는다. 도움말·예시·Skill은 새 명령만 안내한다.
- `list`의 프로젝트·활성 작업 요약, MERGED를 포함한 `--all`, 유효 우선순위·숫자 ID 정렬과 `status`의 프로젝트·개별 작업 상세를 확인한다. 요약과 상세의 상태·사유는 같은 원본과 판단을 사용하며 상세 근거가 목록에 반복되지 않는다.
- 선행 없음·전부 충족·일부 미충족·미확인 공존, PR_OPEN 선행 작업, 근거 없는 MERGED, 유효한 archived dependency, 미존재 ID·잘못된 graph·보류 관계·관측 시각 부재를 확인한다. 목록과 상세의 충족 판정·분모·미확인 수가 일치하며 충족을 현재 수동 시작 허가로 표시하지 않는다.
- `list --source`가 같은 프로젝트의 정확한 Requirement 직접 참조만 반환하고 공통 PRODUCT·본문 유사성·dependency만 있는 작업을 포함하지 않는지 확인한다. 기본/`--all`·정렬·JSON 조합, 공백·구분자·active/archive 대응, 다른 프로젝트·비슷한 파일명, 관계 미확인·0건과 repo 누락·잘못된 경로를 확인한다. source 범위와 선행 조건 요약이 기본 출력과 JSON에서 일치하고 catalog·source·작업 상태를 바꾸지 않는다.
- 사용량 제한 일시정지, 일시적 오류, 사용자 판단 대기, dependency 대기, PR 대기를 서로 다른 fixture로 확인한다. 프로젝트 차단·planning 오류와 독립 계획 대기도 구분하며 기본 출력과 JSON의 사실·사유·재개 조건이 일치한다.
- 단계·상태·마지막 실제 진전·다음 조건을 저장된 근거가 있는 범위에서 제공한다. 전환 이력·진전·프로세스 생존·관측 시각·재개 시각이 없는 경우 미확인이고, 오래된 관측의 시각·경과시간이 보인다. 프로세스 존재만으로 활동을 확정하지 않는다.
- 작업별 `status`는 저장된 복구 결정·횟수·사용자 대상과 후보·입력에 연결된 검증·Review·기존 근거 식별자를 보여준다. 다른 후보의 성공 결과와 단순 DB 갱신 시각을 현재 통과·실제 진전으로 표시하지 않는다.
- 프로젝트와 계획별 `usage`를 두 provider, 역할·Model·Effort·전이·재시도, 부분 token·시간, 전부 미수집, 기록된 0, 미종료·중단·실패 호출, 계획 연결 없는 호출과 빈 조회 범위로 검증한다. 기존 `summary()`의 집계·포함 관계와 결과가 일치하고 미수집은 가짜 0·완전한 합계가 되지 않는다.
- DB 없음, 알 수 없는 프로젝트·plan ID, 지원하지 않는 schema, 손상·접근 실패·읽기 잠금 실패의 메시지·오류 code·종료 코드를 확인한다. DB·디렉터리를 생성하거나 schema를 고치지 않는다. 지원하는 schema의 선택 정보 누락은 미확인으로 안전하게 처리한다.
- 조회 명령의 정상·오류와 지원하는 JSON 경로에서 provider CLI·Git·원격 API·외부 변경 작업·알림 호출을 차단하는 fixture로 호출이 발생하지 않음을 확인한다. bootstrap·runtime 자식·에이전트·verify도 시작되지 않는다.
- 조회 전후 DB schema와 작업·복구·호출·검증·알림 기록이 같음을 확인한다. 재시도 횟수·중단 호출·outbox·완료 기록을 포함한다. 다른 실행 프로세스가 DB를 사용하는 상황에서는 조회가 실행 잠금을 변경하지 않고 일관된 snapshot을 읽거나 유한 시간 안에 조회 오류로 종료함을 확인한다.
- 정상·미확인·부분 수집·조회 오류에서 기본 출력과 JSON의 의미, JSON stdout 순수성, 문서화한 필드·자료형·단위와 종료 코드 계약을 확인한다.
- `logs`의 작업별 로그 연결, 비밀값 제거, `--tail` 범위·잘못된 N, 수집 누락·원문 읽기 실패를 확인하며 조회 후 로그·상태가 변하지 않는다.
- 다중 repo 실행의 경로 중복·미등록 대상 사전 거부·선택 범위·pause 제외·독립 실패 지속과 기존 잠금·동시 실행 상한을 확인한다. 전체 pause의 `run`은 안내·코드 `0` 외 실행·원격 조회·알림 전송을 하지 않는다.
- 전체·프로젝트 pause 중첩, 실행 중 요청 접수, 대상 자식 종료·결과 보존, 종료 확인 실패, 재시작 유지와 범위별 resume를 확인한다. 프로젝트 pause는 다른 프로젝트를 중단하지 않고 resume는 독립 차단·결정·dependency를 해제하지 않는다.
- `maintenance-review <repo>`는 자동 기준값 0·주기 도달 전에도 등록 프로젝트의 전환 요청을 저장하고, 명령 자체에서 모델·verify를 실행하지 않는다. 요청 저장·실제 시작·안전 gate에 따른 대기, 미등록·잘못된 설정·저장 실패, 실행 중 작업·활성 cycle 보존과 같은 요청의 중복 적용 방지를 확인한다. 도움말·예시·Skill은 같은 의미를 안내한다.
- 미착수 유효 수동 제출만 `cancel`·수동 `reset`으로 취소되며 브랜치·작업물·실행 근거와 수동 대기가 보존된다. 과거/이미 취소된 요청의 재확인, 자동 후속 처리 시작과 취소의 경쟁, 착수 뒤 pause에도 취소 자격이 복원되지 않음, 취소 후 자동 재개 없음과 명시적 재제출을 확인한다.
- 자동 `reset`·`manual stop`의 진행 작업 종료, 백업 실패 시 무변경, 관리 rebase만 취소, 정확한 원격 lease와 사용자 source 보존, 현재 실행 근거만 초기화 및 성공 뒤 READY 전환을 확인한다. 중간 실패·재시작에서 백업·감사·미완료 의도가 남고 잘못된 READY나 원격 덮어쓰기가 발생하지 않는다.
- 공유 묶음의 한 G로 취소·중단·초기화를 요청해도 전체 ID·자원에 적용되고 일부 구성원의 거부 조건이면 전체를 보존한다. PR 생성·연결 이후 세 제어 명령은 거부하고 Requirement 수정·새 ExecPlan 경로를 안내하며 실제 Merge 완료 기준은 유지한다.
- 명령어 Skill이 Loop Manager에만 남고 등록 프로젝트로 복사되지 않는다. 수동 준비 성공에서 추가 모델 호출 없이 생성한 복사용 프롬프트에 대상·문서·verify·자연어 재검증·push까지의 지시가 포함되고 PR 생성 지시는 없다. 사용자에게는 별도로 Manager에서 실행할 완료 명령을 안내하며 미완료 준비와 실제 verify·Review 통과를 혼동하지 않는다.
- Skill·수동 완료 안내에서 생략 선택 시 근거 있는 `--skip-reason` 작성을 안내하며 CLI 필수 조건으로 표현하지 않는다. complete·submit의 사유 미입력을 허용하는 R-077과 일치하고 생략 옵션을 자동 선택하거나 검증·Review 수행 사실을 만들어 내지 않는다.
- 실제 provider·모델을 호출하지 않는 관련 targeted unit test와 저장소에서 요구하는 전체 검증이 통과한다. 자동 검증 주체와 실행 범위는 docs/AGENTS.common.md와 해당 역할의 docs/AGENTS.*.md를, 프로젝트 규칙은 프로젝트 지침을, 계획 작성은 docs/PLANS.md를 따른다.

## Product Impact

- 운영자는 로그를 뒤지지 않고 저장된 진행·대기·실패 이유와 다음 조건을 확인할 수 있다.
- 사용자는 저장된 선행 조건과 특정 Requirement의 직접 참조 작업을 확인해 수동 구현 대상을 고를 수 있다. 조회 결과는 실제 수동 시작 조건의 재확인을 대신하지 않는다.
- 운영 조회는 작업 실행·상태·기록·Git·PR·알림에 영향을 주지 않는다.
- 저장 관측과 실시간 상태, 프로세스 존재와 실제 진전, 미수집과 실제 0을 구분한다.
- 상태 설명과 실행 판단은 같은 기존 정책을 사용하며 조회를 위해 복구·재시도 정책을 바꾸지 않는다.
- 사용자는 전체·프로젝트 자동 처리를 명시적으로 중단·재개하고 원하는 등록 대상만 실행한다. pause는 실행 상태와 독립적인 보존 조건이다.
- 사용자는 자동 주기의 기준값이 0이거나 주기가 도래하지 않았어도 CLI로 유지보수 전환을 요청하고, 요청 접수와 실제 전환·대기를 구분한다.
- 수동 제출 취소는 미착수 요청만 종료하고 작업물을 유지한다. 수동 대상 해제·READY 복귀는 `manual stop`에서 수행하며 공유 제출은 묶음 전체에 적용한다.
- 초기화는 소유 작업과 원격 기대값·백업·성공 결과를 확인한 뒤 확정하며 기존 계획·사용자 결정·감사를 보존한다.
- 명령어 Skill과 수동 구현 프롬프트는 같은 CLI 계약을 안내하며 등록 프로젝트에 Skill을 추가 배포하지 않는다.

## Non-Goals

- 새로운 실행 엔진·데몬·상시 수집기, dashboard·TUI·MCP 서버를 추가하지 않는다.
- OpenRig의 daemon·tmux·TUI 구조나 새로운 활동 판정 체계를 도입하지 않는다. [activity-taxonomy](https://github.com/mvschwarz/openrig/blob/decf641773eacf5aa1a8ff84ed2408fbfd846bb6/packages/daemon/src/domain/activity-taxonomy.ts)는 프로세스 존재·활동·재개 가능성·관측 신선도를 구분하는 관점만 참고한다.
- 조회 명령에서 작업 재개·복구 실행·PR 처리·Git 동기화·실시간 원격 조회를 제공하지 않는다. 명시한 상태 변경 명령은 기존 실행·소유권·Git 경계를 재사용한다.
- 금액 비용 계산·예산 제한과 provider reset 시각·cron 실행 시각 추정을 추가하지 않는다.
- 전체 프로세스 재시작 테스트 체계, 알림 outbox 전송 정책 변경, 요구사항별 증거 체계를 추가하지 않는다.
- 이 문서에 명시한 제어·수동 대상 해제·명령 이름 변경 외의 복구·재시도·검증·작업 선택 정책을 변경하지 않는다. pause·READY 전환으로 사용자 결정·dependency·독립 안전 gate를 우회하지 않는다.
- 별도 `backup` 명령, 자동 PR Merge·PR 취소/대체, 소유권 불명 자원 초기화와 독립 Review CLI를 추가하지 않는다.
- R-073의 수집 확대·기간별 분석 전체를 이 작업으로 구현하거나 과거 누락 정보를 추정·보충하지 않는다.
- 명시한 초기화 대상의 소유 작업물은 먼저 복구 가능하게 백업하고 그 밖의 사용자 변경은 덮어쓰지 않는다. 이 명세 작성만으로 커밋·푸시하거나 실행 상태를 변경하지 않는다.
