# [R-049] 변경 입력에 따른 Planner 역할 분리

## Context

현재 Loop Manager는 안전한 선택 경계에서 명세 또는 전체 계획 입력이 바뀌면 실행 가능한 READY보다 일반 Planner를 먼저 실행한다. 일반 Planner는 현재 PRODUCT와 활성 Requirement의 미충족 작업 전체를 확인하고 새 ExecPlan을 만들거나 수정 가능한 미착수 READY를 개정한다.

코드·테스트·설정만 바뀐 경우에도 같은 전체 계획 역할을 수행하므로, 이미 예정된 작업에 영향이 없는 변경까지 넓게 재검토하게 된다. 반면 사용자가 ExecPlan을 직접 변경한 결과는 현재 계획 입력 지문에 포함되지 않는다.

문서 변경에는 전체 계획 역할을 유지하되, 코드 변경에는 기존 예정 작업의 수정 필요성만 빠르게 판단하는 역할을 먼저 적용한다.

## Requirement

### 변경 입력과 실행 역할

- 최신 원격 base에서 PRODUCT, 활성 Requirement, ARCHITECTURE 또는 active ExecPlan이 추가·수정·이름 변경·삭제되면 일반 Planner를 실행한다. 사용자가 직접 게시한 ExecPlan 변경도 포함하며, 변경된 계획과 나머지 작업의 정합성을 함께 확인한다.
- 문서와 코드가 함께 바뀐 경우에는 일반 Planner를 실행한다. `AGENTS.md` 변경도 기존 승인·검증 절차를 거쳐 일반 Planner로 반영한다.
- 위 문서와 지침이 그대로이고 기존 전체 계획 입력에 포함되는 코드·테스트·설정만 바뀌면, 수정 가능한 미착수 READY가 있는 경우 읽기 전용 빠른 점검 Planner를 먼저 실행한다.
- 코드만 바뀌어도 수정 가능한 미착수 READY가 하나도 없으면 빠른 점검을 생략하고 일반 Planner가 새로 필요한 미충족 작업을 확인한다. dependency 대기 중인 무소유 READY는 점검 대상에 포함하되, 실행 중이거나 이미 실행 이력이 있는 계획을 수정 대상으로 삼지 않는다.
- 최초 계획 또는 비교 가능한 성공 기준이 없는 경우에는 일반 Planner를 실행한다. 단순 revision 전진이나 같은 입력의 재관측만으로 두 역할을 반복 실행하지 않는다.
- 실행 중인 작업은 선점하지 않는다. 확정 PR 충돌 복구, 활성·due 유지보수 cycle, dependency, 차단과 게시 복구의 기존 선택 순서 및 안전 조건을 유지한다. 빠른 점검이 필요한 경우에는 다음 READY Worker를 시작하기 전에 그 결과를 확정한다.

### 빠른 점검의 책임과 일반 Planner 인계

빠른 점검 Planner는 마지막 성공 기준 이후의 코드 변경과 현재 비종료 compact catalog, 수정 가능한 미착수 READY를 바탕으로 예정 작업을 그대로 실행할 수 있는지만 판단한다. 관련 계획 본문, 코드·테스트 및 근거 문서는 영향 판단에 필요한 부분만 확인하며, 전체 미충족 작업이나 저장소 전체 개선점을 다시 탐색하지 않는다.

판단 결과는 다음과 같이 구분한다.

- **수정 불필요**: 기존 예정 작업의 목표·범위·의존성·구현 방향·검증 조건을 유지해도 되는 경우다. 일반 Planner 없이 기존 READY 선택을 이어간다.
- **수정 필요**: 변경으로 예정 작업이 이미 충족됐거나 중복·무효가 됐거나 구현 방향·검증 조건·의존성을 바꿔야 하는 경우다. 영향받은 계획과 변경 근거를 일반 Planner에 전달한다.
- **판단 불확실**: 변경 영향 또는 계획의 유효성을 제한된 점검으로 확정할 수 없는 경우다. 확인한 사실과 불확실한 지점을 일반 Planner에 전달한다.

빠른 점검 Planner는 파일, ExecPlan 또는 `FUTURE_IDEAS.md`를 작성·수정하지 않으며, 코드 구현·테스트 실행·commit·push·PR 생성을 수행하지 않는다. 일반 Planner 인계는 같은 최신 입력에 대해 한 번만 수행하고, 인계 뒤에는 일반 Planner가 기존 역할과 권한으로 작업을 확인·작성한다. 빠른 점검 결과만으로 기존 계획의 변경 권한을 확대하지 않는다.

### 변경 기준과 재시작

일반 Planner 자신의 검증된 계획 게시와 유지보수 Planner의 검증된 개정 결과는 적용된 결과로 인식해 동일 변경이 다시 일반 Planner를 유발하지 않도록 한다. 기존의 내용 보존 Requirement archive-only 및 검증된 ExecPlan archive 예외도 유지한다. 자동 결과라는 근거가 불충분하거나 별도의 사용자 문서 변경이 섞이면 문서 변경을 무시하지 않는다. `FUTURE_IDEAS.md`는 계속 계획 입력에서 제외한다.

빠른 점검의 수정 불필요 결과는 해당 입력과 대상 계획이 여전히 같음을 확인한 뒤에만 성공 기준으로 반영한다. 이 결과는 예정 작업의 유지 가능성을 뜻하며, 전체 PRODUCT·Requirement의 추가 작업 없음 판단이나 유지보수 평가 성공을 대신하지 않는다. 일반 Planner 인계, 실패 또는 불확실한 결과만으로 성공 기준을 전진시키지 않는다.

점검·인계·게시 중 원격 입력 또는 대상 계획의 상태·소유권이 바뀌면 오래된 결과를 적용하지 않고 최신 입력으로 역할을 다시 선택한다. 중단·재시작 뒤에도 점검 결과와 일반 Planner 인계를 중복 확정하지 않으며, 실패를 수정 불필요로 간주하지 않는다. Agent 실행·설정·형식 오류에는 기존 planning 오류와 재시도 정책을 적용한다.

### 모델과 사고 수준

일반 Planner와 빠른 점검 Planner의 Model·Effort를 provider별로 독립 설정할 수 있어야 한다. 빠른 점검에 더 가벼운 모델이나 낮은 사고 수준을 사용할 수 있지만 서로 다른 값을 강제하거나 특정 모델을 고정하지 않는다. 빠른 점검 설정을 생략한 기존 설정에서는 일반 Planner의 Model·Effort를 사용한다.

역할 선택은 프로그램이 변경 입력에 따라 결정한다. 일반 Planner로 인계되면 일반 Planner의 설정을 사용하며, 역할·Model·Effort와 인계 사유를 로그 및 기존 호출 사용량 기록에서 구분할 수 있어야 한다. 역할이 바뀔 때 빠른 점검의 읽기 전용 범위와 일반 Planner의 변경 권한이 섞이지 않아야 한다.

## Acceptance Criteria

- PRODUCT, 활성 Requirement, ARCHITECTURE 또는 사용자가 게시한 active ExecPlan 변경은 실행 가능한 READY가 있어도 다음 안전한 선택 경계에서 일반 Planner를 먼저 실행한다. ExecPlan 추가·수정·이름 변경·삭제와 코드 동시 변경을 포함한다.
- 코드·테스트·설정만 바뀌고 수정 가능한 미착수 READY가 있으면 빠른 점검을 먼저 실행한다. 수정 불필요 결과에서는 파일 변경과 일반 Planner 호출 없이 기존 priority·dependency 규칙으로 다음 작업을 선택한다.
- 예정 작업이 이미 구현됐거나 변경된 코드 때문에 구현·검증·의존성을 개정해야 하면 수정 필요로 판단하고, 제한된 점검으로 결론을 내리지 못하면 판단 불확실로 구분한다. 두 경우 모두 근거를 전달받은 일반 Planner가 한 번 실행된다.
- 코드만 바뀌고 수정 가능한 미착수 READY가 없으면 일반 Planner가 미충족 작업을 확인한다. 성공 기준이 없는 최초 계획도 일반 Planner를 사용한다. dependency 대기 READY가 있으면 빠른 점검 후 기존 대기 조건을 유지한다.
- 빠른 점검은 관련 변경과 계획만 확인하고 전체 미충족 작업·저장소 개선점 탐색을 요구받지 않는다. 역할 위반 쓰기나 잘못된 결과는 성공으로 적용되지 않는다.
- 실행 중인 작업, PR 충돌 복구와 유지보수 cycle의 기존 우선순위, mutable READY의 변경 조건 및 snapshot 밖 계획 보호가 유지된다.
- 검증된 자체 계획 게시·개정과 archive-only 처리는 일반 Planner 재실행을 연쇄 유발하지 않는다. 별도의 사용자 계획 변경과 출처가 불확실한 변경은 제외하지 않는다.
- 같은 입력과 대상의 수정 불필요 결과는 반복 실행·재시작 뒤 재점검하지 않는다. 인계·실패는 성공 기준을 전진시키지 않으며, 점검 뒤 문서·코드·대상 상태가 바뀌면 오래된 결과로 Worker를 시작하지 않는다.
- 두 역할에 서로 다른 Model·Effort를 설정하면 각 호출과 인계에 해당 설정이 적용된다. 빠른 점검 설정이 없는 기존 설정도 유효하며 일반 Planner 설정으로 동작한다.
- 로그와 호출 사용량 기록으로 일반 계획, 빠른 점검, 점검 결과 및 인계 사유를 식별할 수 있다. 빠른 점검 성공만으로 프로젝트 완료 또는 유지보수 평가 성공을 새로 확정하지 않는다.

## Product Impact

- 문서 변경은 일반 Planner가 전체 작업 정합성을 확인하고, 코드 변경은 기존 예정 작업의 유지 가능성을 먼저 좁게 확인한다.
- 빠른 점검은 판단만 담당하며 계획 변경은 기존 권한을 가진 일반 Planner가 담당한다.
- Planner 역할별 Model·Effort를 설정할 수 있고, 성공 기준은 실제로 확인한 판단 범위에 한정된다.

## Non-Goals

- 빠른 점검 Planner에 계획·코드·명세 변경 권한을 부여하지 않는다.
- 일반 Planner의 기존 작업 범위, mutable READY 권한 또는 유지보수 Planner의 역할을 확대하지 않는다.
- 같은 프로젝트의 병렬 실행, 자동 Merge, 새로운 외부 서비스 또는 저장소 전체 평가를 추가하지 않는다.
- 특정 모델·사고 수준, 실행 시간 또는 토큰 절감률을 강제하지 않는다.
- Worker·Reviewer의 Model 선택, 세션 정책과 검증 책임을 변경하지 않는다.
