# [R-055] 차단 경로 전수 조사와 불필요한 작업 중단 축소

## Context

현재 제품은 일시 재시도, 상태 재구성, Agent 교정과 최종 사용자 조치를 구분하고 계획·프로젝트 차단을 분리한다. ignored 비교, 비차단 로컬 동기화, 현재 상태 기반 rebase, 게시 checkpoint 재개와 단계별 원격 문서 반영은 이미 구현돼 있다. 저장소 전체 snapshot 비교와 과거 기준선 복원이 정상 Git 작업을 막거나 덮어쓰는 잔여 경로를 제거한다.

개별 계획 문제는 기본적으로 그 계획의 차단으로 처리한다. 이 요구사항은 catalog 전체 유효성 gate 등 개별 오류가 프로젝트 전체 중단으로 확대되는 기존 동작을, 영향받는 범위의 격리와 검증된 독립 작업의 진행으로 변경한다.

이번 조사는 Loop Manager 코드의 차단·중단 생성 및 복구 경로를 대상으로 한다. 현재 운영 SQLite에 저장된 개별 차단 사건을 조사하는 작업은 포함하지 않는다.

## Requirement

### 전수 조사와 판단

설정·시작·bootstrap, 원격 관측·catalog, 일반·유지보수 planning, workspace·Agent 범위, Worker·verify·Review, rebase·게시·PR 및 정리·archive에서 실행을 중단하거나 `planning_error`, `PLAN_BLOCKED`, `PROJECT_BLOCKED`를 만드는 모든 코드 경로와 공통 호출 경로를 조사한다. 차단의 재평가·해제·재개 경로도 함께 확인한다.

각 경로는 발생 조건, 보호하는 실제 불변식, 차단 범위, 자동 복구 가능 여부, 재개 조건과 필요한 사용자 행동을 확인한다. 정상적인 일시 대기, 자동 복구 가능한 실패, 개별 계획 문제와 실제 프로젝트 안전 문제를 구분하고, 현재 명세와 맞지 않는 오탐·중복·과도한 차단을 근거와 함께 식별한다. 기존 안전 차단도 조사 목록에 포함하되 변경할 필요가 없으면 그 이유를 남긴다.

### 불필요한 중단의 수정

Git의 정상 변경 수용·현재 입력·게시 분리에 대한 공통 변경 기준은 아래 절에서 정의한다. 로컬 원본 동기화는 R-056, exact-SHA runtime 귀속은 R-020, 원격 실행·self handoff와 호출 격리는 R-023, 단계별 문서 갱신은 R-082, ignored 파일은 R-022, 성공 근거 재사용은 R-072를 따른다. 해당 문서에서 공통 Git 기준을 반대로 정의하지 않는다.

- 최신 원격 입력과 현재 작업의 소유권·범위·Git 상태로 안전한 다음 단계를 확정할 수 있으면, 낡은 비교 기준이나 복구 기록의 형식 차이만으로 차단하지 않고 기존 작업을 보존해 재구성·재개한다.
- 일시적 네트워크·외부 CLI·Git 경쟁, 다음 외부 실행에서 이어갈 수 있는 실행별 한도와 부수적인 정리·알림·로컬 동기화 실패는 해당 원인에 맞는 재시도·일시 대기·pending으로 처리한다. 그 이유만으로 사용자 수정이 필요한 최종 차단을 만들지 않는다.
- 한 계획에 국한된 실패는 계획 범위로 제한하고, 독립 계획과 다른 프로젝트가 계속 진행할 수 있게 한다. 프로젝트 전체 차단은 실제 공유 자원·안전 조건이 해결되지 않아 해당 프로젝트의 새 작업도 안전하지 않은 경우에 한정한다.
- 개별 ExecPlan의 선언·의존성 오류, 작업 branch·worktree 문제와 승인 대기는 그 계획과 영향받는 의존 계획에 한정한다. catalog 오류라는 분류나 복구 경로의 부재만으로 프로젝트 차단으로 확대하지 않는다. 오류 선언은 유효한 입력으로 채택하지 않고 마지막 검증 선언·작업물·진단을 보존한다. 식별자·의존 관계가 불확실한 범위는 실행하지 않되 독립성과 유효성을 확인한 계획은 진행한다. 프로젝트 전체의 식별·공유 소유권·안전을 확정할 수 없을 때만 근거를 명시해 프로젝트 gate를 유지한다.
- 이미 해소된 원인으로 남아 있는 차단은 현재 근거를 확인한 뒤 그 원인만 해제한다. 입력 지문 변화가 없는 오탐도 재평가할 수 있어야 하며, 다른 차단·승인·실패 이력을 함께 지우지 않는다.
- 상태·작업물·branch·worktree·Agent session과 미해결 피드백을 보존한다. 복구가 후보를 바꾸면 필요한 Worker 확인·targeted test·Manager verify·Review를 다시 거친다.
- 재시도에는 기존 한도와 동일 입력의 진전 여부를 적용한다. 최종 검증 실패, 실제 범위 위반·소유권 불확실성, 손상 또는 사용자 결정이 필요한 상황을 무한 재시도로 바꾸지 않는다.
- 시작 오류처럼 차단 상태를 만들기 전 중단하는 경로도 필요한 조건과 오류 범위를 확인한다. 실제 원격 기준이나 필수 설정을 검증할 수 없는 상황을 성공으로 취급하지 않는다.

원격 ref·runtime 귀속의 수락·거부는 아래 공통 Git 기준과 R-023·R-020대로 Agent 결과, 저장 단계 선검증, 계획/프로젝트 복구와 checkpoint에서 대조한다. 같은 정상 fetch/push나 파생 HEAD 변화를 검사 경로만 바뀌었다는 이유로 다시 공유 ref 위반으로 차단하지 않는다. rebase 중 구현 입력과 순수 기록 변경의 구분은 R-072를 따른다.

checkpoint의 저장 요청과 현재 차단 사유·evidence·상태가 달라지면 게시 전에 같은 repository·계획·branch·worktree·현재 원인을 다시 읽는다. 해결된 원인의 요청은 취소하고, 같은 소유 작업의 새 원인이면 그 원인에 결합된 요청으로 갱신해 안전 검사를 다시 수행한다. 오래된 요청의 identity 불일치만으로 별도 프로젝트 차단이나 Worker 교정 횟수를 만들지 않는다. 실제 자원·원격 lease·소유권 변화는 거부하며, 중단·재시작과 SQLite 확정 경쟁에서도 다른 차단·승인을 해제하거나 낡은 작업물을 게시하지 않는다.

### 정상 Git 변경과 실행 입력

사용자는 원격 원본·로컬 원본·원격 작업 branch에 언제든 push하거나 정상 Git 작업을 수행할 수 있다. Manager와 다른 프로세스의 fetch도 모든 단계에서 발생할 수 있다. remote-tracking ref·`FETCH_HEAD`와 무관한 ref/worktree의 변화만으로 `PLAN_BLOCKED`·`PROJECT_BLOCKED`를 만들지 않는다. ref OID 변화는 새로운 관측 입력이며 Agent의 직접 쓰기 증거와 구분한다.

Planner·Worker·verify·Reviewer의 단계 처리에서도 fetch·pull·rebase가 필요할 수 있다. 실제 Git 쓰기는 기존 Manager 경계에서 수행하고 역할별 파일 권한과 Reviewer의 읽기 전용은 유지한다. 같은 자원의 Agent·verify·Git writer가 실행 중이면 Manager의 동기화를 겹치지 않는다. 안전한 단계 경계에서 갱신하고 실제 경합은 현재 상태를 다시 관측해 제한 재시도·대기로 처리한다.

일반 verify는 Agent invocation 격리 증거를 요구하는 저장소 전체 비교를 사용하지 않는다. 실행 대상 worktree의 identity·HEAD·index·tracked 입력과 실제 검증 입력을 검사한다. source checkout·무관한 worktree·정상 외부 fetch는 후보가 불변이면 성공을 무효화하지 않는다. Agent preflight도 전체 GitSnapshot digest의 완전 일치 대신 해당 호출의 실제 자원·정책·origin·입력을 확인한다. 신규 호출의 쓰기 격리 확인은 계속 필요하다.

실제 후보 HEAD·index·tracked 파일 또는 R-072의 검증 입력이 달라지면 이전 verify·Review·게시 근거를 무효화하고 필요한 단계부터 다시 수행한다. 정상 원격 변경을 수용했다는 사실은 오래된 성공을 재사용할 근거가 아니다. 단계마다 관측한 immutable OID를 사용하며 게시 직전에는 실제 원격을 다시 확인한다.

### legacy 기본 checkout과 BLOCKED 수동 작업

격리 증거 없는 과거 실행에도 기본 checkout의 파일·index·HEAD·로컬 base ref를 scope 비교에서 제외한다. 이는 G-199의 A안을 확정한 정책이다. 격리 성공을 과거 기록에 합성하지 않으며 실제 Agent의 범위 밖 쓰기·origin 변조·보안 설정 변경 증거는 보존한다. 선택 작업의 자원·등록·소유권을 확인할 수 없는 경우에는 해당 영향 범위를 보류한다.

차단으로 사용자에게 작업을 인계한 뒤 파일 수정·staging·commit·rebase·충돌 해결은 현재 작업의 새 입력으로 수용한다. 재개 전에 이전 Agent·verify·Git writer의 종료, 동일 repository·계획·canonical worktree·branch 연결, 현재 HEAD·index·파일·operation을 확인한다. 진행 중인 사용자 Git operation은 완료됐다고 추정하거나 임의 abort하지 않는다.

과거 Agent 시작·결과 snapshot과 현재 파일·index·HEAD의 완전 일치를 재개 조건으로 요구하지 않는다. 역사 snapshot은 진단·감사로 보존하고 현재 사용자 작업을 과거 기준선으로 되돌리지 않는다. `read-tree --reset -u`·reset·checkout 등의 복구도 인계 뒤 변경을 덮어쓰지 못해야 한다. 이전 실패의 감사와 다른 차단·승인을 유지하며 필요한 Worker 확인·targeted test·verify·Review를 새 후보에 결합한다.

### 로컬 수용과 원격 게시의 분리

현재 로컬 작업을 실행 입력으로 수용하는 것, 새 원격 작업을 통합하는 것, 원격을 갱신할 권한은 각각 판단한다. 로컬을 원격 원본 위로 정상 rebase한 `A → C → B'`는 원격 작업 tip `A → B`를 조상으로 포함하지 않아도 수용할 수 있다. 과거 remote OID·checkpoint HEAD·Manager rebase 표식의 일치만을 필수 수용 조건으로 사용하지 않는다. 수행하지 않은 rebase 완료나 게시 성공을 합성하지 않는다.

원격 작업 branch에 새 사용자 commit이 있으면 로컬과 원격을 보존해 기존 통합 경로로 연결하고 바뀐 후보를 재검증한다. 실제 충돌은 해당 통합·작업 범위만 대기 또는 복구한다. 원격의 삭제·force push·재생성도 로컬 결과를 폐기하거나 저장소 전체 차단의 충분조건으로 삼지 않는다. 관계·게시 권한을 확인하지 못하면 해당 원격 게시를 보류한다.

게시 전 관측과 push 사이의 경쟁은 재관측·통합·후보 검증으로 돌아간다. 명시적 expected OID 또는 정확한 부재에 결합된 `--force-with-lease`는 유지하며, 최신 원격 OID만 lease에 바꿔 넣고 무검증 재시도하지 않는다. 중간 checkpoint 게시 실패는 미게시 작업을 보존하고 로컬 수용·구현 재개와 분리한다. 미완료 게시 결과의 관측·확정은 안전한 다음 쓰기 전에 해결한다.

### 동기화·journal·cleanup·변경 없음

runtime은 한 실행의 선택 revision을 유지하고 외부 fetch로 ref가 바뀌어도 파일을 바꾸지 않는다. 다음 실행의 원격 선택, 로컬 동기화 실패와 runtime 소유권 오류를 구분한다. Git journal은 실제 미완료 전이·자원·소유자에만 적용하며 무관한 ref/worktree의 기록으로 다른 작업을 막지 않는다.

Merge 확인 뒤 cleanup 실패는 `cleanup_pending`으로 보존·재시도하고 완료 결과나 독립 작업을 되돌리지 않는다. 이미 원격 확인된 문서 게시의 성공 근거는 해당 게시 revision으로 유지하고, 이후 사용자가 수정한 최신 문서는 새로운 입력으로 평가한다. 미확정 게시를 byte 불일치만으로 성공 처리하지 않는다.

원격 변경으로 후보 diff가 사라지면 기존 PR의 실제 Merge, 외부 변경에 의한 목표 충족, 구현 부족과 대체 필요를 구분한다. `NO_CHANGE`만으로 계획 입력 오류·최종 차단을 만들지 않는다. 외부 목표 충족은 최신 명세·구현·검증 근거로 Planner가 기존 미충족 목표와 관계를 정리하며, 연결 PR Merge 없이 ExecPlan을 `MERGED`로 만들거나 dependency를 충족했다고 기록하지 않는다.

중복 snapshot·ancestry·checkpoint 복구 판정은 기존 공통 경계로 통합하고 불필요한 이전 검사·복원 분기를 제거한다. 새 예외·상태 테이블·복구 계층을 계속 추가하는 방식으로 구현하지 않는다.

### 사용자 계획 삭제와 catalog 자동 정리

- ExecPlan ID는 고유성을 요구하되 번호의 연속성을 요구하지 않는다. 중간 번호가 비었다는 이유로 오류·복원 작업을 만들거나 사용한 ID를 재사용하지 않는다.
- 사용자가 원격의 계획 파일을 삭제하면 active·archive 이동, 실제 삭제와 신규 계획 추가를 현재 원격 변경·게시 감사·실행 이력으로 구분한다. 삭제와 새 ID의 동시 발생만으로 같은 계획의 ID 변경이라고 추정하지 않는다. 미착수·무소유 계획의 확인된 삭제는 정상 취소로 반영하고 ID 취소 감사를 보존한다. 삭제 파일을 임의로 되살리거나 삭제를 Merge 완료로 간주하지 않는다.
- 삭제로 다른 계획의 dependency·source·구현·검증 근거가 낡아지면 최신 PRODUCT·Requirement와 보존된 계획 내용을 대조해 자동 정리를 먼저 시도한다. Planner는 영향받는 미착수·무소유 ExecPlan을 허용된 snapshot에서 함께 개정하고, 아직 필요한 목표는 새 ID의 대체 계획으로 연결할 수 있다. 변경된 전체 관계와 목표 보존을 검증한 뒤 원격 게시·cache 적용을 확정한다. 선행 목표가 남아 있는데 dependency만 지워 실행시키지 않는다.
- 이미 실행한 계획·branch·worktree·session·PR과 완료·취소 감사는 파일 삭제로 없애지 않는다. 계속 실행·취소·대체의 의미를 현재 근거와 권한으로 확정할 수 있으면 필요한 복구를 진행한다. 확정할 수 없으면 해당 계획과 의존 범위만 보존·중단하며 독립 계획의 실행과 PR 관측은 계속한다.

### planning 오류와 기존 계획의 실행

- 계획 생성·교정 오류는 새 Planner 주기의 시작과 프로젝트 완료 선언을 보류하되, 이미 게시된 유효한 독립 ExecPlan의 순차 구현·검증·Review·기존 PR 처리를 막지 않는다. 변경된 코드·구조에도 해당 계획의 목표·dependency·검증 기준이 유효한지 먼저 확인하며, 유효성을 확정하지 못한 계획은 그 영향 범위만 보류한다.
- 오류가 난 planning worktree·session·입력 지문·미게시 결과·진단은 실행 상태와 독립적으로 보존하고 변경 실행 자리를 안전하게 비운다. 다른 계획의 실행·PR Merge가 오류를 지우거나 planning 결과를 성공으로 확정하지 않는다. 진행 중 Git operation·미확정 게시·실제 공유 자원 불확실성은 기존 안전 경계에서 먼저 정리·확정하며 planning 기록을 강제로 덮어쓰지 않는다.
- 같은 실패 입력의 Planner 호출은 반복하지 않는다. 관련 원격 입력 또는 R-062의 로컬 환경 재검사 요청이 생기면 보존된 planning 작업을 재평가하고, 실제 원인이 해소된 뒤에만 오류를 해제한다. 상태 재구성·중단·재시작에서도 기존 계획의 진행과 planning 오류 보존을 함께 유지한다.

일반적인 차단 완화라는 이유로 검사를 통째로 제거하지 않는다. 같은 원인이 여러 경로에서 발생하면 공통 판정·복구 경계에서 일관되게 수정하고, 실제 위반을 계속 거부하는 회귀 조건을 함께 검증한다. 조사 결과와 수정·유지 이유는 관련 ExecPlan에 남기며, 현재 범위 밖의 구조 개선은 이 조사의 구현으로 확대하지 않는다.

## Acceptance Criteria

- 코드의 모든 차단·중단 생성 경로와 재개 경로를 추적 가능한 목록으로 정리하고, 각각의 조건·scope·보호 규칙·자동 복구·사용자 조치를 관련 ExecPlan에서 확인할 수 있다.
- 오탐과 과도한 차단으로 판정한 경로에는 재현 가능한 코드·테스트 근거, 수정 동작과 실제 위반을 유지하는 회귀 검증이 있다. 문제가 없는 경로도 검토 근거를 남긴다.
- 자동 복구 가능한 일시 실패와 실행별 한도는 작업을 보존하는 대기로 처리되고 다음 실행에서 재개한다. 같은 입력에서 진전 없는 무제한 호출·Git 쓰기·중복 알림은 발생하지 않는다.
- 계획별 실패가 독립 READY와 다른 프로젝트를 막지 않으며, 실제 공유 자원·소유권·범위 문제는 적절한 프로젝트 안전 차단을 유지한다.
- 한 계획의 잘못된 선언·의존성, 전용 작업 공간 문제와 승인 대기에서 해당 계획과 영향받는 의존 계획은 중단되고 독립성이 검증된 계획의 선택·planning과 PR 관측은 계속된다. 식별·공유 안전이 실제로 불확실한 경우에는 관련 작업을 실행하지 않고 차단 근거를 확인할 수 있다.
- 번호 공백, 사용자 원격 파일 삭제·archive 이동과 삭제·새 계획 동시 추가를 구분하고, 정상 변경만으로 프로젝트를 차단하거나 계획 ID를 추측·재사용하지 않는다. 확인된 미착수 삭제의 취소 감사와 이미 실행한 작업·PR 이력은 보존된다.
- 삭제된 계획을 참조하는 다른 ExecPlan은 최신 목표에 맞는 개정·대체·관계 정리로 자동 복구를 먼저 시도한다. 유효한 최종 관계를 원격에 게시하고 실행 cache에 반영하며, 아직 필요한 선행 목표를 dependency 제거로 우회하지 않는다. 불확실한 영향 범위만 중단된다.
- planning 오류가 남아도 안전하게 실행 자리를 비운 뒤 기존의 유효한 독립 READY·리팩터링 계획을 순차 실행하고 기존 PR 관측·충돌 복구를 계속한다. 같은 입력의 신규 Planner 반복과 프로젝트 완료 선언은 보류되며, 오류·session·미게시 결과는 다른 계획 진행·중단·재시작 뒤에도 보존된다.
- 이미 해소된 오탐은 단순 입력 지문 변경을 요구하지 않고 검증 후 재개하며, 실제 범위 위반과 독립 차단·승인을 함께 해제하지 않는다.
- 복구와 재시작 전후 작업물·session·실패 피드백이 보존되고, 변경된 후보는 기존 최종 검증·Review·게시 조건을 다시 만족해야 한다.
- R-020·R-023의 정상 외부 base 전진·runtime 재사용·파생 HEAD 변화에 대해 Agent 결과·저장 선검증·계획/프로젝트 복구·정상 및 진단 checkpoint의 Git metadata 귀속 판정이 일치한다. 실제 Agent 위반·ref 재작성·소유권 불확실성 혼합은 계속 거부하며, 선행 구현의 함수별 성공만으로 전체 경로 충족을 선언하지 않는다.
- 차단 원인 갱신·해제·재차단과 checkpoint 요청/게시/SQLite 확정 사이의 중단에서 오래된 요청은 취소 또는 현재 원인으로 재검증된다. stale identity만으로 새 최종 차단·Worker 호출·교정 횟수가 생기지 않고, 실제 소유권 경쟁과 다른 차단·승인은 보존된다.
- rebase 중 R-072가 구분한 순수 진행·검증 기록 변경은 구현 입력 변경 차단을 만들지 않는다. 실제 목표·범위·source·승인 변경과 분류 불확실성은 작업을 보존해 필요한 재확인·재검증을 거친다.
- 로컬 base 동기화와 Python 캐시는 각각 R-056·R-059의 구체적인 정책을 따르며 중복된 상충 정책을 만들지 않는다.
- 조사는 코드와 테스트를 기준으로 수행하며 운영 SQLite 사건의 개별 수정·삭제 또는 그 기록을 근거로 한 운영 발생 빈도 주장을 포함하지 않는다.

### Git 회귀 기준

아래 시나리오는 성공뿐 아니라 관측 경쟁·중단·재시작에서도 작업물·session·독립 원인 보존을 확인한다. 판단·상태 조합은 관측 경계를 mock으로 제공하고 실제 판단·SQLite를 실행한다. shared ref·worktree·rebase·index·lease의 실제 효과만 필요한 통합 회귀로 확인한다.

| ID | 시나리오와 완료 조건 |
|---|---|
| T01 | Planner 중 외부 fetch가 있어도 무관한 ref 변화로 차단하지 않는다. |
| T02 | Worker 중 외부 fetch를 scope 위반으로 귀속하지 않는다. |
| T03 | verify 중 외부 fetch에서 실제 검증 입력이 불변이면 정상 완료한다. |
| T04 | Reviewer 중 외부 fetch에서 후보가 불변이면 정상 완료한다. |
| T05 | remote-tracking ref·FETCH_HEAD 갱신만으로 프로젝트를 차단하지 않는다. |
| T06 | pull/rebase로 실제 후보·검증 입력이 바뀌면 이전 성공을 무효화하고 필요한 단계부터 수행한다. |
| T07 | dirty 원본은 FF-only만 시도하며 실패하면 staged·unstaged·untracked를 보존한다. |
| T08 | clean diverged 원본은 로컬 commit을 보존해 안전한 rebase를 시도한다. |
| T09 | Manager 소유 rebase 충돌은 안전한 abort 뒤 원래 HEAD·index·tracked 파일 보존을 검증한다. |
| T10 | BLOCKED 인계 뒤 사용자 파일 수정·staging을 수용하고 과거 snapshot으로 복원하지 않는다. |
| T11 | BLOCKED 인계 뒤 사용자 commit의 새 HEAD를 입력으로 수용한다. |
| T12 | 원격 작업 tip이 조상이 아닌 정상 원격 원본 기준 로컬 rebase를 수용한다. |
| T13 | 로컬·원격 양쪽의 새 작업을 보존해 통합하거나 실제 충돌 범위만 보류한다. |
| T14 | 게시 직전 사용자 push를 덮지 않고 다시 관측·통합·검증한다. |
| T15 | Planner 단계 사이 원격 ExecPlan·명세 수정은 R-082대로 반영한다. |
| T16 | runtime 실행 중 원격 원본 갱신에도 선택 revision을 유지한다. |
| T17 | 다음 실행은 최신 원격을 확인해 안전한 새 runtime을 준비한다. |
| T18 | index-free ignored-only 변화는 scope·dirty 오탐 차단을 만들지 않는다. |
| T19 | ignored와 들어오는 tracked 경로 충돌은 파일을 보존하고 해당 Git 쓰기만 보류한다. |
| T20 | Merge 뒤 cleanup 실패는 완료 결과를 보존하고 cleanup만 재시도한다. |
| T21 | 원격 확인된 과거 문서 게시 뒤 사용자 수정은 과거 완료와 최신 재평가로 분리한다. |
| T22 | 실제 관리 worktree 오연결·동일 자원 writer·origin 변조는 안전 검사를 유지한다. |
| T23 | 원격 삭제·재작성·재생성은 미게시 로컬 작업을 보존하고 무검증 덮어쓰기를 막는다. |
| T24 | 외부 변경으로 diff가 없으면 목표 충족·구현 부족·실제 PR Merge를 구분하고 NO_CHANGE만으로 차단하지 않는다. |

## Product Impact

- 차단을 실제 사용자 조치와 안전 문제에 맞게 한정하고 자동 복구 가능한 작업을 보존해 이어간다.
- 차단·복구 정책을 모든 실행 경로에서 일관되게 적용한다.

## Non-Goals

- 현재 운영 SQLite의 차단 기록 조사·변경·삭제 또는 운영 데이터 migration을 수행하지 않는다.
- 안전·승인·최종 검증을 생략하거나 모든 실패에 무제한 재시도를 적용하지 않는다.
- 새로운 복구 서비스·Agent 역할이나 범위 밖의 저장소 전체 리팩터링을 추가하지 않는다.
