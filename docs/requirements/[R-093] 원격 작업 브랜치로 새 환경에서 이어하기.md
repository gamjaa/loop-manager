# [R-093] 원격 작업 브랜치로 새 환경에서 이어하기

## Summary

새 환경에 기존 DB가 없어도 원격 작업 브랜치와 PR 기록으로 기존 작업을 식별해 새 Worker 세션으로 이어간다. Worker가 만든 각 checkpoint commit은 Manager가 즉시 원격에 게시한다. PR의 실제 병합은 terminal 완료로 처리하며 이전 검증·Review 증거를 새 환경에 추정해 승계하지 않는다. 같은 프로젝트의 여러 환경에서 동시 개발하는 것은 지원하지 않는다.

## Context

현재 관리 worktree 생성은 로컬 branch의 소유 상태를 확인하며, DB 행이 없을 때 기존 원격 branch를 자동 인수하지 않는다. DB가 없는 환경에서 열린 PR을 자동으로 다시 연결하는 경로도 없다. 이에 따라 기존 원격 작업물을 보존했더라도 새 환경에서 이어가기 어려울 수 있다.

Git commit과 push는 코드 작업의 복구점을 제공하지만 Worker 완료, verify 통과 또는 Review 승인을 증명하지 않는다. 새 환경에 과거 실행 근거가 없으면 필요한 검증을 다시 수행해야 한다. 기존 DB의 손상 복구와 개별 DB 행의 일반 복구는 이 요구사항의 대상이 아니다.

기존 작업의 소유권·원격 변경·정확한 lease 확인은 [R-055](%5BR-055%5D%20차단%20경로%20전수%20조사와%20불필요한%20작업%20중단%20축소.md)의 공통 안전 기준을 따르고, 성공 결과 재사용 여부는 [R-072](%5BR-072%5D%20입력%20동일성이%20증명된%20구현%20후보%20성공%20결과%20재사용.md)의 조건을 유지한다. [R-061](%5BR-061%5D%20Agent%20역할·문서%20권한과%20draft%20ExecPlan%20사용자%20판단.md)의 Git 권한 중 Worker의 로컬 checkpoint commit만 이 요구사항의 좁은 예외이며 나머지 Git 쓰기는 Manager가 담당한다.

## Requirement

### Checkpoint commit과 원격 게시

- Worker는 선택된 관리 작업 branch에 의미 있는 작업 단위의 로컬 commit을 만들 수 있다. 각 commit 직후 Manager가 같은 원격 관리 branch에 push한다. Worker에게 push·fetch·rebase·PR 조작 권한을 주지 않는다.
- 성공한 push는 해당 commit이 원격에 보존된 복구점임을 뜻한다. Worker·verify·Review의 성공 근거로 취급하지 않는다.
- push가 실패하면 로컬 commit과 작업물을 보존하고 게시 대기로 둔다. Manager는 원인을 재관측해 안전한 게시를 재시도하며, 게시가 해결되기 전에 Worker가 새 작업물을 추가하지 않는다.
- 원격 branch가 전진했으면 repository·작업·branch 소유권과 관측한 원격 OID를 확인한다. 안전한 경우에만 원격 commit을 보존한 채 충돌 없는 rebase를 수행하고, fast-forward 또는 정확히 관측한 OID에 결합한 lease로 게시한다. 재작성된 후보에는 변경된 입력에 필요한 검증과 Review를 다시 적용한다.
- 충돌, 소유권 불명, lease OID의 재변경 또는 안전한 통합 여부를 판정할 수 없는 상태에서는 강제 덮어쓰지 않는다. 로컬·원격 양쪽 commit을 보존하고 작업을 보류한다. push 성공만으로 검증 보류를 해제하지 않는다.

### DB가 없는 새 환경에서의 원격 작업 인수

- 인수는 해당 프로젝트 DB 전체가 없는 환경에서 수행할 수 있다. DB 부재는 초기 새 환경뿐 아니라 기존 DB 전체를 잃은 경우도 포함한다. 손상되거나 읽을 수 없는 DB, 일부 행만 빠진 DB를 부재로 간주하지 않으며 기존 DB를 원격 자료로 덮어쓰지 않는다.
- Manager는 원격 저장소, 현재 등록된 프로젝트와 base branch, 활성 ExecPlan 선언과 작업 ID, 정확한 관리 branch 이름 및 원격 HEAD를 대조한다. 이름만 맞는 branch는 인수 근거가 아니다. PR이 있으면 해당 PR의 저장소·base·head와 선언도 일치해야 한다.
- 일치가 확인된 PR 없는 원격 작업 branch는 정확히 관측한 원격 HEAD에서 관리 worktree와 새 DB 소유 상태를 구성하고 새 Worker 세션으로 이어간다. 기존 환경의 Worker 세션이나 실행 상태를 복원했다고 간주하지 않는다.
- 열린 PR이 있으면 기존 PR과 같은 head branch를 연결해 이어간다. 새 PR을 만들지 않는다. 같은 작업에 맞는 열린 PR이 여러 개이거나 repository·base·head·선언이 맞지 않으면 자동 인수하지 않고 보류한다.
- 기존 검증·Review 근거를 새 환경의 DB에서 확인할 수 없으면 Git commit, PR 존재 또는 외부 check 결과만으로 성공을 추정하지 않는다. 해당 작업에 필요한 targeted test, verify, Review를 정상 게이트에 따라 다시 수행한다.
- 같은 이름의 로컬 branch/worktree가 다른 소유권을 갖거나 작업물 충돌이 있으면 덮어쓰거나 재사용하지 않는다. 관리 소유권을 확정할 수 없는 원격 branch도 보존하고 보류한다.
- 사용자가 만든 branch를 별도 작성자 이력으로 추적하지 않는다. 다만 loop-manager/{G ID} 이름만으로 작업 소유권을 인정하지 않으며 위의 선언·저장소·base·원격 상태 대조를 적용한다.

### PR 상태별 재개와 완료

- Manager는 해당 저장소의 loop-manager/{G ID} head branch에 연결된 PR 이력을 모두 조회한다. 이력 조회가 실패하거나 일부만 확인된 상태에서는 PR이 없다고 추정해 새 branch나 PR을 만들지 않는다.
- PR 기록에서 baseRefName과 mergeCommit.oid를 확인할 수 있으면 함께 관측한다. mergeCommit.oid가 현재 등록 base의 조상인지 여부는 조사 정보일 뿐, 실제 MERGED 상태의 완료 판정을 바꾸지 않는다.
- GitHub에서 실제 MERGED 상태가 확인된 작업은 terminal 완료다. merge commit이 현재 등록 base branch의 조상인지 여부로 완료를 뒤집지 않으며 Worker를 재개하지 않는다. merge 후 원격 head branch가 자동 삭제된 것도 정상이다.
- MERGED 확인 후 Manager는 현재 등록 base와 catalog를 동기화하고 계획을 archive하며 의존 작업의 충족 상태를 반영한다. 이 동기화가 실패하면 완료 상태를 유지한 채 동기화만 재시도한다. 병합 뒤 남은 요구사항은 완료된 작업을 되살리지 않고 새 ExecPlan으로 만든다.
- MERGED PR이 없고 정확히 일치하는 열린 PR이 하나 있으면 기존 PR과 branch를 이어간다. 닫혔지만 병합되지 않은 PR만 있으면 작업을 보류한다. 같은 PR이 다시 열리거나 사용자가 명시적으로 재개·재시작을 결정하기 전에는 새 작업이나 대체 PR로 자동 전환하지 않는다. 새 작업으로 재시작하기로 결정하면 새 ExecPlan과 작업 ID를 사용하고 기존 PR 기록을 보존한다.
- PR의 상태가 Open·Closed·Merged로 판정되지 않거나 branch와 PR의 관계가 불명확하면 작업을 보류하고 근거를 보존한다. 상태가 불명확한 작업을 새 Worker 세션으로 실행하지 않는다.

### 환경 전환 경계

Loop Manager는 한 프로젝트를 서로 다른 환경에서 동시에 개발하는 것을 보장하지 않는다. 새 환경의 인수는 이전 환경의 Worker와 Git writer가 멈춘 순차 전환을 전제로 한다. 원격 OID·lease 검사는 예기치 않은 전진에서 작업물을 보호하지만 동시 실행을 지원하거나 조율하는 기능은 아니다.

## Acceptance Criteria

- Worker의 관리 branch 로컬 commit마다 Manager가 같은 원격 branch에 게시를 시도하고, 성공을 복구점으로 기록하며 verify·Review 성공으로 취급하지 않는다.
- 일시적 게시 실패는 로컬 commit을 보존한 대기로 남고, 원격 전진 시 관측한 OID와 소유권을 검사한다. 충돌 없는 안전한 통합은 원격 commit을 보존하며, 충돌·lease 재변경·불명확한 소유권에서는 어느 쪽 commit도 덮어쓰지 않는다.
- DB가 없는 새 환경은 일치하는 활성 작업 선언과 PR 없는 관리 원격 branch를 인수해 정확한 원격 HEAD의 관리 worktree와 새 Worker 세션을 구성할 수 있다. branch 이름만 일치하거나 대조 정보가 불일치하면 인수하지 않는다.
- 일치하는 열린 PR은 같은 branch와 PR로 연결되고 새 PR을 생성하지 않는다. DB에서 검증 근거를 확인할 수 없는 재개는 필요한 검증과 Review를 다시 수행한다.
- 해당 branch의 PR 이력을 모두 확인하고 실제 MERGED PR이 있으면 branch가 이미 삭제됐거나 merge commit이 현재 base의 조상이 아니어도 작업을 완료 처리한다. Worker를 시작하지 않고 base·catalog 동기화, 계획 archive와 dependency 반영을 수행한다.
- 닫혔지만 병합되지 않은 PR만 확인되는 경우 자동 재사용이나 새 PR 생성 없이 보류하며, 명시적인 처리 결정 전 기존 작업물과 PR 이력을 보존한다.
- 서로 다른 환경의 동시 실행을 지원한다고 표기하거나 자동 조율하지 않는다.

## Non-Goals

- 같은 프로젝트를 여러 환경에서 동시에 실행·조율하는 기능
- 손상된 DB의 자동 복구 또는 과거 DB 전체 상태·Worker 세션·검증 receipt의 복원
- 게시에 성공하지 못한 로컬 전용 commit의 새 환경 복구 보장
- 닫힌 PR을 자동 재시작하거나 새 ExecPlan·PR로 자동 대체하는 정책
