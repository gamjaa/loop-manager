# [R-061] Agent 역할·문서 권한과 draft ExecPlan 사용자 판단

## Summary

Planner·Worker·Reviewer의 저장소 접근과 문서 수정·PR 보고 책임을 정리한다. Worker는 선택된 ExecPlan 전체의 구현·교정을 완료하며, 중간 보존이 필요할 때만 Manager에게 checkpoint 생성을 요청한다. Git staging·commit·push는 직접 수행하지 않는다. Worker는 Requirement·다른 ExecPlan·선택 ExecPlan의 frontmatter를 수정하지 않으며 PR 문서 보고는 파일명·요약·이유·영향만 표시한다. 문서 보고에서 Worker는 경로·요약·이유·영향만 제출하고, 해시 계산·후보 결합·값 비교는 Manager 코드가 맡는다. 선택된 ExecPlan은 문서 보고·DOCUMENT_CHANGE 제출 대상에서 제외하되 기존 diff 검토·범위 검증은 유지한다. 문서 diff는 후보의 작업 base를 기준으로 하고, 최신 원격에만 있는 변경을 Worker 수정으로 오인하지 않으며 rebase 완료 뒤에만 통합된 base로 전환한다. 모호한 작업은 원격 draft로 게시하고, 사용자 본문 변경이나 User Decision의 출처·revision·현재 소유권을 검증해 결과를 본문에 통합하고 임시 판단 입력을 정리한다. 게시·DB 반영·감사·dependency를 보존하며 독립 작업은 계속한다.

## Context

Planner는 필요한 근거를 읽어 계획하고, Worker는 구현에 필요한 코드와 허용된 문서를 함께 수정하며, Reviewer는 관련 변경이 요청한 목표를 충족하는지 확인한다. 저장소를 읽을 수 있는 범위와 각 역할이 수정할 수 있는 범위를 구분한다.

현재 문서 보고는 Worker가 `patch_sha256`을 제출하도록 요구한다. G-332에서는 문서 설명이 있어도 모델이 해시 세 글자를 빠뜨려 보고 교정이 반복되고 차단됐다. 기계적으로 계산·검사할 값의 정확성을 모델의 생성·복사에 의존하지 않도록 책임을 분리한다.

G-329에서는 작업 브랜치에 반영되지 않은 최신 base와 작업 트리를 비교해 base에만 있는 문서 변경까지 설명 대상으로 잡았다. Worker가 확인한 작업 변경과 Manager의 보고 대상이 달라 설명 교정이 반복되고 차단됐다. 최신 원격 반영과 작업 변경 보고를 분리하고 양쪽이 같은 비교 기준을 사용해야 한다.

현재 draft 게시·판단 대기와 명시적 User Decision의 관측·감사는 구현돼 있다. 그러나 판단 대기 해제는 사용자의 draft 제거와 동일 판단 지문의 Decision/Revision/Answer를 함께 요구한다. 사용자 본문 변경으로 질문을 해소하는 흐름과 해소 후 임시 입력 정리를 보완하고, 개별 판단 대기가 프로젝트 전체 차단으로 확대되지 않게 한다.

이 Requirement의 역할 권한·사용자 판단 정책은 PRODUCT·ARCHITECTURE·공통 및 역할별 실행 지침·PLANS의 해당 제한을 갱신하는 기준이다. Planner 실행 조건과 Worker 문서 수정 범위는 R-082를 따르고 R-057의 변경 중심 검토·프로젝트 최종 확인은 유지한다. PR 문서 보고는 R-087의 파일명·요약·이유·영향 형식을 따른다. 정적 역할 권한은 R-064의 해당 역할 instruction과 실제 범위 검사에 함께 반영하며, 사용자 prompt만 고쳐 상위 권한 제한을 우회하지 않는다. 아래 변경 목표 전체가 구현 완료됐다는 뜻은 아니다.

## Requirement

### 역할별 접근과 작업 범위

| 역할 | 읽기 | 쓰기와 책임 |
|---|---|---|
| Planner | 프로젝트 저장소 전체를 읽을 수 있다. | 허용된 ExecPlan을 작성·개정하고 범위 밖 아이디어를 `docs/FUTURE_IDEAS.md`에 생성·수정할 수 있다. 설계·제품 문서·코드·설정·공통 및 역할 지침은 수정하지 않는다. |
| Worker | 프로젝트 저장소 전체를 읽을 수 있다. | 현재 작업에 필요한 저장소 작업 파일을 수정하되 Requirement·다른 ExecPlan·선택 ExecPlan의 frontmatter는 수정하지 않는다. |
| Reviewer | 프로젝트 저장소 전체를 읽을 수 있다. | 파일을 수정하지 않고 현재 작업에 관련된 문서·diff·기존 검증 결과를 중심으로 검토한다. |

전체 저장소 접근은 선택한 프로젝트의 관리 작업 공간을 기준으로 한다. 기본 checkout·다른 프로젝트·다른 작업 공간 또는 Manager의 실행 상태·Git 소유권을 변경할 권한으로 확대하지 않는다. 읽기 권한은 매 호출에서 모든 파일을 읽어야 한다는 뜻이 아니며, 관련 영향의 확인에 필요한 범위를 선택한다.

Planner의 기존 계획 개정은 Manager가 제공한 snapshot·mode와 R-082의 PR 전 개정 경계를 따른다. 미착수·무소유 계획의 개정을 우선하며 시작한 계획은 같은 ID·경로·작업물·수행 기록을 보존해 안전한 단계 경계에서 개정한다. 이름 변경·직접 삭제와 유지보수의 미착수·무소유 제한은 유지한다. 사용자 판단 대기 draft는 미실행·무소유가 확인된 대상만 개정하며 이미 실행한 계획을 draft로 돌리지 않는다. ExecPlan·코드·테스트·설정 변경 자체로 점검·일반 Planner를 호출하지 않고, 선택된 작업의 현재 구현 충족 판단과 필요한 보완은 Worker가 함께 수행한다. 선언·dependency·사용자 결정·검증 성공의 공식 반영은 기존 Manager 책임으로 유지한다.

일반 Planner는 현재 PRODUCT·Requirement 범위 밖이지만 보존 가치가 있는 아이디어를 `docs/FUTURE_IDEAS.md`에 생성·수정할 수 있다. 유지보수 Planner는 일반 계획 작성을 허용한 mode에서만 같은 권한을 가진다. 파일 삭제는 허용하지 않으며, 그 항목을 같은 계획 주기의 ExecPlan 범위나 현재 미충족 작업의 근거로 사용하거나 자동 승격하지 않는다.

파일 수정 권한과 제품 목표를 구분한다. Worker는 전체 완료 조건의 충족 근거·잔여 구현·미해결 실패를 본문에 갱신하고 기존 검증 실패를 우선 교정한다. 작은 변경의 테스트 통과만으로 호출을 끝내지 않으며 복구점 확보 등 중간 보존이 필요한 경우에만 이유·전진한 완료 조건·잔여 작업을 기록하고 checkpoint를 요청한다. 같은 잔여 항목의 반복은 원인·접근법 재평가 대상으로 삼으며 범위·정책 변경은 역할 권한에 따른 판단으로 연결한다. Worker는 합의된 목표와 현재 작업을 구현하기 위해 관련 문서를 수정할 수 있지만, 무관한 새 기능이나 다른 계획의 목표를 추가 구현하지 않는다. 별도 사용자 승인이 필요한 목표·Non-Goal·비가역 변경 등의 결정을 문서 수정으로 대신 승인하지 않는다. [R-093](%5BR-093%5D%20원격%20작업%20브랜치로%20새%20환경에서%20이어하기.md)에 따라 Worker는 checkpoint 생성 요청과 COMMIT_TITLE만 제공하며 Git add·commit·fetch·rebase·push·PR 조작은 직접 수행하지 않는다. Manager는 Worker 종료·허용 범위·index·소유권을 확인한 후 commit·게시를 전담한다. 이전 Worker 직접 commit 이력은 복구점으로 보존하고 신규 Git 쓰기 권한의 근거로 사용하지 않는다.

코드·설계·계획 변경 때문에 다른 문서의 경로·계약·dependency·구현·검증 설명도 달라져야 하면 Worker는 허용된 문서를 함께 갱신하고 변경 이유·영향을 남긴다. 직접 수정할 수 없는 Requirement·다른 ExecPlan·선택 ExecPlan 선언의 변경 필요성은 근거와 함께 보고한다. Planner는 영향받는 ExecPlan을 위 snapshot·PR 경계에서 개정하며 제품·설계 문서까지 수정하지 않는다. 다른 실행 작업·미해결 사용자 결정·기존 목표를 덮어쓰지 않고, 변경된 문서·구현·관계의 정합성을 검증한다.

### 모호한 계획의 draft 작성과 게시

- Planner가 설계·계획의 모호함이나 상충 때문에 구현 방향을 확정할 수 없으면, 확정된 목표·근거·범위와 미결정 사항을 기록한 draft ExecPlan을 작성한다. 임의의 가정을 확정 계획으로 만들거나 그 모호함만으로 프로젝트 planning 오류를 만들지 않는다.
- draft의 `Draft Decision`에는 `Question`, `Facts`, `Options`, `Impact` 형식을 유지해 사용자가 판단할 질문·확인한 사실·가능한 선택·작업 영향을 적는다. 여러 질문은 어떤 답변이 어느 질문을 해소하는지 식별할 수 있게 구분한다. 알 수 없는 구현 세부는 미결정으로 표시할 수 있지만 ID·sources·dependency 등 catalog 식별·연결 정보는 유효해야 한다.
- 계획 파일의 `draft: true`는 미실행 계획의 작성 준비도 선언으로 사용한다. 실행 phase·retry·session·workspace·PR 상태는 계속 SQLite가 관리한다. 기존 draft 표시가 없는 계획은 종전의 작업 가능한 계획으로 해석한다.
- Planner 종료 후 Manager는 유효한 draft를 해당 planning 주기의 다른 게시 대상 문서·계획과 함께 검증·push한다. 사용자 답변이나 Worker 실행까지 게시를 미루지 않는다. 다른 문서와 함께 게시한다는 이유로 Planner의 문서 수정 권한을 확대하거나 기본 checkout의 무관한 변경을 포함하지 않는다.
- 게시된 draft는 사용자 판단 대기로 등록하고 Worker 선택·workspace 예약·구현 branch·구현 PR 생성에서 제외한다. 독립적인 작업 가능 계획은 같은 planning 결과에서 정상 등록하고 계속 진행한다.
- draft 표시와 미결정 사항 자체는 `PROJECT_BLOCKED`·프로젝트 planning 오류의 원인이 아니다. 질문과 원격 계획 링크를 알려 사용자가 다른 환경에서도 판단할 수 있게 한다. 같은 미결정 입력의 반복 실행에서 같은 draft와 질문·알림을 중복 생성하지 않는다.

### 사용자 판단과 작업 가능 전환

사용자는 원격 Requirement 또는 ExecPlan 본문에 선택·정책을 명시하거나 명세를 명확히 하는 방법과 기존 `User Decision`을 입력하는 방법 중 편한 방법으로 판단을 전달한다. 본문 변경이 질문을 해소하면 사용자가 `draft`를 직접 제거하거나 별도 양식을 반복 작성할 필요가 없다.

`User Decision`의 `Decision`은 approve/reject/defer 등 결정, `Answer`는 구체적인 답변·선택, `Revision`은 판단 근거 확인에 사용한다. 기존 형식과 유효한 revision 검증은 유지한다. Manager가 사용자 변경과 질문·현재 판단 근거를 고유하게 연결할 수 있으면 revision을 직접 복사·재입력하도록 강제하지 않고 확인한 근거에 결합한다. 명시된 revision이 오래됐거나 근거 연결을 확정할 수 없으면 임의로 최신 승인으로 바꾸지 않는다.

Planner는 변경 전 질문과 최신 사용자 문서의 원격 revision·변경 내용을 비교해 질문별 해소 여부·답변 결과·남은 판단과 목표·완료 조건·구현 방향의 영향을 반환한다. Manager는 사용자 변경 주체·출처, 실제 원격 내용·판단 근거와 현재 계획 identity·상태·소유권·허용된 개정 범위를 확인한다. 원격에 있다는 사실이나 Agent의 추론·문서 수정만으로 승인을 만들 수 없다. 사용자 출처나 질문 해소를 확인할 수 없으면 대기로 보존한다.

Planner 입력에는 사용자 변경의 출처·revision과 문맥 diff를 제공하고, 변경 전후 문서 전문을 반복하지 않는다. catalog에는 질문·판단 identity만 두고 변경 근거는 별도 판단 문맥에 한 번 전달한다. Manager는 저장된 변경 전후 원문으로 인용·출처를 검증하며, 필요한 전체 원문은 Planner가 해당 원격 revision에서 조회한다.

| 판단 결과 | 문서·실행 처리 |
|---|---|
| 모든 질문의 유효한 해소 | 결정이 정한 제품 동작은 해당 ExecPlan 본문에, 기술 선택·이유는 필요한 Decision Log에 통합한다. 확인한 사용자 Requirement는 근거로 읽으며 Planner가 대신 수정하지 않는다. 해결된 Draft Decision의 질문·선택 설명과 User Decision 입력을 제거하고 빈 decision 전용 절을 정리한다. 같은 계획의 `draft: true`와 저장된 판단 대기를 해제한다. |
| 일부 질문만 해소 | 해소 결과를 본문에 통합하고 그 질문에 해당하는 임시 입력만 제거한다. 미해결 질문·필요한 사실·선택·영향과 draft 대기는 유지하며 ExecPlan을 부분 승인만으로 실행하지 않는다. |
| 거절·보류·불충분·상충 답변, 질문과 무관한 수정, 출처·근거 불확실 | 승인·실행을 만들지 않고 필요한 질문·입력·대기를 보존한다. 확인된 거절·보류·답변과 이유는 감사에 남기며 독립 작업은 계속한다. |

정리·대기 해제는 검증된 사용자 결정을 적용하는 Manager의 전환으로 수행한다. Planner·Worker가 `User Decision`을 대신 작성·변경하거나 근거 없이 소비·삭제할 권한으로 확대하지 않는다. R-069의 과거 파일 승인 이력 전환과도 구분한다. 필요한 문서 개정은 R-082의 안전한 게시 경계를 따르며 ID·sources·dependency·작업물·실행 및 실패 이력·유효한 기술 결정을 보존한다.

질문·사용자 원문과 변경 revision·변경 출처·질문별 판단·결정 근거·정리 및 전환 결과는 필요한 DB 감사에 보존한다. 이 근거를 보존한 뒤 문서 정리와 저장된 대기의 변경을 원격 게시 결과에 결합해 확정한다. 게시와 DB 반영 사이 중단은 기존 snapshot·revision·CAS·transaction·publication intent로 복구하고, 원격 게시 확인 전 실행 gate를 열지 않는다. 재시작·같은 변경 재처리에서 입력 양식을 복원하거나 같은 질문·승인을 다시 요구하지 않는다. 양식 제거가 기존 결정 근거의 상실이나 새 scope로 오인돼 대기를 재생성하지 않아야 한다.

질문에 답하지 않은 수정·시간 경과·draft 표시만 제거한 변경은 승인으로 해석하지 않는다. 이후 목표·선택·질문에 영향을 준 사용자 변경은 기존 결정이 여전히 유효한지 다시 판단하고 필요한 새 질문만 갱신한다. 아직 시작하지 않은 작업 가능 계획의 새 모호함은 허용된 개정 과정에서 draft로 전환할 수 있다. 질문·선택 영향·판단 근거·알림 링크는 같은 원격 입력을 가리키며 과거 질문에 최신 링크만 붙여 재통지하지 않는다. 원격 경쟁은 재관측·재검증하고 유효한 Manager 전환을 자기 승인 오류나 프로젝트 planning 오류로 확대하지 않는다.

작업 가능 전환 뒤에도 모든 `depends_on`의 MERGED 확인과 기존 실행 gate를 충족해야 Worker를 시작한다. draft에 직접·간접으로 의존하는 계획은 대기하지만 독립 계획과 다른 프로젝트를 막지 않는다. draft가 남아 있는 프로젝트는 사용자 판단 대기로 표시하고 완료로 처리하지 않는다. 관련 Requirement도 draft가 미완료로 남아 있으면 완료된 것으로 archive하지 않는다.

### Worker의 문서 수정과 PR 보고

- Worker는 구현에 필요한 PRODUCT·ARCHITECTURE·FUTURE_IDEAS·선택 ExecPlan 본문·공통 및 역할 지침·사용 안내·설정·테스트 등을 수정할 수 있다. R-082에 따라 활성·archive를 포함한 모든 Requirement의 추가·수정·삭제·rename·이동과 다른 ExecPlan·선택 ExecPlan frontmatter의 수정은 허용하지 않으며 archive 후보 지정도 예외가 아니다. 이 경계 안의 허용된 문서 수정을 경로 분류나 사용자 소유라는 이유만으로 범위 위반·작업 차단으로 처리하지 않는다.
- 문서 수정은 현재 작업의 목표와 구현에 맞게 이유·동작·설계·작업 기록·검증을 정합하게 유지하기 위한 것이다. 실패를 숨기려고 Acceptance Criteria를 바꾸거나 사용자 요청·필수 검증을 삭제해 성공으로 만들지 않는다. 선택 ExecPlan 본문의 기존 구현·검증·실행 이력과 유효한 사용자 결정을 보존한다.
- PR 본문의 문서 보고에는 R-087에 따라 선택된 ExecPlan을 제외한 실제 변경 문서별 파일명·변경 요약·이유·영향만 표시한다. 선택된 ExecPlan은 `DOCUMENT_CHANGE` 제출 대상에서도 제외하며 기존 diff 검토·범위 검증과 PR의 ExecPlan 링크·Purpose는 유지한다. 새 파일·삭제·이름 변경도 포함하며 파일명 목록이나 일반적인 구현 Summary만으로 대신하지 않는다. 문서 발췌·전체 patch·diff 링크·검증용 hash는 PR 본문에 넣지 않는다.
- Worker의 `DOCUMENT_CHANGE` 필수 입력은 `path`·`summary`·`reason`·`impact`로 한정한다. 해시·체크섬 등 기계적으로 결정되는 검증값을 모델에게 생성·복사·일치 판정하도록 요구하지 않는다. 역할 지침·호출 prompt·교정 메시지도 같은 계약을 사용한다.
- Manager 코드는 실제 최종 diff에서 보고 대상 경로를 확인하고, 보고를 얻은 후보의 문서별 patch와 base/head에 결합해 PR 본문을 완성한다. 해시가 필요하면 Manager가 직접 계산·보존·비교하며 모델이 제출한 값을 검증 근거로 사용하지 않는다. 이전 응답의 `patch_sha256`은 호환을 위해 무시하고, 값의 누락·오타·불일치만으로 Worker 교정이나 차단을 만들지 않는다.
- 문서 보고의 경로·patch·hash 검증은 해당 후보의 작업 base와 후보 HEAD를 기준으로 한다. Worker 결과 commit 전에는 같은 작업 base와 범위 확인·staging된 후보를 사용한다. 최신 원격 base가 전진해도 작업에 반영되기 전에는 비교 기준만 최신으로 바꾸지 않으며, base에만 있는 문서 추가·수정·삭제·rename을 Worker 변경이나 설명 누락으로 취급하지 않는다. Worker의 보고·교정 문맥과 Manager의 경로 수집·patch 결합·검증·새 PR 및 기존 PR 갱신은 같은 기준을 사용한다.
- 최신 base 통합 필요성은 별도로 판단하고, rebase가 완료된 뒤에만 통합된 대상 base와 새 후보 HEAD로 보고 기준을 전환한다. 진행 중 rebase는 최종 보고 확정 대상이 아니다. 작업 base 근거가 없으면 작업물·결과·진단을 보존해 복구하며 최신 원격이나 임의의 공통 조상으로 대체하지 않는다. 실제 문서 patch 변경·설명 누락의 교정과 필수 검증·Review·게시 조건은 유지한다.
- PR head·rebase·문서 변경과 재시작 뒤에도 Manager는 보존한 보고 근거와 현재 문서별 diff를 코드로 다시 비교한다. 실제 문서 patch가 같으면 SHA 변경만으로 설명을 다시 요구하지 않는다. 문서 patch가 달라졌거나 이전 후보와의 결합 근거가 없으면 현재 diff의 의미 설명을 보완하며, 과거 설명을 새 후보에 자동 승인하지 않는다. hash 제거를 오래된 설명의 무조건 재사용으로 대체하지 않는다.
- 누락·중복·형식 오류·최종 diff에 없는 경로와 실제 변경에 맞지 않는 설명은 해당 작업에서 보완한다. 코드가 판정할 값 비교와 모델의 의미 설명을 구분하며, 변경하지 않은 문서를 수정했다고 보고하거나 다른 작업의 중단 사유로 확대하지 않는다. 과거 해시 제출 오류의 차단은 작업물·session·실패 이력을 보존하고 현재 후보의 보고 조건으로 재평가한다. 다른 차단 사유까지 함께 해제하거나 전체 검증·Review 성공을 추정하지 않는다.

### CLI 지침과 개별 작업 대기

공통·역할별 `docs/AGENTS.*.md`는 R-064의 일반 작업 파일 권한과 PR 보고를 따른다. 작업 중 파일을 수정해도 고정된 원본 묶음과 현재 instruction은 바뀌지 않는다. 프로젝트 루트 `AGENTS.md`의 해석은 Agent CLI에 맡기며 R-066·R-069에 따라 별도 변경 제안·사전 승인·patch 대조·승인 대기를 요구하지 않는다. 과거 common·project 승인과 문서는 감사 이력으로 보존하고 현재 권한이나 적용 patch로 사용하지 않는다. Planner·Reviewer의 일반 쓰기 제한과 실행 중 runtime 편집 금지는 유지한다.

개별 작업의 일반 사용자 판단 대기·중단·차단은 그 작업물과 session을 보존하고 변경 실행 자리를 비운다. 문서 수정·계획의 draft 또는 해당 작업의 검증·Review 문제를 다른 계획의 계획 생성·실행·원격 관측과 다른 프로젝트의 중단 조건으로 전파하지 않는다. 과거 파일 승인 대기는 대상 내용을 재검사하거나 사용자 결정·문서를 자동 수정하지 않고 일반 작업·복구 흐름으로 전환하며, 다른 사용자 판단 대기와 독립 차단은 유지한다. 명시적인 dependency 대기와 실제 공유 저장소·소유권·안전 문제가 있는 경우는 별도로 판단하며, 앞의 개별 사유를 그런 프로젝트 안전 문제로 오인하지 않는다.

### Reviewer의 관련 변경 검토

Reviewer는 현재 작업의 목표·승인된 사용자 결정·근거 문서, 구현·문서 diff와 전달받은 검증 결과를 우선 확인한다. 변경 영향이 이어지는 관련 코드는 필요한 범위까지 읽을 수 있지만, 매 Review에서 저장소 전체 또는 무관한 문서 전문을 다시 검토하도록 요구하지 않는다.

Worker가 수정한 허용 문서도 검토 대상이다. 수정 전 요청과 목표, 수정 이유·새 문서·구현의 정합성 및 PR의 문서별 파일명·요약·이유·영향을 함께 확인한다. 허용된 문서 수정 자체를 blocking issue로 삼지 않고 실제 목표 불충족·회귀·잘못된 설계·검증 약화를 판단한다. Reviewer는 문서·코드를 수정하거나 테스트·전체 verify를 재실행하지 않으며 기존 Worker targeted test와 Manager 전체 verify 결과로 검토한다.

## Acceptance Criteria

- Worker는 관리 worktree에서 허용 파일만 수정하고 관련 targeted test를 수행한다. checkpoint 요청 후 Manager가 보호 문서·index·소유권을 검사해 staging·commit·게시한 뒤 같은 Worker 세션을 재개하며, Worker의 직접 Git add/commit/fetch/rebase/push/PR 및 shared metadata 쓰기는 허용하지 않는다.

- 일반·유지보수 Planner와 Reviewer는 저장소 전체를 읽을 수 있다. Planner는 허용된 ExecPlan을 작성·개정하고, 일반 Planner와 일반 계획 작성을 허용한 유지보수 mode는 `docs/FUTURE_IDEAS.md`도 생성·수정할 수 있다. FUTURE_IDEAS 삭제·자동 작업 승격과 제품·설계 문서 쓰기는 거부된다. ExecPlan·코드·테스트·설정 변경만으로 새 점검 Planner를 호출하지 않고 기존 읽기 전용 호출의 결과·감사는 보존한다.
- 설계·계획의 판단이 필요한 경우 유효한 draft에 목표·근거·질문·선택 영향을 기록하고 Planner 종료 시 다른 게시 대상과 함께 원격에 게시한다. 이 draft 때문에 독립 계획 batch를 거부하거나 프로젝트를 차단하지 않는다.
- draft에는 Worker·workspace 예약·구현 branch·PR을 시작하지 않는다. 기존 draft 표시 없는 계획은 정상 처리되고 draft 선언과 실제 실행 상태의 원본이 구분된다.
- Requirement만 명확해진 경우와 `draft: true`를 유지한 ExecPlan 본문 답변도 Planner의 질문별 영향 판단과 Manager의 사용자 출처·입력·상태 검증을 거쳐 같은 계획의 대기를 해제할 수 있다. 명시적 User Decision의 Decision/Answer/Revision 형식도 유지하며, 근거를 고유하게 확인할 수 있으면 revision 재입력을 강제하지 않는다. 명시된 stale revision·불충분 또는 상충 답변·Agent의 자기 승인·표시만 제거한 변경·무관한 변경·재시작은 승인으로 처리하지 않는다.
- 모든 질문 해소 뒤 제품 동작·설계 선택은 본문에 반영되고 해결된 Draft Decision·User Decision 입력과 빈 decision 절·draft 표시가 정리된다. ID·sources·dependency·유효한 기술 결정·실행 이력은 보존된다. 일부 해소에서는 해당 결과·입력만 정리하고 미해결 질문·draft 대기와 의존 작업 대기를 유지한다.
- 작은 사용자 답변을 포함한 대형 문서의 변경 전후 전문이 provider 입력 한도를 넘더라도, Planner 입력에는 변경 diff와 출처·revision만 전달한다. catalog에 같은 변경 근거가 중복되지 않으며 저장된 원문·사용자 인용 검증·판단 대기는 보존된다.
- 거절·보류·새 모호함·출처 불확실·원격 경쟁은 승인과 구분한다. 사용자 원문·출처·revision·질문별 판단·정리 및 전환 근거는 DB 감사에 남고 원격 게시와 상태 반영 사이 중단·재시작에도 복구된다. 정리로 scope 지문이 달라져도 확인된 동일 결정을 잃거나 양식·질문·승인 대기를 다시 만들지 않으며 실제 새 조건 변경은 재판단한다. 최신 문서 링크로 과거 질문을 재통지하지 않는다.
- draft 또는 개별 차단이 남아 있어도 독립 계획과 다른 프로젝트가 진행한다. 직접·간접 dependency 대기, 사용자 판단 대기 표시, 프로젝트 완료와 Requirement archive 조건은 유지된다.
- Worker가 현재 작업에 필요한 PRODUCT·ARCHITECTURE·FUTURE_IDEAS와 선택 ExecPlan 본문을 수정해도 경로 분류만으로 범위 위반·차단하지 않는다. 모든 Requirement·다른 ExecPlan·선택 ExecPlan frontmatter의 변경은 거부한다. 합의된 목표·필수 검증·다른 작업 상태와 사용자 변경을 보존한다.
- 지침 파일 변경에 별도 승인 양식을 요구하지 않으며, 과거 파일 승인·patch는 현재 실행 권한으로 사용하지 않는다. 기존 파일 승인 대기 전환에서도 일반 사용자 결정·독립 차단·작업물·session·감사를 보존한다.
- 코드·설계·계획 변경으로 함께 바뀌어야 하는 허용 문서는 Worker가 갱신하고, 직접 수정할 수 없는 문서의 변경 필요성은 보고한다. Planner는 영향받는 허용 대상 ExecPlan만 개정한다. 최종 문서의 경로·계약·dependency·검증 설명이 구현과 일치하며 관련성만으로 목표·승인·실행 권한을 확대하지 않는다.
- 선택된 ExecPlan을 제외한 모든 변경 문서의 파일명·요약·이유·영향만 최종 PR 문서 보고에서 확인할 수 있고 발췌·patch·diff 링크·hash는 포함하지 않는다. 선택된 ExecPlan의 `DOCUMENT_CHANGE`를 요구하지 않으며 기존 diff 검토·범위 검증과 PR의 ExecPlan 링크·Purpose는 유지한다. 추가·삭제·rename·rebase·PR head 갱신 뒤에도 보고 대상 문서의 실제 최종 diff·hash와 보고의 일치를 검증한다.
- 해시 없는 `DOCUMENT_CHANGE`와 기존 해시를 포함한 응답 모두 경로·요약·이유·영향이 유효하면 수용한다. G-332처럼 61자리 해시를 제출하거나 잘못된 값을 제출해도 그 값 때문에 교정·차단하지 않으며, 문서 설명 누락·중복·형식 오류·보고 대상 경로 불일치는 계속 검출한다.
- 보고를 얻은 후보와 최종 후보의 문서별 diff 결합·비교는 Manager 코드로 검증한다. 문서 patch가 동일한 rebase는 설명을 재사용하고, 실제 patch 변경이나 결합 근거 없는 과거 결과는 현재 설명을 보완한다. 게시 직전 경쟁·중단·재시작에서도 오래된 보고를 새 문서 변경의 근거로 사용하지 않는다.
- 작업 base 이후 원격 base에만 문서가 추가·수정·삭제·rename되고 작업 후보에는 코드와 선택 ExecPlan만 변경된 경우, 원격 전진 전후의 보고 대상은 동일하며 다른 문서의 `DOCUMENT_CHANGE`를 요구하거나 교정 횟수를 소비하지 않는다. Worker 결과 결합·검증·새 PR·기존 PR 갱신에서도 같은 결과를 확인한다.
- rebase 완료 뒤에는 통합된 대상 base와 새 후보로 검증하고, 실제 작업 문서의 추가·삭제·rename·patch 변경은 계속 검출한다. 문서 patch가 동일하면 설명을 재사용하며, rebase 중단·재시작이나 작업 base 근거 부재에서 최신 원격을 대용해 설명을 승인하거나 누락으로 차단하지 않는다.
- G-329와 같은 잘못된 base 비교의 기존 차단은 현재 작업 base와 후보로 재평가한다. 오탐 원인만 해소하고 작업물·session·실패 감사·독립 차단을 보존하며, 재평가만으로 전체 verify·Review·게시 성공을 기록하지 않는다.
- 기존 해시 제출 오류로 차단된 작업은 현재 보고 조건에 따라 재평가하고, 작업물·실패 감사와 무관한 차단·필수 검증을 보존한다. Worker 지침·prompt·보고 파서·교정 메시지·게시 검사가 모델에 검증값 제출이나 값 비교를 요구하지 않는다.
- Reviewer는 관련 문서·구현·문서 변경을 중심으로 읽기 전용 검토하고, 변경 전 목표와 변경 후 결과·PR 보고를 대조한다. 문서 수정만으로 FAIL하지 않으며 파일 쓰기·테스트 재실행을 수행하지 않는다.
- 게시·사용자 판단 반영·작업 가능 전환·PR 보고 갱신의 중단·재시작에서 같은 계획과 결정·작업물을 보존하고 중복 게시·알림·승인 적용을 방지한다.
- 역할 instruction·작업 prompt·계획 형식·catalog·범위 검사·PR 보고가 같은 정책으로 동작한다. 정적 역할 권한은 해당 지침 파일에 반영하고 사용자 prompt에 중복하지 않는다. 실행 이력·Git 쓰기·최종 검증·사용자 Merge의 기존 책임은 유지된다.

## Product Impact

- Planner는 ExecPlan을 작성하고 범위 밖 아이디어는 FUTURE_IDEAS에 보존한다. 모호한 계획은 원격에 게시한 draft로 사용자 판단을 기다린다.
- Worker는 현재 작업에 필요한 허용 문서와 선택 ExecPlan 본문을 갱신하며 사용자는 PR에서 문서별 요약·이유·영향을 확인할 수 있다.
- Reviewer는 관련 변경을 중심으로 검토하고 개별 판단 대기·차단은 독립 작업을 막지 않는다.

## Non-Goals

- Planner에 제품·설계·AGENTS 수정 권한을 주거나 사용자 판단을 Agent가 대신 승인하지 않는다.
- 저장소 쓰기 권한을 무관한 목표·외부 작업 공간·Manager 실행 상태 변경 권한으로 확대하지 않는다.
- dependency·일반 사용자 결정·실제 공유 안전 문제·최종 검증·사용자 Merge를 생략하지 않는다.
- 실행된 계획을 draft로 되돌려 기존 실패·실행 이력을 없애거나 draft를 구현 PR의 Draft 상태와 혼동하지 않는다.
- 같은 프로젝트의 병렬 변경 또는 새로운 외부 서비스를 추가하지 않는다.
