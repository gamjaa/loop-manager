# [R-076] 읽기 전용 운영 상태 조회 CLI

## Context

cron으로 실행되는 Loop Manager가 어디까지 진행됐고, 왜 멈췄으며, 어떤 조건에서 다시 진행되는지 로그를 뒤지지 않고 확인할 수 있어야 한다. 기존 SQLite에 저장된 실행·호출·검증·복구 정보를 읽는 CLI를 추가한다.

사전 검토 기준은 `5c1fb29b3c7b1ec1d05bca1dba5b53be4b7559e0`이다. 초안 작성 시 확인한 원격 `main`과 로컬 HEAD는 이 commit과 같으며 이후 변경은 없었다. 현재 `loop_manager.py`의 인자 파서에는 `status`, `explain`, `usage`가 없다. 구현 시작 시에도 최신 원격 변경과 같은 기능의 추가 여부를 다시 확인한다.

현재 CLI의 공통 진입 경로는 실행 잠금과 Git 기반 bootstrap·runtime 준비를 수행한다. 일반 DB 연결과 일부 Repository 생성자는 schema 초기화·migration을 수행하고, 실행 명령은 중단된 invocation을 정리한다. 조회 명령은 이 부수 효과를 일으키지 않아야 한다.

호출·사용량의 기본 집계는 `loop_manager_internal/storage/agent_invocation_state.py`의 `summary()`에 있고, 복구 판단은 `loop_manager_internal/recovery/recovery_runtime.py`가 소유한다. [R-073](%5BR-073%5D%20Invocation%20Purpose%20Usage%20Scope%20and%20Queries.md)의 호출 목적·실행 여부·사용량 범위 수집 확대와 기간별 분석은 별도 요구사항이다. 이 요구사항은 이미 저장된 정보의 조회를 제공하며 R-073 전체 구현을 선행 조건으로 삼지 않는다.

## Requirement

### 명령과 조회 범위

기존의 `--state-dir` 전역 옵션, repository 경로 인자와 ExecPlan ID를 사용한다. 작업의 식별자는 repository와 plan ID의 조합이며 제목이나 파일명으로 추측해 선택하지 않는다.

```text
python loop_manager.py [--state-dir <dir>] status [repository] [--plan <id>] [--json]
python loop_manager.py [--state-dir <dir>] explain <repository> --plan <id> [--json]
python loop_manager.py [--state-dir <dir>] usage <repository> [--plan <id>] [--json]
```

- `status`에서 repository를 생략하면 등록 프로젝트의 요약과 비종료 작업을 보여준다. repository를 지정하면 해당 프로젝트로 제한한다. `--plan`은 repository를 함께 지정해야 하며, 명시한 작업은 종료 상태여도 조회할 수 있다.
- `explain`은 해당 프로젝트의 특정 ExecPlan 하나를 설명한다.
- `usage`는 해당 프로젝트의 저장된 호출 전체를 집계하며, `--plan`이 있으면 그 계획에 연결된 호출만 집계한다. 계획 연결이 없는 Planner·유지보수 호출은 프로젝트 집계에 포함하고 특정 계획의 사용량으로 배분하지 않는다.
- 기본 출력은 사람이 읽기 쉬운 간결한 형식이다. `--json`은 같은 사실과 미확인·부분 수집의 의미를 기계가 읽을 수 있게 제공한다.

### status

프로젝트 요약과 작업별 항목에서 다음을 확인할 수 있어야 한다.

| 정보 | 표시 규칙 |
|---|---|
| 단계와 상태 | 저장된 프로젝트 phase와 ExecPlan status를 구분한다. 표시를 위해 기존 상태를 변경하거나 새 실행 상태를 저장하지 않는다. |
| 마지막 실제 진전 | 해당 작업의 실제 진전을 식별할 수 있는 저장된 사건의 시각과 출처를 표시한다. 근거가 없으면 미확인이다. |
| 대기·일시정지·실패 사유 | 기존 구조화된 사유와 복구 기록을 이용하고 관련 프로젝트 차단·planning 오류도 함께 표시한다. |
| 관련 대상 | 미충족 dependency의 ID와 저장된 상태, 연결된 PR URL과 저장된 관측값, 확인된 사용자 조치 대상을 표시한다. |
| 다음 진행 조건 | 기존 판단에서 확인되는 재시도·재검사·의존 작업 Merge·PR 처리·사용자 결정 등의 조건을 표시한다. |

프로세스 존재, 실제 작업 활동, 재개 가능성과 관측 신선도는 구분한다. 실행 잠금이나 미종료 invocation이 있다는 사실만으로 프로세스 생존이나 작업 진행을 확정하지 않는다. 프로세스가 종료됐다는 사실만으로 작업 실패를 확정하지 않는다. 관련 정보가 없으면 각각 미확인으로 표시한다.

사용량 제한에 따른 일시정지, 일시적 오류에 따른 재시도 대기, 사용자 판단 대기, dependency 대기, PR 대기를 구분한다. 프로젝트 차단과 개별 계획 차단도 구분하며 한 계획의 대기만으로 프로젝트 전체가 중단됐다고 표시하지 않는다. 여러 사유가 동시에 있으면 확인된 사유를 함께 보여준다. 구조화된 근거가 없는 legacy 오류 문구를 새로 해석해 사유를 확정하지 않는다.

### explain

`status`와 같은 정보를 바탕으로 특정 작업의 현재 상태를 상세히 설명한다.

- 마지막 단계 전환의 이전·이후 단계, 시각과 사유를 저장된 근거가 있는 범위에서 표시한다. 전환 이력이 없으면 현재 상태만으로 전환 이력을 만들지 않고 미확인으로 표시한다.
- 적용된 복구 disposition·pending action·원인 code·scope, 재시도와 반복 횟수, 최종 차단 근거와 남은 불확실성을 표시한다. 저장된 결정과 다음 실행에서 필요한 재판정을 구분한다.
- 현재 후보 commit·plan revision·검증된 base와 연결된 verify·Review 결과, 저장된 결과 식별자·지문·token·checkpoint 등의 기존 근거 식별자를 표시한다. 다른 후보나 입력에 대한 성공 결과를 현재 후보의 통과 근거로 사용하지 않는다.
- 자동 재시도 또는 조건 충족 후 재평가 대상인지, 무엇을 기다리는지, 필요한 사용자 행동과 실제 대상이 확인되는지 설명한다. 근거가 없으면 자동 재개 가능성이나 수정 대상을 추측하지 않는다.
- 진단은 필요한 요약과 기존 식별자로 제공한다. 인증 정보·비밀값·prompt·코드·문서 전문을 새로 출력하지 않고 기존 진단의 비밀값 제거 규칙을 따른다.

### usage

기존 `summary()`의 집계와 provider별 token 의미를 재사용한다. 작업 필터나 수집 누락 표시가 필요하면 기존 집계 경계를 확장하되 별도의 중복 집계 규칙을 만들지 않는다.

- provider·Model·역할별 호출 수와 재시도 수를 보여준다. 기존 집계가 구분하는 Effort와 session 전이도 보존한다.
- 기록된 input·cached input·cache write input·output·reasoning output token과 소요시간을 제공되는 범위에서 표시한다. token의 포함 관계를 보존하며 cache와 reasoning을 다시 더해 총량을 부풀리지 않는다.
- 각 사용량·시간 값은 알려진 부분 합계와 알려진 호출 수·미수집 호출 수를 함께 표시해 완전한 합계와 구분한다. 전부 미수집이면 미확인으로, 일부만 수집되면 부분 합계로 표시한다. 실제로 기록된 0은 미수집과 구분한다.
- 수집 상태와 진행 중·중단·실패 호출의 누락을 드러낸다. 호출 기록이 없는 정상 범위는 호출 0건으로 표시할 수 있지만 미수집 token·시간을 0으로 채우지 않는다.
- 현재 `summary()`의 호출 수는 ledger 행 수이고 재시도 수는 `attempt > 1`인 행 수다. 이 의미를 문서화하고 실제 모델 실행 또는 청구된 호출 수로 단정하지 않는다. 과거 기록에 실제 실행 여부·목적·범위 근거가 없으면 추측해 채우지 않는다. 이후 R-073에서 실행 여부가 구분돼도 해당 의미를 명시적으로 유지·구분한다.
- 금액 비용 계산과 예산 제한은 제공하지 않는다.

### 관측 시각과 정책 재사용

- 조회 시각과 정보의 저장된 관측 시각을 분리한다. 시각이 있는 관측값은 원본 출처와 관측 후 경과시간을 함께 확인할 수 있게 하고 시각이 없는 값은 시각 미확인으로 표시한다.
- 관측값이 오래됐다는 사실을 경과시간으로 드러낸다. 기존 정책에 유효기간이나 신선도 기준이 있으면 그대로 사용하고, 없으면 새로운 시간 기준으로 활동·실패·재개 여부를 판정하지 않는다. 조회 시각을 관측 시각으로 채우지 않는다.
- invocation 시작·종료, 단순 DB 갱신, 복구 재시도·오류 관측 시각을 그 자체만으로 마지막 실제 진전 시각으로 사용하지 않는다. 현재 데이터가 실제 진전을 증명하지 못하면 해당 값은 미확인으로 남긴다.
- SQLite에 저장된 PR·원격 OID·프로세스 관련 정보는 마지막 저장 관측값으로 표시한다. 조회 과정에서 GitHub나 provider를 호출해 실시간 상태를 보충하지 않는다.
- 다음 실행 시각, 사용량 제한 해제 시각과 재개 조건은 기존 데이터·정책으로 확인되는 범위만 표시한다. cron 주기나 provider 제한 reset 시각을 추측하지 않는다. 다음 외부 실행에서 재검사한다는 조건은 성공적으로 재개된다는 보장이 아니다.
- 기존 저장·상태 투영·작업 선택·알림 사유·복구·재시도 정책을 재사용한다. 저장된 결정을 우선하고 설명에 필요한 순수 판단은 실행 경로와 공유한다. 조회용 차단·해제·dependency·재시도 정책을 중복 구현하지 않는다. 조회에 필요한 원격 검증이나 상태 변경이 있으면 실행하지 않고 재검사 필요 또는 미확인으로 표시한다.

### 읽기 전용 실행과 오류 처리

- 세 명령은 에이전트·verify·runtime 자식을 시작하거나 작업을 재개하지 않는다. Git 명령, branch·worktree·PR 변경, 원격 조회, 알림 생성·전송, retry 기록·중단 invocation 정리, 작업 상태·관측·완료 기록 갱신을 하지 않는다.
- 조회는 실행 잠금·bootstrap·runtime 준비 및 실행용 초기화·migration 경로를 거치지 않는다. DB가 없는 경우 state directory나 빈 DB를 만들지 않는다.
- SQLite는 읽기 전용 연결을 기본으로 사용한다. schema 생성·migration·journal mode 변경·checkpoint를 하지 않는다. 플랫폼의 WAL·읽기 전용 연결 제약으로 안전하게 읽을 수 없으면 쓰기 연결로 전환하지 않고 조회 오류를 반환한다.
- 필수 table·column을 읽기만으로 검사한다. 지원하지 않는 schema는 migration하지 않고 명확한 오류로 종료한다. 지원 범위 안에서 선택 정보만 없으면 해당 값을 미확인으로 표시한다.
- 다른 Loop Manager가 실행 중이어도 같은 실행 잠금을 획득하지 않고 일관된 DB 읽기 snapshot을 조회한다. DB 잠금에는 유한한 대기 한도를 두고 한도 내에 읽을 수 없으면 오류를 반환한다. 여러 시점의 읽기를 섞어 하나의 확정 상태처럼 표현하지 않는다.
- DB 없음·손상·접근 불가, 알 수 없는 프로젝트·plan ID, 지원하지 않는 schema, 읽기 잠금 실패를 명확하게 구분한다. 조회 실패 때문에 복원·초기화·복구를 자동 수행하지 않는다.

### JSON·종료 코드와 문서화

`--json`의 stdout에는 JSON 문서 하나만 출력하며 운영 로그·장식 문자열을 섞지 않는다. 식별자와 사유 code는 안정적으로 제공하고, 알 수 없는 값은 `null`, 확인된 빈 목록은 `[]`, 실제 수집된 0은 숫자 `0`으로 구분한다. 수집 범위·미수집 개수와 경고를 보존하고 `null`의 이유를 확인할 수 있게 한다.

| 공통 JSON 필드 | 의미 |
|---|---|
| `schema_version` | CLI JSON 출력 계약의 버전. DB schema 버전과는 별개다. |
| `command` | `status`, `explain`, `usage` 중 실행한 조회 명령. |
| `queried_at` | 조회 시각. 저장된 정보의 관측 시각을 대신하지 않는다. |
| `repository`, `plan_id` | 요청한 조회 범위. 전체 프로젝트 또는 작업 필터 없음은 `null`이다. |
| `data` | 해당 명령의 조회 결과. 값별 관측 시각·출처, 미확인·부분 수집 의미를 포함한다. 조회 실패 시 `null`이다. |
| `warnings` | 읽기는 성공했으나 선택 정보 누락·낡은 관측·부분 수집 등으로 해석에 제한이 있는 경우의 설명. 없으면 빈 목록이다. |
| `error` | 정상 조회는 `null`. 실패는 기계 판독 가능한 code와 설명을 가진다. |

| 종료 코드 | 의미 |
|---|---|
| `0` | 조회 성공. 작업의 일시정지·차단·실패, 정상적인 빈 결과나 선택 정보 미확인은 조회 오류가 아니다. |
| `1` | 요청 범위를 조회할 수 없음. DB 없음·손상·접근 실패·잠금 실패·지원하지 않는 schema·알 수 없는 프로젝트 또는 plan ID를 포함한다. |
| `2` | 기존 인자 파서의 잘못된 명령·옵션·필수 인자 누락. |

코드 `1`의 오류는 JSON에서 `db_not_found`, `db_unreadable`, `db_busy`, `unsupported_schema`, `unknown_project`, `unknown_plan` 등 안정적인 원인 code로 구분한다. 인자 파서가 처리하는 코드 `2`는 기존 stderr 사용법 안내를 따르며 JSON 결과를 요구하지 않는다. 런타임 조회 오류는 `--json`에서도 공통 오류 계약을 따른다.

구현 문서에는 실제 명령·범위, JSON의 모든 필드·자료형·단위·nullable 의미와 버전 호환 규칙, token 포함 관계·집계 의미, 종료 코드·오류 code, 정상·미확인·부분 수집·오류 출력 예시를 기록한다. 완료 보고에는 변경 파일, 명령 사용 예시와 대표 출력, 실행한 검증과 남은 한계를 정리한다.

## Acceptance Criteria

- 최신 원격 코드에서 같은 기능의 추가 여부를 확인하고 기존 구현이 있으면 재사용한다. `status`, `explain`, `usage`의 도움말과 범위 선택이 기존 CLI 관례를 따른다.
- 사용량 제한 일시정지, 일시적 오류, 사용자 판단 대기, dependency 대기, PR 대기를 서로 다른 fixture로 확인한다. 프로젝트 차단·planning 오류와 독립 계획 대기도 구분하며 기본 출력과 JSON의 사실·사유·재개 조건이 일치한다.
- 단계·상태·마지막 실제 진전·다음 조건을 저장된 근거가 있는 범위에서 제공한다. 전환 이력·진전·프로세스 생존·관측 시각·재개 시각이 없는 경우 미확인이고, 오래된 관측의 시각·경과시간이 보인다. 프로세스 존재만으로 활동을 확정하지 않는다.
- `explain`은 저장된 복구 결정·횟수·사용자 대상과 후보·입력에 연결된 검증·Review·기존 근거 식별자를 보여준다. 다른 후보의 성공 결과와 단순 DB 갱신 시각을 현재 통과·실제 진전으로 표시하지 않는다.
- 프로젝트와 계획별 `usage`를 두 provider, 역할·Model·Effort·전이·재시도, 부분 token·시간, 전부 미수집, 기록된 0, 미종료·중단·실패 호출, 계획 연결 없는 호출과 빈 조회 범위로 검증한다. 기존 `summary()`의 집계·포함 관계와 결과가 일치하고 미수집은 가짜 0·완전한 합계가 되지 않는다.
- DB 없음, 알 수 없는 프로젝트·plan ID, 지원하지 않는 schema, 손상·접근 실패·읽기 잠금 실패의 메시지·오류 code·종료 코드를 확인한다. DB·디렉터리를 생성하거나 schema를 고치지 않는다. 지원하는 schema의 선택 정보 누락은 미확인으로 안전하게 처리한다.
- 각 명령의 정상·오류·JSON 경로에서 provider CLI·Git·원격 API·외부 변경 작업·알림 호출을 차단하는 fixture로 호출이 발생하지 않음을 확인한다. bootstrap·runtime 자식·에이전트·verify도 시작되지 않는다.
- 조회 전후 DB schema와 작업·복구·호출·검증·알림 기록이 같음을 확인한다. 재시도 횟수·중단 호출·outbox·완료 기록을 포함한다. 다른 실행 프로세스가 DB를 사용하는 상황에서는 조회가 실행 잠금을 변경하지 않고 일관된 snapshot을 읽거나 유한 시간 안에 조회 오류로 종료함을 확인한다.
- 정상·미확인·부분 수집·조회 오류에서 기본 출력과 JSON의 의미, JSON stdout 순수성, 문서화한 필드·자료형·단위와 종료 코드 계약을 확인한다.
- 실제 provider·모델을 호출하지 않는 관련 targeted unit test와 저장소에서 요구하는 전체 검증이 통과한다. 자동 검증 주체와 실행 범위는 docs/AGENTS.common.md와 해당 역할의 docs/AGENTS.*.md를, 프로젝트 규칙은 프로젝트 지침을, 계획 작성은 docs/PLANS.md를 따른다.

## Product Impact

- 운영자는 로그를 뒤지지 않고 저장된 진행·대기·실패 이유와 다음 조건을 확인할 수 있다.
- 운영 조회는 작업 실행·상태·기록·Git·PR·알림에 영향을 주지 않는다.
- 저장 관측과 실시간 상태, 프로세스 존재와 실제 진전, 미수집과 실제 0을 구분한다.
- 상태 설명과 실행 판단은 같은 기존 정책을 사용하며 조회를 위해 복구·재시도 정책을 바꾸지 않는다.

## Non-Goals

- 새로운 실행 엔진·데몬·상시 수집기, dashboard·TUI·MCP 서버를 추가하지 않는다.
- OpenRig의 daemon·tmux·TUI 구조나 새로운 활동 판정 체계를 도입하지 않는다. [activity-taxonomy](https://github.com/mvschwarz/openrig/blob/decf641773eacf5aa1a8ff84ed2408fbfd846bb6/packages/daemon/src/domain/activity-taxonomy.ts)는 프로세스 존재·활동·재개 가능성·관측 신선도를 구분하는 관점만 참고한다.
- 작업 재개·복구 실행·PR 처리·Git 동기화·실시간 원격 조회를 제공하지 않는다.
- 금액 비용 계산·예산 제한과 provider reset 시각·cron 실행 시각 추정을 추가하지 않는다.
- 전체 프로세스 재시작 테스트 체계, 알림 outbox 전송 정책 변경, 요구사항별 증거 체계를 추가하지 않는다.
- 복구·재시도·검증·작업 선택 정책이나 기존 사용자 동작의 의미를 변경하지 않는다.
- R-073의 수집 확대·기간별 분석 전체를 이 작업으로 구현하거나 과거 누락 정보를 추정·보충하지 않는다.
- 기존 사용자 변경을 덮어쓰지 않는다. 커밋·푸시는 별도 요청 없이는 수행하지 않는다.
