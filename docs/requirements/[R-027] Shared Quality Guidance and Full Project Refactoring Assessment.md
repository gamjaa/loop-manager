# [R-027] Shared Quality Guidance and Full Project Refactoring Assessment

## Context

현재 공통 `AGENTS.md`는 구현 중 필요한 국소 리팩터링과 명백한 책임 혼합의 Review를 요구하고, Loop Manager는 Merge된 ExecPlan 수를 기준으로 코드 구조를 주기적으로 평가한다. 그러나 이 Loop Manager 저장소의 기존 코드·문서는 한 번 전수 점검할 필요가 있고, Worker·Planner prompt에 불필요한 코드·문서 증가를 피하는 구체적 기준은 부족하다. 이미 등록된 프로젝트의 `AGENTS.md`는 공통 원본 변경이 자동 배포되지 않으므로 원본 파일만 바꿔도 모든 프로젝트에 적용되지 않는다.

[DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)은 기존 코드·표준 라이브러리 재사용, 불필요한 추상화 회피와 작은 검증을 강조하므로 코드 비대화를 줄이는 기준으로 적합하다. [ayghri/i-have-adhd](https://github.com/ayghri/i-have-adhd/blob/main/skills/i-have-adhd/SKILL.md)는 주로 에이전트 응답을 행동 중심으로 정리하는 규칙이다. 문서의 가독성에는 일부 도움이 되지만 필수 조건과 실패 흐름을 생략하거나 모든 명세를 짧은 목록으로 강제하는 근거는 되지 않는다. 두 스킬의 설치·호출은 provider와 환경에 따라 달라지므로 Loop Manager의 공통 동작은 특정 외부 스킬 설치 여부에 의존하지 않아야 한다.

현재 공통 `AGENTS.md`는 PRODUCT·Requirement·ARCHITECTURE를 사용자 소유 문서로 두고 대화형 Specification Skill 요청 외의 AI 수정을 제한한다. 사용자는 이번 변경에서 명세 문서의 구조 리팩터링을 자동으로 준비하고 PR에서 검토하는 예외를 선택했다. 이 예외를 적용하기 전에 공통 guidance의 사용자 승인 절차를 거쳐 허용 범위를 명시해야 한다.

## Requirement

Loop Manager는 모든 등록 프로젝트의 코드 작성·Review와 문서 작성·평가에 공통 품질 기준을 적용해야 한다. 코드 변경 전에는 기존 구현과 표준 도구의 재사용 가능성을 확인하고, 현재 목표에 필요하지 않은 추상화·설정·파일 추가를 피한다. 간결화 때문에 검증, 오류 처리, 보안, 접근성 또는 명시된 요구사항을 빠뜨리지 않는다. 문서는 PRODUCT·Requirement·ARCHITECTURE의 역할을 유지하면서 중복·장황한 표현을 줄이고 결정, 예외, 실패 흐름과 Acceptance Criteria의 의미를 보존한다. 행동 지향적 제목과 간결한 문장을 사용할 수 있지만 문서 완전성보다 짧음을 우선하지 않는다.

이 공통 기준은 Loop Manager의 provider 중립 prompt와 Review 계약에 포함해 기존 등록 프로젝트에도 적용하고, 신규 프로젝트에 복사되는 대화형 Specification Skill 지침에도 문서 가독성 기준을 반영한다. 외부 스킬이 안전하게 사용 가능한 환경에서는 해당 스킬을 활용할 수 있으나, 없어도 동일한 핵심 기준이 동작해야 한다. 특정 버전의 외부 스킬을 설치·실행하는 것을 프로젝트의 필수 조건으로 만들지 않는다.

이번 전수 평가는 Loop Manager 저장소 자체의 현재 코드·테스트·제품 문서에 한 번만 수행한다. 다른 등록 프로젝트에는 이 변경을 이유로 등록 시 또는 이후의 일회성 전수 평가를 추가하지 않는다. 기존 주기적 코드 리팩터링 정책은 이 Requirement에서 변경하지 않는다. Loop Manager 저장소의 전수 평가에서는 실제 중복, 책임 혼합, 과도한 크기·결합, 문서의 중복·모순·찾기 어려운 정보와 현재 계획의 중복 개선 범위를 확인한다. 단순 줄 수, 파일 수 또는 스킬의 일반 원칙만으로 변경을 강제하지 않는다. 개선 효과가 확인된 코드 범위는 평가 결과만 기록하고 끝내지 않고, 동작 보존 리팩터링을 독립적으로 검증·Merge 가능한 ExecPlan으로 계획해 기존 Worker·verify·Review·PR 흐름으로 구현한다. 문서 개선은 별도의 의미 보존 ExecPlan으로 계획한다. 현재 활성 작업과 PR은 선점하지 않는다. 개선할 내용이 없으면 평가 완료를 기록하고 반복 평가하지 않는다.

명세 문서 리팩터링 ExecPlan은 표현·구조·중복 정리에 한정한다. Worker가 자동으로 문서 변경을 준비하되 기존 사용자 동작, 정책 결정, Acceptance Criteria, 문서 소유 관계와 이력의 의미를 유지해야 한다. 별도 구현 PR에 초안을 포함하고 Reviewer가 의미 보존과 문서 역할을 검토하며, 사용자가 PR을 Merge해야 반영된다. 정책 선택이나 제품 동작 변경이 필요한 발견은 자동 리팩터링에 넣지 않고 별도 Requirement와 사용자 결정으로 보낸다. 비종료 ExecPlan이 근거로 사용하는 문서는 조사 결과에 포함하되 해당 계획과 안전하게 재검증할 수 있기 전에는 자동 수정하지 않는다.

이 자동 문서 변경 권한은 공통 `AGENTS.md`의 명시적 예외가 기존 guidance 승인 흐름에 따라 승인·반영된 뒤에만 활성화한다. 기존 등록 프로젝트에 복사된 `AGENTS.md`도 자동 덮어쓰지 않는다. 문서 리팩터링을 시작하기 전에 각 프로젝트에서 같은 예외를 승인된 guidance 변경으로 반영해야 하며, 승인되지 않은 프로젝트에서 문서 리팩터링 작업이 계획되면 읽기 전용 평가와 수정 제안만 수행한다.

## Acceptance Criteria

- Worker와 Reviewer가 기존 코드·표준 도구 재사용, 필요한 최소 구조와 회귀 검증을 공통 기준으로 적용하며, provider나 등록 시점에 따라 적용 여부가 달라지지 않는다.
- Planner와 문서 검토가 간결성뿐 아니라 누락된 결정, 실패 흐름, 문서 역할과 Acceptance Criteria의 보존을 함께 확인한다.
- ponytail 또는 i-have-adhd 설치가 없어도 공통 기준이 적용되며, 스킬 호출이 실패해도 작업 전체가 실패하지 않는다.
- Loop Manager 저장소에서만 현재 코드·테스트와 활성 제품 문서를 한 번 전수 평가한다. 생성물·의존성·archive는 대상에서 제외하고, 중단 후에도 평가 결과와 남은 작업을 추적한다.
- 다른 등록 프로젝트에는 일회성 전수 평가를 새로 실행하지 않고, 기존 주기적 평가의 실행 조건을 변경하지 않는다.
- 구조 문제가 확인되지 않으면 파일이나 ExecPlan을 만들지 않고 평가를 완료한다.
- 전수 평가에서 코드 개선이 필요하다고 확인된 범위는 누락 없이 실행 가능한 리팩터링 ExecPlan으로 나누어 실제 코드 변경과 검증·Review·PR까지 진행하며, 기존 주기적 리팩터링의 dependency 및 작업 선택 절차를 재사용하고 이미 계획된 개선을 중복하지 않는다.
- 문서 개선이 필요하면 의미 보존 전용 ExecPlan과 별도 PR을 만들고, 사용자 Merge 전에는 원격 기본 branch의 제품 명세를 바꾸지 않는다.
- 문서 PR의 Review가 PRODUCT·Requirement·ARCHITECTURE 간 역할, 기존 동작·결정과 Acceptance Criteria 보존을 확인한다. 의미 보존을 증명할 수 없으면 게시하지 않고 사용자 결정을 요청한다.
- 공통 및 대상 프로젝트의 `AGENTS.md`에서 문서 자동 수정 예외가 승인되기 전에는 Worker가 해당 문서를 수정하지 않는다. 승인 후에도 명시된 문서 리팩터링 ExecPlan 밖에서는 기존 수정 제한을 유지한다.
- Loop Manager 저장소에서 비종료 계획이 근거로 사용하는 문서는 전수 평가 대상이지만 계획의 목표·source 관계를 안전하게 재검증하기 전에는 자동 수정하지 않는다.
- 활성 Worker, PR_OPEN, `PLAN_BLOCKED`, `PROJECT_BLOCKED` 및 기존 유지보수 장벽의 실행·소유권 규칙을 우회하지 않는다.

## Product Impact

- 모든 프로젝트가 새 코드·문서를 작성하고 검토할 때 같은 간결성 기준을 적용받는다.
- Loop Manager 저장소의 기존 코드·문서는 한 번 전수 평가하고 필요한 리팩터링을 PR로 제안한다. 다른 프로젝트는 기존 유지보수 평가 주기를 따른다.

## Non-Goals

- 외부 스킬 또는 새 서비스를 모든 프로젝트에 강제 설치하지 않는다.
- 짧은 코드·문서를 위해 필요한 검증과 제품 결정을 제거하지 않는다.
- 사용자 동작·정책·데이터 형식을 문서 리팩터링 PR에서 바꾸지 않는다.
- 사용자의 PR Merge 없이 문서 변경을 확정하지 않는다.
- 승인되지 않은 공통 `AGENTS.md` 변경을 자동 적용하지 않는다.
- 다른 등록 프로젝트에 일회성 코드·문서 전수 평가를 추가하지 않는다.
